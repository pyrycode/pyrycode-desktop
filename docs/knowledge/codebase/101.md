# #101 — Pairing fingerprint digest that works under Electron's BoringSSL (BLAKE2s via `@noble/hashes`)

**Shipped:** 2026-07-07 · **Size:** S · **Scope:** one production file (`src/main/pairingConfirmation.ts`) + one **new runtime dependency** (`@noble/hashes`) + one **new build/QA script** (`scripts/electron-digest-check.mjs`). **No renderer/preload change, no IPC/shared-type change, no wire-type drift.** The fingerprint is a **security primitive**, so the architect ran a full in-spec security review (verdict **PASS**).
**Spec:** `docs/specs/architecture/101-pairing-fingerprint-boringssl-digest.md` · **PR:** [#103](https://github.com/pyrycode/pyrycode-desktop/pull/103). A pure **digest-mechanism swap** on the [#53](53.md) fingerprint-confirm gate — surfaced by the [#93](https://github.com/pyrycode/pyrycode-desktop/issues/93) e2e, the first automated test to drive the built app's pairing UI in the real Electron runtime.

Fixes a **completely-broken-in-the-built-app** bug: [`deriveFingerprint`](../features/pairing-confirmation.md) computed the server-key fingerprint with `node:crypto` `createHash('blake2s256')`. **Node ships OpenSSL (has `blake2s256`); Electron ships BoringSSL, which has no BLAKE2 family at all**, so that call threw `Error: Digest method not supported` in the real app. The throw escaped `ipcMain.handle`, the `pyry:pairing` invoke rejected, and the renderer wedged **forever** in `submitting` (the fingerprint card is never reached). vitest passed only because it runs under full-OpenSSL Node — the code had never executed in Electron until the #93 e2e drove it. Swapping the digest to a **pure-JS, synchronous** BLAKE2s (`@noble/hashes`) computes byte-identical output under **both** runtimes and keeps `deriveFingerprint`/`prepare` synchronous. See the [pairing-confirmation feature doc](../features/pairing-confirmation.md) (updated) for the evergreen contract.

## Why this fix, not the alternatives (spike result)

The ticket flagged the digest mechanism as a spike. Three candidates, only one works:

- **`noise-c.wasm` exposes no standalone hash.** The handshake already gets BLAKE2s through it, but the wrapper surfaces only `HandshakeState`/`CipherState`/`CreateKeyPair`/constants (`noise-c.wasm.d.ts`); `GetHandshakeHash()` hashes a handshake *transcript*, not arbitrary 32 bytes. Reaching Emscripten internals for a raw hash is undeclared, fragile, and — via `loadNoiseLib()` — **async and memoized**, which would ripple `prepare` from sync to async through `pairingHandler.ts` and every test.
- **WebCrypto (`crypto.subtle`) has no BLAKE2** either — SHA family only.
- **`@noble/hashes` (chosen)** — audited, zero-dependency, **pure JS**: it never calls `node:crypto`/BoringSSL, so it computes the identical BLAKE2s-256 bytes under vitest/Node **and** Electron, and it is **synchronous**, so the async ripple vanishes. This satisfies CLAUDE.md's "never hand-roll crypto" (a vetted library, same rationale as `noise-c.wasm`) and "don't add dependencies without justification" (BoringSSL lacks BLAKE2; the wasm exposes no standalone hash; WebCrypto has no BLAKE2; hand-rolling is disallowed — a dependency is unavoidable).

## Patterns established

- **A pure-JS crypto primitive is runtime-independent by construction — that's the whole fix.** The BoringSSL divergence exists *because* `node:crypto` delegates to whatever native TLS library the runtime links (OpenSSL under Node, BoringSSL under Electron). A pure-JS implementation has **no native backend to diverge**, so its output is identical everywhere. When a hash/HMAC/KDF must produce the same bytes under both `npm test` (Node) and the built Electron app, reach for the pure-JS library, not `node:crypto` — the reusable rule this bug teaches for anything in `src/main/` that isn't already covered by the Noise wasm.
- **Choosing the right primitive can *eliminate* a failure mode rather than defend it.** AC4 required the digest to *return a typed reason rather than throw*. The single targeted `try/catch` around `blake2s(...)` satisfies it — but because `@noble/hashes` on a validated 32-byte input is deterministic pure computation with no environment dependency, that catch is **effectively unreachable**. This shaped the reason-mapping decision (below): the distinct operator-facing reason the ticket floated would describe a branch that cannot fire. *Evidence-Based Fix Selection* in action — don't ship UX for an unobservable path.
- **Guard only the newly-fallible line, keep the existing typed reasons intact.** The `try/catch` wraps **only** the `blake2s(...)` call; the base64-canonicality and 32-byte-length guards keep returning their existing typed reasons. A blanket try/catch around all of `deriveFingerprint` would have muddied which failure produced which reason. The wedge then closes through the **existing** typed path with **no other production change**: `fingerprint-unavailable` → `deriveFingerprint` returns `{ ok:false }` → `prepare` returns `reject(reason)` (an `ok:false` `PreparedPairing` with **no `confirm` handle**, structurally unpersistable) → the handler's existing `if (!prepared.ok) return { …'invalid-key' }` (`pairingHandler.ts:87`) fires → reducer moves `submitting → editing`. The ticket's deferred generic `parse`/`prepare`/`runSubmit` guards stayed deferred — the typed path absorbs the throw without them.
- **An AC that vitest structurally cannot satisfy needs a runtime-specific gate, honestly scoped.** vitest runs under full-OpenSSL Node and **cannot** catch a BoringSSL divergence, so a vitest-only test would give false confidence. `scripts/electron-digest-check.mjs` runs the *same* derive+format under `ELECTRON_RUN_AS_NODE=1 electron` and pins the daemon vector. The coverage split is stated plainly: the **vitest parity test** proves value-correctness (AC2); the **Electron check** proves the primitive is BoringSSL-safe and reproduces the daemon vector in-runtime (AC3). Neither alone covers "correct bytes in the real app."
- **Cross-repo byte-parity is pinned by literal vectors, doubled as a canary.** The existing `32:0b:5e:a9:9e:65:3b:c2` (zero key) vector stays green under the new digest — the byte-identity oracle for AC2 and the acceptance oracle for whether the installed `@noble` API matches (see Lessons). A **second** non-zero vector (`05:82:56:07:d7:fd:f2:d8`, the 0..31 byte sequence) was added following the `noiseSession.test.ts` golden-vector precedent, so a subverted-or-mismatched hash impl fails loudly on two independent inputs, not one.
- **A distinct-but-coincidental width gets its own named constant.** `DIGEST_BYTES = 32` (the `dkLen` requested from `@noble`) is named separately from `PUBKEY_BYTES = 32` so the two 32s at the call site don't read as one — a future edit to one can't silently move the other. The load-bearing `FINGERPRINT_BYTES = 8` (64-bit truncation) is unchanged and still carries its don't-narrow/don't-widen rationale in-code.

## Reason mapping — collapse to `invalid-key`, do NOT add a shared reason

The ticket floated surfacing a *distinct* crossing reason (`fingerprint-unavailable` in `src/shared/ipc/pairing.ts`) so a crypto failure wouldn't tell the operator to re-paste a good key — a design call, not a mandate. **Decision: no distinct shared reason; keep the handler's existing collapse of every `FingerprintRejectReason → 'invalid-key'`.** Rationale (*Evidence-Based Fix Selection* + *Simplicity First*):

1. Choosing pure-JS `@noble/hashes` **eliminates the failure mode** the distinct reason describes — the digest cannot fail for a validated 32-byte key — so a distinct operator message would defend an unobservable path.
2. `PairingErrorReason` is consumed by `PairingScreen.tsx`'s **exhaustive** `Record<PairingErrorReason, string>`; adding a member forces a renderer copy edit → a **4th production file** (the ticket's own split trigger) for a branch that cannot fire.
3. Security-safe regardless: on any derive failure there is no `confirm` handle and no fingerprint is shown, so the confirm-gate holds whichever value-free reason surfaces; `invalid-key` is already value-free, satisfying AC4's "surfaces as a value-free `PairingErrorReason`."

The typed `fingerprint-unavailable` still exists at the **main-only** `FingerprintRejectReason` layer to satisfy AC4's structural "returns a typed reason, does not throw" — it just never gets its own *crossing* reason. Per the ticket's guidance, the chosen mechanism does **not** reintroduce a throw the typed path can't absorb, so **no route-back was warranted**. If a future digest swap ever reintroduces a genuinely reachable runtime-failure mode, add the distinct crossing reason then — not now.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **`@noble/hashes@1.8.0` (resolved from `^1.7.1`/`^1.8.0`) has deprecated the `@noble/hashes/blake2s` subpath in favor of `@noble/hashes/blake2`** — both re-export the same `blake2s`, byte-identical. The code imports from `/blake2` to avoid shipping a JSDoc-`@deprecated` import in new code. The spec had anticipated exactly this as the "installed API differs, developer adjusts the import" case, and it was caught cheaply: **the parity vector is the acceptance oracle** — if the resolved API had differed in behavior (not just path), `32:0b:5e:a9:9e:65:3b:c2` would have failed loudly. External docs are unavailable in this environment, so pinning-plus-a-golden-vector is the substitute for reading a changelog.

**Root-cause lesson (the reason this ticket existed):** *A test suite that runs under a different crypto runtime than the shipped app cannot catch a runtime-specific crypto divergence.* vitest under full-OpenSSL Node made `createHash('blake2s256')` pass for the entire life of the #53 fingerprint code; the bug was latent until the #93 e2e ran it under Electron. Any `node:crypto` call in `src/main/` whose algorithm isn't in BoringSSL's set (BLAKE2 family, and audit anything exotic) is a latent Electron-only throw that green vitest will never surface — the `check:electron-digest` script is the general shape of the guard. See the [`electron-boringssl-no-blake2`] gotcha carried in session memory.

No React re-render / effect-cleanup surprises — a pure main-process service, no React, no timers, no listeners; `prepare` stays synchronous and total, `confirm` a single `await store.save`.

## Testing

- **Parity vectors (AC2) exercise the real `blake2s`.** The `@noble/hashes/blake2` mock calls through to the genuine hash by default, so the pinned `32:0b:5e:a9:9e:65:3b:c2` (zero key) and the new `05:82:56:07:d7:fd:f2:d8` (0..31 bytes) vectors are true byte-identity assertions against the daemon's `internal/pair.Fingerprint`, not tautologies. Determinism/field-independence (same key → same fingerprint; token/server don't affect it) stays green.
- **`fingerprint-unavailable` — no throw, no confirm, no save (AC4).** `mockImplementationOnce` forces one digest throw; `prepare(RECORD)` returns `{ ok:false, reason:'fingerprint-unavailable' }`, exposes **no** `confirm`, and calls `store.save` **zero** times — mirroring the malformed-key reject assertions. Proves the digest step absorbs a throw into the typed path instead of escaping `ipcMain.handle`.
- **Log-free preserved across the new path (AC5).** The six-method console-spy assertion now also drives the digest-failure path under the mock and asserts no `console.*` — the catch returns the static value-free reason only, never the caught error's message.
- **AC3 — the Electron runtime check** (`npm run check:electron-digest`) is the criterion vitest cannot meet: under `ELECTRON_RUN_AS_NODE=1 electron` it documents that `createHash('blake2s256')` throws and reproduces the daemon vector via `@noble/hashes`. Exits non-zero on mismatch or any throw.
- **No handler/shared/renderer test changes** — the collapse decision leaves `pairingHandler.ts`, `pairing.ts`, and `PairingScreen.tsx` untouched, so their tests are unaffected.

## Deferred / carried forward

- **The #93 e2e stays #93's.** `e2e/pair-to-conversation.spec.ts` lives only on the unmerged `feature/93` branch — **not** on `main`, not in this worktree. Editing it here would collide at merge. Ownership: once #101 merges, #93 does `git merge main` (picking up the fixed digest) and un-`fixme`s its own e2e as part of *its* remaining work. #101 used the sanctioned `ELECTRON_RUN_AS_NODE=1 electron` alternative from AC3 instead.
- **Generic handler/`runSubmit` guards remain deferred** (ticket non-goal) — the typed path closes the observed wedge without them. Add them only if a future change reintroduces a throw the typed-reason path can't absorb.
