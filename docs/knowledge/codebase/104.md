# #104 — fakeRelayForwarder "socket hang up": deterministic dial-lifecycle hardening

**Shipped:** 2026-07-07 · **Size:** S (arguably XS) · **Labels:** `bug` (test flake; **not** `security-sensitive` — the change is confined to the test's own dial helper, the content-blind forwarder module is untouched) · **Scope:** one file, `src/main/transport/fakeRelayForwarder.test.ts` (+37/−6). **No production `src/` change**, **no forwarder-module change**, no new export, no new dependency, no wire-type drift, no consumer cascade.
**Spec:** `docs/specs/architecture/104-fake-relay-forwarder-flaky-dial.md` · **PR:** opened by the dispatcher on `feature/104` after this doc lands. Fixes the pre-existing flake tracked while QA-ing PR #103 (the #101 BLAKE2s swap) — see [#90](90.md) for the module this test drives.

Removes a false "regression" signal at its source. The `fakeRelayForwarder` byte-identical round-trip test intermittently failed with `Error: socket hang up` under full-suite CPU contention (passing in isolation and on re-run). Because the baseline suite runs all-green, a single-shot pre/post QA partition mislabelled whichever PR happened to trip it as introducing a regression, forcing hand-triage on every future PR. This is a pre-existing flake on `main`, not caused by any PR.

## Root cause

`"socket hang up"` is Node's `ECONNRESET`-during-handshake — a **pre-open dial reset**. One of the test's two raw `ws` dials (`/v1/client`, `/v1/server`) has its TCP/upgrade connection reset **before the 101 arrives**, surfacing as a rejected `await connect(...)`. The evidence that pins it to the dial (not the frame exchange): a reset *during* the exchange would leave `nextFrame(...)` unresolved and fail with vitest's 5000ms timeout, not `"socket hang up"`; and the old `connect()`'s persistent `on('error', reject)` made a *post*-open error a harmless no-op, so the only path from `"socket hang up"` to a red test is a pre-open reject.

Why only under full-suite concurrency, and why always the **first** test: six transport test files each churn ephemeral-port `WebSocketServer`s at once, and vitest starts every file's first `it` at roughly the same wall-clock moment across workers → peak loopback ephemeral-port/accept-queue pressure lands exactly on the byte-identical test (source-order first). Isolation and re-runs pass because that contention has dispersed. This matches the spike hypothesis in the spec; no forwarder-side mid-upgrade `terminate` or duplicate-leg refusal was found, so the retry (below) is the right tool rather than a module-side fix.

## What shipped

| File | Change | Role |
|---|---|---|
| `src/main/transport/fakeRelayForwarder.test.ts` | mod | `connect(url, attemptsLeft = 5)` now re-dials a **pre-open transient reset** against the already-listening server; a new `isTransientDialError(err)` predicate classifies the transient set. |

- **`isTransientDialError(err)`** — `err.code === 'ECONNRESET' || err.code === 'ECONNREFUSED' || /socket hang up/i.test(err.message)`. `ECONNREFUSED` is the loopback accept-backlog-overflow variant of the same transient (and also the benign "fresh dial refused after close" case, which simply exhausts attempts and rejects).
- **`connect()` dial lifecycle** — on a pre-open `'error'`: `terminate()` the half-open socket, then if `attemptsLeft > 1` and the error is transient, re-dial after a fixed ~20ms backoff (`setTimeout(() => resolve(connect(url, attemptsLeft - 1)), 20)`); otherwise `reject`. On `'open'`: **swap** the pre-open reject handler for a benign swallow (`off('error', onDialError)` → `on('error', () => {})`) so a later reset never crashes the process, then resolve. This mirrors `fakeDaemon.ts`'s cleaner `once('error', onDialError)`-removed-on-open dial (`fakeDaemon.ts:248-258`).

`npm run build` and `npm test` both green; the fix cleared the flake across the ≥10-consecutive-full-suite-runs-under-load bar the spec set (AC3 — recorded in the PR).

## Design in one paragraph

The server is guaranteed listening before any dial (`startFakeRelayForwarder` resolves on `'listening'`), so a pre-open reset is a *recoverable transient* by definition — an immediate re-dial clears it, and a bounded (≤5) retry converges. This is the same **category** as the ticket's own accepted examples ("await-listen", "ordered close-before-next"): socket-lifecycle hardening of the exact racy operation, **not** a blind whole-test retry — no assertion re-runs, so a real logic bug is never masked, and a genuinely-down target still fails fast once attempts are exhausted. Every establishment hop stays awaited (`start` → `connect('/v1/client')` → `connect('/v1/server')` → `await whenReady()` → first `send`); the retry only affects the two `connect` hops, and each attempt is a fresh socket with the failed one `terminate()`d first, so no half-open socket leaks. Teardown is unchanged.

## Patterns established

- **Distinguish "flaky test" from "flaky code" before hardening — the fix belongs where the race is.** The forwarder module's frame-order races ("101-before-registration", "both legs' upgrade completes before the first frame") were *already* closed by the positive `whenReady` gate and the `await whenReady()` before the first `send` (see [#90](90.md) §Patterns established). The remaining flake was strictly **below** that gate, in the test's raw dial. Leaving `fakeRelayForwarder.ts` untouched is what preserves AC4 ("no behavioural change to the content-blind forwarding contract") and the content-blindness import-list invariant **for free** — the module can't drift a codec/Noise import it never opened.
- **A bounded, error-class-scoped retry is deterministic hardening, not flake-hiding — the boundary is "does an assertion re-run?"** Retrying the *establishment* of an already-listening server on a specific transient error class (bounded, fail-fast on exhaustion) converges on the recoverable case while a genuinely mis-wired dial (wrong port, real logic bug) still turns the test red. This is categorically different from `retry`-ing the whole `it` (which re-runs assertions and masks logic bugs), from `.skip`/`.fixme` (hides it), and from quarantine — all four are explicitly disallowed by the ticket.
- **Mirror the robust sibling's lifecycle rather than inventing one.** `fakeDaemon.ts`'s dial (`once('error', onDialError)` removed on open, benign post-open handler attached) was already the correct shape; the flaky helper's persistent `on('error', reject)` was the outlier. Convergence on the established idiom across the transport test suite is cheaper to maintain than a bespoke retry loop.

## Lessons learned

- **A pre-existing flake, not a regression — but the single-shot pre/post QA partition can't tell them apart.** The full baseline suite runs all-green, so any PR that trips a low-rate flake gets mislabelled as introducing it. That's a QA-harness limitation (a raw pre/post partition assumes a deterministic baseline), and the durable fix is to make the flaky operation deterministic rather than to teach QA to special-case it. The prior triage cost (hand-verifying the failure was unrelated to PR #103's fingerprint-digest swap, which touches nothing near a socket) is exactly the tax this removes.
- **Loopback ephemeral-port churn under worker fan-out is a real, reproducible contention source.** The flake is invisible in isolation because it needs many workers each binding/tearing-down `port: 0` `WebSocketServer`s simultaneously — and vitest's source-order-first scheduling concentrates that peak on every file's first test. When a "socket hang up" only appears under `npm test` and never on a single-file re-run, suspect accept-queue/ephemeral-port pressure at the raw dial, not the code under test.
- **`"socket hang up"` vs a hung `nextFrame` is a diagnostic fork.** The *error class* localises the race: `"socket hang up"` ⇒ pre-open (dial); an unresolved wait to vitest's 5000ms timeout ⇒ mid-exchange. Post-open resets remain correctly swallowed by the benign handler, so a genuine mid-exchange break still surfaces as the legible timeout the retry deliberately does **not** mask.

## Testing

No new test case — the fix hardens an existing helper; a "dials survive a simulated reset" unit test is hard to make deterministic (you can't reliably inject a pre-open reset) and the spec explicitly declined to add one. The regression guard is empirical: **≥10 consecutive full-suite `npm test` runs under artificial CPU load, zero failures** (run count recorded in the PR, per AC3). The other 7 forwarder cases pass unchanged (opcode preservation, `whenReady` pending-then-resolve, send-immediately-after-`whenReady`, `whenReady` timeout, close-before-both-legs, idempotent teardown, ephemeral-loopback URL shape — the [#90](90.md) §Testing set); the forwarder's byte+opcode-verbatim content-blind contract is untouched because the module doesn't change.
