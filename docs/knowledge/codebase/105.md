# #105 — Make `e2e/smoke.spec.ts` hermetic on an unpaired boot

**Shipped:** 2026-07-08 · **Size:** XS (PO sized S) · **Scope:** one file, `e2e/smoke.spec.ts` (test-only, ~48 LOC changed). No production code, no new dependency, no config change.
**Spec:** `docs/specs/architecture/105-smoke-spec-hermetic-unpaired-boot.md` · **PR:** [#159](https://github.com/pyrycode/pyrycode-desktop/pull/159) · **Review:** PASS, zero findings.

## What shipped

`e2e/smoke.spec.ts:10` asserted `.conversation` (ConversationScreen root) visible at boot — written in [#40](40.md), before the [#80/#84 app-shell router](../features/app-shell.md) existed. Post-router, every non-paired outcome routes to PairingScreen, so `.conversation` never mounts on a genuinely unpaired boot and the assertion timed out. It only ever passed on a machine whose shared, non-isolated Electron userData already carried a stale pairing (macOS `~/Library/Application Support/pyrycode-desktop/secrets/`) — non-hermetic by construction, and unreachable on any clean machine or CI. Surfaced by [#93](93.md) (PR #102): un-`fixme`-ing `pair-to-conversation.spec.ts` made `npm run e2e` run the whole `e2e/` dir for the first time, exposing this pre-existing, independent failure.

Two coupled edits, both in `e2e/smoke.spec.ts`:

1. **Stopped importing the shared `./fixtures/electronApp` fixture.** That fixture (`electronApp.ts`) launches `args: ['.']` with no userData isolation by design — it inherits the developer's real userData, which is the root cause. AC4 forbade modifying it (kept scenario-agnostic for future specs per #40/#93), so the fix had to live in the spec itself.
2. **Declared a local `base.extend<{ page: Page }>` fixture**, mirroring [#93](93.md)'s isolated-launch shape stripped to the minimum smoke needs: no `forwarder`/`daemon` fixtures (smoke never dials a fake relay target), no `LOOPBACK_RELAY_ENV_FLAG`/`TEST_SECRET_BACKEND_ENV_FLAG` (smoke never pairs). Kept: the `ELECTRON_RENDERER_URL` strip (built-renderer path, not a dead dev-server URL) and a per-run `mkdtemp` `--user-data-dir`, removed in the epilogue after `await use(page)` — fires on pass and fail through Playwright's fixture lifecycle.
3. **Swapped the boot assertion** from `.conversation` to `.pairing` (the PairingScreen root, `src/renderer/src/screens/pairing/PairingScreen.tsx:48`), asserting the container rather than a specific control so it stays robust to pairing-phase copy changes.

`npm run e2e` 3/3 green; `npm test` 495 pass; `e2e/fixtures/electronApp.ts` untouched and now unimported (intentional — no gate flags an unimported fixture since `e2e/` is outside both tsconfig `include` globs).

## Design in one paragraph

`--user-data-dir` overrides `app.getPath('userData')`, so the isolated launch reads a fresh, empty secrets store regardless of any ambient shared-userData pairing. `window.pyry.pairingStatus()` then resolves `not-paired` → `routeForStatus` → `pairing` route → PairingScreen mounts → `.pairing` appears. The result is identical whether or not a stale shared pairing exists on the machine (AC3) — the isolated dir makes the shared one invisible to this launch. This is the smallest hermetic fix: no seeded pairing record, no new production code, just an isolated boot plus the assertion that matches what the router actually does today.

## Patterns established

- **A scenario-agnostic shared fixture stays untouched; per-scenario isolation lives in the scenario.** This is the second spec (after [#93](93.md)) to fork its own local `test.extend` rather than grow `electronApp.ts` with per-scenario knobs. The ~7-line launch machinery is now duplicated across `smoke.spec.ts` and `pair-to-conversation.spec.ts` — code review called this out explicitly as intentional and spec-endorsed, not a cleanup opportunity.
- **`.pairing` / `.conversation` are the two stable router-outcome roots to assert on in e2e.** Any future boot-path e2e assertion should target one of these containers, not a specific control inside them.

## Lessons learned

- **Non-hermetic e2e stays invisible until a sibling scenario runs the whole suite.** This ticket's root cause — smoke depending on shared userData — was undetectable while smoke was the only spec in `e2e/`; `npm run e2e` running *all* specs is what exposed it (via #93). Any new e2e spec should be run through the full `npm run e2e`, not just standalone, before being declared green.
- **A router change (#80/#84) can silently invalidate an existing e2e assertion with no test failure until the environment stops cooperating.** The `.conversation`-at-boot assertion was stale for the entire time between the router landing and this fix, masked purely by dev-box state. Boot-path e2e assertions are worth a quick sanity pass whenever the router's routing table changes.

## Testing

The deliverable **is** the test. `npx playwright test smoke.spec.ts` passes standalone on a clean environment (AC1/AC2); the harder direction — passing with an ambient shared pairing still present on the box — was verified in the PR (AC3, proves the isolated dir, not luck, produces the result). `npm run e2e` full suite green, 3/3 (AC5). No unit-test surface — `e2e/` is outside both `npm test` and `npm run typecheck` scope.
