## What it does

In v2 the **daemon is the rekey initiator** (pyrycode #450/#453/#454): on a ~1-hour per-session timer it AEAD-seals a `{type:"rekey_request"}` control envelope and sends it as a transport frame to nudge the client to re-handshake. Before this ticket the [Noise session](../features/noise-session.md) was **codec-agnostic** in `transport` state — it AEAD-decrypted each frame and emitted the opaque bytes as `{type:'message', plaintext}` (`noiseSession.ts:146`), importing no codec and decoding no envelope. A sealed `rekey_request` therefore decrypted fine, surfaced as a `message`, and was **silently dropped** downstream by [`parseInboundMessage`](../features/inbound-message-decode.md)'s `default → null` branch — so no rekey was ever triggered (`grep -ri rekey src/` was empty before this ticket).

This ticket adds the **recognition and nothing else**: between the successful transport-state decrypt and today's `message` emit, the session now peeks the decrypted envelope's `type` and diverts a positively-classified `rekey_request` to a **new bare `NoiseSessionEvent` variant** — `{type:'rekey-requested'}` — instead of handing it on as an app message. #109 consumes that trigger. Recognition is a transport-layer concern (it governs the cipher lifecycle), so it lives in the session, not the consumer — keys, sockets, and the handshake never reach the renderer.

Off the first-milestone critical path (a milestone session lasts seconds; the daemon rekeys hourly, so a milestone session never receives a `rekey_request`), built now because long-lived desktop sessions are on the roadmap.

## The recognizer — reuse `decodeEnvelope`, swallow its throw

```ts
function isRekeyRequest(plaintext: Uint8Array): boolean {
  try {
    return decodeEnvelope(plaintext).type === REKEY_REQUEST_TYPE
  } catch {
    return false
  }
}
```

**Total by construction.** It reuses the already-security-reviewed, fail-closed [`decodeEnvelope`](../features/wire-codec.md) (UTF-8-fatal, throws `WireDecodeError` on malformed UTF-8/JSON, a non-object, or a missing/mistyped `id`/`type`/`ts`/`payload`) and swallows that throw to `false`. So **any** decode/peek failure yields `false` and the caller falls through to the unchanged `message` path — a peek failure is **never a rejection**. It reads only `.type`; the control payload (`{reason}`) is discarded, never interpreted (the trigger is shape-only). It carries no key/token/frame/plaintext bytes out. The daemon's `rekey_request` is a full `Envelope` (all four fields present — protocol-mobile.md § Re-key), so strict `decodeEnvelope` decodes it with **zero false-negative risk** for the contracted shape.

## Patterns established

- **A recognizer downstream of the AEAD open reuses the vetted decoder rather than hand-rolling a second parser.** The seam sits strictly *after* `recvCipher.DecryptWithAd` (`noiseSession.ts:141`), so it only ever sees peer-authenticated plaintext. Reusing `decodeEnvelope` (not a bespoke minimal type-peek) inherits its fail-closed guarantees for free and mirrors the daemon twin's "decode-as-Envelope → switch on `type` → fall through on decode failure" seam (#454). The `try/catch → boolean` — not a second parser — is what enforces the fail-closed invariant.
- **Recognition is purely additive: it *diverts*, it never re-decodes an app message.** The `message` path carries the **identical** decrypted bytes it always did; [`parseInboundMessage`](../features/inbound-message-decode.md) stays the **sole** app-message decode/narrow authority. The recognizer must not become a second decode gate for app messages — it only pulls out a positively-matched control frame, and even that carries no bytes onward. (There is a deliberate *double-decode* on the `rekey_request` path — recognizer + downstream — the same tradeoff the daemon twin #454 accepted; threading a pre-decoded envelope downstream would touch `parseInboundMessage` and its tests for no measurable benefit.)
- **A control-type constant stays module-private and OUT of the shared `EnvelopeType` union — mirroring the daemon's `v1TypeSet` exclusion.** `Envelope.type` is `EnvelopeType | string`, so `=== 'rekey_request'` type-checks with no union change. Keeping the constant out of `EnvelopeType` (the app-message vocabulary `parseInboundMessage` switches over) documents the same "control type, not an app-dispatch type" boundary the daemon draws by adding `TypeRekeyRequest` as a constant but keeping it out of `v1TypeSet` (belt-and-suspenders, different fabric: the daemon enforces it on its side; the desktop enforces it here). `types.ts` (shared) stays untouched — **no wire-type drift** — and the one consumer is the recognizer; #109 consumes the *event*, not the wire string.
- **Adding a `NoiseSessionEvent` variant is a build-integrity event for the driver.** Any new session-event variant breaks the `NoiseSessionEvent ⊆ RelaySessionEvent` subset that `noiseRelayDriver.route` leans on, so `npm run build` catches it. The fix is a deliberate routing decision (drop-here vs. propagate-up), not a mechanical patch — here it is drop-here (recognition-only), with the propagate-up decision explicitly deferred to #109. The build gate, not a test, is what forces this decision to be made.
- **A bare signal event, not a byte-carrying payload.** The trigger is `{type:'rekey-requested'}` with no fields — no plaintext, key, token, frame, or `payload.reason` value enters any event, reason string, or diagnostic. This upholds the module's LOG-FREE contract (no `console.*`; the caught `WireDecodeError` is swallowed to a boolean, never forwarded). No new `NoiseSessionErrorReason` — a peek failure is a fall-through, not an error.

## Cipher-state safety (why recognition can't corrupt the session)

`DecryptWithAd` advances the receive nonce counter **before** the recognizer runs, regardless of the recognizer's outcome — so cipher state is correct on **both** the `rekey-requested` and the `message` path. Corruption from recognition is structurally impossible: the recognizer is a synchronous pure read of the already-decrypted `plaintext` local and **holds no cipher reference** (`recvCipher`/`sendCipher`/`hs`/`state` are never touched). The `state === 'closed'` short-circuit at the top of `onFrame` is unchanged, so a post-close frame is still inert (recognition is never reached after teardown). The AEAD-open failure path (`catch → fail('transport-decrypt-failed')`) is upstream of recognition and **unchanged** — a forged control frame from a content-blind relay fails the AEAD open and never reaches the recognizer.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The recognizer reuses `codec.decodeEnvelope` and swallows its `WireDecodeError` to `false`, so a peek failure reproduces today's behavior (fall-through to `message`) rather than becoming a new rejection** — the fail-closed invariant is enforced by the `try/catch → boolean`, not by a second parser.
- **Adding a variant to `NoiseSessionEvent` breaks the `NoiseSessionEvent ⊆ RelaySessionEvent` subset that `noiseRelayDriver.route` relies on for `emit`**, so a two-line early-return guard there is a required build-integrity edit (the `rekey-requested` trigger is intentionally *not* propagated up to `RelaySessionEvent` in #108).

No React re-render / effect-cleanup surprises — a pure main-process crypto unit, no React, no timers, no listeners, no `await` inside any entry point (the module's single-threaded synchronous-crypto invariant, pinned by the close-during-handshake tests, is preserved).

## Testing

All three tests are additive and drive the existing peer-cipher idiom (a real sealed frame from `createNoiseResponder`, assertions read the initiator's collector):

- **AC1 — sealed `rekey_request` recognized as the trigger, not a message.** The responder seals a full control `Envelope` `{ id: 42, type: 'rekey_request', ts, payload: { reason: 'scheduled' } }` (the daemon's exact shape); the initiator collector contains exactly one `{type:'rekey-requested'}`, **no** `{type:'message'}`, and no `error`.
- **AC2 regression — app message still surfaces with identical plaintext.** The responder seals an app `message` envelope; the initiator surfaces one `{type:'message', plaintext}` whose bytes **deep-equal the exact sealed plaintext**, and no `rekey-requested`. This pins that recognition never transforms or re-narrows app-message plaintext.
- **AC3 fail-closed fall-through, no corruption or crash.** Two sub-cases sealed through the responder so they AEAD-open cleanly: (a) a well-formed but **unmodeled control type** (`some_unknown_control`) and (b) **non-Envelope garbage** (`'not-json{{'`) both surface as `{type:'message'}` with identical bytes, no `rekey-requested`, no `error`, no throw. **Strengthening:** a *following* ordinary app message still surfaces intact — proving the recv cipher advanced correctly across the two fall-throughs and recognition left cipher state intact.

Existing coverage stayed green untouched: the mode-2 round-trip, the `transport-decrypt-failed` classification test, the close-during-handshake safety block, and the six-method log-free assertion. The `npm run build` gate exercises the `noiseRelayDriver.ts` route edit (the union-subset assignment).
