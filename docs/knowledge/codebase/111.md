## What it does

In v2 the **daemon is the rekey initiator** (pyrycode #450/#453/#454): on its ~1-hour per-session timer it AEAD-seals a `{type:"rekey_request"}` control envelope, opens a ~30 s reply window, and expects the client — as the responder to the rekey — to run a fresh in-session IK handshake **as the handshake INITIATOR** (a new `noise_init`). The daemon then swaps its own `CipherState`s under a peer-static continuity check; both sides resume under new keys. There is **no `rekey_ack`** — the implicit ack is the next successful AEAD round-trip under the new keys. Miss the window → the daemon closes the session at WS 4426.

[#108](108.md) landed **recognition**: a decrypted `rekey_request` control envelope surfaces the bare `{type:'rekey-requested'}` `NoiseSessionEvent` and diverts. But the driver **drops** that event ([`noiseRelayDriver.route`](../features/noise-relay-driver.md), a build-integrity guard) — recognition happened, nothing acted on it, so a long-lived session was still torn down at the daemon's rekey interval.

This ticket adds the **action at the session layer**: on that recognized trigger the session builds a fresh `HandshakeState` as INITIATOR with the same injected static keys, emits a new handshake message 1, and on the daemon's reply derives new send/recv cipher states via `Split()` and **atomically** swaps the old ciphers for the new. After the swap, transport encrypt/decrypt resume under the new keys — so a session can outlive the daemon's rekey interval instead of dying at WS 4426. Recognition already lives in the session ([#108](108.md)) and IK requires the initiator (the desktop) to send the fresh handshake, so the action lives in the session too — keys, sockets, and the handshake never reach the renderer. Off the first-milestone critical path (milestone sessions last seconds, never an hour); built now because long-lived desktop sessions are on the roadmap.

## The mechanism — a small extension of the initiator state machine

Recognition self-triggers a fresh handshake, which parks the session in a new `awaiting-rekey-reply` phase holding the **old** ciphers live; the reply drives an atomic swap. The whole thing is a variant of the existing `idle → awaiting-handshake-reply → transport` walk, with two load-bearing differences from the initial handshake: **empty early-data**, and **failure returns to `transport` (usable), not `closed`**.

### `beginRekey()` — the fresh handshake as INITIATOR (`:179-205`)

- **Precondition guard (belt, deterministic):** `if (state !== 'transport' || sendCipher === null || recvCipher === null) return`. Only ever reached from the transport branch, so it is purely defensive.
- Builds a **fresh** `HandshakeState(NOISE_ROLE_INITIATOR)` from the closed-over `lib`, reusing the exact `NOISE_PROTOCOL` constant (never retyped — a suite mismatch fails silently, [ADR 0002](../decisions/0002-remote-head-over-relay-shared-wire.md)) and the **same injected keys**. The `Initialize(...)` call is byte-identical to the initial handshake (same `config.prologue`/`staticPrivateKey`/`remoteStaticPublicKey`, same empty-prologue-→-`null` handling). `lib` is closed over, so no wasm reload.
- Writes msg1 with **empty early-data** — `WriteMessage(EMPTY_AD)`, **not** `config.hello`. The rekey handshake carries no `hello`; the device token is **not** re-transmitted on a rekey (spec § Re-key).
- The construct+init+write is wrapped in a `try`. On any throw the library has already auto-freed the fresh handshake, the **old ciphers are untouched**, and `hs` is still `null` → `fail('handshake-read-failed')` and **return without changing state** (stays `transport`, usable). Practically unreachable for a well-formed empty-early-data write; handled for atomicity.
- On success, **in this exact order** (ordering is load-bearing — see below): `hs = fresh`; `state = 'awaiting-rekey-reply'`; **then** `config.sendFrame(msg1)`. At the end the session holds `hs` = fresh handshake, `sendCipher`/`recvCipher` = the **still-live OLD ciphers**.

### `awaiting-rekey-reply` branch — read reply + atomic swap (`:231-262`)

- `hs.ReadMessage(frame, true)` — reads the daemon's reply; the recovered early-data is **discarded** (empty; no `hello_ack` on a rekey).
- `hs.Split()` — consumes + frees `hs`; returns `[send, recv]` **role-adjusted for the initiator, no pair swap** — identical mapping to the initial handshake (`fakeDaemon.ts:179`; crossing them sails through the handshake and only detonates on the first sealed frame).
- **The atomic swap** (the AC2/AC4 invariant). `ReadMessage` and `Split` are the **only** fallible wasm ops; assignments cannot throw. So once `pair` exists: capture the old refs into locals → `sendCipher = pair[0]; recvCipher = pair[1]` (two synchronous assignments, nothing between them throws or awaits) → guarded-free the two **old** ciphers (mirroring `freeAll`'s `try { obj?.free() } catch {}` discipline). Then `hs = null; state = 'transport'`. **No event is emitted** — the swap completes silently; the implicit ack is the resumed round-trip.
- **Failure** (`ReadMessage` or `Split` throws — malformed/wrong-suite reply, or a mid-session peer swap the pinned static can't complete): the library auto-freed `hs`, and **no assignment to `sendCipher`/`recvCipher` happened**, so both still hold the OLD keys. Set `hs = null; state = 'transport'` (usable — **not** `closed`) and `fail('handshake-read-failed')`.

Because both new ciphers are installed before either old one is freed, and no fallible op runs after the first assignment, the session is **never** left with one new cipher and one old — on success both are new, on failure both are old.

## Patterns established

- **Atomicity by ordering fallible ops before any mutation.** The half-swap wedge is prevented structurally, not by a flag or a lock: identify the only two throwing ops (`ReadMessage`, `Split`), run them **both** before touching `sendCipher`/`recvCipher`, then do the swap as two adjacent synchronous assignments with nothing fallible between them, and free the old pair only after. This is the same shape the daemon uses for its own switchover (pyrycode #435) and generalizes to any "replace a pair of live handles atomically" problem in this module.
- **A failed *rekey* returns to `transport`; a failed *initial* handshake goes to `closed`.** The `awaiting-rekey-reply` failure path is a near-copy of `awaiting-handshake-reply`'s crypto (`ReadMessage` → `Split` → install) but diverges on exactly one line: recovery state. The initial handshake has no session to preserve, so a failure closes; the rekey has a live, usable session on the old keys, so a failure **must** leave it `transport`. This state difference — not a distinct error reason — is what lets a consumer tell "rekey failed, session alive" from "initial handshake failed, session dead" (see NIT below).
- **Reusing the pinned static IS the client-side peer-continuity guarantee — do not add a phantom compare.** As the IK initiator the client **supplies** the daemon static (`rs`) in msg1's `es`/`ss` and never re-learns it from the handshake, so there is nothing to compare. A mid-session peer swap produces diverging DH and surfaces as the existing `ReadMessage` failure (→ `handshake-read-failed`, old ciphers intact). The **explicit** peer-static continuity check is the daemon's responsibility (pyrycode #452 captures the client static at the initial handshake; #453 rejects a fresh handshake whose recovered client static differs, closing 4426) — a client-side static-compare would be dead code (belt-and-suspenders, different fabric: each side owns its own half).
- **Empty early-data on a rekey — the token is not re-transmitted.** The initial handshake's msg1 carries `config.hello` (the device-token envelope); the rekey's carries `EMPTY_AD`, and the reply's `hello_ack` is discarded. Rekey is a pure forward-secrecy key rotation over an already-authenticated session — no re-authentication payload rides it.
- **Re-entrancy: set `hs` + `state` before `sendFrame`.** `config.sendFrame` may be a synchronous callback that drives the peer, which synchronously calls back `onFrame` with the reply — the whole rekey can complete **inside** `beginRekey`'s `sendFrame(msg1)` call. So `beginRekey` sets `hs` and `state='awaiting-rekey-reply'` **before** `sendFrame`, exactly as `start()` sets `state` before `sendFrame` (`:168-169`). If it sent first, the re-entrant reply would arrive with `state` still `transport` and be mis-dispatched (re-recognized as another trigger). The extended test responder exercises exactly this cascade.
- **The successful swap emits no event, by protocol.** There is no `rekey_ack` and no wire marker; the implicit ack is the resumed round-trip. Emitting a `rekey-complete` would fan out the `NoiseSessionEvent` union and the driver's `route` for an unobserved need — evidence-based-deferred to a `#112+` ticket if a "rekeying…" UI affordance ever wants it.
- **`sendMessage` is already inert during the window — no change needed.** Its guard `if (state !== 'transport' || sendCipher === null) return` means an app send during the sub-second `awaiting-rekey-reply` window is dropped at the session layer rather than sent under an ambiguous key. Cross-rekey send queueing is a store/driver concern, explicitly out of scope.

## Error reason — reuse `handshake-read-failed`, add nothing

Every rekey-handshake failure (the unreachable build/write in `beginRekey`, and the reachable read/split of the reply) classifies as the **existing** `handshake-read-failed`. No new `NoiseSessionErrorReason` member. It is accurate (the fresh handshake's message read/derive failed), it stays within "no driver change" (`RelaySessionErrorReason ⊇ NoiseSessionErrorReason`, so reuse forwards through the driver untouched), and a consumer distinguishes rekey-fail from init-fail by **recovery state** (`transport` vs `closed`), not by reason. A distinct `rekey-failed` reason is an unobserved need; a later telemetry ticket adds it then.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The spec's scenario-2 (hold back an undelivered responder→initiator K0 frame, then rekey) is not realizable in the JS↔JS harness — and the direction matters.** The AEAD transport stream is **nonce-lockstep**: holding one responder→initiator frame back desyncs the responder's send nonce from the initiator's recv nonce, so the later `rekey_request` (same direction) then fails to open and the rekey could **never trigger**. Re-feeding the *consumed* trigger frame instead only tests replay, not key replacement (it fails in RED too). The realizable clean proof holds back an **initiator**-sealed K0 frame (the trigger travels the *other* direction — responder→initiator — so no desync) and feeds it to the responder after the swap; scenario 1 already proves the initiator's recv cipher is the new key. Documented inline where the test deviates from the spec. **Reusable rule for #112/#495:** to prove an old-key frame dies post-swap, hold back a frame in the direction **opposite** the rekey trigger.

No React re-render / effect-cleanup surprises — a pure main-process crypto unit: no React, no timers, no listeners, no `await` inside any entry point (the module's single-threaded synchronous-crypto invariant, pinned by the close-during-handshake block, is preserved). No dependency-version issues (`lib` is closed over from the initial load; the fresh `HandshakeState` needs no wasm reload).

### Code-review NIT (recorded, no change requested)

`beginRekey`'s build/write catch (`:197`) classifies a **write**-side failure as `handshake-read-failed` (a read-side reason). A slight misnomer, and note `start()`'s analogous unreachable write failure uses `unexpected-frame` (`:165`) — so the two "practically-unreachable write failure" paths are classified differently. **Non-blocking and pre-justified in the spec** (§ Error reason: every rekey failure deliberately folds under `handshake-read-failed` to avoid a driver fan-out; a consumer distinguishes rekey-fail from init-fail by recovery state, not reason). ## Testing

Three additive session-boundary tests in a new `describe`, driven through the file's peer-cipher idiom (real AEAD-sealed frames from the test-only responder, asserted via the initiator's `NoiseSessionEvent` collector). The responder was extended additively with `initiateRekey` + an `awaiting-rekey-init` substate that **atomically swaps its own ciphers** the same way the session does, so the JS↔JS rekey round-trip closes synchronously, exactly like the mode-2 initial handshake.

- **AC1/AC2/AC3 — complete the re-handshake + swap, resume under new keys.** `pair()` to `transport` (keys K0). `responder.initiateRekey(<rekey_request envelope>)` drives the whole synchronous cascade (K0 → K1). Assert: exactly one `{type:'rekey-requested'}` on the initiator, **no** error, and the swap itself emits no event; then a round-trip under the **new** keys succeeds **both directions** (`responder.sendMessage` surfaces as `{type:'message'}` with matching bytes on the initiator, and `initiator.sendMessage` on the responder).
- **AC3 — an old-key frame no longer opens after the swap.** Hold back one **initiator**-sealed K0 frame (captured, not delivered — the direction that doesn't desync the trigger stream, per Lessons), do the successful rekey (K0 → K1), then feed the captured K0 ciphertext to the responder: it emits `transport-decrypt-failed` and surfaces no message — proving the recv cipher was actually **replaced** (a K0 frame does not open under K1), not merely a replay.
- **AC4 — a failed fresh handshake leaves the session usable on the old keys.** Toggle the initiator's `sendFrame` to swallow the fresh msg1 (the responder never rekeys, stays pristine on K0); drive the trigger with a **plain** `responder.sendMessage(<rekey_request>)` (not `initiateRekey`) so the session recognizes it, emits `rekey-requested`, sends the (dropped) msg1, and parks in `awaiting-rekey-reply`. Feed garbage directly (`new Uint8Array(64).fill(0x5a)`): assert exactly one `handshake-read-failed`, **no** second `handshake-complete`, and then a following K0-sealed `responder.sendMessage(app)` **still opens** — the old-key round-trip succeeding is the proof both ciphers stayed K0 (never half-swapped) and the session did not close.

All existing coverage stayed green: the mode-1/2 round-trips, the `transport-decrypt-failed` classification, the #108 recognition block, the close-during-handshake safety block, and the six-method log-free assertion.

## Deferred / carried forward

- **#112 owns the wire framing + e2e.** Framing the fresh msg1 on the wire as `noise_init` so the real daemon accepts it, and the end-to-end round-trip against `fakeDaemon`, are the immediate follow-up (blocked by this ticket). This ticket is the **session-layer crypto mechanism only**, unit-tested at the session boundary. **No driver change is in scope here** — the `rekey-requested` event stays a pure in-main observability signal the driver drops; the action is entirely internal to the session (it produces raw handshake bytes and swaps ciphers). #495 (lost-rekey recovery — the ~30 s window lapsing → WS 4426 → supervisor reconnect) is now blocked by #112.
- **No cross-rekey send queueing.** `sendMessage` is inert during the sub-second window (dropped, not queued). Whether a queued send should replay after the swap is a driver/store concern for a later ticket if the milestone ever surfaces dropped mid-rekey sends — evidence-based-deferred.
- **No client-side rekey rate-limiting.** Only the AEAD-authenticated daemon can seal a `rekey_request` (a content-blind relay cannot forge one — it fails the AEAD open), and a compromised daemon already holds the session, so a rekey flood is not a new relay-exploitable surface. The daemon owns rekey rate-limiting (`noise.rekey_failed`). Add a client-side cap only if a flood is ever observed.
