## What it does

In v2 the **daemon is the rekey initiator**: on its ~1-hour per-session timer it AEAD-seals a `{type:"rekey_request"}` control envelope, opens a ~30 s window, and expects the client — as the responder to the rekey — to run a fresh in-session IK handshake **as the handshake INITIATOR** (a new `noise_init` on the wire). Both sides atomically swap cipher states and resume; there is **no `rekey_ack`** — the implicit ack is the next successful AEAD round-trip under the new keys. Miss the window → the daemon closes at WS 4426.

[#111](111.md) built the client's **session-layer action** (recognize → fresh handshake → atomic swap), unit-tested at the session boundary. But #111 deliberately left two things undone, both owned here:

1. **Wire framing.** The daemon routes the rekey handshake by the `InnerFrameV2.type` (pyrycode #453): an open-state `noise_init` → its rekey responder; an open-state `noise_msg` → transport-decrypt, where the raw IK handshake bytes fail AEAD → WS 4421 close. The driver framed only a connection's **first** outbound frame as `noise_init`; the rekey `msg1` — not the connection's first frame — was framed `noise_msg` and would be mis-routed. **Part 1** re-arms the framing so the rekey `msg1` goes out as `noise_init`.
2. **End-to-end proof.** The test-only `fakeDaemon.ts` was a pure IK responder (one handshake, one round-trip). **Part 2** gives it a rekey-**initiator** capability; **Part 3** wires the assembled-stack e2e.

Off the first-milestone critical path (milestone sessions last seconds, never an hour); built now because long-lived desktop sessions are on the roadmap. Everything lives under `src/main/transport/`; keys, sockets, and the handshake never reach the renderer. `fakeDaemon.ts` stays test-only.

## Part 1 — the driver latch: re-arm `noise_init` for the rekey `msg1`

The coordination is entirely inside the per-connection closure in `onConnected`, driven by the session's existing **synchronous emit-then-send ordering** ([#111](111.md), `noiseSession.ts:223-226`): on a recognized `rekey_request` the session calls, **within a single `onFrame` turn and in this order**, `config.onEvent({type:'rekey-requested'})` → the driver's `route(...)`, then `beginRekey()` → `config.sendFrame(msg1)` → the driver's `sendFrame(...)`. So `route` sees the trigger immediately **before** the `msg1` reaches `sendFrame`. The fix: `route` arms a one-shot latch; `sendFrame` consumes it to tag that one frame `noise_init`.

- `firstFrame` keeps its documented "connection's first frame" meaning, **untouched**. A **dedicated** `rekeyInitPending` latch means "the next outbound frame is a Noise handshake init" — both signals stay self-documenting rather than overloading one flag.
- Both `route` and `sendFrame` sit behind the same `if (gen !== generation) return` generation guard and capture the **same** connection's `gen`, so the arm and the consume are always in the same generation; a superseded connection no-ops both.
- **Observable sink behavior is unchanged.** `rekey-requested` is still dropped from the `RelaySessionEvent` sink (the driver only adds a side-effect — arm the latch — before the existing `return`), so #108's build-integrity guard and its "trigger not propagated" test stay green.

## Part 2 — the fake daemon's rekey-initiator capability (test-only)

Mirrors `noiseSession.test.ts`'s in-memory `createNoiseResponder.initiateRekey` + `awaiting-rekey-init` handling, framed through the production codec over the WS leg. The crypto is **faithful** (a lax fake can pass while diverging from the real daemon); the **outbound `type` tag stays `noise_msg`** for every frame — the client reads by session state and never branches on the inbound tag (`sendNoise`'s uniform-`noise_msg` convention), so no distinct rekey-reply tag is added.

- **`initiateRekey()`** (guard `state === 'transport' && sendCipher !== null`, else no-op): build the `rekey_request` envelope via `encodeEnvelope`, seal it under the **current** send cipher, **set `state = 'awaiting-rekey-init'` BEFORE `sendNoise`** (re-entrancy discipline mirroring the responder), then send.
- **`handleRekeyInit(raw)`**: run a fresh `HandshakeState(NOISE_ROLE_RESPONDER)` reusing the **SAME** static via a byte-identical `Initialize(null, staticPriv, null, null)`; `ReadMessage(raw, true)` (discard the empty early-data); `WriteMessage(EMPTY_AD)` → `msg2` (no `hello_ack` on a rekey); `Split()` → `[send, recv]` role-adjusted, **no swap** (the module note — crossing the mapping sails through the handshake and detonates on the first sealed frame). The **atomic swap** installs both new ciphers before freeing either old one, with nothing fallible between the two assignments (identical discipline to `handleMsg1` / `noiseSession.ts`). Then `sendNoise(msg2)`, `state = 'transport'`, and finally seal the resume frame under the **new** send cipher and send it.
- On any throw: classify `handshake-read-failed`, drop the caught object (log-free), tear down — mirroring `handleMsg1`. No new `FakeDaemonErrorReason` member.

## Part 3 — the assembled-stack e2e round-trip

A third `it` in the existing fake-target `describe`, reusing `standUpRoundTrip` (now with an optional `daemonOpts` passthrough for `rekeyResumeMessage`). It drives the **real** `createDaemonConnection` → real `createNoiseRelayDriver` → real session → real loopback relay against forwarder + fakeDaemon, exercising Part 1's framing on the real wire **and** Part 2's responder together:

1. Stand up with a known `message` `buildReply` and a **distinct** known `rekeyResumeMessage`. Drive to `connected` (K0).
2. Baseline `connection.send` → `messageReceived` (K0 round-trip works).
3. `daemon.initiateRekey()` → daemon seals `rekey_request` (K0) → the real client recognizes it → the driver frames the fresh `msg1` as `noise_init` (Part 1) → the daemon reads it, swaps to K1, sends `msg2` + the resume frame → the client reads `msg2`, swaps to K1.
4. `messageReceived` carrying the **resume** payload → proves the client's recv cipher is K1.
5. `connection.send` under K1 → the daemon opens it (the implicit ack) and replies via `buildReply` under K1 → `messageReceived` carrying the **reply** payload → proves the client's send cipher is K1 (AC3, bidirectional).
6. No `failed` event; `daemon.whenSettled()` is `{ok:true}` (cached from the baseline round-trip).

## Patterns established

- **A driver-local one-shot latch off the session's synchronous emit-then-send ordering.** When a session needs the driver to change the framing of *exactly one* upcoming frame, the driver doesn't need a per-frame type signal threaded through the `sendFrame(frame: Uint8Array)` contract — it can arm a latch from an event that the session is contracted to emit **synchronously immediately before** that frame, and consume the latch on the next `sendFrame`. This kept the change to ~5 driver lines with **no** session/contract churn (the alternative — a frame-type argument — would ripple into the session, the interop `driveClient`, and `fakeDaemon`). It works precisely because #111 pinned "emit `rekey-requested` **then** `sendFrame(msg1)` in one `onFrame` turn"; the latch is only correct while that ordering holds, so the two are coupled by design (the driver unit test drives the exact sequence).
- **A faithful test-only rekey-initiator mirrors the responder crypto, not the wire tags.** `fakeDaemon.initiateRekey`/`handleRekeyInit` reuse the SAME static, the SAME `[send, recv]` no-swap `Split` mapping, and the SAME atomic-swap discipline as the initial handshake and as `noiseSession.ts` — because faithfulness for a fake daemon lives in the crypto (`ReadMessage`/`WriteMessage`/`Split`, cipher role-mapping), where a lax fake would silently diverge. The outbound `type` tag stays uniform `noise_msg`: the client never branches on it, so diverging to a distinct rekey-reply tag would add an unfaithful wrinkle the real client can't observe.
- **The daemon-sent post-swap resume frame is the e2e's deterministic swap signal — substituting for the absent `rekey_ack`.** Because #111's client emits **no event** on a successful swap (implicit ack, no wire marker) and a client `send()` issued during `awaiting-rekey-reply` is silently dropped (the session's `state !== 'transport'` guard), an e2e has **no client-side signal** that the swap to the new keys finished. Having the daemon stream one frame under the new keys immediately after its swap gives a deterministic, ordered client-side receipt: the forwarder splices frames in order, so it arrives **after** the `msg2` the client swapped on, decrypts under the client's fresh recv cipher, and surfaces as `messageReceived`. That receipt proves the client's recv cipher is K1. It is crypto-faithful (any daemon→client frame under K1 is identical crypto to "the daemon streaming the next turn"); *who* sends the first post-rekey frame is a harness concern, not a protocol divergence.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The e2e needs a daemon-sent signal to observe the client's swap.** #111's client emits no event on a successful swap (implicit ack, no `rekey_ack`), and a client `send()` during `awaiting-rekey-reply` is silently dropped — so an e2e has no client-side signal that the swap to the new keys finished. The fake daemon streaming one frame under the new keys right after its swap gives a deterministic, ordered client-side receipt (arrives after the `msg2` the client swapped on, decrypts under the fresh recv cipher → `messageReceived`). This is a harness/choreography detail, not a protocol divergence — any daemon→client frame under the new keys is identical crypto to the daemon streaming the next turn.
- **A driver-local latch keeps the session transport-agnostic.** Threading a frame-type through the session's `sendFrame(frame: Uint8Array)` contract would ripple into the session, the interop `driveClient`, and `fakeDaemon`. Arming a one-shot latch in the driver's `route` (off the session's synchronous emit-then-send ordering) and consuming it in `sendFrame` keeps the change to ~5 driver lines with no session/contract churn.

No React re-render / effect-cleanup surprises — a pure main-process transport change: no React, no timers, no listeners, no `await` inside any entry point (the transport's single-threaded synchronous-crypto invariant is preserved on both seams). No dependency-version issues (`lib` is closed over from the initial load; the fresh `HandshakeState` needs no wasm reload). The `(x as { plaintext })` casts in the fakeDaemon tests match the established file idiom; test-only.

### Testing note — what is deliberately NOT re-proven at e2e

That an old-key (K0) frame no longer opens after the swap is **not** re-staged at e2e. [#111](111.md)'s unit scenario already proves cipher **replacement** (not mere replay) at the session boundary via the nonce-lockstep hold-back trick ([[rekey-test-nonce-lockstep-hold-back]] — hold back a frame in the direction **opposite** the rekey trigger). Re-staging that in a real WS e2e would add significant complexity for no new evidence — evidence-based-deferred.

### Code-review NITs (recorded, no change requested)

- **`fakeDaemon.ts` — post-swap sends inside `handleRekeyInit`'s try/catch.** The `sendNoise(msg2)` + resume-frame send sit inside the `try`, so a throw *after* the swap would misclassify as `handshake-read-failed` despite the swap having succeeded. Practically unreachable (`sendNoise` is non-throwing; `EncryptWithAd` on a fresh cipher with empty AD won't throw) and test-only. Non-blocking.
- **Accepted residual — latch leak under an unreachable throw** (architect's Security review § "latch leak under an unreachable throw", re-confirmed by code review). If `beginRekey`'s `WriteMessage(EMPTY_AD)` threw (session stays in `transport` on the old keys, sends no `msg1`), the armed latch would tag the next app frame `noise_init`, which the daemon rejects and tears down. Fail-safe (connection teardown, **not** session hijack — the frame is already AEAD-sealed under the old cipher and simply gets mis-routed and dropped), and the trigger is a `WriteMessage` on a freshly-initialized handshake with empty early-data, which #111 documents as practically unreachable. The driver can't distinguish this case without a session API change (out of scope); "not gated" agreed.

## Deferred / carried forward

- **#495 — lost-rekey recovery (mobile parity).** Recovering a LOST rekey response (retry / avoid wedging the session on a dropped reply within the ~30 s window before the daemon closes at WS 4426 → supervisor reconnects with a fresh handshake) is the base mechanism's hardening — an always-split. Now unblocked (`blockedBy` #112 satisfied).
- **No rekey-failure e2e.** The session-layer rekey-failure path (a failed fresh handshake returns to `transport` on the intact old ciphers) is [#111](111.md)'s unit coverage; the happy-path e2e treats a daemon rekey failure as a test timeout (the client never receives the resume frame).
