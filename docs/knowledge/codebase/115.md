## What it does

Adds the ability for the background process to **ask** the daemon to start streaming the current session's debug bundle: it builds and encrypts a bare `request_debug_bundle` control envelope onto the live Noise session. That is the whole slice — receiving/reassembling the streamed `.tar.gz` response (#116), saving it (#117), and the renderer command that would invoke this (#118) are the siblings and are **not** here.

The request is a **bare control envelope — no payload struct, no `conversation_id`, no id that selects a session**. The bundle is daemon-global by construction (whole log ring + newest recording across all sessions, no per-session key), so there is **no attacker-selectable field** — which is exactly why this outbound slice is not security-sensitive while the inbound-reassembly sibling is. It mirrors the daemon's `TypeInterrupt` (pyrycode #707): a bare, payload-less control frame intercepted before `dispatch.Route`.

Everything is `src/main/` (transport + the connection layer above it); keys, sockets, and the raw bytes never reach the renderer.

## The load-bearing decision — "no payload" is a *present-but-empty* `payload: {}`, not an omission

The single non-obvious call in the ticket, and the one the inline comment and PR "Lessons learned" both pin so a future reader does not "fix" it:

- The daemon's `Envelope.Payload` is a deferred-decode `json.RawMessage` that is **never read** for a bare control type (intercepted before dispatch, like `interrupt`), so the daemon tolerates an **absent, `{}`, or `null`** payload. The daemon is not the binding constraint.
- The **binding constraint is the desktop's own** `decodeEnvelope`, which requires `'payload' in obj` and throws `WireDecodeError` otherwise (`codec.ts:133`). The AC5 round-trip test exercises exactly that path (same as the `send_message` test). So the builder **must emit a present payload** — an omission would fail the desktop's own decode.
- Among present forms, **`payload: {}`** (empty object literal) is used — not `payload: null` — because the codec's house posture is "never emit `null` on the wire" (`codec.ts:107`; the tightened optionals forbid `null`). `null` would decode fine but violate that posture, so it is rejected even though the daemon tolerates it. `{}` also matches how existing payload-less envelopes are written in tests (`ack`/`hello`).
- **Accepted, daemon-tolerated divergence from mobile:** mobile (`explicitNulls = false`) likely *omits* the field for its bare frames; the desktop cannot, because `Envelope.payload` is required and must not be relaxed. The daemon never reads `Payload` for this type, so the divergence is invisible on the wire.

This is captured in project memory as [[bare-control-frame-needs-present-empty-payload]] — the rule generalizes to any future "no payload" outbound frame (e.g. `interrupt`).

## Why a single `driver === null` guard suffices (AC4)

Same argument as the [outbound send path](../features/outbound-send-path.md)'s `send`: the connection does **not** track handshake state itself. The one `driver === null` guard covers before-`start()` / mid-bootstrap / bootstrap-failed; every *other* "not connected" state (driver constructed but pre-handshake, or post-terminal) is covered by `driver.sendMessage`'s own inertness (`NoiseSession.sendMessage`'s `if (state !== 'transport') return`). So a request is a silent no-op in every disconnected state, never a throw. The `try/catch` is retained for exact `send` parity and the module's never-throw invariant — the build cannot over-cap (fixed ~80-byte envelope), but `driver.sendMessage` (wasm) can throw; the caught object is **dropped**, no log, no event.

## Patterns established

- **A bare control-frame builder is a *thinner* sibling of the application-message builder, not a generalization.** `buildRequestDebugBundle` copies `buildSendMessage`'s shape (pure `(id, ts) → Uint8Array`, `encodeEnvelope`, MAIN-PROCESS-ONLY header, same field order) minus the payload arg and the `make…Payload` constructor. The architect explicitly rejected a generic `buildControlEnvelope(type, …)` helper: there is exactly **one** bare control frame in scope, and a generic abstraction for one consumer is YAGNI (Simplicity First; mirrors the daemon-side #707 "one-line gate, not an abstraction"). If `interrupt` lands later, *that* ticket decides whether to generalize.
- **A second outbound method shares the one `nextEnvelopeId` counter — never a second counter.** `requestDebugBundle` advances the same module-local monotonic counter `send` uses, so envelope ids stay unique across interleaved `send`/`requestDebugBundle` calls (the daemon correlates replies by `id`/`in_reply_to`; the reassembly sibling relies on a well-formed request id). Proven by the shared-counter test (send→request ⇒ ids 2 then 3). Advancing only on a successful build, no `await` in the method → runs to completion, no check-then-act race — identical single-writer discipline to `send`.
- **An additive interface method needs no consumer wiring in the same slice.** `requestDebugBundle` is added to the `DaemonConnection` interface whose sole implementation is `createDaemonConnection`; the `onCommand` switch in `index.ts` stays `sendMessage`-only. The renderer command that would call it is the sibling ticket (#118), so nothing must invoke the new method for this slice to be complete — the interface addition is purely additive.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The "no payload" wire requirement is satisfied by a present-but-empty `payload: {}`, not an omission.** The desktop's own `decodeEnvelope` requires `'payload' in obj` (throws otherwise) and the shared `Envelope.payload` stays required (relaxing it would be a wire-type drift). `{}` over `null` upholds the codec's "never emit null on the wire" posture. This is an accepted divergence from mobile (which omits the field via `explicitNulls = false`); the daemon never reads `Payload` for this bare control type, so it tolerates any form. See § "The load-bearing decision" above.

No React re-render / effect-cleanup surprises — a pure main-process transport change: no React, no timers, no listeners, no `await` in the new method (the transport's single-threaded synchronous invariant holds). No dependency-version issues (no new dependency; `encodeEnvelope`/`decodeEnvelope` reused unchanged). Written test-first per CLAUDE.md.
