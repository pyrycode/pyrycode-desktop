## What it does

The background process now recognizes the daemon's streamed reply to `request_debug_bundle` — ordered `debug_bundle_chunk`* frames followed by one `debug_bundle_done`, or a single `error` in lieu of the stream — and reassembles the ordered chunks into the complete, opaque `.tar.gz` archive, or fails cleanly. Recognition is **additive**: the existing `message` / `message_chunk` inbound path is byte-for-byte unchanged. The archive is never unpacked or inspected — bytes are concatenated in `seq` order and handed to an injected consumer as-is.

Everything lands in `src/main/` / `src/main/transport/`; the reassembled bytes, the raw chunk bytes, and every intermediate state stay in the background process — nothing crosses to the renderer in this slice (CLAUDE.md "keep the transport out of the window").

## The load-bearing decision — one reassembler slot, no `in_reply_to` map

The daemon's reassembly reference (`internal/relay/v2bundlestream.go`) and `protocol-mobile.md` are explicit: the daemon does **not** correlate `debug_bundle_chunk`/`debug_bundle_done` to the triggering request by `id`/`in_reply_to` — it correlates by frame *type*, and clients must not dedup by `id`. Because the desktop only ever has **one** bundle request in flight (the bundle is daemon-global, triggered by one UI action), the correct client-side model is the simplest one: a single per-connection `reassembler` slot, replaced on each `requestDebugBundle` call, with no map keyed by request id. A stray frame with no active slot (or a settled one) is a structural no-op via optional chaining — this is also what makes an unrelated `error` (not bundle-related) harmless when no bundle stream is in flight. If the desktop ever multiplexes concurrent id-correlated streams, this needs revisiting — not an observed failure mode today, so it stays deferred (Evidence-Based Fix Selection).

## Why `requestDebugBundle`'s not-connected path changed from silent no-op to `fail('not-connected')`

`send`'s sibling stays a silent no-op when disconnected (fire-and-forget, no result to wait for). `requestDebugBundle` cannot: it now owns a `consumer` that #118's renderer command will await, and a silent no-op would hang that command forever with no signal. So the not-connected branch was changed to call `consumer.fail('not-connected')` — the wire behavior is still "send nothing," but the caller is now notified. This is the one behavioral change to an existing branch in this slice; everything else about `requestDebugBundle`'s guard/counter/try-catch shape is unchanged from #115.

## Patterns established

- **A stateful accumulator sits in its own file, downstream of recognition, and never logs.** `bundleReassembler.ts` is a clean split from `inboundMessage.ts`: recognition narrows and content-free-logs at the untrusted boundary; the reassembler holds no logging capability at all (it accumulates content-bearing bytes — a log call here would be a hole in the content-free posture the rest of the module maintains). This is the module's first byte-holding, IPC-free, log-free stateful primitive — a template for any future streamed-payload feature.
- **"Which check rejects which failure modes" collapses to one comparison when state is countable.** `seq !== chunks.length` alone rejects a reorder, a gap, *and* a duplicate — no separate branches needed, because the array's `.length` **is** the "chunks seen so far" invariant. Avoid inventing a `Set<seq>` or a max-seen counter when a plain ordered array already encodes the same information.
- **A teardown net belongs at the connection-lifecycle boundary, not inside the accumulator.** `bundleReassembler` has no concept of "the connection died" — that signal is a `daemonConnection`-level fact (`terminal`/`error` driver events), so the `reassembler?.fail('connection-lost')` call lives at `onDriverEvent`'s existing terminal/error handling, unconditionally and safely (a no-op on a settled/absent reassembler). Deterministic code, not a stochastic guard — matches the pipeline's Belt-and-Suspenders posture.
- **An additive `switch` on a discriminated `kind` beats an `if`/`else` chain the moment a union grows past two members.** `onDriverEvent`'s `message` case went from a two-armed `if (inbound.kind === 'message') … else …` to a `switch` — the compiler now enforces exhaustiveness as more kinds are added (a future kind that's forgotten in the switch is a type error, not a silent fallthrough).
- **A required constructor argument is the right tool when "the caller must always be notified" becomes a real invariant.** `requestDebugBundle(): void` → `requestDebugBundle(consumer: BundleConsumer): void` is a breaking signature change, but the one real call site (this ticket's own test — #118 doesn't exist yet) makes it cheap, and an *optional* consumer would have reintroduced the "unnotified caller" failure mode this ticket exists to close.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The content-free `DiagnosticRecord` always carries its own `seq` stamp** (the logger's monotonic counter), which name-collides with a bundle chunk's `seq` field. A "seq is never logged" test must assert the exact field allowlist via `Object.keys(record)` — `not.toHaveProperty('seq')` gives a **false positive** against the logger's own stamp, since that field is always present under that name regardless of what the test is trying to prove absent. The same trap applies to numeric-substring checks against the 64-char BLAKE2s hash hex: it coincidentally contains almost any two-digit run, so a naive `not.toContain('42')`-style assertion is unreliable — assert field presence/absence structurally (`Object.keys`), not string-search the serialized record.
- **Bundle frames emit no `DaemonEvent`**, so the roundtrip harness's bounded waiter (notified only on sink events) never wakes on a bundle completion by itself. The end-to-end test wires the consumer's `complete`/`fail` callbacks to poke the same waiter the sink notifies — a pattern any future feature that bypasses the `DaemonEvent` channel (as this one deliberately does, routing to an injected consumer instead) will need to repeat in its own roundtrip test.

No React re-render / effect-cleanup surprises — a pure main-process transport change: no React, no timers, no listeners beyond the existing driver-event subscription. No dependency-version issues (no new dependency; `@noble/hashes`, `Buffer`, and the existing codec reused unchanged). Written test-first per CLAUDE.md.

## Deferred / carried forward

- **#118 — the renderer command.** Constructs the per-download `BundleConsumer` (mapping `complete` → `saveDebugBundle` (#117), `fail` → error IPC, `progress` → progress IPC) and calls `requestDebugBundle(consumer)`. This ticket fixes that contract; #118 owns the IPC surface and the UI.
- **Reassembly memory cap.** No explicit ceiling on total accumulated bytes — matches the daemon's own accepted stance for a paired, Noise-authenticated peer. `done.total` × a chunk-size cap would give an upper bound to reject early if a hardened cap is ever wanted; flagged for a future hardening ticket, not observed as a real problem today.
- **`error` correlation stays "any inbound `error` while a bundle is in flight."** Correct for the single-in-flight, daemon-global model; revisit only if the desktop ever multiplexes concurrent id-correlated streams.
