## What it does

Turns the relay connection from "LOG-FREE by construction" (a failed dial surfaced only as a generic `connect-error`/1006 with no cause) into "**content-free-log by construction**": the socket now emits three content-free diagnostic records — `relay-open`, `relay-unexpected-response`, `relay-closed` — through the injected [#126 logger](../features/diagnostic-log.md). The single highest-value line is `relay-unexpected-response { status: 404, host, path }`: today a client that dials without `/v1/client` gets the relay's 404 classified by the `error` handler down to a nondescript pre-open 1006 with no status, so the misroute took a manual hunt. The status now reaches the log — **not** the `RelayEvent` stream (no sealed-union change). The what/why lives in the [relay-connection feature doc](../features/relay-connection.md) § *Security posture* / *Diagnostic logging*; the allowlist-not-scrubber contract is [ADR 0007](../decisions/0007-content-free-diagnostics-by-construction.md).

## The load-bearing decisions

- **Ride inside the `connection` blob — a single construction-site edit, no 4-file cascade.** The logger reaches `relayConnection` by riding the `connection` config that already spreads verbatim through every layer: `daemonConnection.loadDialConfig()` → `createDriver({ connection })` → `createSupervisor({ connection })` → `createConnection({ ...conn, onEvent })`. Because `noiseRelayDriver` / `relaySupervisor` both type `connection` as `Omit<RelayConnectionConfig, 'onEvent'>`, the new optional field threads down transitively with **no** edit to either and no fixture cascade. The rejected alternative — a constant field threaded explicitly through `NoiseRelayDriverConfig` + `RelaySupervisorConfig` — is a 4-file change for no benefit (trap 3 in the ticket, resolved).
- **The re-attach the ticket feared is automatic and free.** The ticket flagged that [#83](83.md)'s reload rebuilds the per-dial `connection` blob on every reconnect, so a logger riding inside it "must be re-attached each reload." But `loadDialConfig` is the *single* per-dial construction site and it closes over the constant `deps.diagnosticLog` — so each rebuilt blob references the same singleton (one `seq` counter, one file) with zero extra logic.
- **Do not enrich `RelayEvent`; the status reaches the log, not the event stream (AC4a).** Surfacing status on the sealed union would cascade an additive-union change through `RelaySupervisorEvent` → `RelaySessionEvent` → `daemonConnection`'s choke point (4 files) for no secret-safety gain. The status goes only to the log.
- **The `unexpected-response` handler must capture the status AND drive today's terminal (AC4b).** The `ws` 8.21 trap: with an `unexpected-response` listener present, `ws` emits that event *instead of* `error` for a non-101 response and **stops auto-destroying** the socket. A log-only handler would let the dial hang until the owned 10 s connect-timeout, flipping the observable terminal from `connect-error`/1006 to `connect-timeout`/1006. So the handler copies the exact connect-timeout idiom — `pending = { code: 1006, reason: 'connect-error' }; ws.terminate()` — after logging: `terminate()` during CONNECTING → `abortHandshake` → (next tick) `error` (swallowed on `pending !== null`) then `close` (reads `pending`, emits `closed{1006,'connect-error'}`) — **byte-identical to the pre-#127 refused-upgrade terminal**, and prompt.
- **Log the numeric close code, never the wire `reason` (AC3c).** At the `close` site, `status: terminal.code` is the numeric WS code (always safe); `code: pending?.reason` is the module-static classification (`connect-timeout`/`pong-timeout`/`max-frame-exceeded`/`connect-error`/`client closing`) present **only** on a module-initiated close. On a peer/library close `pending` is `null` → the field is `undefined` → `JSON.stringify` drops it. The attacker-controlled wire `reason.toString()` (`relayConnection.ts:238`) is **never** passed to the log.
- **Coordinates are `hostname` + `pathname` only (AC3a/b).** `new URL(config.url).hostname` / `.pathname`, never `.href` / `.search` (a dev-seam url can carry the token in a `?token=` query), and `config.headers` (which carries `x-pyrycode-token`) is never read into any log field. `new URL` cannot throw at that site — `new WebSocket(config.url)` above already parsed the same string.

## Patterns established

- **Thread an optional dependency down a verbatim-spread config blob — one edit, no cascade.** When a config object already flows unchanged through N intermediary layers typed as `Omit<Config, 'sink'>`, an additive-optional field on the leaf `Config` reaches the leaf with a single construction-site edit and no intermediary or fixture changes. This is the cheapest possible way to inject a cross-cutting main-process singleton (here the [#126](126.md) logger) into a deeply-nested transport primitive — contrast the explicit-field-through-every-config alternative.
- **A new `ws` listener can silently change `ws`'s own default behaviour — copy the sibling terminal idiom, don't just observe.** Adding an `unexpected-response` listener suppresses `ws`'s auto-destroy, so an observability-only handler would regress the terminal. The fix is to make the new handler drive the *same* deterministic terminal the module already owns (`pending` + `terminate()`), pinned by leaving the pre-existing "refused upgrade" test's assertion **unchanged** as the regression guard (it now routes through the new handler).
- **Apply the [#126](126.md) call-site secret-safety checklist at every log site.** The `host`/`path`/`event`/`code` fields are `string` and cannot be *type*-forbidden from holding a secret (the #126 security-review residual). Code review's job on a diagnostics-consumer ticket is to confirm each call site passes static literals for `event`/`code` and `new URL(u).hostname`/`.pathname` for `host`/`path` — never `config.url`/`.href`/`.search` or a header value. #135's review confirmed all three sites clean.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **With an `unexpected-response` listener present, `ws` 8.21 emits that event *instead of* `error` and stops auto-destroying the socket.** A log-only handler would let the dial hang until the connect-timeout, flipping the terminal from `connect-error` to `connect-timeout`. The handler must copy the connect-timeout idiom (`pending = {1006,'connect-error'}; ws.terminate()`) to keep the terminal byte-identical. (This is the `ws` behaviour trap that pins AC4b — verified by the AC1 test's large `connectTimeoutMs` + a sub-500 ms close assertion: a hang would surface as a test timeout.)
- **A peer/library close leaves `pending` null, so `code: pending?.reason` is `undefined` and `JSON.stringify` drops it from the line — assert the *value* is `undefined`, not `'code' in record`.** The property is present-but-`undefined` on the in-memory record the `captureLog` fake sees, but absent from the serialized JSON line; a test that checked key presence would read the wrong layer.

No React re-render / effect-cleanup surprises — a pure main-process transport primitive (no React, no store). No dependency-version issues (no new dependency; reuses the existing `ws` 8.21). The one added `ws` listener is removed by the existing `removeAllListeners()` in `teardownAndEmitClosed`, so the teardown "never re-fires" invariant ([#35](35.md)) holds unchanged. Written test-first per CLAUDE.md.

## Carried forward / deferred

- **Code-review `[NIT]` — `relayConnection.teardown.test.ts:69` `SOCKET_EVENTS` doesn't name `'unexpected-response'`, deliberately NOT applied (non-blocking, cosmetic).** The per-event `listenerCount` loop enumerates only `['open','message','pong','error','close']`, so the new listener isn't checked by name — but the *next* line's stronger `expect(ws.eventNames()).toHaveLength(0)` covers every listener including the new one, so the teardown invariant holds. Adding `'unexpected-response'` to the list would make the per-name signal explicit; left as-is (no gate, purely cosmetic). Evidence-based: no defense shipped for an unobserved gap.
- **`res.statusCode` undefined.** `http.IncomingMessage.statusCode` is `number | undefined`; a status-less unexpected response simply omits the field (`JSON.stringify` drops it, typechecks against `status?: number`) and still yields the `relay-closed` record. Not special-cased — vanishingly rare, and the real relay always sets it.
- **#128 — daemon-leg wiring** (uses `deps.diagnosticLog` directly in the `daemonConnection` event choke point; feeds the `not-paired`/`malformed-hello-ack`/`connection-closed`/`connect-failed` codes). Both #127 and #128 edit `daemonConnection.ts`; the second architect/developer to run must re-read the file (WIP=1 serializes them). #127 touched only the `connection` blob property (`:260`), so the overlap is minimal.
- **#125 — the broader Bucket-1 log** (state-store transitions, payload `hash + length + type`, a shared correlation id). Out of scope; the [#126](126.md) record shape accepts them as additive optional fields (see [ADR 0007](../decisions/0007-content-free-diagnostics-by-construction.md) § Consequences).
