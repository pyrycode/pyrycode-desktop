# #13 — Capstone: end-to-end round-trip (live operator runbook)

**Shipped:** 2026-07-07 · **Size:** XS · **Scope:** documentation only — one new file, [`docs/knowledge/features/live-e2e-runbook.md`](../features/live-e2e-runbook.md) · **zero** production `.ts`/`.tsx`, **zero** tests, **zero** new types/components.
**Spec:** `docs/specs/architecture/13-live-e2e-round-trip-runbook.md` · **PR:** [#86](https://github.com/pyrycode/pyrycode-desktop/pull/86) · review: **PASS** (no blocking findings; QA gates green — `npm run build` clean, `npm test` 367 pass / 2 pre-existing skips; code-review verified every load-bearing citation against source).

The **Phase-1 milestone gate**: the full **pair → connect → send → stream** round-trip against the **live** relay and the **real** `pyry` daemon on pyrybox — pair, watch the Noise handshake reach `connected`, send a message, and watch the structured reply stream back into the window. This ticket cannot be executed by the pipeline: pairing against the live relay and driving a real daemon needs live credentials, a running daemon, and network access to real infrastructure the architect/developer/QA agents do not have. **This is a manual operator gate; no production code is expected.** The deliverable is therefore a **manual operator runbook** a human follows on the live stack, recording the outcome (screenshot and/or daemon-log excerpt) as a comment on the ticket. It is the desktop equivalent of mobile's live-e2e runbook (spec/ticket #661) — desktop reuses the same wire contract ([ADR 0002](../decisions/0002-remote-head-over-relay-shared-wire.md)), so the same manual-vs-automated split applies. See the [runbook](../features/live-e2e-runbook.md) for the operator recipe.

Every code slice this gate waited on had already landed; both stated blockers are **merged**: #78→[#80](80.md) (app-shell routing that mounts the pairing screen and advances to conversation) and #34→[#82](82.md) (connect-on-pair, so a fresh pair immediately dials the live relay). The remaining #34 child [#83](https://github.com/pyrycode/pyrycode-desktop/issues/83) (reload the stored record on every *automatic* reconnect) is **not** a blocker — the first fresh pair dials via #82's `reconnect()`, which re-sources the just-persisted record at dial time; #83 only concerns transient-drop re-dials mid-session.

## Patterns established

- **Documentation-deliverable ticket — the "developer worktree touches only code/tests/spec" rule doesn't fire.** The developer worktree mutated exactly **one** file: the runbook. The usual guardrail exists to stop a fixed-cost knowledge-doc AC from being smuggled onto a *code* ticket; here the doc **is** the work (there is no code), so the rule's rationale doesn't apply. The `codebase/<N>.md` + `INDEX.md` entries stay the documentation phase's job — the spec explicitly told the developer not to write either. Same shape as the mobile precedent (#661).
- **Operator-only live-stack AC = runbook-verified observable, never a CI gate.** All three ACs are operator actions requiring live infra (build+launch+pair against the real daemon; send and observe the streamed reply; record the outcome). None is agent-executable. The automated stand-in for *mechanism* correctness is the fake-transport [e2e harness](../features/e2e-harness.md) ([#40](40.md)) **plus** the per-slice unit suites (#52/#53/#55/#62/#65/#66/#68/#69); this runbook is the operator confirmation that the **same** mechanism works against the **live** stack.
- **Live proof unblocks the hardening phase, not vice versa.** This gate deliberately blocks the Phase-2 batch (#35–#41). The automated round-trip (#39) and UI-driven e2e (#41) encode this milestone as regression coverage and are sequenced **after** the live demonstration, blocked *by* it — mirroring how mobile drew the manual-vs-automated line. Adding a live-relay e2e to CI is explicit scope-creep and out of bounds.
- **The load-bearing operator observable is the UI, because the transport is log-free by construction.** The runbook points the operator at the composer's send button flipping enabled on `connected` ([#31](31.md)) and the `data-message-role="user"`/`"daemon"` thread bubbles ([#69](69.md)), *not* at desktop app logs — the transport emits no `console.*` around the handshake ([#62](62.md)) so a stray log can never leak the token/keys/transcript. The operator watches the **UI + the pyrybox daemon logs**.

## Lessons learned

*Lifted from the PR #86 "Lessons learned" section.*

- **The relay allowlist matches the host only, not the full URL.** `RELAY_ALLOWLIST` is an exact `Set.has` on `URL.hostname` (`src/main/pairingPayload.ts:45-55`), so the runbook's most-likely first-run failure — `relay-host-not-allowed` — is about the payload's `relay` **host** being anything other than `pyrycode-relay.pyryco.de`; the deployed `/v1/client` path is incidental. Stated precisely so an operator debugging the rejection looks at the right field (the `relay` host, not the path or scheme-plus-path). Code-review confirmed the host-only match against `pairingPayload.ts:45-55,118-125`.

No React re-render / effect-cleanup / dependency-version surprises — no runtime code changed; the deliverable is a doc.

## Deferred (carried forward — the operator's live run)

- **The three ACs still require a human operator.** After this runbook landed, an operator must run the built app against the live pyrybox stack, observe the round-trip, and record the outcome (screenshot / daemon-log excerpt) as a comment on [#13](https://github.com/pyrycode/pyrycode-desktop/issues/13). That step is outside the agent pipeline by design — the runbook is the architect/developer/documentation contribution; the live run and recorded outcome are the operator's.
- **Any code gap surfaced during the live run is a new ticket**, not scope for #13 (the ticket body says so).
- **Automated live e2e is deferred by design** — #39 (automated transport round-trip) and #41 (UI-driven e2e) encode this milestone as regression coverage, sequenced *after* this gate.
