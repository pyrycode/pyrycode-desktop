# #130 — Content-free log of every inbound daemon envelope

**Shipped:** 2026-07-08 · **Size:** S · **Scope:** wire the merged [#126](126.md) content-free `DiagnosticLog` into `parseInboundMessage` — the post-decryption decode boundary — so every inbound daemon message leaves a content-free footprint (envelope type + the logger's `seq` + plaintext byte length + a one-way BLAKE2s-256 hash of the frame), never the payload value. Two outcomes now log: a modeled `message` / `message_chunk` (`inbound-decoded`) and a well-formed-but-**unmodeled** type that was previously *silently dropped* (`inbound-unmodeled`). The throw path stays unlogged. Three production files: `inboundMessage.ts` (the only new logic), a one-field additive extension of `diagnosticLog.ts`, and a one-line caller change in `daemonConnection.ts`. `security-sensitive`; architect self-review verdict **PASS**, code review verdict **PASS** (no findings).
**Spec:** `docs/specs/architecture/130-inbound-envelope-content-free-log.md` · **PR:** [#137](https://github.com/pyrycode/pyrycode-desktop/pull/137). Split from [#125](https://github.com/pyrycode/pyrycode-desktop/issues/125) (Bucket-1 diagnostics). The **post-decryption** leg; its opposite-byte-safety sibling [#133](https://github.com/pyrycode/pyrycode-desktop/issues/133) (pre-decryption raw *ciphertext* bytes on the codec/framing throw path) was `blocked-by` this and is now unblocked. See [[ticket-130-inbound-envelope-logging-refined]] and [[ticket-125-bucket1-diagnostics-split]].

## What it does

`parseInboundMessage` is the untrusted→trusted boundary for a decrypted daemon message ([#68](68.md)): it narrows a `message` / `message_chunk` to a typed `InboundDaemonMessage`, returns `null` for a well-formed-but-unmodeled envelope type, or throws `WireDecodeError` on malformed input. Its module header even declared *"This module performs no logging."* Until now all three outcomes vanished from the operator's view — a message that recurs, mutates between send and receive, truncates, or arrives as an unforeseen kind left no footprint, and the unmodeled case was **silently dropped**.

This ticket flips that invariant **for this one file** and records the two non-throwing outcomes as content-free records through the optionally-injected [#126 logger](../features/diagnostic-log.md):

- `inbound-decoded { code: 'message', bytes, hash }` — a modeled `message`, after it fully narrows.
- `inbound-decoded { code: 'message_chunk', bytes, count, hash }` — a modeled chunk, with its batch count.
- `inbound-unmodeled { code: <capped type>, bytes, hash }` — a well-formed `ack` / `error` / future kind, so an unforeseen envelope now leaves a footprint instead of disappearing; behaviour is otherwise unchanged (still returns `null`, still not surfaced to the UI).

This is the Diagnostics design's Bucket-1 *"hash + length + type, never the value"* recovery move plus the *"log unrecognised events by type, size, and hash"* catch-all. The what/why lives in the [inbound-message-decode feature doc](../features/inbound-message-decode.md) § *Diagnostic logging*; the allowlist-not-scrubber contract is [ADR 0007](../decisions/0007-content-free-diagnostics-by-construction.md).

## The load-bearing decisions

- **Log AFTER the modeled envelope fully narrows — that is what keeps the throw path unlogged.** Each modeled-arm log fires *after* `parseMessagePayload` / `parseMessageChunkPayload` returns, so a `message` with a malformed payload throws first and produces **no** record. The size guard and `decodeEnvelope` throws also precede the switch. AC5's "does not change or log the throw path" is satisfied structurally by call-site ordering, not by a flag — and pinned by two negative tests (missing-`text` throw and oversized throw both assert zero records).
- **Hash the plaintext FRAME, not `envelope.payload` — a *security* choice, not merely a determinism one.** `decodeEnvelope` returns `payload` as a parsed `unknown`; re-serializing it would be non-deterministic on JSON key order (the determinism reason the ticket gives). The deeper reason is that hashing the whole frame implicitly **salts** the digest with the server-assigned `id` / `ts` / `message_id` an attacker cannot predict — so a read-the-log dictionary attack ("did the user type X?") must reconstruct the *entire frame* byte-for-byte, not just guess the text. The frame bytes are also exactly what the daemon encrypted end-to-end, so a future daemon-side twin hash would compare directly.
- **The one peer-controlled string is capped deterministically.** The modeled arms log a **static type literal** (`'message'` / `'message_chunk'`) into `code` — safe. The unmodeled arm logs the daemon-supplied `envelope.type` — the catch-all's whole point ("log unrecognised events by type"), but the **one** non-literal, peer-influenced string reaching the log here. It is `slice(0, MAX_LOGGED_TYPE_CHARS)` (64 chars): lossless for every real wire type (all < 16 chars) and a deterministic bound on a hostile daemon that could otherwise stuff up to `MAX_PLAINTEXT_BYTES` (65519) of arbitrary text into `type`. Belt-and-suspenders: a code-level cap paired with the type discipline, not another stochastic rule. The #126 serializer JSON-escapes it, so a crafted `type` cannot split one record into two lines (a 200-char hostile-type test asserts exactly one line, `code.length === 64`).
- **`hash?` is additive; the length reuses `bytes?`.** `DiagnosticEvent` already carried `bytes?` (a byte length) and `count?` (a batch count, reused for the chunk case). The extension is a *single* optional `hash?` field — exactly the slot [ADR 0007](../decisions/0007-content-free-diagnostics-by-construction.md) and the [#126](126.md) header reserved. No existing call site changes; `JSON.stringify` drops `undefined`, so serialization is unchanged for every other event.
- **`blake2s` from `@noble/hashes`, not `node:crypto` — the packaged-app constraint.** Reuses the exact primitive already in-tree from [pairingConfirmation.ts](../features/pairing-confirmation.md) ([#101](101.md)): Electron's BoringSSL has no BLAKE2 family, so `createHash('blake2s256')` throws in the packaged main process. `@noble/hashes/blake2` is the synchronous, BoringSSL-safe path. **No new dependency.**
- **Optional-chaining short-circuits the whole call — absent-logger costs nothing.** `diagnosticLog?.event({ … hash: hashPlaintext(plaintext) })` — when no logger is injected, the `?.` short-circuits the entire call *including* `hashPlaintext`, so there is no wasted hash and no throw. Existing/test callers pass one arg and keep working (AC5 backward-compat), mirroring `relayConnection`'s "does not log and does not throw when no `diagnosticLog` is injected" test.

## Patterns established

- **A per-outcome content-free record at a decode boundary — the third `DiagnosticLog` consumer shape.** [#127](127.md) logs the relay socket's *coordinates + close code*; [#128](128.md) logs the daemon composition layer's *classification*; #130 logs a *decode outcome* — a type discriminator + a size + a one-way hash of an opaque frame. The `hash?` field generalizes the logger from "connection lifecycle" to "any opaque-blob recurrence/change/truncation signal": an identical frame recurring shows a repeated hash, a frame changing between send and receive a differing hash, a truncation a shifting length.
- **Realize a reserved additive field to widen an allowlist without breaking a call site.** `hash?` is the first concrete use of the "new safe fields are additive, non-breaking" consequence [ADR 0007](../decisions/0007-content-free-diagnostics-by-construction.md) predicted. The proof it stayed free: `typecheck` passes with no other call site touched, and the serializer's `{ ...fields, seq, ts }` spread (not a hand-picked tuple) carries the new field automatically.
- **Assert the content-free guarantee at the *serialized* boundary, over a real logger.** AC4's test plants a secret into `text` **and** `conversation_id`, decodes through a real `createDiagnosticLog` over a capture array, and asserts the raw JSON line contains the `hash` but **neither** planted secret — the guarantee is checked where the bytes actually leave, not on a mock's arguments. This is the reusable shape for any future content-free-log consumer.

## Lessons learned

No PR-body "Lessons learned" section — a clean S-ticket that implements the spec precisely. Two points worth recording for the next diagnostics-consumer / decode-boundary ticket:

- **"Hash the frame, not the payload" is the more *secure* instruction, not just the more deterministic one.** It's easy to read the ticket's determinism argument (JSON key-order non-determinism) and miss the security half: hashing the full frame salts the digest with unpredictable server-assigned fields, defeating a log-confirmation dictionary attack. A future author tempted to "hash just the message text for a cleaner correlation key" would silently reopen that attack. The choice is load-bearing on *both* axes.
- **Ordering the log call after the narrower is the entire mechanism that keeps the throw path unlogged.** There is no explicit "should I log this throw?" branch — the throw simply happens first, before control reaches the `event()` call. A refactor that hoisted the log above the narrower (e.g. "log the type as soon as we know it") would start logging frames that then throw, quietly violating AC5. The two negative tests (throw → zero records) are the regression guard.

No React re-render / effect-cleanup surprises — a pure main-process transport boundary (no React, no store; synchronous decode). No dependency-version issues (reuses the in-tree `@noble/hashes` and the [#126](126.md) logger; no new dependency). The added `event()` calls are synchronous, non-throwing side-effects — the sink swallows its own errors ([`diagnosticLog.ts:89-95`](../features/diagnostic-log.md)) so a full-disk log write can't take down the decode boundary, and the module still never throws off the happy path. Written test-first per CLAUDE.md.

## Carried forward / deferred

- **#133 — the pre-decryption raw-byte log** (the codec/framing throw path in `codec.ts` / `noiseSession.ts`). Those bytes are *ciphertext* and therefore safe to keep verbatim — the opposite byte-safety rule from this ticket, which is why the two are separate. `blocked-by` #130, now unblocked.
- **Post-decryption *semantic-throw* logging is a named open question, not this ticket and not #133's either.** A frame that decodes as `message` but fails to narrow (e.g. missing `text`) throws on a *post*-decryption boundary, so its bytes are plaintext (can't keep them raw like #133) yet it isn't a modeled outcome (isn't #130's content-free record). A content-free log for that case — type + size + hash on the narrower-throw — is deferred, flagged in the spec's Open Questions so it isn't lost.
- **#125 — the broader Bucket-1 log** (state-store transitions #134, version banner #132, renderer→main channel #131) and a **daemon↔client correlation/sequence twin**. The client-side receive-order `seq` stands on its own here; cross-side ordering ("arriving out of order" vs. the daemon) needs a daemon twin hash and is deferred. The [#126](126.md) record shape accepts the correlation id as another additive optional field.
- **`event` names** (`inbound-decoded` / `inbound-unmodeled`) were the architect's recommendation for greppability and symmetry with `relay-*` / `daemon-*`; the ACs constrained the *fields*, not the literal names. The developer kept them.
