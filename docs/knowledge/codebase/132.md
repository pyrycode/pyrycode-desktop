# #132 — Stamp the diagnostics log with the app version and wire-protocol version

**Shipped:** 2026-07-08 · **Size:** XS · **Scope:** a once-per-session "session start" banner through the [#126 content-free logger](../features/diagnostic-log.md), carrying the desktop client build and the wire-protocol identity, so a debug bundle is attributable to a specific version pair — the last of the [#125 Bucket-1 diagnostics](https://github.com/pyrycode/pyrycode-desktop/issues/125) split. `security-sensitive` (architect self-review, PASS).
**Spec:** `docs/specs/architecture/132-...` (c7d77af) · **PR:** merged 088374b (feature/132, `main`). Split from #125. Blocked-by [#126](126.md) (merged). See [[ticket-132-version-banner-refined]] and [[ticket-125-bucket1-diagnostics-split]].

## What it does

A version mismatch — client vs. daemon, or a wire-protocol drift — is a real, high-value failure class: the exact `Noise_IK_25519_ChaChaPoly_BLAKE2s` variant is load-bearing and a mismatch fails the handshake **silently** (CLAUDE.md; [ADR 0002](../decisions/0002-remote-head-over-relay-shared-wire.md)). This ticket makes that diagnosable from the bundle alone: at app start, exactly one content-free `session-start` record is logged, carrying `app.getVersion()`, `NOISE_PROTOCOL`, and `PROTOCOL_VERSION`, all reused verbatim from their existing sources — never retyped.

## The load-bearing decisions

- **Three fields, not two.** The ticket's load-bearing target is `noiseProtocol` (the Noise variant — the silent-failure axis) and `appVersion` was explicitly required; `protocolVersion` was added because it is **not redundant** with the Noise variant — v1 and v2 share the *same* Noise handshake variant string, so the Noise variant alone can't disambiguate a v1↔v2 negotiation drift (`protocol_versions: [PROTOCOL_VERSION]` is exactly what the client sends the daemon at `codec.ts:168`). Three cheap static strings for one banner; the open-questions section of the spec allows dropping `protocolVersion` on review pushback, but review didn't ask for that.
- **A dedicated Electron-free helper module, not an inline call in `index.ts`.** The composition root inside `app.whenReady()` has no unit-test surface; `sessionBanner.ts` exists purely to give the banner logic one. Mirrors the #134 renderer-side precedent (a tiny sibling module that builds a content-free record and emits it through the logger, unit-tested in isolation) on the main side.
- **Emission seam is a single call at the root, not inside the connection.** Placing `logSessionStart` before `createDaemonConnection` (not inside `start()`/`reconnect()`/the dial loop) is what makes AC3 ("once per session, not a per-line stamp, no re-emission on transport re-run") hold by construction rather than by a guard — there is exactly one call site in the whole codebase.
- **Extending the #131 `Omit` pin is mandatory, not optional.** The spec calls this out explicitly (Design §4): a main-only field added to `DiagnosticEvent` without extending the pin breaks `npm run typecheck`. This is the second time the pin has been extended (#133 did it first for `safeBytes`) — the pattern is now established: any future main-only field goes on this `Omit` list, any future field the renderer *can* also produce gets mirrored into `RendererDiagnosticEvent` instead.
- **No error handling added.** `app.getVersion()` and the two wire constants are always present (baked at build time); `diagnosticLog.event()` never throws (swallows sink failures internally). There is no untrusted input and no failure branch to guard.

## Patterns established

- **The version-banner shape (dedicated Electron-free helper + single root-level call before the first heavy composition step) is the template for any future once-per-session stamp** — the next candidate being the deferred `corr?` correlation id, which needs a daemon-side twin and stays out of scope here.
- **A second concrete precedent for extending the #131 `Omit` pin** (after #133's `safeBytes`), reinforcing that "main-only field ⇒ extend the Omit list" is now a checked, repeatable step in this codebase, not a one-off exception.

## Lessons learned

None beyond what the spec already anticipated — implementation matched the architecture doc with no deviation (no rework, no PO correction needed on the first pass). No React re-render or effect-cleanup surprises (no React in this module). No dependency-version issues (no new dependency; both wire constants and `app.getVersion()` were already in use elsewhere in the codebase before this ticket).
