# #133 — Log wire-decoder and framing errors with their safe pre-decryption bytes

**Shipped:** 2026-07-08 · **Size:** S · **Scope:** wire the merged [#126](126.md) content-free `DiagnosticLog` into the two **pre-decryption** failure boundaries in the main-process transport — the mirror image of [#130](130.md), which logs the **post-decryption** boundary and keeps no bytes. Four production files: `diagnosticLog.ts` (+42, the branded `safeBytes?` field + its sole minter `encodeSafeBytes`), `noiseSession.ts` (+37, `failWithFrame` at the three inbound-read catches), `noiseRelayDriver.ts` (+29, the framing-catch log + forwarding the logger into each session it builds), `daemonConnection.ts` (+4, one-line wiring). `codec.ts` stays untouched by design (§ below). `security-sensitive`; architect self-review verdict **PASS**, code review verdict **PASS** (one non-blocking `[NIT]`, a stale comment, left untouched).
**Spec:** `docs/specs/architecture/133-predecryption-safe-bytes-logging.md` · **PR:** [#161](https://github.com/pyrycode/pyrycode-desktop/pull/161). Split from [#125](https://github.com/pyrycode/pyrycode-desktop/issues/125) (Bucket-1 diagnostics). Both blockers ([#130](130.md), [#126](126.md)) merged before this ran. See [[ticket-133-predecryption-bytes-logging-refined]] and [[ticket-125-bucket1-diagnostics-split]].

## What it does

Two pre-decryption boundaries in the main process classify a failure into a static code and then, until now, dropped everything else — including the raw failing bytes, which are ciphertext / handshake material / length prefixes and therefore **provably not plaintext** (Bucket 1: *"a framing or transport error is ciphertext and length prefixes, not plaintext, so those bytes are safe to store"*):

- **`noiseSession.ts`** — the three **inbound-read** catches (`transport-decrypt-failed`, and `handshake-read-failed` at the message-2 read and the rekey-reply read) now log the capped raw failing frame alongside the static reason, before still calling the existing `fail(reason)`.
- **`noiseRelayDriver.ts`**'s `onMessage` — the `inbound-frame-decode-failed` catch (a malformed base64 / bad `InnerFrameV2` / length-prefix mismatch thrown by the codec as `WireDecodeError`) now logs the capped raw inbound frame alongside the code, before the existing `emit`+drop.

Both call sites go through one new field, `safeBytes?: SafeBytesEncoding`, and one new function, `encodeSafeBytes(frame: Uint8Array): SafeBytesEncoding`, both added to [`diagnosticLog.ts`](../features/diagnostic-log.md). Observable behaviour is otherwise byte-identical: `noiseSession` still emits the same `{ type: 'error', reason }`, the driver still emits `{ type: 'error', reason: 'inbound-frame-decode-failed' }` and drops the frame, and the frame bytes reach only the main-process diagnostic sink — never `onEvent`, never the renderer.

## The load-bearing decisions

- **A branded type, not a plain `string`, is the whole enforcement mechanism (AC3/AC5).** `SafeBytesEncoding` is a nominal `string` subtype whose brand symbol (`safeBytesBrand`) is `declare`d and never exported — so nothing outside `diagnosticLog.ts` can fabricate a value that satisfies it without an explicit, greppable `as SafeBytesEncoding` cast. `encodeSafeBytes` performs the **one sanctioned cast** in the codebase. A bare `string`, or the shape of a post-decryption value (`hash?`'s hex digest, `hashPlaintext`'s output), does not type-check into `safeBytes` — pinned by two `@ts-expect-error` assertions in the same `src/main` test file the #130 precedent used (avoids the `TS6307` cross-project boundary trap — [[shared-alias-not-available-in-main-preload]]/[[e2e-not-typechecked-by-project-config]]-adjacent lesson: keep compile-time pins in the file whose `tsconfig` actually includes them).
- **Cap the raw bytes BEFORE hex-encoding, not the hex string after.** `encodeSafeBytes` does `frame.subarray(0, MAX_SAFE_BYTES)` then `.toString('hex')` — an over-long frame is truncated to 64 *raw* bytes (→ ≤128 hex chars), verified independently by code review. `bytes: frame.length` carries the true uncapped length alongside, so a truncation or length-prefix mismatch stays visible even at the smaller cap.
- **Only the three inbound-read catches log bytes; every outbound-write catch stays byte-free — this is the load-bearing security boundary, not a style choice.** The only frame carrying a secret is **outbound** message 1 (the `hello` early-data holds the device token), written in `start()` and `beginRekey()`. Every logged frame is **inbound**: post-handshake AEAD ciphertext, or Noise handshake message 2 / rekey reply (ephemeral pubkey + encrypted static + MAC — public handshake material, no client secret). The client static private key never appears on the wire; the daemon never echoes the token back. This is why the spec enumerates exactly three catch sites and the tests pin a fourth (the outbound `beginRekey` catch) as byte-free by construction — the reviewer's job is to reject any future site that logs bytes at an outbound-write catch.
- **`codec.ts` deliberately stays untouched — a scope decision, not an oversight.** The ticket's Technical Notes suggested a doc-comment "reconciliation" in the codec too, but its "performs no logging" / "never echo raw bytes" claims remain **literally true** after this ticket: the codec still throws a category-only `WireDecodeError` and logs nothing; the *driver* — the caller that catches it — is where the safe raw bytes are logged, and the driver's own comment carries the reconciliation. Touching the codec would violate CLAUDE.md's "touch only what the task needs" and could dull the load-bearing purity invariant for no functional gain. Confirmed unchanged by code review (no scope creep).
- **`safeBytes` and `hash?` are structurally distinct fields with opposite safety rules — this is intentional, not incidental overlap.** `hash?` ([#130](130.md)) is a one-way digest of **plaintext**, safe because it's irreversible. `safeBytes` is a **reversible** hex encoding of raw bytes, safe because those bytes are **ciphertext** (never decrypted content). Reusing one field for both would blur that distinction at every call site; the branded type keeps them permanently separable even though both are `string`-shaped at the JSON-line level.

## Patterns established

- **A branded type is the fourth `DiagnosticLog` extension shape, and the first to gate a field by its *safety provenance* rather than just its *presence*.** [#127](127.md)/[#128](128.md) added lifecycle codes, [#130](130.md) added `hash?` as a plain optional `string`. #133 is the first consumer where "is this call site even allowed to populate this field" needed a compile-time answer stronger than "the field exists" — because the field's entire security value depends on *which side of decryption* the value came from. The reusable move: when a field's safety depends on how it was derived (not just its runtime shape), brand it and co-locate the sole minter with the brand symbol.
- **A boundary test that asserts the *absence* of a field is as load-bearing as one asserting its presence.** The `beginRekey` outbound-write byte-free test doesn't check new behaviour — it pins that a specific catch site was **not** converted to `failWithFrame`. This is the regression guard against a future refactor "helpfully" widening the byte-logging to a fourth (secret-bearing) catch.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The #131 renderer→main allowlist pin breaks on any main-only field — `hash?` happened to be mirrorable, `safeBytes` structurally cannot be.** [#131](131.md)'s `receiveDiagnostic.test.ts` pins `Equals<RendererDiagnosticEvent, DiagnosticEvent>` so the two allowlists can never silently drift. #130's `hash?` kept that pin intact by mirroring the field into both `DiagnosticEvent` and `RendererDiagnosticEvent`. `safeBytes` **cannot** be mirrored the same way: it's a branded type defined in `src/main` that the `src/shared` leaf must not import (mirroring it as a plain `string` would defeat the whole brand), and the renderer holds no frame bytes to send in the first place. Resolved by relaxing the pin to `Equals<RendererDiagnosticEvent, Omit<DiagnosticEvent, 'safeBytes'>>` — the security-relevant direction ("renderer cannot invent a non-allowlisted field") is preserved; only the capability-parity direction is dropped, and only for a field the renderer must never produce. **Any future main-only canonical field must be added to that `Omit` list as a conscious, reviewed decision, or the pin fails typecheck.** The spec's "additive-field, proven by #130" framing missed this because `hash?` happened to be mirrorable and `safeBytes` is not — the next diagnostics-consumer ticket adding a main-only field should expect the same relaxation, not assume the pin stays a bare `Equals`.
- **A stale comment was flagged but deliberately left untouched.** `src/shared/ipc/diagnostics.ts` still says `RendererDiagnosticEvent` is "field-for-field identical" to `DiagnosticEvent" (now identical *modulo* `safeBytes`), and also misnames the pin's home as `diagnostics.test.ts` (it actually lives in `receiveDiagnostic.test.ts` — a pre-existing #131 inaccuracy). Left untouched to keep the shipped footprint at the 4 spec files; code review confirmed this was a defensible touch-only-what-you-need call and flagged it as a non-blocking cleanup for the next #131/#134-adjacent ticket or the doc phase to pick up.

No React re-render / effect-cleanup surprises — a pure main-process transport boundary (no React, no store; synchronous catch-block side effects). No dependency-version issues (no new dependency; reuses the in-tree `Buffer` and the [#126](126.md) logger). The `event()` calls are synchronous, non-throwing side effects inside existing catch blocks — no new `await`, listener, or timer, and the sink swallows its own errors so a full-disk log write can't take down the transport it observes. Written test-first per CLAUDE.md.

Revisit only if a real cross-boundary import is ever observed.
