# #134 — Log session-store state transitions through the renderer diagnostics channel

**Shipped:** 2026-07-08 · **Size:** S · **Scope:** the first consumer of [#131's renderer→main diagnostics channel](../features/diagnostics-channel.md) — every dispatched `SessionAction` on the [session store](../features/session-store.md) now emits one content-free record (`{event:'store-transition', code:action.type, count:messages.length}`) through `window.pyry.sendDiagnostic`, so a state-layer fault leaves a footprint in the debug bundle alongside the transport logs. Two production files (one new, one edited), zero edit fan-out. No `security-sensitive` label — a passive observer with no design surface, review skipped that pass.
**Spec:** `docs/specs/architecture/134-log-session-store-transitions.md` · **PR:** [#162](https://github.com/pyrycode/pyrycode-desktop/pull/162). Split from [#125](https://github.com/pyrycode/pyrycode-desktop/issues/125) (Bucket-1 diagnostics). See [[ticket-134-store-transitions-logging-refined]] and [[ticket-125-bucket1-diagnostics-split]].

## What it does

`sessionStore.ts` is the one store the window renders from; every state change goes through `dispatch(action: SessionAction)`. Until now a transition left no trace. This ticket wires a passive observer into `dispatch` itself — the one seam every `SessionAction` flows through, from both the daemon-event bridge and the composer's local `messageSent` echo — that maps each transition to a content-free record and ships it over #131's channel.

## The load-bearing decisions

- **Instrument `dispatch`, not zustand `.subscribe`, not the bridge.** `.subscribe` fires only on an actual state change — a duplicate `messageReceived` whose `appendUnique` returns the same array reference (no new allocation) would go unlogged, violating AC3, and `.subscribe` cannot see the action `type` at all. The bridge (`daemonEventBridge.ts`) never sees the local `messageSent` echo dispatched from `composerSend.ts` — instrumenting it would miss that whole action. `dispatch` is the one choke point every `SessionAction` passes through regardless of origin, and it has both the action and (via `get()` after `set`) the reduced state.
- **A co-located sibling module, not logic inlined in the store.** `sessionDiagnostics.ts` is the only file that imports `window.pyry`; `sessionStore.ts` keeps its documented purity ("Pure renderer state — no IPC, no preload bridge, no transport," `sessionStore.ts:2`) by only importing the *value* `logSessionTransition` and threading it through an injected, optional `observe` param. Test stores built via bare `createSessionStore()` stay observer-free and IPC-free.
- **`code` carries the action `type`, not a separately-derived status name.** The two are 1:1 for status actions (`connecting`/`connected`/`disconnected`/`failed`→`error`, a documented naming skew not a bug) and the action type is the only signal available on message actions, where there is no status change. AC1 permits either; the architect spec records this as a deliberate, non-blocking call — a later consumer needing the resulting status name distinctly is an additive follow-up, not a change here.
- **No `try/catch` in `logSessionTransition`.** Every operation in the guarded path — reading `action.type`, reading `state.messages.length`, an optional-chained function call, constructing a plain `{string,string,number}` object — is structurally incapable of throwing. Evidence-based fix selection: no observed throw mode exists, so one deterministic guard (`typeof window !== 'undefined'`) is the single safety net, not a second stochastic layer on top of it.
- **No store-supplied `seq`.** `RendererDiagnosticEvent` (#131) has no `seq` field, so a store-emitted one would not typecheck and would be dropped by `projectDiagnosticEvent`'s allowlist regardless — ordering is entirely the [#126 logger](../features/diagnostic-log.md)'s job, stamped at `diagnosticLog.ts:122-128` at log time.

## Patterns established

- **The first *renderer-state* consumer of the #131 channel — the channel's design premise proven.** #131 shipped inert, with only a test emitter; #134 is the first real producer, and the "co-located sibling module + optional injected observer" shape it establishes is the template for the render-layer consumer #125 still defers.
- **Optional trailing-param injection keeps a factory source-compatible across an instrumentation add.** `createSessionStore(init, observe?)` is a reusable shape for wiring an app-singleton-only concern (logging, telemetry) into a DI-friendly factory without touching any existing call site — zero edit fan-out, verified by both existing test files needing no change.

## Lessons learned

Two facts recorded in the architecture spec were corrected during implementation (worth flagging since a future ticket touching this file inherits them):

- **The vitest env is `node`, not `jsdom`** (`vitest.config.ts`), so `window` itself is `undefined` in a bare test run — not merely `window.pyry`. The guard must be `typeof window !== 'undefined'` first, not `window.pyry?.sendDiagnostic` alone (which would throw `ReferenceError: window is not defined`). `App.test.tsx`'s `beforeEach`/`afterEach` `globalThis.window` stub is the idiom to follow for any test exercising the observed path.
- **`seq` is stamped at `diagnosticLog.ts:122-128`**, not `:87-88` as an earlier draft of the spec cited — a line-number-only correction, no behavioral impact on this ticket.

No React re-render / effect-cleanup surprises (no React in this module — a plain function pair over a vanilla zustand store). No dependency-version issues (no new dependency). Written test-first per CLAUDE.md.
