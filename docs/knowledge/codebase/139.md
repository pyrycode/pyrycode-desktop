# #139 — Decode the v2 conversation list (`list_conversations` → `conversations`)

Transport half of the conversation-list foundation (mirror mobile #312); the renderer store slice
and on-connect request trigger are the sibling #208 (blocked by this one). Shipped as PR #209
(`c99fe8b`), code-review **PASS** (no findings, two informational notes). Security-sensitive (decodes
input from the untrusted relay AND adds a renderer→main command through the `isRendererCommand`
boundary guard); size S; an explicitly verified clone of the `request_snapshot` → `screen_snapshot`
vertical (#180), scaled to eight files because — like #180 — it needs both the inbound decode chain
*and* the outbound `RendererCommand` plumbing (#199 needed only five, inbound-only).

## Summary

The daemon speaks a request/response pair: the client sends a bare `list_conversations` and the
daemon replies `conversations` carrying an ordered `ConversationSummary[]`. Eight additive
touchpoints, no renames, no signature changes to existing exports:

- **Wire types** (`src/shared/wire/types.ts`) — `'list_conversations'`/`'conversations'` join
  `EnvelopeType`; `ListConversationsPayload` (documentary-only empty type, mirrors the daemon's
  `struct{}`), `ConversationSummary` (`id`, `name: string | null`, `is_promoted`, `is_archived`,
  `cwd`, `last_message_ts`, `last_used_at` — all always-present, no `omitempty`), and
  `ConversationsPayload { conversations: ConversationSummary[] }` (order preserved from the wire).
- **Request builder** (new `src/main/transport/listConversationsEnvelope.ts`) — `buildListConversations`,
  a **bare** control-frame builder cloned from `requestDebugBundleEnvelope.ts`, not the
  payload-carrying `requestSnapshotEnvelope.ts`: emits a present-but-empty `payload: {}` (never an
  omission, never `null` — the desktop's own `decodeEnvelope` requires a present payload even though
  the daemon's `ListConversationsPayload struct{}` would tolerate an absence).
- **Inbound decode** (`inboundMessage.ts`) — a new `requireStringOrNull` helper (the codec's first
  nullable-field checker: admits `string | null`, fails closed on missing/`undefined`/number/object —
  `name` is never absent on the wire), `parseConversationSummary` (fail-closed, one bad row throws),
  `parseConversationsPayload` (array narrow, mirrors `parseMessageChunkPayload`), and a new
  `conversations` `InboundDaemonMessage` kind. Content-free log: `{event, code: 'conversations',
  bytes, hash}` — **deliberately no `count`** (unlike `message_chunk`'s log), since a conversation
  count is more identifying than a message-batch size.
- **Connection method + consumer** (`daemonConnection.ts`) — `requestConversations()`, the `send`
  twin (inert no-op when `driver === null`, shares the one `nextEnvelopeId`, try/catch drops, never
  throws — parity #490); a new `case 'conversations':` on `switch(inbound.kind)` emits a fresh
  literal reusing the already-minimal decoded array verbatim (mirrors `messagesReceived`, **not**
  `snapshotReceived`'s content-drop — there is no secret field to drop).
- **Typed event** (`src/shared/ipc/events.ts`) — `{ type: 'conversationsReceived'; conversations:
  readonly ConversationSummary[] }` joins `DaemonEvent`, reusing the wire row type verbatim,
  snake_case fields intact (no camelCase remap, no invented `kind` enum — "discussion vs channel" is
  derived from `is_promoted` downstream by #208).
- **Command + boundary guard** (`src/shared/ipc/commands.ts`) — a bare `{ type:
  'requestConversations' }` joins `RendererCommand`; `isRendererCommand`'s case is a bare `return
  true` (no payload to validate) — this is the untrusted-boundary edit that makes the ticket
  security-sensitive.
- **Dispatch** (`src/main/index.ts`) — `case 'requestConversations': connection.requestConversations();
  return` in the single `onCommand` switch, direct to the connection method (no orchestrator — a list
  request has no consumer/reassembler).
- **Renderer bridge** (`daemonEventBridge.ts`) — `case 'conversationsReceived': return null`, present
  only because the load-bearing `assertNever` makes a new `DaemonEvent` arm a compile error until
  handled; the real consumer is #208's conversation-list store, not the session store.

`requestConversations()` has no caller in this ticket — #208 triggers it via `sendCommand` on
connect, exactly as #181 triggered `requestSnapshot`. `npm test` (764 pass, 3 skipped incl. the
real-handshake round-trip), `npm run typecheck`, `npm run build` all green.

## Patterns established

- **A payload-carrying inbound arm plus an outbound command arm both cascade onto the same two shared
  files (`types.ts`, `daemonConnection.ts`), so splitting an "exact #180 clone" ticket by
  inbound/outbound is strictly worse, not just unnecessary.** The spec's scope self-check argued this
  explicitly and it held: both halves would still touch the two shared files (guaranteed merge
  conflict) and neither half alone clears the "≥5 production files" split gate. The documented
  exception is TS exhaustive-union atomicity, not under-scoping (#311-style).
- **`requireStringOrNull` is the template for the codec's next nullable wire field, not a one-off.**
  It fails closed on missing/`undefined` (the field is never absent on the wire) while admitting a
  literal `null` as a distinct, valid value — the same "check the type, not truthiness" discipline
  `requireBoolean` established for `yolo` in #180, extended to the null case.
- **A minimal decoded row type stays minimal even when nothing is secret.** Unlike #180's
  `snapshotReceived` (which drops a genuinely sensitive `text` field), `conversationsReceived` has no
  field to drop — but `parseConversationSummary` still returns only the seven known fields, not a
  passthrough of unknown server-added keys, so the emitted event can't silently grow if the daemon
  adds a field later without this ticket's decode changing too.

## Lessons learned

From the merged PR's own "Lessons learned" section:

- **`name` is the codec's first nullable wire field**, so it needed a new `requireStringOrNull`
  helper alongside `requireString`/`requireBoolean`. The subtlety: `null` must be *admitted* as a
  valid value (AC2's distinct "unnamed" signal) while a missing/`undefined`/numeric field must still
  *fail closed* — it is easy to accidentally collapse "unnamed" to `""` or to accept `undefined` as
  equivalent to `null`, either of which would silently misrepresent the wire. `requireStringOrNull`
  checks `typeof value !== 'string' && value !== null` explicitly rather than a looser nullish check,
  which is what keeps `undefined` (absent field) rejected while `null` (present-and-null) passes.

## Handoff note (from the architect's security review)

`cwd` is an untrusted daemon-supplied string, decoded and carried here only as **opaque display
text** — never `path.resolve`d or opened. #141/#208 (and any later "open workspace" feature) MUST
treat `cwd` as untrusted and boundary-check (`path.resolve` + known-root prefix check) before any
real filesystem use. Not gated on this ticket (no fs operation happens here); flagged again so it
isn't lost between tickets.
