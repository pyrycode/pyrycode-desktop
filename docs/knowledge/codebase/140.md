# #140 — List ⇄ thread navigation shell under the paired route

PR #213 (`cec49bc`), code review PASS, no findings. Size S, 4 production files (2 new, 2 modified) +
tests. Not security-sensitive (pure renderer view-state — no keys, sockets, tokens, or frames).

Spec: `docs/specs/architecture/140-list-thread-navigation-shell.md`. Full design write-up:
[Paired shell feature doc](../features/paired-shell.md).

## Summary

Added the inner navigation spine for the paired region — the second-level router under the app
shell's `conversation` route, mirroring the `appRoute.ts` + `AppView` split
[#80](80.md) shipped:

- **New `pairedRoute.ts`** — `PairedRoute = 'list' | 'thread'`, a sealed `PairedNav` event union
  (`open`/`back`), and the pure total transition `nextPairedRoute(current, nav)`. `assertNever` default
  makes a future nav arm without a case a compile error.
- **New `PairedShell.tsx`** — `PairedShellView` (pure route→view, `assertNever`-guarded switch) +
  `PlaceholderList` (in-file, unexported, throwaway — one `Open conversation` button, [#141](https://github.com/pyrycode/pyrycode-desktop/issues/141) replaces it wholesale) +
  `PairedShell` (container, `useReducer(nextPairedRoute, 'list')`, ADR 0006).
- **`App.tsx`** — the `conversation` case in `AppView` now returns `<PairedShell onUnpaired={...}>`
  instead of `<ConversationScreen onUnpaired={...}>` directly.
- **`ConversationScreen.tsx`** — additive `onBack?: () => void` prop (the `onUnpaired?` precedent from
  [#166](166.md)) + in-file `BackControl` (returns `null` when `onBack` absent; otherwise a 48px
  icon-only back button with an inline `arrow_back` SVG, Figma node 16-11) rendered as the first child
  of `.conversation`, ahead of the existing `UnpairControl` header row.

814 tests pass (3 pre-existing skips), `npm run typecheck` and `npm run build` clean.

## Patterns established

- **Second-level router, same shape as the top-level one.** `pairedRoute.ts`/`PairedShell.tsx` are a
  peer set to `appRoute.ts`/`App.tsx`, not a variant — same pure-model + `assertNever`-guarded pure
  view + thin `useReducer` container split. Any future third-level router (e.g. inside Settings) should
  follow the identical shape rather than inventing a new one.
- **`current` kept unreferenced in a reducer signature for forward compat.** `nextPairedRoute(current,
  nav)` never reads `current` today (both transitions are absolute), but the parameter stays in the
  signature so a future stack-aware `back` is an added arm, not a breaking signature change. Verified
  safe because `noUnusedParameters` is off in both tsconfigs — call this out with a comment at the
  definition site so review doesn't flag the unused param as dead code.
- **Additive optional prop is still the right shape for a second consumer.** `onBack?` on
  `ConversationScreen` follows `onUnpaired?`'s exact shape (#166) for the same reason: a component with
  more than one caller (a bare test render vs. a shell-mounted render) needs its new capability to be a
  no-op, not a required prop, or every existing caller breaks.
- **A shell-rendered sibling vs. an additive prop on the child — the child's own top-app-bar affordance
  wins when the design puts it inside that screen's own chrome.** The architecture spec called this out
  explicitly: Figma 16-9 places `arrow_back` inside the thread's own top app bar, so `BackControl` is an
  addition to `ConversationScreen`, not a `PairedShell`-rendered sibling stacked above it (which would
  have produced a second header row over the existing `UnpairControl`).

## Lessons learned

(From the PR body's own "Lessons learned" section — both non-obvious enough to flag here rather than
assume are self-evident from reading the diff.)

- The back-arrow coexists as a separate leading row above the existing unpair header rather than a
  unified top app bar — a deliberate, spec-sanctioned interim, not an oversight. A future top-app-bar
  ticket consolidates back + title + overflow + unpair into one bar (Figma 16-9).
- `nextPairedRoute` keeps an unreferenced `current` param so a future stack-aware `back` is an added
  arm, not a signature change — safe only because `noUnusedParameters` is off in both tsconfigs; flag
  this if that compiler option is ever turned on.
