## Patterns established

- **Two exits from a sub-route can require two distinct nav arms even though one of them "looks
  like" `back`.** `pairServerCancelled` (→ `settings`) and `pairServerPaired` (→ `list`) land on
  different destinations, so neither reuses the existing absolute `back` arm (which always resolves
  to `list`). The rule going forward: only collapse an exit into `back` when its destination
  actually matches what `back` already does — don't reuse it just because the event is "leaving a
  screen."
- **A route with no entry, or an entry with no route, is dead code — ship them as one unit.** Same
  reasoning #333 used for its `settings` route + `ChannelList` entry button; repeated verbatim here
  for `pairServer` + the Settings row. Not split, not staged.
- **Reject the destroy-first sibling flow explicitly, don't just avoid it.** The `runUnpair`-first
  path (#166/#167's RepairControl) clears the paired-server record *before* showing pairing; this
  ticket's spec calls that out by name as the rejected alternative, because it would strand a user
  unpaired on cancel (a direct AC4 violation). Worth restating in any future ticket that touches
  re-pair/unpair ordering: persist-on-confirm-only is the invariant, not persist-then-show-pairing.

## Lessons learned

- Server-rendering a route that mounts `PairingScreen` needs a `globalThis.window = { pyry: {} }`
  stub in the `node` vitest env (`beforeEach`/`afterEach`), because `PairingScreen` derefs
  `window.pyry` at render time — the same stub `App.test.tsx` already uses for its own `pairing`
  route. Any future route or test that renders `PairingScreen` needs this stub or the render throws.

## Carried forward / deferred

- **Still single-server, overwrite semantics.** Confirming a new pairing replaces the one stored
  record (`pairedServerStore.ts`'s fixed `PAIRED_SERVER_NAME` slot) rather than adding a second
  server. Per-server `.${serverId}` keying remains a deliberately deferred, separate change.
- **No stack-aware back.** `pairServerCancelled`/`pairServerPaired` are explicit arms rather than a
  reuse of `back`, which sidesteps (without solving) the stack-aware-back gap `paired-shell.md`
  already flagged as a future need.
