# #166 — Unpair from the conversation screen, back to pairing

Renderer half of the unpair flow (split from #120), consuming the [unpair channel](../features/unpair-channel.md)
(#173) `window.pyry.unpair()` for the first time. Shipped as PR #176, code-review **PASS**.

## Summary

Adds a slim header row above the conversation thread with a two-step confirm (`Unpair` →
`Forget this pairing?` / `Cancel` / `Confirm`). On confirm, `runUnpair` — a pure, injected-effects
helper mirroring `composerSend.ts` — calls `window.pyry.unpair()`:

- **`result: 'ok'`** → dispatch a new `{ type: 'reset' }` session action, *then* call `onUnpaired`,
  which `App.tsx` wires to `setRoute('pairing')` — the exact reverse of the existing `onPaired`
  flip to `'conversation'`. Reset-before-flip so neither the pairing screen nor an immediate
  relaunch observes stale session state.
- **`result: 'error'` or a rejected invoke** → coerced to the same path: dispatch
  `{ type: 'failed', error: { code: 'unpair', message: 'Could not forget this pairing.',
  retryable: false } }`, which the existing `composerAvailability` predicate turns into the
  composer's `'Connection error'` hint + disabled send. The route never flips — no
  cleared-in-UI-but-still-on-disk half-state.

`AppRoute`/`routeForStatus` are untouched — this is a runtime user action, not a launch-status
mapping.

## Patterns established

- **`runUnpair` mirrors `composerSend.ts`'s shape exactly**: the one place with branching logic
  (ok/error) that a server-render test can't drive (async click) is extracted into a pure,
  React-free function with every effect injected (`unpair`, `dispatch`, `onUnpaired`), tested with
  plain spies. The confirm-phase toggle itself is trivial `useState` glue left untested in the
  container, by the same precedent as `Composer`'s `text` and `PairingScreen`'s container wiring.
- **A route flip is fail-safe by construction when it only fires on the narrowest success value.**
  `runUnpair` calls `onUnpaired()` only inside the `result.result === 'ok'` branch — a thrown/
  rejected invoke is caught and coerced to the same `failed`-dispatch path as an explicit
  `result: 'error'`, so there is exactly one route to "stay on screen with a visible error" and one
  route to "navigate," with no third silent-success/silent-fail state.
- **`window.pyry.*` is dereferenced only inside the interaction handler, never during render** —
  same discipline as `Composer.handleSubmit` — so the server-rendered container smoke test never
  touches the preload bridge.
- **A store "reset to initial" action is distinct from an existing "clear status only" action.**
  `disconnected` deliberately preserves `messages` (reconnect-clears-history was left an open
  question — see [session-store.md](../features/session-store.md)); `reset` is a new, separate
  mutation path for the one caller (unpair) that actually wants both facets cleared. Returning the
  shared `initialSessionState` const (not a fresh object) makes a second reset a no-op reference.

## Lessons learned

From the merged PR's own "Lessons learned" section:

- The visible affordance intentionally does **not** port Figma node `17-12` (the mobile
  Settings → Connection server row) — the spec scoped it to a minimal, de-emphasized text control.
  No `--color-error` token exists on desktop and a minimal escape hatch needs none; the mobile
  `#BA1A1A` destructive color is deliberately unused. This is documented directly in
  `conversation.css` so a future top-app-bar ticket reads the divergence as intentional, not an
  oversight.

From code review (PASS, one non-blocking NIT):

- **Focus is not managed across the confirm-phase toggle.** Activating `Unpair` unmounts the idle
  trigger and mounts the `Cancel`/`Confirm` pair (and `Cancel` reverses it), so a keyboard user's
  focus lands on `<body>` after each transition. Reachability and visible focus rings
  (`:focus-visible` → `--color-outline`) are otherwise correct, so this was accepted as a polish
  item for a future top-app-bar pass rather than a blocker for a minimal escape hatch — worth
  picking up if/when #166's control is folded into a real top app bar or overflow menu.
- **Live-session teardown remains explicitly deferred** (carried over from #173's own open
  question, reaffirmed here): unpair clears the *stored* pairing and resets *renderer* state; it
  does not proactively tear down an already-live Noise session in main. In the target scenario
  (stale/wrong record, dead conversation screen) the session is not live, so this is a
  no-observed-failure edge — a subsequent re-pair supersedes any stale session via connect-on-pair
  (#82).
