# #167 — Offer re-pair on terminal connection failure or daemon rejection

Split from #120 (twin of [#166](166.md)). Renderer-only: a pure `shouldOfferRepair` predicate beside
`composerAvailability`, plus a conditionally-shown `Re-pair` affordance on the conversation screen that
reuses #166's `runUnpair` clear-and-return-to-pairing flow. Shipped as PR #189, code-review **PASS**
(two non-blocking NITs).

## Summary

When the stored pairing can no longer be used — a terminal transport/handshake failure or a
non-retryable daemon rejection — the conversation screen now **proactively** surfaces the same
clear-and-return-to-pairing path #166 added as a manual control, instead of leaving the user on a dead
screen with a disabled composer and no recovery (the live incident this closes, 2026-07-07, #120).

- `shouldOfferRepair(status)` — pure, beside `composerAvailability` in `composerSend.ts`. `true` only
  for `status.type === 'error' && !status.error.retryable && status.error.code !== 'unpair'`.
- Exported pure `RepairPrompt({ status, onRepair })` view + in-file `RepairControl` container, split
  along the file's established pure-view/store-bound-container seam (`MessageThread`, `StatusSheet`).
- `Re-pair` fires the **same** `runUnpair` wiring `UnpairControl` uses — no second clear path (AC2).

## Patterns established

- **The predicate is a boolean over one arm, not a total mapping** — unlike `composerAvailability`
  (which branches on all four `ConnectionStatus` arms and needs `assertNever` exhaustiveness),
  `shouldOfferRepair` is a single boolean expression. No switch, no exhaustiveness guard needed for a
  boolean gate that only cares about one arm.
- **A self-loop guard on a reused failure path.** `runUnpair` synthesizes its own
  `{ code: 'unpair', retryable: false }` error on a failed clear. `!retryable` alone would make a failed
  re-pair immediately re-satisfy the predicate and re-offer itself — the `code !== 'unpair'` clause is
  load-bearing, not defensive, and is the reason this predicate cannot be reduced to `!retryable` alone.
- **`status` as a prop, not a container-only read, when the populated branch isn't server-render-
  reachable.** Same zustand v5 `getInitialState()` gotcha #177/#181 already hit
  (`ConversationScreen.test.tsx:114-118`): a store-bound container always server-renders the *initial*
  `disconnected` state, so `RepairPrompt` takes `status` as an explicit prop — the true-branch is proven
  by server-rendering the pure view directly with an arbitrary status, not by mutating the store and
  re-rendering the container.
- **No confirm phase, no busy guard, by deliberate contrast with `UnpairControl`.** `UnpairControl`
  guards an *accidental* destructive click while everything still works; `RepairControl` only ever
  appears in an already-terminal error, so a confirm step is pure friction. No busy state either: the
  affordance self-hides on both outcomes (`ok` → store resets to `disconnected`, predicate → false,
  route unmounts the screen; `error` → store lands on `code: 'unpair'`, predicate → false), and
  `runUnpair` never rejects (catches internally), so `handleRepair` fires a bare `void runUnpair(...)`
  with no `.then` and no unhandled-rejection risk.
- **`window.pyry` dereferenced only at interaction time.** `RepairControl.handleRepair` reads
  `window.pyry.unpair` inside the handler body, never during render — the same discipline as
  `Composer.handleSubmit` and `UnpairControl.handleConfirm` — so the container's server-render smoke
  test never touches the preload bridge.

## Lessons learned

From the merged PR's own "Lessons learned" section:

- The `!retryable` gate alone isn't enough: `runUnpair` synthesizes its own
  `{ code: 'unpair', retryable: false }` failure error, so a proactive re-pair prompt keyed only on
  non-retryable `error` would re-offer itself in a loop when the clear fails. The `code !== 'unpair'`
  clause is load-bearing, not defensive.

From code review (PASS, two non-blocking NITs, neither applied):

- **The `'unpair'` self-loop guard is a bare literal**, duplicated independently in
  `composerSend.ts`'s predicate, `composerSend.test.ts`'s test, and `unpairAction.ts`'s
  `UNPAIR_FAILED_ERROR.code` (a module-private const) — nothing cross-links the three, so a future
  rename of that code would silently break AC5 with no test catching it. Deliberate per the spec
  (literal, not a shared export, to keep the module surface minimal); a shared `UNPAIR_ERROR_CODE`
  export would make the coupling deterministic if a future ticket touches this seam again.
- **`.composer__repair` is a slightly misleading BEM name** — the element is a direct child of
  `.conversation` (a sibling of `.composer`, not nested inside it), so `.conversation__repair` would
  match the DOM more literally. `composer__` was kept because the affordance conceptually extends the
  composer's error hint. Cosmetic only, not fixed.
