## What it does

On the renderer's bare `requestDebugBundle` command, drives **request → reassemble → save** end to end and reports progress plus exactly one terminal result back to the window. It is the composition-root glue: the transport (#115/#116) and persistence (#117) slices stay Electron-free and IPC-free; this ticket is where they meet the daemon-event channel (#168) and `app.getPath('downloads')`.

## Patterns established

- **`active` is set synchronously *before* the transport call, not after.** `daemonConnection.requestDebugBundle` can fail the consumer *synchronously* when there's no driver (`not-connected`) — its `fail` handler is what clears `active`. Setting the flag after the call would leave it stuck `true` on that path. `request()` has no `await` anywhere in its body, so two calls can never interleave mid-body — the second always observes a fully-settled `active` from a prior turn.
- **The single-in-flight flag clears at exactly the terminal-emit sites, not at `complete`.** For a successful stream the terminal is the *save* outcome (`debugBundleSaved`/`write-failed`), not `complete` itself — `complete` only kicks off the async `save`. Clearing `active` inside `complete` (before the save settles) would let a second `request()` in during the save window and re-arm the transport's reassembler slot out from under the first download. This is the crux of AC4 and was the primary thing code review verified against the surrounding code, not just the diff.
- **Fail-map is a total, exhaustive `switch` with a `never` default, mirroring the codebase's per-module `assertNever` idiom** (`daemonEventBridge.ts`) rather than a shared helper — consistent with this repo's convention of not centralizing that one-liner.
- **Save-errno collapse is a separate path from the `BundleFailReason` switch, never routed through it.** The reject handler in `save(bytes).then(_, onReject)` takes no error parameter at all — the fs errno is structurally impossible to leak, not just discarded by convention.
- **`Object.keys` allowlist assertions on every emitted event**, continuing #116's discipline — each test asserts the emitted object's exact key set (`['type','reason']`, `['type','path']`, `['type','chunksReceived']`), not just that the wanted field is present.

## Lessons learned

- **Modeling the async-save window needs a controllable deferred, not just `await Promise.resolve()`.** The AC4 test that proves a second `request()` is short-circuited *between* `complete()` and the save settling uses a hand-rolled `deferred<T>()` (a promise whose `resolve`/`reject` are captured externally) so the test can assert the locked state mid-flight, then resolve and assert the unlock — a plain immediately-resolving stub can't represent that window at all.
- **`flush()` via `setTimeout(r, 0)`, not a fake clock.** Draining the microtask queue after a real (non-mocked) promise settles needed a zero-delay macrotask, since a real `.then()` chain queues microtasks that a synchronous assertion would race. Fake timers were avoided entirely — the async behavior under test *is* real promise scheduling.
- **The AC1 integration test reused the #116 harness verbatim** (`standUpRoundTrip`, `bundleFrames`, the `waiter.notify()`-from-`emit` pattern) rather than building new fixture code — the same lesson #116 itself flagged forward: poke the existing waiter from the new emit path so the bounded wait resolves on the terminal, since bundle frames themselves emit no `DaemonEvent`.
- **Code review NIT, non-blocking, carried forward:** `src/main/index.ts`'s `onCommand` switch has no `default: assertNever(command)` arm even though this PR already uses the `assertNever` idiom in `debugBundleDownload.ts` and `commands.ts` documents the union as growing additively. Today `isRendererCommand` guards the boundary and the switch is complete, so nothing is broken — but a future third command member added to `RendererCommand` without a matching `case` here would silently no-op instead of failing to compile. Worth picking up whenever `index.ts`'s switch is next touched.

## Deferred / carried forward

- **A never-terminating / slow-dribble bundle stream from an authenticated daemon** leaves a download wedged (`active` never clears, later requests ignored). Flagged in the architect's security review as out of scope for this ticket — the correct mitigation is a per-message read/idle deadline at the transport layer (`relayConnection` timeout discipline), not a stochastic timeout guessed in the orchestrator. No hang has been observed; a real socket drop already resolves via the existing `connection-lost` teardown net (#116).
- **`onCommand`'s missing `assertNever` default** — see Lessons learned above.
- **#72 — the download button + progress UI.** The only remaining consumer of this feature; it drives `window.pyry.sendCommand({type:'requestDebugBundle'})` and reads the three `DaemonEvent`s this ticket now actually emits (previously inert since #168).
