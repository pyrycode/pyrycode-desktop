# #17 — Typed command channel: window → background process

**Shipped:** 2026-07-03 · **Size:** S · **Scope:** shared + background + preload (`src/shared/ipc/`, `src/main/`, `src/preload/`) · additive to the #18 IPC module, zero consumer cascade · no new dependency.
**Spec:** `docs/specs/architecture/17-typed-command-channel.md` · **PR:** [#24](https://github.com/pyrycode/pyrycode-desktop/pull/24) (review: PASS, no blocking findings; two NITs, non-gating).

The **command-pipe half** of the background↔window bridge — the reverse-direction twin of the event half (#18). A sealed `RendererCommand` union + `COMMAND_CHANNEL` constant join `DaemonEvent` in `src/shared/ipc/`, with a pure `sendMessageCommand` constructor and an `isRendererCommand` boundary guard; the preload exposes a typed `sendCommand` on `window.pyry`; `src/main/receiveCommand.ts` adds an `onCommand` seam that validates each command at the untrusted renderer→main boundary before surfacing it to a single handler. No transport is wired — that is #11 (composer submit) and the transport (#4/#7), which consume this seam. See the [command-channel feature doc](../features/command-channel.md) for the full contract, union shape, and data flow.

Split from #16 (the same split produced #18 background→window events and #19 events→`SessionAction`). Note: `sessionStore.ts`'s doc comments still say "#3 translates … #12 binds" — that predates the renumber; read "#3" there as "this channel work."

## Patterns established

- **The renderer→main boundary gets a real runtime guard; the mirror-image main→renderer half did not.** This is the one place #17 diverges from #18. Every IPC message crossing `ipcMain` is untrusted-to-trusted, even though both sides are our own code, so `onCommand` gates every incoming command through `isRendererCommand` before the handler sees it. **The guard is what makes the handler's `RendererCommand` type honest** — without it the type would claim `RendererCommand` over an attacker-controllable `unknown`. When adding any future renderer→main channel, validate at the seam; do **not** reuse the event half's "trusted producer, no validator" reasoning — there is no transitive trust across this boundary.
- **The guard and the union must grow in lockstep.** `isRendererCommand` uses a `switch (value.type)` with `default: false`. A union member added without a matching case is **silently dropped at the boundary** — a correctness trap. The code review (NIT) and the spec (Open Question 2) both flag a type-only exhaustiveness tripwire (`Record<RendererCommand['type'], true>`) worth adding when the second member (connect/disconnect) arrives. Mirrors #19's `assertNever` discipline.
- **Pure constructor, tested; boundary guard, tested; wiring left to typecheck.** `sendMessageCommand` (field pass-through, verbatim reuse of `SendMessagePayload`) and `isRendererCommand` (accept/reject matrix) are the unit-test surface. The contextBridge/`ipcRenderer`/`ipcMain` wiring is intentionally **not** unit-tested (no Electron harness) — `npm run build` + `npm run typecheck` cover it, and an unknown command shape → compile error (AC4, inherent to the `RendererCommand` return/param types).
- **`message_id` generation deliberately lives with the producer (#11), not the constructor.** `sendMessageCommand` stays pure by taking an already-assembled `SendMessagePayload`; #11's composer mints the id (`crypto.randomUUID()` — main-safe) before calling it. Keep randomness out of the pure factory.
- **Structural source over `ipcMain` for testability.** `receiveCommand.ts` types its parameter as the minimal `CommandSource` (`{ on, removeListener }`) and imports no `electron` — a `vi.fn()` fake satisfies it, a real `ipcMain` is structurally assignable. Same shape #18 used with `DaemonEventSink`. Reuse for any main-side helper that touches an Electron object but shouldn't require an Electron test harness.
- **Fire-and-forget `send`/`ipcMain.on`, not `invoke`/`ipcMain.handle`.** Commands need no synchronous reply — the daemon's response returns later as a separate `DaemonEvent` (#18). Using `send` means there is no reply channel a handler could leak data back through. `sendCommand` is `void` (no floating promise), correct for `ipcRenderer.send`.
- **AC5 enforced by construction.** `RendererCommand` references only `SendMessagePayload` — no member has a token/key/byte field, so a developer cannot serialize a secret onto this channel. `COMMAND_CHANNEL` is hardcoded inside `sendCommand`; `ipcRenderer` never crosses the bridge; the `IpcMainEvent` first arg is stripped in the receiver (no `.sender`/`.reply`/`.ports` leak); the only log is a fixed string, never the payload. Same secret-free-by-type discipline #18 established for the event union.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section, plus the code-review notes.*

- **The renderer→main direction needs a runtime guard the main→renderer direction did not.** `isRendererCommand` at `onCommand` is what makes the handler's `RendererCommand` type honest, since the incoming value is untrusted `unknown`. The guard and the union must grow in lockstep — a union member the `switch` doesn't cover is silently dropped at the boundary.
- **Property access on `unknown` narrows without a cast.** After `typeof value === 'object' && value !== null`, the `in` operator (`'type' in value`, `'payload' in value`) narrows the property to `unknown`, so `isRendererCommand` reads fields with **no** non-null assertion (`!`) and **no** blind `as` cast — an honest `value is RendererCommand` predicate. Prefer this to casting when writing runtime guards.
- **Same relative-import gotcha as #18 applies.** `src/main` and `src/preload` have no `@shared` alias (only the renderer/`tsconfig.web.json` does), so `receiveCommand.ts` and `preload/index.ts` import the contract as `../shared/ipc/commands`, not `@shared/ipc/commands`. Recorded in project memory as `shared-alias-not-available-in-main-preload`; test files (vitest) may use `@shared/...`.

## Deferred (open questions carried forward)

- **Single registration + teardown ownership (#11).** The composition root must call `onCommand(ipcMain, handler)` exactly once for the app lifetime and invoke the returned unsubscribe on teardown. Registering twice double-dispatches every command. #17 provides the handle; wiring is deferred (no live receiver to observe yet). Flag when #11 wires the first handler.
- **Exhaustiveness tripwire when the union grows (code-review NIT).** Add the `Record<RendererCommand['type'], true>` type-only cross-check — and the matching `isRendererCommand` case — when connect/disconnect land, so a new member the guard doesn't validate becomes a compile error rather than a silent drop.
- **Symmetric guard-test coverage (code-review NIT).** The "non-string field" rejection case exercises `conversation_id: 1` but not a non-string `message_id`/`text`. The guard checks all three symmetrically so correctness is fine; add the two cases if touching the test for tidiness.
- **Dropped-command observability.** #17 logs a fixed-string `console.warn` on a dropped malformed command (no renderer data). If a metric on malformed-command rate becomes useful (e.g. to detect a misbehaving renderer build), the seam can count drops later — deferred, no evidence needed now.
- **`sandbox: false` in `src/main/index.ts:17`.** Pre-existing scaffold value, out of scope for #17 (must not touch that file). Route the flip to a dedicated hardening ticket (the same one #18 flagged) — do not expand #17 to flip it.
