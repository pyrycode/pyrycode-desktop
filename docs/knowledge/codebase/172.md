# #172 — Paired-server store gains an erase capability

**Shipped:** 2026-07-08 · **Size:** XS · **Scope:** a symmetric `clear()` method on the background-process
[paired-server store](../features/paired-server-store.md), so a later ticket ([#173](https://github.com/pyrycode/pyrycode-desktop/issues/173))
can erase the persisted pairing record and return the app to a clean not-paired state. Domain
capability only — no IPC, no preload, no renderer reach. Split child of
[#165](https://github.com/pyrycode/pyrycode-desktop/issues/165); twin of the #131→#134 "ship the
store capability ahead of its IPC consumer" shape.
**Spec:** `docs/specs/architecture/172-paired-server-store-erase.md` · **PR:** [#174](https://github.com/pyrycode/pyrycode-desktop/pull/174).

## What shipped

Two files only — `src/main/pairedServerStore.ts` (+23/-1) and `src/main/pairedServerStore.test.ts`
(+76 lines, 6 new tests):

- **New `ClearablePairedServerStore` interface**, extending the base `PairedServerStore` with
  `clear(): Promise<void>`. `createPairedServerStore`'s return type widens from `PairedServerStore`
  to `ClearablePairedServerStore` — the base interface itself is untouched.
- **`clear()`** is a one-line delegation: `await secureStore.delete(name)`, using the same `name`
  local (`deps.name ?? PAIRED_SERVER_NAME`) that `save`/`load` already route through. No
  `try`/`catch` — a `secureStore.delete` failure propagates unchanged.
- **Test additions:** erase-then-not-paired (AC2), idempotent-when-absent (AC3), name-precision +
  device-keypair-preserved via a Map-backed fake seeded under both `PAIRED_SERVER_NAME` and the
  literal `'pyrycode.device_static'` (AC1/AC4), injected-name honored (the deferred per-server-id
  seam), fail-closed propagation via a new `control.deleteError` toggle on `fakeSecureStore`, and
  an extension of the existing log-free test to cover `clear()`'s happy and delete-failure paths.

`npm test` (584 pass / 3 pre-existing skips) and `npm run build` (typecheck + electron-vite) both
green. Typecheck passing is the evidence that the widened return type assigns into all three
composition-root call sites (`createPairingConfirmation`, the pairing-status handler, the
daemon-connection driver deps — `src/main/index.ts:132-167`) with zero consumer edits.

## Patterns established

- **Widen the concrete return type, not the shared interface, to ship a capability ahead of its
  consumer without a fixture cascade.** Every existing consumer and fake (pairing-status,
  pairing-confirmation, daemon-connection) is typed against the base `PairedServerStore`; because
  `ClearablePairedServerStore` is a subtype, `createPairedServerStore`'s wider return assigns into
  every one of those slots for free. None of the three base-typed fakes needed a `clear` stub. This
  is the same shape #131 used for its store/logger capability ahead of its IPC consumer #134, now
  proven a second time on a different store.
- **Structural AC enforcement over runtime checks.** AC4 (device keypair preserved) needed no
  defensive code — `clear` only ever names its own fixed `name` local, and the device static
  keypair (`pyrycode.device_static`, `src/main/deviceKeypair.ts:70`) lives under a different name
  in a different store instance entirely. The test proves this by seeding both names in one
  Map-backed fake and asserting only one is gone; there is no code path that could touch the other.

## Lessons learned

- The code-review NIT (non-blocking): the AC4 test hardcodes the literal `'pyrycode.device_static'`
  rather than importing `DEVICE_STATIC_KEY_NAME` from `deviceKeypair.ts` — deliberate, per spec, to
  keep the store's test suite free of a cross-module dependency. AC4's real guarantee is structural
  (`clear` only ever names its own `name` local), not this literal match, so a future rename of the
  device-static key name would not silently break this invariant — it's worth re-checking the
  literal if `deviceKeypair.ts` ever changes that constant.

No React re-render or effect-cleanup surprises (no React in this module — a plain factory over an
injected `SecureStore` seam, same as `save`/`load`). No dependency-version issues (no new
dependency).

## Carried forward / deferred

- **The IPC channel + preload method that let the renderer trigger `clear()`** ship in
  [#173](https://github.com/pyrycode/pyrycode-desktop/issues/173) (blocked-by #172). The security
  review's MUST-verify for #173: the channel must be value-free (no args), so a compromised
  renderer can at most trigger an unpair (an availability annoyance), never leak or inject a
  secret.
- **Live-session teardown on unpair is out of scope.** `clear()` erases the at-rest record only —
  it does not tear down an in-flight Noise session or relay socket. Orchestrating that belongs to
  #173's caller or a later ticket.
