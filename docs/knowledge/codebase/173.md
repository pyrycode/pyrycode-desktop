# #173 — Unpair IPC surface: value-free channel + handler + preload method + registration

**Shipped:** 2026-07-08 · **Size:** S · **Scope:** the renderer→main IPC surface that lets the window
ask the background process to erase the stored pairing, built on top of #172's
`ClearablePairedServerStore.clear()`. Four additive pieces — a shared value-free contract, a
main-side handler, a preload bridge method, and composition-root registration + teardown — the
byte-for-byte [pairing-status signal](../features/pairing-status-signal.md) (#79/#80) / [diagnostics
channel](../features/diagnostics-channel.md) (#131) footprint. No caller yet; the visible unpair
control ships in renderer follow-ups #166/#167. Split child B of #165 (twin of #172, split child A).
**Spec:** `docs/specs/architecture/173-unpair-ipc-surface.md` · **PR:** [#175](https://github.com/pyrycode/pyrycode-desktop/pull/175).

## What shipped

Five files — three new, two additive edits, zero consumer cascade:

- **`src/shared/ipc/unpair.ts`** (new) — `UNPAIR_CHANNEL = 'pyry:unpair'` + a value-free
  `UnpairResult = { result: 'ok' } | { result: 'error' }`. No runtime logic, no `isUnpairRequest`
  guard (the invoke carries zero arguments, so there is no untrusted request field), imports nothing
  from `src/main`. The error arm deliberately carries no reason field.
- **`src/main/unpairHandler.ts`** (new) — `registerUnpairHandler(target, { store })`, a faithful clone
  of `pairingStatusHandler.ts`: an injected minimal `UnpairHandleTarget` (`handle`/`removeHandler`),
  single-registration + exact-teardown, stateless, `try { await store.clear(); ok } catch { error }`
  classify-don't-forward, zero `console.*`. The store dep is typed against the concrete
  `ClearablePairedServerStore` (not base `PairedServerStore`), so the handler's fake stubs only
  `clear`.
- **`src/preload/index.ts`** (+11) — one fixed-channel method, `unpair: () => Promise<UnpairResult>`,
  called with no arguments. No `index.d.ts` edit — `PyryApi = typeof api` re-derives
  `window.pyry.unpair` automatically.
- **`src/main/index.ts`** (+11) — `registerUnpairHandler(ipcMain, { store: pairedServerStore })` +
  `app.on('will-quit', ...)` teardown, registered in the pairing-status sibling slot (needs only the
  store, no `connection`), reusing the single composition-root `pairedServerStore` — no second store
  built.
- **`src/main/unpairHandler.test.ts`** (new, 6 tests) — registration + exact teardown against the
  exported constant; success → `ok`; erase-exactly-once-and-never-read (`clear` called once,
  `load`/`save` never); throw → value-free `error` (resolves, never rejects); no secret/detail
  crosses back (`JSON.stringify` doesn't contain the seeded keychain-path substring; success
  stringifies to exactly `{"result":"ok"}`); log-free on both the ok and error paths (`console.error`/
  `log`/`warn` spied, none called).

`npm test` (590 pass / 3 pre-existing skips, 6 new), `npm run typecheck`, and `npm run build` all
green. TDD: the six tests went RED against a stub with no registration, GREEN once the real handler
landed.

## Patterns established

- **Clone the nearest twin, don't design from scratch.** The spec named `pairingStatus.ts` /
  `pairingStatusHandler.ts` as the literal source pattern and the developer copied it with exactly
  two deltas: the store dep type (`ClearablePairedServerStore` vs. base `PairedServerStore`) and the
  store call (`clear()` vs. `load()`). Code review found zero findings — "clean, faithful clone" —
  because the design space was already closed by precedent, not because the ticket was trivial.
- **Value-free-by-construction generalizes past diagnostics.** #131 established "no field beyond the
  allowlist/discriminant" for a logging boundary; #173 applies the same discriminated-union-with-no-
  extra-field shape to a *destructive-action* boundary. The error arm's missing `reason` field is the
  same judgment call #79/#80 made for `pairingStatus`'s `error` outcome: a coarse category is still a
  leak surface, so omit it until a real consumer needs to distinguish sub-cases.
- **A capability's IPC surface can ship strictly after its domain capability, with the store's
  widened-return-type trick absorbing the whole gap.** #172 widened `createPairedServerStore`'s
  return type to `ClearablePairedServerStore` with no cascade; #173 is the first (and, per #172's own
  doc comment, only currently-anticipated) consumer of that widened type. This is the third instance
  of the #131→#134 "ship the boundary ahead of its consumer" shape in this codebase (after
  #79→#80/#43-44 and #131→#134).

## Lessons learned

- The architect flagged one design finalization worth carrying forward for the #166/#167 consumers:
  the result discriminant field is named **`result`** (`{ result: 'ok' | 'error' }`), not `status` —
  a pre-split PO refinement had sketched `status`, but the spec (source of truth) settled on `result`
  to match `pairingStatus`'s own field-naming convention exactly. Renderer code calling
  `window.pyry.unpair()` must destructure `.result`, not `.status`.
- No React re-render, effect-cleanup, or dependency-version surprises — no React in any of the three
  new/edited files (`src/shared`, `src/main`, `src/preload` only).

## Carried forward / deferred

- **The visible unpair UI** — a manual unpair action and an offer-re-pair-on-failure prompt that call
  `window.pyry.unpair()` — ships in #166/#167, both re-pointed from #165 to #173 when this ticket
  split off.
- **Live-session teardown on unpair stays out of scope**, same as #172: `clear()` erases the at-rest
  record only; it does not tear down an in-flight Noise session or relay socket. Orchestrating that is
  the #166/#167 caller's concern or a later ticket.
