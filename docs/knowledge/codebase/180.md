# #180 — Fetch the session's Model/Effort/YOLO via `screen_snapshot`

Split A of [#156](156.md) (the full Run configuration sheet). Shipped as PR #185, code-review
**PASS** (no findings). Delivers the transport data path only: an on-demand `request_snapshot` →
`screen_snapshot` round-trip in the Electron background process, a fail-closed field-for-field
decode of the reply, and one typed `snapshotReceived` daemon event carrying only `model` / `effort`
/ `yolo` to the window. No UI, no store facet — the render sits in #181 (blocked on this).

## Summary

`screen_snapshot` is ADR-025's always-available, parser-independent daemon escape hatch — **not**
gated on the `interactive` capability, so this desktop client can fetch it today even though it
withholds `interactive` (pyrycode #847/#848). The ticket follows the `send_message` spine
end-to-end, five thin additions:

- **Wire types** (`src/shared/wire/types.ts`) — two new `EnvelopeType` members
  (`request_snapshot`/`screen_snapshot`) and two ported payloads: `RequestSnapshotPayload
  {conversation_id}` (outbound) and `ScreenSnapshotPayload {conversation_id, text, ts, model, effort,
  yolo}` (inbound), field-for-field with the daemon's `internal/protocol/snapshot.go`, no `omitempty`.
- **Outbound builder** (new `src/main/transport/requestSnapshotEnvelope.ts`) — `buildRequestSnapshot`,
  a structural clone of `buildSendMessage`: payload-carrying (unlike the bare
  `request_debug_bundle`), pure `(id, ts, payload) → Uint8Array`.
- **Connection method** (`daemonConnection.ts`) — `requestSnapshot(payload)`, the `send` twin: inert
  no-op when `driver === null` (a snapshot has no consumer to fail, unlike `requestDebugBundle`),
  shares the one `nextEnvelopeId` counter, never throws (parity #490).
- **Inbound decode** (`inboundMessage.ts`) — a new `snapshot` `InboundDaemonMessage` kind and
  `parseScreenSnapshotPayload`, fail-closed like `parseMessagePayload`; a new `requireBoolean` sibling
  of `requireString`/`requireNumber` checks `yolo`'s *type*, not truthiness, so `''`/`false` decode as
  valid values (AC2/AC3), never absences.
- **Command + event surface** (`commands.ts`/`events.ts`) — `requestSnapshot` joins `RendererCommand`
  with its own `isRequestSnapshotPayload` guard (the untrusted renderer→main boundary check, the
  reason this ticket is security-sensitive); `snapshotReceived {model, effort, yolo}` joins
  `DaemonEvent` as a **dedicated minimal shape**, deliberately not reusing `ScreenSnapshotPayload` —
  the content-minimisation seam that keeps the rendered-screen `text` off the wire to the renderer.

Both channels are the existing generic `sendCommand`/`onDaemonEvent` — no new IPC channel, no new
preload method.

## Patterns established

- **A payload-carrying request/reply pair can ship as one ticket when the daemon reply needs no new
  state machine.** Unlike the debug-bundle split (request #115 / reassembly #116 / orchestrator
  #169), a `screen_snapshot` is one fire-and-forget request and one independent, uncorrelated reply —
  no reassembler slot, no consumer, no pending-request map. The whole round trip (builder → connection
  method → inbound decode → event) fits in one S-sized ticket; see the spec's scope-and-size
  self-check for why splitting it further would have been strictly worse (a request-vs-reply split
  double-touches `daemonConnection.ts` and `types.ts` — a guaranteed merge conflict).
- **A dedicated minimal event shape is the content-minimisation control**, not a code-review
  afterthought. When an inbound wire payload carries a sensitive field the design doesn't want to
  surface (`text`, here — the rendered screen contents), don't reuse the wire type for the outbound
  `DaemonEvent`; declare a narrower one by hand so the sensitive field has no field to leak into.
  Reusable for any future daemon reply with a "carries more than the renderer should see" shape.
- **Correlation-by-type, not `in_reply_to`, is acceptable when there's a single in-flight request and
  a single conversation.** The desktop transport has no request/reply correlation map yet; an
  unconditional "any `screen_snapshot` that arrives gets decoded and emitted" is safe today because
  only the authenticated daemon can produce one. Revisit if/when multiple conversations or concurrent
  snapshot requests become real (evidence-based, not preemptive).

## Lessons learned

From the merged PR's own "Lessons learned" section:

- **The spec's "the renderer needs zero change" claim was inaccurate for this repo.**
  `translateDaemonEvent` (`daemonEventBridge.ts`) has a load-bearing `assertNever` exhaustiveness
  guard, so adding a `DaemonEvent` member is a compile error until it gets a case — added
  `case 'snapshotReceived': return null` (mirroring the #168 debug-bundle arms). This is **one
  production file beyond the spec's stated 7** (8 total: `types.ts`, `commands.ts`, `events.ts`,
  `inboundMessage.ts`, `daemonConnection.ts`, `index.ts`, `requestSnapshotEnvelope.ts` (new),
  `daemonEventBridge.ts`). The generic preload channels genuinely need no change; it's the typed
  renderer *consumer* — any module with an exhaustive switch over `DaemonEvent` — that always does.
  Any future spec estimating "N files" for a new `DaemonEvent` member should budget for
  `daemonEventBridge.ts` up front.

From code review (PASS, no findings — the architect's one SHOULD-FIX guardrail (confirm `text` never
reaches the `snapshotReceived` event) was verified rather than left as a finding):

- The content-minimisation seam was verified **by construction and by test**: the dedicated
  `snapshotReceived` shape has no field `text` could occupy, the emit site
  (`daemonConnection.ts:262`) explicitly drops `text`/`ts`/`conversation_id`, and the AC5 E2E test
  asserts the secret screen text and `conversation_id` are absent from every emitted event and from
  the content-free diagnostic log. Nothing to fix, but a useful confirmation that "reuse the wire type
  for the event" is the failure mode this design pattern exists to prevent.
