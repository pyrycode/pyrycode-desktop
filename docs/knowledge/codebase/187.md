# #187 — Run configuration sheet: request a snapshot on open and hold Model/Effort/YOLO

Split A (data path) of [#181](https://github.com/pyrycode/pyrycode-desktop/issues/181) (itself
split from [#156](156.md)); sibling [#188](https://github.com/pyrycode/pyrycode-desktop/issues/188)
(render) is blocked on this. Shipped as PR #190, code-review **PASS** (no findings). Not
security-sensitive — the untrusted renderer→main boundary guard (`isRequestSnapshotPayload`)
already landed with [#180](180.md).

## Summary

Wires the renderer half of the Run configuration data path that [#180](180.md)'s transport left
unconsumed: `translateDaemonEvent` already mapped `snapshotReceived` to `null`, reserved for "the
Run configuration render bridge, not the session store." This ticket **is** that consumer — and
delivers **no visible surface**; the sheet still renders nothing new. It ships three new modules
plus a one-line mount, following the established store/logic/container split
(`sessionStore.ts` / `composerSend.ts` / `Composer`):

- **`src/renderer/src/store/runConfigStore.ts`** — a dedicated Zustand vanilla store (a separate
  consumer, per #180's landed comments, *not* a session-store facet), mirroring `sessionStore.ts`'s
  DI-factory → app singleton → hook → selectors shape but with a **single setter**
  (`setSnapshot`) instead of a reducer — there is exactly one mutation ("record the latest
  snapshot"), so a one-member action union would be ceremony without benefit. `snapshot: null` is
  the distinct "not yet loaded" state; a received `{ model: '', effort: '', yolo: false }` is a real
  snapshot of inherited-defaults/permissions-enforced, not `null` (#188 distinguishes the two).
- **`src/renderer/src/screens/conversation/runConfigSnapshot.ts`** — framework-free, effects
  injected (the `composerSend`/`logDataDownload` idiom): `toRunConfigSnapshot` (the
  `toDownloadAction` analogue — `snapshotReceived → {model,effort,yolo}` verbatim, every other
  `DaemonEvent` → `null`, a permanent filter, not an `assertNever`), `requestRunConfigSnapshot`
  (fires one inline `requestSnapshot` command literal for `MILESTONE_CONVERSATION_ID`), and
  `subscribeRunConfig` (wires `onDaemonEvent` → `toRunConfigSnapshot` → `setSnapshot`, returns the
  off handle).
- **`src/renderer/src/screens/conversation/RunConfigData.tsx`** — a headless container
  (`(): null`) mounted as the first child of `<StatusSheet>` in `ConversationScreen.tsx`, ahead of
  `<LogDataSection />`. Because the sheet body only mounts while open
  (`{sheetOpen && <StatusSheet>…}`), the container's mount **is** the open transition. Two mount
  effects: a subscription effect (off-handle cleanup — nets one live listener across a StrictMode
  double-mount, the `daemonEventBridge` idiom) and a request effect guarded by a `useRef(false)`
  one-shot flag, so the StrictMode dev double-invoke still fires exactly one `requestSnapshot`
  (AC2). A genuine close→reopen is a new component instance with a fresh ref, so it re-requests.

`ConversationScreen.tsx` gained one import + one JSX line; no other production file changed.

## Patterns established

- **A one-member mutation doesn't need a reducer.** When a store has exactly one write operation
  ("hold the latest X"), a bare setter (`setSnapshot`) keeps the unidirectional-flow invariant
  (read-only selectors, one write path, no two-way binding) without inventing a one-arm
  discriminated union just to match `sessionStore`'s shape. Reusable for any future store whose
  entire write surface is "replace with the latest received value."
- **A headless container can satisfy an "exactly once per open" AC via a `useRef` guard on a mount
  effect with no symmetric cleanup**, rather than tracking an `isOpen` prop transition on an
  always-mounted component. This works specifically because the surrounding tree already
  conditionally mounts the container (`{sheetOpen && …}`) — the mount *is* the open event. Don't
  reach for the ref-guard trick on a component that isn't already open-gated by its parent; that
  case needs the `isOpen`-transition variant instead (see the spec's own note that this was an
  explicit design choice, not the only valid one).
- **`toX` DaemonEvent filters return `null` via `default`, never `assertNever`,** when the consumer
  intentionally only cares about one event — `daemonEventBridge.ts` is the *only* place exhaustiveness
  is enforced; every other event-filtering module (`toDownloadAction`, now `toRunConfigSnapshot`)
  documents "ignore the rest" as permanent intent, not a gap to close later.

## Lessons learned

No "Lessons learned" section in the merged PR body; nothing surfaced in code review beyond the
PASS. One documentation-worthy correction folded in above: the spec's own open questions were
resolved as written (inline `requestSnapshot` literal, no shared constructor; store keeps the last
snapshot across a close→reopen, no reset-on-close) — no deviation from the architecture doc.
