# #195 — Modal store: match-and-replace by `modalId`, idempotent re-delivery

Reliability/correctness ticket, not security-sensitive, no UI/wire/daemon change. Shipped as PR #412
(`802e1c3`). Size XS — single pure-reducer file. Per [ADR 0009](../decisions/0009-modal-prompt-model.md),
predicted there as a one-arm extension the id-addressed array would make cheap; confirmed.

## Summary

Makes `reduceModal`'s `shown` arm idempotent on `modalId`, the client half of the daemon's
reconcile-on-connect contract (daemon: pyrycode/pyrycode#877; wire: pyrycode/pyrycode#879): after a
connection blip the daemon re-unicasts any still-outstanding permission/trust prompt under its
**original** `modalId`. Before this ticket, `shown` always appended, so a re-delivery would double-show
the same prompt. Only `src/renderer/src/store/modalPrompts.ts` and its test changed — the daemon-event
bridge (`modalBridge.ts`) is untouched, since the tag-rename it does (`modalShown → shown`) is invisible
to the reducer's internal id-tracking.

- **`ModalState` gains `resolved: readonly string[]`** — internal reducer bookkeeping, no selector, no
  consumer. Records every `modalId` that has left `outstanding` via `dismissed`, letting the `shown` arm
  distinguish never-seen (→ append) from seen-then-resolved (→ no-op). `initialModalState` becomes
  `{ outstanding: [], rejections: [], resolved: [] }`.
- **`shown` arm — three-case decision, `resolved` checked first:**
  1. `modalId ∈ resolved` → same-`state`-reference no-op (already answered/dismissed; the reconnect-race
     early-out).
  2. `modalId ∈ outstanding` → replace that entry in place (`outstanding.map(...)`), rebuilt from the
     **re-delivered** event's fields (match-and-replace takes the latest, not stale, values) — array
     length and position preserved, no duplicate.
  3. else → append, exactly as before (first-delivery unchanged).
- **`dismissed` arm — records `resolved` only on a genuine removal.** `dismissed` is the single choke
  point where a prompt leaves `outstanding` (answer, cancel, remote, and timeout all dispatch it), so
  this one arm covers "already answered or dismissed" for AC3. Computes `removeById` first; if the
  result is the *same* array reference (unknown id, no match), returns `state` unchanged and does **not**
  touch `resolved` — the ordering-edge guard: a `dismissed` for an id that was never outstanding must not
  poison `resolved`, or a later legitimate `shown` of that id would be wrongly suppressed forever.
- `resolved` retains ids for the store's lifetime, with no eviction — correct because `modalId`s are
  one-time nonces, never reused for a new prompt, so a retained id can never legitimately need to
  re-surface. Flagged in the spec as deliberate, evidence-based (no observed growth problem; the ADR's
  Open Questions section covers the reasoning).

7 new vitest cases added to `modalPrompts.test.ts` (idempotent re-delivery preserving position/count,
match-and-replace taking the re-delivered fields over stale ones, no-op-after-resolution via `toBe`
same-reference, the dismiss-before-show ordering edge, purity under re-delivery, initial-state
`resolved: []`). All pre-existing tests (append, dismiss-by-id, rejection surface, orthogonality,
selectors) stay green unchanged — additive fold refinement, not a behavior change on any already-tested
path. `npm test`, `npm run typecheck`, `npm run build` all green.

## Patterns established

- **A same-reference early-out keyed on a *retained resolved-id set*, checked before the existing
  outstanding-membership branch.** When a reducer needs to distinguish "never seen" from "seen and
  settled" — not just "currently present" — a plain membership array checked first, before the
  usual outstanding/unknown split, is enough; no need for a `Map`/richer structure. Reach for this
  whenever a re-delivery or replay can legitimately re-arrive for an id the reducer already resolved.
- **The choke point that removes an item from a collection is the correct place to record it as
  resolved**, not the individual call sites that trigger the removal (answer, cancel, remote, timeout
  all funnel through one `dismissed` dispatch) — one recording site instead of four.
- **Guard the *unknown-id* branch of a removal explicitly against poisoning resolved-state.** The
  same-reference-on-no-match convention (`removeById` returning the original array when nothing
  matched) is what makes this guard a one-line reference check (`if (outstanding === state.outstanding)
  return state`) rather than a second lookup.

## Lessons learned

None — the spec's decision table (check `resolved` first, then `outstanding`, then append) mapped onto
the implementation with no deviation, and the architect's guidance to reuse `appendUnique` verbatim for
recording resolved ids (rather than adding new same-reference logic) held up as written. No PR-body
Lessons-learned section.
