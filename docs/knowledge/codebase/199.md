# #199 — Decode `assistant_delta` + `turn_end` on the transport (structured-stream L1)

Transport slice (L1) of the Phase-2 structured-streaming vertical, decomposed from #199's original
combined scope along the transport → store → render seams the snapshot vertical (#180 → #187/#188)
proved. Shipped as PR #207 (`b54bbae`), code-review **PASS** (no MUST/SHOULD-FIX, one informational
NIT). Security-sensitive (adds wire types decoded from the relay socket); size S; a structural clone
of [#180](180.md) scaled down (no outbound builder, no renderer command). Blocks #202 (timeline
store + `DaemonEvent → ThreadEvent` bridge) → #203 (render, gates #179).

## Summary

Desktop withholds the `interactive` capability by design (`codec.ts:147`, `helloExchange.ts:34`),
so the daemon sends none of the v2 structured stream today — turning it on is #179. This ticket
builds the decode path Strangler-Fig alongside the coarse `message` path so that once #179 flips,
`assistant_delta` (the blank-thread-critical event — on the interactive path assistant text arrives
*only* this way, replacing the coarse `message` fan-out per pyrycode #699) and `turn_end` are already
decoded rather than dropped at `parseInboundMessage`'s `default → inbound-unmodeled → null`.

Five thin, additive touchpoints — exactly the file count the spec's self-check argued is the
architectural floor for any new inbound `DaemonEvent` (wire type → decode → connection consumer →
event union → renderer bridge), one file fewer than #180's 8 (no outbound builder/command/`index.ts`
wiring here, inbound-only):

- **Wire types** (`src/shared/wire/types.ts`) — `'assistant_delta'` / `'turn_end'` join
  `EnvelopeType`; two new payload interfaces, field-for-field with the daemon (pyrycode #607,
  `protocol-mobile.md`), no `omitempty`: `AssistantDeltaPayload{conversation_id, turn_id, seq, text}`,
  `TurnEndPayload{conversation_id, turn_id, stop_reason}`.
- **Inbound decode** (`inboundMessage.ts`) — two new `InboundDaemonMessage` kinds
  (`'assistant-delta'` / `'turn-end'`, kebab per the existing `bundle-chunk`/`daemon-error`
  convention) and two parse functions, `parseAssistantDeltaPayload` / `parseTurnEndPayload`, built on
  the existing `isRecord`/`requireString`/`requireNumber` helpers verbatim (no new helper — neither
  payload needs `requireBoolean`). Narrow-before-log, category-only error messages, content-free
  `inbound-decoded` diagnostic (`code`+`bytes`+`hash`, never `text`/`turn_id`/`seq`/`stop_reason`) —
  the exact `parseScreenSnapshotPayload` shape.
- **Consumer + `DaemonEvent` arms** (`daemonConnection.ts` + `src/shared/ipc/events.ts`) — two new
  camelCase arms, `{ type: 'assistantDelta'; turnId; seq; text }` and
  `{ type: 'turnEnd'; turnId; stopReason }`, emitted from two new `switch (inbound.kind)` cases.
  Both **drop `conversation_id`** (single active conversation; #202's bridge scopes identity) as a
  fresh named-field literal, never a spread of the decoded payload.
- **Renderer bridge** (`daemonEventBridge.ts`) — `case 'assistantDelta':` / `case 'turnEnd':` both
  `return null`, present purely because the `assertNever` default makes a new `DaemonEvent` arm a
  compile error until handled — #202's timeline bridge, not the session store, is the real consumer.

`npm test` (737 pass), `npm run typecheck`, `npm run build` all green. Coarse `message` /
`message_chunk` path untouched (regression-tested).

## Patterns established

- **The content-carrying arm is the deliberate exception to #180's content-minimisation pattern, not
  a regression of it.** #180's `snapshotReceived` dropped the sensitive rendered `text` via a
  dedicated minimal shape — the pattern documented in [#180's codebase notes](180.md). Here the
  assistant `text` **is** the render payload (#203 renders it), so it crosses IPC on purpose, as a
  fresh literal with named fields (never a spread), carrying no key/token/raw frame. The boundary
  this slice defends is the fail-closed **decode** at `parseInboundMessage`, not the text crossing
  the internal channel. Read both tickets' code side by side before assuming "new DaemonEvent ⇒ strip
  the payload" is a universal rule — it depends on whether the renderer is the one deciding what's
  sensitive (snapshot) or the one that's supposed to display the content (assistant text).
- **A same-un-guarded-inner-switch precedent can be reused twice before it needs fixing.** Like #180,
  this ticket added two more cases to `daemonConnection.ts`'s `switch (inbound.kind)`, which still
  has no `default: assertNever(inbound)` — deliberately deferred a second time (see Open questions
  below); the emit test remains the deterministic safety net.

## Lessons learned

None beyond the pattern above — the PR body's "Lessons learned" section covered the same
content-carrying-arm distinction (folded in above, not duplicated) and reported no other surprise;
the spec's 5-file scope-self-check matched the actual diff exactly (0 new files, all 5 predicted
production files touched, no 6th file discovered mid-implementation the way #180 discovered
`daemonEventBridge.ts` as an "8th file").

## Open questions carried forward

- **Inner-switch exhaustiveness** (`daemonConnection.ts`'s `switch (inbound.kind)` has no
  `default: assertNever`) is now two-tickets deferred (#180, #199) rather than fixed. Flagged again
  for the eventual cleanup ticket; not adopted here per the architect's explicit scope call.
- **`stop_reason` value set** — decoded and carried as an opaque string; #202/#203 decide whether any
  specific value (e.g. `end_turn`) drives render behavior. No enum narrowing at this layer.
- **Untrusted `text` at render** — `assistant_delta.text` is untrusted daemon content correctly
  carried verbatim here (this slice does not render). The render-time safety (display as text, never
  HTML) belongs to #203 — named in the architect's security review so #203's review treats the
  streamed `text` as untrusted at the DOM boundary.
