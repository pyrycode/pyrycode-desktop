# #2 — Connection and conversation state store

**Shipped:** 2026-07-03 · **Size:** S · **Scope:** renderer-only (`src/renderer/src/store/`) · greenfield module, zero existing consumers · no new dependency (`zustand ^5.0.2` already present).
**Spec:** `docs/specs/architecture/2-connection-and-conversation-state-store.md` · **PR:** #15 (review: PASS, no blocking findings).

The renderer-side state foundation for the connect-send-stream milestone: one Zustand store holding the active session's connection status and conversation message list, mutated only through a sealed action union. Pure renderer state — no IPC, preload bridge, or transport (those are #3/#4). Nothing binds it yet: #3 dispatches into it, #12 reads it.

## Patterns established

The template for future renderer stores:

- **Sealed action union + pure exported reducer.** State mutates only through a `SessionAction` discriminated union on `type`; `reduceSession(state, action): SessionState` is a pure, exported function and the primary test unit. New renderer state should follow this shape, not ad-hoc `set` mutations.
- **The vanilla `createStore` factory is the DI/test seam.** `createSessionStore(init)` yields an isolated, React-free store per test; the app-wide `sessionStore` singleton is built from it. This is how AC5 ("exercise the store directly, no channel/IPC/transport") is met — tests call `reduceSession` directly or construct a fresh store, sharing no global state.
- **Reuse wire types verbatim; no parallel renderer model.** Messages are stored as wire `MessagePayload` (imported from `@shared/wire/types`, not redefined) so #3 dispatches exactly what it parsed off the wire — zero drift. The `role: 'assistant'` ↔ UI `'daemon'` / `message_id` ↔ `id` transform is deferred to the #12 component boundary.
- **One justified renderer-owned thin model: `ConnectionError`.** Structurally mirrors the wire `ErrorPayload` but is store-owned, so transport/handshake failures (which have no wire `ErrorPayload`) synthesize `code: 'transport' | 'handshake'` into the same `status.error` shape the UI reads. The review flagged this explicitly (NIT): do **not** "dedupe" it back into the wire type — that reintroduces the drift it exists to avoid.
- **Narrow-slice selectors are the only read surface.** `selectStatus`/`selectMessages`; no exposed setter — `dispatch` is the sole mutation path (satisfies AC2/AC3 at the type level). `selectMessages` returns the same array reference across a status-only change and a fresh one on append, so a status change never re-renders the thread and vice-versa.
- **Compile-time exhaustiveness via `assertNever`.** The reducer's `default` arm calls `assertNever(action: never)` — adding a `SessionAction` variant without a reducer case is a type error, not a runtime surprise. No runtime reject/throw branches otherwise (the sealed union guarantees no malformed action).
- **Status and messages are orthogonal, unconditionally set.** Status actions never touch `messages`; message actions never touch `status`; each status action sets its target regardless of the current one. Transition ordering is the caller's (#3's) responsibility — no state-machine guard is built (none has been needed).

## Lessons learned

- **Zustand v5 vanilla API, confirmed against installed 5.0.14 types:** `createStore` from `zustand/vanilla`, `useStore(api, selector)` from `zustand`. The vanilla `createStore` factory doubles as the DI seam — reducer/selector tests run under `environment: 'node'` with no DOM harness because nothing touches React.
- **Build reducer results from `state.status`/`state.messages` explicitly, not `...state`-spread.** This keeps `reduceSession` a clean `SessionState → SessionState` function, independent of the store's extra `dispatch` field — and lets `set((s) => reduceSession(s, action))` shallow-merge the returned `{ status, messages }` while preserving `dispatch` (its reference stays stable across updates, verified by a dedicated test).
- **`createSessionStore` defaults `init` to the shared `initialSessionState` singleton**, so its `messages: []` reference is shared across default-constructed stores. Safe because `reduceSession` is pure (always allocates a new array on append) and the type is `readonly` — the "keeps two stores independent" test confirms no cross-talk. A future mutable-init store would need to guard this; this one does not.

## Deferred (open questions carried forward)

Flagged in the spec, to revisit when #3 wires the channel / reconnect / backfill:

- **Dedupe** of re-delivered `message_chunk` backfill (same `message_id`) — appends unconditionally today; revisit when `backfill_since` is wired.
- **Reconnect and history** — whether a fresh `connecting`/`disconnected` clears `messages` (kept orthogonal / no-clear for now).
- **`conversation_id` scoping** — single active conversation assumed; multi-conversation routing out of scope.
- **Optimistic send** — the composer's own-message echo will need a dedicated action (e.g. `messageSent`) or reuse of `messageReceived` when transport lands.
- **`connected` payload width** — carries the whole `HelloAckPayload`; narrow to `{ server_id, conn_id }` later only if the UI proves it needs less.
