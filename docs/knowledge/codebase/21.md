# #21 — Single-shot relay connection in the background process

**Shipped:** 2026-07-03 · **Size:** S · **Scope:** background transport only (`src/main/transport/`) · greenfield module, zero consumer cascade · **adds `ws` + `@types/ws`** (the project's first network dependency).
**Spec:** `docs/specs/architecture/21-single-shot-relay-connection.md` · **PR:** [#25](https://github.com/pyrycode/pyrycode-desktop/pull/25) (review: PASS, no MUST/SHOULD/NIT findings).

The **connection primitive** at the base of the Phase 1 connect–send–stream round-trip: `createRelayConnection` opens **one** `wss://` connection to a caller-supplied relay URL with caller-supplied headers, keeps it alive with a 30 s/30 s heartbeat, caps inbound frames at 1 MiB, carries **raw frames both ways as opaque bytes**, and funnels every failure into a **single terminal `closed` event**. Lives entirely in `src/main`; nothing touches IPC or the renderer, and it is **log-free by construction**. See the [relay-connection feature doc](../features/relay-connection.md) for the full contract, state machine, and heartbeat detail.

Scope lock held: **no reconnect, no backoff** (that's the supervisor #22, which recreates this connection), **no Noise decode, no framing interpretation** (the handshake and codec land on top later). This is the single-connection half of the pyrycode Go binary's `internal/transport` shape — its `Send`/`Receive`/heartbeat/`SetReadLimit`, minus the reconnect loop and jittered backoff.

## Patterns established

- **Factory + injected `onEvent` for main-side transport, matching the existing DI idiom.** Same functional/DI shape as `emitDaemonEvent(sink, …)` (#18) and `onCommand(source, handler)` (#17): the composition root constructs config and owns the sink; the module returns a `{ send, close }` handle. No class, no EventEmitter, no `.on()`. Data flow stays unidirectional — events out via `onEvent`, imperatives in via `send`/`close`. Reuse this for the supervisor and codec layers that join `src/main/transport/`.
- **Non-tunable wire-spec constants enforced by the type, not a comment.** The 30 s idle-ping / 30 s pong-timeout cadence is pinned as module constants and only overridable through a **test-only second `timing` parameter** — a production caller passing one argument literally cannot reach it through the typed public config. This is the deterministic (belt-and-suspenders) way to express "the relay implements the symmetric side, do not deviate", mirroring the Go mirror's test-only constructor. Contrast: `connectTimeoutMs` **is** public (an architect default, not wire-spec-pinned).
- **One terminal `closed` event, emitted exactly once, for every failure cause.** Connect-timeout, pong-timeout, oversize, remote close, socket error, and local `close()` all funnel into a single `{ type: 'closed'; code; reason }`. A module-private `closed`-once guard + a single `teardownAndEmitClosed` (clears both timers, `removeAllListeners()`, emits once) makes late `ws` events unable to re-enter `onEvent`. The consumer tells "never connected" from "dropped after connect" by whether it saw `connected` first — no separate `error` member needed yet.
- **`pending` field separates module-authored reasons from forwarded peer reasons.** Self-initiated closes set `pending = {code, reason}` *before* calling `terminate()`/`close()` so the terminal event is deterministic (`connect-timeout` / `pong-timeout` / `max-frame-exceeded` / `client closing`); peer/library closes leave `pending` null and forward the `'close'` event's own `code` + `reason.toString()`. This is how the static-reason discipline (never leak `err.message`) coexists with faithful peer-close forwarding.
- **Log-free by construction as the security control.** The module has no `console.*` anywhere — headers carry device/server identity, frames carry payload, and a stray log leaks either to main-process stdout. All diagnostics travel as `RelayEvent` data; the consumer decides logging. This is the deterministic alternative to a "don't log the headers" advisory rule, and the template for every future transport layer.
- **Test against a real in-process `ws` server, not a mock.** `relayConnection.test.ts` stands up `new WebSocketServer({ port: 0 })` parameterized per scenario (accept+echo, `verifyClient: () => false` to refuse, a bare `http.Server` that holds the upgrade for connect-timeout, `autoPong: false` to force pong-timeout, an oversize sender, `terminate()` for remote drop). Cadences driven through the test-only `timing` param + small `connectTimeoutMs`/`maxFrameBytes` so the suite runs well under a second on real timers. This is the "content-blind test forwarder" the Go side used with `httptest` — reuse the `startRelay`/`startBlackHole`/`makeSink` helper shape for #22.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section, plus the code-review notes.*

- **`ws`'s client-side `'close'` code for an oversized inbound frame is `1006`, not `1009`** (verified on ws 8.21). The `1009` is only sent to the *peer*. What the client reliably gets is an `'error'` with a stable `err.code === 'WS_ERR_UNSUPPORTED_MESSAGE_LENGTH'` and — crucially — **no `'message'` emitted**. The module detects that error code and normalizes the terminal event to `{ code: 1009, reason: 'max-frame-exceeded' }` so the observable code matches the wire-spec `message.too_long` (AC4). **Assert oversize by "terminal close + no `message` emitted", not by the raw ws close code** — a trap for anyone extending the oversize test.
- **Own the connect deadline; do not use `ws`'s `handshakeTimeout`.** An owned `setTimeout` that calls `ws.terminate()` during CONNECTING reliably emits `'close'` 1006, giving a deterministic `connect-timeout` reason **without** string-matching `ws`'s internal error text, and avoids two abort paths racing on an equal deadline. This is a deliberate, documented deviation from the spec's `handshakeTimeout` suggestion — flagged by the review as an improvement, not a gate.
- **`ws` is the project's first network dependency — justify network deps against the built-in `WebSocket`.** The browser/`undici` `WebSocket` in the Electron main process cannot set request headers, cap inbound payload, or bound the handshake — all four AC mechanics require `ws` (`headers`, `maxPayload`, `ping()`/`'pong'`, `'message'`/`send()`). The Go mirror made the identical call (`coder/websocket`, `SetReadLimit(1<<20)`). MIT-licensed, no runtime transitive deps.
- **`toFrame` narrows `RawData` without a cast, no-copy in the common case.** `ws` delivers a `Buffer` (a `Uint8Array` subclass) in default nodebuffer mode, so the inbound `frame` is the received bytes with **no copy**; the `Array.isArray` (fragmented) and `instanceof ArrayBuffer` arms cover the other delivery modes. No `any`, no unchecked `as`, no non-null `!` in production code (confirmed by review).

## Deferred (open questions carried forward)

- **Separate `error`/`failed` event vs folding into `closed`.** Every failure currently folds into the terminal `closed { code, reason }`. If #22's supervisor needs to distinguish "never connected" from "dropped after connect" beyond "did I see `connected` first", add a discriminated convention or a fourth union member then — evidence-based, deferred.
- **Reset-ping-on-activity.** The heartbeat pings unconditionally every 30 s (matching the Go `pingLoop`). Resetting the interval on inbound/outbound activity (true "idle" ping) is a safe later refinement — the relay tolerates either.
- **Async `send` error after a socket dies mid-flight.** `send` throws only on `readyState !== OPEN`; a frame handed to `ws.send` microseconds before the socket dies is dropped silently. Acceptable at the single-connection layer; the supervisor/handshake owns reissue-after-reconnect. Revisit only if an observed loss motivates surfacing the async send error.
- **`connectTimeoutMs` default (10 s).** A reasonable WS-upgrade deadline, not wire-spec-pinned. Tune if field experience shows the relay's real upgrade latency differs.
- **Relay-URL / scheme validation** (allowlist `wss://` only, host check, no embedded credentials) belongs at the **pairing/config layer** that produces the URL from the QR payload — this module is deliberately semantics-blind about the URL. Named by the security review so it is not lost; not gated here (#21 has no access to the pairing payload).
- **`sandbox: false` in `src/main/index.ts:17`.** Pre-existing scaffold value, out of scope for #21 (must not touch that file — and #21 doesn't). Route the flip to the dedicated hardening ticket #18/#17 already flagged.
