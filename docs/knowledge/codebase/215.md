# #215 — Thinking indicator bound to the conversation phase

The render sibling of [#214](214.md): renders a "Thinking…" affordance while the timeline store's
coarse `phase === 'thinking'` and nothing otherwise. Shipped as PR #219 (`f6a0e36`), code-review
**PASS** (no MUST/SHOULD-FIX, one non-gating NIT). Not security-sensitive — pure renderer, no keys,
sockets, or raw bytes. Size S: one production file modified (`ConversationScreen.tsx`), one CSS edit,
one test file; zero new files, zero new exported types. Built with **zero deviation** from the
architecture spec.

## Summary

[#214](214.md) gave `selectPhase` its first real source, but nothing in the renderer read it — during
the `thinking` window (the daemon opens a turn with `turn_state{thinking}` before any
`assistant_delta`, pyrycode #632) there are no timeline items yet, so `Timeline` renders `null` and the
thread showed nothing. A slow turn was indistinguishable from a stalled one. This ticket closes that
gap with `Timeline`'s structural twin over a boolean rather than a `ThreadItem[]`:

- **`ThinkingIndicator({ isThinking }: { isThinking: boolean })`** — new in-file, exported component in
  `ConversationScreen.tsx`, alongside `Timeline`. `isThinking === false` → `null` (zero layout footprint,
  AC2 — the `Timeline`-on-empty-`items` precedent); `isThinking === true` → a `flex: 0 0 auto`
  `.conversation__thinking` wrapper (deliberately **not** `.conversation__thread`'s `flex: 1 1 auto`, so
  it never claims a competing region) containing `<div className="bubble bubble--daemon
  bubble--thinking">Thinking…</div>` — the daemon-bubble surface, muted to `--color-on-surface-variant`.
- **Boolean input, not `phase` (the AC3 decision).** The view takes `isThinking: boolean`, never
  `phase: TurnPhase`. This makes AC3 ("no daemon-supplied string is rendered by this slice") a
  **type-level guarantee** rather than a convention — the view structurally cannot render a daemon
  string because it never receives one. The container does the trivial `phase === 'thinking'`
  derivation. No `switch`/`assertNever` — a plain boolean guard, since there is no union to
  discriminate (unlike `TimelineRow`).
- **Container edit** — `ConversationScreen` reads `const phase = useTimelineStore(selectPhase)` beside
  the existing `selectItems` read, and mounts `<ThinkingIndicator isThinking={phase === 'thinking'} />`
  immediately after `<Timeline items={items} />`, before `<StatusRow>` — the tail of the
  structured-stream render surface, i.e. where the next assistant bubble will appear.
- **CSS** — `.conversation__thinking` (the stable test seam, the `bubble__cursor` role) +
  `.bubble--thinking { color: var(--color-on-surface-variant) }`. Token names only, no color literal;
  everything else (fill, radius, measure) inherits from `.bubble`/`.bubble--daemon`. No animation was
  added (the spec's "optional polish" was explicitly not load-bearing; shipped static per the interim
  posture).
- **No transport, no store, no bridge touched** — `selectPhase` and `useTimelineStore` already existed
  ([#121](121.md)/[#202](202.md)); this ticket adds only a read and a view.

4 new tests in `ConversationScreen.test.tsx`: the pure view's inert-when-false case (markup `''`), the
pure view's showing case (markup contains `conversation__thinking` / `bubble--thinking` / `Thinking…`),
and the container's inert-against-the-idle-store smoke (AC4, the `bubble__cursor` inert-slice precedent
— `getInitialState()` → `phase: 'idle'` under server render, so the populated path is unreachable and
lives only on the pure-view assertions). `npm test` (834 pass, 3 pre-existing skips), `npm run
typecheck`, `npm run build` all green.

## Patterns established

- **A phase-scalar render slice mirrors an items-list render slice one-for-one, down to the file
  structure.** `ThinkingIndicator` is `Timeline`'s structural twin: same in-file/exported/props-in
  shape, same "return `null` for the nothing-to-show case," same container placement pattern
  (`useTimelineStore(selector)` read beside the existing one, component mounted right after its
  sibling). The only real divergence is the input type (`boolean` vs. `ThreadItem[]`) and the absence
  of exhaustiveness machinery, since a boolean has no cases to enumerate.
- **A boolean prop (not the sealed enum it's derived from) is the belt-and-suspenders way to make a
  "never render untrusted data" AC a type guarantee.** `phase: TurnPhase` is already a validated,
  trusted three-way literal by the time it reaches the container (validated at #214's transport
  boundary) — the risk here isn't malformed input, it's a future edit accidentally threading `phase`
  itself into rendered text. Narrowing the view's prop to `boolean` makes that mistake a compile error,
  not a code-review catch. Same posture as [#122](122.md)'s modal-store id-keyed design and #133's
  branded `safeBytes` — the safety net is a type, not a remembered convention.

## Lessons learned

No corrections from code review (PASS). One non-gating NIT worth carrying forward: `.conversation__thinking`
has no live region, so a screen reader will not announce "Thinking…" appearing/disappearing — the
reviewer noted the file already has a `role="status"` idiom for exactly this class of transient state
(`composer__hint`, `LogDataSection`'s status paragraph) and that adding it here would be a one-line,
token-free fix. Deferred deliberately: the indicator is dormant until #179 flips `interactive`, the AC
doesn't require it, and the spec explicitly routes the polished treatment to the desktop-design pass.
**Fold `role="status"` into whichever of #179 or the desktop-design pass touches this markup next.**

## Open questions carried forward

- **Missing live-region announcement** (see Lessons learned above) — a one-line `role="status"` add,
  not yet done.
- **Dual-thread/dual-surface layout at the #179 cutover** — inherited verbatim from
  [#203](203.md)'s open question, now with a third element in play. Today (`phase` always `idle`) the
  indicator is `null` and the layout is pixel-identical. Post-#179, when `interactive` flips: during
  `thinking`, the coarse `MessageThread` renders an empty `flex: 1 1 auto` region, `Timeline` is `null`,
  and the `flex: 0 0 auto` `ThinkingIndicator` sits just above the status row; when the first delta
  arrives (`phase → responding`), the indicator vanishes and the reply appears in `Timeline`'s region —
  a small positional shift. #179 owns reconciling all of this (render one thread surface or the other
  off the interactive flag, empty-thread `null`, indicator placement); this ticket must not touch it.
- **Interim visual is non-prescriptive.** The muted daemon-bubble "Thinking…" is a deliberately minimal
  stand-in for the absent Figma node (verified against `g2HIq2UyPhslEoHRokQmHG` node `16-8` — no
  dedicated thinking-indicator node exists in the locked mobile design). The polished treatment (and any
  animation) lands in the deferred desktop-design pass; the developer may adjust wording/weight within
  the token set without a spec change.
