# #218 — Render pending tool-call rows on the conversation thread

The render slice of the tool-call vertical, split from [#205](https://github.com/pyrycode/pyrycode-desktop/issues/205)
alongside its transport half [#217](217.md) (`#217` → `#218`, blocked-on chain). Shipped as PR #222
(`580ac93`), code-review **PASS** (no MUST/SHOULD-FIX). Not security-sensitive — pure renderer of
already-decoded, already-untrusted-flagged daemon strings; no keys, sockets, or raw bytes. Size S: one
switch-arm swap plus its CSS, no store/bridge/transport/key-strategy/`interactive` change.

## Summary

Before this ticket, `TimelineRow`'s `case 'toolCall'` was a documented no-op (`return null`) — the
`toolCall` `ThreadItem` #217 started feeding the store had nowhere to draw. This ticket replaces that
arm with the pending tool row (Figma node `16:28`): a compact bordered chip, left-aligned in the
thread, carrying the tool name and its one-line input summary, interleaved with the assistant-text
bubbles in the reducer's arrival order.

- **`ConversationScreen.tsx`** — the `case 'toolCall'` arm now renders
  `<div class="tool-row"><div class="tool-row__chip" data-thread-role="tool"><span
  class="tool-row__name">{item.name}</span><span class="tool-row__summary">{item.inputSummary}</span>
  </div></div>`. `name`/`inputSummary` are React children (auto-escaped) — never
  `dangerouslySetInnerHTML`, the `assistantText` arm's posture one case up. `data-thread-role="tool"`
  (not `"assistant"`) is deliberate: it hooks the test **and** keeps `threadBubbleCount` (which matches
  only `"assistant"`) at 0 for tool rows. `Timeline`'s array-index `.map` key is untouched — no
  `toolUseId`-based key introduced; `toolUseId` stays on the item, unread here, reserved for #206's
  correlation. `inProgress` needs no guard in this arm: `Timeline` computes the cursor flag as
  `index === lastIndex && item.kind === 'assistantText'`, which is structurally always `false` for a
  `toolCall`. Two now-stale comments were corrected in the same diff: the header comment ("today's
  three kinds, two of them null") now reads "only `turnBoundary` null", and the inline comment above
  the arm now states the pending-render intent instead of "deferred: #205/#206 own the tool render".
- **`conversation.css`** — three new token-only rules. `.tool-row` (the wrapper): `flex`, left-justified,
  `opacity: 0.5` — the pending/unresolved dimming, inheriting `.conversation__thread`'s gap with no
  margin of its own. `.tool-row__chip` (the pill): `--color-surface-container` fill, 1px
  `--color-outline-variant` border, `--radius-sm` (12px, exact Figma match), `--space-2`/`--space-3`
  padding/gap, `max-width: 100%; min-width: 0; overflow: hidden` so an unbounded untrusted summary
  can't blow out the layout. `.tool-row__name` (mono, `--color-tertiary`, `flex: 0 0 auto; white-space:
  nowrap` — never shrinks) and `.tool-row__summary` (`--color-on-surface-variant`, `min-width: 0;
  text-overflow: ellipsis; white-space: nowrap` — ellipsizes rather than overflowing). Two deliberate,
  code-commented deviations from a literal Figma reading: the raw 13px mono name maps to
  `--text-body-small-size` (12px, the file's ±2px tokenization convention — zero new type literals),
  and Figma's `overflow-clip` becomes `text-overflow: ellipsis` (the friendlier desktop degrade for an
  unbounded string vs. a hard clip).
- **`ConversationScreen.test.tsx`** — the superseded *"renders a toolCall as a safe no-op"* case is
  rewritten to *"renders a pending tool row"*: asserts `tool-row__chip`, `data-thread-role="tool"`, both
  daemon strings verbatim, `threadBubbleCount === 0`, no cursor. Two new cases: an AC4 escaping case
  (both `name` and `inputSummary` carrying `<b>`/`<i>` markup, asserted escaped in the markup and never
  live), and an AC1 interleaving case (`[assistantText, toolCall, assistantText]` — the tool row sits
  between the two bubbles in array order, exactly one cursor, trailing the tail bubble).

`npm test` (868 pass, 3 pre-existing skips), `npm run typecheck`, `npm run build` all green. Figma
`get_design_context` on node `16-28` at code-review time confirmed the architect's inlined token
mapping 1:1 — no MUST-FIX findings.

## Patterns established

- **A single-arm switch swap is the right shape for "the union member already exists, only its render
  was deferred."** No store, bridge, transport, or key change was needed — the entire slice lives
  inside one `case` and its CSS, because #121/#202/#217 had already done the data-layer work and left
  the render arm as an explicit, documented placeholder. When a future `ThreadItem` render slice finds
  the same shape (a `null`-returning `case` with a "deferred to #N" comment and a real item already
  reaching the store), a single-arm swap — not a wider refactor — is the correct, minimal fix.
- **`data-thread-role` is a role-scoped test hook, not a styling class — a second value on the same
  attribute cleanly excludes a new render kind from an existing count helper.** `threadBubbleCount`
  (from #203) matches only `data-thread-role="assistant"`; giving the tool row `data-thread-role="tool"`
  rather than reusing `"assistant"` or omitting the attribute kept that helper correct with zero edits,
  while still giving the new row its own stable query hook. A future per-kind count (e.g. a tool-row
  count) would follow the same value-per-kind convention rather than inventing a new attribute.
- **Untrusted daemon strings that were flagged at the decode boundary (#217) are discharged at render
  exactly as flagged — no new escaping mechanism per field.** `name`/`inputSummary` reach this arm as
  plain React children, verified by the same test shape (`renderToStaticMarkup`, assert `&lt;b&gt;`
  never `<b>`) #199/#203 already established for `text`. Two untrusted fields on one item did not need
  two different postures — one children-only rule covers both.

## Open questions carried forward

- **#206 handoff — the pending dimming lives on `.tool-row`, not a per-field flag.** When #206 fills
  `result`, it needs to lift or override the `.tool-row` `opacity: 0.5` (e.g. a `.tool-row--resolved`
  modifier keyed off `item.result !== null`) and add the success/error treatment. This slice
  deliberately owns only the `result === null` visual.
- **The tool row is dormant until #179** (the `interactive` flip) — same posture as #203/#215's
  Strangler-Fig coexistence. No `tool_use` frames reach production yet, so the chip's visual fidelity
  rests on the Figma-verified token mapping plus the deterministic `renderToStaticMarkup` structure
  test, not a live Electron render (code-review-flagged, non-blocking).
