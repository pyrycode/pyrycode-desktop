# #224 — Interactive modal render: outstanding permission/trust prompt

The render slice of the modal vertical (ADR [0009](../decisions/0009-modal-prompt-model.md)), fifth of
six: [#201](201.md) (transport) → [#223](223.md) (store + bridge) → **#224 (this, interactive
render)** → #225 (answer path) → #226 (second-confirm) / #227 (surface rejection). Shipped as PR
[#233](https://github.com/pyrycode/pyrycode-desktop/pull/233) (`c386396`). Not security-sensitive (a
pure render of already-typed renderer state; React auto-escapes the daemon-supplied strings — the
decode was #201's, internet-exposed and already reviewed). Size S — one render surface + container + a
two-line `App.tsx` bridge mount, mirroring #203. Code review: **PASS**, zero MUST/SHOULD-FIX, three
non-blocking NITs deferred to the answer-path slice.

## Summary

Closes the store → UI path #223 left open: `useModalBridge` shipped dormant (nothing mounted it, so
`modalStore` never populated from live daemon events). This ticket mounts the bridge at App level and
renders the store's outstanding prompt as a read-only interactive dialog. Two changes:

1. **`App.tsx`** — `useModalBridge()` added beside `useDaemonEventBridge()` / `useTimelineBridge()`
   (two lines + import), the third independent subscriber on the `onDaemonEvent` channel. App-lifetime,
   unconditional, derefs `window.pyry` only inside its effect — the `<App/>` server-render invariant
   (`renderToStaticMarkup(<App/>) === ''`) holds unchanged.
2. **New `src/renderer/src/screens/conversation/PermissionModal.tsx`** (73 LOC) — two components
   mirroring `RepairPrompt`/`RepairControl`:
   - **`PermissionModalView({ prompt: ModalPrompt })`** — pure, exported. A centered M3 dialog (Figma
     "Dialogs", node `22-3`) reusing `StatusSheet`'s overlay+scrim+panel *structure*
     (`role="dialog"`, `aria-modal="true"`, `aria-labelledby` → the title's id, a dedicated scrim, an
     opaque panel, absolutely positioned inside `.conversation`, no portal) but centered instead of
     bottom-anchored. `prompt.title` in an `<h2>` (`headline-small`), `prompt.prompt` in a `<p>`
     (`body-medium`, muted) — both React children, auto-escaped, never `dangerouslySetInnerHTML`.
     `prompt.options` map 1:1 to inert `<button type="button">`s (no `onClick`) in array order, keyed
     by `option.id`. The option whose `id === prompt.defaultOptionId` carries an added
     `permission-modal__option--default` modifier class; every other option carries only the base
     `permission-modal__option` class — the `message-row--${type}` idiom, assertable in the pure view.
     `prompt.class` (`permission`/`trust`) is read but not rendered this slice (kept minimal per spec).
   - **`PermissionModal()`** — the store-bound container. `useModalStore(selectOutstanding)`, renders
     `outstanding[0]` (oldest-first FIFO — a permission/trust prompt is a blocking decision, so
     single-dialog is the simplest correct choice) via `PermissionModalView`, or `null` when nothing is
     outstanding. No `selectCurrentModal` selector added — the container derives `[0]` locally, honoring
     ADR 0009's explicit deferral ("add only when a render needs it").
3. **`ConversationScreen.tsx`** — `<PermissionModal />` mounted as the **last child** of `.conversation`,
   after the conditional `StatusSheet`, so the dialog overlays the whole conversation surface.
4. **`conversation.css`** — ~100 new lines: `.permission-modal-overlay` / `__scrim` (structure cloned
   from `.status-sheet-overlay`, `justify-content` swapped from `flex-end` to `center`), `.permission-modal`
   (`surface-container-high`, `radius-lg`, 24px padding, column + 16px gap, `max-width: 360px`,
   `max-height: 90%` + `overflow-y: auto` so a long untrusted prompt scrolls inside the panel rather than
   overflowing), `__title` (`headline-small`), `__prompt` (`body-medium`, `word-break: break-word`),
   `__options` (flex-wrap row, `justify-content: flex-end`), `__option` (transparent pill,
   `--color-primary` text — the Dialogs text-button treatment) and `__option--default` (filled-tonal:
   `--color-secondary-container` bg + `--color-on-secondary-container` text — the emphasized safe-deny
   choice). A **distinct class set**, not a reuse of the status-sheet classes: the two modals share a
   chrome *pattern*, not a stylesheet. All 27 referenced tokens verified present in `tokens.css`; zero
   color/type/radius literals.

7 new tests in `PermissionModal.test.tsx` (server-rendered, `renderToStaticMarkup`, no DOM harness — the
`ConversationScreen.test.tsx`/`App.test.tsx` idiom): title/prompt text render; three options render in
array order (index-comparison assertion); the `--default` modifier lands on exactly the matching option
(a default that is neither first nor last, proving order and default-marking are independent); daemon
text containing `<script>`/`<b>`/`<i>` renders escaped, not as live markup; the dialog carries
`role="dialog"` + `aria-modal="true"` + correct `aria-labelledby`/title-`id` pairing; a single-option
prompt renders exactly one button; the container renders `''` when the store is at its initial (empty)
`outstanding`. The **populated** container render is not tested directly — zustand v5's `useStore` reads
`getInitialState()` under server render, so a `setState` never reflects (the `RepairControl` note,
#69/#167); populated rendering is proven entirely through `PermissionModalView` with injected fixtures.
`npm test` (948 total, +7), `npm run typecheck`, `npm run build` all green.

## Patterns established

- **A dormant bridge's mount site is a two-line, zero-risk change once the render consumer exists** —
  the exact shape #202→#203 established for the timeline bridge, now proven a second time for the modal
  bridge. The App-level mount comment explicitly calls out the server-render invariant it must preserve,
  matching the `useTimelineBridge` comment it sits beside.
- **A modal's chrome can reuse another modal's overlay+scrim *structure* while diverging on
  panel placement and stylesheet** — `.permission-modal-overlay` clones `.status-sheet-overlay` almost
  line-for-line except `justify-content: center` vs `flex-end`, but gets its **own** class names
  end-to-end rather than sharing `.status-sheet*` classes. The architecture spec was explicit about why:
  "the two modals share a chrome pattern, not a stylesheet, and coupling them would make the sheet's
  future changes leak into the dialog."
- **The fail-safe default is marked with an additive modifier class, never a separate default-only
  prop or a second render path** — `permission-modal__option--default` sits alongside the base
  `permission-modal__option` class exactly like `bubble--thinking`/`conversation__unpair--confirm`,
  keeping the "assertable, visually distinct, single code path" property the AC asked for.

## Lessons learned

From the code-review PR comment (`c386396`, PASS with three NITs, all explicitly scoped to the
downstream answer-path slice rather than this one):

- The dialog has `role="dialog"` + `aria-modal="true"` but **no focus trap, `Escape` handler, or
  initial focus** — correct for this read-only, inert render (consistent with the `StatusSheet`
  precedent), but the answer-path slice will need to add focus management so keyboard/screen-reader
  users can't tab into the background the `aria-modal` claims is inert.
- The fail-safe default is distinguished **only visually** (the filled `--default` pill) — AC3 only
  required visual distinction (met), but the answer path should also give it a programmatic cue
  (initial focus / `aria`) so it reads as the default non-visually too.
- `word-break: break-word` (used on `.permission-modal__prompt`) is the legacy alias for
  `overflow-wrap: break-word` — functionally fine everywhere, flagged as a cosmetic non-blocker only.

None of these blocked merge or changed the shipped implementation; they're recorded here as the
answer-path slice's (#225) starting checklist.
