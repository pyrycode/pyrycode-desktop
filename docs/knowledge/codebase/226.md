# #226 — Second-confirm: a client-side confirm before an allow answer

The final render slice of the modal vertical (ADR [0009](../decisions/0009-modal-prompt-model.md)),
built on the terminal answer-path ticket [#237](237.md). Shipped as PR
[#250](https://github.com/pyrycode/pyrycode-desktop/pull/250), commit `48c1846`. Not security-sensitive
(renderer-only UX gate over the already-built answer command; no keys, sockets, or wire bytes — the
answer-frame construction is #236/#237's). Size S. Code review: **PASS**, two non-blocking NITs.

## Summary

There is no machine-readable `destructive` class on the wire — `class` is `permission | trust` only
(ADR 0009) — so "a consequential action needs a second confirm" can only be a **client-side UX policy**
on the answer path. This ticket inserts a confirm sub-step in front of the `modal_answer` dispatch for
the deliberate-move-away case only: selecting a **non-default** option now surfaces a `Back`/`Confirm`
sub-step before the command is sent. The default (fail-safe deny) option and the Cancel affordance stay
ungated — both resolve immediately, exactly as #237 shipped them. No wire change, no store change, no
new `ModalEvent` arm.

1. **`modalResolution.ts` gains `selectOption(prompt, optionId, deps)`** — the pure, React-free gate
   (plain-spy tested, same discipline as `answerPrompt`/`cancelPrompt`). `deps` is `{ answer,
   requestConfirm }`, two injected effects; `selectOption` itself sends and dispatches nothing, it only
   routes. `optionId === prompt.defaultOptionId` → `deps.answer(optionId)` (straight through, ungated);
   anything else → `deps.requestConfirm(optionId)` (held pending a second confirm). The degenerate
   single-option-is-default prompt (e.g. a single-option trust prompt) routes to `answer` — correct,
   since the only choice *is* the safe default.
2. **`PermissionModalView` gains a `pendingOption: ModalOption | null` prop** and renders one of two
   modes off it — a **prop**, not internal `useState`, so both modes stay SSR-testable under the `node`
   test env. `onAnswer` is renamed `onSelect` (every option click now routes through the gate); two new
   required effects, `onConfirm(modalId, optionId)` / `onBack()`, are added.
   - `pendingOption === null` (list mode, #237's original render): unchanged except `onAnswer` →
     `onSelect`.
   - `pendingOption` set (confirm mode, new): the same `.permission-modal` chrome (title stays shown so
     the user stays oriented), a client-owned confirm sentence naming `pendingOption.label` (auto-escaped
     React children, never `dangerouslySetInnerHTML` — the daemon label is untrusted text even quoted
     back at the user), and a two-button row: leading `Back` (`onBack()`) / trailing `Confirm`
     (`onConfirm(prompt.modalId, pendingOption.id)`). The daemon option list is **not** rendered in this
     mode.
3. **`PermissionModal` container gains one `useState<string | null>`** — `pendingOptionId`, declared
   **before** the `if (!prompt) return null` early return (rules-of-hooks; the empty-case SSR test still
   passes because the hook runs first and the guard fires after). The actual `pendingOption` passed to
   the view is derived, not the raw state: `prompt.options.find((o) => o.id === pendingOptionId) ??
   null` — against the **current** prompt's options, not a snapshot taken when the id was set.
4. **`conversation.css`** — `.permission-modal__back`/`.permission-modal__confirm` join the shared
   text-button selector group (pill, transparent fill, `--color-primary` label) alongside
   `.permission-modal__option`/`.permission-modal__cancel`; `.permission-modal__back` joins
   `.permission-modal__cancel` in the `margin-right: auto` leading-placement rule. No new tokens.

No new store representation, no new `ModalEvent` arm, no wire touch, no `interactive` flip (already
live since #179) — this ticket is a pure render/container-level gate.

### Data flow

```
user clicks a non-default option "allow-once"
  → PermissionModalView onClick → onSelect('m1', 'allow-once')
    → PermissionModal container → selectOption(prompt, 'allow-once', { answer, requestConfirm })
      → 'allow-once' !== prompt.defaultOptionId → deps.requestConfirm('allow-once')
        → setPendingOptionId('allow-once')  [no send yet — prompt stays outstanding]
  → view re-renders in confirm mode (pendingOption = the 'allow-once' ModalOption)

user clicks Confirm
  → onConfirm('m1', 'allow-once') → answerPrompt('m1', 'allow-once', { sendCommand, dispatch })
                                     [same guarded-send + unconditional dismissed-dispatch as #237]
                                   → setPendingOptionId(null)

user clicks Back (instead)
  → onBack() → setPendingOptionId(null)   [no send — returns to the option list]

user clicks the default option "deny" (fail-safe)
  → onSelect('m1', 'deny') → selectOption → 'deny' === prompt.defaultOptionId → deps.answer('deny')
    → answerPrompt('m1', 'deny', { sendCommand, dispatch })   [straight through, ungated, exactly as #237]

user clicks Cancel
  → onCancel('m1') → cancelPrompt(...)   [unchanged from #237, never gated]
```

`npm test` (1054 passed, 3 pre-existing skips), `npm run typecheck`, `npm run build` all green.

## Patterns established

- **Transient view state as a container `useState`, passed to a pure view as a prop, not as internal
  view state.** The confirm marker could have lived inside `PermissionModalView` as its own `useState`,
  but that would make the view impure (no longer `props → markup`) and break the SSR-test idiom every
  other view in this codebase relies on (`renderToStaticMarkup`, no DOM). Lifting it one level to the
  container and passing it down as `pendingOption` keeps the view testable in both modes with zero new
  test infrastructure — the same container/view discipline ADR 0006 established for screen-local state,
  applied one level deeper (component-local, not screen-local).
- **Derive transient state from current data, don't trust the id you stored.** `pendingOption =
  prompt.options.find(o => o.id === pendingOptionId) ?? null` re-validates against the *current*
  `outstanding[0]`'s options every render, rather than caching a `ModalOption` object at select-time.
  This is a deterministic safety net: if the outstanding prompt is swapped out from under a pending
  confirm (see Lessons learned below for the current limit of that guarantee), a stale id degrades to
  list mode instead of silently confirming the wrong prompt.
- **A classification gate with no wire signal reduces to "compare against the one required id you
  already have."** `prompt.defaultOptionId` was already present and rendered (#224's `--default`
  modifier) before this ticket; #226 didn't add a signal, it added a second consumer of the existing
  one. Worth remembering next time a "there's no `destructive` flag on the wire" ticket shows up — check
  whether the required fields already carry enough to approximate the classification before assuming a
  wire change is needed.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- The `pendingOption = prompt.options.find(...) ?? null` derivation, paired with the explicit
  `setPendingOptionId(null)` reset on confirm/back, is deliberate belt-and-suspenders — **but the two
  are different fabric only in the cases they actually cover.** The derivation guards against a prompt
  *swap*; the explicit reset guards against confirm/back *not* clearing state. Neither guards against a
  swap where the new prompt happens to reuse the *same* option id as the stale pending one — see the
  code-review finding below, which the PR author accepted as a known, currently-unreachable gap rather
  than reworking the keying.
- Design fidelity: the confirm sub-step affordance is **not drawn in Figma** (the architecture spec's
  Design source section flagged this up front, mirroring #199's precedent for a missing node). It is a
  client-owned sub-step assembled from the already-shipped Dialogs chrome (node `22-3`, #224/#237),
  reusing `.permission-modal__prompt` for the confirm sentence and the shared text-button treatment for
  `Back`/`Confirm`. No new node, no new tokens; validated structurally via the SSR render tests (proving
  the markup shape) rather than a screenshot comparison, since there is nothing to compare a screenshot
  against.

From the code-review PR comment (PASS, two NITs, neither blocking):

- **Latent staleness gap in the prompt-swap safety net, not reachable today.** The `pendingOptionId`
  marker is keyed by `optionId` alone, not `{modalId, optionId}` or `modalId`. The comment above it
  claims a stale pending id "falls back to list mode rather than confirming against the wrong prompt" —
  that only holds when the swapped-in prompt's options **don't** reuse the stale id. Permission/trust
  prompts realistically reuse option ids across prompts (`allow-once` / `deny` / `allow-always`), so if
  `outstanding[0]` is swapped while a confirm is pending — the review names remote/timeout dismissal of
  the current prompt — a colliding id would keep confirm mode open, now against the *new* prompt's
  matching option. **Not reachable today**: the only way `outstanding[0]` currently changes while a
  confirm is pending is the user's own Back/Confirm/Cancel/answer — remote/timeout dismissal of an
  *outstanding-but-not-current* prompt isn't wired yet (that lands with the #227 rejection surface,
  split into #248/#249). Reviewer's guidance for when that lands: key the
  pending marker by `modalId` (or `{modalId, optionId}`), not `optionId` alone. **Left unaddressed by
  this ticket** — flagged for #248/#249 or whichever slice first makes remote/timeout dismissal of a
  non-current outstanding prompt reachable.
- **Stale comment reference.** `PermissionModal.tsx` still had a #237-era comment reading `onAnswer(...)`
  in prose after the prop was renamed `onSelect`. Cosmetic, non-blocking.

## Testing

- `modalResolution.test.ts` (extended) — `selectOption`: default option → `answer` spy called once with
  `optionId`, `requestConfirm` not called; non-default option → `requestConfirm` spy called once,
  `answer` not called; degenerate sole-option-is-default prompt → `answer` called, `requestConfirm` not
  — the single-option-trust case (AC3's three branches).
- `PermissionModal.test.tsx` (extended) — list mode (`pendingOption={null}`): all #237 assertions hold
  after the `onAnswer`→`onSelect` rename. Confirm mode (`pendingOption={{id,label}}`): confirm sentence
  contains the option label, `Back` and `Confirm` buttons render, `optionCount(markup) === 0` (the
  daemon option list is absent), untrusted text still escaped, dialog chrome/aria unchanged. Container
  empty-case (`renderToStaticMarkup(<PermissionModal />) === ''`) still passes — the added `useState` is
  declared before the early return.
- `interactiveRoundtrip.test.tsx` — the sole other `PermissionModalView` call site, updated for the five
  now-required props (`pendingOption`, `onSelect`, `onConfirm`, `onBack`, `onCancel`).
