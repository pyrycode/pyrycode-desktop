# #229 — Decode the daemon `tool_result` stream and resolve its timeline tool-call

The **last** frame of desktop's Phase-2 structured-streaming vertical (ADR
[0008](../decisions/0008-thread-timeline-model.md)), split from
[#206](https://github.com/pyrycode/pyrycode-desktop/issues/206) (transport **#229**, this + render
[#230](https://github.com/pyrycode/pyrycode-desktop/issues/230)). Wires the missing wire → transport →
bridge chain that feeds a `toolResult` `ThreadEvent` into `reduceTimeline` (#121)'s pre-existing
`fillResult` correlation — **resolving** the correlated `toolCall`'s `result` in place (matched by
`toolUseId`), not appending a new row. Shipped as PR
[#232](https://github.com/pyrycode/pyrycode-desktop/pull/232) (`fbca814`), code-review **PASS** (no
MUST/SHOULD-FIX), security review **PASS**. Security-sensitive (adds a wire type decoded from the relay
socket); size S; a near-exact structural clone of [#217](217.md)'s `tool_use` chain. **No render** — the
resolved-row visual (success/error styling) is the sibling slice **#230**, blocked on this one. **No
`interactive` flip.**

## Summary

Before this ticket, a `tool_result` envelope was unmodeled and fell through `parseInboundMessage`'s
`default → inbound-unmodeled → null`. The downstream (`reduceTimeline`'s `toolResult` arm, `fillResult`,
`selectItems`) already existed from #121 with nothing feeding it. This ticket adds the wire → transport →
bridge chain — the same six touchpoints #217 established, plus one the spec's scope self-check missed:

- **Wire type** (`src/shared/wire/types.ts`) — `ToolResultPayload{conversation_id, turn_id, tool_use_id,
  is_error, result_summary}`, four strings + one boolean, all always present (no `omitempty`); `'tool_result'`
  joins `EnvelopeType`. **No new wire enum** — one exported type, like #217.
- **Inbound decode** (`inboundMessage.ts`) — `{ kind: 'tool-result'; toolResult: ToolResultPayload }` joins
  `InboundDaemonMessage`; `parseToolResultPayload` clones `parseToolUsePayload`'s idiom: `isRecord` guard,
  four `requireString` calls, **one `requireBoolean` call for `is_error`**, returning only the five known
  fields. `case 'tool_result'` narrows before logging, then emits `inbound-decoded{code:'tool_result',
  bytes, hash}` — no decoded field logged.
- **Consumer emit** (`daemonConnection.ts`) — one `case 'tool-result'` in the `switch (inbound.kind)`, a
  fresh literal `{ type: 'toolResult', turnId, toolUseId, isError, resultSummary }`; `conversation_id`
  dropped (single active conversation).
- **`DaemonEvent` arm** (`src/shared/ipc/events.ts`) — `{ type: 'toolResult'; turnId: string; toolUseId:
  string; isError: boolean; resultSummary: string }`. No new import.
- **Session bridge (no-op)** — `daemonEventBridge.ts` adds `toolResult` to the
  `assistantDelta`/`turnEnd`/`turnState`/`toolUse` fall-through `return null` group.
- **Timeline bridge (real mapping)** — `timelineBridge.ts` adds `case 'toolResult': return { type:
  'toolResult', turnId, toolUseId, isError, resultSummary }` to the owned block — field-for-field
  identical to its `ThreadEvent` counterpart, so this is a filter + fresh copy, not a remap. This is the
  arm `reduceTimeline` folds through `fillResult`, **resolving** the correlated `toolCall`'s `result` in
  place rather than appending — the one behavioral delta from every prior owned arm.
- **Modal bridge (no-op, the seventh touchpoint)** — `modalBridge.ts` adds `case 'toolResult'` to its
  fall-through `null` group. Not in the architect's spec's 6-file scope self-check — see § Lessons
  learned.

The only two deltas from #217, exactly as designed:

1. **`is_error` decodes via `requireBoolean`** (the `yolo` #180 idiom), not a fifth `requireString` and not
   an enum — the check is on the type, so `is_error: false` decodes as the value `false` (success), never
   treated as an absence; a non-boolean (`'true'`, a number, `null`, an object) throws `WireDecodeError`.
2. **The timeline arm resolves, it does not append.** Unlike #217's `toolUse` (appends a pending `toolCall`,
   `result: null`), this ticket's `toolResult` `ThreadEvent` is folded through `fillResult` — already-shipped
   correlation logic (#121) that finds the `toolCall` with a matching `toolUseId` and fills its `result` in
   place, returning the same array reference (a same-ref no-op) on an orphan or duplicate. This ticket adds
   no new reducer code; it only produces the event that drives the existing one.

19 new tests across `types.test.ts`, `inboundMessage.test.ts` (recognition; fail-closed for each of five
fields absent/mistyped including the full non-boolean `is_error` set `'true'`/`1`/`null`/`{}`; content-free
logging), `daemonConnection.test.ts` (emit mapping, `conversation_id` dropped, `isError` both values),
`daemonEventBridge.test.ts` / `modalBridge.test.ts` (→ `null`), and `timelineBridge.test.ts` (correlated
fill for both `isError` values, orphan no-op, duplicate no-op — all driven through a real
`createTimelineStore()` via `subscribeTimeline`, asserted on `selectItems`). `npm test` (938 pass, 3
pre-existing skips), `npm run typecheck`, `npm run build` all green.

## Patterns established

- **A new `DaemonEvent` arm's true touchpoint floor tracks the number of exhaustive `assertNever`-guarded
  `DaemonEvent` subscribers live at merge time, not the count at spec-writing time.** The #229 spec's scope
  self-check (written before #223 merged) counted 6 production files — the correct floor when only
  `daemonEventBridge` and `timelineBridge` existed. By the time #229 shipped, [#223](223.md) had added
  `modalBridge.ts` as a **third** independent exhaustive subscriber, so the true floor was 7: wire + decode
  + emit + event + **all three** renderer bridges. `npm run build` (not `npm test` — esbuild strips the
  TS exhaustiveness error) caught the missing case pre-PR. The general rule for the next stream arm (and
  #230, which touches no new `DaemonEvent` arm and so is unaffected): count exhaustive `DaemonEvent`
  switches by grepping for `assertNever(event)` against `DaemonEvent`, not by trusting a spec's file list
  written before the newest bridge landed.
- **A resolving arm (correlate-and-fill) costs the same six-to-seven touchpoints as an appending arm
  (#217)** — the wire/decode/emit/event/bridge chain is identical either way; only the *reducer* arm it
  feeds differs, and that reducer arm was pre-existing here (#121), so this ticket added zero reducer
  code. The transport slice's job is uniformly "produce the typed event," never "decide what the event
  does downstream."
