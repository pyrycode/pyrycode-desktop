# #230 — Render resolved tool-call rows on the conversation thread

The render slice of desktop's Phase-2 structured-streaming vertical (`#206` split; transport
sibling [#229](229.md) merged, PR #232). Shipped as PR #234 (`6dfa9e9`). Extends [#218](218.md)'s
**pending** tool-row chip to resolve in place once `item.result` fills — success or error. Pure
renderer: no store, no transport, no IPC, no wire types, no new component. This is also the
**last** open slice of the vertical besides `#179` (the `interactive` capability flip) — see
[ADR 0008](../decisions/0008-thread-timeline-model.md).

## Summary

Before this ticket, `case 'toolCall'` in `TimelineRow` (`ConversationScreen.tsx`) drew only the
pending chip at a fixed `.tool-row` class, regardless of `item.result` — a resolved call still
looked perpetually pending. This ticket reads `item.result` (`ToolResult | null`, narrowed by the
case) and derives the wrapper's `className`:

| `item.result`            | wrapper `className`                             |
| ------------------------ | ------------------------------------------------ |
| `null`                   | `tool-row` (unchanged)                            |
| filled, `isError: false` | `tool-row tool-row--resolved`                     |
| filled, `isError: true`  | `tool-row tool-row--resolved tool-row--error`     |

- **`ConversationScreen.tsx`** — the arm gained one `const { result } = item` + a ternary building
  `rowClass`, consumed by the wrapper `<div>`. The chip's inner markup (`.tool-row__chip`, the two
  spans) is **byte-identical** to #218 — `result.resultSummary` is deliberately not read anywhere
  in the arm, so there's no new untrusted-text surface to escape. The switch's `case 'toolCall'`
  gained braces (`{ … }`) to scope the new `const`.
- **`conversation.css`** — two new rules appended immediately after the existing `.tool-row { opacity:
  0.5 }` block, so source order gives the equal-specificity modifiers precedence:
  `.tool-row--resolved { opacity: 1 }` (lifts the pending dimming, both outcomes) and
  `.tool-row--error .tool-row__chip { border-color: var(--color-error) }` (the only outcome that
  recolors — success adds no accent, matching the Figma mock's "existing chip, dimming lifted").
- **`tokens.css`** — one new token, `--color-error: #ffb4ab` (M3 default dark error role, tone 80),
  added beside the existing `--color-success`. This is desktop's **first** error-family token — see
  Design tokens below.
- **`ConversationScreen.test.tsx`** — four new cases in `describe('Timeline …')`: resolved-success
  (asserts `tool-row--resolved` present, `tool-row--error` absent, chip markup unchanged), resolved-
  error (asserts both modifiers present), pending-unchanged (AC1 regression pin: `class="tool-row"`
  exactly, neither modifier), and a `resultSummary`-not-leaked case (a sentinel string in `result.
  resultSummary` asserted absent from the rendered markup).

`npm run build` + `npm test` green (per the ticket's own regression gate). No key-churn test needed
— `fillResult` (#121) replaces the `toolCall` at its existing array index, so the row resolves in
place with no remount.

## Design tokens — `--color-error` introduced, not invented

Desktop had `--color-success` (`#2fc038`) but no error family; two comments in `conversation.css`
(lines 68, 665 — the unpair confirm-guard and a composer hint, both pre-existing and **left
untouched** by this ticket, out of scope) recorded the gap. The architecture spec resolved the
value by provenance rather than picking a literal: `tokens.css`'s header declares the palette the
"Resolved Material 3 default (dark) scheme," and no node in the Figma file (`g2HIq2UyPhslEoHRokQmHG`)
references an M3 error scheme to mirror from directly — so the faithful mirror is the M3 default
dark `error` role, tone 80 (`#ffb4ab`), inlined in the spec and shipped verbatim. Only this one
token was introduced — no `on-error`/`error-container`/`on-error-container` family, since the
chosen treatment (chip border tint) consumes exactly `--color-error` and nothing else has a
consumer yet.

## Patterns established

- **A resolved/unresolved boolean-derived state is a wrapper-`className` variation, not a second
  render branch.** The arm's inner chip markup is untouched; only the outer `<div>`'s class list
  varies with `item.result`. This kept the diff to a `const` + ternary inside the existing `case`,
  matching the ticket's explicit "extend the arm, do not add a component" constraint — the same
  shape #218 established for the pending state itself (a class-only distinction from "no row at
  all").
- **A new design token is introduced with documented provenance, not picked as a plausible-looking
  literal — even absent a literal design-node mirror.** When Figma has no node to point at (no
  error variant mocked), the token still can't be invented ad hoc: the spec derived `#ffb4ab` from
  the palette's own documented source (the M3 default dark scheme the file header names) rather
  than eyeballing a coral. Future desktop-only tokens with no Figma mock should follow the same
  "cite the design system's own default, don't guess" discipline.
- **"Not surfacing a field" is itself a discharged, testable AC.** AC4 (untrusted text stays inert)
  is satisfied here not by an escaping mechanism but by never reading `result.resultSummary` in the
  render arm at all — proven by a sentinel-absence assertion, not by an escaping-format assertion.
  When a later slice decides to surface `resultSummary`, that decision reopens this AC and needs its
  own escaping test, mirroring `name`/`inputSummary`'s existing posture (#218).

## Open questions carried forward (from the architecture spec, unbuilt)

- **Color-only error signal.** The error state is distinguished from success by border color alone
  (a WCAG color-only concern) — no ARIA, no icon, no label. Matches the codebase's existing
  decorative-thread posture (no a11y AC was scoped); a non-color signal is a follow-up if a design
  pass calls for one, not built here.
- **`--color-error` (`#ffb4ab`) and `--color-tertiary` (`#ffb59f`, the tool-name color) are both
  coral** — visually close. The signal is the border shifting neutral-gray → coral, which reads
  distinctly against the pending/success gray border; if a visual review finds it too subtle, the
  documented fallback is an error-container fill (needs two more tokens), deferred unless observed.
