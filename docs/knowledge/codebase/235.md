# #235 — Outbound wire: `modal_answer` / `modal_cancel` envelope types + fail-closed builders

Base slice of the answer/cancel path, split 3-way (by transport/render layer) from
[#225](https://github.com/pyrycode/pyrycode-desktop/issues/225): **#235 (this, wire + builders)** →
[#236](https://github.com/pyrycode/pyrycode-desktop/issues/236) (main-command wiring, mints
`answer_token`, security-sensitive) →
[#237](https://github.com/pyrycode/pyrycode-desktop/issues/237) (answerable-modal renderer buttons).
Shipped as PR #238 (`68d42e1`), spec `8e3b82d`. Security-sensitive; size S; a near-exact structural
clone of `requestSnapshotEnvelope.ts` doubled for the answer/cancel pair. **No consumer** in this
slice.

## Summary

Adds the two outbound (client → daemon) modal-resolution frames to the wire:

- `src/shared/wire/types.ts` — `'modal_answer'` / `'modal_cancel'` join `EnvelopeType` beside the
  existing inbound `'modal_shown'`/`'modal_dismissed'`. Two new payload interfaces,
  `ModalAnswerPayload{ modal_id, option_id, answer_token }` and `ModalCancelPayload{ modal_id }`,
  placed immediately after `ModalDismissedPayload`. Confirmed against SSOT spec #701
  (`protocol-mobile.md § Modal (v2)`, ADR 0009): **single** `option_id` (not the daemon-repo ADR 025's
  stale `option_ids[]`), **no** `conversation_id` (`modal_id` is the sole correlation key).
- `src/main/transport/modalResolutionEnvelope.ts` (new) — `buildModalAnswer` / `buildModalCancel`,
  each wrapping the caller-supplied payload in a typed `Envelope` and returning
  `encodeEnvelope(envelope)`. Pure — `id`/`ts`/`payload` injected, no clock/counter read, no side
  effects. MAY throw `WireEncodeError` on over-cap (propagated unchanged from `encodeEnvelope`, no
  try/catch added). Both builders share one file — the architect's call: they're two halves of one
  concern (*resolving an outstanding modal*, both keyed solely by `modal_id`), and #236 imports both
  together. No barrel; the module has never had one, and the renderer must never reach these.
- `src/shared/wire/types.test.ts` — a parallel **outbound** modal-vocabulary block beside the #201
  inbound block: admits the two `EnvelopeType` members, shapes both payloads, and asserts
  `not.toHaveProperty('conversation_id')` / `not.toHaveProperty('option_ids')` on the answer
  payload — the deterministic guard against the stale ADR-025 shape leaking back in.
- `src/main/transport/modalResolutionEnvelope.test.ts` (new) — four tests using the **real** codec
  (round-trip through `decodeEnvelope`, not a mock): happy path + over-cap `WireEncodeError` for each
  builder.

`npm run build` + `npm test` green. Fan-out check (done, per the spec): zero consumer cascade — no
production code does an exhaustive `switch` over `EnvelopeType` (the three exhaustive switches in the
tree all discriminate `DaemonEvent`, not `EnvelopeType`), so the two new union members needed no
companion `assertNever` fix-up anywhere.

## Patterns established

- **A stale, superseded external ADR shape gets a deterministic test guard, not just a code-comment
  warning.** A QMD search surfaces daemon-repo ADR 025's older `modal_answer{conversation_id,
  option_id|option_ids[]}` shape; the SSOT (#701) supersedes it with single-`option_id`,
  no-`conversation_id`. Rather than trust the type alone to keep the stale shape out, the test suite
  pins `expect(payload).not.toHaveProperty('conversation_id')` /
  `not.toHaveProperty('option_ids')` — belt-and-suspenders where the type is the belt (compile-time)
  and the test is the suspenders (deterministic runtime check), not a second stochastic rule.
- **Two builders share one file when they're two halves of one concern, not two unrelated concerns.**
  The module's one-concern-per-file rule doesn't mean one-function-per-file — `sendMessageEnvelope.ts`
  and `requestSnapshotEnvelope.ts` are each single-builder precedents, but `modal_answer`/
  `modal_cancel` both resolve the same outstanding-modal concern and are always imported together by
  their sole future consumer (#236), so one file is the correct grain here.
- **An outbound-only wire slice needs no decode path and no `DaemonEvent` fan-out.** Unlike every
  prior wire-type ticket in this codebase (#201, #214, #217, #229 — all inbound), this slice touches
  neither `inboundMessage.ts` nor any of the three `DaemonEvent`-consuming bridges. The touchpoint
  floor for a pure outbound builder is exactly two files (`types.ts` + one new builder file) plus
  their tests — smaller than any inbound counterpart.

## Lessons learned

- None beyond the above — the ticket built exactly to spec with no surprises (the architecture spec's
  own fan-out check and field-set re-confirmation were the sources of what could have gone wrong, and
  both held).
