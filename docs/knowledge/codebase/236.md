# #236 — Main-side modal-answer command: mint `answer_token`, route + send `modal_answer` / `modal_cancel`

Main-command slice of the answer/cancel path, split 3-way (by transport/render layer) from
[#225](https://github.com/pyrycode/pyrycode-desktop/issues/225): [#235](235.md) (wire + builders,
done) → **#236 (this, main-command wiring, security-sensitive)** →
[#237](https://github.com/pyrycode/pyrycode-desktop/issues/237) (answerable-modal renderer buttons,
next). Shipped as PR #240 (`7ba81f4`), spec `ebe76a6`. Security-sensitive; size S; the exact analogue
of the `requestSnapshot` command path (#180 → #187) — the command is defined and handled main-side
even though nothing dispatches it yet.

## Summary

Wires the main-side command path that resolves an outstanding permission/trust modal, mirroring the
existing `sendMessage`/`requestSnapshot` command-path precedent across three production files:

- `src/shared/ipc/commands.ts` — two new `RendererCommand` members. `answerModal{payload:
  AnswerModalCommandPayload}` where `AnswerModalCommandPayload = Omit<ModalAnswerPayload,
  'answer_token'>` (`{ modal_id, option_id }`, `answer_token` structurally excluded by construction —
  not by convention); `cancelModal{payload: ModalCancelPayload}`, the wire cancel payload reused
  verbatim. Pure constructors `answerModalCommand`/`cancelModalCommand` (neither mints a token). Two
  new `isRendererCommand` switch cases added in lockstep with two new module-private guards,
  `isAnswerModalPayload`/`isCancelModalPayload` — structural minimum (object, non-null, the modeled
  string fields present); neither guard rejects a smuggled extra `answer_token` field, since the
  main-side sender's fresh-literal construction (below) is the actual net.
- `src/main/index.ts` — two new `onCommand` switch cases, direct to the connection method (no
  facade/orchestrator, mirrors `requestSnapshot`): `case 'answerModal': connection.answerModal(command.payload)`
  / `case 'cancelModal': connection.cancelModal(command.payload)`.
- `src/main/daemonConnection.ts` — two new methods on `DaemonConnection`, both the `send`/`requestSnapshot`
  inert-no-op-when-disconnected shape (`if (driver === null) return`, full-body `try {} catch {}`,
  never throws out of the module). `answerModal` mints a fresh `answer_token` via a new `mintToken`
  DI seam (default `() => randomUUID()` from `node:crypto`, resolved alongside `now`/`createDriver`)
  and builds the wire `ModalAnswerPayload` as a **fresh object literal** naming exactly the three
  modeled fields (`modal_id: payload.modal_id, option_id: payload.option_id, answer_token:
  mintToken()`) — never a spread of the command payload — before calling `buildModalAnswer` (#235)
  and `driver.sendMessage(bytes)`. `cancelModal` does the same with a fresh `{ modal_id:
  payload.modal_id }` literal into `buildModalCancel`. Both share the module's single `nextEnvelopeId`
  counter, advancing only on a successful build.

No renderer dispatch, no `interactive` flip — the fire site (renderer buttons) is #237.

`npm test` (998 passed, 3 pre-existing skips) + `npm run build` green.

## Patterns established

- **`Omit<WirePayload, 'field'>` makes a field-exclusion a compile-time guarantee, not a convention.**
  `AnswerModalCommandPayload = Omit<ModalAnswerPayload, 'answer_token'>` ties the command payload's
  field names to the wire contract while making "no member carries a token" (AC1) something the
  compiler enforces, not something a docstring asserts. Pinned by a `@ts-expect-error` excess-property
  test — gate-enforced because `src/shared/**/*` is in both `tsconfig.node.json` and the renderer
  tsconfig's `include`, so the pin can't silently rot on one side.
- **Belt-and-suspenders across two *different* enforcement layers, not two copies of the same one.**
  The untrusted-boundary guard (`isAnswerModalPayload`) is a structural minimum — it does not reject a
  smuggled `answer_token` field, because rejecting it isn't its job. The actual net is the main-side
  sender's **fresh-literal construction**: `answerModal` never spreads the command payload into the
  wire payload, so a renderer-supplied token can never reach the wire regardless of what the guard
  lets through. The guard (stochastic-adjacent, boundary validation) and the fresh literal
  (deterministic, always-runs code shape) are different fabric — mirrors the pipeline's general
  belt-and-suspenders principle.
- **A DI seam for the one place randomness enters a security-sensitive module.** `mintToken?: () =>
  string` on `DaemonConnectionDeps`, resolved the same way as `now`/`createDriver`
  (`deps.mintToken ?? (() => randomUUID())`), keeps `answerModal`'s token-mint deterministic under
  test (a fixed string, or a counter for the anti-replay-uniqueness test) without touching production
  behavior. `randomUUID` from `node:crypto` needed no new dependency — the module already imports
  `randomBytes` from the same package (`fileSecretPersistence.ts`).

## Lessons learned

*Lifted from the PR body's "Lessons learned" section (verbatim).*

- `AnswerModalCommandPayload = Omit<ModalAnswerPayload, 'answer_token'>` makes the token-exclusion
  (AC1: "no member carries a token") a compile-time guarantee, and the `@ts-expect-error`
  excess-property test that pins it is gate-enforced because `src/shared/**/*` is in both typecheck
  configs' `include`.
- Two layers guard the smuggled-token case with *different fabric*: the boundary guard
  `isAnswerModalPayload` is a structural minimum (a smuggled `answer_token` still passes — it isn't
  the guard's job to reject it), and the main-side sender's **fresh-literal** construction (never a
  spread of the command payload) is the deterministic net that makes the minted token always win.

## Testing

- `src/shared/ipc/commands.test.ts` — `isRendererCommand` guard cases (valid/missing-field/no-payload
  for both members), constructor round-trip cases, and the boundary assertion that a payload carrying
  an *extra* `answer_token` still guards `true` (documents structural-minimum, not rejection).
- `src/main/daemonConnection.test.ts` — two describe blocks mirroring `requestSnapshot`'s four cases
  (no-op before `start()`, forwards one envelope decoding to the right `type`/`id`/`ts`/payload,
  shares the `nextEnvelopeId` counter with `send`, does not throw when `driver.sendMessage` throws),
  plus `answerModal`-specific: the sent frame's `answer_token` equals the injected `mintToken()`
  result; two calls with a counter `mintToken` produce two distinct tokens (anti-replay uniqueness);
  and a payload cast through `unknown` carrying a smuggled `answer_token` sends the *minted* token, not
  the smuggled one (fresh-literal proof). `cancelModal`-specific: an extra field on the input payload
  does not cross the wire.
