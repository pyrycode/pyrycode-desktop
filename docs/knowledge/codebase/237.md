# #237 — Answerable modal: option buttons dispatch `modal_answer` / `modal_cancel` and clear the prompt

The terminal render slice of the modal vertical (ADR [0009](../decisions/0009-modal-prompt-model.md)),
last of six: [#201](201.md) (transport) → [#223](223.md) (store + bridge) → [#224](224.md) (interactive
render) → #225 (answer path, split 3-way, no codebase file — a pure split ticket) → [#235](235.md)
(wire + builders) → [#236](236.md) (main-command) → **#237 (this, answerable buttons)**. Shipped as PR
[#243](https://github.com/pyrycode/pyrycode-desktop/pull/243). Not security-sensitive (renderer-only;
the `answer_token` is minted main-side by #236, never here). Size S. Code review: **PASS**, one
non-blocking SHOULD-FIX (Cancel placement vs. Figma) + one NIT (focus trap/`Escape`, deferred again).

## Summary

Wires #224's inert option buttons and adds a new leading cancel affordance so the modal actually
resolves, closing the modal vertical:

1. **New `src/renderer/src/screens/conversation/modalResolution.ts`** — a React-free, framework-free
   `deps`-injected pair, the `composerSend.ts`/`submitMessage` precedent applied a second time (this
   file is *where* the AC4 guard lives, since `vitest.config.ts` runs `environment: 'node'` — no DOM,
   no click firing — so the pure helper is the only unit-testable surface):
   - `answerPrompt(modalId, optionId, deps)` — guarded `deps.sendCommand(answerModalCommand({ modal_id:
     modalId, option_id: optionId }))` (the camelCase→snake_case rename happens **here**, at the
     dispatch site), then **unconditionally** (outside the `try`) `deps.dispatch({ type: 'dismissed',
     modalId, outcome: optionId, source: 'local' })`.
   - `cancelPrompt(modalId, deps)` — same shape, `cancelModalCommand({ modal_id: modalId })`, outcome
     `MODAL_CANCEL_OUTCOME = 'cancelled'` — a sentinel deliberately chosen to match the daemon's own
     `OutcomeCancelled` wire vocabulary (pyrycode #727/#701) so #227's resolution toast can reconcile
     local-optimistic and daemon-sent dismissals under one vocabulary.
   - A `sendCommand` throw is swallowed (`try { … } catch (error) { console.error(...) }`, AC4); the
     `dispatch` is outside the `try` so a bridge failure never blocks the local clear.
2. **`PermissionModal.tsx`** — `PermissionModalView` gains two **required** injected effects,
   `onAnswer(modalId, optionId)` / `onCancel(modalId)` (the `RepairPrompt` idiom — a view that cannot
   answer is a bug, so not optional). Each option button gains `onClick={() =>
   onAnswer(prompt.modalId, option.id)}`; a **new** leading cancel button (`.permission-modal__cancel`,
   deliberately **not** `.permission-modal__option` — see Testing) is prepended to the action row with
   `onClick={() => onCancel(prompt.modalId)}` and the client-owned label `Cancel`. The container
   (`PermissionModal`) now also reads `dispatch` via `useModalStore(s => s.dispatch)` and wires both
   handlers to `modalResolution`'s helpers, dereferencing `window.pyry.sendCommand` only inside the
   handler closures (the `Composer.handleSubmit` discipline — the empty-case server-render test never
   touches the bridge).
3. **`conversation.css`** — `.permission-modal__option` and the new `.permission-modal__cancel` share
   one grouped selector for the text-button treatment (pill, transparent fill, `--color-primary` label,
   `:focus-visible` outline); `.permission-modal__cancel` alone adds `margin-right: auto` so it
   left-aligns in the `flex-end` action row while the daemon options stay right-aligned. No new tokens.

No new store representation, no new `ModalEvent` arm (reuses the existing `dismissed` arm verbatim), no
new command (both landed in #236), no `interactive` flip (AC5, still #179's).

### Data flow

```
user clicks option "allow-once"
  → PermissionModalView onClick → onAnswer('m1', 'allow-once')
    → PermissionModal container → answerPrompt('m1', 'allow-once', { sendCommand, dispatch })
      → sendCommand(answerModalCommand({ modal_id: 'm1', option_id: 'allow-once' }))   [guarded]
          → main: daemonConnection.answerModal mints answer_token, sends modal_answer  (#236)
      → dispatch({ type: 'dismissed', modalId: 'm1', outcome: 'allow-once', source: 'local' })
          → reduceModal removes m1 → outstanding[1] becomes [0] → next prompt renders (FIFO, #224)

user clicks Cancel
  → onCancel('m1') → cancelPrompt → sendCommand(cancelModalCommand({ modal_id: 'm1' }))  [guarded]
                                  → dispatch({ type:'dismissed', modalId:'m1', outcome:'cancelled', source:'local' })
```

The clear is **optimistic**: once #179 is live, a later daemon `modal_dismissed` for the same
already-cleared `modalId` hits `reduceModal`'s same-reference no-op (ADR 0009) — no double-removal
hazard.

`npm test` (1005 passed, 3 pre-existing skips), `npm run typecheck`, `npm run build` all green. New
coverage in `modalResolution.test.ts` (snake_case rename assertion, unconditional-dispatch-after-throw
for both functions, `answer_token` absent from the sent payload); `PermissionModal.test.tsx` updated for
the now-required view props and a leading-cancel-button assertion.

## Patterns established

- **The `node` test environment forces behavior into a pure, deps-injected helper co-located with the
  view.** `vitest.config.ts`'s `environment: 'node'` (no DOM) means a click handler on a React element
  can never be exercised directly. `modalResolution.ts` is the second instance (after
  `composerSend.ts`) of the shape this forces: put the guarded-send + dispatch logic in a plain function
  taking injected `{ sendCommand, dispatch }`, test *that* with spies, and let the view/container wiring
  stand on type-level guarantees (required props, correct arg order) rather than DOM assertions.
- **A container-vs-content class distinction matters for test-string matching, not just CSS.** The
  cancel button got its own `.permission-modal__cancel` class instead of reusing
  `.permission-modal__option` specifically so `optionCount`-style test helpers that match on class
  substring don't silently inflate. The PR's own "Lessons learned" independently rediscovered a sharper
  version of this same hazard one level up (see below).
- **Optimistic local clear + same-reference reduce no-op is how a render slice can resolve state before
  the round-trip completes.** `answerPrompt`/`cancelPrompt` dispatch `dismissed` immediately on click,
  never waiting on a daemon reply; ADR 0009's `reduceModal` same-reference-on-unknown-id behavior is
  what makes a later, genuine daemon `modal_dismissed` for the same id safe as a no-op rather than a
  double-removal bug. The render slice leans on a reduce guarantee written three tickets earlier
  (#122) precisely because that guarantee existed before it was needed.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section (verbatim).*

- The `.permission-modal__options` **container** class is a prefix of the option-button class
  (`__option` ⊂ `__options`), so a naive `class="permission-modal__option` count/order check silently
  matches the container div (which precedes all children). Bound the class-token match with a trailing
  `"`/space to isolate the buttons.

From the code-review PR comment (PASS, one SHOULD-FIX + one NIT):

- **Cancel placement diverges from the Figma reference, flagged non-blocking.** The Figma Dialogs
  section (node `22-3`) clusters Cancel with the confirming action at the **trailing (right)** edge in
  every example dialog (`Cancel Save`, `Cancel Create`, `Cancel Pair`) — there is no far-left Cancel in
  the source, and the M3 basic-dialog convention agrees. This slice's `margin-right: auto` pushes Cancel
  to the **far-left** instead, a deliberate adaptation for the *multi-option* permission modal (visually
  separating "abandon" from the daemon's N options, which a single-action dialog doesn't have to solve).
  The reviewer called this a defensible read of a genuine Figma gap, not a spec-compliance bug, but
  flagged it for the PO/architect to confirm the intended placement **before #179** makes the modal
  live — if the Dialogs trailing-group pattern should hold instead, drop `margin-right: auto` and let
  Cancel lead the right-aligned group rather than the far-left of the row. **Unresolved — next slice
  touching this modal's chrome (or #179 itself) should settle it.**
- The dialog still has no `Escape`-to-cancel handler or focus trap (the #224 NIT, deferred a second
  time). The buttons are keyboard-operable via native `<button>` + `:focus-visible`, so this slice's a11y
  bar is met; picking this up is explicitly deferred again to whenever #179 flips `interactive` and the
  modal actually renders live, not to a specific ticket.

## Testing

- `modalResolution.test.ts` (new) — `answerPrompt`/`cancelPrompt` each: `sendCommand` called once with
  the correctly-renamed snake_case payload; `dispatch` called once with the `dismissed` event
  (`outcome` = `optionId` for answer, `MODAL_CANCEL_OUTCOME` for cancel, `source: 'local'` both); a
  throwing `sendCommand` spy does not propagate and `dispatch` still fires exactly once (AC4); the sent
  payload has only `modal_id`/`option_id` — no `answer_token` (documents the `Omit`-exclusion from #236
  at this call site too).
- `PermissionModal.test.tsx` (updated) — `PermissionModalView` calls now pass no-op `onAnswer`/`onCancel`
  spies (props are required); `optionCount` narrowed to match `permission-modal__option"` (quote-
  terminated) so the new cancel button and the `__options` container div don't inflate the count; new
  assertion that the cancel button is the action row's leading element with the `Cancel` label; the
  container's empty-case (`renderToStaticMarkup(<PermissionModal />) === ''`) is unchanged.
