# #242 — New-discussion FAB on the Channel List: create + open thread

Render half of the "create a new conversation" vertical (split from [#142](../codebase/142.md)),
sibling of the already-merged transport ticket [#241](241.md). Shipped as PR #271. Not
security-sensitive — renderer-only; dispatches an already-typed command and consumes an
already-typed event, touching no keys, sockets, or frames. Size S.

## Summary

Adds the `+` new-discussion FAB (Figma 15-106) to the Channel List home screen. On click it fires
the `createConversation` command (fire-and-forget); when the daemon confirms with a
`conversationCreated` event, the paired shell navigates list → thread by reusing the existing
`open` transition. No new route, nav arm, or store slice — the ticket's explicit constraint.

- **New `src/renderer/src/store/conversationCreatedBridge.ts`** — the twin of
  `conversationListBridge.ts` for the create/created pair, four exports:
  - `requestNewConversation(sendCommand)` — sends the inline literal
    `{ type: 'createConversation', payload: { is_promoted: false, name: null, cwd: null } }` (an
    ad-hoc discussion, daemon-default name/cwd; `null` is on the wire, not an omission). No
    builder, mirroring `requestConversationList`.
  - `translateConversationCreated(event)` — the filter: `conversationCreated` → its payload,
    every other arm → `null` (`default: null`, not `assertNever` — this path deliberately
    consumes only the one arm, the `translateConversationsEvent` posture).
  - `subscribeConversationCreated(onDaemonEvent, onCreated)` — wraps the filter over the injected
    `onDaemonEvent`, returns the off-handle. Never throws into React.
  - `useConversationCreatedNav(onCreated)` — the React glue. Subscribes exactly once (empty-dep
    effect); holds the latest `onCreated` in a `useRef` so a fresh inline arrow each render
    doesn't cause a re-subscribe. `window.pyry` is dereferenced only inside the effect.
- **`ChannelList.tsx`** — `ChannelListView` gains `onNewConversation: () => void` and renders a
  new `NewConversationFab` as a **sibling of `renderBody(...)`**, so it appears in all three list
  states (not-loaded/empty/populated — AC1). `NewConversationFab` is an icon-only
  `<button type="button" aria-label="New discussion">` with an inline Material `add` SVG glyph,
  mirroring `BackControl`'s idiom — a native button is keyboard-focusable (AC4), `aria-label`
  supplies the accessible name. The container `ChannelList` wires
  `onNewConversation={() => requestNewConversation(window.pyry.sendCommand)}` — the `window.pyry`
  deref is inside the click arrow, never during render, so the server-render smoke is untouched.
- **`PairedShell.tsx`** — one added line in the container:
  `useConversationCreatedNav(() => dispatch({ type: 'open' }))`. The hook's effect derefs
  `window.pyry`, not the container, so `PairedShell` stays server-renderable. The payload is
  ignored — navigation is conversation-agnostic today (opens the single active conversation, the
  same interim as a row's `onClick={onOpen}`); the created `id` is available at the bridge seam
  for a future select-and-load ticket.
- **`channels.css`** — `.channel-list__fab` (+ `:hover`/`:focus-visible`) and
  `.channel-list__fab-icon`. See Lessons learned for the positioning fix and the two documented
  token-mapping deviations (radius, elevation).

`npm test` (1184 pass, 3 pre-existing skips), `npm run typecheck`, `npm run build` all clean.
Visual fidelity checked against the Figma screenshot (node 15-106) in a headless browser across
all three list states.

## Patterns established

- **A daemon-event-driven nav trigger is a small headless hook mounted in the router container,
  not a store slice.** `useConversationCreatedNav` subscribes directly via `window.pyry.onDaemonEvent`
  and calls the container's own `dispatch` — no new `PairedRoute`/`PairedNav` member, no Zustand
  slice. This is the pattern for any future "daemon event drives ephemeral nav" case as long as the
  nav is conversation-agnostic (single active conversation).
- **A command/event pair with only one live consumer still gets its own bridge module**, mirroring
  `conversationListBridge.ts` member-for-member (pure filter → pure subscribe → React glue) even
  though `conversationCreatedBridge.ts` has a single call site today. The consistency pays for
  itself in testability (spy-driven, no DOM harness) and matches the codebase's established
  request/reply bridge shape.
- **`margin-top: auto` + `align-self: flex-end` composed with `position: sticky; bottom` is the
  fix for pinning a floating element to the bottom-right of a flex-column scroller in every content
  state** — sticky alone only offsets during scroll overflow, so a short/empty list left the
  element at its top-of-flow position. This is now the reference pattern for any future
  floating-affordance-over-a-scroller case in this codebase.

## Lessons learned

From the merged PR's own "Lessons learned" section:

- **Sticky-bottom alone does not pin a FAB in a flex-column scroller.** `position: sticky; bottom`
  only offsets an element once its container actually overflows and scrolls — in the not-loaded /
  empty / short-list states nothing overflows, so the FAB stayed at its top-of-flow position
  instead of the bottom-right corner. Composing `margin-top: auto` (pushes the FAB to the bottom of
  the flex column when content is short) with `position: sticky; bottom` (floats it over the rows
  once the list overflows) pins it correctly in every state, with no portal and no DOM
  restructuring. This is the outcome of the spec's "if sticky proves fiddly, fall back to
  `position: fixed`" open question — the composed-rule fix was found first and preferred.
- **A Figma design-context extract's inline fallback color can name the wrong role.** The extract
  for this FAB emitted `bg-[var(--schemes/primary-container,#cfe4ff)]` — but `#cfe4ff` is actually
  the *on*-primary-container (light) color, not the container fill. The rendered screenshot (dark
  square, light glyph) was authoritative and confirmed the intended mapping
  (`--color-primary-container` fill / `--color-on-primary-container` glyph); a future ticket
  reading a Figma extract's inline CSS-variable fallback should treat it as a hint, not ground
  truth, and cross-check against the screenshot.

## Deviations (documented, code-review-accepted)

- **FAB radius:** Figma specifies a 16px corner; the token scale jumps 12→20 with no 16px slot.
  Mapped to `--radius-md` (20px), a +4px delta, documented in a `channels.css` comment (the
  `pairing.css:55` ±token-mapping precedent). No new shared radius token added for a 4px gap.
- **FAB elevation:** the FAB is the first elevation consumer in this codebase. The M3 level-3
  (base) and level-4 (hover) two-layer `box-shadow`s are inlined as structural literals with a
  comment, rather than extracting a new `--elevation-*` token — deferred until a second consumer
  appears (evidence-based, per CLAUDE.md's fix-selection principle).
