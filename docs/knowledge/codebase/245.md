# #245 — `userText` item in the conversation-timeline model

**Split from** [#179](179.md) (peeled out as the model prerequisite for the interactive-flip's
composer-echo cutover). **Size:** XS. **Status:** DONE, PR merged `8581af4`.

## What shipped

`ThreadItem` gains a fourth kind, `{ kind: 'userText'; text: string }`, and `ThreadEvent` gains the
matching `{ type: 'userText'; text: string }` arm. `reduceTimeline` folds it with a plain fresh
tail-append — mirroring the `toolUse`/`turnEnd` arms, not `assistantDelta` — leaving `phase` and all
existing items untouched:

```ts
case 'userText':
  return { items: [...state.items, { kind: 'userText', text: event.text }], phase: state.phase }
```

Minimal fields only: no `turnId` (the daemon assigns those; a renderer-sourced echo has none) and no
`seq` (wire fidelity for daemon deltas, irrelevant to a whole, renderer-local message).

Ships **dormant** — no producer dispatches a `userText` event yet, and no real render row exists.
`src/renderer/src/store/threadTimeline.ts`, its test file, and `ConversationScreen.tsx` are the only
files touched (3 total, all under the 5-file gate). `composerSend`, `sessionStore`, and
`timelineBridge.ts` are untouched — `userText` is renderer-sourced and never flows through the
`DaemonEvent` bridge.

See [ADR 0008](../decisions/0008-thread-timeline-model.md) for the model this extends.

## Patterns established

- **The `TimelineRow` exhaustiveness tripwire (`ConversationScreen.tsx`) fired exactly as designed.**
  That `switch (item.kind)` has no `default` and no `assertNever`, by intent (see the comment at
  `ConversationScreen.tsx:145-148`, built by #203/#218) — a fourth `ThreadItem` kind makes it
  non-exhaustive under `strict`, producing TS2366 until every kind is handled. Any future `ThreadItem`
  kind will retrip this the same way; the expected fix is a one-line placeholder arm, not a `default`
  catch-all. This is the mechanism, not a one-off — expect it again the next time `ThreadItem` grows.
- **A dormant item still forces the render switch to acknowledge it, via the type system, not a
  runtime check.** The placeholder (`case 'userText': return null`) is safe here *only* because no
  producer exists yet — the comment on that arm explicitly flags it as a stand-in, since a produced
  `userText` item is content and must be drawn, unlike the structural `turnBoundary` null arm it
  otherwise resembles.
- **The placeholder does not re-arm the tripwire for its own replacement.** Because `userText` is now
  handled (returns `null`), the switch is exhaustive again — the compiler will not force #179 to
  touch this arm when it lands the composer-echo producer. The obligation to replace `return null`
  with the real user bubble is carried by #179's own acceptance criteria, not by a future compile
  error. Anyone reviewing #179 should confirm that AC explicitly, not assume the tripwire will catch a
  forgotten render.

## Lessons learned

- The architecture spec flagged, ahead of implementation, that AC5's literal "`ConversationScreen`
  untouched" could not hold simultaneously with the build staying green, given the pre-existing
  tripwire. That was resolved in-spec (one-line dormant placeholder) rather than routed back to PO —
  worth remembering as the shape of the resolution when a similar tension shows up again: a
  deliberately-built compile-time tripwire wins over an AC's literal wording, and the deviation is
  cheap to call inline when it's minimal and deterministic.
