# #248 — Correlate a rejected `modal_answer` to a content-free rejection event (transport/main)

PR #266. Split from #227 (transport half; render half is #249, blocked-by this). Depends on #236/#237 (the answer path this correlates against, merged). `security-sensitive`, architect self-review PASS.

## Summary

Before this ticket, a daemon `error` that followed an ungranted device's `modal_answer` (#236 sends it, #237 optimistically clears the modal on send) decoded content-free to `{ kind: 'daemon-error' }` (#116) and fed exactly one consumer: `reassembler?.fail('daemon-error')`. With no debug bundle in flight that call was a silent no-op — the rejection vanished and the user saw nothing, because the modal was already gone from screen.

This ticket adds a new `DaemonEvent` arm, `{ type: 'modalAnswerRejected'; modalId: string }`, emitted by a main-side correlation window in `daemonConnection.ts` when a `daemon-error` arrives while an answer this client sent is still awaiting its reply. The arm ships **dormant**: all three exhaustive renderer bridges route or no-op it; #249 is the render slice that actually shows something.

## How it works

**`outstandingAnswers: string[]`** — a FIFO queue of outstanding answered `modal_id`s, module-local in `createDaemonConnection` beside `nextEnvelopeId`/`reassembler`. FIFO because the wire `error` carries no `modal_id` (ADR 0009) — attribution is pure send-order memory, not content.

Four seams, each 1–3 lines, `src/main/daemonConnection.ts`:

1. **Set-on-answer** (`answerModal`) — `outstandingAnswers.push(payload.modal_id)` runs *after* `driver.sendMessage(bytes)` succeeds, inside the existing `try`. A build/send throw records nothing (no `error` will ever come back for an answer that never left).
2. **Emit-on-error** (`case 'daemon-error':`) — keeps `reassembler?.fail('daemon-error')` unchanged, first, then `outstandingAnswers.shift()`; a defined result emits `modalAnswerRejected`, `undefined` (empty queue) emits nothing (AC2, preserves the prior drop behaviour).
3. **Clear-on-accept** (`case 'modal-dismissed':`) — `indexOf` + `splice` removes the first matching `modal_id` from the queue before the existing `modalDismissed` emit; a no-op if absent (a dismissal for a modal this client didn't answer, or an already-drained id). This is what stops a later unrelated `error` from mis-attributing to an already-accepted answer.
4. **Clear-on-reconnect** (`dial()`) — `outstandingAnswers.length = 0`, next to the existing `nextEnvelopeId = 2` reset. A fresh connection starts with no correlation window.

No `inboundMessage.ts` change — `error` → `daemon-error` already existed (#116); this is pure routing-layer state, no new inbound kind or parse function.

### Why FIFO, not a single slot

The grant is per-device, not per-modal (ADR 0009 §70): within one connection either every answer round-trips to `modal_dismissed` (granted) or every answer round-trips to `error` (ungranted). An ungranted user can answer modal A then queue an answer to modal B before A's `error` returns (#237 clears each modal optimistically — nothing on screen signals "wait"). A single slot would overwrite A with B and mis-attribute both errors. FIFO dequeues in send order, matching the daemon's own reply order.

### Precedence: bundle vs. answer correlation

The two `daemon-error` consumers are independent — neither suppresses the other. In the common case exactly one fires. The one documented overlap (a bundle download AND an outstanding answer AND a single `daemon-error` in that window) double-fires: the bundle fails *and* a rejection emits, and one is spurious because the content-free `error` genuinely carries no way to disambiguate. Accepted as a documented limitation (evidence-based: the overlap is unobserved; disambiguating it would need a new `isPending()` on the reassembler, scope creep into #116).

## No-echo discipline (AC3/AC4)

The emitted `modalId` is always the client's own outstanding-queue value — never a field read off the untrusted `error` payload. `error`'s `ErrorPayload.code`/`.message` are never decoded (already true since #116) and never surfaced. The arm's only field is `modalId`, so no field exists that could carry a token, key, or raw frame — enforced by the type, not convention.

## Bridges — atomic exhaustiveness touch

The new arm forced a case in all three `assertNever`-guarded `DaemonEvent` switches (the #241/#254 posture — compiler-forced one-liners, not independent design surface, satisfying the ≥5-file split gate as one `size:s`):

- `daemonEventBridge.ts` / `timelineBridge.ts` — folded into the existing null group, one-line no-op each.
- `modalBridge.ts` — the **owning** bridge. Added as a **distinct** dormant case (not lumped into the anonymous null group) so ownership reads clearly in the file; #249 flips this case to translate a real `ModalEvent` and add the `reduceModal` arm.

## Patterns established

- The FIFO-outstanding-answer-queue shape (push-after-send / shift-on-terminal-reply / drain-on-accept / reset-on-dial) is a reusable correlation pattern for any future "client sent X, needs to know if the daemon's opaque reply was a rejection of X" problem where the wire reply carries no correlating id.
- Confirms the #241/#254 "DaemonEvent-arm atomic-bridge exception": a new arm + its three compiler-forced bridge one-liners is one `size:s` ticket, not a split, because the intermediate state (arm without all three cases) does not compile.

## Lessons learned

- The spec named three exhaustive-`assertNever` bridges as the blast radius, but two more `DaemonEvent` consumers exist — `conversationListBridge` and `sessionIdBridge` (from #208/#259) — which switch on `event.type` with `default: return null` rather than `assertNever`. A new arm doesn't force a case there, so it's easy to undercount "how many files must change" from the spec's named list alone; grep each `DaemonEvent`-typed switch in the renderer rather than trusting a fixed bridge count. (Mirrors the same lesson already recorded for #227.)
