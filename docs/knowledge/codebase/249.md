# #249 — Render the modal-answer rejection surface

PR #268. Render half of #227 (split alongside #248, the correlated-emission transport half, merged
first). Blocked-by #248 (merged, PR #266). Not `security-sensitive` — pure renderer reading an
already-typed, content-free event; no keys, sockets, tokens, or raw bytes.

## Summary

Before this ticket, `modalBridge.ts` owned the `modalAnswerRejected` `DaemonEvent` arm as a **distinct**
dormant case (#248 deliberately kept it out of the anonymous null group) but returned `null` — so an
ungranted device's rejected answer produced no UI at all. Because the answer path clears the prompt
**optimistically** on click (#237's `answerPrompt`/`cancelPrompt` dispatch a local `dismissed`), the user
had no way to learn their answer round-tripped to a daemon `error` — the modal just silently vanished.

This ticket flips that dormant case and renders a transient, dismissible "Your answer was rejected."
banner stack at the modal host (`PermissionModal.tsx`), fully wired end to end: bridge → reducer/state →
pure view → container.

## How it works

**`store/modalPrompts.ts`** — two new `ModalEvent` arms:

- `{ type: 'rejected'; modalId: string }` — produced by the bridge from `modalAnswerRejected` (tag-flip
  precedent: `modalShown → shown`, `modalDismissed → dismissed`, so `modalAnswerRejected → rejected`).
- `{ type: 'rejectionDismissed'; modalId: string }` — a **local** user action, never produced by the
  bridge, dispatched inline from the container exactly as `answerPrompt`/`cancelPrompt` dispatch
  `dismissed` locally.

`ModalState` gains `rejections: readonly string[]` — arrival-ordered, de-duplicated bare `modalId`
strings, **orthogonal to `outstanding`** (the answered prompt is already gone by the time a rejection
arrives, so this is new UI state, not a re-surfaced prompt). Two new helpers mirror `removeById`'s
same-reference-on-no-op contract: `appendUnique` (dedup on `rejected`) and `removeRejection` (no-op on
an unknown id for `rejectionDismissed`). The existing `shown`/`dismissed` reduce arms were changed from
returning `{ outstanding: … }` to `{ ...state, outstanding: … }` so they stop silently dropping
`rejections` — the `assertNever` default is what forced both new cases to exist at compile time.
`selectRejections` is the new selector, returning the slice by reference.

**`store/modalBridge.ts`** — the flip: `case 'modalAnswerRejected'` now returns
`{ type: 'rejected', modalId: event.modalId }`, a fresh named-field literal (never `return event`,
matching the `modalShown`/`modalDismissed` reconstruction). No other bridge touched —
`conversationListBridge`/`sessionIdBridge`/`timelineBridge` use `default: return null` over `DaemonEvent`,
not `assertNever`, so a new `ModalEvent` arm doesn't force a case there.

**`screens/conversation/PermissionModal.tsx`** — one new pure view, one extended container:

- `RejectionSurfaceView({ rejections, onDismiss })` — new, exported, SSR-testable. Returns `null` on an
  empty list (zero layout footprint, the `Timeline`/`ThinkingIndicator` idiom). Else renders
  `.modal-rejections` containing one `.modal-rejection` per id, **keyed by `modalId`**, each with
  `role="alert"` (a live region so a screen reader announces the failure on arrival), the client-owned
  copy `"Your answer was rejected."`, and a `Dismiss` button calling `onDismiss(modalId)`. `modalId`
  is used only as the React key and the `onDismiss` argument — never rendered as visible text (AC4).
  `onDismiss` is a **required** injected prop (the `PermissionModalView` "a view that cannot answer is a
  bug" rule).
- `PermissionModal()` (container) — now reads **two** narrow slices, `selectOutstanding` and the new
  `selectRejections`. The early return fires only when **both** are empty
  (`if (!prompt && rejections.length === 0) return null`), since a rejection can show with no outstanding
  prompt. `pendingOption` is now guarded on `prompt` existing (it can be `undefined` while a rejection
  shows alone). Returns a fragment: `<PermissionModalView>` only when `prompt` exists, plus
  `<RejectionSurfaceView>` always, wired with an inline
  `dispatch({ type: 'rejectionDismissed', modalId })` — deliberately **not** extracted into a
  `modalResolution.ts` helper (it neither sends a command nor renames to the wire; that would add a 5th
  production file for one line).

**`conversation.css`** — new `.modal-rejections` (bottom-anchored absolute stack inside `.conversation`,
`pointer-events: none` so the full-width strip never blocks the composer beneath it, each banner
re-enabling its own `pointer-events: auto`) and `.modal-rejection` (a `--color-surface-container-high`
card with a `--color-error` `border-left` accent — a leading accent, not a filled error container, since
only the bare `--color-error` role token exists on desktop, #230). No new theme tokens added, per the
ticket's constraint. No bespoke Figma design exists for this surface (PO-confirmed gap); the chrome
reuses the existing modal/M3 tokens as a placeholder pending a follow-up.

### Data flow

```
daemon rejects an ungranted answer (correlated main-side, #248)
  → DaemonEvent{ type: 'modalAnswerRejected', modalId }
  → modalBridge.translateModalEvent → ModalEvent{ type: 'rejected', modalId }
  → modalStore.dispatch → reduceModal → rejections: [...,  modalId]  (outstanding untouched)
  → PermissionModal reads selectRejections → RejectionSurfaceView renders a banner

user clicks Dismiss
  → dispatch({ type: 'rejectionDismissed', modalId })
  → reduceModal removes the id from rejections (same-reference no-op if already gone)
```

`npm test` and `npm run build` both green (per PR description / ticket AC).

## Patterns established

- **A store slice can be orthogonal to an existing one and still live on the same `ModalState`.** Rather
  than a parallel store or a `Map`, `rejections` sits beside `outstanding` on one object; the two existing
  reduce arms (`shown`/`dismissed`) needed a one-line change each (`{ outstanding }` → `{ ...state,
  outstanding }`) to stop silently dropping the new field. Any future orthogonal slice added to
  `ModalState` should audit every existing non-spreading reduce arm the same way.
- **A container's early-return guard must consider every surface it renders, not just the first one
  added.** `if (!prompt) return null` was correct until a second, independent surface could render alone;
  the fix is `if (!prompt && rejections.length === 0) return null`, and every prompt-only derivation below
  it (`pendingOption`) needs an existence guard added at the same time.
- **A dormant `DaemonEvent` arm kept as a distinct case (not folded into the null group) pays off exactly
  once — at the flip.** #248 left `modalAnswerRejected` as its own `case` specifically so this ticket's
  diff is a one-line body swap, not a search through an anonymous `null` fallthrough list.

## Testing

- `store/modalPrompts.test.ts` — `rejected` appends and dedupes (same-reference on repeat);
  `rejectionDismissed` removes and no-ops on an unknown id (same-reference); FIFO stack order
  (`['m1','m2']`); field preservation across `shown`/`dismissed` vs. `rejected`/`rejectionDismissed`
  (each surface survives the other's reduce, by reference); `initialModalState.rejections` is `[]`;
  `selectRejections` returns by reference.
- `store/modalBridge.test.ts` — `translateModalEvent` maps `modalAnswerRejected` → `{ type: 'rejected',
  modalId }`, a fresh object (`not.toBe(event)`); removed from the "returns null" inverse-filter list;
  `subscribeModal` drives `rejections` `[] → ['mdl-9']` via a spied dispatch, with `outstanding` proven
  untouched.
- `screens/conversation/PermissionModal.test.tsx` — `RejectionSurfaceView`: empty list → `''`; one
  rejection → copy + dismiss control present, raw `modalId` absent from markup (a distinctive nonce,
  `mdl-nonce-deadbeef`, makes the negative assertion meaningful); `role="alert"` present; two rejections
  → two `.modal-rejection` elements. The container's existing empty-case test
  (`renderToStaticMarkup(<PermissionModal />) === ''`) was updated in wording only and stays green (both
  slices are empty under `getInitialState()`).
- **Coverage note (by design, not a gap):** the dismiss click→dispatch wiring is not click-tested — this
  file is SSR-only (`vitest.config.ts` runs `environment: 'node'`, no DOM, matching how answer/cancel
  clicks are not view-tested either, #237). Proven at two seams instead: the `rejectionDismissed` reduce
  arm (state transition) and the view rendering the dismiss button (structure). AC2 ("renders independently
  of `outstanding`") is a **type-level** guarantee — `RejectionSurfaceView` receives only `rejections`,
  never `outstanding`, so it structurally cannot depend on the prompt.

## Lessons learned

- Extending a shared reducer state object (`ModalState`) with an orthogonal field is not purely additive
  even when the new field's own reduce arms are new — every *existing* arm that builds its return value
  by naming fields rather than spreading (`{ outstanding: next }` vs. `{ ...state, outstanding: next }`)
  silently drops the new field the first time it fires. TypeScript's structural typing doesn't catch this
  (the narrower object is still assignable) — it only surfaces as a runtime data-loss bug. Worth grepping
  for non-spreading return literals in a reducer before adding a second field to its state shape.
