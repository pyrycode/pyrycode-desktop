`docs/specs/architecture/251-routing-aware-fake-relay.md`. Security-sensitive — architect

#252 (the real-daemon UI round-trip, blocked on this).

## What shipped

Two new files in `src/main/transport/`, following the codebase's `*Envelope.ts` convention:

- **`routingEnvelope.ts`** (86 lines) — a pure, I/O-free JSON codec for the daemon's
  `RoutingEnvelope` wire type (ported from `../../pyrycode/internal/protocol/envelope.go:42-77`).
  `encodeRoutingEnvelope(connId, frameText, token?)` splices `frameText` **verbatim** into the
  output (never parsed/re-serialized — the direct port of Go's `json.RawMessage`), `JSON.stringify`s
  `conn_id`/`token` for escaping, and omits `token` when absent/empty. `decodeRoutingEnvelope(text)`
  is **fail-closed**: returns `null` (never throws) on malformed JSON, a non-object, or a missing/
  mistyped `conn_id`; reads only `conn_id`/`frame`/`close_code` — it does not read `token` at all,
  so a hostile server-leg envelope can never smuggle a token back to a client.
- **`fakeRoutingRelay.ts`** (272 lines) — the relay itself. `startFakeRoutingRelay()` stands up one
  `ws` server on an ephemeral loopback port with two upgrade paths: `/v1/client` (raw, byte-identical
  to what the app already dials for `fakeRelayForwarder`) and `/v1/server` (routing-envelope, where a
  real `pyry` daemon registers). Client legs are multiplexed by a `conn_id` map; the server leg is
  singular (first-claim-wins, `x-pyrycode-server` header captured but unvalidated — leg identity is
  by upgrade path). Public surface (`url`/`whenReady`/`close`) mirrors `FakeRelayForwarder`
  field-for-field; the `whenReady` gate now waits for the server leg **and at least one client leg**
  (the routing analog of the forwarder's two-leg gate).

Two test files (`routingEnvelope.test.ts`, `fakeRoutingRelay.test.ts`) covering the codec in
isolation and the relay end-to-end against a fake raw client + fake routing peer — 19 new tests,
all loopback-only, no daemon/claude/UI involved.

## Patterns established

- **Content-blindness by import list, not by runtime check.** `fakeRoutingRelay.ts` imports only
  `ws`, Node built-ins, and its own `./routingEnvelope` — no `./codec`, no Noise modules, no
  `@shared` wire types. This is the same structural argument `fakeRelayForwarder.ts` uses; code
  review treats the import list itself as the enforcement mechanism for AC5, not a test assertion.
- **Fail-closed decode returning `null`, never throwing**, on the untrusted server-leg boundary —
  consistent with `codec.ts`'s category-only decode-error discipline elsewhere in the codebase.
- **Token handling as a structural, not incidental, guarantee**: the decoder simply has no code path
  that reads `token` off the wire, so "never echoed to a client" holds by construction rather than by
  a filter that could regress.

## Lessons learned

- `ws`'s `WebSocket.close(code)` sets `readyState = CLOSING` **before** it validates the code and
  throws on an out-of-range value — so a guarded (`try`/swallow) close still leaves that one socket
  poisoned (mid-close, unusable for further assertions). The relay itself stays up, which is the
  actual invariant under test; a robustness test asserting "the relay survives a bad `close_code`"
  must prove liveness via a **second, healthy** client, not by expecting the poisoned client's own
  socket to recover. (From the PR body's Lessons Learned section.)
