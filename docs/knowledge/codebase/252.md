Every other Desktop e2e ([#89](89.md) transport round-trip, [#93](93.md)/[#94](94.md) UI pair/send/
stream) drives a fake relay + a fake daemon that **always answer**, so they stay green even if a
real daemon never replies. This spec drives the **real** stack instead: it spawns a real `pyry`
daemon running real `claude --model haiku`, bridges it to the built Electron window through
[#251](251.md)'s `startFakeRoutingRelay()`, and asserts a non-empty `data-thread-role="assistant"`
reply streams into the thread for two consecutive sends. It is the thin client-layer net over the
daemon-side liveness test, `pyrycode#854` (merged) — that ticket fixed a fresh-daemon
interactive-bootstrap deadlock; this spec is what would have caught it from the desktop side.

## The binding problem — how it was actually resolved

The desktop always sends `conversation_id: 'default'` (`composerSend.ts`'s `MILESTONE_CONVERSATION_ID`,
verbatim) and cannot seed the daemon's registry from the client. A fresh real daemon does **not**
auto-bind an ad-hoc `'default'` conversation — `send_message` rejects an unbound conversation
(`pyrycode#678`) and the turn would time out with no reply ever streaming.

The fixture's `seedRegistry()` writes `<daemonHome>/.pyry/test/sessions.json` (one bootstrap-pool
session, fixed UUID `77777777-…`) and `conversations.json` (binds `id: "default"` →
`current_session_id: <that UUID>`) **before** spawning the daemon — the registry loads once at
startup, no reload. This works because `ConversationID` is an opaque string, not a validated UUID
(`pyrycode`'s `internal/conversations/conversation.go:17-18`), so `'default'` is a legal id. Field-
for-field port of `pyrycode#854`'s `seedBootstrapRegistry`/`seedBoundConversation`, with the one
change being the bound id itself.

## Design in one paragraph

The harness reuses [#94](94.md)'s pattern verbatim — the two `app.isPackaged`-gated dev affordances
([#97](97.md) loopback `ws://` relay, [#99](99.md) keychain-free secret backend), an isolated
`--user-data-dir`, `encodePairingPayload`, and the paste/Pair/Confirm/Send-enabled flow — with one
substantive swap: [#251](251.md)'s `startFakeRoutingRelay()` replaces #94's `fakeRelayForwarder` +
fake daemon pair, and a spawned real `pyry` sits on the relay's `/v1/server` leg instead. Fixture
chain `relay → daemon → page` forces LIFO teardown (`page → daemon → relay`, app closes first so its
supervisor can't churn-reconnect on the drop). Skip-gating (missing `claude`/`pyry`/credentials)
runs before any resource is created, so an unavailable real stack **skips cleanly** rather than
failing — the correct outcome for the agent pipeline, which has none of the three.

### Selectors — the one place #94 is stale

A real v2 daemon fans its structured stream to interactive conns, which renders into the timeline
(`ConversationScreen.tsx`) as `data-thread-role="assistant"`/`"user"` — **not** #94's non-interactive
`data-message-role="daemon"`/`"user"` `MessageBubble` path, which never fires here. This is the
[#179](179.md) prerequisite: before it, a non-interactive client got no reply at all from a v2
daemon.

### The cursor trap and the two-turn race

The streaming cursor `▎` (U+258E) is a child `<span class="bubble__cursor">` **inside** the assistant
row, so raw `textContent` is non-empty even on an empty streaming bubble. `nonEmptyAssistantCount()`
strips `▎` before the non-empty check. Turn 1 asserts count ≥ 1, then waits `.bubble__cursor` to hit
count 0 (the `turn_end` quiesce signal) before snapshotting a `base` count for turn 2 — this kills
the race where turn 2's poll could see turn 1's still-streaming reply. Turn 2 asserts
**strictly-increasing** count (not `== 2`), robust to a tool call splitting one turn into multiple
assistant rows.

## Patterns established

- **A real-external-process e2e still forks a file-local `test.extend`, not a shared fixture** — same
  reasoning as [#93](93.md)/[#94](94.md): the daemon/relay/credential setup is scenario-specific, so
  it stays out of the scenario-agnostic `e2e/fixtures/electronApp.ts` ([#40](40.md)).
- **Skip-gating happens before any resource creation, inside the fixture, not the test body** —
  `testInfo.skip(condition, reason)` called for each missing prerequisite (binary, credential,
  readable `~/.claude.json`) before `mkdtemp`/`spawn`. A skip after resource creation would leak a
  temp dir or process; gating first makes "unavailable" and "leaked resource" mutually exclusive.
- **Process-group reaping via `detached: true` + `kill(-pid)`** is the deterministic backstop for
  reaping a spawned daemon's own grandchild (real claude): SIGTERM the group → grace period →
  SIGKILL the group if still alive, ESRCH-guarded throughout. The daemon's own SIGTERM handler reaps
  claude on the graceful path; the group-kill covers the case where `pyry` itself is force-killed
  first.
- **Startup-only stderr surfacing.** The daemon's stderr is captured only until the control socket
  becomes dialable (`waitForDaemonReady`); capture stops on readiness (`capturing = false`) so a
  post-handshake diagnostic can never tee message plaintext into a failure — the transport is
  content-free by construction ([#62](62.md)), and this is the deterministic guard that keeps it that
  way even in a test failure path.
- **Never echo `pyry pair` stdout.** It embeds the pairing token. `decodePairFields` scans lines,
  base64url-decodes, `JSON.parse`s, and picks the first object shaped like the three credential
  fields — but throws a static string on failure, never interpolating the scanned stdout.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The daemon's relay leg is `/v1/server`, not the Go liveness test's `/v2/server`.** [#251](251.md)'s
  relay identifies legs by exact upgrade path and rejects anything else (`legFor() → null`,
  terminating the socket); the daemon preserves an explicit `-pyry-relay` path verbatim. `/v2/server`
  in `pyrycode#854` is a Go-fake-relay-only convention — it does not apply to this bridge.
- **The `'default'`-binding fix hinges on `ConversationID` being an opaque string, not a UUID** (see
  above) — worth restating because it's easy to assume conversation ids are validated UUIDs and
  conclude seeding is impossible.
- **`e2e/` is excluded from both project `tsconfig`s**, so `npm run build` never typechecks specs — a
  standalone strict `tsc` pass is the only type signal, and it inherits [#94](94.md)'s harmless
  Playwright-`env` typing artifact (`string | undefined` vs. `electron.launch`'s expected env type).
  Same standing note as #94's lessons.
- **A decode/pair failure must surface only stderr, never stdout** — `pyry pair` stdout carries the
  pairing token, so `runPyryPair`'s rejection path interpolates captured stderr only.

## Testing

The deliverable **is** the test. `npm run build` and `npm test` (1073 unit tests) are unaffected —
this ticket adds no unit test and no production code. `npx playwright test --list` confirms the
default config lists only the three fake-transport specs and the new config lists only
`real-claude.spec.ts`. Run in the agent env (no credentials): skips cleanly at the credential gate
before any subprocess spawn or Electron launch — the exact pipeline-safe behavior the gating AC
requires. The RED/GREEN observation (a pre-#854 `pyry` times out on turn 1; a #854-inclusive `pyry`
passes both turns) is recorded as a manual operator note in the PR body, not runnable in the agent
env (no CI by policy, no Anthropic credentials here) — mirroring how [#89](89.md)/[#93](93.md)/
[#94](94.md) treat their own live-stack counterpart, [Live e2e runbook](../features/live-e2e-runbook.md)
(#13).
