# #256 — Run configuration pending write machine (optimistic → confirm/reject)

Renderer-side store machine for the interactive Run-configuration write path (parent #183), split
alongside #254 (merged)/#255/#259 (merged)/#257. Shipped as PR #281 (`737ab71`), code-review **PASS**
(one NIT, non-blocking — see below). Not security-sensitive; size S (upper edge — the architect noted
it as "the #259 single-ticket template" scaled up to a reducer). No Figma anchor — this slice delivers
only the state the interactive controls (#257) dispatch onto and read back; the visible surface is
entirely #257's.

## Summary

The Run configuration sheet holds the session's Model/Effort/YOLO as a read-only daemon snapshot
(`runConfigStore`, #187). Making it *writable* is hard because `set_session_settings`'s reply carries
no settings and the change lands on the *next* session spawn (daemon ADR 031) — the sheet cannot re-read
the new value from the daemon, so it must hold the requested change optimistically and settle it on a
correlated confirm or reject. Both correlated events already shipped dormant — `sessionSettingsUpdated
{sessionId, changeId}` (#261) and `sessionSettingsRejected {changeId}` (#269) — no-op'd in every
renderer bridge, waiting for this consumer. This ticket adds that consumer: two new files + a one-line
`App.tsx` mount.

- **`src/renderer/src/store/runSettingsWriteStore.ts`** (new) — an **adjacent** dedicated store, not a
  `runConfigStore` facet (the same two reasons as `sessionIdStore`, #259: App-level always-listening
  lifecycle vs. sheet-scoped; state orthogonal to the snapshot shape). `RunSettingsWriteState { pending:
  ReadonlyMap<changeId, SettingsChange>; confirmed: {model?; effort?; yolo?}; error: field | null }`, a
  **reducer** (not a single setter, unlike `sessionIdStore`) over the sealed
  `changeDispatched | settingsConfirmed | settingsRejected` event union, `createRunSettingsWriteStore`
  (DI-factory) → `runSettingsWriteStore` (singleton) → `useRunSettingsWriteStore` (hook). Three arms:
  `changeDispatched` records the pending change and clears `error`; `settingsConfirmed` commits **the
  value the client sent** (the event carries none) into `confirmed` and deletes the pending marker, or
  no-ops if `changeId` matches nothing (AC4 fail-closed); `settingsRejected` deletes the pending marker
  and sets `error` to the field, or no-ops on no match. A no-match returns the *same* state object so
  zustand skips the notify. `selectEffectiveSettings(snapshot, state)` composes the display per field:
  last-inserted pending value (optimistic) > `confirmed` override > snapshot base, `??`-on-`undefined`
  only (empty-string/`false` held verbatim, the `runConfigStore` posture). `selectError` and
  `selectPendingFields` round out the read surface for #257.
- **`src/renderer/src/store/runSettingsWriteBridge.ts`** (new) — the bidirectional data path, mirroring
  `sessionIdBridge.ts`'s shape. **Inbound:** `translateWriteEvent` maps `sessionSettingsUpdated` →
  `settingsConfirmed` and `sessionSettingsRejected` → `settingsRejected`, `default: null` for every other
  arm (the `translateSessionTransition` permanent-ignore idiom, not `assertNever`); `subscribeRunSettingsWrite`
  wires it to `dispatch` and returns the off-handle. **Outbound:** `submitSettingsChange(deps, change)`
  mints one `changeId` (default `crypto.randomUUID()`, injectable — the #236 token-mint DI precedent),
  **dispatches `changeDispatched` before sending** (so the pending marker exists before a race-back
  reply), then sends `{type: 'setSessionSettings', payload, changeId}` with the payload built by a
  per-field `switch` (`buildSettingsPayload`) carrying `session_id` + only the changed key — the
  omitempty presence contract honored by construction. `deps.sessionId` is typed non-null: #257 gates
  the controls on a present session id, so there is no null case for this ticket to guard. **Component:**
  `RunSettingsWriteData(): null` — one App-level `useEffect` subscribing via `window.pyry.onDaemonEvent`,
  off-handle as cleanup, `window.pyry` dereferenced only inside the effect (server-render invariant).
- **`src/renderer/src/App.tsx`** (modified, +6 lines) — mounts `<RunSettingsWriteData />` as a third
  App-level headless leaf, alongside `<ConversationListData />` and `<SessionIdData />`.

`npm test` (1229 pass, 3 pre-existing skips) and `npm run build` both green. Test-first: 32 new tests
across the reducer, the `selectEffectiveSettings` derivation, and the bidirectional data path, in two new
files (`runSettingsWriteStore.test.ts`, `runSettingsWriteBridge.test.ts`), isolated `createStore()`
instances / plain spies, no React, no jsdom.

## Patterns established

- **"Clearing the pending marker IS the rollback" — no explicit rollback mutation.** Both terminal arms
  (`settingsConfirmed`/`settingsRejected`) only ever delete the pending entry; the view falls back to
  `confirmed`/snapshot automatically through `selectEffectiveSettings`'s composition order. This is a
  cleaner generalization of `sessionIdStore`'s "whole-value replace" idiom to a three-state (pending /
  confirmed-override / base) composed read, without the reducer ever needing to know what the "old"
  value was.
- **A reducer over a single-mutation store is the right escalation when a holder gains real transitions.**
  `sessionIdStore` (#259) stayed a single setter because it has exactly one mutation ("record the latest
  id"). This ticket needed three real transitions (dispatch/confirm/reject) tied together by a
  correlation key, so it used the `sessionStore`-style sealed-event-union reducer instead — confirming
  the house rule is "reducer when there's more than one real transition," not "reducer for every store."
- **The confirmed-value-is-client-side design is now proven end-to-end.** The architect's key design
  call — that `runConfigStore.snapshot` stays the daemon's and the write store holds sparse overrides
  composed *over* it, never a duplicated full triple — shipped exactly as specified, closing the
  divergence hazard the ticket flagged (the confirmed display legitimately differs from the live daemon
  snapshot until the next spawn).
- **A fourth App-level always-listening leaf is now a firmly established shape**, not a one-off: after
  `ConversationListData` (#208) and `SessionIdData` (#259), `RunSettingsWriteData` is the third
  headless, `null`-rendering, off-handle-cleanup subscriber mounted in `App.tsx`'s top-level fragment —
  each isolating its own daemon-event subscription so a push event never cascades a re-render into `App`
  itself.

## Lessons learned

- **`vi.fn<[Args], Return>()` (the two-argument tuple generic) is rejected by this repo's vitest (2.1.9).**
  Use bare `vi.fn()` or the single function-signature generic (`vi.fn<(...args) => Return>()`) instead —
  the existing bridge tests already use bare `vi.fn()`, and this ticket's new tests follow that idiom
  after hitting the type error. Worth checking before writing spy-heavy bridge tests in this codebase.

## Code review note (non-blocking)

- **[NIT]** The spec's testing-strategy line claims two same-field outstanding changes resolve correctly
  "in **either** order," but the shipped tests cover only the dispatch-order case. `confirmed` tracks
  *confirmation* order, not *dispatch* order: if two same-field changes confirm in reverse (the second
  dispatched change's ack arrives first), `confirmed` lands the *first-dispatched* value, not the truly
  latest one. Benign under the single-client, sequential-daemon-reply model this app runs under, and it
  self-heals on the next snapshot; violates no AC. No change made — flagged for awareness only, in case a
  future ticket needs stricter same-field confirm-ordering guarantees.
