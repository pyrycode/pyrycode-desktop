# #257 — Interactive Model / Effort / YOLO controls (Run configuration sheet)

The last child of #183's interactive Run-configuration write path. Shipped as PR #283 (`3b3ac9d`),
code-review **PASS** (one SHOULD FIX, non-blocking — see below). Not security-sensitive; size S.
Figma `20-100` subtree (`20:111` Model, `20:130` Effort, `20:143` YOLO) — the interactive frame is
visually identical to #188's read-only render; only the operability changed.

## Summary

#188 rendered the Run configuration sheet's Model/Effort/YOLO sections read-only from `runConfigStore`'s
daemon snapshot. Both halves of the write machine had already landed dormant — the current session id
(`sessionIdStore`, #259) and the pending → confirm/reject → rollback machine (`runSettingsWriteStore`,
#256, reading `selectEffectiveSettings`/`selectError`). This ticket is the last piece: it wires the three
sections to that machine so selecting a model, picking an effort level, or toggling YOLO actually submits
a `setSessionSettings` change and the sheet reflects it optimistically, then confirmed or rolled back.

Two production files:

- **`src/renderer/src/screens/conversation/runSettingsControls.ts`** (new) — a React-free helper
  co-located with the sheet, mirroring `modalResolution.ts`'s shape. `changeSetting(deps, change)` is
  the whole AC5 gate: `deps.sessionId: string | null` — `null` (no `session_transition` marker yet)
  no-ops (no send, no dispatch); otherwise it narrows to `string` and forwards verbatim to #256's
  already-tested `submitSettingsChange`. Adds no send/dispatch logic of its own.
- **`src/renderer/src/screens/conversation/RunConfigSections.tsx`** (modified — the only view file this
  slice touches) — both the pure view and the container gained the write-path wiring:
  - `RunConfigView` gained two optional props, `onChange?: (change: SettingsChange) => void` and
    `errorField?: SettingsChange['field'] | null`, and derives three narrow per-control callbacks from
    the single `onChange` so the `SettingsChange` construction lives in exactly one place.
  - Each sub-section (`ModelSection`/`EffortSection`/`YoloSection`) gained a matching optional
    `onSelect`/`onSelect`/`onToggle` plus `error?: boolean`. **Operability keys off handler presence**,
    not a boolean flag: a section given a handler renders `role="button"`/`role="switch"` (drops
    `aria-readonly`), `tabIndex={0}`, and an `onClick`; a section given none renders byte-identical to
    #188's inert markup. This is the AC5 gate at the view layer.
  - The container now reads three store slices — `useSessionIdStore(selectSessionId)`,
    `useRunConfigStore(selectSnapshot)`, and `useRunSettingsWriteStore((s) => s)` (the **raw** write
    state, not `selectEffectiveSettings` — see *Lessons learned*) — composes `selectEffectiveSettings`/
    `selectError` in the render body, and builds `onChange` **only when `sessionId !== null`**, closing
    over `window.pyry.sendCommand` and the store's `dispatch` at that point. When `sessionId` is `null`
    (including under SSR) `onChange` is `undefined`, so the closure — and any `window.pyry` touch — is
    never constructed.
  - A new `RUN_CONFIG_ERROR_COPY` map (one apostrophe-free string per field — `renderToStaticMarkup`
    escapes `'` → `&#x27;`, the #188/#279 lesson) backs a new `RunConfigError` component: a
    `role="alert"` line under the section whose field matches `errorField`, styled with the existing
    `--color-error` token (no new theme token).
- **`conversation.css`** (modified) — the operable-affordance CSS (`cursor: pointer` +
  `:focus-visible` outline, keyed off `[role='button']` / `:not([aria-readonly])` so the read-only
  markup is untouched) and the `.run-config__error` rule (the `--color-error` accent line).

Rollback itself needed zero new code here: it is #256's store dropping the pending marker on reject,
which `selectEffectiveSettings` already falls through past automatically (AC4). This slice's only new
AC4 surface is the visible error line.

## Patterns established

- **Operability-by-handler-presence** is now the concrete instance of the "structural gate over
  runtime guard" shape this codebase already uses elsewhere (e.g. `LogDataSection`'s mock-free SSR): the
  container withholds the capability itself rather than passing a boolean the view has to check, so the
  inert path is provably the same code as the pre-existing read-only render, not a parallel branch that
  could drift from it.
- **Belt-and-suspenders, both deterministic fabric.** The AC5 gate is enforced twice — structurally (the
  container never builds `onChange` without a session id) and at runtime (`changeSetting`'s null guard)
  — and both are plain code, not a stochastic rule backed by a stochastic check. `sessionIdStore` only
  ever sets, never un-sets, its id, so the runtime layer is pure insurance plus the unit-test seam for
  AC5 (a view-only render test can't exercise a click).

## Lessons learned (from the PR body)

- The operable affordance keys off **handler presence**, not a boolean flag: a section given no
  `onChange` renders byte-identical to #188's read-only markup, so the AC5 "inert until a session id
  exists" gate is enforced structurally at the container (it withholds the handler) with
  `changeSetting`'s null guard as the deterministic safety net.
- `selectEffectiveSettings` returns a fresh object per call, so it must **not** be the zustand selector
  (would defeat `Object.is` and re-render every tick). The container selects the raw write state
  (`(s) => s`, stable identity between dispatches) and composes in the render body.
- Keyboard activation (Enter/Space on `role="button"` rows/segments) is deferred per the spec's Open
  Questions — click + `role="button"` is the baseline; the model list is intentionally not elevated to a
  `radiogroup` here.

## Code review note (non-blocking)

- **[SHOULD FIX, not applied]** The operable rows/segments/switch are non-native elements
  (`<div role="button">`, `<span role="button">`, `<span role="switch">`) made focusable with
  `tabIndex={0}` and a focus ring, but wire only `onClick`. React's synthetic `onClick` fires on pointer
  events, not on Enter/Space for these tags the way a native `<button>` gets for free — so a keyboard-only
  user can Tab onto each control and see the focus ring, but Enter/Space do nothing. This partially
  undercuts the "becomes operable" framing for keyboard users; `PermissionModal.tsx` uses native
  `<button type="button">` precisely to avoid this gap. The architect scoped keyboard activation out as a
  deliberate Open Question, so this was surfaced rather than blocking. Below the fail threshold — no
  change made. **Flagged for a fast-follow**: add `onKeyDown` (Enter/Space → the same `onSelect`/
  `onToggle` handler) to complete keyboard operability without restructuring.
