# #259 — Retain the current session_id from the session_transition marker

Renderer-side retention half of the interactive Run-configuration write path (parent #183), split
alongside #254 (merged, transport decode)/#255/#256/#257. Shipped as PR #262 (`7f07077`), code-review
**PASS** (one NIT, non-blocking — see below). Not security-sensitive; sized XS by the architect
(PO estimated S) — the smallest of the read-path holders, `conversationListStore` (#208) minus the
entire request half. Not UI-visible, no Figma.

## Summary

The transport (#254) decodes the `session_transition` marker and emits it to the renderer as the
`sessionTransition` `DaemonEvent`, carrying only `newSessionId`. Before this ticket nothing retained
it — the event is a one-shot IPC message, so a component not mounted when it arrives never sees it.
This ticket adds the holder: two new files + a one-line `App.tsx` mount, cloned from the
`conversationListStore`/`conversationListBridge` pair (#208) with the entire request half stripped:

- **`src/renderer/src/store/sessionIdStore.ts`** (new) — `SessionIdState { sessionId: string | null }`,
  `createSessionIdStore` (DI-factory, vanilla `zustand/vanilla`), the `sessionIdStore` singleton,
  `useSessionIdStore` hook, `selectSessionId` selector. `setSessionId` does an unconditional
  `set({ sessionId })` — whole-value replace, last-write-wins (AC2), holding an empty string verbatim
  rather than coercing it to `null` (AC4). `sessionId: null` is the distinct "no marker seen yet" state
  (AC1).
- **`src/renderer/src/store/sessionIdBridge.ts`** (new) — `translateSessionTransition` (pure filter,
  `switch (event.type) { case 'sessionTransition': return event.newSessionId; default: return null }`,
  AC3), `subscribeSessionId` (subscribes via injected `onDaemonEvent`, writes on `id !== null` — not
  truthiness, so an empty-string id isn't silently dropped), and `SessionIdData` (`(): null`, one
  `useEffect(() => …, [])` returning the subscription's off-handle as cleanup).
- **`src/renderer/src/App.tsx`** (modified, +5 lines) — mounts `<SessionIdData />` next to
  `<ConversationListData />` in the App-level fragment. The **only** existing file touched.

`npm test` (1111 pass, 3 pre-existing skips) and `npm run build` (typecheck + main/preload/renderer)
both green. Test-first, two new test files (`sessionIdStore.test.ts`, `sessionIdBridge.test.ts`)
cloned from the #208 tests.

## Patterns established

- **App-level always-listening vs. sheet-scoped is a real fork in the holder family, not a detail.**
  `runConfigStore`'s `RunConfigData` subscribes only while the Run config sheet is mounted (request +
  subscribe together, torn down on close); this ticket's `SessionIdData` subscribes unconditionally at
  App level, alongside `ConversationListData`, because the daemon can push a `sessionTransition` marker
  before any sheet ever opens. The architect explicitly declined to fold `session_id` into
  `runConfigStore` over this lifecycle mismatch (plus the orthogonal-shape argument: a bare string vs.
  a `{model,effort,yolo,usedTokens,windowTokens}` snapshot) — confirming "one store per independently-
  lifecycled concern" as the house rule, not just "one store per wire shape."
- **A reactive-only (push, no request) holder is strictly smaller than every prior read-path holder.**
  Both `runConfigStore` (#187, requests on sheet-open) and `conversationListStore` (#208, requests on
  the connected-edge) pair a subscribe effect with a request effect. This ticket has only the subscribe
  effect — no command, no `MILESTONE_CONVERSATION_ID`-keyed request, no connected-edge trigger, no
  `useRef` one-shot guard. Confirms the PO/architect's XS-over-S size call was correct in practice, not
  just estimated: the diff is 2 files instead of 3-4, with no request-guard test scenarios needed.
- **A shipped-dormant selector export is expected, not a smell, for this holder family.** Code review's
  one NIT (`useSessionIdStore`/`selectSessionId` unconsumed until #257) is the same pattern already
  precedented by `useConversationListStore` before #141 and `useModalBridge` before #223 — each time,
  the reviewer flagged it for awareness and passed anyway, because the split explicitly separates the
  data path from its consumer.

## Lessons learned

None beyond what's captured above — this ticket was a close structural clone of an already-reviewed
precedent (#208) with a mechanical subtraction (drop the request half), and shipped with zero review
findings beyond the expected dormant-export NIT.

## Open questions carried forward

- **#257 (later)** is the actual consumer: the interactive Run configuration controls read
  `useSessionIdStore(selectSessionId)` to un-inert themselves and to address a `set_session_settings`
  write to the session this holder currently retains. Until #257 lands, `sessionIdStore` is populated
  live (the App-level subscriber is unconditional) but read by nothing.
- **Empty-string `session_id` is a live daemon possibility, not just a test fixture** — the holder
  records it verbatim rather than normalizing it away. If a future `set_session_settings` write needs
  to reject an empty id, that validation belongs at #257's write site, not here (per the spec's open
  question 1).
