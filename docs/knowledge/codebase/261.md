# #261 — Correlate `set_session_settings` replies to a confirmed event by `in_reply_to`

Correlation slice of the interactive Run-configuration write path (grandparent #183 → #255 → #263/#264,
both merged). Peeled from #261's own sizing hedge at architect review: the rejected/error path is split
to the follow-up **#269** (blocked by this). Shipped as commit `4350f63` (branch `feature/261`),
security-sensitive; size S. Introduces the **match-key mechanism** #269 reuses. Consumed by **#256**
(pending→confirm/reject store, not yet built).

## Summary

#264 shipped `session_settings_updated` decode as an unconditional, uncorrelated emit — dormant because
a reply carrying only `session_id` cannot say *which* pending change it confirms. This ticket closes that
gap with a renderer-minted correlation key threaded IPC-only (never onto the wire) and a main-side pending
map keyed by the request's envelope id, matched against the reply's `Envelope.in_reply_to` (already
decoded by `decodeEnvelope`, codec.ts, but dropped past `parseInboundMessage` until now). Five production
files, zero new files, zero new exported types, no bridge edits — the file set and rationale the spec's
§ Scope determination predicted:

- **`src/shared/ipc/commands.ts`** — `setSessionSettings` gains a `changeId: string` field, a **top-level
  sibling of `payload`**, not nested inside it (the builder consumes only `payload`, so this is what keeps
  `changeId` structurally off the wire). `isRendererCommand`'s guard adds `'changeId' in value &&
  typeof value.changeId === 'string'` — the `message_id` precedent applied to a second command.
- **`src/main/index.ts`** — `connection.setSessionSettings(command.payload, command.changeId)`, a
  one-line pass-through in the `onCommand` switch.
- **`src/main/daemonConnection.ts`** — the bulk of the slice:
  - a new module-local `pendingSettings = new Map<number, string>()`, sited next to `outstandingAnswers`
    with the identical single-writer rationale (every mutation runs synchronously, no `await` between
    read and write).
  - `setSessionSettings(payload, changeId)` captures `envelopeId = nextEnvelopeId` **before** the build
    (the value the daemon will echo as `in_reply_to`), then records `pendingSettings.set(envelopeId,
    changeId)` **after** a successful `driver.sendMessage` — the `answerModal`/`outstandingAnswers.push`
    order, so a build/send throw (caught below) leaves no phantom entry.
  - `case 'session-settings-updated'` in the inbound switch flips from unconditional emit to
    correlation-gated, fail-closed emit: `inbound.inReplyTo === undefined` short-circuits before any map
    lookup; a `pendingSettings.get(inReplyTo)` miss also short-circuits (AC3 — a reply matching no pending
    entry, whether stale or a hostile daemon forging a confirmation for an id the client never sent, is
    silently ignored); a hit `delete`s the entry and emits a **fresh literal** `{ type:
    'sessionSettingsUpdated', sessionId, changeId }` — the numeric `in_reply_to` never rides the event,
    only the renderer's own `changeId` does.
  - `dial()` gains `pendingSettings.clear()` alongside the existing `outstandingAnswers.length = 0` reset
    (AC5 — a reconnect abandons outstanding changes; this is what makes `nextEnvelopeId`'s restart-at-2
    recycling safe, since a stale reply from the dead session can no longer correlate on the new one).
- **`src/main/transport/inboundMessage.ts`** — the `session-settings-updated` kind widens with an optional
  `inReplyTo?: number`; the `session_settings_updated` decode case propagates the **already-decoded**
  `envelope.in_reply_to` rather than re-decoding it (`decodeEnvelope` parsed it at codec.ts:135 all along
  — this slice is the first consumer). The content-free diagnostic log is unchanged (still `bytes`/`hash`
  only).
- **`src/shared/ipc/events.ts`** — the `sessionSettingsUpdated` `DaemonEvent` arm widens from `{ sessionId
  }` to `{ sessionId; changeId }`. A field-widen of an existing arm is transparent to all three exhaustive
  `assertNever` bridges (`daemonEventBridge`/`modalBridge`/`timelineBridge`) — they switch on `type` and
  no-op this arm regardless of its fields, so none needed a code change, only a test-literal update to
  satisfy the now-required `changeId`.

`npm test`, `npm run typecheck`, `npm run build` all green. Test-first: the two #264 inbound tests at
`daemonConnection.test.ts:1344`/`:1358` were reworked (unmatched-reply-emits-nothing +
matched-round-trip-carries-`changeId`, plus the "only `type`/`sessionId`/`changeId` cross IPC, no
`in_reply_to`" key-set pin), and new coverage added for two-outstanding-same-`session_id` (AC4) and
clear-on-`dial()` (AC5). The #263 outbound tests gained the new `changeId` arg to `setSessionSettings(...)`
calls, and their existing frame assertions now double as the "`changeId` never rides the wire" check.

## Patterns established

- **The match-key mechanism: mint client-side, remember server-process-side, correlate by
  `in_reply_to`, never echo the wire routing id back.** This is the first ticket to correlate a
  fire-and-forget command's reply where the renderer cannot learn the minted envelope id (unlike
  `answerModal`, where main mints and the renderer never needs to correlate at all). The renderer mints an
  opaque `changeId`, main is the sole party that ever sees `envelopeId`, and the two are joined only in
  the pending map — a hostile daemon forging `in_reply_to` for an unsent id finds no entry and is ignored
  by construction. #269 (rejected path) reuses this exact map and key.
- **A correlation map's lifecycle mirrors `outstandingAnswers` exactly: push-after-send, delete-on-match,
  clear-on-`dial()`, no cap.** Orphaned entries (a rejected change, whose error reply this slice doesn't
  correlate — that's #269) are accepted as bounded by human-paced settings changes and the `dial()` reset,
  the same evidence-based no-cap call `outstandingAnswers` (#248) already established.
- **Widening an existing `DaemonEvent` arm's fields is bridge-transparent.** Confirmed a second time
  (after #191's `used_tokens`/`window_tokens` widen) that growing an arm's payload, as opposed to adding a
  new arm, never touches the three `assertNever` bridges — only `npm run typecheck` finds the test
  literals that need the new required field.

None beyond what's captured above. No code-review PR comment recorded a finding; the architect spec's

## Open questions carried forward

- **#269 (rejected path)** reuses `pendingSettings` and `changeId` to correlate a `daemon-error` reply
  back to a pending entry by `in_reply_to`, and is the ticket that actually removes an orphaned entry left
  by a rejected change before `dial()`. The `daemon-error` kind currently carries no `inReplyTo` — #269
  needs the same carrier widen this slice added to `session-settings-updated`.
- **#256 (pending→confirm/reject store)** is the first real consumer of the widened `{ sessionId,
  changeId }` event; it must mint the same `changeId` into the `setSessionSettings` command it dispatches
  as the one this slice's `daemonConnection` receives back.
