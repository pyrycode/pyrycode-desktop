# #269 — Correlate `set_session_settings` errors to a rejected event by `in_reply_to`

Rejected-half sibling of [#261](261.md) (confirmed round-trip, merged PR #270). Peeled from #261's own
sizing hedge at architect review. Shipped as commit `74634cb` (branch `feature/269`, PR #272),
`security-sensitive`, size S, code review **PASS** (no findings). Reuses #261's `pendingSettings` map +
renderer-minted `changeId` unchanged. Consumed by **#256** (pending→confirm/reject store, not yet built,
blocked by both #261 and this).

## Summary

#261 correlated a *confirmed* `session_settings_updated` reply to its request via `Envelope.in_reply_to`,
but a *rejected* change comes back as the daemon's deliberately content-free `error` frame (#116) — which,
before this ticket, decoded to bare `{ kind: 'daemon-error' }` with no routing id at all. This ticket
widens that decode to carry the numeric `in_reply_to`, then correlates it against the same
`pendingSettings` map #261 built, emitting a new `sessionSettingsRejected{changeId}` `DaemonEvent` on a
match. Six production files, zero new files, zero new exported types — the documented atomic
new-`DaemonEvent`-arm exception (a union member + its three compiler-forced `assertNever` bridge cases
cannot be split across tickets and still pass `npm run build`):

- **`src/main/transport/inboundMessage.ts`** — the `daemon-error` kind widens from `{ kind: 'daemon-error' }`
  to `{ kind: 'daemon-error'; inReplyTo?: number }`. The `'error'` decode case now returns `{ kind:
  'daemon-error', inReplyTo: envelope.in_reply_to }` — propagating the **already-decoded** `Envelope.in_reply_to`
  (`decodeEnvelope`, codec.ts, always parsed it), never re-decoding or parsing `ErrorPayload`. The
  content-free diagnostic log is byte-for-byte unchanged (`bytes`/`hash` only) — `in_reply_to` is a
  routing id, not logged.
- **`src/main/daemonConnection.ts`** — the bulk of the slice, rewriting `case 'daemon-error':`
  (`:340-354` pre-ticket) into a **precedence gate**: `inbound.inReplyTo` is looked up in `pendingSettings`
  *first*; a hit `delete`s the entry and emits `{ type: 'sessionSettingsRejected', changeId }`, then
  `return`s — consuming the frame entirely, skipping **both** `reassembler?.fail('daemon-error')` **and**
  the #248 modal-answer FIFO `outstandingAnswers.shift()`. A miss (absent `inReplyTo`, stale id, or a
  hostile daemon forging a rejection for a change never dispatched) falls through to the two existing
  consumers exactly as before.
- **`src/shared/ipc/events.ts`** — new `DaemonEvent` arm, `{ type: 'sessionSettingsRejected'; changeId:
  string }`, sited next to `sessionSettingsUpdated`. Carries **only** `changeId` — deliberately no
  `sessionId` (the content-free `error` frame carries none, and `changeId` alone disambiguates two
  outstanding changes to the same session per AC4), no `in_reply_to` (stays main-internal), no error
  code/message (attacker-influenceable bytes; no consumer needs them).
- **`daemonEventBridge.ts` / `timelineBridge.ts` / `modalBridge.ts`** — one compiler-forced no-op case
  each, identical shape to `sessionSettingsUpdated`'s existing no-op (the `sessionSettingsUpdated`-was-a-
  no-op-until-#256 precedent, now doubled).

`npm test` (1197 passed, 3 pre-existing skips), `npm run typecheck`, `npm run build` all clean.

## Patterns established

- **A correlation map can gate which of several co-consumers of the same wire frame gets to see it.**
  Before this ticket, `daemon-error` had exactly two unconditional consumers (`reassembler?.fail`, the
  #248 modal FIFO). This is the first ticket to insert a **precedence check in front of** existing
  co-consumers rather than adding a third independent one — a settings-match consumes the frame entirely
  and both existing consumers are skipped, not merely also-fired. The rationale generalizes: an error
  correlated by a **unique per-request envelope id** is unambiguously the reply to *that* request, so it
  is provably neither a bundle error nor a modal-answer rejection — precedence isn't a tradeoff here, it's
  correctness.
- **Closing an orphan a sibling ticket explicitly deferred.** #261's own notes flagged that a rejected
  change's `pendingSettings` entry survived until `dial()` under the confirmed-only slice — an accepted,
  documented orphan. This ticket is the one that actually removes it on the correlated `error`, tightening
  the map's lifecycle to fully mirror `outstandingAnswers`' push-after-send/delete-on-match/clear-on-dial
  shape with no orphan window at all.
- **Widening a content-free decode kind with only a numeric routing id, never payload content.** The same
  move #261 made on `session-settings-updated` (`inReplyTo?: number`, propagated not re-decoded), now
  applied to `daemon-error` — confirms the idiom generalizes to any inbound kind needing request
  correlation without loosening its content-free posture.

## Lessons learned

- The content-free `error` decode (#116) required only carrying the numeric `Envelope.in_reply_to`
  (already surfaced by `decodeEnvelope`) — no `ErrorPayload` is parsed, so no attacker string can enter
  via a decode field.
- `toEqual({ kind: 'daemon-error' })` on the existing pre-#269 #116 test stayed green with no edit —
  vitest's `toEqual` ignores a present-but-`undefined` property, so widening a kind with an optional field
  is non-breaking to callers asserting the old literal shape.
