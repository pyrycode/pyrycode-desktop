# #275 — Reflect `conversation_updated` in the live Channel List

The list-reflect slice of the "save a discussion as a channel" vertical (split from #143, after the
transport half #273). Keeps the Channel List live: on a `conversationUpdated` daemon broadcast, the
desktop client re-requests the authoritative conversation list so a promoted (or renamed/archived)
row lands its new `is_promoted` in `conversationListStore` — moving it into the Channels tier via
the existing `partitionByPromotion`, with no reconnect and no view change. Shipped as PR #287, one
production file changed (`conversationListBridge.ts`) plus its test.

## Summary

Three edits, all in `src/renderer/src/store/conversationListBridge.ts`:

- **New pure predicate `isConversationUpdated(event): boolean`** — `event.type ===
  'conversationUpdated'`. Deliberately a plain boolean, not a type guard that narrows to the
  payload: the event's `id`/`name`/`cwd` are never consulted (AC3). Kept separate from
  `translateConversationsEvent` so that pure `event → rows | null` filter stays single-purpose.
- **`subscribeConversations` gained a required third param, `refreshOnChange: () => void`.** Still
  exactly one `onDaemonEvent` subscription (AC4) — the listener now has two independent `if`
  branches (`conversationsReceived` writes rows via `setConversations`; `conversationUpdated` calls
  `refreshOnChange`) that never cross-fire, since a single event is never both. Making the param
  required (not optional) forces every call site — the one production site and every existing test
  — to opt in explicitly; the compiler is the migration enforcement.
- **The re-request bound at the single `ConversationListData` call site**, reusing the existing
  `requestConversationList(window.pyry.sendCommand)` — no new command member, no new IPC channel.
  `window.pyry.sendCommand` is dereferenced only inside the arrow (i.e., when a `conversationUpdated`
  actually fires), never during render, so the pre-existing "server-renders to empty markup without
  touching `window.pyry`" test is unaffected.

`translateConversationsEvent` and `partitionByPromotion` are both untouched — the mechanism is
re-request (recommended by the ticket over an in-place store patch): the daemon's authoritative
`conversations` reply overwrites the store via the existing whole-array-replace `setConversations`,
so the path is drift-free and idempotent, including against a self-originated broadcast (the
promoting client also receives its own `conversation_updated`, but the re-request just re-fetches
the same authoritative list — no dedup needed).

`npm test` (1282 passed, 3 pre-existing skips), `npm run build` (typecheck + electron-vite) both
clean.

## Patterns established

- **A re-request over an in-place patch dissolves a whole category of concern for an unsolicited
  broadcast.** #273's spec explicitly flagged self-broadcast dedup and unknown-id reconciliation as
  "#275's concern" — choosing re-request over patching the store in place made both concerns
  vanish rather than requiring code to handle them: the daemon's authoritative reply is idempotent
  by construction (whole-array replace), and the broadcast's payload fields never need to be trusted
  or matched against local state.
- **A boolean trigger predicate, not a narrowing type guard, is the correct shape when a consumer
  reacts to an event's occurrence but never its payload.** `isConversationUpdated` returns `boolean`
  rather than `event is Extract<DaemonEvent, {type: 'conversationUpdated'}>` specifically to signal
  "the payload is structurally unused here" — a reviewer checking AC3 (id/name/cwd never consulted)
  can confirm it from the return type alone.
- **One `onDaemonEvent` listener, multiple independent reactions via separate `if` branches, scales
  cleanly** — this is now twice-precedented (`translateConversationsEvent` + `isConversationUpdated`
  living in the same listener body) as the way to add a new reaction to an existing single-listener
  bridge without introducing a second subscription. The two reactions are safe from cross-firing
  because the underlying event union already guarantees a single event carries only one `type`.

None beyond what's captured above — the PR shipped with no "Lessons learned" section (a clean,
