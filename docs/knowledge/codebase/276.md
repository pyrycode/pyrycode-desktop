# #276 — Thread overflow menu: top-app-bar entry point for the Channel Info sheet

Split from #148 alongside #277/#278/#279 (all three merged). PR #326. Spec:
`docs/specs/architecture/276-thread-overflow-menu.md`. See [Conversation
shell](../features/conversation-shell.md) for the feature line; this file covers implementation notes
and lessons.

## Summary

Adds the trailing `more_vert` overflow menu to the thread top app bar (Figma node 16-16) — the single
entry point to per-conversation actions, opening the Channel Info sheet first (#155, not built here).
Delivers the button, the open/close menu surface, and a documented `onChannelInfo?` extension slot; the
menu's one item ("Channel info") is enabled and live today but routed to a no-op since `PairedShell.tsx`
doesn't pass the callback yet. Renderer-only, one file plus its CSS and tests — no transport/store change.

Two new symbols in `src/renderer/src/screens/conversation/ConversationScreen.tsx`, mirroring the file's
pervasive pure-view/in-file-container split (`RepairPrompt`/`RepairControl`, `ConnectionBanner`/
`ConnectionBannerControl`):

- `ThreadOverflowMenuView` (exported, pure) — trigger button (`aria-haspopup="menu"`, `aria-expanded`)
  plus, when `open`, a `role="menu"` surface with one `role="menuitem"` row. No state, no effects — the
  entire tested contract, server-rendered both open and closed (the `InterruptButton`/`ThinkingIndicator`
  posture).
- `ThreadOverflowMenu` (in-file container) — screen-local `useState` for open/closed (ADR 0006, the
  `sheetOpen` precedent — resets on remount, never the session store), plus one `useEffect` that attaches
  `document` `mousedown`/`keydown` listeners only while open, torn down on close/unmount. Escape and
  outside-click both call `close()`; selecting the item calls `select()` (`onChannelInfo?.()` then close).
  Both close paths return focus to the trigger via a `triggerRef`.

Mounted at `{onBack && <ThreadOverflowMenu onChannelInfo={onChannelInfo} />}`, right after `BackControl` —
gated on `onBack` presence, the file's established "mounted in the paired shell" signal, and gated at the
*mount site* rather than self-gated so the container's hooks stay unconditional (rules-of-hooks). A bare
`<ConversationScreen />` renders neither the trigger nor `aria-haspopup="menu"`.

`ConversationScreenProps` gained one optional prop, `onChannelInfo?: () => void` — undefined this ticket,
so the menu item is a live no-op; `PairedShell.tsx` is untouched, #155's entire diff is threading this one
callback through to it.

## Patterns established

- **Render-site gating over self-gating when the gated component holds hooks.** `ThreadOverflowMenu` uses
  `useState`/`useRef`/`useEffect`; an internal `if (!visible) return null` would violate rules-of-hooks
  across remounts as `onBack` flips. Gating with `{onBack && <ThreadOverflowMenu .../>}` at the call site
  keeps the component's own hooks unconditional and still yields identical bare-render markup.
- **Optional-callback extension seam for a not-yet-built follow-up ticket.** Same shape as #278's
  `onChange?` for the #157 Workspace Picker: the prop is declared and forwarded now, ships absent (a live
  no-op), and the entire follow-up ticket (#155) is passing it from one call site.
- **DOM event types shadowed by React's synthetic import.** See Lessons below — the fix (`DocumentEventMap['keydown']` instead of a bare `KeyboardEvent` annotation) is a reusable pattern anywhere a
  `document`-level listener is added to a file that already imports React's `type { KeyboardEvent }`.
- **No z-index needed for a positioned overlay that must stay below other overlays.** DOM order alone
  keeps a `position: absolute` element above non-positioned siblings and below later-mounted positioned
  siblings (status sheet / permission modal) — see Lessons.

## Lessons learned

From the PR body:

- **DOM event types are shadowed by React's synthetic ones.** `ConversationScreen.tsx` does
  `import { type KeyboardEvent } from 'react'`, so a bare `KeyboardEvent` annotation on a `document`
  listener resolves to React's generic synthetic type, not the DOM one. Index the DOM event map instead —
  `DocumentEventMap['keydown']` / `['mousedown']` — for the exact global types without touching the
  import.
- **The overflow wrapper needs no z-index.** A `position: absolute` element already paints above the
  non-positioned message thread, and the later-in-DOM status-sheet / permission-modal overlays keep
  painting above it by tree order. Adding a positive z-index would lift the menu above those overlays —
  the exact stacking regression the spec's Open Question 2 flagged — so it was deliberately omitted
  (documented inline in the CSS). The menu and a sheet/modal never coexist anyway (outside-click dismisses
  the menu first).

## Verified at review time

- Visually confirmed against a token-loaded render: the trigger balances the back arrow across the
  top-bar band with a clean 4px gap above the Unpair row — the spec's Open Question 1 (trigger vs.
  Unpair-row clearance) resolved with no nudge needed.
- Interaction behavior (open→close toggle, Escape dismiss, outside-click dismiss, focus-return) is
  untested reviewed glue, per spec — the repo's `node`-env `renderToStaticMarkup` harness fires no events
  and runs no effects (the `Composer.handleKeyDown` / `UnpairControl` precedent). Only the pure view's
  static open/closed markup and the `onBack`-gated mount are asserted in tests.

## Open questions (flagged, not built)

- **Focus-into-menu on open** (arrow-key navigation among menu items) is out of scope — AC3 only requires
  Escape-dismiss and focus-return-to-trigger, both shipped. A later ticket adding keyboard menu navigation
  would add a first-item-focus-on-open effect.
- **Menu z-index vs. future overlays** — confirmed no regression against the current status-sheet/
  permission-modal stacking (see Lessons), but this relies on DOM mount order staying fixed; a future
  overlay mounted *before* the overflow menu in the child list would need its own stacking check.
