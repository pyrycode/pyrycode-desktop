# #278 — Workspace chip on the empty new-discussion thread

Split from #148 alongside #276/#277/#279. PR #310. Spec:
`docs/specs/architecture/278-workspace-chip-empty-thread.md`. See [Workspace
chip](../features/conversation-shell.md#workspace-chip-278) for the full feature write-up; this file
covers implementation notes and lessons.

## Summary

A pre-first-message pill at the top of the empty new-discussion thread showing the workspace `cwd` the
discussion will run in, with a disabled "Change" placeholder reserved for the not-yet-built #157
Workspace Picker sheet. Renderer-only — no transport/main-side change, no new dependency.

Three production files:

- `src/renderer/src/store/activeConversationStore.ts` (new) — a `sessionIdStore`-shaped Zustand store
  holding `ConversationCreatedPayload | null` verbatim.
- `src/renderer/src/PairedShell.tsx` — the `conversation_created` nav callback now also snapshots the
  payload into that store (previously it only fired the `open` nav, discarding the payload it already
  received).
- `src/renderer/src/screens/conversation/ConversationScreen.tsx` — the exported pure `WorkspaceChip`
  view (the `ThinkingIndicator` idiom) plus one store read and one mount line in the container.

Plus `conversation.css` (`.conversation__workspace-chip*`, token-only, no new token) and two new test
files/blocks.

## Patterns established

- **Payload previously received-and-dropped, now consumed.** `useConversationCreatedNav`'s callback
  signature didn't change — it already delivered the decoded `ConversationCreatedPayload`; the callback
  body just started using the argument it was throwing away. Worth checking for this shape before adding
  a new subscription: the data may already be flowing past a call site that ignores it.
- **Sibling-not-nested placement over threading a prop through a pure view's contract.** `WorkspaceChip`
  mounts as a flex sibling above `Timeline` rather than being threaded through `Timeline` → `EmptyThread`,
  even though the chip visually "belongs" to the empty-thread surface. Widening `Timeline`'s `{ items,
  now }` contract for an orthogonal concern would have cascaded every existing bare-render test call
  site; the sibling placement gets the identical visual result for zero edits elsewhere.
- **`disabled={!onChange}` as both the AC placeholder and the future extension seam in one line.** No
  separate "is this feature built yet" flag — the optional prop's absence *is* the placeholder state,
  and passing it later is the entire follow-up ticket's diff. Same seam #276 reserves for #155's
  `onChannelInfo?`.

## Lessons learned

From the PR body:

- The `onChange?` optional prop doubles as the AC4 placeholder and the #157 additive seam: the button
  renders `disabled={!onChange}`, so this ticket ships it disabled and #157 un-disables it by passing an
  `onChange` — no structural change. This is the same optional-prop extension seam #276 reserves for
  #155.

## Verified at review time

- No new CSS token was invented — `--radius-full`, `--color-surface-container-high`,
  `--color-outline-variant`, `--color-on-surface`, `--color-on-surface-variant`,
  `--color-surface-container-highest`, `--font-mono` all pre-existed in `tokens.css`, confirming the
  spec's "no new token" claim.
- The rejected "correlate `sessionIdStore` with `conversationListStore`" alternative (floated in the
  ticket body) has no join key — `sessionIdStore` holds a *session* id from `sessionTransition`,
  `ConversationSummary` is keyed by conversation `id`; the spec's `conversation_created`-snapshot design
  was the only narrow option and is what shipped.

## Open questions (flagged, not built)

- **Stale snapshot across unpair/re-pair.** `activeConversationStore` is a module singleton that outlives
  `PairedShell` unmounts; a re-pair landing on an empty thread could briefly show the prior discussion's
  `cwd`. Gated in the common case by `isEmpty`, not observed. A future ticket may clear it beside
  `sessionStore.clear()` on unpair.
- **Type generalization for select-and-load.** The store holds `ConversationCreatedPayload` (the
  create-reply shape); opening an existing list row eventually yields a `ConversationSummary` (different
  shape) and the store's held type will need to generalize or gain an adapter then. Out of scope here.
