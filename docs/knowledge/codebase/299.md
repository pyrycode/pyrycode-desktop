# #299 — Outbound wire: `dequeue_message` envelope type + frame builder

Wire+builder base slice, split from [#295](https://github.com/pyrycode/pyrycode-desktop/issues/295)
along the #235/#236 seam (see [#145 split record](codebase/145.md) in memory — #295 was re-split
after tripping the ≥5-file gate). Shipped as PR
[#302](https://github.com/pyrycode/pyrycode-desktop/pull/302), spec committed `81935d6`, code
`5241074`. Security-sensitive (constructs an outbound frame on the internet-exposed relay path);
size S; a near-exact structural clone of `requestSnapshotEnvelope.ts`, doubling the #235 precedent
for a single-builder (not answer/cancel-pair) outbound slice. **No consumer** in this slice — blocks
[#300](https://github.com/pyrycode/pyrycode-desktop/issues/300) (the `daemonConnection` method + IPC
command that will call this builder).

## Summary

Adds the outbound (client → daemon) `dequeue_message` control frame that removes one queued message
from a conversation's backlog before it runs — driving the daemon's `msgqueue.Remove`. Two production
files:

- `src/shared/wire/types.ts` — `'dequeue_message'` joins `EnvelopeType`, placed immediately after
  `'queue_state'` so the outbound counterpart sits beside its inbound sibling in the same Queue
  feature family (the modal frames' inbound-then-outbound grouping precedent). A new
  `DequeueMessagePayload{ conversation_id: string, queued_msg_id: number }` interface lands right
  after `QueueStatePayload`. `queued_msg_id` is **symmetric with the inbound
  `QueuedItem.queued_msg_id`** (#292) — a plain JSON number, never a string; the builder does not
  police its range (an out-of-range id is a daemon-side no-op, the same "narrows but does not police"
  posture #292 established). The frame is **ungated**: no nonce, no answer token (contrast
  `ModalAnswerPayload.answer_token`) — any paired client may drop a queued message it enqueued itself
  (project security model, daemon SSOT pyrycode #720).
- `src/main/transport/dequeueMessageEnvelope.ts` (new) — `buildDequeueMessage`, a byte-for-byte
  structural twin of `buildRequestSnapshot`: `DequeueMessageInput{ id, ts, payload }` →
  `Envelope{ id, type: 'dequeue_message', ts, payload }` → `encodeEnvelope`. Pure, synchronous,
  caller-injects `id`/`ts`/the already-validated payload — no clock/counter read, no side effects, no
  token minting. MAY throw `WireEncodeError` over `MAX_PLAINTEXT_BYTES`; the eventual caller (#300)
  catches and drops, the same posture as every sibling builder. MAIN-PROCESS ONLY (imports
  `./codec`, which uses Node `Buffer`) — never re-exported through a renderer barrel; the sibling
  builders (`requestSnapshotEnvelope`, `sendMessageEnvelope`) are relative-import-only and never
  barrelled, and this one follows the same shape.

Two test files: `dequeueMessageEnvelope.test.ts` (new) round-trips through the real `decodeEnvelope`
(happy path asserting `type`/`id`/`ts`/payload equality, a `typeof queued_msg_id === 'number'`
assertion, and the over-cap `WireEncodeError` case), and `types.test.ts` gains a
`describe('dequeue-message wire vocabulary (#299)')` block mirroring the `queue_state` block: a
compile-time `EnvelopeType` membership assertion, an `Object.keys` wire-order pin
(`['conversation_id', 'queued_msg_id']`), and a `@ts-expect-error` pin rejecting a
`queued_msg_id: '7'` string literal.

No `daemonConnection` method, no IPC command, no renderer UI — explicit non-goals per the AC, deferred
to #300. `npm test` (1371 passed, 3 pre-existing skips), `npm run typecheck`, `npm run build` all
green. Fan-out check: zero `EnvelopeType` consumer cascade — no production code does an exhaustive
`switch` over `EnvelopeType` (the three exhaustive switches in the tree all discriminate
`DaemonEvent`), so the new union member needed no companion `assertNever` fix-up anywhere, and no
`DaemonEvent` arm exists to force one either (outbound-only, no decode path).

## Patterns established

- **A single-builder outbound slice is the same shape as #235's answer/cancel *pair*, just with one
  function instead of two.** #235 established "two builders share one file when they're two halves of
  one concern"; #299 confirms the inverse holds too — a lone outbound concern (*drop this queued
  entry*) gets its own lone file, still cloned from `requestSnapshotEnvelope.ts`'s
  `Input{id,ts,payload}` → pure `build*` → `encodeEnvelope` shape. The touchpoint floor for a pure
  outbound builder stays at exactly two production files (`types.ts` + one builder file) regardless
  of how many frame variants the concern has.
- **An outbound field's "policed or not" posture is set by its inbound twin, not re-derived.**
  `queued_msg_id`'s "type-checked, range-unpoliced" contract was decided once, on the inbound decode
  (#292's `requireNumber`, no extra integer/range validation — the SSOT's job, not desktop's). This
  outbound slice doesn't re-litigate that: it reuses the same number type and the same non-policing
  stance for the field it selects by, rather than adding a bounds check "to be safe" on the way out.

## Lessons learned

None beyond the above — the ticket built exactly to spec, mirroring `requestSnapshotEnvelope.ts` with
no surprises. The spec's own file-count estimate (2 production files) held exactly.
