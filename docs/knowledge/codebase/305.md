# #305 — `interrupt` wire type + frame builder

Wire+builder base slice, split from [#146](https://github.com/pyrycode/pyrycode-desktop/issues/146)
(interrupt-running-turn), slice 1 of 3 (memory: `ticket-146-interrupt-turn-split`). Shipped as spec
commit `ae94d87`, code commit `7306661`. Security-sensitive (transport-layer wire+builder for a
control frame on the internet-exposed Noise surface, labelled consistent with its twin #299), size
XS; a structural clone of `requestDebugBundleEnvelope.ts` / `listConversationsEnvelope.ts` — **not**
`dequeueMessageEnvelope.ts` as the ticket body's "mirroring `buildDequeueMessage`" phrasing suggested,
since `interrupt` is bare (no payload) where `dequeue_message` carries one. **No consumer** in this
slice — blocks [#306](https://github.com/pyrycode/pyrycode-desktop/issues/306) (the `interrupt`
`daemonConnection` method + IPC command), which in turn blocks
[#307](https://github.com/pyrycode/pyrycode-desktop/issues/307) (the composer stop-state render).

## Summary

Adds the outbound (client → daemon) `interrupt` control frame — the desktop equivalent of pressing
Esc at the local terminal. Two production files:

- `src/shared/wire/types.ts` — `'interrupt'` joins `EnvelopeType`, placed immediately after
  `'dequeue_message'`, documented inline (no `InterruptPayload` interface exists to host the doc,
  since AC5 forbids one) as a v2-only, payload-free phone→binary control frame: maps to a single
  claude Esc, carries no `conversation_id`/nonce/answer token/payload, daemon-gated on the
  `interactive` capability (already advertised, #179), fire-and-forget (no reply). SSOT: daemon
  pyrycode #707.
- `src/main/transport/interruptEnvelope.ts` (new) — `buildInterrupt`, an `InterruptInput{id,ts}` →
  `Envelope{id,type:'interrupt',ts,payload:{}}` → `encodeEnvelope` pure builder. **No payload arg** —
  this is the first bare-frame builder added since `request_debug_bundle` / `list_conversations`
  shipped, and it follows their precedent exactly rather than the payload-carrying
  `dequeueMessageEnvelope.ts` twin the ticket body named. `payload: {}` is emitted
  present-and-empty, never omitted or `null`: `decodeEnvelope` throws on an absent `payload`
  (`codec.ts:133`), and `Envelope.payload` is required by the wire type (relaxing it to optional
  would be a drift touching every consumer). MAIN-PROCESS ONLY (imports `./codec`, Node `Buffer`) —
  never re-exported through a renderer barrel.

One test file: `interruptEnvelope.test.ts` round-trips through the real `decodeEnvelope`, asserting
`type`/`id`/`ts` and `payload` deep-equals `{}` — the `payload` assertion is load-bearing, proving
the codec did not throw on an absent payload. **No over-cap `WireEncodeError` test** — a fixed-shape
~60-byte empty-payload envelope can never exceed `MAX_PLAINTEXT_BYTES`, so the case would be vacuous;
the bare-frame twins (`requestDebugBundleEnvelope.test.ts`, `listConversationsEnvelope.test.ts`) omit
it for the same reason, and this follows them, not `dequeueMessageEnvelope.test.ts` (which tests
over-cap because it can inflate `conversation_id`). **No `types.test.ts` change** — the existing bare
control frames (`request_debug_bundle`, `list_conversations`) have no per-family `describe(...)`
block there; their `EnvelopeType` membership is exercised only via the builder round-trip, and
`interrupt` follows that precedent (adding one here would manufacture a test the bare-frame twins
deliberately don't carry).

No `daemonConnection` method, no IPC command, no renderer UI — explicit non-goals per the AC,
deferred to #306. Zero `EnvelopeType` consumer cascade — no production code does an exhaustive
`switch` over `EnvelopeType` (only `DaemonEvent` has exhaustive switches), and `interrupt` is
outbound-only (no `DaemonEvent` arm, no `assertNever` fix-up anywhere).

## Patterns established

- **A bare frame's structural twin is chosen by payload shape, not by feature-family proximity.**
  The ticket body pointed at `buildDequeueMessage` as the mirror (same #146 "stop a running turn"
  feature area as the eventual command/IPC slice), but the architect spec corrected this at design
  time: `dequeue_message` carries a real payload, so its `Input{id,ts,payload}` shape doesn't fit a
  payload-free frame. The correct twins were the two already-shipped bare builders
  (`requestDebugBundleEnvelope.ts`, `listConversationsEnvelope.ts`), confirming the module now has
  two established builder shapes — payload-carrying (`Input{id,ts,payload}`) and bare
  (`Input{id,ts}`, `payload:{}` inlined) — and a new outbound frame's shape, not its feature area,
  decides which one it clones.
- **`payload: {}` present-and-empty is now a three-time-repeated bare-frame convention**, not a
  one-off: `request_debug_bundle`, `list_conversations`, and now `interrupt` all emit it for the same
  reason (`decodeEnvelope` throws on an absent payload, `codec.ts:133`) and all document the reasoning
  inline rather than relying on a shared payload type (there is none to host it, by design — AC5).

## Lessons learned

- **A ticket body's "mirror X" pointer can be wrong when the target has evolved past the mirror's
  shape.** The ticket said "mirroring `buildDequeueMessage`"; the architect spec caught that
  `dequeue_message` isn't structurally bare and re-pointed to the two payload-free builders instead.
  Worth checking a named "mirror" ticket's actual shape (payload-carrying vs. bare) before cloning it,
  rather than trusting the ticket prose over the code.
