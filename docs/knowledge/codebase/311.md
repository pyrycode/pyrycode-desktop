**Scope:** one file, `src/main/transport/fakeRoutingRelay.test.ts` (+8/−2). No production change —

Fixes a flaky test in the [Fake routing relay](../features/fake-routing-relay.md) suite (#251):
`startFakeRoutingRelay — server → client unwrap + close_code (AC3)` →
`closes a client with no prior frame on a close-only envelope` failed intermittently with
`Error: Parse Error: Expected HTTP/, RTSP/ or ICE/`, but **only** under full `npm test`
parallel-worker load — 10/10 clean single-file on both `main`@`24c713c` and the branch (PR #310)
that surfaced it. QA had already established `fakeRoutingRelay.ts`/`.test.ts` were byte-identical
between `main` and `feature/278`, confirming PR #310 (renderer-only) merely surfaced a pre-existing
flake by running the full suite, not introduced it.

## What shipped

`isTransientDialError` in `fakeRoutingRelay.test.ts` — the file-local classifier feeding the test's
own `connect()` retry ladder (added in [#104](104.md) for `fakeRelayForwarder.test.ts`, carried into
this file at #251) — gained a fourth clause:

```ts
function isTransientDialError(err: Error): boolean {
  const code = (err as NodeJS.ErrnoException).code
  return (
    code === 'ECONNRESET' ||
    code === 'ECONNREFUSED' ||
    /socket hang up/i.test(err.message) ||
    /Parse Error/i.test(err.message) // pre-open HTTP-upgrade parse race under full-suite CPU load
  )
}
```

The match is on the llhttp `Parse Error:` prefix (stable across Node versions), not the
version-specific reason text (`Expected HTTP/, RTSP/ or ICE/`) — mirroring the existing
`/socket hang up/i` family-style idiom rather than an exact-string pin.

## Design in one paragraph

The ticket explicitly warned against defaulting to the cheaper retry edit, citing a same-sounding
Go `pyrycode` fix (`WaitBinary`, QMD specs `789`/`371`/`290`) that used a **synchronization barrier**
instead. The architect confirmed root cause before choosing a seam and found the two are
different-layer problems: the Go case is a dial that **succeeds** but reads stale *server-side
application state* (`s.binaries[id]` not yet populated post-Accept) — a barrier is correct because
there's registered state to wait for. This case is a dial that **fails** — the HTTP-upgrade response
itself is malformed under CPU starvation, so the WS never reaches `'open'` — and there is nothing to
wait for; only a fresh re-dial clears it. The desktop already ships the Go tickets' barrier
equivalent (`whenReady()`, gating on `serverLeg !== null && clients.size > 0`) one layer up in the
choreography; this flake sits one layer *below* that, at dial establishment, where retry is the only
remedy that operates. `onDialError` is `ws.off()`-detached on `'open'` (line ~49), so the classifier
is structurally consulted **only pre-open** — a genuine post-open close-code/teardown regression
still fails the test unchanged, and a persistent dial failure still exhausts the bounded 5-attempt
ladder and `reject`s. `Parse Error` is a legitimate fourth member of the same pre-open
dial-establishment family the ladder already re-dials past, not a retry list widened to paper over a
logic bug.

## Patterns established

- **Confirm root cause before picking retry vs. barrier — same-sounding flakes across projects can
  be different-layer bugs.** "Dial succeeds, stale app state" (barrier) and "dial fails pre-open"
  (retry) look alike from the symptom ("flaky under full-suite load only") but demand opposite fixes;
  the tell is whether the connection ever reaches the state the barrier would be waiting to read.
- **A file-local dial-retry classifier is the systemic seam for pre-open transients in this test
  harness — extend it, don't build a parallel mechanism.** This is the second ticket (after #104) to
  add a clause to an `isTransientDialError` predicate rather than touch retry mechanics (attempt
  count, backoff, `ws.terminate()`-before-redial); the classifier is now the established single
  point of change for "a new pre-open dial failure mode showed up under load."
- **Evidence-based scope on a flake fix: match the one family observed, not the ones that might
  exist.** The spec declined to add speculative `HPE_*` llhttp error-code matches beyond the observed
  `Parse Error` prefix — consistent with [#303](303.md)'s "widen prefix ≠ fix" caution and the
  pipeline-wide evidence-based-fix-selection principle.

## Testing

- `npm test` (full suite) run 10× back-to-back: 10/10 clean, zero `Parse Error` / AC3 failures (per
  the spec's guidance — the flake never reproduces single-file, so verification is repeated
  full-suite runs, not a new isolated unit test).
- `npm run build` (typecheck + electron-vite build): pass.
- Teeth check: `git diff` touches `isTransientDialError` (+ its doc comment) only;
  `expect(await closed).toBe(4408)` and `expect(gotFrame).toBe(false)` (the close-only-envelope
  test's assertions) are byte-identical; `fakeRoutingRelay.ts` and `fakeRelayForwarder.test.ts` are
  absent from the diff.
- Security re-review (architect self-review + code-review goggles): PASS. The added clause is a
  boolean predicate over a Node/llhttp-generated dial-error string, never relay-origin frame bytes or
  the pairing token; the retry it feeds stays bounded (5 attempts) and leak-free
  (`ws.terminate()` before each re-dial); no logging added. `fakeRoutingRelay.ts`'s content-blindness
  contract is untouched by construction (production file not in the diff).
