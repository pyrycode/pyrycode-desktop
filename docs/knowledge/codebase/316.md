# #316 — Surface the screen-snapshot rendered `text` via a `screenSnapshotReceived` event

Data-path slice of the live-screen-view vertical, split from #147, sibling of the stall transport
(#315) — same DaemonEvent-arm/bridges-atomic shape, opposite security posture. Shipped as PR #321
(`1f739cb`), code-review **PASS** (no MUST/SHOULD-FIX, one informational NIT on the `ts` field name,
pre-adjudicated in the spec's Open Questions — no action taken). Security-sensitive: this is a
**deliberate widening** of what daemon content crosses IPC, reversing the exact `text`-drop [#180's
security review](180.md) defended. Ships dormant; the display slice #318 (already blocked-by this
ticket) is the first consumer.

## Summary

`request_snapshot` → `screen_snapshot` was already fully wired by [#180](180.md): the outbound
request, the fail-closed decode (`parseScreenSnapshotPayload`, decoding all eight
`ScreenSnapshotPayload` fields), and the run-config `snapshotReceived` event all existed unchanged.
`text` — the rendered daemon screen — was decoded (so a malformed frame still fails closed) but
**dropped** at the `case 'snapshot'` emit seam, since no consumer needed it yet. This ticket adds a
**second**, dedicated `screenSnapshotReceived` emit at that same seam, carrying only `text` + `ts`:

- **`DaemonEvent` arm** (`src/shared/ipc/events.ts`) — `{ type: 'screenSnapshotReceived'; text:
  string; ts: string }`, inserted immediately after `snapshotReceived`. Doc-commented like
  `assistantDelta` (the other arm that carries real content deliberately): the boundary defended
  upstream is the fail-closed decode, not this internal channel. Carries the standard untrusted-text
  warning for #318 — render as plain text, never `innerHTML`/`dangerouslySetInnerHTML`.
- **Second emit** (`daemonConnection.ts` `case 'snapshot'`) — the existing `snapshotReceived` emit
  (5 fields) is byte-for-byte unchanged; a second `emitDaemonEvent` call follows it, a **fresh
  named-field literal** (`{ text: inbound.snapshot.text, ts: inbound.snapshot.ts }`), never a spread
  of `inbound.snapshot` — bounding the widening to exactly two fields so a future decoder field can't
  smuggle onto this arm. No new log call: the content-free `screen_snapshot` diagnostic in
  `inboundMessage.ts` is untouched, so `text` never reaches a sink.
- **Three exhaustive bridge no-ops** — `daemonEventBridge.ts`, `timelineBridge.ts`, `modalBridge.ts`
  each add `case 'screenSnapshotReceived': return null`, compile-forced by their `assertNever`
  defaults — the fifth ticket (after #241/#229/#254/#315) to force a case in all three at once.

**No wire-type change and no new decode** — both landed in #180; this slice is purely the second emit
+ the arm + the three no-ops. `npm test` (1428 pass, 3 pre-existing skips), `npm run typecheck`,
`npm run build` all green. Test-first: RED (2 failing on the missing emit, 173 passing) before adding
the emit, then GREEN. 10 files touched (5 production, 5 test), 0 new files.

## Patterns established

- **A DaemonEvent-arm ticket can be a deliberate widening, not just a minimisation.** Every prior
  arm added since #180 either drops fields (`snapshotReceived`, `sessionTransition`) or carries
  content that was always meant to cross (`assistantDelta`, `toolUse`). #316 is the first ticket
  whose entire point is to reverse an earlier ticket's minimisation decision once a real consumer
  exists — proof that content-minimisation at #180 was a "don't cross what you don't need yet"
  policy, not a permanent security boundary. The correct test for "does this field cross IPC" is
  "does a consumer need it," re-evaluated per ticket, not "was it excluded once."
- **A fresh named-field literal is the deterministic net for a widening, same as for a
  minimisation.** `{ text: inbound.snapshot.text, ts: inbound.snapshot.ts }` bounds the new arm to
  exactly two fields the same way the unchanged `snapshotReceived` literal bounds itself to five —
  the widening doesn't relax that discipline, it just widens which two fields the literal names.
- **One decoded wire frame can feed two independent `DaemonEvent` emits at the same `case` seam.**
  `case 'snapshot'` now fires `snapshotReceived` (run-config) and `screenSnapshotReceived` (rendered
  text) from a single `inbound.snapshot`, each a separate fresh literal, each read by separate
  renderer consumers (#187/#188 vs. #318). Confirms the double-emit shape sibling `case`s could reuse
  if a future frame ever needs to split across two consumers again.

## Lessons learned

None beyond the patterns above — this was a mechanical mirror of #315's bridges-atomic shape with the
emit content reversed; code review found no issues requiring rework (from the PR body and the
code-review comment).

## Open questions carried forward

- **`ts` naming.** Kept as the wire name `ts` (not renamed to `occurredAt` as `sessionTransition` did
  for `occurred_at`) — the AC names `ts`, and the sibling `snapshotReceived` arm on the same frame
  already keeps wire names (`used_tokens`/`window_tokens`). Code review flagged this as a NIT, no
  action taken; noted that #318 should stay consistent with `ts` if it needs the timestamp.
- **Inner-switch exhaustiveness.** `daemonConnection.ts`'s `switch (inbound.kind)` still has no
  `default: assertNever` — unaffected by this ticket (no new `inbound.kind` was added, only a second
  emit inside the existing `case 'snapshot'`).
