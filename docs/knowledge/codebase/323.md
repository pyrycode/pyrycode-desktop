# #323 — Screen-snapshot store: hold the daemon's latest rendered-screen text in renderer state

Split from [#318](https://github.com/pyrycode/pyrycode-desktop/issues/318) (itself split from
[#147](147.md)); sibling [#324](https://github.com/pyrycode/pyrycode-desktop/issues/324) (action +
display) is blocked on this and is now unblocked. Shipped as PR #325 (`ea8e6b7`), code-review
**PASS**. Not UI-visible, no Figma (N/A — headless leaf, no DOM sink). Size S, as estimated.

## Summary

The transport ([#316](316.md)) already emits `screenSnapshotReceived{text,ts}` on every `screen_
snapshot` reply, but all three exhaustive renderer bridges discarded it as `null` — nothing retained
the value, so a display surface mounted after a snapshot arrived would never see it. This ticket adds
the missing holder: two new files + a one-line `App.tsx` mount, cloned from the `runConfigStore`/
`runConfigSnapshot` pair (#187) with the request half stripped, following the more precise structural
precedent of the reactive-only, App-lifetime holders (`sessionIdStore`/`sessionIdBridge`, #259;
`queueStore`/`queueBridge`, #293).

- **`src/renderer/src/store/screenSnapshotStore.ts`** (new) — `ScreenSnapshotState { snapshot:
  ScreenSnapshot | null }`, `createScreenSnapshotStore` (DI-factory, vanilla `zustand/vanilla`), the
  `screenSnapshotStore` singleton, `useScreenSnapshotStore` hook, `selectScreenSnapshot` selector.
  `setSnapshot` does an unconditional `set({ snapshot })` — whole-value replace, most-recent-wins
  (AC1), holding an empty `text` verbatim rather than dropping it (AC1's empty-text clause).
  `snapshot: null` is the distinct "no screen received yet" state.
- **`src/renderer/src/store/screenSnapshotBridge.ts`** (new) — `translateScreenSnapshot` (pure
  filter, `case 'screenSnapshotReceived': return { text: event.text, ts: event.ts }; default: return
  null`, a fresh named-field literal never a spread — AC3), `subscribeScreenSnapshot` (subscribes via
  injected `onDaemonEvent`, writes on `snapshot !== null` — not truthiness, so an empty-text snapshot
  isn't silently dropped — AC1/AC5), and `ScreenSnapshotData` (`(): null`, one
  `useEffect(() => …, [])` returning the subscription's off-handle as cleanup, no connected-gate).
- **`src/renderer/src/App.tsx`** (modified, +7 lines incl. comment) — mounts `<ScreenSnapshotData />`
  as a fifth sibling headless leaf beside `<ConversationListData />`/`<SessionIdData />`/
  `<RunSettingsWriteData />`/`<QueueData />`. The **only** existing file touched.

`npm test` (1466 pass, 3 pre-existing skips), `npm run typecheck`, `npm run build` all green. Two new
test files (`screenSnapshotStore.test.ts`, `screenSnapshotBridge.test.ts`), cloned from the
`conversationListStore.test.ts`/`conversationListBridge.test.ts` idiom — framework-free, injected
spies, one `renderToStaticMarkup` server-render sanity check for the headless leaf.

## Patterns established

- **A push-only holder with no request half at all is a distinct, smaller shape than the
  request-on-open family.** `runConfigStore`'s `RunConfigData` (#187) pairs a subscribe effect with a
  request effect gated by a `useRef` one-shot flag; this ticket (like `sessionIdStore`/#259 and
  `queueStore`/#293 before it) has only the subscribe effect — no command, no conversation-id-keyed
  request, no connected-edge trigger. The daemon pushes `screenSnapshotReceived` unsolicited off the
  same `case 'snapshot'` seam that also fires the (request-triggered) `snapshotReceived`, so **one
  wire frame feeds one push-only holder and one request/response holder simultaneously** — the two
  holder families aren't mutually exclusive per event source, they're determined by whether *this
  particular* consumer chose to trigger the fetch.
- **`snapshot !== null`, not `if (snapshot)`, is the house idiom for "presence, not content" guards**
  across every push-only holder in this family (`sessionIdBridge`'s `id !== null`, `queueBridge`'s
  equivalent, now `screenSnapshotBridge`'s `snapshot !== null`) — mechanically identical to `if
  (snapshot)` for an object value, but it reads correctly beside an empty-string/empty-object AC and
  keeps the guard's intent legible without re-deriving it from the type.
- **A shipped-dormant selector export is expected, not a smell, for this holder family** — the same
  pattern #259 and #223 (`modalStore`) already established: ship the data path ahead of its consumer,
  accept the "unconsumed until #324" observation as the intended split boundary, not a gap.

## Lessons learned

None beyond what's captured above — this ticket was a close structural clone of two already-reviewed
precedents (#187's shape, #259's reactive-only posture) with a mechanical subtraction (drop the
request half), and shipped with zero code-review findings. No "Lessons learned" section appeared in
the merged PR body.

## Open questions carried forward

- **#324 (next) is the actual consumer** — it reads `useScreenSnapshotStore(selectScreenSnapshot)`
  to render the live-screen text as plain text (never HTML — the discipline `screenSnapshotReceived`
  documents at the event boundary) and owns whatever user action or timing triggers the display.
  Until #324 lands, `screenSnapshotStore` is populated live (the App-level subscriber is
  unconditional) but read by nothing.
- **No reset boundary exists yet.** Unlike `runConfigStore`, which resets implicitly by requesting
  fresh on each sheet-open, this store has no analogous close/reopen edge — it holds the last-known
  screen for the app's lifetime. Revisit only if #324 surfaces a staleness concern.
