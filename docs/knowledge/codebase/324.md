# #324 — Screen-snapshot action & display: request the daemon's screen and show it

The view half of #318's store/render split, sibling to [#323](323.md) (store, merged PR#325). Shipped
as PR #327 (`a6fb858`), code-review **PASS** (one NIT, architect-owned spec-file cosmetic issue,
non-gating). Size S, as estimated — not split, per the ticket's sizing note. Figma N/A (no
daemon-screen surface in the mobile file).

## Summary

Closes the screen-snapshot vertical: #180 wired the `requestSnapshot`/`screen_snapshot` round trip,
#316 surfaced the reply's `text`/`ts` as `screenSnapshotReceived`, #323 held the latest value in
`screenSnapshotStore`. This ticket adds the two pieces nothing else supplied — a user action that
requests a fresh snapshot, and a display that shows the held one:

- **`src/renderer/src/screens/conversation/requestScreenSnapshot.ts`** (new) —
  `requestScreenSnapshot({ sendCommand })`: fires the inline `{ type: 'requestSnapshot', payload: {
  conversation_id: MILESTONE_CONVERSATION_ID } }` literal (the `requestRunConfigSnapshot` precedent,
  no new command/IPC), wrapped in the `sendInterrupt` guarded-send posture (try/catch +
  `console.error`, never rethrow, no local dispatch, `void` return).
- **`ScreenSnapshotView` + `ScreenSnapshotControl`** (`ConversationScreen.tsx`) — the `InterruptButton`/
  `InterruptControl` triad, but bundling the request button and the display region into one exported
  pure view (action + display are one surface per the ticket's sizing note). `ScreenSnapshotControl`
  reads `useSessionStore(selectStatus)` and `useScreenSnapshotStore(selectScreenSnapshot)`, derives
  `canRequest` from `composerAvailability(status).canSend` (the same gate the composer's send button
  uses), and binds `onRequest` to `requestScreenSnapshot({ sendCommand: window.pyry.sendCommand })` —
  dereferenced only inside the click closure. Mounted between `<StatusRow/>` and `<InterruptControl/>`.
- **Render contract** — always renders the request button (`disabled={!canRequest}`); the display
  region discriminates on `snapshot === null` (placeholder `<p>`, no `<pre>`) vs. `snapshot !== null`
  (`<pre className="screen-snapshot__screen">{snapshot.text}</pre>`, present even when `text === ''`)
  — the null-vs-blank distinction AC3 requires falls out for free from that one conditional.
- **`conversation.css`** — four new rules (`.screen-snapshot`, `__request`, `__screen`, `__empty`),
  all token-only; the `<pre>` reuses `.bubble--daemon`'s fill/radius, `max-height: 240px` +
  `overflow: auto` so a large screen dump scrolls internally instead of pushing the composer
  off-screen.

`npm test` (1479 pass, 3 pre-existing skips), `npm run build` both clean. Two new test files/additions:
`requestScreenSnapshot.test.ts` (exactly-one-command + bridge-failure-swallow) and a 6-branch
`ScreenSnapshotView` describe in `ConversationScreen.test.tsx` (null/populated/blank/HTML-escape/
enabled/disabled) plus a disconnected+null-snapshot container smoke.

## Patterns established

- **"Guarded action helper + pure bundled view + thin container" is the closed shape for a
  request-and-show affordance reading an existing store.** No new pattern here — this is the third
  instance (#307 `sendInterrupt`+`InterruptControl`, #166 `runUnpair`+`UnpairControl`) of the same
  triad, confirming it as the house idiom rather than a one-off.
- **Action + display bundled into one exported view, not two, when neither half is independently
  observable.** Unlike `ThinkingIndicator`/`StallIndicator` (props-in booleans, no action) or
  `InterruptButton` (action, no display of its own), `ScreenSnapshotView` takes both `snapshot` and
  `onRequest` because a request button with nothing to render is dead UI and a display with no
  trigger only shows unsolicited pushes — the ticket's sizing note called this out explicitly and the
  implementation followed it exactly.
- **The null-vs-empty-string distinction is a rendering fork, not a separate flag.** Discriminating
  on `snapshot === null` (not `if (snapshot)`) at the view layer is the same "presence, not content"
  idiom #323 established at the store layer (`snapshot !== null`, not truthiness) — carried through
  one layer further, into JSX branching, with no additional boolean threaded down.

## Lessons learned

From the merged PR body: the blank-screen-vs-null distinction (AC3) falls out for free from
discriminating on `snapshot === null` at the view — `null` → placeholder `<p>` (no `<pre>`),
`{ text: '', ts }` → an empty `<pre>` — structurally distinct in the markup, so the two states are
told apart without a separate flag. (No other lessons flagged; code review found no correctness
issues.)

## Open questions carried forward

- **Placement and always-visible posture are provisional, not load-bearing.** The spec's own Open
  Questions flagged that a toggle/sheet host is acceptable if the always-visible bounded panel proves
  visually wrong in practice — not required by the ACs, and not revisited here since nothing surfaced
  a problem.
- **Static request-label** (`'Show daemon screen'`) covers both the first request and a later
  re-request/refresh; a snapshot-aware label swap remains optional polish, not built.
- **No Figma design exists** for this surface (documented gap, same as #279/#294/#296/#317) — a
  desktop-design-pass follow-up if a bespoke visual is wanted.
- **Spec-file cosmetic NIT** (code review): `docs/specs/architecture/324-screen-snapshot-action-display.md`
  has stray tool-artifact lines at its end (leaked from the architect's authoring turn) — cosmetic,
  outside this PR, not fixed here.
