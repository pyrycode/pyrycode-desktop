# #329 — Renderer relay-link status store + bridge

Slice 2 of 3 toward the two-dot connection-status indicator, split from [#149](149.md):
[#328](328.md) (relay-leg transport) → this (renderer relay-link store + bridge) →
[#330](https://github.com/pyrycode/pyrycode-desktop/issues/330) (two-dot render). Shipped as
PR #335, code-review **PASS**, no findings. Size S, not split (3 production files: 2 new stores +
one `App.tsx` mount line).

## Summary

[#328](328.md) (merged) landed the `relayLinkChanged` `DaemonEvent` arm — a content-free
`RelayLinkStatus` (`'connected' | 'offline' | 'daemon-absent'`) — but shipped it dormant: all three
exhaustive bridges (`daemonEventBridge` / `timelineBridge` / `modalBridge`) just no-op it. This
ticket adds its **first real consumer**: a dedicated `relayLinkStore` + a headless `RelayLinkData`
bridge leaf, mounted at the App root alongside the other reactive-only leaves — the same posture
the conversation-list arm got in #208 (its own store, not a `sessionStore` facet).

A near-verbatim clone of the `sessionIdStore`/`sessionIdBridge` pair (not `conversationListStore`,
which has a request half + connected-gate this arm doesn't need — the daemon pushes
`relayLinkChanged` unsolicited):

- **`relayLinkStore.ts`** — `RelayLinkState { status: RelayLinkStatus | null }`, DI-factory
  (`createRelayLinkStore`) → app singleton (`relayLinkStore`) → React binding (`useRelayLinkStore`)
  → the only read surface (`selectRelayLinkStatus`). One setter, `setRelayLinkStatus`, whole-value
  replace — no reducer, since the arm always carries the final category (nothing to fold or dedup).
  `status: null` is the distinct initial not-connected sentinel (AC1) — the same "not yet arrived"
  form every sibling store (`sessionIdStore`, `conversationListStore`, `queueStore`,
  `runConfigStore`, `screenSnapshotStore`) uses, not a fabricated 4th wire category.
- **`relayLinkBridge.ts`** — `translateRelayLink(event): RelayLinkStatus | null` (a `switch` with
  `default: null`, not `assertNever` — a 4th independent single-arm subscriber, the
  `sessionIdBridge`/`queueBridge` posture); `subscribeRelayLink(onDaemonEvent, setter)` — one
  listener, `status !== null` guard (documents "sentinel is `null`, not falsiness," though all three
  categories are truthy today); `RelayLinkData(): null` — the headless leaf, one subscribe effect,
  `window.pyry` dereferenced only inside the effect (server-render-to-`''` invariant). Reactive-only:
  no request effect, no connected-gate, no `useState`/`useRef`/`useSessionStore`.
- **`App.tsx`** — one import + `<RelayLinkData />` dropped into the existing headless-leaf
  fragment next to `<SessionIdData />` / `<QueueData />` / `<ScreenSnapshotData />`.

Ships **dormant** — nothing reads `relayLinkStore` yet; #330 is its first reader, combining this
relay leg with the daemon leg already in `sessionStore`'s `ConnectionStatus`.

`npm test` (1509 pass, 3 pre-existing skips), `npm run build` (typecheck + electron-vite) both
clean. New tests: `relayLinkStore.test.ts` (initial `null`, each category round-trip, last-write-
wins, DI isolation, injected init, setter reference stability) and `relayLinkBridge.test.ts` (filter
table over all three categories + a sample of unrelated events, single-subscribe, last-write-wins,
ignore-unrelated, off-handle cleanup, the AC1→AC5 null→each-category seam wired to a real store, and
the `renderToStaticMarkup` server-render-to-`''` sanity check).

## Patterns established

- **A dormant content-free arm's first consumer is a new dedicated store, not a fold into an
  existing multi-arm one.** `sessionStore`'s reducer models six session-lifecycle arms with
  message-dedup logic; this arm carries exactly one mutation ("record the latest category"), so a
  reducer here would be ceremony. Confirms the #208 precedent generalizes: a single-category push
  arm gets its own `createStore`/selector/singleton pair, borrowing only that scaffolding — not the
  reducer shape — from `sessionStore`.
- **Reactive-only vs. request-gated is a per-arm choice, not a per-store-family default.** The
  ticket named `conversationListStore` (#208) as the nearest precedent, but the architecture spec
  correctly picked `sessionIdStore`/`queueStore` as the literal template instead, because those two
  are also unsolicited pushes with no request half — `conversationListStore`'s connected-edge
  request trigger doesn't apply here. Match the wire behavior (pushed vs. requested), not the most
  recently shipped sibling.
