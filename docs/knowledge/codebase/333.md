## Patterns established

- **A chrome-only scaffold ticket is one indivisible unit — route + entry + screen — not three
  separately-mergeable pieces.** A route with no screen, or a screen with no route, is dead code; the
  spec called this out explicitly and the shipped diff honors it (all three land in one PR).
- **Adding a nav arm to an already-`current`-independent reducer needs no new transition logic for the
  reverse direction.** `nextPairedRoute`'s `back` arm was written absolute from #140 onward specifically
  so a future arm like `openSettings` wouldn't need a matching new `back` case — this ticket is the
  first to cash that bet in, and it paid off exactly as the original comment predicted.
- **Screen-local desktop-invented affordances (no Figma node) clone the nearest sibling's shape rather
  than inventing a new one.** `SettingsButton` is a structural clone of `NewConversationFab`
  ([#242](242.md)) — same icon-only-button-with-aria-label idiom, same "present in all three list
  states" placement rule, same "corner is a free CSS swap, not a blocker" framing in the spec.

## Lessons learned

- **The spec's suggested test marker collided with an unrelated existing marker.** The architecture
  spec proposed using the `"Connection"` section-heading text to discriminate the `settings` view in
  `PairedShell.test.tsx`. But the `thread` view already renders `aria-label="Connection status"` (the
  two-dot indicator, [#330](330.md)) — so `"Connection"` as a substring match would have false-matched
  both views. The developer caught this before writing the test and used the genuinely-unique root
  marker `aria-label="Settings screen"` instead. Worth generalizing: when a spec proposes a text-content
  marker for a `renderToStaticMarkup` discrimination test, grep the sibling views' existing
  `aria-label`s for substring collisions before trusting the spec's suggestion — the spec author reasons
  about one view at a time and can miss a cross-view collision like this one.

## Carried forward / deferred

- **The Connection section ships empty.** [#334](../codebase/334.md) mounts the store-bound Server row
  (host name, two-dot Relay+Server status) into `.settings__section-body`.
- **`<ServerInfoData />` ([#340](340.md)) is still not mounted anywhere.** #340 deferred the mount to
  "#333 or #334, whichever owns the paired-only Settings tree." This ticket shipped the tree but not the
  mount — `SettingsScreen` stays a pure, store-free view by design (the spec's explicit contract: "no
  store read, no effects, no `window.pyry`"). The mount now falls to #334, which needs the store's data
  to render the Server row anyway.
- **No stack-aware back.** `settings → back` is the same absolute `list` landing every other route's
  `back` uses; a future sub-screen under Settings (the [#152](152.md) "pair another server" flow is the
  first plausible candidate) is what would finally need `current` to matter in `nextPairedRoute`.
