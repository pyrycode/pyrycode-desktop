# #336 — fakeDaemon.test.ts: bounded transient re-dial for the full-suite WS 404 dial race

**Shipped:** 2026-07-13 · **Size:** XS · **Labels:** `bug`, `security-sensitive` (the module's
Noise-session / no-nonce-reuse invariant was re-audited, not just the flake).
**Scope:** one file, `src/main/transport/fakeDaemon.test.ts` (+86/−25). No production change —
`relayConnection.ts` and `fakeRelayForwarder.ts` untouched.
**Spec:** `docs/specs/architecture/336-fakedaemon-404-dialrace.md` · **PR:**
[#337](https://github.com/pyrycode/pyrycode-desktop/pull/337). Not a split.

Fixes a flaky suite in [Fake daemon](../features/fake-daemon.md) (#91): `fakeDaemon.test.ts`
intermittently false-reds **only** under full-suite (`npm test`) worker-pool concurrency with
`Error: Unexpected server response: 404` — never single-file (5/5 clean on
`vitest run src/main/transport/fakeDaemon.test.ts`). Confirmed pre-existing and independent of
#329/PR #335 (a 100% renderer-only diff): reproduces on the pre-#329 merge-base under the same
full-suite conditions, landing on a different sub-test each run.

This is the same **family** as [#311](311.md)/PR #312 (a `fakeRoutingRelay` dial-race) and
[#104](104.md) (the originating `fakeRelayForwarder` dial-race) — a **distinct symptom** (`404`
upgrade response, vs. #311's `Parse Error`) at a **distinct location**, and — unlike those two —
this file had **no** pre-existing `connect()`/`isTransientDialError` ladder to extend; the ticket's
issue body corrected an earlier assumption that one existed. The seam was introduced here, lifted
from the siblings.

## What shipped

Two client dial sites in the suite hide two different shapes of the same pre-`connected` dial race,
because only one of them dials through code that has an `unexpected-response` handler:

- **Site A — the raw `new WebSocket` dial** (`fail-closes a non-InnerFrameV2 frame` test). No
  `createRelayConnection` in the loop, so a 404 upgrade escapes as a raw `Error: Unexpected server
  response: 404` throw. Fixed by lifting `connect(url, attemptsLeft = 5)` + `isTransientDialError`
  verbatim from `fakeRelayForwarder.test.ts` (#104's ladder), with a new `404` clause:
  `/Unexpected server response: 404/i.test(err.message)`. The inline
  `new WebSocket(...)` + open/error promise is replaced by `await connect(...)`; everything
  downstream (`raw.send('{not json')` → `frame-decode-failed`, zero-console assertion) is untouched.
- **Site B — `createRelayConnection` inside `driveClient`** (the 5 handshake/round-trip/rekey
  tests). Production's `unexpected-response` listener
  ([`relayConnection.ts:203-235`](../features/relay-connection.md)) converts a 404 into a **silent**
  `closed{1006,'connect-error'}` `RelayEvent` before any `connected` — never a raw throw. So the
  re-dial trigger here is that `closed` event, not a string match: a `connectedOnce` flag + a
  5-attempt budget gate a `closed`-before-`connected` re-dial (20 ms backoff,
  `activeRelay = makeRelay()`). `sendFrame` routes through the mutable `activeRelay`.

`npm run build` clean; single-file 8/8; **12/12 consecutive clean full-suite `npm test` runs**
(anchored on the vitest `Test Files N passed (N)` summary line — a `wasm streaming compile failed`
stderr line is benign noise-c.wasm fallback, not a failure signal).

## Design in one paragraph

The architect ruled out a "stronger accept-readiness contract on `startFakeRelayForwarder`": the
forwarder wires its `'connection'`/upgrade routing in the `WebSocketServer` constructor — synchronous,
and complete *before* `'listening'` fires — so the server is already upgrade-ready the instant a
consumer receives the URL; there is no server-side readiness gap to close, and a server-side gate
can't prevent the *next* dial from stalling under CPU starvation. The race is client-side, at the
TCP/HTTP dial, so the fix belongs at the two client dial sites — mirroring #311's "confirm root
cause before defaulting to the cheaper retry" discipline, except here the cheaper retry **is**
correct because the sibling ladders already prove re-dial converges and the server genuinely has no
gap. The security-load-bearing piece is the Site-B invariant: re-dial fires **only before the first
`connected`**, and the real Noise `initiator` is created once and only `start()`s after a successful
connect, so every re-dial attempt hands a pristine initiator (msg1 never sent) — no half-advanced
handshake is ever re-driven, no `(key, nonce)` pair is ever reused, and no `expect(...)` re-runs. A
naive "retry the whole handshake" would have been a crypto hazard; gating strictly pre-`connected`
avoids it by construction.

## Patterns established

- **A dial-race fix doesn't always have a pre-existing ladder to extend — check whether production
  code between the raw socket and the test already reclassifies the error.** #104 and #311 both
  extended an existing file-local `isTransientDialError`. Here there wasn't one, *and* the two dial
  sites in the same file needed different triggers (a string match at the raw site, a `RelayEvent` at
  the production-primitive site) because `relayConnection.ts`'s `unexpected-response` handler sits
  between the socket and the test at Site B but not Site A. When a "connect-relay" test dials through
  both a raw `ws` and the production connection helper, expect the same root race to need two
  differently-shaped fixes, not one shared string-match clause.
- **Gate a pre-connect retry ladder on a "has the stateful session started" flag, not just attempt
  count, whenever the retried resource is a real crypto/session initiator.** `connectedOnce` (Site B)
  is what turns a bounded re-dial from a nonce-reuse hazard into a safe pattern: it's not enough that
  attempts are bounded — the invariant that matters is that the stateful thing being protected
  (`initiator.start()`) provably fires at most once across every retry path.
- **Evidence-based scope, again:** `isTransientDialError`'s new clause matches only the observed
  `404` string, not a broadened `4\d\d`/`5\d\d` — same discipline as [#311](311.md)'s `Parse Error`-only
  clause and [#303](303.md)'s "widen the tolerance ≠ fix the race."

## Testing

- `npm test` (full suite) run 12× back-to-back: 12/12 clean, zero `404`/dial-race failures.
- `npm run build` (typecheck + electron-vite build): pass.
- Teeth check (code review): every `expect(...)` across all 8 `it` blocks is byte-identical —
  handshake-complete + `hello_ack` field checks, sealed round-trip plaintext equality, the
  multi-frame streaming order check, both rekey resume checks, the "no client error / daemon settled
  ok" checks, the zero-console-output security assertion (both security tests), and the fail-closed
  non-InnerFrameV2 `frame-decode-failed` assertion. `relayConnection.ts` and `fakeRelayForwarder.ts`
  are absent from the diff.
- Security re-review (architect self-review + code review): PASS. No trust-boundary, secret, or
  logging change; the re-dial reuses the same dummy `X-Pyrycode-Token`; the pristine-initiator
  invariant means the retry introduces no `(key, nonce)` reuse; both zero-console-output assertions
  hold. Code review flagged one NIT (a re-dial `setTimeout` still pending at `afterEach` could fire
  post-teardown and spawn late, self-exhausting dials against the closed forwarder) and explicitly
  endorsed the architect's evidence-based deferral — bounded/benign, not worth guarding pre-emptively.

## Lessons learned

- The same 404 dial-race manifests in two *different* observable shapes depending on the dial site:
  a raw `ws` dial throws `Unexpected server response: 404`, but a dial through
  `createRelayConnection` never throws — its `unexpected-response` listener converts the 404 into a
  silent `closed{1006,'connect-error'}` `RelayEvent`. One root race, two fixes: a string-matched
  re-dial for the raw site, a `RelayEvent`-triggered re-dial for the production-primitive site.
- Gating the Site-B re-dial to *before the first `connected`* is what keeps a retry loop safe around
  a real Noise session: the initiator's `start()` runs exactly once on exactly one transport, so no
  `(key, nonce)` pair is ever reused. A naive "retry the whole handshake" would have been a crypto
  hazard.
