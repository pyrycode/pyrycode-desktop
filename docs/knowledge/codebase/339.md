# #339 — Server-info IPC surface: expose paired serverId + relayUrl across the bridge

**Shipped:** 2026-07-13 · **Size:** S · **Scope:** shared + background + preload + composition root
(`src/shared/ipc/`, `src/main/`, `src/preload/`) · additive, **zero consumer cascade** (`PyryApi`
auto-flows the new preload method; no `index.d.ts` edit) · **no new dependency**.
**Spec:** `docs/specs/architecture/339-server-info-ipc-surface.md` · **PR:** merged as `bb7a833` ·
review: architect self-review PASS (`security-sensitive`). Split child of [#332](332.md) (structural
5-file floor split); blocks [#340](340.md) (renderer store + one-shot loader), which in turn feeds
[#334](334.md) (visible Settings Server row).

Ships the renderer→main IPC surface that exposes the paired server's **non-secret** identity — its
server id and relay URL — from the at-rest [paired-server store](../features/paired-server-store.md),
so a Settings screen can show which server the client is paired with **including while disconnected**.
See the [server-info channel feature doc](../features/server-info-channel.md) for the full contract,
layers, and data flow.

## What shipped

Five files — three new, two additive edits, zero consumer cascade:

- **`src/shared/ipc/serverInfo.ts`** (new, 50 lines) — `SERVER_INFO_CHANNEL = 'pyry:server-info'` +
  the sealed `ServerInfo = { status: 'available'; serverId: string; relayUrl: string } | { status:
  'unavailable' }`. No runtime logic, no request guard (zero-argument invoke), imports nothing from
  `src/main`.
- **`src/main/serverInfoHandler.ts`** (new, 67 lines) — `registerServerInfoHandler(target, deps)`, a
  faithful clone of `pairingStatusHandler.ts`: injected `ServerInfoHandleTarget`
  (`handle`/`removeHandler`), single-registration + exact-teardown, stateless `store.load()`-per-call,
  the available arm built as an **explicit** `{ serverId: record.server, relayUrl: record.relay }`
  literal (never `...record`), a type-blind `catch` that drops the caught object and resolves
  `{ status: 'unavailable' }`. Store dep typed against the **base** `PairedServerStore` (only `load()`
  needed), not `ClearablePairedServerStore`.
- **`src/preload/index.ts`** (+11) — `serverInfo: (): Promise<ServerInfo> =>
  ipcRenderer.invoke(SERVER_INFO_CHANNEL)`, next to `pairingStatus`/`unpair`. No `index.d.ts` edit —
  `PyryApi = typeof api` re-derives `window.pyry.serverInfo`.
- **`src/main/index.ts`** (+11) — `registerServerInfoHandler(ipcMain, { store: pairedServerStore })` +
  `app.on('will-quit', ...)` teardown, registered at the existing pairing-status/unpair slot
  (`L142-153`), reusing the single composition-root `pairedServerStore` — no second store built.
- **`src/main/serverInfoHandler.test.ts`** (new, 161 lines, 7 tests) — registration + exact teardown
  against the exported constant; present record → `available` sourced from `server`/`relay`
  (deep-equal, exact-keys); **exactly-two-crosses / no-secret-crosses** — `JSON.stringify` contains
  `record.server`/`record.relay` but not the seeded `token`/`server_static_pubkey` sentinels (chosen
  as non-overlapping substrings so the assertion can't false-pass by collision), plus an
  `Object.keys` pin on `['relayUrl', 'serverId', 'status']`; `null` → `unavailable`;
  `MalformedPairedServerRecordError` throw → `unavailable`, resolves-never-rejects; a **plain** `Error`
  (not the domain error type) carrying a keychain-path-shaped message → `unavailable` with the path
  absent from the serialized response, proving the handler doesn't branch on error type; log-free
  across all four paths (`console.error`/`log`/`warn` spied, none called).

`npm test`, `npm run typecheck`, and `npm run build` all green.

## Patterns established

- **The third twin in the pairing-status / unpair family, and the first with a non-empty present
  arm.** #79 and #173 are fully value-free; #339 is the first ticket to relax "value-free by
  construction" to "exactly N named non-secret fields, statically enforced by the union type" — the
  present arm can carry data as long as the type has no field for a credential to occupy. This is a
  reusable escalation: a future IPC surface exposing more non-secret record fields can apply the same
  relaxation rather than inventing a new discipline.
- **Explicit field-naming as a second, runtime-level backstop beside the type-level one.** The spec
  and the handler both insist on `{ serverId: record.server, relayUrl: record.relay }` over
  `{ ...record }` even though the return type alone would already reject a stray `token` field at
  compile time (an object literal with excess properties fails structural typing here, since the
  literal is checked directly against `ServerInfo`). The explicit-literal rule is belt-and-suspenders
  against a future refactor that returns a differently-typed intermediate object before the final
  return — a case where TypeScript's excess-property check would not catch a leaked field.
- **Disconnected-safe source as a named design constraint, not just an implementation detail.** The
  spec calls out that `hello_ack.server_id` (live, in `sessionStore`) is a *distinct* value from the
  persisted record's `server` field, and mandates the handler never read the former. This is the same
  "read the at-rest source, not a live/derived one" shape as `pairingStatus`/`unpair`, made explicit
  here because a plausible-looking alternative source existed for the first time.

## Lessons learned

- No React re-render, effect-cleanup, or dependency-version surprises — no React in any of the three
  new/edited files (`src/shared`, `src/main`, `src/preload` only), consistent with #79/#173.
- The test file's sentinel-collision guard (`SECRET_TOKEN`/`SECRET_KEY` chosen as non-overlapping
  substrings of `server`/`relay`) is worth reusing verbatim in any future test asserting
  "field A crosses, field B doesn't" via `JSON.stringify(...).not.toContain(...)` — a real secret
  value that happens to share characters with a legitimate crossing field would make the assertion a
  false negative.

## Carried forward / deferred

- **The renderer store + one-shot loader — #340**, blocked on this slice, is the first caller of
  `window.pyry.serverInfo()`.
- **The visible Settings Server row — #334** (Figma 17-2), the UI consumer of #340's store.
- **No error sub-reason** — same discipline as `pairingStatus`/`unpair`; `unavailable` never
  distinguishes not-paired from malformed from undecrypted. A future consumer needing that distinction
  extends the union additively.
