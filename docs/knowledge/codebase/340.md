# #340 — Server-info renderer store + one-shot loader

**Shipped:** 2026-07-13 · **Size:** S · **Scope:** renderer only (`src/renderer/src/store/`) ·
additive, no `App.tsx` edit · no new dependency.
**Spec:** `docs/specs/architecture/340-server-info-renderer-store.md` · **PR:** merged as `1581533`.
Split child of [#332](332.md); blocked on the now-merged [#339](339.md) (server-info IPC surface);
feeds [#333](333.md)/[#334](334.md) (Settings scaffold + visible Server row).

Ships the renderer-side half of the paired server's non-secret identity: a dedicated store holding
`{ serverId, relayUrl } | null` plus a one-shot loader that fetches it once via
`window.pyry.serverInfo()` and maps the response into the store shape. See the [server-info store
feature doc](../features/server-info-store.md) for the full contract, layers, and data flow.

## What shipped

Two new production files, two matching test files — 308 lines total, zero prod dependency:

- **`src/renderer/src/store/serverInfoStore.ts`** (64 lines) — `ServerInfoValue`/`ServerInfoState`/
  `ServerInfoStore`, `initialServerInfoState`, `createServerInfoStore` (DI factory over
  `zustand/vanilla`), the `serverInfoStore` singleton, `useServerInfoStore` (narrow-slice `useStore`
  binding), `selectServerInfo`. Byte-for-byte structural clone of `sessionIdStore.ts`, object-or-null

- **`src/renderer/src/store/serverInfoLoader.ts`** (69 lines) — `mapServerInfo` (pure union→store-shape
  collapse, the `translateSessionTransition` analog), `loadServerInfo` (injected-`invoke`,

  shape — `active`-flag guarded write, not a subscription).
- **`serverInfoStore.test.ts`** (79 lines) — the `sessionIdStore.test` plain-function idiom: absent
  start, set/clear/replace, present-vs-absent distinctness (including empty-string fields), DI
  independence, setter reference stability.
- **`serverInfoLoader.test.ts`** (96 lines) — `mapServerInfo` pure-map cases (`not.toHaveProperty

## Patterns established

- **One-shot mount-effect loader, not a subscription bridge — the second application of the `App.tsx`
  `pairingStatus()` idiom as a *named, reusable* shape** (distinct from the `sessionIdBridge`/
  `conversationListBridge`/`relayLinkStore` family, which all subscribe to `onDaemonEvent`). The
  discriminator: is there a daemon event behind the value? If yes, subscribe (the #259/#328 family);
  if the value is a fetch-once main-side read with no push event, mount-effect + `active`-flag instead.
  A future IPC surface shaped like `serverInfo` (one-shot invoke, no daemon event) should reach for this
  shape rather than inventing a bridge.
- **The store never accepts a partial value by construction, not by validation.** `mapServerInfo`
  reconstructs a *fresh* `{ serverId, relayUrl }` literal from the same present arm rather than
  destructuring/passing through — the type system, not a runtime check, guarantees the store can never
  hold `status` or a half-populated pair.
- **Ships dormant with zero `App.tsx` edit**, extending the `modalBridge`/`screenSnapshotBridge`
  "boundary ahead of consumer" shape to the *store* layer, not just the IPC layer (#339 already shipped
  the IPC side dormant) — two dormant layers stacked, both additive, before any UI reads either.

## Lessons learned

- No React re-render, effect-cleanup, or dependency-version surprises. The one non-trivial timing
  property — the StrictMode double-mount `active`-flag guarding exactly one applied write — was
  verified **by inspection** against the `App.tsx` `pairingStatus` precedent per the spec's testing
  strategy, not unit-tested; `loadServerInfo`'s injected-`invoke` tests carry the actual behavioral
  coverage instead. Worth keeping in mind for the next one-shot loader: the effect-timing property
  doesn't need its own test if the underlying `load*` function is exercised directly with a fake
  `invoke` and the effect is a thin, inspectable wrapper matching an existing precedent verbatim.

## Carried forward / deferred

- **Mounting `<ServerInfoData />`** — left to #333 (Settings scaffold) or #334 (visible Server row),
  whichever owns the paired-only Settings tree; either mounts it fresh on screen-open so a same-session
  pair is reflected without a relaunch.
- **No error sub-reason** — inherited from the channel (#339): the store can't distinguish
