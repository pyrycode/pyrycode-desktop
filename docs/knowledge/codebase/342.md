**Scope:** one file, `src/main/transport/fakeRoutingRelay.test.ts` (+28/−1). No production change —

**Spec:** `docs/specs/architecture/342-fakeroutingrelay-ac1-dial-stall.md` · **PR:**

Fixes a flaky test in the [Fake routing relay](../features/fake-routing-relay.md) suite (#251):
`startFakeRoutingRelay — lifecycle parity (AC1)` →
`exposes an ephemeral loopback url and holds whenReady until BOTH server and a client leg are up`
intermittently failed with `Error: Test timed out in 5000ms.`, but **only** under full `npm test`
parallel-worker load — 3/3 clean single-file in ~200–250ms on both the merge-base and the PR branch
that unmasked it (#341/#339, a 6-file diff with zero overlap with this file), confirming pre-existing,
not introduced.

## What shipped

Same file, same family as [#311](311.md)/[#336](336.md), but a **different failure shape**: those
two are *rejections* (a malformed upgrade response arrives and emits `'error'`, which the existing
`isTransientDialError`-fed `connect()` ladder re-dials past); this one is a *hang* — a dial whose TCP
connect lands but whose HTTP upgrade a CPU-starved server never processes, so `ws` emits **neither**
`'open'` nor `'error'`, and the emitted-`'error'` ladder never fires. No error object exists to feed a
classifier, so the remedy is a **timeout**, not a new `isTransientDialError` clause:

```ts
const DIAL_STALL_MS = 1500 // > healthy contended dial (~250ms); leaves ≥2 attempts within 5000ms

// inside connect()'s Promise executor, alongside the existing 'error'/'open' handlers:
const dialTimer = setTimeout(() => {
  ws.off('error', onDialError) // detach so terminate()'s events can't spawn a duplicate re-dial
  ws.terminate()
  if (attemptsLeft > 1) {
    resolve(connect(url, { headers, attemptsLeft: attemptsLeft - 1 })) // stall is inherently transient
  } else {
    reject(new Error(`dial to ${url} stalled: no open/error within ${DIAL_STALL_MS}ms`))
  }
}, DIAL_STALL_MS)
```

`onDialError` and the `'open'` handler both gained a `clearTimeout(dialTimer)` at the top, so the
timer can never fire after a dial already settled. Second change: AC1's own `relay.whenReady()` call
(the only test in the file that arms the readiness timer while just the server leg is up) was widened
to `relay.whenReady(4000)` — the default 1000ms margin would otherwise reject the test at ~1000ms
before a stalled-then-retried client-leg dial (detected at 1500ms) could converge. Production
`DEFAULT_READY_TIMEOUT_MS` (still 1000) is untouched; only this one test's call-site argument changed.

## Design in one paragraph

Root cause was confirmed by elimination over AC1's five `await`s, not by reproduction (the flake is
not machine-reproducible in isolation, same as #311/#336): a 5000ms **vitest timeout** is definitionally
a hung `await`, distinct from a rejection, and the only two awaits in AC1 that can hang for 5000ms are
the `serverLeg`/`clientLeg` dials — `whenReady()` itself is already settled by the time it's awaited
(resolved via `maybeSettleReady`, or rejected by its own 1000ms timer with a distinct message, never a
silent 5000ms hang). This ruled the `whenReady` margin **out** as the cause (candidate seam B from the
ticket) — per the family's "retry vs. barrier vs. margin are different-layer remedies" discipline, a
non-causal seam doesn't get a fix *as the remedy*. It still needed to move, though: the margin sits in
the way of the dial-timeout remedy at the client-leg site, since the default 1000ms fires before a
1500ms stall-detection-and-retry can complete. "Obstacle to the remedy" and "the cause" are different
things, and the spec is explicit that widening the margin is not a second fix for a second cause. The
dial timer itself follows the same discipline as #311/#336: consulted structurally only pre-`'open'`
(cleared on settle, same as the existing `onDialError`), so a genuine post-open behavioural regression
in any of the AC2–AC5 tests still fails unchanged.

## Patterns established

- **A 5000ms vitest timeout is categorically a hang, not a rejection — enumerate every `await` in the
  failing test and ask which one can't settle, rather than guessing at the seam.** This is what let
  the spec rule out the `whenReady` margin (which would reject with a distinct message at ~1000ms, not
  hang to 5000ms) without needing a reproduction. Confirms the family's root-cause-first discipline
  generalizes beyond rejection-flavoured flakes (#311's `Parse Error`, #336's `404`) to hang-flavoured
  ones.
- **A silent stall (no `'open'`, no `'error'`) needs a timeout, not another `isTransientDialError`
  clause.** The classifier pattern from #104/#311/#336 only applies when there's an error object to
  classify; a stall produces none, so extending the classifier here would be dead code. The dial-retry
  mechanism now has two independent trigger shapes in this file's `connect()`: an emitted `'error'`
  matched by the classifier, and a timer for the no-event case — both feeding the same bounded
  `attemptsLeft` re-dial.
- **An eliminated candidate can still require a code change, if it merely blocks the real remedy.**
  The `whenReady(4000)` bump is not a second fix for a second mechanism; it's headroom so the
  confirmed remedy (the dial timeout) can converge at a site where a pre-existing default would
  otherwise pre-empt it. Worth distinguishing explicitly in future flake specs so a reviewer doesn't
  read two file changes as two competing theories of the bug.

- Single-file: 12/12 in ~200ms.

- Security re-review (architect self-review, format per #311): PASS. The timer reacts to the absence

  `console.*` added; the stall-rejection message carries only the loopback URL and the timeout
  literal.

## Lessons learned

- Diagnosing a flake by symptom shape (hang vs. rejection) rather than by file/location narrows the
  seam search fast: once "5000ms vitest timeout = hung await" was established, only two candidate
  `await`s in the whole test remained plausible, and the `whenReady`-margin candidate the ticket
  flagged fell out of contention without needing to reproduce it.
- `ws`'s default socket has no `handshakeTimeout`, so a dial that never receives a `101` (or any error)
  from a CPU-starved peer sits forever with no signal at all — worth remembering for any future raw
  `ws` test harness in this codebase; the fix here is local (a manual timer in `connect()`), not a
  change to how `ws` sockets are constructed.
