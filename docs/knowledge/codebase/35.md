# #35 — Pin "a torn-down relayConnection never re-enters onEvent" (mobile #496 parity)

**Shipped:** 2026-07-07 · **Size:** XS · **Scope:** test-only (`src/main/transport/relayConnection.teardown.test.ts`) · **zero production changes** · one new file, no new production surface, no dependency change.
**Spec:** `docs/specs/architecture/35-superseded-connection-teardown-regression.md` · **PR:** [#106](https://github.com/pyrycode/pyrycode-desktop/pull/106). Mirror of mobile **#496** (close-then-connect race) — the **invariant**, not the fix. Pins the [relay connection](../features/relay-connection.md)'s teardown guarantee ([#21](21.md)) with a named regression fixture. Same shape as [#33](33.md) (mobile #497 re-scoped to a zero-production-change regression pin).

The invariant pinned: **a superseded (torn-down) `relayConnection` can never fire a late socket event into `onEvent`.** `teardownAndEmitClosed` (`relayConnection.ts:147-155`) runs exactly once — sets `closed = true`, clears every timer, calls `ws.removeAllListeners()`, and emits the terminal `closed` exactly once — so no second `closed` and no stray `message` can reach `config.onEvent` no matter what the underlying socket does afterward.

## Why it is load-bearing (and why security-sensitive)

The [relay supervisor](../features/relay-supervisor.md)'s `onConnEvent` (`relaySupervisor.ts:190`) is a **single shared handler** passed to every connection it dials, with **no per-connection generation fence**: on any `closed` it nulls the live `current` and schedules a re-dial. Desktop is safe from mobile #496's "a superseded connection clobbers the live one" race **only** because a torn-down connection never fires again — the whole defense lives at the connection layer, and the supervisor relies on it entirely. The guarantee was enforced by production code but **not directly pinned by a test**; this ticket turns that silent dependency into a red test, so a future refactor that removes `removeAllListeners()` or the teardown `closed` guard trips a test instead of silently reopening the race across an internet-exposed socket. `security-sensitive` is applied for that reason — a lifecycle/safety property of the relay socket — even though there is zero production surface change.

## What shipped

One new file, `relayConnection.teardown.test.ts` (+144 lines): a synchronous `EventEmitter` fake plus one `describe` with **two** focused `it` cases, each pinning one of the **two mutually-redundant** teardown guards with the assertion that targets it *specifically*.

| Case | Scenario | Biting assertion (and what removal reddens it) |
|---|---|---|
| **removeAllListeners pin** | drive `open → close`, then re-fire raw `close`/`message` on the same socket after teardown | after teardown `ws.listenerCount(name) === 0` for every socket event (`eventNames()` empty). Absent `ws.removeAllListeners()` (`relayConnection.ts:153`) the counts are non-zero → RED — even though the re-emit itself stays inert (the per-handler `closed` guard still covers it). |
| **closed-guard pin** | capture the module's `'close'` handler **before** teardown, then re-invoke it directly **after** teardown | still exactly one `closed`. Absent the `if (closed) return` teardown guard (`relayConnection.ts:148`) the re-invocation re-runs teardown and emits a **second** `closed` → RED. |

The observable "a late raw event reaches nobody" assertions (AC1's literal ask — still exactly one `closed`, zero `message`, `connected` unchanged, no throw) are **also** present, but they only bite when **both** guards are removed; the two mechanism-specific assertions above are what make a *single* removal bite.

Gates: `npm test` green (418 passed, the 2 new cases included); `npm run build` (typecheck + electron-vite) clean. Test-first is trivially satisfied — the guards pre-exist, so the block is GREEN on first run, and any red assertion would have exposed a real reopened race. Bite verified both ways (AC2): removing `removeAllListeners()` reddens only the listener-count test; removing `if (closed) return` reddens only the captured-handler test; both reverted (AC3, production sources untouched). Code review: **PASS**.

## Patterns established

- **When two guards are mutually redundant, a naive "re-fire and assert nothing happens" test bites on neither — pin each mechanism with its own targeted assertion.** At the `onEvent` boundary, `removeAllListeners()` (structural) and the per-handler `closed` flag (short-circuit) each independently stop a late event, so a re-emit test stays green even after you delete *either* one. The `listenerCount === 0` check isolates `removeAllListeners()`; the captured-handler re-entry isolates the `closed` guard. Reuse this whenever belt-and-suspenders redundancy would let a happy-path test pass a partially-broken guard.
- **Captured-handler re-entry is the connection-layer analog of #33's "call an entry point after `close()`".** `teardownAndEmitClosed` is only ever reached via the `'close'` handler, and `removeAllListeners()` deletes that handler — so the *only* way to re-enter teardown (and thus exercise its `closed` guard past `removeAllListeners()`' belt) is to hold the handler reference captured *before* teardown. Intentionally white-box; stated in a test comment.
- **Pin the invariant, not the ported fix, when the platform makes the fix moot.** Desktop's main process is single-threaded on the event loop and teardown is synchronous — mobile #496's threaded close-then-connect interleaving is structurally impossible here. Port the *safety property* into a regression fixture; **decline** the runtime synchronization primitive (pure make-work, forbidden by *Evidence-Based Fix Selection*), exactly as [#33](33.md) declined mobile #497's mutex.
- **Pin at the layer that holds the protection — refuse a same-run assertion that would demand out-of-scope production change.** The ticket asked whether to add a *supervisor-level* assertion (a superseded fake connection cannot clobber `current` / trigger a re-dial). It was **deliberately omitted**: `onConnEvent` has no generation fence, so that test would *fail* against current code and only pass after adding a production fence — out of scope, and defending a race the connection layer already makes impossible. The connection→supervisor relationship is captured in prose (this note + spec § Security review) and a test comment, not a second production mechanism.

## Lessons learned

*Lifted from PR [#106](https://github.com/pyrycode/pyrycode-desktop/pull/106)'s "Lessons learned" section.*

- **Node's `EventEmitter` throws on `emit('error')` when no `'error'` listener is registered.** After `removeAllListeners()`, firing a raw late `'error'` would throw under the *correct* code yet *not* throw if the error listener were still attached — **inverting** the assertion. So the spec's literal "emit a raw `'error'`" was deliberately not followed: the redundant guards are pinned via `'close'`/`'message'` re-emits plus a `listenerCount('error') === 0` check, never a raw `'error'` emit. (The code reviewer flagged this as more correct than the spec.)
- **`relayConnection` constructs `new WebSocket(...)` with no injection seam**, so the only way to hand it a controllable socket is `vi.mock('ws')`. The fake's instances are captured through a `vi.hoisted(() => ({ instances: [] }))` array (the `vi.mock` factory is hoisted above imports, so it can't close over an ordinary `const`), and the `FakeWebSocket` class is defined *inside* the lazily-run factory to dodge a "cannot access before initialization" error. Its `on`/`emit`/`removeAllListeners`/`listenerCount`/`listeners` are the **real** `EventEmitter` methods — those *are* the mechanism under test, so they must not be stubbed; only `send`/`close`/`terminate`/`ping` are `vi.fn()` (never invoked — the lifecycle is driven by emitting raw events, and teardown reaches `'close'` before any connect/ping timer fires, so no fake timers are needed).
- **Coverage boundary — green here is NOT "the supervisor is race-free."** These are *connection-layer* pins: green means "a torn-down `relayConnection` does not fire again". "A superseded connection cannot clobber the live one at the supervisor" is *derived* from that guarantee plus the shared-handler wiring, and is argued in prose, **not** asserted in code (the supervisor has no generation fence). And because the two guards are redundant, removing only one leaves the observable re-emit inert — each is caught solely by its own targeted assertion, not by the re-emit. The test carries a `COVERAGE BOUNDARY` comment saying exactly this so a maintainer does not misread green as "the guards are individually necessary at the boundary" or "the supervisor is proven safe".

No React / effect-cleanup / dependency-version surprises: a pure main-process unit-test addition with no runtime surface.

## Deferred / carried forward

- **A per-connection generation fence in the supervisor is NOT filed.** `onConnEvent` relies entirely on the connection-layer guarantee this ticket pins, which makes a supervisor-side fence moot today — **no observed failure**, so no speculative ticket (*Evidence-Based Fix Selection*). If a future refactor ever lets a superseded connection fire (i.e. this pin goes red), *that* is when the fence becomes a real design question.
- **Mobile #493 (reconnect-gating stall) lands with its feature.** No conversation-list / load-on-reconnect surface exists on desktop; the guard ships with that feature and its own reconnect test — no retroactive sweep.
