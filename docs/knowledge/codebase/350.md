## What shipped

Six files touched, 75 insertions:

- **`electron.vite.config.ts`** — reads `package.json`'s `version` via `readFileSync` (not a JSON
  import — this config is typechecked by `tsconfig.node.json`, which sets no `resolveJsonModule`) and
  exposes it as a Vite `define`, `__APP_VERSION__: JSON.stringify(appVersion)`, inside the `renderer`
  block.
- **`vitest.config.ts`** — the **same** `define`, fed the same way, added at the top level of
  `defineConfig`. Load-bearing: this is a separate Vite config from `electron.vite.config.ts`, so a
  `define` added only to the electron-vite side is invisible to the vitest run and the render test throws
  `ReferenceError: __APP_VERSION__ is not defined` instead of a clean assertion miss.
- **`src/renderer/src/version.d.ts`** (new, 5 lines) — ambient `declare const __APP_VERSION__: string`,
  no `import`/`export` (keeps it a global), picked up by `tsconfig.web.json`'s existing
  `src/renderer/src/**/*` glob alongside `env.d.ts`. Kept as its own file rather than folded into
  `env.d.ts`, which stays the `vite/client` triple-slash-reference file only.
- **`SettingsScreen.tsx`** — extends `SETTINGS_COPY` with `about: 'About'`; adds a module-const
  `VERSION_LINE = \`Version ${__APP_VERSION__}\``; appends a second `<section
  className="settings__section">` after the existing Connection section, with an `<h2
  className="settings__section-header">` header (the Connection header's exact treatment) and a
  `settings__about-row` / `settings__about-version` row holding the version line. Inline, not a new
  component file — no store, no loader, no populated/null matrix, so a container/pure-view split would be
  over-engineering for a static string. `SettingsScreen`'s `{ onBack }` signature is unchanged; it stays
  server-renderable.
- **`settings.css`** (+19 lines) — `.settings__about-row` (`padding: var(--space-3) var(--space-4)`,
  mirroring the Server row's padding) and `.settings__about-version` (`margin: 0` + `--color-on-surface`
  + the four `--text-body-large-*` declarations, copied from `.settings__server-row-label`). No new token
  or literal.
- **`SettingsScreen.test.tsx`** (+10 lines) — two new assertions on the `renderToStaticMarkup` output:
  `toContain('>About</h2>')` (AC1) and `toContain('Version 0.1.0')` (AC2/AC5).

## Patterns established

- **Build-time `define`, not IPC, for a static client-owned value.** The version lives in `package.json`,
  is baked in at build time, is non-secret, and has no async/untrusted character — the deliberate
  opposite of `serverInfo` (#339/#340/#334), which crosses the main→renderer boundary precisely because
  it's daemon-sourced, async, and nullable. A future build-time constant with the same shape (e.g. a
  build-hash, deferred here — see Carried forward) should follow this same `define`-in-both-configs +
  ambient-`.d.ts` mechanism rather than reaching for a preload/IPC bridge.
- **A `define` must be mirrored into `vitest.config.ts` whenever it's added to `electron.vite.config.ts`.**
  The two are independent Vite configs; `npm run dev`/`npm run build` only sees the electron-vite one,
  `npm test` only sees vitest's. Any future compile-time constant needs the same two-file edit, read from
  `package.json` via `readFileSync` (never a JSON import — `electron.vite.config.ts` is typechecked with
  no `resolveJsonModule` set anywhere in the repo's tsconfigs).
- **Inline markup over a new component file when there's no state to isolate.** Unlike `ServerRow.tsx`
  (#334), which earned its own module because it's store-bound and has a populated/null matrix worth a
  dedicated test file, the About version row has neither — it stayed inline in `SettingsScreen.tsx`. The
  house rule this confirms: a dedicated component file is for state or a distinct test seam, not for
  visual grouping alone.

## Carried forward / deferred

- **The build-hash sub-line (Figma 17-109, "build a8f3c2d") is out of scope.** No wired build-metadata
  source exists on desktop today. A follow-up can add it with a second `define` fed by a build-time git
  hash, using the exact mechanism this ticket established.
- **The `Version 0.1.0` test assertion is coupled to `package.json`'s current version.** It will need a
  one-line update on the next version bump — a deliberate accepted tradeoff (see the spec's Open
  Questions) since deriving the expected value dynamically in the test would need its own JSON import,
  which the same `resolveJsonModule` gap blocks.
- Remaining Settings rows from the #151 split ([#351](151.md) archived count, #352 Defaults, #353 Push)
  are unrelated siblings, not blocked by this ticket.
