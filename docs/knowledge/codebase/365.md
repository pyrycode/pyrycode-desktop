# #365 — Channel Info sheet: shell + overflow entry + conversation detail

Split from #155 (itself split from #148 alongside #276/#277/#278/#279). PR #372. Spec:
`docs/specs/architecture/365-channel-info-sheet-shell.md`. See [Conversation
shell](../features/conversation-shell.md#channel-info-sheet-365) for the feature line; this file covers
implementation notes and lessons.

## Summary

Wires the thread overflow menu's **Channel info** item (#276, a live no-op until now) to open a new
Channel Info sheet (Figma node 20-48). The sheet reuses the Run-configuration `StatusSheet`'s
`.status-sheet__*` chrome verbatim and renders the active conversation's **About** detail (Workspace
`cwd` + Last activity), an empty **Actions** section slot for the Archive/Delete/Rename tickets to fill,
and a monospace **Channel ID** footer. Opens gracefully with a placeholder About when there is no active
conversation (a list-opened thread). Renderer-contained: no transport, IPC, or wire code. Everything
lands in `ConversationScreen.tsx` + `conversation.css` (+ the test) — three files, 354 lines.

Two new symbols in `src/renderer/src/screens/conversation/ConversationScreen.tsx`, the `StatusSheet` /
`ThreadOverflowMenu` pure-view/in-file-container split:

- `ChannelInfoSheetView` (exported, pure) — `{ conversation: ConversationCreatedPayload | null, now?:
  number, onClose }` → the overlay/scrim/panel/handle/header/close chrome (cloned from `StatusSheet`) plus
  the About rows, the empty Actions `<div>`, and the Channel ID footer. No state, no effects, no
  `window.pyry` — server-render-tested with injected props.
- `ChannelInfoSheet` (in-file, unexported) — owns only the Escape `document`-`keydown` effect (the
  `ThreadOverflowMenu` idiom), scoped to the sheet's mount lifetime since it only mounts while open (no
  `open` flag needed). Renders the pure view.

`ConversationScreen` gained one new `useState(false)` — `channelInfoOpen`, the `sheetOpen` twin — and
rewired the overflow mount from `<ThreadOverflowMenu onChannelInfo={onChannelInfo} />` to
`<ThreadOverflowMenu onChannelInfo={() => setChannelInfoOpen(true)} />`.

## Patterns established

- **Retiring a speculative extension-seam prop in favor of screen-local ownership.** #276 shipped
  `ConversationScreenProps.onChannelInfo?` on the assumption the sheet would be opened from `PairedShell`
  (matching how `onBack`/`onUnpaired` are threaded down). Once building the sheet, its trigger (the
  overflow menu), its data (`activeConversationStore`, already read in this screen), and its chrome (an
  absolute overlay inside `.conversation`) turned out to be entirely `ConversationScreen`-local — exactly
  like `StatusSheet`, whose `sheetOpen` is *not* threaded through `PairedShell` either. The prop was
  removed from the interface and the destructure rather than wired through a second file, after confirming
  no caller (`PairedShell`, `App.tsx`, or any test) ever passed it. **Lesson for future "the caller will
  supply this later" seams:** don't assume the eventual shape from the split-ticket write-up — re-derive it
  from the actual data/trigger locality once the follow-up ticket is in hand, and retire the seam if the
  original assumption doesn't hold. A code-review or PO objection to the literal AC wording ("PairedShell
  passes...") is the fallback path, not the default.
- **`conversation === null` as a first-class render branch, not a guard clause.** Because
  `activeConversationStore` is populated on exactly one path (the FAB create-nav callback) and a
  list-opened thread never reaches it, the sheet's About section has two full branches (populated rows vs.
  `CHANNEL_INFO_EMPTY_COPY` placeholder) and the Channel ID footer is conditionally rendered at all. No
  early return / crash guard — the sheet is designed to open cleanly regardless of `activeConversationStore`
  state, since the overflow-menu trigger has no way to know in advance whether the store is populated.
- **Reusing a differently-named sheet's chrome CSS is fine when the alternative is real duplication.** The
  ticket explicitly sanctioned reusing `.status-sheet__*` (a name coined for the Run-configuration sheet)
  for a second, unrelated sheet rather than extracting a generic `.bottom-sheet` — avoids ~100 lines of
  duplicated chrome CSS for a shell-only ticket; a rename is deferred to a real refactor if a third sheet
  appears.

## Lessons learned

From the PR body:

- Reusing the run-config-named `.status-sheet__*` chrome for a second bottom sheet is sanctioned by the
  ticket and avoids ~100 lines of duplicated CSS; a rename to a generic `.bottom-sheet` (if a third sheet
  appears) is a separate refactor.
- The Channel ID footer is rendered at `body-small` (12px) mono where the Figma uses 11px — a spec-chosen
  token simplification (the app's fixed type scale is the fidelity vocabulary, not a literal pixel match),
  noted here so it is not mistaken for drift.

## Verified at review time

- `npm test` (1668 pass, 3 pre-existing skips), `npm run typecheck`, `npm run build` all clean. Seven new
  server-render tests on `ChannelInfoSheetView`: chrome (`role="dialog"`/`aria-modal`/`aria-labelledby`/
  handle/close), populated header+About+footer, the unnamed-name fallback, the null-conversation
  graceful-empty path, the empty Actions slot (asserting none of Rename/Archive/Delete/Change-workspace
  appear), untrusted-string escaping (`<b>`/`&`/`'` on `name`/`cwd`), and the absence of the deferred
  Figma rows (Created/Total sessions/Total messages/Memory).
- Interaction behavior (Escape-dismiss, the overflow-select → `setChannelInfoOpen(true)` wiring) is
  reviewed glue, not unit-tested — the suite is `renderToStaticMarkup`-only (no jsdom), the same
  constraint #276's Escape/outside-click and `StatusSheet`'s open-on-click wiring were shipped under.

## Open questions (flagged, not built)

- **Two sheets open at once** — `sheetOpen` (run-config) and `channelInfoOpen` are independent booleans;
  both overlays could in principle stack. Not reachable through normal use (separate triggers, one at a
  time) and no AC requires mutual exclusion — left as-is, a future `<BottomSheet>` extraction (if a third
  sheet appears) could enforce it.
- **`.status-sheet__*` reuse vs. rename** — a mild semantic coupling (see Patterns above), deferred.
