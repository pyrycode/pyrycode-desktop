# #366 — Channel Info sheet: Archive action

Split from #155 (itself split from #148 alongside #363/#364/#365/#367/#368). PR #374. Spec:
`docs/specs/architecture/366-channel-info-sheet-archive-action.md`. See [Conversation archive
(transport)](../features/conversation-archive.md) and [Conversation
shell](../features/conversation-shell.md#channel-info-sheet-365) for the feature lines; this file
covers implementation notes and lessons.

## Summary

Fills the Channel Info sheet's `.channel-info__actions` slot's **second** row with an **Archive**
control (Figma 20:94) — the row that dispatches the already-shipped, previously-dormant
`archiveConversation` command (#363). Landed second, not first: #368 (Rename) merged just before
this ticket and already created the shared `.channel-info__action` tonal-pill style and the
callback-gated-button idiom, correcting the ticket body's and prior project-memory's stale
assumption that #366 would be the one to establish it. Archive reuses both verbatim.

One production file, `ConversationScreen.tsx`, four changes:

- **`ChannelInfoSheetView`** gains an `onArchive?: () => void` prop, rendered as a second
  `.channel-info__action` button below Rename, gated on the callback exactly like `onRename?` (the
  view asks "was the callback supplied," never re-derives from `conversation`).
- **A new exported dispatch helper, `requestArchiveConversation(sendCommand, conversationId)`** —
  a verbatim clone of `requestUnarchiveConversation` (`ArchiveScreen.tsx:216`): bare
  `sendCommand({ type: 'archiveConversation', payload: { conversation_id } })`, no try/catch, no
  deps object, no constructor. The inline literal type-checks against `RendererCommand`
  (`commands.ts:98`), requiring one new type-only import (`RendererCommand` was not previously
  imported in this file). Exported because the sheet renders server-side only — the click handler
  can't be exercised via a fired DOM event, so the helper needs to be independently unit-testable.
- **The `ChannelInfoSheet` container** supplies `onArchive` only in the `conversation !== null`
  branch (AC1 guard, mirroring `onRename`'s gate). Unlike Rename, which opens a dialog, the Archive
  handler is a direct dispatch-then-close: `requestArchiveConversation(window.pyry.sendCommand,
  conversation.id)` followed by the container's existing `onClose` (AC2) — no new local state.
- **Button order**: Rename → Archive → the future Delete (#367) — a destructive-last convention
  (edit, then soft-remove, then the eventual permanent action last).

No CSS, wire, or IPC code — #363 already shipped the command, its guard, and the wire type; this
ticket is a pure renderer dispatch site. The archived conversation leaving the active list is free:
the daemon's `conversation_updated` broadcast reply rides the existing #275 list-re-request path,
already proven by the symmetric unarchive/restore flow (#346/#348). No reflection code added (AC3).

## Patterns established

- **A second sibling action reusing a just-landed shared style needs no new CSS, only the
  established callback-gate idiom repeated.** #368 landed one merge before this ticket and had
  already generalized `.channel-info__action` as (per its own code comment) "a generic base #366/#367
  reuse." This ticket is the first proof that the generalization holds: adding Archive touched zero
  CSS lines. Worth checking, when a spec's "Context" section claims a ticket "establishes" a shared
  style, whether a blocking sibling actually landed first and already did — the architect spec for
  this ticket explicitly corrected that stale assumption before design started.
- **Mirror-image transport verbs (archive/unarchive) get mirror-image dispatch helpers**, not a
  single parameterized one. `requestArchiveConversation` is a byte-for-byte structural twin of
  `requestUnarchiveConversation` — same signature shape, same bare dispatch, differing only in the
  command's `type` literal — kept as two functions rather than one taking a verb parameter, matching
  how #363/#346 already keep the underlying wire payload types (`ArchiveConversationPayload` /
  `UnarchiveConversationPayload`) as distinct, non-aliased types rather than one shared shape. Two
  near-identical five-line functions read clearer at each call site than one with a mode flag.

## Lessons learned

- Anchoring server-render assertions on the **button label** (`>Archive</button>`), not the shared
  CSS class, matters even more once a *second* button shares that class. #368's PR already flagged
  the `channel-info__action` (singular) vs. `channel-info__actions` (plural, the slot) substring trap;
  this ticket adds the second half of the same lesson — `class="channel-info__action"` alone can no
  longer disambiguate *which* button rendered once Rename and Archive both carry it. Tests here
  assert on the full opening tag with label instead of the class in isolation.

## Verified at review time

- `npm test` (1676 pass, 3 pre-existing skips), `npm run build` (typecheck + electron-vite) both
  clean.
- Four new server-render assertions on `ChannelInfoSheetView`: Archive button present
  (conversation + `onArchive` both supplied); absent when `conversation === null` (AC1 guard);
  absent when `onArchive` is omitted despite a populated conversation (proves the gate is the
  callback, not the data — same discipline #368 established for Rename); Rename's existing tests
  stay green unmodified (positive case supplies only `onRename`, so only one button renders).
- One direct dispatch test on `requestArchiveConversation`: a spy `sendCommand` is called exactly
  once with `{ type: 'archiveConversation', payload: { conversation_id: 'conv-x' } }`.
- AC3 (archived conversation leaves the active list) is inherited from #275/#346's already-tested
  re-list path and gets no new test at this layer. AC4 (server-renderability — `window.pyry`
  dereferenced only inside the click callback) is covered structurally: the render tests never touch
  `window.pyry`, and the container's `onArchive` closure is the only place it's read.
