# #368 — Channel Info sheet: Rename action (reuse the rename dialog)

Split from #155 (itself split from #148 alongside #363/#364/#365/#366/#367). PR #373. Spec:
`docs/specs/architecture/368-channel-info-rename-action.md`. See [Rename dialog + per-row
affordance](../features/rename-conversation-dialog.md) and [Conversation
shell](../features/conversation-shell.md#channel-info-sheet-365) for the feature lines; this file
covers implementation notes and lessons.

## Summary

Fills the Channel Info sheet's empty `.channel-info__actions` slot (#365's mount point) with a
**Rename** tonal pill (Figma 20:89) — a second entry point for renaming the active conversation,
alongside the existing Channel List per-row affordance (#360). Both entry points reuse the exact
same dialog (`RenameConversationDialogView`) and the exact same dispatch helper
(`requestRenameConversation`), imported verbatim — no clone, no new transport, IPC, or wire code.

Two files carry the behavior:

- **`ConversationScreen.tsx`** — `ChannelInfoSheetView` (pure, exported) gains an optional
  `onRename?: () => void` prop; the Actions slot renders the pill only when it's supplied. The
  in-file `ChannelInfoSheet` container grows a screen-local `useState` pair
  (`renameOpen`/`renameName`, the `ChannelList.tsx:48-96` shape) and renders
  `RenameConversationDialogView` as a conditional sibling. `onRename` is threaded to the view only
  in the `conversation !== null` branch, so a list-opened thread (no active conversation) offers no
  button — the AC1 guard is the prop's presence, not a re-check inside the view.
- **`RenameConversationDialog.tsx`** — one line changed: `requestRenameConversation`'s `row` param
  narrowed from `ConversationSummary` to `Pick<ConversationSummary, 'id'>`, since the helper reads
  only `.id`. This lets the sheet pass its `ConversationCreatedPayload` (a 5-field payload lacking
  `is_archived`/`last_message_ts`) directly — no adapter object, no `as` cast — while the existing
  `ChannelList.tsx:94` call site (a full `ConversationSummary`) keeps typechecking unchanged, since
  a wider shape still satisfies a `Pick` of its own fields. Zero call-site fan-out.

Plus one new CSS class, `.channel-info__action` (`conversation.css`), the M3 tonal pill: token-only
(`--color-secondary-container`/`--color-on-secondary-container`/`--radius-full`/
`--text-label-large-*`/`--space-2`/`--space-4`), with a `min-height: 40px` literal to hit Figma's
exact button height (justified against the file's existing pattern of hardcoded component heights
elsewhere in `conversation.css`, not a token-scale violation).

## Patterns established

- **Widen a helper's param type to what it actually reads, instead of adapting the caller's data to
  fit an over-specified type.** `requestRenameConversation` only ever touched `row.id`; its
  `ConversationSummary` param was an accident of its first caller's shape, not a real requirement.
  Narrowing to `Pick<ConversationSummary, 'id'>` is a structural-typing move that's simultaneously a
  honesty fix (the signature now says what it consumes) and the cheapest way to let a second,
  narrower payload type flow through the same function with zero fan-out — no wrapper object, no
  cast, and the wider original caller is unaffected because TypeScript's structural typing makes a
  `Pick` a strict widening of what's assignable. Worth reaching for whenever a second caller's data
  shape is a strict subset of an existing helper's declared (but over-broad) param type.
- **A button gated on an optional callback prop, not on the data the callback closes over.** The
  view never re-derives "is there a conversation" — it only asks "was `onRename` supplied." The
  container is the single place that decides gating (`conversation !== null`), so the view stays a
  pure function of its explicit props and the guard logic isn't duplicated across the pure/container
  boundary. Same idiom as `ChannelList`'s `onRename?`/`onSaveAsChannel?` row affordances.

## Lessons learned

From the PR body:

- `channel-info__action` (the new button class) is a literal substring of `channel-info__actions`
  (the pre-existing slot container class from #365). A naive `expect(markup).toContain('channel-info__action')`
  assertion would silently pass even with no button rendered, because it also matches the always-present
  plural slot `<div>`. The fix is to anchor on the quote-terminated attribute form,
  `class="channel-info__action"`, which only matches the singular class. Worth checking for this
  shape (`X` vs `Xs`, or any prefix/suffix pair) whenever adding a new CSS class that's a textual
  extension of an existing one being asserted on with `toContain` in a server-render test.

## Verified at review time

- `npm test` (1672 pass, 3 pre-existing skips), `npm run typecheck`, `npm run build` all clean.
- Three new server-render tests on `ChannelInfoSheetView`: button present (conversation + `onRename`
  both supplied), button absent (`conversation === null`, AC1), button absent (`onRename` omitted
  even with a populated conversation — proves the gate is the callback, not the data).
- One new test on `requestRenameConversation`: a `ConversationCreatedPayload`-shaped arg (not a
  `ConversationSummary`) dispatches the expected trimmed `{conversation_id, name}` payload,
  documenting that the widened `Pick<…, 'id'>` param accepts it directly.
- Code review PASS, no findings (MUST FIX / SHOULD FIX / NIT all empty) — confirmed the widened
  param's zero fan-out at both call sites, the AC1 gating, the trim-before-dispatch, the
  server-render-safety of deferring `window.pyry` to interaction callbacks, sound TS narrowing of
  `conversation` inside the `onSave` closure, and 100%-token CSS with a visual-fidelity check
  against the Figma 20:89 screenshot.
- The container's open→seed→dispatch→close wiring, the dialog's Save/Cancel interaction, and the
  `window.pyry` deref are **not** unit-tested — the suite is `renderToStaticMarkup`-only (no jsdom),
  the same boundary `ChannelList`'s rename interaction and `StatusSheet`'s open-wiring ship under;
  guarded by `npm run typecheck` + `npm run build` instead.

## Open questions (carried from the spec, not built)

- **Escape while the rename dialog is open closes the whole sheet**, not just the dialog — the
  sheet's own `document` Escape listener fires and unmounts everything, including the dialog. This
  is an accepted "Escape = cancel, no dispatch" outcome, matching the reused #360 dialog's lack of
  an independent Escape handler (the same posture as `ChannelList`'s rename dialog). Left as-is; a
  future shared `<BottomSheet>`/`<Dialog>` extraction, if a third sheet or a third dialog trigger
  appears, could give the dialog its own Escape precedence first.
