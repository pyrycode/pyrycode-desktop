# #375 — `conversation_deleted` inbound decode → `conversationDeleted` event

**Shipped:** 2026-07-14 · **Size:** S · **Scope:** `src/shared/wire/types.ts`,
`src/shared/ipc/events.ts`, `src/main/transport/inboundMessage.ts`, `src/main/daemonConnection.ts`,
plus the three exhaustive renderer bridges (`daemonEventBridge.ts`/`modalBridge.ts`/`timelineBridge.ts`).
**Spec:** `docs/specs/architecture/375-*.md` · **PR:** #378. Split from [#367](367.md) (the decode
half; list-reflect is #376, Delete action + confirm UI is #377). Security-sensitive (architect
self-review PASS, see below).

Ships **dormant** — decoded and emitted, no renderer subscriber yet. The inbound mirror of the
`conversation_updated` decode (#273), scaled to one field.

## Summary

[#364](364.md) shipped the dormant outbound `deleteConversation` command. Unlike archive/unarchive
— confirmed by an unsolicited `conversation_updated` broadcast the existing list-reflect path
(#273/#275) already consumes — a delete is confirmed with a **distinct, correlated
`conversation_deleted { id }` record and no broadcast** (pyrycode#822). That reply was previously
undecoded. This slice adds the inbound half only:

- **Wire type** (`src/shared/wire/types.ts`) — `ConversationDeletedPayload { id: string }`, placed
  immediately after `ConversationUpdatedPayload` (grouped with the other inbound reply types, not
  next to the outbound `DeleteConversationPayload`). A single required field; the reply's `id` is
  distinct from the request's `conversation_id` — a no-drift doc-comment says so explicitly.
- **Parse fn** (`src/main/transport/inboundMessage.ts`) — `parseConversationDeletedPayload`: an
  `isRecord` guard, then one `requireString(payload, 'id')`, returning a **fresh single-field
  object** (unknown extra keys tolerated, not copied through).
- **`InboundDaemonMessage` variant** — `{ kind: 'conversation-deleted'; conversationDeleted: ConversationDeletedPayload }`,
  added after `conversation-updated`.
- **Decode case** — `case 'conversation_deleted':` clones the `conversation_updated` arm exactly:
  narrow-before-log (a malformed reply throws before any log record is written), a content-free
  diagnostic (`code`/`bytes`/`hash` only, no `id`, no `count`).
- **`DaemonEvent` variant** (`src/shared/ipc/events.ts`, shared file) —
  `{ type: 'conversationDeleted'; id: string }`. Deliberately **not** a clone of
  `conversationUpdated`'s `{ conversation: ConversationUpdatedPayload }` shape: a delete reply has
  exactly one field, so it flattens to a fresh literal naming the bare `id` (the `turnState`/
  `sessionSettingsUpdated` single-field emit idiom), keeping `events.ts` free of a
  `ConversationDeletedPayload` import.
- **Emit arm** (`src/main/daemonConnection.ts`) — `case 'conversation-deleted':` emits
  `{ type: 'conversationDeleted', id: inbound.conversationDeleted.id }` **unconditionally** on
  decode, mirroring `conversation-updated`'s broadcast emit — even though this reply *is*
  correlated by `in_reply_to`, no correlation state (no `pendingSettings`/`outstandingAnswers`-style
  map) is threaded, since the bare `id` is self-sufficient for #376's by-id removal. Not
  `assertNever`-guarded in this inner switch (the `stall` arm's precedent) — the round-trip test in
  `daemonConnection.test.ts` is the only thing guarding this emit, not the compiler.
- **Three renderer bridges** — `daemonEventBridge.ts`/`modalBridge.ts`/`timelineBridge.ts` each
  gained a `conversationDeleted` no-op case, forced by their `assertNever` exhaustiveness guards
  (the `conversationUpdated`/`stallDetected`/`relayLinkChanged` dormant-arm precedent).

`npm test`, `npm run typecheck` clean.

## Patterns established

- **A fourth confirmation of "decode reply as a bare flattened primitive when the payload has
  exactly one field, reuse the wire type by reference only when it has several fields with nothing
  to drop."** `conversationDeleted{id}` joins `turnState{state}`/`sessionSettingsUpdated{sessionId}`
  on the single-field-literal side, `conversationUpdated{conversation}` stays the reference-reuse
  precedent for multi-field payloads with nothing to drop.
- **A correlated reply (matched by `in_reply_to`) can still be emitted unconditionally with zero
  correlation memory, when the payload alone is sufficient for the consumer's job.** Distinguishes
  this from the `pendingSettings`/`outstandingAnswers` family (#261/#248/#269), which thread
  send-time state specifically because their consumers need more than the reply payload alone
  provides (a `changeId`, a FIFO-attributed `modal_id`). Here #376 only needs the `id` to remove a
  row — nothing else to correlate.
- **A malformed-payload decode failure and an unsolicited/spurious-but-well-formed reply are
  different threat categories, and only the former needs a parser.** The security review treats a
  hostile daemon sending an arbitrary `conversation_deleted{id}` as within its existing authority
  (it already owns the conversation set via `conversation_updated`/`conversations`), not something
  requiring a client-side correlation gate — consistent with `conversationUpdated`'s unconditional
  broadcast emit.
