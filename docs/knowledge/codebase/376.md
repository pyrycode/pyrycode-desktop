# #376 — Renderer reflects a deleted conversation (leaves the list)

**Shipped:** 2026-07-14 · **Size:** XS · **Scope:** `src/renderer/src/store/conversationListBridge.ts`
(production) + `src/renderer/src/store/conversationListBridge.test.ts`. **Spec:**
`docs/specs/architecture/376-conversation-deleted-list-reflect.md` · **PR:** merged to `main` via
`feature/376`. Split from [#367](367.md) (decode `#375`, done / list-reflect `#376`, this ticket /
Delete action + confirm UI `#377`, not yet built). Not security-sensitive — renderer-only, no keys,
sockets, or raw bytes.

## Summary

[#375](375.md) shipped a dormant `conversationDeleted{id}` `DaemonEvent` — decoded and emitted, no
renderer subscriber. This slice wires the one consumer: a `conversationDeleted` now fires the same
authoritative full-list re-request that `conversationUpdated` already fires, so a permanently
deleted conversation leaves every reader of `conversationListStore` without a reconnect.

The whole production change is one predicate, renamed and broadened, in
`conversationListBridge.ts`:

```ts
// was: isConversationUpdated(event) { return event.type === 'conversationUpdated' }
export function shouldRefreshList(event: DaemonEvent): boolean {
  return event.type === 'conversationUpdated' || event.type === 'conversationDeleted'
}
```

`subscribeConversations`'s single call site changed from `if (isConversationUpdated(event))` to
`if (shouldRefreshList(event)) refreshOnChange()` — nothing else in the function changed.
`translateConversationsEvent` is untouched: `conversationDeleted` still falls through its
`default: null`, so the event never lands rows directly. No store, IPC, wire, or bridge file
changed — `daemonEventBridge.ts`/`modalBridge.ts`/`timelineBridge.ts` keep their existing
`conversationDeleted` no-ops from #375.

## Why a rename, not a parallel predicate

The architecture spec decided this explicitly (developer had no discretion here): `isX` predicates
OR'd at the call site split the "which events refresh the list" policy across three places (two
predicates + the caller's `||`). One predicate, renamed to match its now-two-arm responsibility,
keeps the policy in one place and reads as intent at the call site. The function's doc comment
already described a general "should this event re-request the list?" contract before this ticket
(see [conversation-list-store.md § the data path](../features/conversation-list-store.md)) — the
old name (`isConversationUpdated`) was narrower than the contract it documented from the start.

A local remove-by-id store setter was explicitly rejected (AC4 of the ticket): it would have to
re-implement the null-safe (AC2) and absent-id-safe (AC3) guarantees the re-request path gets for
free from `setConversations`'s whole-array replacement.

## Why no other file needed a change (AC1)

All list surfaces — the Channel List (#141), the Settings archived-count row (`selectArchivedCount`,
#351), any future reader — read the single `conversationListStore` singleton. The re-request fires
the existing bare `requestConversations` command; the daemon's fresh `list_conversations` reply
omits the deleted id; `setConversations`'s whole-array replacement (no merge) lands the shorter
list. Every reader re-renders off that one store update — no per-reader wiring exists to add.

## Patterns established

- **A refresh-trigger predicate models "should this event re-request the authoritative list?", not
  "did this specific event type occur?"** — when a second event arm gets the same answer, the fix is
  broadening and renaming the one predicate, not adding a sibling predicate OR'd at the call site.
  Confirms the naming discipline `translateConversationsEvent` vs. `shouldRefreshList` already
  established (a *filter* names what it selects; a *trigger* names what it decides) stays a
  single-purpose split even as the trigger's own arm count grows.
- **A correlated reply and a broadcast can share one refresh trigger despite differing delivery
  semantics**, because the trigger only cares about occurrence, never about how the event arrived or
  what it carries (AC3, unchanged from #275's original id-blind design). This is the same
  occurrence-not-payload posture #375's DaemonEvent doc comment set up for `conversationDeleted`,
  now proven out at its consumer.
- **The re-request path is null-safe and absent-id-safe by construction, not by added guards** — a
  `conversationDeleted` while `conversations === null` fires the request but the store stays `null`
  (no arm reaches `setConversations`); a `conversationDeleted` for an id already absent from the list
  produces a content-identical whole-array replacement. Neither needed a dedicated code path; both
  fall out of "the only store writer is `conversationsReceived`."
