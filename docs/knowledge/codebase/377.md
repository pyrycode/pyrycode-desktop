# #377 — Channel Info sheet: Delete action + destructive confirm

**Shipped:** 2026-07-14 · **Size:** S · **Scope:** `src/renderer/src/screens/conversation/ConversationScreen.tsx`
(production) + `ConversationScreen.test.tsx` + `conversation.css`. **Spec:**
`docs/specs/architecture/377-channel-info-delete-action.md` · **PR:** #387, merged to `main`.
Split from [#367](367.md) (decode `#375`, done / list-reflect `#376`, done / Delete action +
confirm UI `#377`, this ticket — the last of the three-way split). Not security-sensitive —
renderer-only; the `deleteConversation` command and its renderer→main boundary guard shipped
dormant in [#364](364.md).

## Summary

Fills the Channel Info sheet's `.channel-info__actions` slot's **third and final** row with a
**Delete** control (Figma 20:96) — the row that dispatches the already-shipped, previously-dormant
`deleteConversation` command (#364). Unlike Rename (#368, opens a dialog) and Archive (#366,
dispatches directly), Delete is destructive and irreversible, so it gates dispatch behind an
inline two-step confirm — a client-owned invention (no Figma node), the #226 second-confirm /
#360 rename-affordance posture.

One production file, `ConversationScreen.tsx`, three parts:

- **A new exported dispatch helper, `requestDeleteConversation(sendCommand, conversationId)`** —
  a verbatim clone of `requestArchiveConversation`: bare `sendCommand({ type: 'deleteConversation',
  payload: { conversation_id } })`, no try/catch, no constructor. Exported for the same reason as
  its siblings — the sheet renders server-side only, so the confirm handler can't be exercised via
  a fired DOM event.
- **`ChannelInfoSheetView`** gains four cohesive optional props — `onDelete?`, `deleteConfirmPending?`,
  `onDeleteConfirm?`, `onDeleteCancel?` — supplied together or not at all. `onDelete` only opens the
  confirm (never dispatches); the pill and the confirm block are mutually exclusive renders inside
  the same `.channel-info__actions` slot, gated on `onDelete` presence then branched on
  `deleteConfirmPending`. The confirm block replaces the pill in place: a prompt line
  (`.channel-info__confirm-text`, "Delete this conversation permanently? This cannot be undone.")
  plus a base-styled Cancel pill and a `--danger`-styled confirm pill, both full-width in the
  existing flex column — no new layout class, no modal, no dialog chrome.
- **The `ChannelInfoSheet` container** owns `deleteConfirmOpen` (a `useState` boolean, the
  `renameOpen` twin — ADR 0006, never the store). `onDelete`/`onDeleteConfirm` are supplied only in
  the `conversation !== null` branch (AC1 guard, mirroring `onRename`/`onArchive`); `onDeleteConfirm`
  is the **only** place `window.pyry` is dereferenced (AC5) — it dispatches then calls the
  container's existing `onClose`. `onDeleteCancel` just flips the boolean back, no wire effect.

Button order is now Rename → Archive → Delete, completing the destructive-last convention the
in-file comment at `.channel-info__actions` has documented since #366. The deleted row leaving the
list is #376's job (already merged, wired to the `conversationDeleted` event) — no reflection code
added here.

CSS: two new token-based rules, no new theme tokens. `.channel-info__action--danger` layers onto
the base `.channel-info__action` pill — desktop has only `--color-error` (no error-container fill
token), so the destructive treatment is an **error-tinted outlined** pill rather than filled red:
transparent background, `color: var(--color-error)`, and the 1px outline via
`box-shadow: inset 0 0 0 1px var(--color-error)` rather than `border` (the base pill is
`border: none` with no `box-sizing: border-box`, so a real border would resize it; the inset
shadow adds the outline with zero layout shift). `.channel-info__confirm-text` follows the
`.channel-info__empty` token set for sizing, tinted with `--color-error`.

## Patterns established

- **A third sibling action completes a slot's destructive-last convention without new layout.**
  Rename → Archive → Delete all share `.channel-info__actions`' flex column; Delete's two-step
  confirm swaps in as a sibling render inside the same column rather than a new region — the
  cohesive-optional-props shape (`onDelete`/`deleteConfirmPending`/`onDeleteConfirm`/`onDeleteCancel`,
  supplied as a set or not at all) keeps the pure view server-renderable across both sub-states
  without a discriminated-union prop or a second component.
- **An inline two-step confirm, not a modal, is the desktop posture for a client-invented
  destructive gate with no Figma node** — the #226 (`PermissionModal`'s second-confirm) precedent
  now proven a second time. Chosen over a dialog reusing #360's rename-dialog chrome because it
  needed zero new chrome CSS and stayed fully prop-state-testable under `renderToStaticMarkup`; a
  modal remains a clean drop-in later if a reviewer wants more destructive weight (noted as an open
  question in the spec, not acted on).
- **`box-shadow: inset` is the outline technique for a variant layered onto a `border: none`,
  non-`border-box` base pill** — a real `border` would resize the element; the inset shadow doesn't.
  Worth checking for any future modifier class layered on `.channel-info__action` or a sibling
  pill-shaped base.

## Lessons learned

- Desktop has only `--color-error` (no error-container fill token), so a destructive variant on a
  tonal-pill base can't just swap the fill token the way a filled-red mock might suggest — it has to
  become an outlined treatment instead. Worth checking token inventory before matching a design's
  literal color intent when the design itself (Figma 20:96) doesn't actually show the destructive
  color (see below).
- Figma 20:96 renders Delete as the plain `secondary-container` tonal pill — **no red**. The
  destructive `--color-error` treatment is entirely a client-side invention layered on top of the
  Figma-sourced geometry, not a misread of the design. Distinguishing "the shape is from Figma, the
  color is not" mattered for both the spec and the code review's visual-fidelity check.

## Verified at review time

Code review: **PASS**, one non-blocking NIT (activating Delete unmounts the focused pill and swaps
in the confirm, so keyboard/AT focus drops to `document.body` until the user tabs to Cancel/Delete —
matches the established #226 inline-confirm posture, flagged for a future focus-management pass, no
change required now).

- `npm test` (1707 pass, 3 pre-existing skips), `npm run typecheck`, `npm run build` all clean.
- Server-render assertions on `ChannelInfoSheetView`, anchored on `>Delete</button>` /
  `channel-info__action--danger` (never the shared `.channel-info__action` class, never the bare
  word "Delete" — the confirm prompt copy also contains it as text): pill present (`onDelete` +
  falsy `deleteConfirmPending`); absent for `conversation === null`; absent when `onDelete` is
  omitted despite a populated conversation (proves the gate is the callback, not the data); confirm
  block renders (prompt text + `>Cancel</button>`) when `deleteConfirmPending` is true; the
  pre-existing `not.toContain('Delete')` no-callbacks assertion stays green.
- One direct dispatch test on `requestDeleteConversation`: a spy `sendCommand` called exactly once
  with `{ type: 'deleteConversation', payload: { conversation_id: '<id>' } }`.
- Dispatch-on-confirm and close-on-confirm (the container's `onDeleteConfirm` closure) are not
  click-testable under SSR-only rendering — same as Archive's dispatch-on-click — and are covered
  structurally by the helper test (command shape) plus the pure-view tests (confirm controls
  render), not a fired click.
