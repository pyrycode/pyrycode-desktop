# #379 — Outbound `change_workspace` wire command (transport)

**Shipped:** 2026-07-14 · **Size:** S · **Scope:** `src/shared/wire/`, `src/shared/ipc/`,
`src/main/transport/`, `src/main/daemonConnection.ts`, `src/main/index.ts`.
**Spec:** `docs/specs/architecture/379-change-workspace-transport.md` · **PR:** #386.
Split from #157 (the transport half; the Workspace Picker UI is #157's remaining slice, not yet
built). Security-sensitive (architect self-review PASS, no findings).

Ships **dormant** — fully tested, no consumer. Field-for-field clone of the just-merged
`rename_conversation` slice ([#359](359.md)) across the same five mirror sites, with the second
required string renamed `name` → `cwd`.

## Summary

The daemon shipped `change_workspace` (client → daemon) in pyrycode/pyrycode#823 (merged): a verb
that updates a conversation's recorded workspace (`cwd`) and confirms by **replying** with the
**existing** `conversation_updated` record — no new inbound type. This slice wires the outbound verb
only:

- **Wire type** (`src/shared/wire/types.ts`) — `'change_workspace'` joins `EnvelopeType` beside
  `'rename_conversation'`; `ChangeWorkspacePayload{conversation_id: string, cwd: string}` — two
  required value-strings, wire order `conversation_id, cwd`. The field tag is **`cwd`, not
  `workspace`** — the daemon flagged this as the single reconcile point and the merged daemon uses
  `cwd`, matching `PromoteConversationPayload`/`ConversationCreatedPayload`. Kept a distinct type,
  not an alias of `RenameConversationPayload`.
- **Builder** (new `src/main/transport/changeWorkspaceEnvelope.ts`) — `buildChangeWorkspace`, a
  byte-for-byte clone of `buildRenameConversation`: two required strings means no explicit-`null`
  preservation concern, the payload serializes verbatim. Main-process only (imports `./codec`'s
  `Buffer` use), never re-exported through a renderer barrel.
- **Connection method** (`daemonConnection.ts`) — `changeWorkspace(payload)`, the `send` twin: inert
  no-op when `driver === null`, builds a **fresh literal** naming only `conversation_id`/`cwd` (never
  a spread of `payload` — the anti-smuggling net), shares the one monotonic `nextEnvelopeId` counter
  with `send`/`renameConversation`/etc., never throws out of the module (parity #490) — the caught
  object is dropped, no log, no event (`cwd` is a filesystem-shaped string and must never reach a log
  call on this path).
- **Command** (`src/shared/ipc/commands.ts`) — a new `RendererCommand` member,
  `changeWorkspace{payload: ChangeWorkspacePayload}`, guarded by `isChangeWorkspacePayload` — cloned
  from `isRenameConversationPayload` with the second field's key `name` → `cwd`: both fields
  present-and-string, type checked not emptiness (an empty-string `cwd` passes; the daemon polices
  the path server-side, #823). Structural minimum — a smuggled extra field is accepted here and
  stripped later by the connection method's fresh literal.
- **Dispatch** (`src/main/index.ts`) — a `case 'changeWorkspace':` in the `onCommand` switch, direct
  to `connection.changeWorkspace(command.payload)`, no orchestrator (fire-and-forget, no
  consumer/reassembler) — the exact shape of the `renameConversation` arm.

**No inbound change.** The reply is `conversation_updated`, already decoded (#273) and reacted to by
the existing re-list path (#275) — list-reflect is free, the same path rename/promote/archive/
unarchive already ride. This ticket adds no new inbound decode, correlation, or store change.

**`cwd` is never resolved locally.** Traced end to end by the architect's self-review: type-check →
fresh literal → `encodeEnvelope` → `driver.sendMessage`. No `path`/`fs` call touches it anywhere
on-device; it is carried as opaque wire bytes exactly like `PromoteConversationPayload.cwd`. The
daemon is the sole authority on path validity (#823).

`npm test` (1702 passing, incl. 9 new: builder round-trip + over-cap, guard accept/reject block,
connection no-op/forward/shared-counter/no-throw/fresh-literal), `npm run build` (typecheck +
electron-vite build) both clean.

## Patterns established

- **Reconfirms the "outbound wire-verb slice = 5 files, irreducible S" shape a fourth time** (after
  #241/#273/#346/#359) — the two-field payload costs the same five mirror-site edit set as the
  one-field siblings, not six; the architect's spec recorded this explicitly as a scope self-check so
  code-review didn't need to re-derive it.
- **A two-required-field verb's nearest clone target is the closest *field-count* twin, not the
  closest *domain* twin, confirmed a second time.** `change_workspace` clones `rename_conversation`
  (both carry `conversation_id` + one more required string) rather than the single-field
  archive/unarchive/delete siblings — the same principle #359 established when it cloned promote's
  guard shape over unarchive's.
- **Reaffirms (fifth instance, after #273/#236/#346/#359) that a security-sensitive outbound
  command's connection method must build a *fresh* literal, never spread the caller's payload.** A
  test pins this directly: a smuggled extra key never reaches the serialized wire bytes.
- **A filesystem-path-shaped payload field needs no client-side validation beyond type-checking** —
  the security review's focus (given `cwd` looks like a path, unlike rename's `name`) confirmed the
  desktop never resolves it locally, so the guard stays structural-minimum like every sibling; the
  carry-forward note for its future caller (#157's Workspace Picker) is to source `cwd` from a
  validated folder chooser, not free text — a UX concern for that ticket, not a transport-guard one.

## Lessons learned

None outside the patterns above — code review passed with no findings on the first attempt. This
ticket was a near-mechanical clone of #359's plumbing with one field renamed, main-process/shared
only, no renderer code, no new React/timing surprises. The one thing worth flagging forward: this is
now the **fourth or fifth** time this exact 5-file outbound-verb shape has shipped identically at S
(#241, #273, #346, #359, #379) — if a sixth nearly-identical verb appears, it may be worth asking
whether a shared test-generator/factory for this family is warranted, though no such need has been
observed yet (Evidence-Based Fix Selection: don't build it until a real pain point appears).
