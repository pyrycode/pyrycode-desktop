# #381 — `create_workspace_folder` transport: send create, decode created folder

PR #389 (merged 255754c). Size S, security-sensitive (PASS, no findings). Split from #157. Blocks the
still-unbuilt Create-folder dialog.

## What shipped

The full-vertical transport half of the daemon's new `create_workspace_folder` write verb (pyrycode/pyrycode
#887): a payload-carrying outbound builder that sends `{ parent, name }`, plus a fail-closed decode of the
direct-reply `workspace_folder_created { path }` frame into a dormant, flattened `workspaceFolderCreated`
`DaemonEvent`. No renderer store, no UI — the Create-folder dialog is #157's remaining slice.

This is a 1:1 clone of the `create_conversation` vertical (#241) — both the outbound builder and the inbound
decode are new here, unlike its two `create_workspace_folder`-family siblings (#379 `change_workspace`
reflects through the existing `conversation_updated` broadcast; #380 `recent_workspaces` is inbound-only).
The one deliberate refinement from #241: the reply is single-field, so its event arm flattens to a bare
`path: string` — the `conversationDeleted` (#375) single-field idiom, not `conversationCreated`'s
by-reference reuse.

### Wire contract
- Request `create_workspace_folder`: `{ parent: string, name: string }`, both required. `name` is a single
  folder name; the daemon rejects a separator, `..`, an absolute path, or empty — server-side, not checked
  here.
- Reply `workspace_folder_created`: `{ path: string }`, the created folder's canonical path. **Direct reply
  to the requester** (correlated by `Envelope.in_reply_to`, no broadcast, no `conversation_id`) — the
  `conversation_created` posture, not `conversation_updated`.
- A bad `name` / empty `parent` comes back as a correlated `malformed` daemon error, riding the existing
  generic daemon-error path (#248's rejection-surface mechanism) — no new inbound arm for the reject case,
  symmetric with `create_conversation` (which registers no rejection-correlation state either). Surfacing
  it is #157's job.

## Patterns established / reaffirmed

- **A single-field reply flattens at the `events.ts` emit rather than carrying its wire payload type by
  reference — the `conversationDeleted` idiom now has a second precedent.** `conversationCreated` (#241)
  carries `ConversationCreatedPayload` by reference because it has five fields with nothing to drop;
  `WorkspaceFolderCreatedPayload` has exactly one (`path`), so it flattens like `conversationDeleted{id}`,
  `turnState{state}`, `sessionSettingsUpdated{sessionId}` — keeping `events.ts` free of the payload-type
  import. Code review flagged this as the correct call, not a deviation from the #241 clone target.
- **The ≥5-file split gate's atomicity exception has a fourth precedent** (after #139, #241, #380): a new
  `DaemonEvent` arm and its three `assertNever` bridge consumers must compile together, so there is no
  sub-5-file version that builds. Zero consumer cascade (ships dormant) kept the actual per-edit cost near
  the floor despite the ~10-file count.
- **Reuse `requireString` before adding a new narrower** — both `CreateWorkspaceFolderPayload`'s outbound
  fields and `WorkspaceFolderCreatedPayload`'s one inbound field are plain required strings; no nullable,
  boolean, or enum, so no new decode helper was needed (mirrors #380's `RecentWorkspace` reasoning).
- **A security-sensitive outbound command's guard is a structural minimum; the connection method's
  fresh-literal construction is the real net** — reaffirms #236/#241: `isCreateWorkspaceFolderPayload`
  would tolerate a smuggled extra field, and `createWorkspaceFolder`'s fresh two-field literal (not a
  spread of `payload`) is what actually bounds the wire (AC4-tested at both the decode and the send side).

## Security

Label-gated review, verdict PASS, no findings. Crux: no desktop code path ever constructs a local
filesystem path from `parent`/`name`/`path` — outbound fields are serialized to wire bytes only, inbound
`path` is decoded as an opaque string and emitted as a bare string, never `fs`-/`path.resolve`-d. Path
traversal is structurally impossible because the filesystem is never touched on the desktop; the daemon is
the sole `$HOME`-confinement + clean-name authority (#887's two deterministic server-side gates). The
outbound catch drops on over-cap/driver-throw with no log (the caught object could echo the payload); the
inbound diagnostic log stays content-free (`code`/`bytes`/`hash`, no `path`, no `count`); `WireDecodeError`
messages are category-only, never interpolating `path`. Carry-forward for #157 (Create-folder dialog):
render `path` as plain text only (never `innerHTML`/`dangerouslySetInnerHTML`), never resolve it into a
local filesystem operation, and surface the daemon's `malformed` rejection via the existing #248
rejection-surface path rather than a bespoke channel.
