# #383 — Workspace Picker sheet UI

The UI slice of #157. Split from #157 alongside the transport slices #379 (`change_workspace`) and
#380/#382 (recent-workspaces read); the create-folder dialog is the remaining split-child, #384. PR
#394. Spec: `docs/specs/architecture/383-workspace-picker-sheet.md`. See [Workspace Picker
sheet](../features/conversation-shell.md#workspace-picker-sheet-383) for the full feature write-up;
this file covers implementation notes and lessons.

## Summary

A bottom sheet (Figma node 20-2), opened from the pre-first-message `WorkspaceChip`'s "Change"
button (#278), that lists the recent-workspaces store (#382), marks the active conversation's
current workspace with a "default" pill, and dispatches the existing `change_workspace` command
(#379) on selection. The daemon's `conversation_updated` reply reflects the change into the
conversation list for free — the same re-list path rename/archive/promote already use — so there is
no optimistic update and no extra client request.

Everything the sheet consumes was already merged: the recent-workspaces store + its dormant data-path
bridge (#382), the `changeWorkspace` command (#379), `formatLastActivity` (#141), and the
`.status-sheet__*` chrome (#177/#365). This ticket's only new production code:

- `src/renderer/src/screens/conversation/WorkspacePickerSheet.tsx` (new) — three exports mirroring the
  `ChannelInfoSheetView`/`ChannelInfoSheet` split: the pure `WorkspacePickerSheetView`, the
  `requestChangeWorkspace` dispatch helper, and the in-file `WorkspacePickerSheet` container.
- `src/renderer/src/screens/conversation/ConversationScreen.tsx` — an ~8-line wiring delta: a
  `pickerOpen` `useState` twin of `channelInfoOpen`, `WorkspaceChip.onChange={() =>
  setPickerOpen(true)}`, and the conditional `WorkspacePickerSheet` mount beside `ChannelInfoSheet`.
- `src/renderer/src/screens/conversation/conversation.css` — new `.workspace-picker__*` classes,
  token-only, no new CSS token.

No new command, no new transport plumbing, no store change.

## Patterns established

- **A dormant store + dormant command finding their first real consumer in the same ticket.** #382's
  recent-workspaces store/bridge and #379's `changeWorkspace` command both shipped dormant, months
  apart, each explicitly naming "the not-yet-built Workspace Picker" as its intended caller. This
  ticket is the payoff: both went live in one commit with zero changes to either — the dormant-arm
  pattern (ship the plumbing, document the intended mount point, let a later ticket bind it) worked
  exactly as designed across a three-ticket span.
- **Mount the dormant bridge only while the overlay is open, not app-wide.** `RecentWorkspacesData` is
  a child of `WorkspacePickerSheet`, which itself only renders while `pickerOpen`. A fresh mount per
  open means a fresh `useRef` guard, so every reopen fires exactly one fresh
  `requestRecentWorkspaces` — "re-fetch on reopen" falls out of React's mount/unmount lifecycle for
  free, with no extra staleness-tracking code.
- **Null-vs-empty-vs-populated as three structurally distinct render branches**, not one branch with a
  loading flag — continues the #141/#324 precedent. `workspaces === null` renders the section header
  alone (no spinner — there's no Figma node for one); `workspaces.length === 0` adds a client-owned
  empty line; otherwise, rows. Cheap to keep distinct and cheap to test (three assertions, not a state
  machine).
- **Present-but-disabled as the extension seam, three tickets running.** The "Other" create-folder
  entry ships `disabled={!onCreateFolder}` with the callback omitted — the exact `WorkspaceChip.onChange`
  shape this same ticket un-disabled, itself the `#276 onChannelInfo?` shape. #384 becomes a pure
  additive: pass a handler, nothing else changes.

## Lessons learned

From the PR body:

- `activeConversationStore` is written only on `conversation_created` (never `conversation_updated`),
  so reopening the picker after a successful change still marks the *old* `cwd` until the next create
  — a pre-existing #278 limitation, out of scope here. Worth remembering for any future surface that
  reads this store expecting it to track the active conversation's live state: it's a snapshot from
  the create round-trip, not a subscription to the conversation's current record.

## Code review

PASS, two non-gating NITs (neither required a change):

- The inline folder / folder-plus glyphs render in `--color-on-surface-variant` (muted monochrome)
  where Figma 20-2 shows accent colors (warm salmon / blue) — a deliberate, consistent
  design-system call (every inline glyph in this app renders in `currentColor`/on-surface-variant;
  there is no accent token matching the Figma illustration colors, and hardcoding those hexes would
  violate the token-only rule). Flagged for designer awareness only.
- The create-folder entry's generic `'Create new folder…'` label, versus Figma's parent-specific
  "…under &lt;parent&gt;" — already documented in the spec's Open questions and in-code; deferred to
  #384, which owns the parent resolution.
