# #391 — Push notifications A: main-process delivery primitive

delivery primitive) → [#392](https://github.com/pyrycode/pyrycode-desktop/issues/392) (renderer

UI-visible (OS-drawn notification chrome, no Figma node). Size S.

## Summary

Given a `notify` command from the renderer carrying a closed `kind` (`'turn-complete' | 'prompt'`),
main raises an Electron `Notification` — but only when the main window is unfocused. Ships
**dormant**: nothing sends `notify` yet.

Two invariants enforced **by construction**, per the spec:

1. **Focus is a main-process concept**, queried synchronously at fire-time
   (`mainWindow.isFocused()`) — no stateful tracker, since `isFocused()` is already `false` exactly
   when the notify condition holds (blurred/minimized/hidden).
2. **No daemon-relayed text can reach an OS notification.** The command carries only a closed
   `kind` enum; main owns the copy table mapping `kind` → title/body via
   `Record<NotifyKind, …>`.

Three files changed, one new:

- `src/shared/ipc/commands.ts` — `NotifyKind`/`NotifyPayload` (main-local, defined here not on the
  wire) + `notify` union member + `isNotifyPayload` guard.
- `src/main/fireNotification.ts` (new) — injected-Electron-dependency module (shaped like
  `emitDaemonEvent.ts`), the copy table, the focus gate.
- `src/main/index.ts` — one `case 'notify':` in the single `onCommand` switch, closing
  `mainWindow.isFocused()` and Electron's `Notification` into `fireNotification`.

See [Push notifications](../features/push-notifications.md) for the full feature writeup.

## Patterns established

- **`isNotifyPayload` breaks the sibling `is*Payload` shape on purpose.** Every other guard in
  `commands.ts` checks `typeof value.field === 'string'`, accepting any string. This one tests
  closed-set membership (`kind === 'turn-complete' || kind === 'prompt'`). Call out this divergence
  explicitly in a guard's doc comment whenever a payload's field is a closed enum rather than free
  text — the default `typeof === 'string'` shape is the *wrong* one to clone for an enum field, and
  it's easy to reach for it out of habit.
- **A payload type can be main-local.** Not every `RendererCommand` payload has to reuse
  `../wire/types` — when a command is a pure client-side side effect that never serializes to the
  daemon, define its payload type in `commands.ts` itself (the `AnswerModalCommandPayload`
  precedent, now with a second example).
- **Injected-Electron-dependency shape scales below the transport layer too.** `fireNotification.ts`
  is the same shape as `emitDaemonEvent.ts` — plain function, structural interfaces for the Electron
  types it needs, zero `import 'electron'` — confirming this isn't specific to event emission; it's
  the general pattern for any main-process module that needs an Electron capability but should stay
  Node-testable.

## Lessons learned

From the merged PR body: the real Electron `Notification` satisfies the injected
`OsNotificationConstructor` structurally with **no cast** — its options type is an all-optional
superset of `{ title: string; body: string }`, and `.show()` exists on the real class. This
confirms the spec's open question (flagged as a risk requiring a possible type-widen) resolved
cleanly; no widening was needed. When injecting a structural interface for an Electron type going
forward, expect this to hold rather than defensively widening options to `Partial` up front —
verify against the real type first.

## Open questions carried forward

- **Copy wording is provisional** — `'Your turn is complete.'` / `'Waiting for your response.'` are
  client-invented placeholders (no Figma, no daemon source). Only the shape (static, main-owned,
  keyed by `kind`) is load-bearing; wording can be revisited once #392's trigger makes the feature
  live and the copy is actually seen.
- **No `Notification.isSupported()` gate, no try/catch around construct/`show()`** — both deliberate,
  evidence-based omissions (no observed failure). Revisit only if a platform surfaces one.
