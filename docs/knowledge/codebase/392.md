# #392 — Push notifications B: renderer trigger on turn-end + prompt, toggle-gated

Slice 2 of 3 toward desktop push notifications, split from [#158](158.md): [#391](391.md)
(main-process delivery primitive, merged) → **this** (renderer trigger) →
[#393](393.md) (click-to-focus, merged). Shipped as PR #414 (`b25a0b8`), code-review **PASS**, no
findings. Not security-sensitive (reads already-decoded daemon events, sends a closed-enum
MAIN-LOCAL command that never reaches the transport); not UI-visible (headless bridge, no Figma
node). Size S. Spec: `docs/specs/architecture/392-push-notify-trigger.md`.

This is the piece that makes push notifications live end-to-end: #391 and #393 shipped dormant
because nothing sent `notify` yet. This ticket is that sender.

## Summary

A new filter-bridge, `pushNotifyBridge.ts`, watches the already-decoded `DaemonEvent` channel for
the two notify-worthy moments and, gated by the Settings push toggle ([#408](408.md)), sends the
`notify` command asking main ([#391](391.md)) to raise an OS notification when the window is
unfocused.

Two files changed, one new:

- `src/renderer/src/store/pushNotifyBridge.ts` (new) — three exports:
  - `notifyKindForEvent(event): NotifyKind | null` — a `switch` owning exactly `turnEnd →
    'turn-complete'` and `modalShown → 'prompt'`, `default: null` for everything else. Deliberately
    a **filter**, not an `assertNever` exhaustive switch — it introduces no new `DaemonEvent` arm, so
    it does not force a matching no-op case into `modalBridge`, `timelineBridge`, or
    `daemonEventBridge`. Every `modalShown` is a permission/trust prompt by construction
    (`WireModalClass` admits exactly `'permission' | 'trust'`, ADR 0009 — no destructive class), so
    no class-narrowing filter is needed.
  - `subscribePushNotify(onDaemonEvent, sendCommand, isPushEnabled): () => void` — the React-free
    data path. Filter-first, then toggle: `notifyKindForEvent` short-circuits before the toggle is
    ever read, keeping "every other daemon event no-ops" true regardless of toggle state. Sends an
    inline `{ type: 'notify', payload: { kind } }` literal — no `notifyCommand()` helper added (the
    `requestNewConversation` precedent). Returns the `onDaemonEvent` off-handle as cleanup.
  - `usePushNotify(): void` — an empty-dep `useEffect` closing `window.pyry.onDaemonEvent`,
    `window.pyry.sendCommand`, and a thunk reading
    `pushNotificationPrefStore.getState().pushNotificationsEnabled`. No `useRef` (unlike
    `useNotificationActivatedNav` / `useConversationCreatedNav`) — all three deps are module-level
    singletons, so the effect closure needs no per-render callback ref.
- `src/renderer/src/PairedShell.tsx` — one mount, `usePushNotify()`, beside
  `useNotificationActivatedNav`.

`npm test` (1918 pass, +11 new), `npm run typecheck`, `npm run build` all clean.

## Patterns established

- **`isPushEnabled` is a per-event thunk, not a captured boolean.** Passing `() =>
  store.getState().field` instead of `store.getState().field` at subscribe time is what makes a
  mid-session Settings flip take effect on the very next event — the sibling bridges that read
  static config at subscribe time don't need this because they have no analogous live toggle. Worth
  reaching for whenever a bridge's behavior must react to a store value that changes between
  subscribe and each event, not just at mount.
- **A filter-bridge can drop the `useRef` ceremony its siblings use.** `useConversationCreatedNav` /
  `useNotificationActivatedNav` hold a per-render caller callback in a `useRef` because the caller
  supplies a fresh closure each render. `usePushNotify` takes no caller callback — every dependency
  (`window.pyry.*`, the pref-store thunk) is a module-level singleton — so the ref is dead weight
  here. When a new bridge hook has no per-render argument, skip the ref.
- **Filter-first-then-toggle ordering matters for correctness, not just efficiency.** Checking
  `notifyKindForEvent(event) === null` before consulting `isPushEnabled()` isn't just an
  optimization — it's what keeps "every other daemon event no-ops, full stop" true independent of
  toggle state, which is exactly what AC4 asserts.

## Lessons learned

No PR-body "Lessons learned" section was included and no open question was carried forward — the
architecture spec confirmed both landed dependencies (#391, #408) against current `main` before
design, and the implementation is a direct clone of the `notificationActivatedBridge` /
`conversationCreatedBridge` shape with no structural surprises. The one deliberate simplification
(dropping `useRef`) was already called out as intentional in the spec, not discovered during
implementation.
