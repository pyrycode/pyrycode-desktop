# #393 — Push notifications C: clicking a notification focuses the window and shows the conversation

Slice 3 of 3 toward desktop push notifications, split from [#158](158.md): [#391](391.md)
(main-process delivery primitive, merged) → [#392](https://github.com/pyrycode/pyrycode-desktop/issues/392)
(renderer trigger, blocked on the interactive stream #353, still open) → **this** (click-to-focus).
Shipped as PR #400, code-review PASS, no findings. Not security-sensitive (no socket/key/token/wire
frame touched; the click originates from a local OS notification, not a relay peer); not UI-visible
(no new visual surface — reuses the existing thread screen and the existing `open` transition). Size
S. Spec: `docs/specs/architecture/393-notification-click-focus.md`.

Ships **dormant** — #392 (the trigger that causes a real notification to fire) is still open, so
this slice is exercised only with a fake notification + fake window in tests.

## Summary

Makes the [#391](391.md) OS notification actionable. On click:

1. The main process activates the window — `restore()` if minimized, `show()`, then `focus()` — via
   a new injected `activateWindow(win: ActivatableWindow)` helper (AC1).
2. The main process emits a new nullary `{ type: 'notificationActivated' }` `DaemonEvent` (AC2/AC3).
3. A new renderer filter-bridge (`notificationActivatedBridge.ts`) consumes it and dispatches the
   existing `open` nav in `PairedShell`, landing on the `thread` view regardless of which paired view
   (list / settings / archive) was showing.

Five files changed, one new:

- `src/main/fireNotification.ts` — `OsNotification` widened with `on(event: 'click', listener: () =>
  void): void`; `fireNotification`'s `deps` gained `onClick: () => void`, registered on the
  notification **before** `.show()` (a click could arrive the instant it's shown). New, co-located
  `ActivatableWindow` interface + `activateWindow(win)` function: `if (win.isMinimized())
  win.restore(); win.show(); win.focus()`.
- `src/main/index.ts` — the sole composition site (the `notify` case, alongside the existing
  `isWindowFocused`/`Notification` injection): `onClick: () => { activateWindow(mainWindow);
  emitDaemonEvent(mainWindow, { type: 'notificationActivated' }) }`. `mainWindow` satisfies both
  `ActivatableWindow` and `DaemonEventSink` structurally.
- `src/shared/ipc/events.ts` — one new bare arm, `{ type: 'notificationActivated' }`. Doc comment
  flags it as the **first main-local signal** on the `DaemonEvent` channel — not derived from a
  validated wire envelope, but emitted directly by the main-process click handler.
- `src/renderer/src/store/notificationActivatedBridge.ts` (new) — `subscribeNotificationActivated`
  (inlined `event.type === 'notificationActivated'` filter, no payload to translate) +
  `useNotificationActivatedNav` (the `useConversationCreatedNav` React-glue shape: latest-callback
  ref, empty-dep effect, off-handle cleanup).
- `src/renderer/src/PairedShell.tsx` — one mount: `useNotificationActivatedNav(() => dispatch({ type:
  'open' }))`, beside `useConversationCreatedNav`. Deliberately **no** `setActiveConversation` — the
  arm is nullary; in the single-active-conversation model, "open" already means "show the existing
  active conversation's thread."
- `daemonEventBridge.ts` / `timelineBridge.ts` / `modalBridge.ts` — one-line `case
  'notificationActivated':` no-op each, compile-forced by the `assertNever` exhaustiveness guard.

`npm test` (122 files, 1811 pass, 3 pre-existing skips), `npm run typecheck`, `npm run build` all
clean.

## Patterns established

- **A main-process click handler can be the sender on a channel documented as wire-only.**
  `emitDaemonEvent.ts`'s header says "nothing else sends on the channel" — this ticket adds the first
  exception, and the chosen mitigation was to note it at the **arm's own doc comment** in
  `events.ts`, not edit `emitDaemonEvent.ts` itself. When a future ticket needs another
  main-local (non-wire) signal on this channel, check `events.ts` for this precedent before treating
  the emitter's "nothing else sends" comment as an invariant to preserve — it now means "nothing else
  *wire-derived* sends."
- **A nullary arm needs no `translate` function.** Every prior consumer bridge (`conversationCreatedBridge`,
  the session/timeline/modal bridges) returns a translated payload or action. Because
  `notificationActivated` carries nothing, `subscribeNotificationActivated` inlines the type-guard
  directly in the subscription callback instead of factoring out a `translateX(event): Y | null`
  — the right shape when an arm's only job is "did this specific event happen," not "what data did it
  carry."
- **Reused an existing absolute nav transition instead of adding one.** Because `nextPairedRoute`'s
  `open` arm was already unconditional (any route → `thread`), a second trigger for it needed zero
  changes to the reducer — the same bet `#333`/`#347` cashed for `back`. Worth checking whether a new
  trigger can reuse an existing transition before reaching for a new nav arm.

## Lessons learned

From the merged PR body: **Open Question #1 resolved cleanly, no cast needed.** The spec flagged a
risk that Electron's real `Notification.on('click', …)` (an `EventEmitter` overload returning `this`,
with a wider one-arg listener) might not structurally satisfy the injected `OsNotification.on(event:
'click', listener: () => void): void`. `npm run typecheck` confirmed it does — `this → void` and a
zero-arg listener assignable to a one-arg listener are both sound TS assignability, no `as` cast
required. This is the same "verify the real Electron type before defensively widening" lesson #391
already banked for `OsNotificationConstructor`; now confirmed a second time for an `EventEmitter`
method, not just a constructor.

## Open questions carried forward

None — both open questions from the spec (the structural typecheck; the `restore()`→`show()`→`focus()`
sequence) resolved during implementation and are pinned by tests (`activateWindow` un-minimizes +
shows + focuses; shows + focuses without `restore` when not minimized).
