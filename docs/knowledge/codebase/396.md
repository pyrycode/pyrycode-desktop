no findings). Split-child A of [#384](384.md) (Create-folder dialog). Blocks
[#397](https://github.com/pyrycode/pyrycode-desktop/issues/397) (round-trip store), which blocks
[#398](https://github.com/pyrycode/pyrycode-desktop/issues/398) (dialog UI). Spec:
`docs/specs/architecture/396-correlate-create-workspace-folder-rejections.md`.

Ships **dormant** — correlated and emitted, no renderer subscriber yet. The rejection-path twin of
[#381](381.md)'s `workspace_folder_created` success decode.

## Summary

[#381](381.md) shipped `create_workspace_folder`'s outbound request and its `workspace_folder_created`
success reply, but not the rejection path. When the daemon rejects a bad name (a path separator, `..`,
an absolute path, or empty), it returns a **content-free** `error` frame correlated only by
`Envelope.in_reply_to` — the same undiscriminated shape used for a bundle failure, a `set_session_settings`
rejection, or a `modal_answer` rejection. Nothing previously attributed that frame to an outstanding
create-folder request, so the renderer could never learn the request failed.

This slice clones the `set_session_settings` rejection machinery (#269, itself layered on #261/#248)
already living in `src/main/daemonConnection.ts`:

- **New correlation memory** — `pendingCreateFolders: Set<number>`, envelope ids of outstanding
  `create_workspace_folder` requests. A `Set`, not a `Map` like `pendingSettings`: the emitted event is
  bare, so only membership matters. Recorded *after* a successful `driver.sendMessage` inside
  `createWorkspaceFolder` (captured `envelopeId = nextEnvelopeId` before the build), so a build/send
  throw leaves no phantom entry — the `setSessionSettings`/#269 order.
- **New `DaemonEvent` arm** — `{ type: 'workspaceFolderRejected' }` (`src/shared/ipc/events.ts`), the
  rejected twin of `workspaceFolderCreated` (#381). **Bare** — carries nothing at all, stronger than
  `sessionSettingsRejected`'s `changeId` or `modalAnswerRejected`'s `modalId`: only one create-folder
  dialog is ever open, so there is no concurrency to disambiguate.
- **Match site** — `case 'daemon-error':` now checks `pendingCreateFolders.has(inReplyTo)` alongside the
  existing `pendingSettings` check, inside the same `inReplyTo !== undefined` guard. A match deletes the
  entry, emits the bare rejection, and `return`s *before* both `reassembler?.fail('daemon-error')` and the
  `outstandingAnswers.shift()` modal FIFO — the same precedence #269 established for settings rejections,
  since an envelope id is minted once and can be held by at most one of the two sets.
- **Reset site** — `dial()` clears `pendingCreateFolders` next to `pendingSettings.clear()`: a reconnect
  abandons outstanding create-folder requests, so a stale id from a dead session can never correlate on
  the reconnected one (ids recycle from 2).
- **Three exhaustive renderer bridges** — `daemonEventBridge.ts` / `modalBridge.ts` / `timelineBridge.ts`
  each gained a one-line `case 'workspaceFolderRejected'` no-op, compile-forced by the `assertNever`
  guard (the `workspaceFolderCreated`-was-a-no-op precedent).

`npm test` (10 new cases in `daemonConnection.test.ts` cloning the `sessionSettingsRejected` describe
block: correlated match, delete-on-match, absent `in_reply_to` short-circuit, non-matching id
fall-through, bundle-not-failed precedence, modal-FIFO-untouched precedence, no-echo bare-shape pin,
`dial()` clear, send-throw leaves no phantom entry, three bridge no-ops), `npm run typecheck` clean.

## Patterns established

- **A `Set<number>`, not a `Map`, is the right correlation primitive when the emitted event is bare.**
  `pendingSettings: Map<number, string>` exists because `sessionSettingsRejected` must carry the
  `changeId` back; `pendingCreateFolders: Set<number>` needs no value because
  `workspaceFolderRejected` carries nothing — membership alone answers "is this envelope id an
  outstanding create-folder request?". Distinguishes both from `outstandingAnswers: string[]` (a FIFO,
  used only when the reply carries no discriminating id at all — a create-folder request's envelope id
  *is* discriminating, so a keyed set beats a FIFO here).
- **A second precedent for "insert into the existing `daemon-error` precedence ladder, in the
  unique-per-request-id tier, ahead of the bundle-fail / modal-FIFO tier."** #269 established the shape
  (correlate first, consume-and-return on match, unchanged fall-through on no match); this ticket adds a
  second, independent lookup at the same tier rather than a new ladder rung — order between the two
  unique-id checks is immaterial since an envelope id is minted once and can appear in at most one set.
- **Bare (zero-field) events are the strongest content-minimisation posture available, and are correct
  precisely when there is no concurrency to disambiguate.** `modalAnswerRejected{modalId}` and
  `sessionSettingsRejected{changeId}` each carry a client-owned nonce because multiple same-kind requests
  can be outstanding at once; `workspaceFolderRejected` carries nothing because the product only ever
  opens one create-folder dialog at a time — the success twin `workspaceFolderCreated{path}` sets the
  symmetry precedent (no correlation key either, just the minimum success payload).

## Security

Label-gated review, verdict PASS, no findings. Crux: the only untrusted→trusted crossing is the inbound
`daemon-error` frame (already content-free at parse, `inboundMessage.ts` strips `ErrorPayload` text
before this module ever sees it); this slice reads only the numeric `inReplyTo` for a `Set.has` lookup
and emits a bare event — no code, message, path, or wire id can ride it, by construction. A hostile
daemon forging an `error` whose `in_reply_to` matches a *real* outstanding create-folder request can
trigger a spurious content-free rejection, but the daemon can reject any request it likes anyway (within
its existing authority) — worst case is an incorrect "couldn't create that folder" signal with zero data
disclosure. A forged id matching nothing the client sent for create-folder misses the `Set` and falls
through unchanged. No new IPC channel, no new async task/timer, no crypto, no filesystem/path touch.
