## Summary

Introduces a client-owned "push notifications when claude responds" on/off preference, persisted
locally, structurally cloning [defaultWorkspaceStore](../features/default-workspace-store.md) (#403)'s
injected-storage-port idiom. One new file pair (no existing file touched):

- **NEW `src/renderer/src/store/pushNotificationPrefStore.ts`** — a dedicated Zustand store (the
  `defaultWorkspaceStore` DI-factory → singleton → hook → selector shape) holding a bare `boolean`,
  hydrated once at construction from an injected `PushNotificationPrefStorage` port
  (`read(): boolean | null`, `write(value: boolean): void`) and set-through via
  `setPushNotificationsEnabled` (persist-then-record). `localStoragePushNotificationPref()` is the real
  backend, key `pyry.pushNotificationsEnabled` — the app's **second** `localStorage` key, sibling to
  `pyry.defaultWorkspace` — guarded by `typeof window === 'undefined'` for `node`/SSR import safety,
  mirroring `localStorageWorkspacePref` exactly.
- **NEW `src/renderer/src/store/pushNotificationPrefStore.test.ts`** — clones
  `defaultWorkspaceStore.test.ts`'s `fakeStorage()` closure-with-`vi.fn`-spies idiom, plus a dedicated
  block for the extracted `encodePushPref`/`decodePushPref` helpers (see Deltas below).

No IPC command/event, no preload wiring, no `isRendererCommand` guard — same renderer-contained
posture as #403.

## The two deltas vs. the #403 precedent

1. **Boolean with a meaningful default-on-empty.** `defaultWorkspace` treats absence as *itself* the
   value (`null` = "no default set"). Here absence must resolve to **enabled** (the mobile knob's
   on-position, Figma 17-68). The mapping — `storage.read() ?? PUSH_NOTIFICATIONS_DEFAULT_ENABLED` —
   lives at store construction, not in the port: the port stays a faithful "what's persisted" reporter
   (`boolean | null`), and the default is one exported `const` (`PUSH_NOTIFICATIONS_DEFAULT_ENABLED =
   true`), not duplicated at each read site.
2. **Serialization + a not-set-vs-stored-`false` sentinel, extracted as pure functions.**
   `localStorage` only holds strings, so the boolean is encoded/decoded via `encodePushPref`/
   `decodePushPref` — extracted (unlike `defaultWorkspaceStore`'s inline `getItem`/`setItem`, which
   pass a `string | null` straight through) because the coercion is a correctness trap the vitest
   `node` runtime cannot exercise through the real, `window`-guarded port: under `node`,
   `localStoragePushNotificationPref().read()` always short-circuits to `null` before ever reaching
   `decodePushPref`. Extracting the pure function lets `decodePushPref(null)`, `decodePushPref('false')`,
   `decodePushPref('true')`, `decodePushPref('garbage')` be pinned directly. `decodePushPref` recognizes
   **exactly** the two strings `encodePushPref` emits; anything else (`null` or a corrupt/hand-edited
   value) maps to `null` — "not a valid persisted value" — which is what keeps "never set" distinguishable
   from an explicit stored `false`, so a user who toggled off is not silently re-enabled on next launch.

## Patterns established

- **The second use of the #403 injected-storage-port idiom confirms it's a reusable house pattern, not
  a one-off.** Any future renderer-local persisted preference should clone this shape (port interface →
  `read`/`write` seam → `node`-safe `typeof window` guard → DI-factory → singleton → hook → selector)
  rather than inventing a variant.
- **When a value needs string coercion for storage, extract the coercion as named pure functions and
  test them directly**, rather than leaving it inline inside the port. The `node` test runtime can't
  reach a `window`-guarded port's internals, so any correctness-sensitive coercion logic living only
  inside the port is untestable in this repo's test environment. `defaultWorkspaceStore`'s `string |
  null` didn't need this (no coercion, just pass-through); a `boolean` did.
- **Map a domain default (e.g. "empty means enabled") at the store, not the port.** Keeps the port a
  simple, honest "what's on disk" reporter and keeps the default a single source of truth instead of
  smeared across read call sites.
- **Do not extract a shared key-namespacing helper on the second key.** Both this ticket and #403's own
  comment agree: `pyry.<name>` by convention is enough at two instances; a helper is deferred to a
  genuine third case (no premature abstraction, per CLAUDE.md).

## Security

Not security-sensitive, confirmed by code review: a non-secret UX boolean in renderer-local storage.
No key material, token, socket, or wire frame touched. No new IPC surface, no boundary guard, no
transport code.
