## Summary

Adds the Settings screen's fourth section, "Notifications" (Figma 17:62 header / 17:64 row),
inserted between the existing Defaults and Storage sections. One new file, two edited:

- **NEW `src/renderer/src/screens/settings/PushNotificationRow.tsx`** — the `ArchivedCountRow`
  two-part idiom (pure view + store-bound Control), plus one callback prop the `ArchivedCountRow`
  lacks. `PushNotificationRowView({enabled, onToggle})` renders a text column (the Figma-verbatim
  label "Push notifications when claude responds") beside a native `<button type="button"
  role="switch">` carrying `aria-checked={enabled}`, `aria-label={PUSH_TOGGLE_LABEL}`, and a
  decorative `aria-hidden` knob span. `PushNotificationRowControl` reads
  `usePushNotificationPrefStore(selectPushNotificationsEnabled)` and wires `onToggle` to
  `pushNotificationPrefStore.getState().setPushNotificationsEnabled(next)`, dereferenced inside the
  callback only — never at render, never a two-way binding.
- **NEW `src/renderer/src/screens/settings/PushNotificationRow.test.tsx`** — the
  `renderToStaticMarkup`/`node` harness (`DefaultWorkspaceRow.test.tsx`/`ArchivedCountRow.test.tsx`
  idiom). Three cases: enabled → `aria-checked="true"` + `settings__switch--on` present; disabled →
  `aria-checked="false"` + that class absent; both states render `role="switch"` + the label text.
  A fourth assertion (`<button` + `type="button"` present) is the deterministic structural proxy for
  the keyboard-operability AC — the harness cannot dispatch key events, so "it's a native button, not
  a click-only span" is asserted by construction instead.
- **EDIT `SettingsScreen.tsx`** — adds `notifications: 'Notifications'` to `SETTINGS_COPY`, imports
  `PushNotificationRowControl`, and mounts a new `<section className="settings__section">` between
  the Defaults `</section>` and the Storage section, matching the Figma vertical order (Notifications
  y=610 above Storage y=910).
- **EDIT `settings.css`** — adds `.settings__notifications-row` / `-text` / `-label` (mirroring
  `.settings__storage-row` geometry) plus `.settings__switch` / `--on` / `-knob` + a
  `:focus-visible` ring, cloned from `conversation.css`'s `.run-config__switch` family and adapted
  for a `<button>` (button-reset, unconditional `cursor: pointer` — no read-only variant here).

No data path added — reads `selectPushNotificationsEnabled` and writes
`setPushNotificationsEnabled` on the existing [#408](408.md) store; no new store, bridge, reducer,
or discriminated union.

## The keyboard-operability delta vs. the run-config switch precedent

The nearest prior accessible-switch markup, `run-config__switch` in
`RunConfigSections.tsx`, is a `<span role="switch">` wired only to `onClick` — focusable but not
keyboard-operable, since Space/Enter do nothing on a `<span>` with no `onKeyDown`. This ticket's
keyboard AC required real Space/Enter activation, so the architect spec called for a native
`<button role="switch">` instead of cloning the span verbatim: a native `<button>` fires its
`onClick` on both Space and Enter with zero extra wiring. The CSS clone therefore needed a button
reset (`appearance: none; margin: 0; padding: 0; font: inherit`) that the span original didn't need,
following the `.settings__back` / `.settings__pair-another-row` button-reset idiom already present
in `settings.css`.

## Accessible name

`role="switch"` computes its accessible name from the author, not from sibling content — and the
switch button is a *sibling* of the label `<p>`, not its parent, so there is no implicit
label-wraps-control relationship. The row sets an explicit `aria-label={PUSH_TOGGLE_LABEL}` on the
button, reusing the same module-level copy constant the visible `<p>` renders, so the accessible
name and the visible label can never drift apart (a single source of truth, not two copies of the
same string to keep in sync).

## Patterns established

- **Keyboard-operable accessible switch = native `<button role="switch">`, not `<span
  role="switch" onClick>`.** The run-config switch (pre-existing) is click-only; this ticket is the
  first to need real keyboard operability, and the fix was a tag change plus a button reset — no
  `onKeyDown` handler was written or needed. Any future switch in this app should default to a
  `<button>`, not a `<span>`, for this reason.
- **Client-owned copy shared between the visible label and its `aria-label` twin via one constant**,
  rather than duplicating the string — the `SERVER_ROW_LABEL` idiom, now also proven for a
  sibling-not-parent label/control relationship.
- **Clone-not-reuse across screens for CSS still holds at three points of confirmation now**
  (`.settings__storage-row` not reusing `.settings__server-row`, `.settings__default-workspace-row`
  fusing two prior idioms rather than importing one, and now `.settings__switch*` cloned from
  `conversation.css` rather than importing `run-config__switch`) — the client-owned-copy idiom is a
  settled house convention for this codebase, not a one-off judgment call.

## Testing

Reflect matrix proven on the pure `PushNotificationRowView` with injected props only — never the
store singleton (`DefaultWorkspaceRow`/`ArchivedCountRow` precedent). Not tested here, by design:
the Control's store-write wiring (`onToggle` → setter) is unreachable under `renderToStaticMarkup`
(no click) — reviewed glue, the `DefaultWorkspaceRow` `onChoose` precedent; the persist-across-restart
round-trip is [#408](408.md)'s already-tested responsibility, inherited, not re-tested here.

## Security

Not security-sensitive: no keys, sockets, tokens, or wire frames. No security-review pass (confirmed
at spec time and unchanged by the shipped diff).
