# #415 — Reconnect reconcile (renderer): clear the outstanding modal slice on re-handshake

PR #417 (`da0e0ea`). Split-child A of #196 (2-way split; sibling #197 owns the separate `queue_state`
reconnect reset, out of scope here). Size S, as estimated. Not security-sensitive (renderer-only,
reacting to an already-typed/decoded `connected` event). Not UI-visible in the Figma sense — pure
reducer + bridge, modal design already locked at #122/#224. Code review: PASS, no blocking findings.

## Summary

Applies the daemon's connect-time reconcile contract (pyrycode/pyrycode#877, wire pyrycode/pyrycode#879)
to the renderer's modal store. The relay supervisor re-emits `connected` on every (re)handshake — v2 has
no session resume — and the daemon now re-sends every still-outstanding `modal_shown` prompt right after.
Before this ticket nothing reset `outstanding` across that boundary, so a reconnect could leave a stale,
already-resolved prompt frozen on screen (the user could still try to answer it), or silently miss one
that had been raised while the connection was down.

Two edits, both additive:

- **`modalBridge.ts`** — `connected` moves out of the shared fall-through group (previously grouped with
  `connecting`/`disconnected`/etc., all → `null`) into its own case, returning a new payload-free
  `{ type: 'reconnected' }` `ModalEvent`. `event.ack` (`HelloAckPayload`) is ignored — the reset needs
  nothing from it. The `assertNever` guard over `DaemonEvent` stays load-bearing because `connected` was
  *removed* from the fall-through list, not just handled twice.
- **`modalPrompts.ts`** — new `{ type: 'reconnected' }` arm on `ModalEvent`, and a `reduceModal` case:
  same-state-reference no-op when `outstanding` is already empty (AC4 — covers first-connect and a
  reconnect after everything already resolved), else `{ ...state, outstanding: [] }`. The spread is what
  preserves `resolved` ([#195](195.md)) and `rejections` ([#249](249.md)) by reference untouched.

Repopulation is not this ticket's code — it falls out of the already-shipped #195 `shown` arm for free:
after the reset `outstanding` is empty, so a re-sent still-held prompt appends fresh (exactly once, no
duplicate), and an optimistically-answered prompt's `modalId` is still in the preserved `resolved` slice,
so the `shown` arm's resolved-first early-out keeps it suppressed even though the daemon re-sends it.

Ordering (reset-before-repopulate) is a transport-level guarantee outside this diff, not something this
ticket had to build: `daemonConnection.ts` emits `connected` at handshake-complete strictly before its
inbound loop re-sends `modal_shown`, and the single daemon-event channel delivers in arrival order. The
architect's spec confirmed no reordering seam in the renderer path; this ticket did not need to add any
ordering logic of its own.

8 new vitest cases (6 reducer, 2 bridge) — clears `outstanding`; resolved-while-away stays cleared;
`resolved`/`rejections` survive by reference; empty-`outstanding` returns the same reference for both
first-connect and reconnect-after-resolved; a re-sent still-held prompt surfaces exactly once; an
optimistically-answered prompt stays suppressed across the reset; the bridge translates `connected` →
`{ type: 'reconnected' }`; `connected` removed from the bridge test's "every other arm → null" fixture
array (leaving it there would have made that test fail after the flip). `npm test` (1926 pass, 3
pre-existing skips), `npm run typecheck`, `npm run build` all clean.

## Patterns established

- **A reconnect reset arm needs no payload and touches exactly one slice** — `{ type: 'reconnected' }`
  carries nothing off the `connected` ack, and the reducer clears only `outstanding` while spreading
  every other slice through by reference. When a future slice needs the same daemon-reconcile-on-connect
  treatment (per #196's original scope — see #197), the shape to mirror is: bare event, one slice
  cleared, everything else preserved via `{ ...state, thatSlice: [] }`.
- **Repopulation-for-free is a reason to keep a reset arm minimal.** Because `shown` was already made
  idempotent by #195 before this ticket landed, the reset didn't need to special-case "prompt still
  outstanding" vs. "prompt resolved-while-away" — clearing and letting re-delivery re-populate through
  the existing idempotent arm is strictly simpler than trying to diff old-vs-new outstanding sets in the
  reset itself.
- **Moving a `DaemonEvent` case out of a shared fall-through group, not just adding a new case, is what
  keeps `assertNever` honest.** `connected` had to be deleted from the fall-through's case list, not left
  duplicated — a case label can't appear twice in a `switch`, so this is enforced by the compiler, but the
  bridge test's parallel "every other arm" fixture array required the matching manual edit (removing
  `{ type: 'connected', ack }` from it) since that list isn't type-checked against the switch.

## Lessons learned

None — no PR-body Lessons-learned section, and code review found nothing that changed the implementation
(its one NIT was a test-isolation observation about which reset path a specific fixture exercises,
explicitly flagged as not worth a change since aggregate coverage across the other new tests already
proves the spread path). The architecture spec's design mapped onto the diff with no deviation.
