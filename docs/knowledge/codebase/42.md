# #42 — Secure key store over Electron `safeStorage`

**Shipped:** 2026-07-03 · **Size:** S · **Scope:** background process only (`src/main/`) · greenfield primitive, zero consumer cascade · **no new dependency** (`safeStorage` ships with `electron`; `node:fs/promises`/`node:path`/`node:crypto` are built-ins).
**Spec:** `docs/specs/architecture/42-secure-key-store-safestorage.md` · **PR:** [#45](https://github.com/pyrycode/pyrycode-desktop/pull/45) (`security-sensitive`; review: **PASS**, no MUST/SHOULD/NIT findings — architect security-review pass + a code-review adversarial pass over the diff).

The **secret-at-rest primitive** underneath every long-lived desktop secret: a generic, key-domain-blind `set`/`get`/`delete` over named `Uint8Array` blobs, encrypted at rest with the OS keychain via Electron `safeStorage`. The device static private key (#43), the paired-server record (#44), and later pairing state are all *consumers* that serialize their own structures to bytes and store them by a string name — this ticket ships only the blind byte store underneath them. It is the desktop equivalent of mobile's Android Keystore / `EncryptedSharedPreferences` layer. See the [secure-store feature doc](../features/secure-store.md) for the full contract and [ADR 0005](../decisions/0005-secret-at-rest-safestorage-fail-closed.md) for the decision.

Scope lock held: **the storage primitive only.** No key-domain semantics, no Noise, no wire types, no serialization of key-domain structures (consumers own that). Fail-closed when the keychain is unavailable — **never** a plaintext fallback. Zero renderer / preload / IPC surface. `src/main/index.ts` is **untouched** — the composition-root wiring of a live store is deferred to the first consumer ticket (#43/#44), exactly as #21/#22 left `index.ts`.

## Patterns established

- **A security boundary is a small blind primitive over injected effectful edges.** The at-rest guarantee is carried by *one* auditable surface (`createSecureStore`) that knows nothing about what the bytes mean — mirroring `relayConnection`'s "semantics-blind byte pipe". Both effectful edges (keychain, filesystem) are **injected interfaces** (`SecretEncryption`, `SecretPersistence`), so the pure core unit-tests with fakes and no real keychain/fs — the `relayConnection` `onEvent` DI seam ([#21](21.md)) applied to the secret boundary. Reuse this shape for any future security-property-bearing primitive: prove the property once in a blind core, ship the effectful reality as thin adapters.
- **Isolate the effectful adapters into their own files so each test graph stays clean.** `electronSecretEncryption.ts` is the *only* module that imports `electron`; `fileSecretPersistence.ts` is deliberately split from it so *its* test module graph is electron-free too. This makes "the AC-required tests run without a keychain" a **structural** guarantee, not an incidental one — the core's test never transitively pulls in `electron` or `fs`.
- **Fail-closed is an ordering invariant, asserted by a test.** `set` checks `encryption.isAvailable()` **before** any persistence call — availability-check → encrypt → persist. The unavailable-path test asserts `persistence.write` was **never called** and `encrypt` never ran, so "plaintext never hits disk" is proved by construction, not hoped. The template for any fail-closed write path: gate first, and test that the gated resource stays untouched.
- **Close path traversal structurally, not by validation.** The secret name is base64url-encoded (`[A-Za-z0-9_-]`, no `/`/`.`/`..`) before it is ever a path segment — a name like `../../etc/passwd` maps to an inert `.bin` token inside `dir`. No blocklist, no name validation, no observed-failure defense: the encoding is a bijection that *cannot* produce a separator. Prefer a structural impossibility over a filter every time.
- **Atomic secret writes: unique-temp + rename, never write-in-place.** `writeFile(tmp.<randomhex>.tmp)` then `rename` — atomic on the same filesystem, so a crash mid-write leaves the prior file intact or the new file whole, never a truncated secret; a unique temp suffix stops two concurrent same-name writes clobbering a shared temp. Per-name file isolation (one file per secret) means different-name ops never race — deliberately avoiding a single-JSON-map's read-modify-write hazard.
- **Re-used the transport modules' security discipline verbatim:** **log-free by construction** (no `console.*` anywhere — a stray log would leak a secret value to main-process stdout); a **static error message** (`EncryptionUnavailableError` carries no secret, name, or value); secrets held only as **opaque `Uint8Array` locals**, never named fields of a logged struct (sidesteps the KitchenClaw `GatewaySettings` `toString` leak by design); and **zero renderer/IPC surface** (main-process only — a renderer compromise gains no path to the store).

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **`safeStorage` round-trips through UTF-8, so the byte↔string bridge must use base64, not `latin1`.** `safeStorage.encryptString(s)` encodes `s` as UTF-8 and `decryptString` returns a UTF-8 string. base64's alphabet is pure ASCII (`< 0x80`), so arbitrary bytes survive the round-trip byte-for-byte. A `latin1`/`binary` string would re-encode any byte `>= 0x80` as a 2-byte UTF-8 sequence and **silently corrupt** on the way back. The ~33% size inflation on small secrets is negligible and correct. (The opaque/empty-bytes core test round-trips `[0x00, 0x80, 0xff, 0x7f]` precisely to guard this encoding assumption.)
- **On Linux with no keyring, `safeStorage.isEncryptionAvailable()` can return `true` for a `basic_text` backend that is obfuscation, not encryption** (hardcoded key). A fail-closed store must additionally reject `process.platform === 'linux' && safeStorage.getSelectedStorageBackend() === 'basic_text'` and treat it as unavailable — otherwise it silently stores weakly-obfuscated secrets while reporting success. `getSelectedStorageBackend` is Linux-only, so guard the call behind the platform check.
- **A good fake encryption must make ciphertext observably ≠ plaintext (and empty input non-empty), and throw on a foreign blob.** The in-file `fakeEncryption` prefixes a marker byte then XORs the payload, so a round-trip is observable, "stored value is ciphertext not plaintext" is provable even for a 0-byte secret, and `decrypt` throws when the marker is missing — standing in for `safeStorage`'s authenticated-decryption failure. Without the throw-on-foreign-blob behaviour, the "decrypt-failure propagates, not masked as absence" test would pass vacuously. When faking a security seam, replicate the *failure* contract, not just the happy path (the [#22](22.md) send-guard lesson, again).

## Deferred (open questions carried forward)

- **Composition-root wiring.** Nothing constructs a live `createSecureStore` yet; `src/main/index.ts` stays untouched. The first consumer (#43/#44) wires `electronSecretEncryption()` + `fileSecretPersistence(join(app.getPath('userData'), 'secrets'))` — the production `dir` is computed by the consumer, so the fs adapter needs no `app` import.
- **Decrypt-failure recovery policy.** The primitive *propagates* decrypt failures (honest). Whether a failure means "delete + re-pair" (the KitchenClaw corrupted-prefs recovery pattern) or "hard error" is a **consumer** decision, deliberately not baked into the blind primitive — auto-deleting here would risk a tamper→forced-downgrade path.
- **Stale `.tmp` sweep.** A hard kill between `writeFile(tmp)` and `rename` can leave an inert `.tmp` (ignored by `read`, which only opens `fileFor(name)`). A best-effort startup sweep of `dir/*.tmp` can be added when a consumer wires the store — deferred.
- **Folder vs flat.** Three flat files match the existing flat `src/main/` modules. If #43/#44 grow the domain, introduce `src/main/secrets/` then — deferred, YAGNI.
- **Empty / weird names.** base64url encoding makes any string (incl. empty) a safe filename, so no validation is required for *safety*. A non-empty-name guard is a nicety, not a security need — left out per evidence-based-fix; revisit if a consumer wants it.
- **Backup/sync exclusion.** `userData/secrets` may be captured by Time Machine / cloud backup, but the ciphertext is keychain-bound and useless without the machine keychain. No portable per-OS backup-exclusion API — accepted residual risk, not addressed.
