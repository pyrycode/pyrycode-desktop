# #425 — fake e2e: run-config sheet (model, effort, YOLO)

[Ticket](https://github.com/pyrycode/pyrycode-desktop/issues/425) · [PR #459](https://github.com/pyrycode/pyrycode-desktop/pull/459) · Spec: `docs/specs/architecture/425-run-config-settings-e2e.md` · Size **S** · test-only, zero production code · not `security-sensitive` · no Figma

Split from #421 (via #422's realizability fork). Sibling of #423 (save-as-channel promote), #451/#452 (conversation lifecycle), #456 (workspace picker) — the #422-family of per-flow fake-e2e specs riding the shared `launchPairedApp` fixture (#433).

## What it covers

`e2e/run-config-settings.spec.ts` — one continuous drive covering all three run-config sheet controls (#257's interactive model row / effort segment / YOLO switch) plus one rejection, in a single `test()` block against a single launch:

1. Open the sheet, assert an **operable** baseline (model/effort/yolo selected per a seeded snapshot).
2. Change model, effort, and YOLO in turn — each proven by the **captured outbound** `set_session_settings` frame (`isDeepStrictEqual` on the payload + `.toBe(1)`), since the correlated `session_settings_updated` confirm is DOM-indistinguishable from the still-pending optimistic overlay.
3. One rejected change (model → `haiku`) — the one visually distinct outcome: the control reverts to the prior accepted value and `.run-config__error[role="alert"]` appears.
4. Close via `aria-label="Close"`.

## Patterns established / reused

- **Spec-local capturing reply factory** (`capturingRunConfigFake`), the #456 `capturingWorkspaceFake` shape: decodes each inbound, pushes it to a spec-owned `captured: Envelope[]`, answers per verb, delegates the rest. This ticket's factory is stateless — the reject vs. confirm branch is a value discriminant (`model === REJECTED_MODEL`), not a counter, since the only scripted rejection is identifiable by its own payload.
- **`conversationStateFake` (#434) does not cover this flow.** It only answers the seven conversation-list verbs; `set_session_settings`, `request_snapshot`, and `session_transition` all fall to its `default` (no reply). This confirms the parent ticket's stale premise and is why every #422-family spec that needs non-list verbs writes its own factory rather than extending the shared one.
- **Two preconditions `launchPairedApp` does not set up, needed by any future spec touching run-config or session id:**
  - A session id (`sessionIdStore`) is required before `RunConfigSections`' controls build an `onChange` at all — absent it, controls render #188's inert markup and clicks no-op. It arrives only via an **unsolicited** `session_transition` marker (`sessionIdBridge`, App-level, route-independent) — the spec must `daemon.pushFrame(...)` one after launch.
  - The run-config baseline needs a seeded `screen_snapshot` reply to the one `request_snapshot` `RunConfigData` fires on sheet open; absent it, the baseline falls through to `'' / '' / false`.
- **Effort-segment locator must be anchored.** `.run-config__effort-segment` selection by text needs `new RegExp(`^${level}$`)`, not a bare `hasText: 'high'` — `'high'` is a substring of the `xhigh` segment and would match two segments. (PR lessons-learned; confirmed by code review as the right call.)
- **`node:util`'s `isDeepStrictEqual`** inside `expect.poll(...).toBe(1)` proves both halves of the AC in one assertion: send-once (the count only grows, so a duplicate send fails `.toBe(1)`) and only-the-changed-field (any extra key fails the deep-equal). Reusable idiom for any future "exactly one wire frame with only these fields" assertion.
- **Confirm-commit is accepted as not independently DOM-observable.** `runSettingsWriteStore`'s `selectEffectiveSettings` composes `pending` and `confirmed` to the same displayed value, so a landed confirm and a still-pending optimistic overlay are visually identical. The spec proves the send-half from the wire, not the display; the confirm reply is still pushed (exercises the full decode + correlation path) but its landing is not separately assertable without a future pending/disabled DOM surface (`selectPendingFields` exists but is unused by the view).

## Lessons learned

- Effort-segment locators need an anchored regex (`/^high$/`), not a substring match — `'high'` is a substring of `'xhigh'`, so `hasText: 'high'` would ambiguously match both segments.
- `node:util`'s `isDeepStrictEqual` (Playwright specs run in Node, so builtins are free to import) gives an order-independent, single-assertion way to prove "exactly one frame carrying only the changed field."
