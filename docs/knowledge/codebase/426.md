# #426 — fake e2e: permission/trust modal answer paths

## What it covers

`e2e/permission-modal-answer-paths.spec.ts` — the five `PermissionModal` answer paths, all previously covered only by unit tests (`interactiveRoundtrip.test.tsx`, `PermissionModal.test.tsx`, `modalResolution.test.ts`), now driven end-to-end (renderer → IPC → main → Noise wire → decode) over the fake stack. Each prompt is surfaced by `daemon.pushFrame(modal_shown)` after launch — `PermissionModal` is mounted unconditionally and renders off `modalStore.outstanding[0]` directly, with no interactive-timeline gate (#179) to un-inert first.

Two `test()` blocks, split by the reject's FIFO subtlety (not convenience):

1. **Block 1 (one launch)** — default option one-tap (AC2), non-default → confirm sub-step with Back vs Confirm (AC3), cancel (AC4), remote `modal_dismissed` clear (AC6). The fake never returns a reject here, so leftover `outstandingAnswers` entries are harmless.
2. **Block 2 (fresh launch)** — a rejected answer (AC5): the fake answers `modal_answer` with a bare `error` (`payload: {}`, no `in_reply_to`), the `role="alert"` rejection banner renders, and Dismiss clears it.

## Patterns established / reused

- **The modal reject correlates by FIFO send order, not `in_reply_to`.** A daemon `error` with no `in_reply_to` falls through the settings/folder correlation in `daemonConnection.ts` straight to `outstandingAnswers.shift()` — it dequeues the *oldest* outstanding answer, not a specific one. `outstandingAnswers` is pushed only by `answerModal` (not `cancelModal`), drained by a matching `modal_dismissed` or by an error, and reset once per `dial()`. This is why the spec needs two blocks rather than one continuous drive: block 1's un-drained answer residue is inert only because block 1 never triggers an error; block 2 needs a fresh launch (empty queue) so its single answer is unambiguously the one the reject dequeues.
- **`answer_token` is asserted present-but-opaque, not deep-equal.** It's minted main-side via `crypto.randomUUID`, so unlike #425's whole-payload `isDeepStrictEqual`, the captured `modal_answer` is matched on `modal_id` + `option_id` with the token checked only for `typeof === 'string' && .length > 0`.
- **"Exactly one" as the negative guard for Back.** AC3 asserts `answersFor(B, 'allow')` is exactly `1` after Allow → Back → Allow → Confirm — had Back wrongly sent a frame, the count would be `2`. Confirmed by code review as sound (Back sends nothing per `modalResolution.ts`).
- **Guaranteed-absence guard for remote dismiss.** AC6 asserts zero `modal_answer`/`modal_cancel` frames for the dismissed prompt's `modal_id` — since its controls are never clicked, this is a true zero-frame check, not just a DOM assertion.
- **Content-free rejection banner.** `RejectionSurfaceView` never renders `modal_id` — the banner assertion is DOM-only (`role="alert"` + the client-owned copy `"Your answer was rejected."`) and deliberately cannot assert *which* prompt was rejected.
- **Spec-local capturing reply factory** (`capturingModalFake`), the same shape as #456's `capturingWorkspaceFake` / #425's `capturingRunConfigFake`: decode each inbound, push to a spec-owned `captured: Envelope[]`, answer `list_conversations` with `seedConversationsFrame()`, answer `modal_answer` with the reject error only when `rejectAnswers` is set (block 2), no-op everything else.

## Lessons learned

- The modal reject is **FIFO by send order, not `in_reply_to`** — a bare `error` dequeues the oldest `outstandingAnswers` entry regardless of which answer it's "replying" to. Any future spec pushing more than one outstanding answer before a reject must account for this ordering, not assume per-modal correlation.
- `answer_token` being main-minted and non-deterministic means outbound-frame assertions on `modal_answer` must match on `modal_id` + `option_id` and assert token presence only — a whole-payload deep-equal (the #425 idiom) doesn't apply here.
