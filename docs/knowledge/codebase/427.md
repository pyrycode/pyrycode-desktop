# #427 — fake e2e: queued backlog + dequeue + interrupt

[Ticket](https://github.com/pyrycode/pyrycode-desktop/issues/427) · PR #462 · Spec: `docs/specs/architecture/427-queued-backlog-interrupt-fake-e2e.md` · Size **S** · test-only, zero production code · not `security-sensitive` · no Figma

Sibling of #423/#425/#426/#451/#452/#456 — the #422-family of per-flow fake-e2e specs riding the shared `launchPairedApp` (#433) fixture. Clones the `run-config-settings.spec.ts` (#425) capture-and-push skeleton rather than `conversationStateFake` (#434) — like #425/#426, the verbs under test (`queue_state`, `turn_state`, `dequeue_message`, `interrupt`) sit outside `conversationStateFake`'s seven-verb list-conversation surface, so a spec-local capturing factory is the right fit.

## What it covers

`e2e/queued-backlog-interrupt.spec.ts` — three already-shipped, server-push-driven client flows that had unit coverage but no e2e: the queued-backlog render (#294, over the replacement-truth queue store #293), dropping a queued message (`dequeueMessage`, #296/#300), and interrupting a running turn (the #215 running indicator + #307 control). All three are driven end-to-end (renderer → IPC → main → Noise wire → decode for the send half, `daemon.pushFrame` for the reflecting-state half) in **one** `test()` block on **one** launch — the run-config precedent, not #423/#426's two-block split, since neither the queue store nor the timeline `phase` accumulates one-way residue within a single launch.

- **Queue render** — plants one delivered row via a real composer Send (the fake no-ops `send_message`, so the optimistic echo renders with no daemon reply), then `daemon.pushFrame(queue_state)` with two items. Asserts the queued rows (`[data-thread-role="queued"]`, inside `.conversation__queued`) render distinctly from the delivered row (`[data-thread-role="user"]`) — same shared `.message-row--user`/`.bubble--user` markup, partitioned only by role attribute and container.
- **Dequeue** — clicks a queued row's drop control (`Drop queued message`), proves the send-half via `expect.poll` on a captured `dequeue_message` frame carrying `{ conversation_id: SEEDED_ROW.id, queued_msg_id }` (whole-payload `isDeepStrictEqual` — the payload is fully deterministic, no opaque token), then pushes a fresh replacement `queue_state` omitting the dropped item and asserts it leaves the DOM while the other queued row survives.
- **Interrupt** — pushes `turn_state{thinking}`, asserting it mounts *both* the interrupt control (`Stop the running turn`) and the running indicator (`.conversation__thinking`) since `isTurnRunning` is `thinking || responding`. Clicks interrupt, proves the send-half via `expect.poll` on a captured bare `interrupt` frame (type-only match — payload is `{}`, no ids). Pushes `turn_state{idle}` and asserts both controls retract — **not** `turn_end`, which appends a turn boundary but doesn't reset `phase`.

## Patterns established / reused

- **`queue_state` must carry `conversation_id === SEEDED_ROW.id`.** `QueuedBacklogControl` reads `selectBacklogFor(activeConversation.id)`, and list-open (`PairedShell.tsx`) records the clicked `SEEDED_ROW` as active. A snapshot under any other id lands in the store but is selected by nothing — **zero rows render, silently**, no error. The run-config session-id-gate analogue (#425), now established for the queue store too.
- **Push `queue_state` only after `launchPairedApp` resolves.** `subscribeQueue` resets all backlogs on every `connected` event (#197), and the fixture's Send-enabled completion signal is gated on that same `connected` — so a pre-resolve push would be silently wiped. No further `connected` fires within this spec's single launch, so post-resolve pushes are safe.
- **Interrupt quiescing signal is `turn_state{idle}`, not `turn_end`.** `isTurnRunning(phase)` (`thinking || responding`) gates the interrupt control; `ThinkingIndicator` gates on `phase === 'thinking'`. `turn_state{thinking}` lights both; only `turn_state{idle}` retracts both. `TurnPhase` has no literal `running` value.
- **Two-part assertion per non-optimistic mutation.** Neither `dropQueuedMessage.ts` nor `sendInterrupt.ts` mutates the store locally — each is (a) act on the DOM, (b) `expect.poll` the captured outbound frame (the send-half proof, since the DOM alone can't show the send landed), (c) `daemon.pushFrame` the reflecting state and assert the DOM change. Same shape as #425/#456's outbound-frame proofs, now paired with a subsequent DOM-reflection step because these two verbs are push-reflected rather than terminal.
- **"Keyed by `queued_msg_id`" proven behaviorally, not by inspecting a DOM attribute.** A React key isn't queryable — correctness is shown by the dequeue step removing exactly the omitted row while the sibling row survives.
- **One block, one launch — the run-config precedent generalized.** #423/#426 split into two blocks because of genuine one-way state (an irreversible promotion; FIFO reject residue). This ticket is the first #422-family spec to explicitly document *why* a flow does NOT need the split: both stores under test are freely re-settable by pushing a fresh snapshot/state, so splitting would only triple the ~60s real-handshake launch cost for no isolation benefit.

## Lessons learned

- A wrong `queue_state.conversation_id` or a pre-launch-resolve push both fail the same way — **zero rows, no error** — so a future regression here needs the render assertion's auto-wait timeout to surface it; the *cause* still has to be diagnosed against these two specific traps.
- `turn_end` is easy to reach for as the "turn is over" signal but does not retract the phase-gated interrupt/thinking UI — only `turn_state{idle}` does. Any future turn-lifecycle spec should push `turn_state{idle}` explicitly rather than relying on a `turn_end` side effect.
