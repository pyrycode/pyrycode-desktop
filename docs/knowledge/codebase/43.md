# #43 — Device static keypair: generate once and persist

**Shipped:** 2026-07-04 · **Size:** S · **Scope:** background process only (`src/main/`) · greenfield, zero consumer cascade (nothing imports it yet; `src/main/index.ts` untouched) · **no new dependency** (`noise-c.wasm@0.4.0` landed with [#29](29.md); `SecureStore` landed with [#42](42.md)).
**Spec:** `docs/specs/architecture/43-device-static-keypair.md` · **PR:** [#47](https://github.com/pyrycode/pyrycode-desktop/pull/47) (`security-sensitive`; review: **PASS**, no MUST/SHOULD findings, one non-blocking naming NIT — architect security-review pass + a code-review adversarial pass over the diff).

The desktop client's **stable Noise_IK cryptographic identity**: a device static X25519 keypair, generated **once** on first use and persisted through #42's `SecureStore`, so every later launch reads the same pair without the private key ever leaving the secure store or reaching the renderer. This is the initiator static key (`s`) the Noise_IK handshake will construct its state from. It mirrors mobile's device-static keypair (one per paired binary, public key mirrored for fast startup, rotation tied to re-pair — `protocol-mobile.md` §"Static keys — mobile side"; pyrycode ADR 024). See the [device keypair feature doc](../features/device-keypair.md) for the full contract.

Scope lock held: **generation + persistence + retrieval only.** It (a) generates one X25519 keypair from the #29 library on first use, (b) persists it as one opaque 64-byte blob through #42's `createSecureStore`, (c) is generate-once (never a fresh key when a blob exists), (d) exposes the pair to in-process callers with the public key retrievable. It does **not** perform the handshake, does **not** parse pairing input, does **not** touch `safeStorage`/the filesystem directly (all persistence goes through the injected `SecureStore`), does **not** wire itself into app startup, and adds **zero** renderer/preload/IPC surface. Rotation, per-server-id keying, and transport wiring are out of scope (see Deferred).

## Patterns established

- **A cryptographic-identity service is a pure core over two injected effectful seams — the #42 shape, reused verbatim.** Persistence (`SecureStore`, **type-only** import) and X25519 keygen (`KeyPairGenerator`) are both injected interfaces, so the core's test module graph pulls in **no** `electron`, `fs`, or wasm — the AC5 "tests run with no keychain, no real filesystem" isolation is **structural**, not incidental. The real keygen call ships in a separate untested adapter (`noiseKeyPairGenerator.ts`), exactly as #42 isolated `electronSecretEncryption.ts`. Reuse this split for any future module that both bears a security property and must call an effectful crypto/OS edge: prove the property in a blind core with fakes, ship the effectful reality as a thin adapter.
- **Generate-once = a lazy-async-singleton memo over a persisted source of truth.** `ensure()` caches its in-flight/resolved `Promise<DeviceKeyPair>`; a second or concurrent call returns the same promise, so keygen + persist run **at most once per process** and the two-callers-both-read-`null` race is closed by construction. Across launches, a fresh handle re-reads the store — **the persisted blob is the single source of truth**, the memo is only a within-process serialization point over it. This is the idiomatic answer to "do this expensive thing exactly once, and never twice concurrently".
- **Clear the memo on rejection so a transient failure can't poison the process.** `memo = load().catch(err => { memo = null; throw err })`. Without the clear, one keychain-unavailable rejection would be cached and every later `ensure()` this process would re-throw it — so a retry after the keychain comes back could never succeed. A test pins this (reject, swap in a working store, succeed). The rule generalizes: a memoized promise that can reject must reset itself on rejection, or it caches the failure forever.
- **Persist both keys (`priv‖pub`), don't re-derive the public.** `noise-c.wasm` derives the public key **inside** `HandshakeState.Initialize` and exposes no standalone "public-from-private" call, so re-derivation on read isn't cleanly available — persisting both is forced by the library surface *and* mirrors mobile's public-key mirror for fast startup reads. The blob is a fixed 64 bytes (`privateKey[32] ‖ publicKey[32]`); `decodeKeyPair` rejects anything else as `MalformedDeviceKeypairError`.
- **Fail-loud on a present-but-bad blob; never silently regenerate.** A decrypt throw from `SecureStore.get` propagates out of `ensure()`; a wrong-length blob throws `MalformedDeviceKeypairError`; in **both** the generator runs **zero** times (tests assert `count === 0`). Silently regenerating on corruption would rotate the device identity — a tamper→forced-re-pair/identity-downgrade path. Recovery (delete + re-pair vs hard error) is deliberately left to the consumer (the transport ticket), the ADR 0005 "recovery is a consumer decision" principle applied. Matches mobile's "pair record corrupted; re-pair" posture (`protocol-mobile.md` line 384).
- **Re-used the #42 / transport security discipline:** **log-free by construction** (no `console.*` anywhere — a dedicated test spies all six `console` methods across generate/persist/both error paths and asserts none fire); **static error messages** carrying no key bytes (`MalformedDeviceKeypairError`, `EncryptionUnavailableError`); keys held only as **opaque `Uint8Array` locals** with `readonly` fields, never a named field of a logged struct; **zero renderer/IPC surface** so AC4 ("private key never returned to the renderer") is structural, not conventional.
- **A counting fake proves "exactly once", not "coincidentally equal".** The test `KeyPairGenerator` returns a **distinct** pair per call (`fill(count)` / `fill(0x80 + count)`), so an *equal* pair across two `ensure()` calls can only mean generation ran once — a constant-returning fake would let a double-generation bug pass. Same "replicate the failure contract, not just the happy path" discipline as #42's fake encryption.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The generate-once invariant lands cleanly as a lazy-async-singleton.** A memoized `Promise<DeviceKeyPair>` both serializes concurrent first-calls (closing the two-callers-both-see-`null` race) and dedupes within a process, while the persisted blob is the cross-launch source of truth. **Clearing the memo on rejection is the load-bearing detail** — without it, a transient keychain-unavailable failure would poison the store for the whole process lifetime.
- **`noise-c.wasm` exposes no standalone "public-from-private" derivation** (the public key is derived inside `HandshakeState.Initialize`), which independently forces persisting **both** keys as `priv‖pub` rather than re-deriving the public on read — the same shape mobile uses for its fast-startup public-key mirror.

## Deferred (open questions carried forward)

- **Composition-root wiring is the transport ticket's job, not this one.** #43 has **no runtime consumer** — nothing calls `ensure()` until the transport needs the initiator static key. Wiring it into `index.ts` with no caller would be untestable and premature (the #21/#22/#42 defer-wiring precedent), so `src/main/index.ts` stays untouched. The recorded assembly recipe for the transport ticket: `createDeviceKeypairStore({ secureStore: createSecureStore({ encryption: electronSecretEncryption(), persistence: fileSecretPersistence(join(app.getPath('userData'), 'secrets')) }), generator: noiseKeyPairGenerator() })`, then `await ensure()` at connect time.
- **Own wasm loader in the adapter, not an import from the spike.** `noiseKeyPairGenerator.ts` rolls its own ~10-line memoized `loadNoiseLib()` rather than importing from `noiseSpike.ts` — that file is a throwaway spike slated for deletion by **#7**. Format compatibility with the handshake comes from calling the **same package + curve** (`noise-c.wasm`, `NOISE_DH_CURVE25519`), not from sharing a loader. #7 consolidates wasm loading (single-instance model + electron-vite bundling) and this adapter folds into it then. Verifying production static-key entropy and electron-vite wasm bundling remain **#7's** gates ([#29](29.md)).
- **Per-server-id keying is out of scope.** Milestone 1 is a single pyrybox → one keypair under `DEVICE_STATIC_KEY_NAME` (`'pyrycode.device_static'`). Mobile keys per server-id (`pyrycode.device_static.<server-id>`); appending `.${serverId}` is a **one-line change** the explicit constant + injectable `name` param already enable (a test exercises the injected-name seam). Deferred to the multi-server ticket.
- **Rotation / re-pair is out of scope.** The identity is generate-once and immutable for the process; rotation is tied to re-pairing (mobile line 121) and belongs with the pairing flow (#44 / a re-pair ticket). #43 only guarantees a stable identity is available.
- **Naming casing NIT (non-blocking).** The public surface mixes two spellings — `DeviceKeyPair`/`KeyPairGenerator`/`encodeKeyPair` (two words) vs `DeviceKeypairStore`/`createDeviceKeypairStore`/`MalformedDeviceKeypairError` (one word "Keypair"). This faithfully mirrors the spec surface, not a developer defect; a future cleanup ticket can settle on one casing.
