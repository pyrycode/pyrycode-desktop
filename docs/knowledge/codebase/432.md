## Summary

The deepest tier-3 liveness net in the suite: proves the permission modal over the **real** chain —
real `pyry` daemon → real claude actually blocking on a per-tool permission → the daemon relaying
`modal_shown` to the remote desktop → the desktop answering "allow" → the tool running → the turn
completing. Every prior modal test scripts the modal via `daemon.pushFrame` (the unit tests and the
fake-stack twin `permission-modal-answer-paths.spec.ts`, #426); this is the first proof against a
prompt a real daemon actually emits.

Clones `real-claude.spec.ts`'s precondition verbatim (pairing, FAB-created conversation, connected
gate) and swaps only the turn body: send a prompt engineered to force exactly one deterministic,
permission-gated tool call (a single file write, "do not read or list any files first"), wait for
`page.getByRole('dialog')` to become visible (the core liveness assertion — a timeout here is a
genuine liveness signal, not a flake), answer "allow", wait for the dialog to clear, then assert the
turn completes via the same two-signal shape #445/#446 established (`.bubble__cursor` count-0 +
non-empty assistant reply).

Adds a single-consumer `skipPermissions` fixture option to `e2e/fixtures/realDaemon.ts` (default
`true` = current behavior byte-for-byte), gating the one `--dangerously-skip-permissions` claude flag
at the post-`--` spawn args. This spec is the only caller and sets `test.use({ skipPermissions: false
})`, mirroring the `seedPromoted` single-consumer precedent from #439. Every sibling spec (including
#445/#446) sets no override, so their spawn args are unchanged.

## Patterns established

- **Over the real stack, the modal's answer surface is only partially test-controlled.** The
  fake-stack twin (#426) both scripts the `modal_shown` payload and owns the option labels /
  `default_option_id`. Here only the client-owned buttons (`Cancel`/`Back`/`Confirm`) are
  deterministic — the affirmative option's label and whether it is the daemon's default are
  **daemon-supplied**, unknown ahead of time. The answer helper (`answerAllow`) absorbs both unknowns:
  a start-anchored, case-insensitive regex over plausible affirmative vocabulary
  (`/^(yes|allow|approve|accept|grant)\b/i`, scoped inside the dialog, first match) locates the
  option, and a conditional `Confirm` click (`if (await confirm.count()) > 0`) resolves the
  non-default confirm sub-step (`modalResolution.ts`'s `selectOption`) only if it actually appeared.
  This is the general shape for any real-stack assertion against a daemon-owned enum: match by
  intent-pattern, not by exact string, and treat the confirm/no-confirm branch as one call site rather
  than two.
- **A permission-gated tool call is a structural (not merely observational) causation proof.** Turn
  completion (`turn_end`/cursor-clear) can only follow the tool running, which can only follow the
  allow — so, unlike #445's "long prompt makes premature completion implausible" mitigation, this
  spec's proof is airtight by construction: there is no code path where `turn_end` fires without the
  permission having been granted. Reuse this shape whenever the daemon behavior under test itself
  blocks on the assertion, rather than merely making the false-positive window improbable.
- **A single-consumer fixture option that flips daemon behavior (not just seeds data) still rides
  in-ticket.** `skipPermissions` changes what claude actually does (blocks vs. auto-runs), a bigger
  lever than `seedPromoted`'s data-shape toggle, but the same single-consumer / byte-for-byte-default
  rule from #439 applies unchanged — the fixture-boundary rule is about consumer count, not about how
  much the option changes downstream behavior.
