# #433 — E2E fixture: shared `launchPairedApp` fake-daemon pairing harness

**Shipped:** 2026-07-15 · **Size:** S · **Security-sensitive:** no (test infrastructure only, zero production LOC) · **Scope:** one new file, `e2e/fixtures/launchPairedApp.ts`; two specs migrated (`e2e/pair-to-conversation.spec.ts`, `e2e/send-and-stream.spec.ts`).
**Spec:** `docs/specs/architecture/433-launch-paired-app-fixture.md` · **PR:** [#437](https://github.com/pyrycode/pyrycode-desktop/pull/437), code review PASS, no findings. Split from #421; unblocked by [#435](435.md) (which repaired the drive this ticket extracts). Foundation for the #422–#429/#434/#420 e2e batch.

## Summary

Both milestone e2e specs (`#93`, `#94`) hand-rolled an identical harness: a file-local `test.extend` chain standing up the fake relay forwarder + fake Noise_IK daemon, launching the built app with two `isPackaged`-gated dev flags and an isolated `--user-data-dir`, driving the real pairing UI (paste → Pair → Confirm), clicking the seeded ChannelList row to cross the post-#140 `list → thread` step, and waiting for Send to enable. This ticket extracts that duplicated harness into one shared factory fixture, `e2e/fixtures/launchPairedApp.ts`, so a new fake-daemon UI e2e spec starts at "paired, connected, on the thread, Send enabled" in a few lines instead of re-transcribing it.

## What shipped

- **`launchPairedApp(options?)`** — a Playwright *factory fixture* (`base.extend`, the fixture yields a function, not a value) built for exactly this reason: each spec passes different daemon reply options, which a plain value fixture can't accept.
- **Default seeding + precedence.** The fixture's own `startFakeDaemon` call passes `buildReply: () => seedConversationsFrame()` first, then spreads `...options` after it — so a caller's `buildReply`/`buildReplyFrames`/`helloAck` wins. Because `fakeDaemon.ts` prefers `buildReplyFrames` over `buildReply` whenever set, a spec that scripts `buildReplyFrames` makes the default seed dead code and must reseed the row itself on its own default arm — which is exactly what `send-and-stream.spec.ts` does, reusing the fixture's exported `seedConversationsFrame()` rather than re-declaring the row.
- **The drive** (paste synthetic payload → `Pair` → fingerprint visible → `Confirm` → click `.channel-list__row-open` → `Send` enabled) is fixture-owned; only per-flow *assertion* selectors stay in the specs. The row click is a real product-UI navigation (`onClick` → dispatch `open` → route `'thread'`), never a test hook.
- **LIFO teardown**, pushed in creation order and drained in reverse in the fixture epilogue (runs on pass and fail via Playwright's lifecycle): `app.close()` → `daemon.close()` → `forwarder.close()` → `rm(userDataDir)`. Each thunk is pushed the moment its resource comes up (not after the whole drive succeeds), so a mid-drive failure — e.g. the row click timing out — still cleans up everything already created. Each thunk is best-effort (`try/catch`) so one failure doesn't abort the rest of the drain.
- **Returned handle:** `{ page, app, daemon }` — `daemon` is the full `FakeDaemon` control surface (`staticPublicKey`, `pushFrame`, `initiateRekey`, `whenSettled`, `close`). The forwarder is deliberately not exposed — no in-scope spec needs its leg controls; a future reconnect spec (#434 family) can widen the handle then.
- **Timeout ownership:** the fixture calls `testInfo.setTimeout(LAUNCH_TEST_TIMEOUT_MS ≈ 60s)` in setup, so both migrated specs dropped their per-test `test.setTimeout(...)` boilerplate.
- Both specs migrated: `pair-to-conversation.spec.ts` went thin (`const { page } = await launchPairedApp()` + the milestone end-state assertion, dropping its pre-state absent-check since the fixture's own drive already proves the transition); `send-and-stream.spec.ts` kept its reply-frame builders and `buildReplyFrames` dispatcher but now imports `seedConversationsFrame` from the fixture for its default arm instead of declaring its own row.

## Patterns established

- **Factory fixture for per-spec setup args.** When specs under a shared harness need to pass *different* creation-time options (here: daemon reply scripting), the fixture should yield a function (`await use(async (options) => {...})`), not a value — the value-fixture shape (`electronApp.ts`'s `electronApp`/`page`) only fits when every consumer wants identical setup.
- **Push-as-you-go LIFO teardown stack.** Register each resource's teardown thunk immediately after that resource is created, not after the whole setup sequence succeeds — this is what makes a mid-drive failure (not just a post-setup test failure) leak nothing. Combined with best-effort (`try/catch`-swallowed) thunks so one teardown failure doesn't block the rest of the drain.
- **Reusable seed export for cross-file reply-builder reuse.** `seedConversationsFrame()` is exported specifically so a spec that must override the default `buildReply` (by supplying `buildReplyFrames`, which takes precedence) can still reuse the *same* seed frame on its own default arm, rather than re-declaring the row literal a second time.
- **`Omit<FakeDaemonOptions, 'url'>` as the reply-scripting options type**, rather than enumerating `buildReply`/`buildReplyFrames`/`helloAck` as three named fixture params. This is what lets a future daemon knob (e.g. a reconnect-family option) reach a spec through the fixture with zero fixture edits.

## Lessons learned

*Lifted from the PR body's own "Lessons learned" section.*

- A factory fixture (`await use(async (options) => {...})`) is the right shape when consumers pass differing setup args a plain value fixture can't accept; the fixture epilogue drains a per-resource LIFO teardown stack, so a mid-drive failure still cleans up whatever was created and no Electron process is orphaned on pass or fail.
- `e2e/` is excluded from every project tsconfig (Playwright transpiles with esbuild, no typecheck), so the `{...process.env}` → `LaunchOptions.env` assignment carries a benign `string | undefined` index-signature mismatch in all e2e files; a standalone `tsc` pass over `e2e/` surfaces it but it never reaches runtime. The fixture kept this consistent with the existing `electronApp.ts`/`smoke.spec.ts` pattern rather than diverging for a non-gated, transpile-only file.
