# #434 — E2E fixture: `conversationStateFake` stateful reply factory

**Shipped:** 2026-07-15 · **Size:** S · **Security-sensitive:** no (test infrastructure only, zero production LOC) · **Scope:** two new files, `e2e/fixtures/conversationStateFake.ts` and the demonstrating `e2e/conversation-state-fake.spec.ts`.
**Spec:** `docs/specs/architecture/434-conversation-state-fake.md` · **PR:** [#447](https://github.com/pyrycode/pyrycode-desktop/pull/447), code review PASS, no findings. Split from #421; rides [#433](433.md)'s `launchPairedApp`. Unblocks the #422–#429 per-flow UI e2e family.

## Summary

The fake daemon (`src/main/transport/fakeDaemon.ts`) is reply-driven and stateless: a run scripts one `buildReply`/`buildReplyFrames` per test. The #422–#429 per-flow specs (conversation lifecycle, save-as-channel, workspace change, …) all need a fake that **holds** a conversation list and mutates it across a real UI drive, instead of each re-transcribing the wire semantics for the seven list verbs. This ticket ships that fake: `conversationStateFake(options)` returns a stateful `buildReplyFrames` closure over a seeded `ConversationSummary[]` that answers `list_conversations` from current state and applies `create` / `rename` / `archive` / `unarchive` / `promote` / `change_workspace` / `delete` to it, reflecting through the app's two real reflect paths.

## What shipped

- **`conversationStateFake(options?)`** (`e2e/fixtures/conversationStateFake.ts`) — takes an optional seed `conversations: ConversationSummary[]` (default: a single promoted, named `DEFAULT_SEED`) and returns the bare `(inbound: Uint8Array) => Uint8Array[]` shape `FakeDaemonOptions.buildReplyFrames` expects. A spec composes it into `launchPairedApp({ buildReplyFrames })` itself — the factory does not know about `launchPairedApp`.
- **One switch over `env.type`, decoded once per inbound**, mutating the held list in place before building the reply:
  - `list_conversations` → `[conversationsFrame(list)]`, no mutation.
  - `rename` / `archive` / `unarchive` / `promote` / `change_workspace` → find the row by `payload.conversation_id`, mutate it, reply a `conversation_updated` **broadcast** (no `in_reply_to`) — the app's `shouldRefreshList` auto re-requests `list_conversations`, which the next inbound answers from the now-updated `list`.
  - `delete_conversation` → splice the row out, reply the bare `{ id }` `conversation_deleted` **correlated** to the request via `in_reply_to: env.id` (no broadcast) — also auto re-lists.
  - `create_conversation` → mint a row (`id: created-${nextCreatedId++}`, a closure-held monotonic counter — no clock/random), append it, reply `conversation_created { record }` (consumed by the create→nav bridge; the row itself only surfaces on the *next* `list_conversations`, not via a re-list).
  - Row-not-found on any of the five mutation verbs → `[]`, a defensive no-op (the demonstrating spec and the #422–#429 family always target a seeded row; this is not daemon-rejection modeling, which stays out of scope).
  - default (unhandled verb, e.g. a snapshot request) → `[]` — the fake daemon settles `ok:true` on an empty reply array.
- **Four private frame builders**, each projecting the held 7-field `ConversationSummary` onto the exact wire shape and field order from `src/shared/wire/types.ts`, built with the production `encodeEnvelope`: `conversationsFrame` (full list), `conversationUpdatedFrame` (5-field, `name` before `cwd`, omits `is_archived`/`last_message_ts`), `conversationDeletedFrame` (bare `{ id }` + `in_reply_to`), `conversationCreatedFrame` (5-field, `cwd` before `name` — the intentional reorder vs. `conversation_updated`). Reply envelope `id`/`ts` are fixed literals (`REPLY_ENVELOPE_ID = 1`, `FIXED_TS`), matching the existing `fakeDaemon` HELLO_ACK convention.
- **The demonstrating spec** (`e2e/conversation-state-fake.spec.ts`) reuses `real-daemon-rename.spec.ts`'s proven drive (pencil → dialog → fill → Save) against the fake instead of a real daemon: seed one promoted/named row, `launchPairedApp({ buildReplyFrames })` (which lands in the thread), back-nav to the list, click `.channel-list__rename`, rename, then assert the new title is visible and the old one has count 0 in `.channel-list`. This single scenario exercises the fixture's core contract end-to-end — non-empty-seed launch, `list_conversations`-from-state, `conversation_updated` broadcast reflect, re-list-from-updated-state — while the other six verbs are covered by the uniform mutation-apply plus field-exact frame builders (type-level fidelity); their live end-to-end exercise is the #422–#429 family's job.
- Rename was chosen deliberately over archive: `ChannelList.tsx`'s `partitionByPromotion` does not filter `is_archived` (a latent #366 behavior, see [#440](440.md)'s findings), so an archived row never leaves the active list — an "archived row gone from list" assertion would be unrealizable. Rename keeps the row in-list with only the title changing, so "new title present / old title gone" is unambiguous.

## Patterns established

- **Stateful closure over a held list, not a per-call script.** Where `send-and-stream.spec.ts`'s `buildReplyFrames` is a stateless dispatch on `env.type`, this factory demonstrates the next tier: a closure holding mutable state (`list`, `nextCreatedId`) that a spec seeds once and then drives through multiple real mutations, with the fake answering every follow-up query from current state rather than a fixed script. This is the shape any future stateful per-flow fake (e.g. queue/backlog) should copy.
- **Trusted-input posture for fakes.** Inbound is cast per-verb to the known outbound payload type (`env.payload as RenameConversationPayload`, etc.) rather than re-implementing the production decoder's fail-closed narrowing — a fake daemon's job is to be lean and correct against a well-formed app-under-test, not to validate untrusted input.
- **Frame-builder fidelity over frame-builder abstraction.** The four builders don't share a generic "project row onto payload" helper — each hand-lists its exact field set and order, because the field-exact shape (name-before-cwd vs. cwd-before-name) *is* the fidelity the fixture exists to guarantee; a shared helper would obscure exactly the divergence a future spec needs to trust.

## Lessons learned

*Lifted from the PR body's own "Lessons learned" section.*

- A fresh worktree had no `node_modules`; `npm install` was needed before any test/build gate could run.
- Bare `npx playwright` resolved a cached global install that couldn't find `@playwright/test` — use `./node_modules/.bin/playwright` (or `npm run e2e`, which invokes the local install) instead of `npx` in this repo.
