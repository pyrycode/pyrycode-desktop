# #435 — E2E: drive `list → thread` so the two milestone pairing specs reach the connected thread

**Shipped:** 2026-07-14 · **Size:** S · **Security-sensitive:** no (test-infra repair; drives existing product UI, adds no new screens or wire types) · **Scope:** two files touched, both test-only — `e2e/pair-to-conversation.spec.ts` (#93) and `e2e/send-and-stream.spec.ts` (#94). **Zero production-source edits.**
**Spec:** `docs/specs/architecture/435-milestone-e2e-list-to-thread.md` · **PR:** [#436](https://github.com/pyrycode/pyrycode-desktop/pull/436), code review PASS. Unblocks [#433](https://github.com/pyrycode/pyrycode-desktop/issues/433) (the `launchPairedApp` fixture extraction) and transitively the #422–#429/#434/#420 e2e batch.

## Summary

Both milestone e2e specs were **red on `main`**, and had been since [#140](140.md) (`PairedShell` nav-shell) landed: pairing no longer drops straight into `ConversationScreen`, it enters the paired route at `route='list'` (ChannelList). Both specs asserted `.conversation` visible + Send enabled immediately after `Confirm`, so both timed out at that assertion — invisibly, because `npm run e2e` is not CI-gated (`npm test`/`npm run build` scan `src/`, not `e2e/`).

The fix drives one real `list → thread` step in both specs: the fake daemon's `buildReply`/`buildReplyFrames` seeds a one-row `conversations` reply, giving ChannelList a clickable `.channel-list__row-open` button; the spec clicks it (real product `onClick={onOpen}` → `dispatch({type:'open'})` → `route='thread'`), *then* asserts `.conversation` + Send-enabled. No production code changed — the reply builders and the click live entirely in the two spec files.

## Design decision: seed-a-row-then-click (Path 1), not the New-discussion FAB

The architecture spec named two candidate `list → thread` paths and picked **Path 1** because it is the only one with a free, deterministic connected gate:

- `ConversationListData` (`src/renderer/src/store/conversationListBridge.ts`) auto-fires `requestConversations` **only on the connected rising edge**. So the seeded row can only appear *after* the handshake completes — Playwright's auto-wait on `.channel-list__row-open` doubles as the connected gate, with no extra gating logic needed.
- Path 2 (the New-discussion FAB) is visible on the *empty* list immediately after Confirm, before any connected signal exists on that screen. Clicking it before the daemon is connected would drop the outbound `create_conversation` (the `canSend` guard) and hang the drive — making it safe would require inventing a new connected-gate affordance on the list screen, which is strictly more work for what becomes the batch's shared drive.

This choice is load-bearing beyond this ticket: it becomes the default fake-daemon reply contract that #433's `launchPairedApp` fixture — and transitively the whole #422–#429 batch — inherits.

## The second, independently-discovered staleness in #94

The architecture spec prescribed keeping #94's existing daemon reply (a coarse `message` envelope) and its `data-message-role` selectors unchanged — only inserting the row click. That turned out to be **wrong**: those assertions had *also* gone stale, independently of #140, from [#179](179.md)/[#245](245.md)/[#203](203.md) (which all landed **after** #140). Because #94 was already red at the earlier `.conversation` assertion, this second layer of drift was invisible until the first was fixed:

- The optimistic user echo and the assistant reply now render as **timeline rows** (`data-thread-role`), not the retired coarse `MessageThread`/`MessageBubble` (`data-message-role`) — see `ConversationScreen.tsx:52-53`.
- A coarse `message` reply now decodes to `messageReceived` → `sessionStore`, which the timeline **never renders** (`timelineBridge.ts` maps it to `null`; `assistant_delta` "REPLACES the coarse message fan-out" per `types.ts:222`).

So #94's `send_message` reply became the v2 interactive stream — `assistantDeltaFrame()` (whole `REPLY_TEXT` in one `assistant_delta`) followed by `turnEndFrame()` (closes the turn, dropping the streaming cursor so the bubble's final text is *exactly* `REPLY_TEXT` — an `assistant_delta` alone leaves a trailing `▎` that fails `toHaveText`) — sent via `buildReplyFrames` (multi-frame, precedence over `buildReply`). Both bubble assertions moved to `.bubble[data-thread-role="user"]` / `[data-thread-role="assistant"]`. This was verified both empirically (the prior RED run's DOM snapshot showed a bare timeline row, not a `data-message-role` bubble) and in code, and disclosed as a deliberate spec deviation in the PR body.

## Patterns established

- **A long-red e2e can carry more than one layer of staleness — check every assertion past the first failure, not just the one the ticket names.** An e2e spec times out at its *first* failing assertion; everything after it stops being exercised, so later drift (a selector rename, a reply-shape change) accumulates invisibly. When repairing a long-red spec, re-verify every downstream assertion against current code before assuming "fix the first failure" is the whole job.
- **A fake daemon's `buildReply`/`buildReplyFrames` can double as a deterministic UI-readiness gate for free**, when the reply is only sent in response to a request that itself only fires on the state you want to wait for. Here: `ConversationListData` requests the list only post-connect, so seeding that reply makes "the row is clickable" and "the daemon is connected" the same fact — no separate wait/poll needed. Worth reaching for this shape again wherever a UI-only e2e needs to gate on a transport-level state without a dedicated DOM affordance for it.
- **`buildReplyFrames`'s `default` dispatch arm, not an explicit case per known inbound type, is deliberate future-proofing for a drive-enabling fake.** #94 dispatches only `send_message` explicitly; every other inbound (the auto-fired `list_conversations`, and any future auto-fire the app grows) falls through to the idempotent list-seed reply. This keeps the fake from needing a new explicit case every time the app adds another auto-fired request — at the cost of being reply-shape-unaware for anything besides the one type under test. Acceptable here (a drive-enabling fake, not a faithful daemon simulator); the type-faithful reply table is deferred to #434's `conversationStateFake`.

## Lessons learned

*Lifted from the PR body's own "Lessons learned" section.*

- The milestone e2e specs carried **two** layers of staleness, not one: #140 (route landing) *and* #179/#245/#203 (selectors + reply shape). Because `npm run e2e` isn't CI-gated and the specs failed at the *first* stale assertion, the later drift stayed hidden until the earlier one was fixed. When repairing a long-red e2e, expect assertions past the first failure to have drifted too.

## Testing

The deliverable **is** the two repaired tests, run by `npm run e2e` (`npm run build` + Playwright, `workers:1`). `e2e/` sits in neither tsconfig, so `npm run typecheck` doesn't validate these specs — `npm run e2e` is the only gate that does. `npm test`/`npm run build` stay green because they scan `src/` only, which this ticket left untouched.
