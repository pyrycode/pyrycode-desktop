# #44 — Paired-server record storage

**Shipped:** 2026-07-04 · **Size:** S · **Scope:** background process only (`src/main/`) · greenfield, zero consumer cascade (nothing imports it yet; `src/main/index.ts` untouched) · **no new dependency** (`SecureStore` landed with [#42](42.md); `QrPayload` is an existing wire type from [#5](5.md)).
**Spec:** `docs/specs/architecture/44-paired-server-record-storage.md` · **PR:** [#49](https://github.com/pyrycode/pyrycode-desktop/pull/49) (`security-sensitive`; review: **PASS**, no MUST/SHOULD/NIT findings — architect security-review pass + a code-review adversarial pass over the diff).

Persists and retrieves the **paired-server record** — the `{server, relay, token, server_static_pubkey}` tuple pairing yields (the QR/paste payload). Storing it lets the client reconnect to the same daemon and drive the `Noise_IK` handshake on every launch **without re-pairing**: on connect the transport reads `server_static_pubkey` as the responder's static key and `token` for the relay/hello auth. This module neither validates nor uses either field cryptographically — it stores what it is given and returns it verbatim. It is the **near-twin** of the [#43](43.md) device-keypair sibling: the same consume-the-primitive shape over [#42](42.md)'s `SecureStore`, minus the keygen seam and the generate-once memo. See the [paired-server store feature doc](../features/paired-server-store.md) for the full contract.

Scope lock held: **serialize + store + retrieve only.** It (a) serializes the four-string tuple to one opaque JSON blob and persists it through #42's `createSecureStore`, (b) retrieves it with the absent-vs-undecryptable-vs-malformed semantics below, (c) exposes a main-process-only handle. It does **not** parse or validate the pairing input (relay-URL scheme check, fingerprint — that is [#9](https://github.com/pyrycode/pyrycode-desktop/issues/9), which calls `save()` after validating), does **not** touch `safeStorage`/the filesystem directly (all persistence goes through the injected `SecureStore`), does **not** perform the handshake or use `server_static_pubkey` cryptographically, does **not** wire itself into app startup, and adds **zero** renderer/preload/IPC surface.

## Patterns established

- **Aliasing the wire type makes drift a compile error, not a silent divergence.** `PairedServerRecord = QrPayload` — an alias, **not** a re-declaration of the four fields. Any change to `QrPayload` (`src/shared/wire/types.ts:120`) flows straight through; a record that no longer matches the wire contract fails `typecheck` rather than persisting a stale shape. This is the mechanical realization of CLAUDE.md's "don't drift the wire types" — the wire protocol stays the single source of truth for the record shape. (This is the ticket's one "Lessons learned" bullet, promoted to a pattern because it is the cleanest structural guard here.)
- **A secret-storage service is a pure core over one injected `SecureStore` seam — the #42/#43 shape, minus the second edge.** Because serialization is pure, `SecureStore` (a **type-only** import) is the *only* effectful dependency, so the core's test module graph pulls in no `electron`/`fs` — the AC5 "tests run with no keychain, no real filesystem" isolation is **structural**, not incidental. Where #43 had two injected seams (`SecureStore` + `KeyPairGenerator`), #44 has one; where #43 needed a separate untested adapter (`noiseKeyPairGenerator.ts`), #44 needs none. This is the lighter end of the same DI spectrum: inject every effectful edge, prove the security property in a blind core with fakes.
- **Fail-loud on a present-but-broken blob; the only `null` path is genuine absence.** `load` returns `null` **only** when `secureStore.get` returns `null` (nothing stored). A decrypt failure inside `get` **propagates** (not caught); a decrypted-but-malformed blob throws `MalformedPairedServerRecordError`. Coercing corruption to `null` (never-paired) would hide tampering or silently force a re-pair — the exact anti-pattern AC3 forbids, closed structurally. Recovery (delete + re-pair vs hard error) is deliberately left to the consumer — the [ADR 0005](../decisions/0005-secret-at-rest-safestorage-fail-closed.md) "recovery is a consumer decision" principle, same posture as #43.
- **Structural validation only — `decodeRecord` checks the shape we wrote, not the values.** It rejects bad JSON, non-objects, `null`, arrays, and any of the four fields missing / non-string. It does **not** validate the relay URL scheme or token — that is #9's job, run *before* `save`. This guard defends only against a corrupt/foreign decrypted blob, not against bad pairing input.
- **Pick the four fields explicitly on both encode and decode.** `encodeRecord` writes exactly `{server, relay, token, server_static_pubkey}`, so a caller's stray fields are never persisted (a test seeds `{...RECORD, extra: 'leak-me'}` and asserts `extra` never lands). `decodeRecord` re-picks the same four, dropping any extra keys a blob may carry. Belt-and-suspenders against both an over-eager caller and a foreign blob.
- **Re-used the #42/#43/transport security discipline verbatim:** **log-free by construction** (no `console.*` anywhere — a dedicated test spies all six `console` methods across `save` + `load` + every error path and asserts none fire, so the `token` never reaches stdout); **static error message** carrying no field value (`MalformedPairedServerRecordError`); the record held only as opaque locals, never a named field of a logged struct; **zero renderer/preload/IPC surface**, so "the token never reaches the renderer" (AC4) is structural, not conventional.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The record type aliases `QrPayload` rather than re-declaring the four fields** — so drift from the wire contract becomes a type error, not a silent divergence. (Elaborated as the first "Patterns established" bullet above.)

No re-render / effect-cleanup / dependency-version surprises to record — this is a pure main-process module with no React, no timers, no listeners, and no new dependency. The near-twin structure to #43 meant no new pitfalls surfaced.

## Deferred (open questions carried forward)

- **Composition-root wiring is deferred, not this ticket.** #44 has **no runtime consumer** — nothing calls `save`/`load` until #9 (pairing input) persists and the transport (#7/#30) reads at connect time. Wiring it into `index.ts` with no caller would be untestable and premature (the #21/#22/#42/#43 defer-wiring precedent), so `src/main/index.ts` stays untouched. The recorded assembly recipe for the consumer: `createPairedServerStore({ secureStore: createSecureStore({ encryption: electronSecretEncryption(), persistence: fileSecretPersistence(join(app.getPath('userData'), 'secrets')) }) })`, then `save()` after #9 validates / `load()` at connect time.
- **Per-server-id keying is out of scope.** Milestone 1 pairs a single pyrybox → one record under `PAIRED_SERVER_NAME` (`'pyrycode.paired_server'`). Mobile keys per server-id; appending `.${serverId}` is a **one-line change** the explicit constant + injectable `name` already enable (a test exercises the injected-name seam). **Security note carried forward:** when that lands, a `serverId` derived from a QR/paste field becomes part of the store *name* and must be validated/encoded before use so it can't influence the persistence path. Today the name is a **fixed constant** — no untrusted input reaches it, so there is no traversal surface. Deferred to the multi-server ticket.
- **Un-pair / forget is out of scope.** `SecureStore` already exposes `delete`; a `clear()` on this store is a one-line `secureStore.delete(name)` when a forget flow needs it. No AC required it (Simplicity First). Re-pair is handled by `save` overwriting (last-writer-wins, one blob kept — tested).
- **Token lifecycle beyond storage is out of scope.** Generation, rotation, expiry, and revocation of the pairing token are the daemon's / pairing flow's concern; this module only persists and returns whatever it is given. Rotation surfaces here only as `save` overwriting.
