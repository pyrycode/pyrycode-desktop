## Summary

Real-daemon twin of the merged fake-stack spec [#423](423.md), keeping **only its scratch branch**:
pairs one claude-less spawned `pyry` (the [#439 realDaemon fixture](../features/real-daemon-credential-light-e2e.md),
`spawnClaude:false, seedPromoted:false`) and promotes the single seeded Recent discussion through
`SaveAsChannelDialog`'s "Keep in scratch" arm — the one path that sends `promote_conversation` alone
over the real wire, with no `create_workspace_folder` prelude.

This is the tier's **marquee case**: pyrycode/pyrycode#949 is the exact contract gap the credential-light
real-daemon tier exists to catch — the daemon defined the `promote_conversation` type, payload, and
registry op but registered **no handler**, so save-as-channel answered `unsupported` on the real wire
while the entire fake-daemon suite stayed green (a fake answers anything). #949 has since shipped the
handler (Option B: flips `is_promoted` + `name`, ignores the payload `cwd`, replies
`conversation_updated { is_promoted: true }` correlated). This spec pins that fix.

**Provability rests on no-optimism.** The scratch `onSave` arm (`SaveAsChannelDialog.tsx:287-295`) fires
`promote_conversation` and closes the dialog — it never touches the list store. The seeded row moves
"Recent discussions" → "Channels" only after the daemon's `conversation_updated` reply drives
`conversationListBridge`'s `shouldRefreshList` re-list, and `partitionByPromotion` re-buckets the row by
`is_promoted`. A pre-#949 binary answers `unsupported`: no re-list fires, the row stays put, and the
"Channels" visibility assertion times out — the intended loud regression signal, the same
`conversation_updated` → re-list path #440's archive/restore already live-passed.

**Dedicated branch deliberately dropped** (scope call from the architecture spec, not an oversight): the
dedicated ("Move to dedicated channel folder") branch first sends `create_workspace_folder`, already
real-wire-proven by sibling #441, and under #949's Option B the daemon *ignores* the promote payload
`cwd` — so the dedicated leg's "promote with the daemon-returned path" contract has no real-wire DOM
surface on this tier (client concern, covered by the fake twin #423). Scratch isolates the #949 gap
cleanly and avoids a second ~180s claude-less launch for redundant coverage.

**Name-less seed, resolved before writing (no fallback built).** `seedRegistry` writes no `name`, so the
row renders "Untitled"; `SaveAsChannelDialog` seeds its Name field from `titleFor(row.name)` = `"Untitled"`
(non-blank) — Save is enabled with no typing, and the daemon accepts the promote since the seed is the
sole conversation (the promoted-name-uniqueness check passes trivially).

**Assertion = the #423 section-header trio minus the title-text check.** With exactly one seeded row, a
non-promoted row renders only the "Recent discussions" header and a promoted row renders only the
"Channels" header (a zero-row section renders no header — `ChannelList.tsx`), so "Channels appears AND
Recent disappears" fully captures the transition. The fake twin's `getByText('<name>')` check is dropped:
"Untitled" is neither unique nor meaningful, and `partitionByPromotion` keys on `is_promoted`
(title-independent).

## Patterns established

- **A verb is provable on the claude-less real-daemon tier only if its reply gates a visible DOM
  transition with no optimistic pre-render.** Sibling #442 (dequeue + set-session-settings, demoted to
  Inbox without shipping — both verbs proved DOM-invisible on this tier) stated this rule negatively; this
  spec is the positive instance — the scratch `onSave` arm's total absence of list-store interaction is
  what makes the section-header transition a sound, non-optimistic proxy for a genuine daemon round-trip.
- **Scope a real-daemon spec to the branch that isolates the daemon verb under test**, dropping a second
  branch whose daemon-side contract has already been proven by a sibling spec (here, `create_workspace_folder`
  by #441) even when the production UI offers both. Coupling two verbs in one assertion would make a
  failure ambiguous about which handler regressed.
- **List row → dialog on click, no thread-open needed.** Unlike #440/#441's specs (which open a seeded row
  into its thread first), Save-as-channel mounts on the list row directly (`ChannelList.tsx`'s
  `onSaveAsChannel={(row) => setSaveRow(row)}`), so this spec's drive is the shortest of the four sibling
  action specs: pair → readiness gate → click `.channel-list__save` → radio → Save → assert.

## Lessons learned

*Lifted from the PR body / architecture spec's resolved open questions — no fallback was pre-built for
either.*

- The name-less-seed concern (does Save enable, does the daemon accept the promote) and the
  no-optimism premise (is the promote reply-gated with no pre-render) were both resolved analytically
  before writing the spec, by reading `SaveAsChannelDialog.tsx` and `channelListViewModel.ts` directly —
  not deferred to a live run. Both held.
- No new fixture option was needed: `seedPromoted:false` (already added by #439/#441) is exactly the
  non-promoted-seed precondition this spec requires.
