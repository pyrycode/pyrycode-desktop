## Summary

**Not standard agent-developable work.** `e2e/real-claude.spec.ts` is gated out of the agent
pipeline (`testIgnore` in `playwright.config.ts`) — a dispatched developer agent has no daemon, no
`claude`, and no credentials, so it hits a clean SKIP and cannot observe the reply-fan-out path the
ticket is about. The issue's two falsifiers (step-zero re-run against a current-`main` `pyry`; the
suspect-1 `<daemonHome>/.local/bin/claude` fixture-seed contract) are specified as an **operator
checklist** to run on the live Mac stack, not as pipeline-runnable ACs. The only piece this ticket
could land through the pipeline was the doc reconciliation, and that is what PR#476 shipped.

**Context:** #448 (PR#450, merged 2026-07-15) fixed the *client-side* cause of the harness being red
— the thread screen hardcoded `conversation_id: 'default'`, which a real daemon rejects. After that
fix, `e2e/real-claude.spec.ts` is still red on the live stack for a **separate, environment-specific**
reason: the isolated-HOME daemon *delivers* the turn (`send_message enqueued`, no
`msgqueue: delivery failed` in `PYRY_E2E_DAEMON_LOG`; a manual PTY probe under the harness's exact
isolated-HOME conditions completes the identical turn in ~1s) but **no reply event ever fans back to
the app** — silence to the 120s spec timeout. Meanwhile `scripts/live-drive.mjs` (built app →
production relay → live Mac daemon → vault workdir) streamed a real reply in ~4s the same day,
proving the app and the live daemon both work; only the isolated-HOME harness path is broken.

**What actually landed (developer phase, pipeline-safe):**

- `docs/knowledge/features/live-e2e-runbook.md` — replaced the claim that `e2e:real-claude` is a
  working pre-ship gate with the honest state: it is red on the live stack for #449, SKIPs cleanly
  under `npm run e2e` (the `testIgnore` gate), and **`scripts/live-drive.mjs` is the current interim
  operator pre-ship gate**. Added a new cross-reference entry for `scripts/live-drive.mjs` itself.
- `e2e/real-claude.spec.ts` — a one-line `// TODO(#449)` note in the header comment recording the
  same honest-red state and pointing at `scripts/live-drive.mjs` as the interim gate. No assertion,
  no `testIgnore` wiring, no fixture touched.

**Deliberately not done here:** the suspect-1 fixture seed (symlinking a working `claude` into
`<daemonHome>/.local/bin/` inside the `claudeJsonBytes !== null` branch of `e2e/fixtures/realDaemon.ts`,
per the architecture spec's contingent contract at `:193-227`) was **not applied**. It flips no
pipeline-observable — the spec still SKIPs cleanly either way in-pipeline — and its only justification
is a live-verified pass the pipeline cannot produce. Landing it anyway would be exactly the
seeded-green move #448's fixture rule forbids (a fixture change that fits a symptom without a verified
live pass). The green-fork / red-pending-daemon-fork decision, and the fixture seed if suspect 1 holds,
are the operator's closing edit against the live stack — not reproduced or simulated here.

## Patterns established

- **A ticket can be entirely operator-gated and still need a developer-phase doc commit.** When an
  issue's real diagnosis requires a live external stack the pipeline structurally cannot reach
  (no daemon/claude/creds), the architecture spec should still carve out whatever slice *is*
  pipeline-verifiable — here, reconciling docs that had drifted to over-claiming a gate works — and
  scope everything else as an explicit operator checklist with contingent contracts (spelled out in
  full, ready to apply mechanically once the live result is known) rather than leaving the ticket
  fully unstarted.
- **A doc fix that only removes an over-claim needs no live verification to land.** Recording "this
  gate is currently red, use the other one instead" is a true statement regardless of how the live
  diagnosis eventually resolves — it doesn't need the fork outcome to be safe to commit now, unlike
  the fixture seed which does.
- **Never let a `// TODO(#N)` doc pointer silently go stale.** The header note and runbook entry both
  name #449 specifically so a future reader can distinguish "still under live diagnosis" from
  "operator resolved it, doc forgot to update" — the architecture spec's two named forks (green /
  red-pending-daemon) each carry an explicit doc-edit instruction for whoever closes the loop live.
