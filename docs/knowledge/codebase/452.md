# #452 — fake e2e: conversation archive → restore → delete lifecycle

Split from #422. Size **S**, not security-sensitive, no Figma section. PR #454, merged as `5cdb31d`.

## Summary

Adds `e2e/conversation-archive-lifecycle.spec.ts` — one new Playwright fake-stack UI e2e spec, **zero
production code**. It rides the same two merged fixtures as its sibling #451
([`launchPairedApp`](../features/e2e-harness.md) (#433) and `conversationStateFake` (#434)) on a single
launch, and covers the **destructive** lifecycle that had no e2e guard: archive, restore, delete. This is
the fake-stack twin of the real-daemon lifecycle spec #440 — both hit the same structural constraint and
land on the same assertion surface.

One FAB-created conversation is driven through:

1. **Archive** (Channel-info sheet, `Archive` pill) — asserted via the Archive view's Discussions tab
   count, `0 → 1`.
2. **Restore** (`.archive__restore`, on the Discussions tab) — asserted via the same count, `1 → 0`.
3. **Delete** (Channel-info sheet, two-step `Delete` confirm) — asserted as gone from **both** the
   re-listed Channel List and the Archive view.

### Why the Archive view, not the active Channel List

Two code-confirmed gaps (first documented on #440) rule out asserting against the active Channel List:

- **Gap A** — `conversationListBridge.shouldRefreshList` is `false` for `conversationCreated`, so a
  FAB-created conversation never enters the active list at create time. It first lands in the store when
  archiving triggers a `conversation_updated` → re-list.
- **Gap B** — `partitionByPromotion` (active-list split) filters on `is_promoted` only, with **no**
  `is_archived` filter, so an archived conversation keeps rendering in the active list. Active-list
  departure/return is unrealizable as an assertion. Latent product bug, flagged out of scope (same as #440).

`partitionArchived` (Archive view) *does* filter `is_archived`, so its tab counts (`tabCountLabel`) are the
sound assertion surface for archive/restore. Delete is the one step where "gone" holds everywhere — it
**splices** the row from the fake's held list rather than tagging it, so the post-delete re-list drops it
from both surfaces at once; that Channel-List absence is the load-bearing "deleted from store" proof (the
Archive-view absence alone wouldn't distinguish delete from the already-restored `Discussions (0)` state).

## Patterns established

- **Two-step destructive confirm resolves by name in both states.** The Channel-info Delete pill arms on
  first click (`onDelete`, no wire traffic) and is replaced by a confirm block with `Cancel` + a second
  `--danger` button, also labelled "Delete". Exactly one button named "Delete" renders per state, so
  `getByRole('button', { name: 'Delete', exact: true })` resolves unambiguously both times; asserting the
  interposed confirm-prompt text between the two clicks pins the arm→confirm transition so the second click
  can't race the first.
- **`.channel-info__action` is not unique** (confirmed again here, same as #451) — target Archive/Delete by
  accessible name.
- **Row-scoping by title avoids strict-mode violations once two rows exist.** After restore, the Channel
  List holds both the seed and the created row; the created row's re-entry click is scoped via
  `.channel-list__row` `.filter({ hasText: UNTITLED })` `.locator('.channel-list__row-open')` rather than a
  bare `.channel-list__row-open` click.
- **Count-delta assertions on `role=tab` labels are a robust reflect surface** for state that has no
  dedicated "empty" DOM marker — `tabCountLabel` renders `(0)`/`(1)` regardless of which tab is selected, so
  a delta can be asserted before switching tabs.

## Lessons learned

- **The Channel-info sheet does not always need the `.status-sheet__close`-first workaround #451
  discovered.** #451's rename path leaves the sheet open (the rename dialog's `onSave` closes only the
  dialog), so `.conversation__back` needs the scrim closed first. Here, **both** `onArchive` and
  `onDeleteConfirm` call `onClose()` after dispatching (`ConversationScreen.tsx:1122,1136`), unmounting the
  sheet automatically — so `.conversation__back` is immediately clickable after Archive or a confirmed
  Delete, and adding `.status-sheet__close` first would fail (the button no longer exists to click). The
  lesson generalizes: whether the sheet auto-closes after an action depends on that action's own callback
  wiring, not on the sheet shell itself — check the specific `onX` handler before assuming either behavior.
- **A splice-based delete needs a control subject to prove precision.** The promoted, never-archived seed
  conversation stays present and unarchived through every step; its continued presence at the final
  assertion is what proves the delete verb targeted only the created row and not a wider wipe.
