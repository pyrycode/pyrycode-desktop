# #464 — fake e2e: unpair and re-pair return to the app-root PairingScreen

[Ticket](https://github.com/pyrycode/pyrycode-desktop/issues/464) · PR [#477](https://github.com/pyrycode/pyrycode-desktop/pull/477) · Spec: `docs/specs/architecture/464-unpair-repair-fake-e2e.md` · Size **S** · coverage-only, zero production code · not `security-sensitive` · no Figma

Split from #429 (child A — sibling of #465 / #466, the #422-family of per-flow fake-e2e specs riding the shared `launchPairedApp` (#433) fixture).

## What it covers

`e2e/unpair-repair.spec.ts` — the **session-EXIT path**: the flip from a paired, connected thread back to the app-root `PairingScreen`. Only the initial pairing happy path had e2e coverage before this; the exit path had none. Two affordances drive it, both funneling through the same `runUnpair` → `onUnpaired()` → `App.tsx setRoute('pairing')` flip:

- **Unpair (block A, one launch)** — the two-phase `UnpairControl` confirm in `ConversationScreen`. Clicking `Unpair` opens `Forget this pairing?`; `Cancel` returns to idle keeping the session (thread still mounted, `Send` still enabled, `textarea[aria-label="Pairing code"]` at count 0); re-opening and clicking `Confirm` (same launch — Cancel keeps state, so no second launch is needed) flips to the app-root `PairingScreen`.
- **Re-pair (block B, its own launch)** — the `RepairControl`/`RepairPrompt` (#167) `Re-pair` button, shown only when `shouldOfferRepair(status)` is true. A fatal relay close is terminal, so this case needs its own `launchPairedApp()` call.

## Test-only infra added (production relay path untouched)

Two additive edits made the Re-pair trigger reachable on the fake stack:

- **`src/main/transport/fakeRelayForwarder.ts`** — new `closeClientLeg(code: number): void` on `FakeRelayForwarder`, alongside the existing `dropClientLeg()`. Body: `if (clientLeg !== null) clientLeg.close(code)` — a clean WS close with a caller-chosen code, contrasting `dropClientLeg`'s abnormal `terminate()` (1006, which a supervised client treats as retryable and auto-reconnects from). A code in the client's `DEFAULT_FATAL_CLOSE_CODES` (`4401`/`4421`/`4426`, `relaySupervisor.ts:40`) instead drives the client to a **terminal, non-retryable** failure — no re-dial armed — which is what surfaces `Re-pair`. The code is an opaque numeric argument; the module's content-blind import discipline (only `ws` + Node built-ins) holds unchanged. Reuses the existing identity-guarded leg-null-on-`close` handler (#416) verbatim — no new nulling logic.
- **`e2e/fixtures/launchPairedApp.ts`** — `PairedApp` gained a `forwarder: FakeRelayForwarder` field, added to both return sites (the `reuseUserDataDir` path and the default drive path). Previously the forwarder was deliberately withheld ("no in-scope spec needs its leg controls"); #464 is the first in-scope consumer of a forwarder leg control. Purely additive — existing consumers destructure a subset (`{ page }`, `{ page, daemon }`, …), so no call-site cascade.

## Patterns established / reused

- **The app-root `PairingScreen`'s `Pairing code` textarea is the unambiguous teardown proof for a top-level route flip** — its **visibility** proves return-to-pairing, its **count-0 absence** proves the session stayed intact. This is a clean corollary of the #465 same-component-two-routes discipline, not a new problem: `PairingScreen` also renders at the in-shell `pairServer` route (#465), but *that* ambiguity doesn't apply here because both #464 exits flip the top-level `App` route and unmount `PairedShell` entirely — the app-root pairing route simply isn't mounted while on the thread, so no round-trip proof (unlike #465's Cancel→Settings) is needed.
- **Select the four Unpair/Cancel/Confirm/Re-pair buttons by role + accessible name, never by class** — all four carry the shared `conversation__unpair` class; only one is present at a time given the phase, so the name alone disambiguates.
- **A fatal-close test hook, verified reachable end-to-end before writing the spec** (the #440 realizability discipline, applied proactively rather than reactively this time): the architecture doc traced `closeClientLeg(4401)` → `relayConnection.ts` peer-close forwards the raw code verbatim → `relaySupervisor.ts` `DEFAULT_FATAL_CLOSE_CODES` match → `emitTerminal` (no re-dial armed) → `daemonConnection.emitFailed(code, retryable: false)` → renderer `sessionStore` error status → `shouldOfferRepair` true, entirely through merged code, before any infra was written.

## Lessons learned

From the merged PR's own "Lessons learned" section:

- The app-root pairing route is not mounted while on the thread, so `textarea[aria-label="Pairing code"]` `toHaveCount(0)` is a clean session-intact proof (Cancel) and its visibility a clean return-to-pairing proof (Confirm / Re-pair) — no same-component ambiguity here (unlike the in-shell pair-another route, #465), because both exits flip the *top-level* App route and unmount `PairedShell` entirely.
- Standalone-`tsc` over `e2e/` surfaces 4 pre-existing errors — the `{ ...process.env }` (`string | undefined`) spread assigned to Electron's `env: { [key: string]: string }` in `electronApp.ts` / `realDaemon.ts` / `smoke.spec.ts` / `launchPairedApp.ts`. Latent (the project never typechecks `e2e/`) and unrelated to this ticket; the new spec and infra are type-clean.
