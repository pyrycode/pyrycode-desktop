## What it covers

`e2e/paired-shell-navigation.spec.ts` — every `PairedRoute` transition in `PairedShell`'s `nextPairedRoute` reducer that had no e2e coverage beyond the launcher's own single `list → thread` click: the pair-another-server round-trip (#152) and the back-navigation chain (`thread → list → settings → list → archive → list`). One `test()` block, one `launchPairedApp()` launch, one continuous drive — none of these transitions mutate persistent or session state, so no second launch is needed (the #425/#427/#428 one-block precedent, now generalized to five transitions).

- **Pair another server** — from Settings, "Pair another server" opens the in-shell `PairingScreen` (`pairServer` route); asserted via the `'Paste pairing code'` heading.
- **Cancel→Settings round-trip** — clicking Cancel on that in-shell pairing surface returns to the **Settings screen**, not the app-root pairing screen. This is the teardown proof (see below), not the pairing-surface render itself.
- **Back-navigation chain** — `.conversation__back` (thread→list), `.settings__back` (settings→list), `.archive__back` (archive→list), each landing arrival asserted via its screen's distinctive root `section[aria-label=…]` hook before the next click.
- **No wire scripting anywhere in the spec** — DOM visibility and real product-UI clicks only; no `daemon.pushFrame`, no custom `buildReplyFrames`, no forced route dispatch. The default launcher seed is sufficient since nothing downstream reads a daemon reply.

## Patterns established / reused

- **Teardown is provable only via a round-trip, not an on-surface assertion, when two routes render the identical component.** The `pairServer` route and the app-root pairing route both render `PairingScreen` — the DOM is byte-identical whether the session survived or was torn down, so asserting *on* the pairing surface can't distinguish them (the #440-realizability discipline: don't assert something unrealizable). The observable that *does* separate them is the **Cancel destination**: in-shell Cancel dispatches `pairServerCancelled`, which the reducer lands on `settings`, so the Settings screen re-renders — proving the shell (and session) was never torn down. A teardown would instead leave the app-root pairing screen with no Settings to return to. This generalizes past #465: any future in-shell surface that shares a component with an app-root/torn-down equivalent needs the same round-trip proof, not an on-surface assertion.
- **Identical accessible names across sibling screens select by scoped class, not role-name.** The thread/settings/archive back buttons all expose `aria-label="Back"`. `getByRole('button', { name: 'Back' })` would resolve unambiguously in this spec (only one screen renders at a time), but the spec selects by screen-scoped class (`.conversation__back` / `.settings__back` / `.archive__back`) instead — self-documenting and immune to a future screen mounting two back-labeled controls at once.
- **One block, one launch, now for five chained transitions.** Extends the #425/#427/#428 "one launch when nothing under test is one-way" precedent from three server-push flows to five pure client-side nav transitions — reinforcing that the deciding factor is state one-wayness, not transition count.

## Lessons learned

- Teardown-vs-in-shell pair-another is provable **only** via the Cancel→Settings round-trip, not an on-pairing-surface assertion: the `pairServer` route and the app-root pairing route render the identical `PairingScreen`, so the DOM on the pairing surface is byte-identical whether or not the session survived. The load-bearing observable is the Cancel destination (Settings screen renders again), not the pairing render itself.
- The three back buttons (thread/settings/archive) all expose the identical accessible name `'Back'`; select them by screen-scoped class (`.conversation__back` / `.settings__back` / `.archive__back`) rather than role-name.
