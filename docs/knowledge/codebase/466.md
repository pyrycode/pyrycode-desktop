# #466 — fake e2e: push-notification toggle persists across an app relaunch

[Ticket](https://github.com/pyrycode/pyrycode-desktop/issues/466) · PR #468 · Spec: `docs/specs/architecture/466-push-toggle-persist-relaunch-fake-e2e.md` · Size **S** · coverage-only, zero production code · not `security-sensitive` · no Figma

Split from #429 (→ #464 unpair+re-pair / #465 PairedShell navigation / #466 this ticket). Sibling of the #422-family of per-flow fake-e2e specs riding the shared `launchPairedApp` (#433) fixture — but the first of that family to need **two launches**, since the thing under test (persistence) is only observable across a process boundary.

## What it covers

`e2e/push-toggle-persist-relaunch.spec.ts` proves the push-notification preference (`pyry.pushNotificationsEnabled`, #408 store / #409 UI) survives a full app relaunch that reuses the same `--user-data-dir`, so a storage regression (wrong key, hydration bug, clear-on-boot) can't silently reset it uncaught.

- **Launch 1** — `launchPairedApp()` (default drive, ends on the thread) → back to list → Settings gear → assert the switch (`getByRole('switch', { name: 'Push notifications when claude responds' })`) starts **checked** (default-empty ⇒ ENABLED, #408) → click it → assert **unchecked**.
- **Relaunch barrier** — `await app.close()` (releases the `SingletonLock`, flushes renderer `localStorage` on graceful exit) then `await daemon.close()` (kills daemon 1 so launch 2 provably cannot reconnect through the persisted launch-1 relay URL — a deterministic no-live-daemon scenario, not just a benign one).
- **Launch 2** — `launchPairedApp({}, { reuseUserDataDir: userDataDir })`, which lands directly on the ChannelList with no pairing drive and no connection wait → Settings gear → assert the switch is **unchecked**. A reset-to-default regression would render it checked; unchecked is the entire test.

## Patterns established / reused

- **A relaunch/persistence spec needs a fixture affordance the family didn't have yet: reuse a `--user-data-dir` across two launches and skip the pairing drive on the second.** Added as one narrow, additive control on `launchPairedApp` (`e2e/fixtures/launchPairedApp.ts`) — a second optional parameter `control?: LaunchControl` with a single `reuseUserDataDir?: string` flag, plus one additive `PairedApp.userDataDir` return field. `LaunchPairedAppOptions` (the existing daemon-reply passthrough, first param) is untouched, so all ~9 existing consumers are unaffected. Dir-reuse and drive-skip are deliberately **one** flag, not two independently-settable options: a reused *paired* dir must skip the drive, because the paste→Pair→Confirm steps would hang waiting for a pairing screen that never appears on an already-paired boot.
- **On the reuse launch, the forwarder + daemon still start, unconditionally.** The reuse launch's daemon is vestigial (the app dials the *persisted* launch-1 relay URL baked into the pairing blob, not launch 2's fresh forwarder port) but is started anyway so `PairedApp.daemon` stays a non-optional `FakeDaemon` — making it optional would ripple a possibly-undefined check through every `daemon.pushFrame` consumer across the #425/#426/#427/#428/… family. A deliberate simplicity-vs-fan-out trade: one throwaway daemon per relaunch test beats a cross-consumer type cascade. The wasm codec is compiled once per process, so the second start is cheap.
- **The reuse launch returns at the list, not the thread, and skips both the row-click and the Send-enabled wait.** `routeForStatus` (App.tsx) reads the *persisted pairing record* at mount, independent of the Noise handshake — so `section[aria-label="Conversations"]` is reachable with zero live-daemon interaction. Waiting for Send-enabled the way the default drive does would hang, since the persisted relay URL can't reconnect through a new forwarder port.
- **Teardown ordering: exactly one `rm`, drained after both launches close.** The reuse launch does *not* register its own `rm` teardown — the minting (first) launch already pushed one, and Playwright's LIFO drain runs it last, after every app on that dir has closed. This is the first fixture change in the family to require reasoning about teardown ordering across two launches sharing one fixture instance.
- **`app.close()` before the second launch is a hard barrier, not a convenience.** Two Electron processes on one `--user-data-dir` collide on the `SingletonLock`; `await app.close()` is also the point renderer `localStorage`'s LevelDB commit gets flushed to disk on graceful exit, which is what makes the DISABLED value durable for launch 2 to read. Skipping or not awaiting it manifests as a launch-2 timeout, not a wrong-value assertion failure.

## Lessons learned

- A persistence-across-relaunch scenario is structurally different from every other #422-family spec: those all prove something within one continuous session (server-push, request→reply, or pure client nav); this one can only observe its target by tearing an Electron process down and standing a second one up on the same disk state. That forced the first two-launch spec in the family and the first fixture change that has to reason about cross-launch teardown ordering (single `rm`, drained last) rather than single-launch teardown.
- `app.close()` doing double duty — releasing the `SingletonLock` *and* flushing `localStorage` — means the barrier before a relaunch is not just "wait for the process to exit" but "wait for the exact exit path that flushes state." A crash-close or a forceful kill would not give the same guarantee; this spec relies on `close()`'s graceful-shutdown behavior specifically.
- Coupling `reuseUserDataDir` to drive-skip as a single flag (rather than two orthogonal options) kept the fixture surface small, but it means any *future* reuse scenario that wants a reused-but-still-drive-the-pairing-UI combination isn't representable without extending the type — not needed here, worth knowing before the next fixture consumer assumes independent knobs.
