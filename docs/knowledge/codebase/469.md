# #469 — bug: filter archived conversations out of the active Channel List

**Shipped:** 2026-07-16 · **Size:** XS · **Security-sensitive:** no · **Type:** bug (Gap B, from
#440/#452). PR #478, commit `509b0cf`. Spec: `docs/specs/architecture/469-active-list-archived-filter.md`.
See [Channel List home screen](../features/channel-list.md) for the feature line this fixes.

## Summary

Archived conversations rendered in **both** the active Channel List and the Archive screen: the active
list's `renderBody` → `partitionByPromotion` (`channelListViewModel.ts`) split store rows by
`is_promoted` only and never filtered `is_archived`. This was a latent regression in #366 (Channel Info
→ Archive action) — #366's AC "the archived conversation leaves the active channel list" was assumed
free via the #275 `conversation_updated` → re-list, but the re-list returns the row still tagged
`is_archived`, and nothing downstream dropped it. Documented as "Gap B" during #440's architecture review
and worked around in both #440 and its fake twin #452, which had to assert archive/restore against the
Archive view instead because the active list couldn't be trusted.

Fix, exactly as specced:

- New `partitionActive(rows)` in `channelListViewModel.ts` — filters `!r.is_archived` first, then
  delegates to the unchanged `partitionByPromotion` for the channels/discussions split. The exact dual
  of `archiveViewModel.partitionArchived` (which filters `r.is_archived`). `partitionByPromotion` itself
  is untouched — it stays the neutral shared primitive both `partitionActive` and `partitionArchived`
  wrap, since baking the archive filter into it directly would have stripped every row the Archive
  screen feeds it (which passes an already-`is_archived`-filtered subset) and broken that screen.
- `ChannelList.tsx`'s `renderBody` switched from `partitionByPromotion` to `partitionActive`, **and** the
  empty-state guard moved from a raw `conversations.length === 0` check to
  `channels.length === 0 && discussions.length === 0`, computed *after* the partition. A store holding
  only archived rows has `conversations.length > 0` but zero active rows — the old guard would have
  fallen through to a blank body (no rows, no empty message); the new guard covers loaded-zero and
  all-archived with the same check.

Four files touched: `channelListViewModel.ts` (+15), `channelListViewModel.test.ts` (+45),
`ChannelList.tsx` (+16/-6), `ChannelList.test.tsx` (+24). No store, transport, IPC, or wire changes —
pure render-path filtering over the already-live `conversationListStore` slice.

## Patterns established

- **A new dual function, not a shared-primitive change, when a filter has exactly two asymmetric
  callers.** The same seam #348's `partitionArchived` established (filter first, delegate to
  `partitionByPromotion`) is now used twice from opposite ends (`is_archived` vs `!is_archived`),
  confirming `partitionByPromotion` as a stable neutral primitive rather than a candidate for a
  parameterized `filter?` argument — matches the mirror-image-verb-gets-mirror-image-function precedent
  already recorded for #366's `requestArchiveConversation`/`requestUnarchiveConversation`.
- **An empty-state guard keyed on the raw store must move when a filter is added upstream of it.** The
  general lesson: any `X.length === 0` empty-state check written before a filtering step existed becomes
  silently wrong once one is added — the guard has to be recomputed from the filtered output, not the
  input. Worth checking on any future ticket that adds a filter ahead of an existing render-body branch.

## Verification

Implementation matched the architecture spec exactly — no code-review findings. Both new render-level
tests are direct regressions for the bug: an archived row absent from the active list's markup, and an
all-archived store rendering "No conversations yet" rather than a blank body. Four new `partitionActive`
unit tests mirror the existing `partitionByPromotion`/`partitionArchived` `describe` block shape (drops
archived rows, splits the non-archived subset by promotion, preserves store order, all-archived → both
sections empty).
