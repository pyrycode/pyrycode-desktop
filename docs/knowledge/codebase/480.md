# #480 — `live-drive.mjs` sets a failing exit code without skipping cleanup

**Shipped:** 2026-07-16 · **Size:** S · **Security-sensitive:** yes (credential-lifecycle bug fix, zero new trust boundary) · **Figma:** N/A (operator CLI script, no UI surface).
**Spec:** `docs/specs/architecture/480-live-drive-failing-exit-code.md` · **PR:** [#485](https://github.com/pyrycode/pyrycode-desktop/pull/485), security review PASS, no findings.

## Summary

`scripts/live-drive.mjs` — the interim operator pre-ship gate that pairs a throwaway device against the **live** daemon over the **production** relay and drives a real claude send — only `console.log`d `LIVE DRIVE GREEN`/`RED` and always exited 0. `npm run build && node scripts/live-drive.mjs .` reported success even on RED, so the script could not gate a chained command. Same bug class as [#479](479.md) (an operator gate that exits 0 when it should fail).

The fix defers the exit code via `process.exitCode` (never `process.exit` inside the guarded region), so Node applies the code only after the `finally` cleanup — close app, remove temp dir, `pyry pair revoke` the live pairing — runs to completion. The load-bearing constraint was that a naive `process.exit()` on a failure path would skip `finally` and leak a live credential.

## What shipped

- **RED/timeout path** — screenshots to `/tmp/live-drive-448-fail.png` (unchanged), then sets `process.exitCode = 1` and falls through to `finally`. Not converted into a thrown error — RED is a measured outcome, not an exception.
- **No-payload early exit** — used to be `process.exit(1)` *after* `pyry pair` had already created a device, which skipped the revoke and leaked a live credential. Now the check moved inside the guarded `try` and `throw`s instead, so `catch` → `exitCode = 1` → `finally` → revoke runs. This is the actual credential-leak fix.
- **`mkdtempSync` + `electron.launch`** moved from above the `try` to inside it. Previously a launch failure (or a bad app dir) threw before the `try` existed and leaked the temp dir. `userDataDir` and `app` are now `let`-declared `null` before the `try` and null-checked in `finally`, since on the no-payload path neither was ever created.
- **`finally` cleanup steps are independently guarded** — close app, then `rmSync` the temp dir (its own `try`/`catch` so a failure there can't prevent the next step), then `pyry pair revoke`. No single step's failure can skip another.
- **`PYRY_BIN` env override** (`process.env.PYRY_BIN ?? join(homedir(), '.local/bin/pyry')`) — the only way to force the pyry-pair-failure branch deterministically on a machine that already has a working `pyry`. Mirrors #479's `PYRY_BIN=/nonexistent` idiom. Default behavior is byte-for-byte unchanged when unset.
- The one legitimate `process.exit(1)` — the pyry-pair-failure branch — is **unchanged**: at that point no device and no temp dir exist yet, so there is genuinely nothing to clean up.

## Design: deferred exit code, not early termination

`process.exitCode = <n>` records the code without terminating; Node exits with it only once the event loop drains naturally, which happens *after* `finally`. The script already drained cleanly to exit 0 before this ticket (GREEN reached end-of-module), so the same drain path now carries whatever code was set. No forced `process.exit` at the end of the script was added or needed.

## Patterns established

- **A gate script sets `process.exitCode`, not `process.exit`, on every failure path that has cleanup pending.** `process.exit()` is only correct at a point where no resource has been created yet — reserve it for the earliest possible failure, and audit every other early-return for what it would skip.
- **A "no resource found" early exit that runs *after* a resource was already created must `throw` into the guarded region, not exit directly** — otherwise its cleanup is silently skipped. The tell is asking, at each early-exit site, "does anything exist yet that needs tearing down?"
- **Resource creation (`mkdtemp`, process launch) belongs inside the `try` whose `finally` cleans it up**, with the handle null-initialized outside and null-checked in `finally` — not above the `try`, where its own failure bypasses cleanup entirely.

## Lessons learned

*Lifted from the PR body's own "Lessons learned" section.*

- The spec's "Check B" (a bad app dir forcing a thrown step after temp-dir creation) was designed to pair against the live daemon locally. The `PYRY_BIN` forcing hook — added for Check A — turned out to also let the *entire* `finally` invariant, including revoke-on-a-thrown-path, be proven with a **stub** `pyry` binary and zero live-stack access, which is safer and equally deterministic. Worth keeping in mind for any future forcing-hook design on this script: a hook added for one check can end up de-risking a different one too.

## Testing

`npm test` (1950 pass; the one `fakeRoutingRelay.test.ts` failure is a pre-existing parallel-load flake, passes 12/12 in isolation, unrelated to this `.mjs`-only change) · `npm run build` clean. Three deterministic checks, none touching the live stack:
- **A** — `PYRY_BIN=/nonexistent node scripts/live-drive.mjs .` → exit 1, no temp dir ever created (proves the one legitimate `process.exit(1)` branch and its "nothing to clean up" invariant).
- **B** — stub `pyry` + bad app dir → temp dir created then removed, `pair revoke` runs, exit 1 (proves the full `finally` chain on a thrown-after-creation path).
- **C** — stub `pyry` emitting no payload → `throw` → `pair revoke` runs, exit 1 (proves the credential-leak fix directly).

The GREEN path and the live RED-vs-real-daemon path stay operator-only against the live stack, per the runbook — this ticket did not attempt to make the full round-trip runnable under CI.
