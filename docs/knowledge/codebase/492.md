# #492 — Decode the daemon `api_retry` frame into a typed `apiRetry` event

Transport slice of the api-retry-signal vertical, split from #488, peer of the `stall` transport (#315).
Shipped as PR #494 (`e08f33d`), code-review **PASS** (zero findings). Security-sensitive (adds a wire type
decoded from the relay socket, and — unlike `stall` — a genuine widening of what crosses main→renderer
IPC: one boolean and two integers instead of nothing); size S; a structural clone of #315 scaled from a
nullary arm to one carrying data. **No render** — the on-thread "attempt N/M" indicator is the sibling
slice #493, blocked on this one.

## Summary

When claude hits an API error it retries, rendering a live status line (`API error · Retrying in Ns ·
attempt N/M`). The daemon detects this and emits an `api_retry` frame on the v2 interactive stream
(pyrycode #1074, merged 2026-07-21; detector upstream tui-driver #303, closed), fanned out only to
`interactive`-capable clients — desktop already advertises `interactive` (`daemonConnection.ts:855`), so
the frame reaches us today. Before this ticket the frame was unmodeled and fell through
`parseInboundMessage`'s `default → inbound-unmodeled → null`. This ticket adds the same six thin,
additive touchpoints the `stall` (#315) template established, with one shape difference: this event is
**not nullary**.

- **Wire type** (`src/shared/wire/types.ts`) — `'api_retry'` joins `EnvelopeType`, beside `'stall'`.
  `ApiRetryPayload { conversation_id: string; active: boolean; current: number; total: number }` — all
  four fields always present, no `omitempty`. Doc-comment records the three contract traps that
  distinguish it from `stall`: **not onset-only** (`active: false` is an explicit falling edge, not
  derived from turn activity), the rising edge **re-fires as the count climbs** with no wire dedup, and
  **`current: 0`/`total: 0` is a legitimate "count unknown" state**, not an error.
- **Inbound decode** (`inboundMessage.ts`) — `{ kind: 'api-retry'; apiRetry: ApiRetryPayload }` joins
  `InboundDaemonMessage`. `parseApiRetryPayload` is `parseStallPayload` scaled from one field to four, but
  invents no new check — every field maps onto an existing helper: `requireString` (`conversation_id`),
  `requireBoolean` (`active` — a TYPE check, so `false` passes), two `requireNumber` calls (`current`,
  `total` — `typeof === 'number'`, so `0` passes for free). `case 'api_retry'` narrows before logging, then
  emits `inbound-decoded{code:'api_retry', bytes, hash}` — no decoded field logged. Returns a fresh
  four-field literal, never a spread of the incoming payload.
- **Consumer emit** (`daemonConnection.ts`) — one `case 'api-retry'` in the `switch (inbound.kind)`, a
  fresh **named-field** literal `{ type: 'apiRetry', active: inbound.apiRetry.active, current: …, total: … }`
  copied by name, never a spread of `inbound.apiRetry` — the anti-smuggling net: a decoder field added
  later cannot ride across IPC without an explicit edit here. `conversation_id` is dropped (never
  referenced). Deliberately stateless: no dedup, no coalescing, no timer, no last-value memo — which is
  what gives the wire's "re-fires as the count climbs" contract for free. Not compile-forced (this inner
  switch has no `assertNever` default) — the round-trip test is the guard, same posture #315 established.
- **`DaemonEvent` arm** (`src/shared/ipc/events.ts`) — `{ type: 'apiRetry'; active: boolean; current:
  number; total: number }` — the first status-liveness arm since `stallDetected` to carry a payload
  rather than ship nullary, because the render slice #493 needs the attempt counter and the wire gives it
  nowhere else.
- **Three exhaustive bridge no-ops** — `daemonEventBridge.ts`, `timelineBridge.ts`, `modalBridge.ts` each
  add `case 'apiRetry': return null` (in `timelineBridge.ts` joining the no-op fall-through cluster, *not*
  copying the now-owned `stallDetected` case — that arm is owned since #317 and out of scope here). All
  three are compile-forced by their `assertNever` default.

`npm test` 590/590 green (RED first: 19 failures across the six touched files before implementation),
`npm run typecheck`, `npm run build` all green. 13 files touched (7 production, 6 test), 0 new files — the
commit-time ≥5-production-file self-check trips here but is structurally unsatisfiable for this shape (see
the architecture spec's Scope note): the new `DaemonEvent` arm compile-forces a case in all three
exhaustive bridges, and the transport decode exists only to feed that arm.

## Patterns established

- **A non-nullary status-liveness arm follows the same six-touchpoint shape as a nullary one — only the
  literal at each end gains fields.** #315's `stall` proved the nullary shape (drop the one decoded field,
  emit `{ type }`); #492 proves the template generalizes cleanly to a payload-carrying arm without any
  structural change — same six touchpoints, same "fresh named-field literal, never a spread" discipline at
  both the decode and the emit. Future status frames that need to carry a value (not just an edge) should
  reach for this shape rather than inventing a new one.
- **A four-field wire payload needs no new helper if every field is a scalar the codec already knows.**
  `parseApiRetryPayload` confirms `requireString`/`requireBoolean`/`requireNumber` compose directly for a
  multi-field payload with no cross-field validation and no enum — scale `parseStallPayload`'s template up
  by adding one `require*` call per field, nothing else.
- **"Not onset-only, re-fires with no dedup" is satisfied by adding no state, not by adding a filter.** The
  correctness risk for a frame like this is a developer reaching for a debounce/dedup instinct; the correct
  implementation is the absence of any tracking, letting N frames produce N events for free.

## Lessons learned

- `requireNumber`'s docstring rationale ("JSON.parse never yields NaN/Infinity") is half-right:
  `JSON.parse('{"a":1e999}').a === Infinity` is reachable — only the bare `NaN` literal is rejected, as
  invalid JSON. Not exploitable here (a JSON number is a fixed-width double; no length-driven allocation),
  and the spec's security review deliberately routes the counter's defensive formatting to #493 rather
  than inventing an unprecedented client-side range check. Worth knowing before anyone quotes that
  docstring as a guarantee. (From the PR body; also recorded in the architecture spec's security review,
  finding 6.)
- The `switch (inbound.kind)` in `daemonConnection.ts` has no `assertNever`, unlike the three renderer
  bridges — a missing or wrong emit compiles silently. The round-trip test in `daemonConnection.test.ts`
  is the only guard on that leg. (From the PR body; same open item #315 carried forward, now a fifth
  ticket to rely on it.)

## Open questions carried forward

- **Inner-switch exhaustiveness.** `daemonConnection.ts`'s `switch (inbound.kind)` still has no
  `default: assertNever` — now five tickets deferred (#180, #199, #214, #315, #492). The round-trip test
  remains the deterministic safety net.
- **Counter formatting is #493's job, not this slice's.** The counter is type-checked but not
  range-checked (house posture — no precedent for range-validating a wire integer, and a client-invented
  bound would silently drop valid future frames). The render slice must format `current`/`total`
  defensively: never render a literal `"0/0"`, and never compute `current / total` without handling the
  legitimate `0/0` (→ `NaN`).
- **The sibling `compacting` frame (#489) needs the same seam** (`conversation_id` + `active`, no
  counter) but is explicitly out of scope here — no generic "status frame" abstraction was built to
  anticipate it, per the spec's speculative-generality guidance.
