# #504 — Unpair tears down the live daemon session

Spec `770e926` → dev `8da605f` → code-review **PASS (no findings)** PR#521. Security-sensitive; size S;
2 production files + 2 test files, 225 insertions, zero deviations from the architecture spec.

## Summary

`registerUnpairHandler` erased the stored pairing and nothing else, so an authenticated Noise session
outlived the record that authorised it: the renderer reset and routed to the pairing screen, but the
still-live session kept repopulating both `sessionStore` and `timelineStore` behind it — a not-paired
UI backed by a live authenticated session until the socket happened to drop.

The fix gives `registerUnpairHandler` the mirror image of the pairing handler's `onPaired`: an optional,
value-free `onUnpaired?: () => void` dep, called once after `clear()` resolves, wired at the composition
root to `connection.reconnect()`. **Zero `daemonConnection.ts` edits** — `reconnect()` already fences
the superseded driver's in-flight events (the `generation` bump is `dial()`'s first statement), closes
its socket, and — with the record now erased — settles at `failed{not-paired}` without constructing a
replacement, all verified line-by-line rather than assumed. See [daemon connection](../features/daemon-connection.md)
§ Teardown-on-unpair and [unpair channel](../features/unpair-channel.md) for the full contract.

The registration moved from `index.ts`'s store-only group (which cannot close over `connection`) down
to sit beside the pairing handler, below `createDaemonConnection`. Two now-stale comment blocks at the
old site were rewritten (one asserting "needs only the store — no `connection`", now false; one
describing the group's `will-quit` symmetry, now repointed to `unregisterPairingStatus`).

## Patterns established

- **A post-success callback that must never downgrade an already-completed mutation.** `onUnpaired`
  sits *outside* the fail-closed `catch` and is wrapped in its own try/catch that drops the caught
  object — the deliberate inverse of `onPaired` (`pairingHandler.ts:103`), which sits *inside* its try.
  The reason lives in the renderer, not the main process: `runUnpair` coerces both `result: 'error'`
  **and** a rejected invoke to "stay on the conversation screen, never flip the route." Cloning
  `onPaired`'s placement, or letting a teardown throw propagate, would both report failure for a
  record that is already gone — a paired-looking UI over an erased record, worse than the bug being
  fixed. The rule: once the security-critical step (the erase) has committed, a post-hoc side effect's
  own failure must never be allowed to relabel that commit as failed.
- **`reconnect()` as a "re-dial from disk" primitive, not a "disconnect" primitive.** This is why the
  same method safely serves three unrelated callers (connect-on-pair, reload-per-dial's automatic
  retry, and now teardown-on-unpair) with zero new state: every caller converges on "connect to
  whatever the store holds right now, or fail closed if it holds nothing," which is also what makes a
  concurrent unpair/re-pair interleaving race-safe without any interleaving-specific code.
- **A wiring fix needs a test that composes the wiring, not the mechanism it reuses.** The regression
  test could not just drive `connection.reconnect()` directly — that already fences on unmodified
  `main` and would prove nothing. It had to register the real `registerUnpairHandler` against a real
  `DaemonConnection` (there is no `index.test.ts`), the same technique [#518](518.md) used for its
  orchestrator AC.
- **A "nothing arrives" assertion needs a positive control.** The regression test drives the same
  `message` frame once *before* the unpair (proving it reaches the sink while the session is live) and
  once *after* (proving it doesn't) — without the first drive, a mis-shaped fixture could pass the
  "nothing arrives" assertion vacuously.

## Lessons learned

- One mutable `record: PairedServerRecord | null` variable shared by two closures — `build({ load: () =>
  Promise.resolve(record) })` and a fake `ClearablePairedServerStore` whose `clear()` sets `record =
  null` — models the real store pair (erase-then-read-through) with no new test helper. A `repair()`
  closure over the same variable made the re-pair regression case (AC5) nearly free to add alongside it.
- The two teardown tests only jointly pin `reconnect()` over `stop()` as the mechanism: either test run
  alone under-constrains the implementation (a `stop()`-based teardown would pass the "driver stopped"
  assertion but fail either the `['connecting','failed']` event-sequence assertion or the re-pair test,
  never both from one test). When an architecture doc says "these N tests jointly cover this," re-check
  what each proves in isolation before trusting the set.
- The base moved between the ticket body being written and the architecture spec being read (#518
  merged in between, +58 lines) — two of the ticket body's own file:line anchors were already stale by
  the time the spec was drafted (`daemonConnection.test.ts:135-147` → `:154-207`; `:858` → `:912-930`).
  A spec's anchors are only as fresh as its own stated base commit, not the ticket's.
