**Spec:** `docs/specs/architecture/505-*.md` · **PR:** [#523](https://github.com/pyrycode/pyrycode-desktop/pull/523). Closes [#505](https://github.com/pyrycode/pyrycode-desktop/issues/505). Extends the [#116](116.md) connection-teardown net; corrects a scoping belief recorded in [#169](169.md).

## What it does

An armed [`bundleReassembler`](../features/debug-bundle-reassembly.md) settles its consumer only via chunk/done/fail — no timeout. Two connection-teardown paths reached no fail at all, wedging the [orchestrator](../features/debug-bundle-orchestrator.md)'s single-in-flight `active` flag for the rest of the process lifetime after just one badly-timed relay hiccup:

1. **`relay-link-down`** emitted `relayLinkChanged` but never failed the reassembler. A retryable close is stream-fatal anyway — the supervisor re-dials into a fresh Noise session with no resume, so the daemon-side request dies and no more chunks arrive.
2. **`dial()`** bumps `generation` *before* stopping the old driver, so the superseded driver's `terminal{1000}` is dropped by the generation fence and never reaches the existing `terminal`-arm fail. Both live triggers are `connection.reconnect()` at the composition root (re-pairing, and unpairing since [#504](504.md)).

## What shipped

One new module-local helper, `failBundleStream()`, inserted in `src/main/daemonConnection.ts` right after `emitFailed`:

```ts
function failBundleStream(): void {
  const abandoned = reassembler
  reassembler = null
  abandoned?.fail('connection-lost')
}
```

Release-then-fail (not fail-then-release): the slot is cleared before the consumer's synchronous `fail` call runs, so the module never holds a reference to a stream it has already abandoned. Idempotent and total — `?.` absorbs an empty slot, the reassembler's own `settled` flag absorbs a second fail — so "exactly one terminal" stays a property of construction, not a guard added here.

Four call sites, all `failBundleStream()`:

| Site | Before | Notes |
|---|---|---|
| `relay-link-down` arm | (nothing) | Inserted as the arm's first statement, **above** the close-code classification — the emitted `relayLinkChanged` is byte-identical for every close code, so the new fail discloses nothing about it. |
| `terminal` arm | `reassembler?.fail('connection-lost')` | Same position; now also releases the slot. |
| `error` arm | `reassembler?.fail('connection-lost')` | Same position; now also releases the slot. |
| `dial()` | (nothing) | Added as the fourth per-connection reset, alongside `outstandingAnswers`/`pendingSettings`/`pendingCreateFolders.clear()`, before the `connecting` emit. Must live in `dial()` itself — the generation fence already dropped the old driver's `terminal`. |

The daemon `error`-reply arm (a different code path, correlated via FIFO, keyed on the wire's `error` reply rather than a connection-lifecycle event) deliberately keeps its own inline `reassembler?.fail('daemon-error')` and was **not** converted — `failBundleStream()` encodes the connection-lifecycle teardown net specifically, and converting an unrelated branchy path would be scope creep the ticket didn't call for.

## Patterns established

- **A shared teardown helper beats N copies of the same two-line pattern once N reaches four.** The `terminal`/`error` arms already had the fail call; folding them into `failBundleStream()` alongside the two new sites means the slot-release behavior is uniform across all four rather than added to two and missed on two.
- **Release-then-fail, not fail-then-release, for a slot whose settle callback hands control outward.** Clearing the field before calling `consumer.fail` means the module holds no reference to an abandoned stream at the moment control leaves it — cheap insurance against a future consumer that settles synchronously, even though today's real consumer path (`webContents.send`) is asynchronous IPC and can't re-enter.
- **The wedge is only observable through the real orchestrator, not a spy consumer.** `active` lives in `debugBundleDownload.ts`, not the reassembler — three of the six new tests compose the real `createDebugBundleDownload` over the real `connection.requestDebugBundle` and assert on whether a *later* `download.request()` reaches the wire, the only way to actually see the flag clear.
- **Assert the fail lands *at* the teardown event, not on the end state.** A bare "exactly one terminal" assertion passes on unfixed `main` too, because a trailing `terminal` supplies that one fail regardless. The straggler test asserts `failed` immediately after the link-down, before the later terminal/chunk arrive.
- **A synchronous, pre-`tick()` assertion is what proves a fail came from `dial()` and not from the new driver.** `gen = ++generation` fences the superseded driver's `terminal{1000}` before any `await`, so asserting `failed` before `await tick()` is the only position that isolates `dial()`'s own fail from a coincidentally-timed one on the fresh driver.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The wedge is only observable through the real orchestrator.** A spy consumer driven directly cannot distinguish "wedged" from "fine" since `active` lives in `debugBundleDownload`, not the reassembler.
- **Assert the fail lands *at* the teardown, not on the end state.** A bare "exactly one terminal" assertion passes unfixed, because the trailing `terminal` supplies that one fail.
- **Release-then-fail is the safe ordering** for a slot whose settle callback hands control outward: the module holds no reference to a stream it has already abandoned while the consumer runs. Costs nothing and survives a future consumer that settles synchronously.

Code review added one non-blocking NIT (not a rework trigger): the composed link-down test's name/comment ("reaches the wire") slightly overstates what `FakeDriver.sent` proves — the fake records what `daemonConnection` hands the driver, not what reaches the socket (driver inertness during backoff is proven elsewhere, `noiseRelayDriver.test.ts:304-358`). "Reaches the driver" would be the exact phrasing; left as-is, not worth a rework cycle.

## Deferred / carried forward

- **A third, adjacent wedge — flagged to the PO for its own ticket.** `requestDebugBundle` gates only on `driver === null`. After `dial()`'s bootstrap microtask resolves — and after a `terminal`/`error` — the driver is non-null but **not live**: the reassembler arms, `driver.sendMessage` is silently inert pre-handshake/post-terminal, and nothing ever settles the consumer. Reachable from this ticket's own scenario (retrying the download while a reconnect handshake is still in flight). Not two lines to fix — needs a driver-liveness flag set at `handshake-complete` and cleared at `dial()`/`terminal`/`error`/`malformed-hello-ack`, a new sub-state-machine across ~6 sites with its own test matrix. The `send` twin's "no `connected` flag needed" rationale does not transfer, because a dropped `send` is harmless whereas a dropped bundle request strands a consumer.
- **No stream timeout — still explicitly out of scope**, per [#169](169.md)'s original ruling: a never-terminating or slow-dribble daemon stream needs a per-message read/idle deadline at the transport layer, not a timeout guessed in the orchestrator or accumulator. No such hang has been observed.
- **No total-bytes cap on the reassembled archive** — pre-existing, not introduced or worsened here (this change strictly *reduces* retention by releasing the slot early). Flagged alongside the driver-liveness follow-up.

## Corrects

[`docs/knowledge/codebase/169.md:36`](169.md) scoped the wedged-`active` failure mode to "a never-terminating daemon stream," reasoning that "a real socket drop already resolves via the existing `connection-lost` teardown net (#116)." That held only for a *fatal* close (surfaces as `terminal`) — it did not hold for a *retryable* close (surfaces as `relay-link-down`) or for a superseded driver's fenced `terminal` during `dial()`. This ticket closes both gaps; #169's file is left as historical record (its own "Deferred / carried forward" section already named the belief this ticket revisits), not edited.
