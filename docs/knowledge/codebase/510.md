# #510 — a modal answer clicked while disconnected re-surfaces after the reconnect

PR #544 (`75fcfe1`, spec `6c16b60`). Sibling of [#415](415.md) / [#195](195.md) / [#249](249.md) on the
same reducer. Size XS (PO estimated S; architect overrode down — one production file, one reducer arm,
zero new exported symbols, zero consumer call sites). `security-sensitive` (architect self-review PASS,
no blocking findings). Code review: **PASS**, 0 blocking, 1 NIT (pre-existing, not introduced here).

## Summary

An answer clicked while the relay link is down is dispatched optimistically (`answerPrompt` dispatches
`dismissed` outside its try block) but the send itself is swallowed: `answerModal` early-returns when
`driver === null` (`daemonConnection.ts:1394-1397`). The click still recorded the `modalId` into
`modalPrompts.ts`'s `resolved` slice, and the `shown` arm's resolved-first early-out then suppressed the
daemon's connect-time re-delivery of that same prompt unconditionally. The turn stayed blocked on an
invisible prompt until the daemon's 2-minute deny-on-timeout window resolved it — the user's explicit
Allow silently became a timeout deny, with no way to re-answer.

**This deliberately reverses shipped #415 AC3**, which preserved `resolved` across the `reconnected`
reset believing that prevented a double-show. The premise didn't hold: the daemon's connect-time
reconcile (pyrycode #876/#877, `Registry.Snapshot()`) re-sends only **still-outstanding** modals, so a
prompt it already resolved is never re-sent in the first place — retaining `resolved` across the reset
guarded nothing real, and cost exactly this bug.

One production file, `src/renderer/src/store/modalPrompts.ts`. The `reconnected` arm now clears both
per-connection slices, each behind its own no-change guard so the same-reference discipline survives:

```ts
case 'reconnected': {
  const outstanding = state.outstanding.length === 0 ? state.outstanding : []
  const resolved = state.resolved.length === 0 ? state.resolved : []
  if (outstanding === state.outstanding && resolved === state.resolved) return state
  return { ...state, outstanding, resolved }
}
```

`outstanding` keeps its reference when already empty — `PermissionModal.tsx:186` selects it under
`Object.is`, so minting a fresh `[]` would re-render the container for no state change. `rejections`
still passes through the spread untouched (no daemon repopulation path, #249). The `dismissed` arm is
**untouched** — the rejected alternative shape (record `resolved` only on a daemon-sourced `dismissed`)
would have had to relax it, colliding with the shipped ordering-edge test at `:119`; see Patterns
established.

Four load-bearing comments were rewritten alongside the behaviour, not just the arm itself: the
`resolved` docstring's "retain forever" claim, the `shown` arm's early-out comment, `reduceModal`'s
top-level docstring, and the `reconnected` arm's own rationale — all four previously asserted the (now
reversed) buggy behaviour as intent.

Three shipped #415 tests were updated in place, each keeping its `it(...)` slot and gaining a comment
naming #510 as the deliberate reversal — not deleted, not skipped:

- `:271` *"preserves the resolved slice by reference across the reset"* → now asserts it **clears**.
- `:295` *"same state reference on a reconnect after everything already resolved"* → now asserts a
  **new** state (a real change to clear), with `outstanding` preserved by reference.
- `:308` *"an optimistically-answered prompt stays suppressed if re-sent after the reset"* → now asserts
  it **re-surfaces**.

Plus new coverage for both required orderings: answered-then-reconnect-then-reshown (re-surfaces with
re-delivered fields, can be answered again, re-surfaces alongside a still-held sibling exactly once
each) and answered-then-dismissed-then-reshown with **no** reconnect (stays suppressed — today's
within-connection dedupe survives; the `dismissed()` fixture defaults to `source: 'remote'`, so the
user's own answer is passed `'local'` explicitly). A purity test confirms the reset does not mutate the
input state's `resolved` array. 39/39 in the touched file (RED first: 7 failing, then green); the #415/
#249 regression fence (`:109`, `:119`, `:280`, `:290`, `:302`) and the #416 reconnect e2e halves
(`modalBridge.test.ts`, `daemonConnection.roundtrip.test.ts:802`) pass unedited. `npm run typecheck` and
`npm run build` clean.

## Patterns established

- **On a reducer whose invariants live in comments, the comment corrections are part of the fix, not
  cleanup.** Four sites asserted the bug as intent; a diff that touched only the arm would have left the
  file self-contradictory. Budget prose time accordingly on this class of change.
- **A new "can re-answer" test can pass vacuously against the pre-fix reducer.** The `can be answered
  again` test's outcome assertions (`after.outstanding` empty, `resolved` re-recorded) are also what a
  same-reference no-op against an empty `outstanding` would produce — so without asserting the
  *precondition* (`before.outstanding` has length 1) and `after !== before`, it would have been green
  before the fix landed too. Assert the precondition, not just the outcome, when a test's whole point is
  "this used to be inert and now isn't."
- **Two independently-guarded slice clears, not one combined guard, because the common case only
  changes one of them.** The everyday sequence (answer, then a drop) leaves `outstanding` empty and
  `resolved` non-empty; guarding each slice separately is what keeps `outstanding`'s reference stable in
  that case (avoiding a needless `PermissionModal` re-render) while still clearing `resolved`. A single
  combined guard would have forced a fresh `outstanding` array whenever *either* slice needed clearing.
- **Verify a security claim with the cheapest artifact that settles it, not the most thorough one.**
  The architect's PASS rested on three independently-checkable facts, each settled by one grep or one
  QMD lookup rather than a deep trace: `shown` has exactly one production producer (`modalBridge.ts:45`,
  grep for `type: 'shown'` across `src/`); `answerModal` mints a fresh `answer_token` into a literal,
  never a spread (`daemonConnection.ts:1402-1410`); and the daemon's `Resolve` is a mutex-guarded
  one-shot (QMD `pyrycode-docs`, corroborated by upstream pyrycode#903's e2e for this exact scenario).

## Lessons learned

*(from the PR body)*

- The four load-bearing comments (the `resolved` docstring's "retain forever", the `shown` early-out,
  the `reduceModal` docstring, the `reconnected` arm) asserted the buggy behaviour as *intent* — a diff
  that changed only the arm would have left the file self-contradictory. On a reducer whose invariants
  live in prose, the comment corrections are part of the fix, not cleanup.
- One new test (`the re-surfaced prompt can be answered again`) passed vacuously against the pre-fix
  reducer: with `outstanding` empty, the follow-up `dismissed` is a same-reference no-op that trivially
  satisfies both assertions. Asserting the *precondition* (`before.outstanding` has length 1) and
  `after !== before` made it genuinely RED. Worth checking that each new test actually fails before
  implementing, not just that the suite as a whole does.
- `npm run lint` is not wired in this repo (no `lint` script in `package.json`) — `typecheck` + `build`
  are the gates.

*(from code review, not applied — filed as a follow-up, not a blocker)*

- **`PermissionModal.tsx:203`'s `pendingOptionId` (#226's second-confirm marker) is component-local
  `useState` keyed to option id, not `modalId`.** Option ids are generic (`allow`/`deny`) across prompts,
  so a confirm armed on one prompt can survive a swap and pre-arm the confirm view for a *different*
  prompt. #510 adds a new route to reach this: answer m1 while disconnected, arm (but don't confirm) a
  destructive option on m2, reconnect clears both slices, the daemon re-delivers m1 first — m1 renders
  pre-armed in confirm mode, one click from Allow. Pre-existing on `main` (reachable today without
  #510: arm a confirm, let deny-on-timeout dismiss that prompt, the next prompt renders pre-armed) — not
  a blocker, but the spec's Security review §8 reasoned only about the *answered* prompt's own arming
  (always null post-answer), not about a sibling armed at reconnect time. Worth a follow-up ticket to
  key the marker on `modalId`.
