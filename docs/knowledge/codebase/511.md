# #511 — Scope the second-confirm marker to the prompt it was selected on

`security-sensitive` · size **S**. Spec `59fe9cb`, shipped `f165b5c`, PR
[#545](https://github.com/pyrycode/pyrycode-desktop/pull/545). Refinement of the original report;
sibling of [#510](510.md) on the modal vertical (disjoint files, no ordering dependency). Two production
files, two test files, no new files. Code review: **PASS**, 0 blocking, 1 NIT (a shadowed `optionId`
identifier, cosmetic).

## Summary

`PermissionModal.tsx`'s #226 second-confirm marker held only a bare option id, with no tie to the prompt
it was selected on. The comment above its derivation asserted a cross-prompt safety net — a stale id
"falls back to list mode rather than confirming against the wrong prompt" — but that net could never
fire: daemon option ids are a **closed per-class vocabulary**, not per-prompt nonces
(`permission` → `allow_once`/`allow_always`/`reject_once`/`reject_always`, `trust` → `proceed`/`exit`,
QMD `pyrycode-docs` `modalbridge-package.md`). Two prompts of the same class share their entire id set,
so a held non-default id was *guaranteed* to match the next same-class prompt, not merely likely to.
Three routes swap `outstanding[0]` under a live marker — remote/timeout `dismissed`, `reconnected`
(widened by #510, merged first), and the empty-`outstanding` window ( `ConversationScreen.tsx` mounts
the container unconditionally, so returning `null` never unmounts it, and the state doesn't self-heal).
One click on Confirm could answer a prompt whose option list the user was never shown, with a
permission-granting option — the exact gap #226's own code review flagged and left as "not reachable
today," and that #510 widened by making the `reconnected` route re-surface previously-suppressed prompts.

The fix re-keys the marker instead of clearing it. `modalResolution.ts` gains:

```ts
export interface PendingConfirm {
  readonly modalId: string
  readonly optionId: string
}

export function resolvePendingOption(
  prompt: ModalPrompt | undefined,
  pending: PendingConfirm | null
): ModalOption | null {
  if (!prompt || !pending || prompt.modalId !== pending.modalId) return null
  return prompt.options.find((o) => o.id === pending.optionId) ?? null
}
```

`modalId` is the daemon's per-modal nonce — a `crypto/rand` UUIDv4 minted once per surfaced modal at the
single mint site (`Registry.Record`) — so it is distinct per prompt, the property the marker needed and
the option id never had. `PermissionModal.tsx` swaps its `useState<string | null>` for
`useState<PendingConfirm | null>`, renders `pendingOption = resolvePendingOption(prompt, pending)`, and
arms the marker as `setPending({ modalId, optionId })` where `modalId` is `onSelect`'s own first
argument — sourced by the view from the prompt it actually rendered, never re-read from a possibly-newer
store. The old comment asserting the ineffective net as intent is rewritten to state the real contract.

The option-id lookup inside `resolvePendingOption` is **retained, not deleted as redundant** — its job
is redemoted from the (broken) cross-prompt net to the within-prompt net for a `shown` re-delivery that
replaces the prompt in place with a changed option set, and it is still how the `ModalOption` the confirm
sentence names is obtained at all.

### Why re-derive instead of clearing on a prompt change

Re-deriving `pendingOption` every render, rather than clearing `pending` in an effect on prompt change,
means a stale marker is **inert** rather than something with a lifecycle to get wrong: it can only ever
match the prompt it was minted against, so the empty-`outstanding` window is structurally safe rather
than defended. This is also what made the fix provable at all — the repo's renderer has no DOM harness
(`environment: 'node'`, no `jsdom`/`@testing-library`), so a `useEffect`-based clear would have had no
way to be exercised; a pure function over `(prompt, pending)` slots directly into the existing
React-free `modalResolution.ts` seam and is unit-testable with plain values.

**Deliberate, named consequence:** if the *same* prompt returns (a `reconnected` reset followed by the
daemon re-sending a still-outstanding modal), the confirm sub-step is restored with the held option.
That's correct — the user did see that prompt's option list and did select that option on it.

### What did not change

`selectOption`/`SelectOptionDeps` in `modalResolution.ts` (`requestConfirm` keeps its
`(optionId: string) => void` signature; the container supplies `modalId` from its own closure), the
`PermissionModalView` props (still `pendingOption: ModalOption | null`), and the modal store
(`outstanding`/`resolved` semantics are untouched — the defect was entirely screen-local). No wire
change, no JSX/CSS/copy change.

## Patterns established

- **A "deterministic safety net" comment is a claim about the wire contract, not just the code —
  re-derive it against the actual vocabulary before trusting it.** The old comment was locally
  consistent with the code it sat above but wrong about daemon behavior; the repo's own test fixtures
  (`allow-once`/`deny`, disjoint ids) never exercised the collision because they didn't reflect the real
  closed vocabulary. A collision-class bug's regression tests need the real id sets or they prove
  nothing — this ticket's fixtures use the actual `permission`/`trust` option sets from QMD, not
  fixture-of-convenience ids.
- **Re-key transient state on a stable identity rather than adding a clearing effect**, when the
  underlying bug is "the key isn't unique enough." A `useEffect` reset would have needed a DOM harness
  this repo doesn't have to prove; a pure re-derivation over the correct key needed none. The general
  shape: before reaching for a lifecycle fix, check whether the state's *correlation key* is the actual
  defect.
- **A positive control is mandatory when every failure-mode assertion is "→ null."** A
  `resolvePendingOption` that unconditionally returned `null` would have passed every negative test in
  this ticket's suite; the AC3 same-prompt case (marker armed on A, rendered prompt A → returns A's
  option) is what catches that stub. Confirmed by mutation: dropping the `modalId` guard fails 4 tests,
  a `return null` stub fails 3 (the positive control among them). This is the same vacuous-pass shape
  #510's code review caught in a different reducer — worth checking for on any ticket whose tests are
  dominated by negative assertions.

## Lessons learned

*(from the PR body)*

- A "deterministic safety net" comment is worth re-deriving against the wire contract before trusting
  it. This one keyed client-owned trusted state on a daemon-controlled, non-unique value; the daemon's
  option ids are a 4-value closed set per class, so the net had a 0% hit rate for same-class prompts.
  The repo's own fixtures (`allow`/`deny`) hide this — the closed vocabulary is only visible in the
  daemon docs, so test fixtures for a collision bug must use the real id sets or they prove nothing.
- Re-deriving state each render beat clearing it on a change: there is no `useEffect` to get wrong, and
  — decisive here — no lifecycle to exercise, which matters because this repo's renderer has no DOM
  harness (`environment: 'node'`, `renderToStaticMarkup` only). Designing the fix as a pure function
  over `(prompt, pending)` is what made it provable without adding one.

*(from code review, not applied — cosmetic, non-blocking)*

- `PermissionModal.tsx:226`'s `requestConfirm: (optionId) => setPending({ modalId, optionId })` shadows
  the outer `optionId` parameter of the enclosing `selectOption(prompt, optionId, { ... })` call at
  `:221`/`:211`. Both bind to the same value at this call site (the click's own option id), so it is not
  a correctness issue — flagged as a NIT for readability only, left as shipped.

## Testing

`npm test -- modalResolution.test.ts PermissionModal.test.tsx interactiveRoundtrip.test.tsx
modalPrompts.test.ts` → 75 passed (9 new, RED before the fix); `npm run build` (typecheck + electron-vite)
clean.

- `modalResolution.test.ts` — new `resolvePendingOption` describe, fixtures drawn from the real daemon
  vocabulary (two `permission` prompts, distinct `modalId`s, identical `allow_once`/`allow_always`/
  `reject_once`/`reject_always` option sets): armed-on-A/rendered-A → returns the option; armed-on-A/
  rendered-B → `null` (also asserting B's list genuinely contains the armed id, so the test can't pass
  vacuously through an accidental non-match); `prompt === undefined` → `null`; `pending === null` → `null`;
  armed-on-A/A re-delivered without that option id → `null` (the within-prompt net); the `trust` pair
  cross-prompt → `null` (the second closed vocabulary).
- `PermissionModal.test.tsx` — new swap-regression describe driving the **real** `reduceModal` reducer
  rather than hand-built arrays: route 1 (remote `dismissed` swaps `outstanding[0]`) → list mode; route 2
  (`reconnected` then re-send) → asserts `outstanding.length === 0` at the empty-window point, then list
  mode after re-send; the AC3 positive control (marker armed on A, rendered prompt A → confirm mode,
  `optionCount === 0`).

No DOM harness added (AC4) — both new describes run under the existing `environment: 'node'` vitest
config.
