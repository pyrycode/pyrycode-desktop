# #512 — composer must not submit on the Enter that commits an IME composition

PR [#548](https://github.com/pyrycode/pyrycode-desktop/pull/548), spec [`docs/specs/architecture/512-composer-ime-composition-guard.md`](../../specs/architecture/512-composer-ime-composition-guard.md). Size S, no `security-sensitive` label.

## What shipped

`Composer.handleKeyDown` (`ConversationScreen.tsx`) treated every non-shift Enter as submit, including the Enter that *commits* an in-progress IME composition — ordinary typing for a CJK user. That keydown both sent the half-composed text and `preventDefault()`ed the commit itself, stranding the candidate.

The fix lifts the keystroke-intent decision into a new pure predicate, `shouldSubmitOnKeyDown`, in [`composerSend.ts`](../features/composer-send.md), placed directly after `submitMessage` (a different axis than the `composerAvailability`/`shouldOfferRepair`/`shouldShowBanner` `ConnectionStatus` cluster lower in the file — this one asks "did this keystroke ask to send", not "may the composer send"):

```ts
export function shouldSubmitOnKeyDown(event: ComposerKeyEvent): boolean {
  return event.key === 'Enter' && !event.shiftKey && !event.isComposing
}
```

`handleKeyDown` is now three statements, with the `return` on `false` **preceding** `preventDefault()`:

```ts
const { key, shiftKey, nativeEvent } = event
if (!shouldSubmitOnKeyDown({ key, shiftKey, isComposing: nativeEvent.isComposing })) return
event.preventDefault()
handleSubmit()
```

`isComposing` is read via `event.nativeEvent.isComposing` — it is not on React's synthetic `KeyboardEvent` (`@types/react` extends `UIEvent<T, NativeKeyboardEvent>` with no `isComposing`), so `event.isComposing` is a TS2339 compile error, not a silent `undefined`. `handleSubmit`'s `canSend` gate and `submitMessage` are untouched.

**Out of scope, deliberately:** the `compositionstart`/`compositionend` tracking fallback an earlier note on the ticket proposed "for WebKit". This app ships Electron `^33.2.1` (Chromium only), where `isComposing` on the committing keydown is reliable, so the fallback's motivating rationale doesn't apply. Also out: `keyCode === 229` (one signal is enough) and any DOM harness.

## Patterns established

- **Ordering is the load-bearing half of a preventDefault-then-decide fix, not the predicate.** Calling `preventDefault()` and *then* declining to act still breaks the underlying input event if the event's own default behavior (here, the IME commit) was the thing suppressed. A guard that only gated the *send* would have passed every unit assertion on the predicate and still shipped the bug — the container-level statement order is the actual fix, and it's asserted by code-review reading three statements, not by a spy.
- **Boolean predicate seam over effect-injected, when the handler is already this thin.** The spec's stated tradeoff: `shouldSubmitOnKeyDown` is a total boolean over plain fields (matching `shouldOfferRepair`/`shouldShowBanner`'s shape), not an effect-injected void helper (matching `submitMessage`/`selectOption`'s shape). Injecting `preventDefault`/`handleSubmit` as spies would upgrade two of the four AC1 clauses from consequence-of-predicate to direct assertion, but at the cost of a real footgun — `preventDefault: event.preventDefault` passed unbound loses `this` and silently no-ops. Worth remembering as a concrete argument for the boolean-predicate seam next time a handler is 3 statements.
- **A DOM-shadowing compile error is what makes untested container glue safe to leave untested.** `event.isComposing` (wrong) vs `event.nativeEvent.isComposing` (right) is exactly the kind of mistake `npm run typecheck` catches for free — so the one field extraction left inside `Composer.handleKeyDown` (still *untested reviewed glue*, per the `docs/knowledge/codebase/276.md` precedent) doesn't need a test to be safe. This is the second ticket running (after #511) where the review posture is "structural, not spied" for a similar reason.

## Lessons learned

From the PR body:

- `isComposing` is absent from `@types/react`'s synthetic `KeyboardEvent` (it extends `UIEvent<T, NativeKeyboardEvent>`), so the read must go through `nativeEvent`, where `lib.dom.d.ts` declares it non-optional `boolean` — no cast, no `?.`. The upside is that the mistake (`event.isComposing`) is a compile error rather than a silent `undefined`, which is what makes it safe to leave the extraction inside untested glue.
- Ordering is the load-bearing half of this fix, not the predicate: calling `preventDefault()` and *then* declining to submit still breaks the IME, because the candidate never commits. A guard that only suppresses the send would have passed every unit assertion and still shipped the bug.
