# #513 — a rejected pairing IPC invoke wedges the screen in a permanent busy state

PR [#549](https://github.com/pyrycode/pyrycode-desktop/pull/549), spec [`docs/specs/architecture/513-pairing-rejected-invoke-recovery.md`](../../specs/architecture/513-pairing-rejected-invoke-recovery.md). Size XS, `security-sensitive` label (architect self-review, PASS, no findings).

## What shipped

`runSubmit` / `runConfirm` in [`pairingState.ts`](../features/pairing-input-screen.md) awaited their injected `PairingBridge` call bare. Both preload methods resolve to a typed `{ok:false, reason}` for every *domain* outcome, so the existing mapping never needed a catch — but an *infrastructure*-level rejection (handler absent or already unregistered on `will-quit`, an invoke racing registration, a non-serializable reply) had nowhere to go. The container fires `void runSubmit(…).then(dispatch)` with no `.catch`, so a rejection dispatched no `PairingEvent`: the reducer stayed in `submitting`/`confirming` forever, and in those phases `busy` disables the textarea, the primary action, **and Cancel** — unrecoverable short of an app restart, plus an unhandled promise rejection.

Both runners are now total functions — they never reject:

```ts
export async function runSubmit(bridge: PairingBridge, paste: string): Promise<PairingEvent> {
  let response: PairingSubmitResponse
  try {
    response = await bridge.submitPairingPaste(paste)
  } catch {
    return { type: 'submit-failed', reason: 'malformed-request' }
  }
  return response.ok
    ? { type: 'submit-succeeded', fingerprint: response.fingerprint }
    : { type: 'submit-failed', reason: response.reason }
}
```

`runConfirm` mirrors this exactly, returning `{ type: 'confirm-failed', reason: 'malformed-request' }`. The `try` wraps *only* the bridge call — the `response.ok` mapping stays outside it, so a malformed response object still throws as a genuine contract violation rather than being read as "try again". The catch binds nothing (`catch {`, not `catch (error) {`): no message, stack, or cause from the caught value ever reaches renderer state, the UI, or the console.

No new `PairingErrorReason` member — `malformed-request` (an existing member of the closed 5-member union) is reused, byte-identical to the domain event the handler's own guard already produces. `PairingScreen.tsx` is untouched: the fix lands entirely in `pairingState.ts`, the pure, React-free, `node`-env module that is this screen's tested seam, mirroring `runUnpair`'s posture (`unpairAction.ts:53-59`). The two container call sites needed no migration since the runners' `Promise<PairingEvent>` signature is unchanged — they simply stop rejecting.

## Why this actually unwedges the screen

The reducer was never the trap — it already accepts `cancel` from any phase. The trap is the **view**: `busy` disables Cancel itself. The coerced failure event routes through the existing `submitting`/`confirming` → `editing` arms (unchanged by this ticket), landing on `editing` with the paste preserved and `error: 'malformed-request'` set. In `editing` with a non-empty paste, `busy` is `false`, so no control renders `disabled` and the inline error line appears — one-click retry, no restart.

## Patterns established

- **The `try` scope is itself a load-bearing decision, not incidental.** Scoping it to the bridge call only (not the whole function body) is what keeps a mapping bug from reading as an infra hiccup — a fake resolving `undefined` would make `response.ok` throw, and that must surface as a real failure, not get silently coerced to "try again". Pin this with a synchronously-throwing fake bridge method, not just a rejecting one.
- **Bare `catch {}` vs `console.error('…', error)` is decided by the argument, not the layer.** The renderer's four `console.error` sites are conversation-screen helpers whose bridge calls carry no secret argument. Pairing's `paste` transitively holds the pairing token, and `unpairAction.ts` / `clearPairingScopedState.ts` already establish bare-catch as the posture for pairing-scoped paths — this ticket extends that precedent rather than introducing it.
- **An exact-literal `toEqual` is a structural proof, not a promise.** Asserting `toEqual({ type: 'submit-failed', reason: 'malformed-request' })` against a reject value like `new Error('boom')` fails on any extra field — message, stack, cause, or an accidentally-threaded `paste` — making "the caught value never reaches the UI" a property the test enforces rather than something a reviewer has to trust.

## Lessons learned

From the PR body:

- `renderToStaticMarkup` **does** emit the `disabled` attribute for `disabled={true}`, so enabled/disabled view assertions are writable in this repo's `node`-env vitest even though clicks can't be simulated — check markup-observability before assuming a view AC needs a DOM harness. (Third ticket running where this DOM-harness assumption showed up in an incoming ticket body; see [#512](512.md).)
- Rethrowing from inside a `catch` is a faithful stand-in for "revert the catch" when computing mutation counts: for an `async` function it's observationally identical to having no `try` at all, including on the sync-throw path.
