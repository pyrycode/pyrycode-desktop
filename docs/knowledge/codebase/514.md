# #514 — one OS notification per prompt, however many times the link re-handshakes

Bug fix on top of [#392](392.md)'s push-notify trigger. Shipped as PR #553, code-review **PASS** (0
MUST/SHOULD, 1 NIT). Not security-sensitive (architect self-review PASS — no new trust boundary, no
IPC/wire change). Not UI-visible: the prompt itself still renders exactly as before; only the OS
notification count changes. Size XS (held from PO). Spec:
`docs/specs/architecture/514-prompt-notify-dedup.md`.

## Summary

The daemon re-sends every still-outstanding `modal_shown` after each re-handshake ([#415](415.md)
reconcile). `subscribePushNotify` held no memory of what it had already announced, so a prompt left
unanswered while the window was in the background earned a fresh OS notification per network flap or
sleep/wake cycle.

One production file changed, `src/renderer/src/store/pushNotifyBridge.ts`:

- `subscribePushNotify` now opens a closure-local `const announcedModalIds = new Set<string>()`
  before returning its `onDaemonEvent` listener.
- Inside the listener, after the existing `notifyKindForEvent` filter: `const modalId = event.type
  === 'modalShown' ? event.modalId : null` — the only new read of a daemon-supplied field, narrowed
  on the discriminant (no cast), never leaving the listener.
- `if (modalId !== null && announcedModalIds.has(modalId)) return` — before the toggle read, so a
  duplicate short-circuits regardless of the Settings push state.
- The `sendCommand({ type: 'notify', payload: { kind } })` literal is byte-for-byte unchanged (AC5:
  `modalId` is never spread or interpolated into it).
- `if (modalId !== null) announcedModalIds.add(modalId)` — placed **after** the send, not at the
  dedup check.

`turnEnd` is untouched by construction: `modalId` is `null` for every non-`modalShown` arm, so both
the check and the record are skipped for the rest of the union without a second rule.

Test file gained 6 new scenarios (17/17 total, 3 confirmed RED before the fix): same `modalId` twice,
same `modalId` across a `{ type: 'connected', ack }` event (the reconnect shape, and the test that
kills the rejected clear-on-`connected` sketch), a genuinely new `modalId` after a suppressed
re-delivery, two `turnEnd`s with the toggle held on, a toggle-off-then-on delivery pinning the
record-after-send ordering, and a fresh-subscription/fresh-`Set` check guarding the unpair reset edge.

`npm test` 17/17 on the bridge suite + 14/14 on `PairedShell.test.tsx`, `npm run build` (typecheck +
electron-vite) clean.

## Patterns established

- **A dedup `Set` keyed on a daemon-supplied id belongs in the subscription closure, not the store,
  when the store's own reset-on-reconnect would erase it too early.** The modal store
  ([modal-prompt-model.md](../features/modal-prompt-model.md)) clears both `outstanding` and
  `resolved` on every `reconnected` edge ([#510](510.md)) — by design, so a disconnected-Allow can
  re-surface. A bridge that needs to survive that same edge cannot borrow the store's memory; it needs
  its own, scoped to something that outlives reconnect but dies on unpair.
- **Verify the router before trusting a "hold state in the subscription closure" design.** The whole
  fix is only correct because `App.tsx`'s `route` state moves on nothing but the mount-time
  pairing-status read, `onPaired`, and `onUnpaired` — no daemon event, including `connected`, ever
  flips it. That makes `PairedShell` (and `usePushNotify`'s closure) span every reconnect without
  remounting. This is a property of the router, not of this bridge, and it is the fact the entire
  design rests on — reverify it before reusing this pattern elsewhere.
- **Record the "already handled" fact after the side effect, not at the dedup check.** If a delivery
  is dropped by an unrelated gate (here, the push toggle), it must not be marked as announced — a user
  who flips the toggle on mid-prompt still needs the daemon's re-send to notify them. This is the same
  shape as `isPushEnabled` being a per-event thunk ([#392](392.md)): correctness, not an optimization.
- **Never prune a dedup set on the "obvious" eviction trigger without checking what re-delivery means
  for THIS producer.** A `modalDismissed`-driven eviction looks natural but would reintroduce
  [#510](510.md)'s bug in notification form: an Allow clicked while disconnected is swallowed
  client-side, the renderer optimistically dispatches `dismissed` anyway, and the daemon's genuine
  re-send after the handshake would then re-notify. Growth is one short string per distinct prompt per
  pairing session — not a failure mode anyone has observed — so no cap either.
- **`!== null`, never truthiness, when the sentinel is a possibly-empty string id.** `requireString`
  (`inboundMessage.ts`) admits `''`; `if (modalId)` would treat an empty id as "not a modal" and skip
  both the dedup check and the record.

## Lessons learned

From the PR body:

- The renderer's dedup memory can only live in the subscription closure because `App`'s `route` moves
  on nothing but the mount-time pairing-status read, `onPaired`, and `onUnpaired`. If any daemon event
  ever gains the power to move the route, `PairedShell` would remount on a reconnect and this fix
  silently reverts to today's behaviour — a regression that would show up only as "duplicate
  notifications came back," with no failing type or lint to catch it.
- `requireString` admits `''`, so the `modalId` guard is `!== null` rather than a truthiness check —
  `if (modalId)` would treat an empty id as "not a modal" and skip both the dedup check and the
  record.
