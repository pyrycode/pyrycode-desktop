# #515 — `conversationCreated` re-requests the conversation list

**Shipped:** 2026-08-02 · **Size:** S (held from PO's default, not dropped to XS) · **Security-sensitive:**
no · **Scope:** `src/renderer/src/store/conversationListBridge.ts` + its `.test.ts`, three lifecycle e2e
specs, and `e2e/fixtures/conversationStateFake.ts`. Zero store/transport/daemon change.
**Spec:** `docs/specs/architecture/515-conversation-created-list-refresh.md` · **PR:**
[#555](https://github.com/pyrycode/pyrycode-desktop/pull/555), code review PASS, 0 MUST/SHOULD, 2 NIT.

## Summary

`shouldRefreshList` re-requested the conversation list on `conversationUpdated` and `conversationDeleted`
but not `conversationCreated`, and the daemon sends no broadcast on a plain create — only a correlated
`conversation_created` reply to the requester. Since the list is otherwise requested once per connection
episode, a FAB-created discussion stayed absent from the Channel List until a reconnect or an unrelated
rename/archive/promote/delete. This is "Gap A", first documented by the e2e suite at
[#440](440.md)/[#451](451.md)/[#452](452.md).

The fix is one clause: add `event.type === 'conversationCreated'` to `shouldRefreshList`'s disjunction
(`conversationListBridge.ts:53-59`). No store, transport, wire-type or daemon change — the existing
`conversationsReceived → setConversations` seam already lands a complete row once the re-request's reply
arrives, exactly as promote/rename/archive/delete already do. The design deliberately rejected an
optimistic local insert: the 5-field `ConversationCreatedPayload`
([conversation create](../features/conversation-create.md), #241) carries neither `is_archived` nor
`last_message_ts`, so inserting it directly would either fabricate those fields or force
`conversationListStore` to grow a per-row setter it deliberately doesn't have (whole-array
`setConversations` only).

Ten comment sites described the gap as current behaviour and were rewritten: three production docblocks in
`conversationListBridge.ts`, the `conversationStateFake` "two reflect paths" docblock, and the create/archive
step comments across `e2e/real-daemon-conversation-lifecycle.spec.ts`,
`e2e/conversation-archive-lifecycle.spec.ts`, and `e2e/conversation-create-rename.spec.ts`. **Zero e2e
assertions changed** — the rewrites replace each comment's *reason*, not its *conclusion*: the three specs
still assert thread-navigation rather than list membership right after a create, because the route flips to
`thread` and `ChannelList` unmounts, not because the row isn't in the store.

## Patterns established

- **A label-grep finds citations; a symbol-grep finds dependents.** The ticket's own `"Gap A"` grep found 7
  comment sites. A second grep on the actual symbols (`shouldRefreshList` / `conversationCreated`) found
  10 — three sites asserted the gap's *behaviour* in different words without ever writing the phrase "Gap
  A". The worst, `e2e/fixtures/conversationStateFake.ts:34-40`, named `shouldRefreshList` directly and was
  false in both halves of its claim ("two reflect paths" — now three; "not via a re-list" — now it is).
  When sweeping a documented gap for staleness, grep the predicate/event name the comments *depend on*, not
  just the label they happen to use.
- **Rewriting a stale comment often means keeping the conclusion and replacing the reason.** The two
  lifecycle e2e specs' Gap-A header blocks correctly conclude "assert nav, not list membership, at the
  create step" both before and after this fix — but the *why* changed from "the row isn't in the store yet"
  to "the route is `thread`, so `ChannelList` is unmounted regardless of what's in the store". Don't treat a
  comment sweep as delete-and-regenerate; verify which half of a stale comment (conclusion vs. justification)
  actually went stale.
- **Refresh-trigger over optimistic insert is the standing pattern for this store**, now proven a third
  time (after promote/rename/archive and delete): when a wire event signals a change but doesn't carry a
  complete row, re-request the authoritative list through the existing `conversationsReceived →
  setConversations` seam rather than reshaping the store to accept partial local writes.
- **A second, independent consumer on the same `DaemonEvent` doesn't need cross-fire code, only a
  documented invariant.** `conversationCreatedBridge`'s `subscribeConversationCreated` only navigates and
  sends no command; `conversationListBridge`'s `subscribeConversations` only re-lists. Two subscriptions on
  one event with disjoint side effects stay safe with no coordination — verified by reading the *subscriber*
  function, not by grepping the file (the file also contains the unrelated outbound `sendCommand` from
  `requestNewConversation`, which a naive file-level grep would false-positive against).

## Lessons learned

*Lifted from the PR body's own "Lessons learned" section.*

- A label-grep finds the sites that *cite* a gap; only a symbol-grep finds the ones that *depend* on it.
  Grepping `"Gap A"` returned 7 sites; grepping `shouldRefreshList` / `conversationCreated` returned 10. The
  three extras assert the gap without naming it — the worst is
  `e2e/fixtures/conversationStateFake.ts:34-40`, whose "**Two** reflect paths … the new row surfaces on the
  next `list_conversations`, **not via a re-list**" cites the predicate directly and was false in both
  halves after the fix.
- Rewriting a stale test comment often means keeping its *conclusion* and replacing its *reason*. The two
  lifecycle specs assert thread-nav rather than list membership at the create step; that is still correct
  after the fix, but for a different reason (the route flips to `thread`, so the Channel List is unmounted),
  not the one the comment gave.
