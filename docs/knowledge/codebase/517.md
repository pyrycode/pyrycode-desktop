# #517 — e2e fixtures must reap the Electron app and its user-data dir on a setup failure

Spec `b72c314` (architect self-review, security verdict PASS). Shipped `d0e2106`. Code review **PASS**
(PR#563, 0 MUST/SHOULD, 2 NIT, zero deviations). Security-sensitive: the leaked artefact is the
`--user-data-dir`, which is where the `PYRY_TEST_SECRET_BACKEND` test path persists the pairing record.

## Summary

Three e2e fixtures registered teardown only *after* `await use(...)`: `e2e/fixtures/realDaemon.ts`'s
`page` and `relay` fixtures, and `e2e/smoke.spec.ts`'s local `page` fixture. A throw between "resource
created" and "`use` returned" — e.g. `firstWindow()` rejecting once the Electron process was already
up — made the cleanup lines unreachable, leaking both the Electron process and its `mkdtemp
--user-data-dir`. With `workers: 1` in both Playwright configs, that orphan then persisted across every
remaining spec in the run. At the `page`/`realDaemon.ts` site the leaked dir carries a pairing record
for a real spawned `pyry`.

Fixed with **nested `try`/`finally`, one level per resource**, not a teardown-stack. Each site owns
exactly two resources (dir, app/relay), so a stack (`launchPairedApp.ts`'s four-resource pattern) would
be pure ceremony; nesting instead makes "no `await` between create and cleanup registration" a
structural property — the `try` textually follows its `const x = await create()` — and gives
close-then-`rm` ordering for free (the inner `finally` always completes before the outer one begins).

### `withIsolatedElectronApp` (new, `e2e/fixtures/realDaemon.ts`)

The `page` fixture's body moved **verbatim** (env, launch args — a pure move, byte-diffed by code
review against the removed lines) into an exported function:

```ts
export async function withIsolatedElectronApp(
  run: (handles: IsolatedElectronApp) => Promise<void>
): Promise<void>
```

`mkdtemp` → outer `try` → `electron.launch(...)` → inner `try` → `firstWindow()` → `run(...)` → inner
`finally` best-effort `app.close()` → outer `finally` best-effort `rm(userDataDir, ...)`. The `page`
fixture itself collapses to a one-line delegation: `await withIsolatedElectronApp(({ page }) =>
use(page))`. Takes **no path parameter** — the `rm` target is always the value `mkdtemp` just returned,
deliberately, so it can never become an arbitrary recursive-delete primitive fed by a caller.

Both teardown steps (`app.close()`, `rm()`) are wrapped in their own `try { … } catch { /* best-effort
*/ }` and swallow without logging: a throwing `finally` would replace the causal error the developer
needs to see, and — worse — would abort the unwind before the outer `rm` ran, stranding the
credential-bearing dir on a narrower path than the bug this ticket fixes. A close error can carry the
launch argv, which embeds `--user-data-dir=<path>`; `realDaemon.ts`'s existing no-echo rule (never echo
`pyry pair` stdout, since it carries the token) extends to teardown diagnostics, so nothing is logged at
all.

### `relay` fixture (`realDaemon.ts`)

Single-level `try { await use(relay) } finally { await relay.close() }` — no swallow here, deliberately:
one resource means there's no drain for a throwing `finally` to abort, and a fake-relay close failure is
a genuine harness signal worth surfacing. This site was never an orphan risk (an in-process server dies
with the worker anyway), so per the ticket it's a consistency conversion with no dedicated test.

### `smoke.spec.ts`

Same nested-`try`/`finally` shape as `withIsolatedElectronApp`, **transcribed independently** — not
extracted to a shared helper, since de-duplicating the three launch recipes was explicitly out of scope.
The stale comment at `:24-26` (which claimed teardown ran on every exit path, when it didn't) was
rewritten to state the actual, now-correct guarantee, including its one named gap (below).

### Regression test (`e2e/fixture-teardown-leak.spec.ts`, new)

Drives `withIsolatedElectronApp` directly with `test`/`expect` from `@playwright/test` — not the `test`
`realDaemon.ts` exports, which carries the `daemon` fixture — so importing the module runs only
`base.extend({...})`; no `pyry`/`claude` is spawned. Not named `real-*`, so the default config runs it
and the real-claude config's `testMatch` ignores it (AC4).

Sequence: launch via the helper, inside the callback assert the mutation controls (`process.kill(pid,
0)` succeeds, `existsSync(userDataDir)` is true — proving the probes work before relying on them), then
throw a fixed-literal sentinel error. Assert the returned promise rejects with that exact message
(teardown neither swallowed nor replaced it), then poll `process.kill(pid, 0)` to `ESRCH` and assert
`existsSync(userDataDir)` is now false, both via `expect.soft` so a pre-fix run shows *both* halves of
the leak instead of the liveness assertion masking the dir assertion.

## Patterns established

- **Nested `try`/`finally` beats a teardown stack at exactly two resources.** Reach for
  `launchPairedApp.ts`'s array-based stack only once a fixture owns three or more; below that the
  nesting itself proves the invariants a stack exists to enforce.
- **`launchPairedApp.ts`'s shape is a trap outside its own context.** Its drain sits plainly *after*
  `use()`, which is safe there only because every resource it creates lives *inside* the `use()`
  callback (the factory the test body invokes) — so a mid-drive failure is a test failure, and `use()`
  still returns. Copying that shape into a setup-time fixture (resource created before `use()` is even
  called) reintroduces this exact bug. The fixture that was already correct for a setup-time shape is
  the `daemon` fixture in the same file (cleanup closure over nullable handles, `use()` wrapped in
  `try`/`finally`).
- **A capture-in-callback test pattern needs an array, not a nullable `let`.** `let record: T | null =
  null` assigned inside a callback is narrowed to `null` by TypeScript's flow analysis at every later
  read (`e2e/` is in neither tsconfig, so nothing catches this before runtime); an array sidesteps the
  narrowing, and a hard `expect(launched.length).toBe(1)` after the drive is the non-vacuity guard —
  without it, every post-assertion would pass vacuously if the callback never ran.
- **`expect.soft` is what makes RED evidence legible** when two independent post-conditions guard the
  same bug: a hard assertion on the first (process liveness) aborts before the second (dir existence) is
  ever evaluated, so a naive pre-fix run only ever shows half the leak.
- **Don't make the runner's own failure the test.** (Cross-project lesson, pyrycode #68,
  `docs/lessons.md:122` in that repo — this repo has no `docs/lessons.md`.) An inner Playwright test
  whose failure you want to observe propagates to the parent and ends it before post-state assertions
  run. Calling the extracted fixture body (`withIsolatedElectronApp`) directly, outside Playwright's own
  test lifecycle, sidesteps this — the throwing callback and the post-state assertions live in the same
  outer test.
- **Never interpolate a credential-adjacent path or pid into an assertion message**, even post-deletion.
  The regression test asserts booleans only; both thrown messages are fixed literals.

## Lessons learned

- `let record: T | null = null` assigned inside a callback is narrowed to `null` by TS's flow analysis
  at every later read, so the "capture in the callback, assert after" pattern needs an array (or a
  re-assert `throw`) rather than a nullable local. `e2e/` is in neither tsconfig, so nothing would have
  caught this before runtime.
- `expect.soft` on the two post-state assertions is what makes the RED evidence readable — with hard
  assertions the process-liveness failure aborts before the dir assertion is ever evaluated, so the
  pre-fix run only ever shows half the leak.
- Node's `mkdtemp` suffix is six characters, a cheap way to tell your own leaked temp dirs apart from
  another harness's lookalikes in `$TMPDIR` (a 10-digit `pyry-e2e-*` sibling there belongs to the
  pyrycode Go repo's test harness, not this one).

## Accepted gap (not fixed, named in spec and code)

A setup `await` that never settles (a hung `firstWindow()`) is not reapable by `try`/`finally` —
Playwright kills the worker without unwinding the stack, so no `finally` runs. The ticket's AC1 scopes
to a failure *raised*, not a hang; a future ticket would need to race `firstWindow()` against a
deadline. No follow-up filed.
