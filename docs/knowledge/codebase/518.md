# #518 — Guard every main-process reach into a destroyed BrowserWindow

Split from #503. Sibling: #519 (live-window holder), `blocked_by` this ticket. Shipped as PR #520
(`a5c597b` + `2227f8a`, spec `e08e212`), code-review **PASS** (1 NIT, cosmetic, not fixed). Security-
sensitive (Electron IPC/lifecycle surface); size S; 3 production files + 5 test files, 638 insertions.
Zero deviations from the architecture spec.

## Summary

On macOS, closing the window destroys the `BrowserWindow` without quitting the app (`window-all-closed`
only quits on non-darwin), so the daemon connection — which captured the window as its event sink at
construction — kept emitting into a destroyed object. `emitDaemonEvent`'s `sink.webContents.send` throws
from the `webContents` **accessor itself** once the window is destroyed, before `send` is ever reached,
and nothing caught it: the transport invokes the event callback synchronously inside a ws `message`
handler with no try/catch. The next daemon event after a window close was an uncaught main-process
exception.

The fix is a single predicate, `isDestroyed()`, checked at call time on three narrow structural
interfaces — no new state, no `'closed'` listener, no cached flag:

- **`src/main/emitDaemonEvent.ts`** — `DaemonEventSink` gains a **required** `isDestroyed(): boolean`.
  `emitDaemonEvent` returns early (`if (sink.isDestroyed()) return`) before any `sink.webContents`
  access. This one guard covers all 32 `daemonConnection.ts` call sites (verified by `grep webContents
  src/` returning exactly one production read, and it sits below the guard) plus the debug-bundle
  orchestrator's injected `emit: (event) => emitDaemonEvent(mainWindow, event)`. **No production edit
  to `daemonConnection.ts` or `debugBundleDownload.ts`** — the whole funnel is closed from one file.
- **`src/main/fireNotification.ts`** — two sites reach the window outside that funnel. A new
  `FocusableWindow` interface + `windowHasFocus(win)` reports a destroyed window as **unfocused**
  without calling `isFocused()` (semantically correct, not a fudge — a closed window cannot hold focus,
  and that is exactly when a notification should fire). `ActivatableWindow` gained `isDestroyed()`,
  checked first, above `isMinimized()`, so `activateWindow` on a destroyed window is a total no-op.
- **`src/main/index.ts`** — one line: `isWindowFocused: () => mainWindow.isFocused()` becomes
  `() => windowHasFocus(mainWindow)`. `activateWindow(mainWindow)` and the paired
  `emitDaemonEvent(mainWindow, …)` call are untouched — their guards now live inside the callees.
  `windowHasFocus` was extracted rather than inlined because `index.ts` has no peer `.test.ts`; the
  house pattern for testable main-process logic is the Electron-free module with injected dependencies.

**Second-order fix, no code change:** the debug-bundle orchestrator's three terminal handlers
(`debugBundleDownload.ts:94-95`, `:99-100`, `:106-107`) all emit *before* clearing the single-in-flight
`active` flag. Before this ticket, a throw out of `emit` on a destroyed window left `active` stuck
`true` forever. With the emitter guard in place the throw no longer happens, so the flag clears
normally — the orchestrator itself needed no guard (one was explicitly rejected; see spec). This is
observable only via a regression test that composes the real `emit: e => emitDaemonEvent(destroyedSink,
e)` wiring, since the module's other tests use a plain collector that never imports `emitDaemonEvent`.

`isDestroyed()` was made a **required** (not optional) member of `DaemonEventSink` — an optional member
would let a future sink silently opt out of the guard. This turns `npm run typecheck` into the fan-out
audit: every existing sink literal fails to compile until it gains the member, so the compile-error list
*is* the completeness proof, not a hope.

## Patterns established

- **The one member safe to call post-destruction is the check itself.** `isDestroyed()` is placed first
  in every guarded interface (`DaemonEventSink`, `ActivatableWindow`, `FocusableWindow`) and checked
  before any other member access — no destructure, no early alias of `webContents`. On a real destroyed
  `BrowserWindow` the **property read itself** throws, not just the method call, so a guard placed after
  a hoist is silently wrong. The regression test that catches this uses a fake whose `webContents` is a
  **throwing getter**, not a throwing method — a getter body satisfies the declared property type with
  no cast needed.
- **A destroyed-window check is a synchronous call-time query, never a cached flag.** No `'closed'`
  listener, no boolean set from an event. A cached flag would be a second source of truth that can
  disagree with the object; `isDestroyed()` is free and authoritative. This mirrors the existing
  house discipline in the same closure (`fireNotification.ts`: "focus is read at fire-time, no stateful
  tracker").
- **Widen the minimal structural interface a leaf module already owns; don't introduce a shared base.**
  `DaemonEventSink` and `ActivatableWindow`/`FocusableWindow` each gained their own one-line
  `isDestroyed()` declaration rather than importing a shared `DestroyableWindow` interface — duplicating
  a one-line method beats coupling two otherwise-independent leaf modules.
- **A second defense for a failure mode a first guard makes unreachable is not warranted.** The debug-
  bundle orchestrator gets no guard of its own — the emitter guard removes the only way its terminals
  could throw. Observing that the flag no longer strands takes a test that composes the *real* emitter
  into the orchestrator's wiring, rather than a change to the orchestrator itself.
- **No try/catch, no logging, on the drop path.** A catch could not distinguish "window destroyed" from
  a genuine `send` fault (bad channel name, non-cloneable payload) and would convert real defects into
  silent drops. Logging the dropped event would require threading a logger through a 32-site funnel and
  risks leaking `MessagePayload.text` — the module is log-free by construction.

## Lessons learned

- On a destroyed `BrowserWindow` the throw comes from the **`webContents` accessor**, not from `send`.
  A guard placed after any destructure or alias of `sink.webContents` is dead code — only a fake whose
  `webContents` is a *throwing getter* catches that specific mistake, and the getter body satisfies the
  declared property type with no cast.
- Making the destroyed-check a **required** interface member (not optional) turns `npm run typecheck`
  into the fan-out audit: the compile-error list is the census of every sink literal that needs the new
  member, so the "fan-out is bounded" claim in the spec is a checkable fact, not an estimate.
- A fake sink that throws from `webContents` breaks any test helper that reads
  `sink.webContents.send.mock.calls` after destruction — `daemonConnection.test.ts`'s `fakeSink()` had
  to expose a stable `send` handle (the spy itself) alongside the sink object so assertions can still
  reach it once the sink reports itself destroyed.
- Code review independently re-verified — rather than trusting the spec's "verified" claim — that both
  `.not.toThrow()` regression legs and the AC4 test actually fail without the guard: a `.not.toThrow()`
  assertion passes vacuously if the driven event never reaches a real emission site, or if the fake
  harness swallows the throw in its own try/catch. Here `makeDriverFactory`'s `emit` callback is
  synchronous with no try/catch, so the destroyed sink's throwing getter genuinely propagates.
- The one NIT from code review: `index.ts`'s pre-existing comment above the `notify` closure still read
  "closes `mainWindow.isFocused()`" after the wiring changed to `windowHasFocus(mainWindow)` — cosmetic,
  left as-is (a new comment block immediately below already documents the three guarded touches
  correctly).

## Open questions carried forward

- **Recovering events dropped while no window exists** (buffering, snapshot-on-reattach) is explicitly
  out of scope here and belongs to **#519**, the live-window holder, which is `blocked_by` this ticket.
  After this ticket the app no longer crashes on a post-close daemon event, but a user who closes the
  window mid-turn and reopens it still returns to a timeline missing whatever arrived while it was shut.
- **Whether a dropped event should be counted or logged** — rejected here (no observed need, and the
  emitter is log-free by construction). If #519's reattach work needs to know events were missed, a
  content-free counter belongs there, not retrofitted here.
- **Whether #519 collapses `DaemonEventSink`/`ActivatableWindow`/`FocusableWindow`** once a live-window
  holder exists (the sink may become a getter over the current window) is left to #519 to decide.
