# #519 — Point window-bound calls at the live window, and converge a fresh one

Spec `a9b0f39` → dev `35507ce` PR#522 → code-review **FAIL** (1 MUST FIX) → rework `56f66c8`
(evidence + permanent e2e spec, **zero production change**) → code-review **PASS** (1 NIT, cosmetic).
Security-sensitive; size S; 2 production files + 1 comment-referent fix + 2 test files, ~330 LOC,
zero deviations from the architecture spec. Split from #503, blocked by [#518](518.md) (merged first).

## Summary

On macOS the app outlives its window (`window-all-closed` quits only on non-darwin), and the
composition root had captured its one `BrowserWindow` reference at startup and handed it to every
window-bound consumer: the daemon connection's event sink, the load gate, the debug-bundle
orchestrator's emitter, and the `notify` closure's focus query and click activation. [#518](518.md)
made every one of those reaches destroyed-safe (a no-op instead of a crash), but a dock-reopened
window still received nothing — routing was safe, not working. Worse, even a correctly-routed fresh
window would start its renderer at `{ type: 'disconnected' }` and, on a stable connection, might never
receive another status event to correct it.

The fix is one new Electron-free module, `src/main/liveWindow.ts` (`createLiveWindow()`), that holds
the current window behind two faces:

- **`sink: DaemonEventSink`** — the process-lifetime channel handed to the connection and the
  bundle orchestrator. Its `isDestroyed()` is **always `false`** (the load-bearing decision — see
  below); it records the last of the four connection-status events (`connecting`/`connected`/
  `failed`/`disconnected`) then forwards through `emitDaemonEvent`, so #518's guard stays load-bearing
  rather than becoming dead code.
- **`window: FocusableWindow & ActivatableWindow`** — the current-window stand-in for the `notify`
  closure's focus query and click activation. `isDestroyed()` here is honest (`true` when nothing is
  attached, or the attached window reports destroyed), because `windowHasFocus`/`activateWindow`
  decide whether to act by asking first.

`WindowTarget = DaemonEventSink & FocusableWindow & ActivatableWindow` answers #518's open question 3
(do the three window interfaces collapse into one?): they don't — they **intersect**, here, in the one
module that needs all three at once. Zero interface edits, zero fixture cascade.

`src/main/index.ts`'s local `mainWindow` binding is **deleted**. Window creation moved into a
root-local `openWindow()`, called once for the first window and again from `activate` (which
previously discarded its replacement window outright):

```ts
const openWindow = (): void => {
  const window = createWindow()
  live.attach(window)
  window.webContents.on('did-finish-load', () => {
    live.replayStatus() // no-op on the first window: nothing recorded yet
    connection.start()  // idempotent; the first call dials, later ones return
  })
}
```

One uniform path for every window — no "is this the first one?" branch. `reconnect()` is never
called from this path (AC4): it re-dials and would kill a streaming turn; `start()`'s idempotence
(`daemonConnection.ts:1477-1482`, already tested) is what makes replay-then-start safe on every
window, first or reopened. The listener is `.on`, not the prior `.once` — safe because of that same
idempotence, and it additionally converges a window that reloads (dev HMR, Cmd-R).

Three stale comment referents were corrected in place: `index.ts`'s "notify is dormant" note (#392
shipped since), and two doc comments in `debugBundleDownload.ts`/`.test.ts` quoting the old
`mainWindow`-based emit wiring.

## Why the sink is never destroyed (the one non-obvious decision)

The recorder must sit **above** #518's destroyed-window guard. If the sink answered `isDestroyed()`
honestly, `emitDaemonEvent` would return early and the router would never see events emitted while no
window exists — a status change during the closed-window gap would be missed, and `replayStatus()`
would deliver a **stale** value into the new window. Not theoretical: [#504](504.md)'s unpair tears
the session down and settles permanently at `failed(not-paired)` with no further event ever; a window
reopened after that would be told `connected` and would keep saying so forever. Replaying a stale
status is worse than replaying none. So the sink is not a window and must not pretend to be one — it
is the process-lifetime channel *to* whatever window is current, never destroyed, dropping one hop
down through `emitDaemonEvent` on every forward.

## The code-review cycle: an evidence MUST FIX, answered with a permanent spec

First pass **FAILED** on exactly one finding, and it was about proof, not code: `live.replayStatus()`
fires on `did-finish-load`, and the design's premise is that this lands *after* the new window's
renderer has subscribed. That subscription happens inside `useDaemonEventBridge`'s React **passive
effect** — two Scheduler macrotasks (initial render, then effect flush) racing the page `load` task
`did-finish-load` follows. Nothing in the app had ever proven that ordering: the only event emitted at
that point today is `connecting`, and losing it is harmless (`connected`/`failed` converge a
round-trip later); for a *reopened* window on a stable connection the replayed status is the **only**
status event it will ever get. `liveWindow.test.ts` drove `replayStatus()` directly against a fake —
proving the module, not the delivery. No test at any level (unit, e2e, manual) had exercised the real
close→reopen round trip.

The rework did not patch code — it observed the round trip and committed the observation as
`e2e/window-reopen-converges.spec.ts` (89 lines, **zero production diff**, verified by
`git diff 35507ce..56f66c8 --stat`). It reuses the existing `launchPairedApp` fixture, which already
reaches the expensive half (built app, real pairing drive, a real `Noise_IK_25519_ChaChaPoly_BLAKE2s`
handshake, `connected`) — the missing piece was three lines: `BrowserWindow.close()` → poll
`getAllWindows().length` to 0 → `Promise.all([app.waitForEvent('window'), app.emit('activate')])`.
Both assertions (`ChannelList` row visible, then `Send` enabled after a click) are gated on the
`connected` **rising edge** (`conversationListBridge.ts`'s request-on-connect, `composerSend.ts`'s
`canSend`) — reachable in a fresh store *only* through the replay, which is what keeps this from being
a vacuous "the window reopened" test. A positive control pins the first window as connected before
anything closes; a mutation control (deleting `live.replayStatus()` from the load handler, rebuilt)
reproduces the exact bug on demand — the reopened window hangs on an empty list. Converges in ~1.0s,
3/3 under `--repeat-each=3`; runs under the default `npm run e2e` (the filename doesn't match
`playwright.config.ts`'s `testIgnore: /real-.*\.spec\.ts$/`).

Re-review **PASSED**, independently re-verifying the diff was production-untouched, that both
assertion surfaces were genuinely replay-gated rather than reopen-gated, and that the mutation control
reproduced the right failure — plus one cosmetic NIT (`app.emit('activate')` passes no arguments,
where real Electron passes `(event, hasVisibleWindows)`; faithful today since the handler reads
neither, but would silently stop being faithful if someone started reading `hasVisibleWindows`).
Two NITs from the first pass (a fifth status member going silently unrecorded; relay-link status not
converging on reopen — both inside the ticket's "dropped events are not recovered" exclusion) were
left as-flagged, not fixed.

## Patterns established

- **An "unverified" MUST FIX calls for observation plus a permanent test, not a defensive retry or a
  mechanism change.** The reviewer explicitly offered two paths — observe and report, or change the
  mechanism if it doesn't converge (routed back to the architect). The chosen path answers the
  question once and leaves a standing guard behind, rather than trusting a one-off manual run.
- **Check what the harness already reaches before declaring a scenario "its own slice."** The
  architecture spec deferred window-lifecycle e2e coverage on the assumption a Playwright harness
  didn't exist for it; `launchPairedApp` already did the expensive 90% (build, pairing, real
  handshake, connected), leaving a ~3-line lifecycle drive. Re-read existing fixtures before scoping a
  new one.
- **Pick the assertion surface by what can *only* be reached through the mechanism under test.** The
  `connected` rising edge (list request) and `canSend` (composer) are both unreachable in a fresh
  store without the replay; "window exists / shell rendered / route is list" would have passed under
  the mutation that removes it.
- **A sink test that drives `webContents.send` directly is vacuous** — production reaches the sink
  through `emitDaemonEvent(sink, event)`, which checks `isDestroyed()` first. The fix routes every
  test emit through the real `emitDaemonEvent`, the same composed-callee discipline [#518](518.md)
  used for its own AC4 test; a mutation to an honest `isDestroyed()` then kills exactly the gap-case
  test, which is what proves the crux decision is load-bearing.
- **Deleting a stale binding outright is a cheaper correctness argument than rewiring it.** With
  `const mainWindow` gone from `whenReady`, "nothing can go stale" reduces to
  `grep -n mainWindow src/main/index.ts` returning only `createWindow`'s own local — a structural
  proof, not an assertion.
- **Two faces on one module can have opposite `isDestroyed()` contracts, and picking the wrong one
  for either is silent.** The sink must lie (stay above the guard so gap-window status is recorded);
  the focus/activate face must tell the truth (its callees decide whether to act by asking first). A
  single honest implementation still compiles and passes every routing test — it only fails the one
  gap scenario, which is why that scenario gets its own dedicated test rather than folding into the
  routing suite.

## Lessons learned

- The code-review worktree has no `node_modules`, so re-review of the rework's e2e run couldn't be
  re-executed independently — the reviewer verified everything re-checkable by reading (the diff stat,
  the name-status, the replay-gating of the assertion surfaces, the mutation's consistency with the
  code) and said explicitly whose numbers were reported vs. re-run.
- A round trip that looks like it "needs a manual dock click" often doesn't: firing `app.emit('activate')`
  on the running Electron process drives the identical handler a real dock click would, leaving only
  macOS's own event-delivery hop unexercised — and that hop predates this ticket (the `activate`
  handler already created a window before #519; only its body changed).
- `git diff <base>..<rework> --stat` is the concrete way to make "zero production change" a checked
  fact for a reviewer, not a claim to trust.
