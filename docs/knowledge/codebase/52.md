# #52 — Parse the pairing payload and validate the relay against an allowlist

**Shipped:** 2026-07-04 · **Size:** S (comfortable S bordering XS) · **Scope:** background process only (`src/main/`) · greenfield, **zero consumer cascade** (nothing imports the new surface yet; composition-root wiring lands with #53) · **no new dependency** · **no effectful dependency** (no keychain, filesystem, socket, IPC, or crypto).
**Spec:** `docs/specs/architecture/52-parse-pairing-payload-validate-relay-allowlist.md` · **PR:** [#56](https://github.com/pyrycode/pyrycode-desktop/pull/56) · review: **PASS** (architect security-review pass folded embedded-credential rejection into the design; code-review adversarial pass over the diff). Split from #9.

Adds the **pairing input gate** — the pure `src/main/` function that parses a pasted pairing payload into the four [`QrPayload`](5.md) fields and validates its `relay` URL before anything downstream (fingerprint display, persistence, connect) can use it. Desktop pairing is **paste-only**, so the pasted string is the **first point where attacker-influenceable text enters the pairing flow**; this ticket is that gate. See the [pairing-payload gate feature doc](../features/pairing-payload-gate.md) for the full contract, pipeline, and security properties.

Scope lock held: **parse + relay validation only.** It (a) parses the daemon's `base64url(JSON)` four-field tuple into a `QrPayload`, rejecting any malformed input with a typed rejection, and (b) validates the `relay` URL (`wss:` scheme only, exact-host match against a single-sourced main-process allowlist, no embedded userinfo). It does **not** persist (that is #53, over the [paired-server store](44.md)), does **not** touch crypto/IPC/UI, does **not** validate the `server_static_pubkey` or `server`-id (opaque strings here — see below), and does **not** wire itself into app startup.

## Patterns established

- **A validation gate returns a discriminated result, it does not throw.** Rejection is an *expected, routine* outcome (the operator can paste anything), so every failure is an `ok:false` **data arm** with a bounded value-free `PairingRejectReason`, not an exception. Control-flow-by-exception is wrong for a validation gate — and modeling failure as data keeps the "no field value in an error" property **structural**: there is no `Error` object to accidentally interpolate a value into. This is the pure-logic counterpart to [#44](44.md)'s throw-based `MalformedPairedServerRecordError` (which throws because it guards a *stored* blob, not an untrusted paste).
- **The success type reuses the wire type (`QrPayload`), it does not re-declare it.** Same guard as `PairedServerRecord = QrPayload` ([#44](44.md)): a `QrPayload` change (`src/shared/wire/types.ts:120`) flows straight through as a type change, never a silent divergence — the mechanical realization of CLAUDE.md's "don't drift the wire types."
- **The gate is the *only* `string → QrPayload` path, so the trust boundary is enforced by data flow.** A caller obtains a `payload` only by taking the `ok:true` arm; the reject arm carries no record. #53 cannot hold a "validated" record that skipped this gate. A branded output type (`ValidatedPairingPayload`) was considered and deferred — the union arm + single code path already gate it, and reusing `QrPayload` prevents wire drift.
- **Restore platform strictness the JS runtime discards, and take the strictness it gives for free.** Node's `Buffer.from(s, 'base64url')` is *lenient* (silently drops out-of-alphabet chars), so a strict `^[A-Za-z0-9_-]+$` pre-check restores the daemon's `RawURLEncoding` strictness. Conversely, `JSON.parse('{…}x')` *throws* on trailing garbage (unlike Go's `json.Unmarshal`), so the daemon's separate trailing-byte check is subsumed — no extra stage needed. Encoding fidelity across a language boundary is not automatic; it is a per-primitive audit.
- **Scope the semantic check to the field that can do harm before a handshake.** Only the `relay` value can redirect the connection to an attacker *before* any Noise_IK handshake, so it is the one field validated semantically. `server_static_pubkey` and `server`-id are opaque strings here: a wrong pubkey fails the handshake closed and is caught by #53's fingerprint visual-verify; a wrong `server`/`token` fails auth at the relay/daemon. Adding format checks for them would be defense theatre against threats other layers already close (Evidence-Based Fix Selection). This keeps the reject taxonomy at **8 categories**, well under the 10-branch red line.
- **The security-load-bearing constant is single-sourced, exact-match, and never payload-derived.** `RELAY_ALLOWLIST` is a `ReadonlySet` with one entry, matched by exact `Set.has` (no prefix/substring matching), living in exactly one place in the main process (AC4). `URL.hostname` is lowercased and userinfo-stripped, so look-alike hosts miss. Re-used the #42/#43/#44/transport **log-free-by-construction** discipline verbatim (no `console.*`; caught errors discarded; console-spy test over every branch).

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The spec had an internal contradiction on relay-check ordering; the developer resolved it host-first, credentials-second.** The spec's § Design stage table ordered the embedded-credentials check (5c) *before* the host-allowlist check (5d), but **both** the test matrix **and** the stage-5d prose example listed `wss://evil@pyrycode-relay.pyryco.de.evil.example/` (userinfo **and** wrong host) as `relay-host-not-allowed`. The shipped order is **scheme → host allowlist → credentials**: identical security outcome (both orders reject; nothing reaches `ws`), it satisfies the entire test matrix, and it makes the `relay-has-credentials` branch mean exactly what its rationale describes — reject userinfo *on the otherwise-trusted host*. **Takeaway:** when a spec's normative table and its own examples/tests disagree, the examples-plus-tests are the tie-breaker, and a security-equivalent reordering is the right call over transcribing a contradictory table.

No re-render / effect-cleanup / dependency-version surprises to record — a pure, synchronous, total main-process function with no React, no timers, no listeners, no async, and no new dependency.

## Deferred (open questions carried forward)

- **Composition-root wiring is #53's job, not this ticket.** The gate has no runtime consumer — nothing calls `parsePairingPayload` until #53 feeds a pasted string over a future IPC/command boundary, then calls `store.save(record)` on the `ok:true` payload. Wiring it in with no caller would be premature (the #21/#22/#42/#43/#44 defer-wiring precedent), so no existing file was touched.
- **IPC arg type-guard is carried to #53 (SHOULD FIX, hand-off — not a defect here).** The future IPC/command handler that feeds the pasted string into this function must validate the argument is a `string` before calling — the renderer→main IPC arg is untrusted, and `parsePairingPayload(pasted: string)` assumes the type. That deterministic type-guard belongs at the IPC boundary #53 introduces, not duplicated inside this pure function; no such caller exists yet, so there is no exploitable path in *this* ticket.
- **Server-id / pubkey shape validation deferred** (see the [feature doc § Deliberately not validated](../features/pairing-payload-gate.md#deliberately-not-validated-here)). If #53's fingerprint step or a security follow-up wants the gate to also reject a non-base64/wrong-length `server_static_pubkey` and a non-UUID `server`, it is an additive two-stage/two-reason extension. Deferred; the fingerprint visual-verify in #53 is the load-bearing key check.
- **Port not constrained on the allowed host.** The relay check matches `URL.hostname`, not the port (the deployed relay serves 443; a payload with the allowed host but a dead port fails to connect downstream). A future non-default-port deployment matches `URL.host` or widens the allowlist entry — a one-line change. No observed need.
- **Multi-relay / multi-pyrybox.** `RELAY_ALLOWLIST` is milestone-1 single-entry; per-server allowlisting (or config-sourced hosts) is the same deferred multi-server change as `pairedServerStore`'s per-server-id keying, and must stay main-process-defined and never payload-derived when it lands.
