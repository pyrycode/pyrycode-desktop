## What it does

`fakeDaemon.ts`'s untrusted→trusted boundary (`onMessage`) routed purely on session **state** while in `awaiting-rekey-init`: every inbound frame went to `handleRekeyInit`, which fed it to `fresh.ReadMessage`. A sealed app frame the real daemon had fanned out *before* the client's rekey `noise_init` landed is not an IK message 1, so `ReadMessage` threw, the run settled `{ ok: false, reason: 'handshake-read-failed' }`, and the leg closed. The real daemon dispatches on the inner frame **type** instead (`pyrycode` `internal/relay/v2session.go:664-669`) and keeps serving transport frames under the old `CipherState`s throughout its awaiting-reply window (spec #450). The gap meant the realistic interleaved-frame rekey collision — the exact scenario #507 needs to fix — could not be reproduced against the fake at all.

## What shipped

**The production change — one added conjunct.** `onMessage`'s dispatch chain:

```ts
if (state === 'awaiting-msg1') handleMsg1(raw)
else if (state === 'awaiting-rekey-init' && innerType === 'noise_init') handleRekeyInit(raw)
else if (innerType === 'noise_init') handleReconnect(raw)
else handleTransport(raw)
```

Only `&& innerType === 'noise_init'` was added to the second arm. A non-`noise_init` frame in `awaiting-rekey-init` now falls through to `handleTransport`, which never assigns `state` (so `awaiting-rekey-init` survives a served frame for free) and already seals replies under the `send` cipher captured at entry — the pre-swap old-cipher behaviour spec #450 requires came for free, no new logic needed. `awaiting-msg1` and `handleTransport` itself were both left untouched, exactly as the spec required.

**The `driveClient` fidelity fix — the substantive half of the diff.** The test harness's `driveClient` tagged only the *first* outbound frame `noise_init`; the client's in-session rekey msg1 therefore went out tagged `noise_msg`. That was invisible under state-based routing (the daemon ignored the tag) and would have been **fatal** under type-based routing — the msg1 would have fallen to `handleTransport`, AEAD-failed, and never completed the swap, breaking both pre-existing rekey tests. `driveClient` now mirrors the production driver's second latch (`noiseRelayDriver.ts:196/203/225-226`): a one-shot `rekeyInitPending` boolean, armed in `onEvent` on `rekey-requested` (before the event is pushed), read in `sendFrame` as `firstOut || rekeyInitPending`, both cleared unconditionally after. The session hands its fresh rekey msg1 to `sendFrame` synchronously within the same `onFrame` turn (`noiseSession.ts:225-229`), so the latch lands on exactly the right frame with no race.

**The interleave harness — an inbound gate.** `driveClient` gained `holdInbound()`/`resumeInbound()` (arm/disarm a capture gate on the relay's `message` event), a `held: Uint8Array[]` array of raw `InnerFrameV2` bytes captured while armed, `deliverHeld(i)` (replay a held frame through the normal decode + `initiator.onFrame` path), and `sendRaw(raw)` (frame raw bytes as a `noise_msg` and push past the initiator's ciphers, for AC4's garbage-frame case). The ordering trick: withholding the daemon's `rekey_request` keeps the client in `transport` (so its `sendMessage` isn't dropped by the session's state guard) while the daemon has already synchronously assigned `awaiting-rekey-init` before sending — an exact race with no timer and no second Noise initiator.

**Two new tests**, both deliberately skipping the baseline round-trip every existing rekey test does first (`settle()` is first-wins; a baseline round-trip settles `{ ok: true }` immediately and swallows every later reason, making the must-fail-first assertion unobservable):

- *The interleave* (AC2/AC3/AC5): holds the rekey_request, sends an app frame, asserts `daemon.whenSettled()` resolves `{ ok: true }` (was `handshake-read-failed` pre-fix), asserts the served reply is a `noise_msg` of the expected sealed length (canned reply + 16-byte ChaChaPoly tag — distinguishes a served reply from a handshake msg2), then releases the withheld `rekey_request` and asserts the swap still completes (one `rekey-requested` event, the post-swap resume frame under the client's new recv cipher, no `error`). The withheld interleaved reply (`held[1]`) is never delivered — feeding it to the client would desync it into consuming it as its handshake reply, which is #507's bug and explicitly out of scope here.
- *The undecryptable frame* (AC4): holds the rekey_request, sends 48 bytes of garbage tagged `noise_msg`, asserts `daemon.whenSettled()` resolves `{ ok: false, reason: 'transport-decrypt-failed' }` (was `handshake-read-failed` pre-fix) and that no reply was captured — non-vacuous because the interleave test above uses the identical gate and *does* capture a reply.

**Comment updates**, all three named in the spec, moved with the behaviour: the module header's rekey-INITIATOR + ROUTING-ONLY paragraphs, the `onMessage` inline comment, and one clause added to `initiateRekey`'s JSDoc.

## Patterns established

- **A harness lax in the same direction as the code under test hides its own infidelity.** `driveClient` had mis-tagged the client's rekey msg1 for two prior tickets (#111, #112) with zero red tests, because the fake's state-based routing never inspected the tag it was getting wrong. Tightening the production routing to type-based surfaced the harness bug as a hard break. Worth checking, whenever a routing decision moves from "keyed on A" to "keyed on B," whether the harness was ever exercising B honestly — it may have been silently riding on A the whole time.
- **`settle()`'s first-wins latch makes a "harmless" baseline round-trip destroy observability.** Any test asserting a specific `FakeDaemonOutcome` reason during a rekey window must rekey *before* a round-trip, not after — `initiateRekey` only requires `state === 'transport'`, not a completed exchange.
- **Withholding an inbound frame from the initiator pins a client/daemon ordering race with no timer.** Since `initiateRekey` assigns `state` synchronously before it sends, gating the client's inbound delivery (rather than driving a second Noise initiator, or racing on timing) makes the "daemon already in the rekey state, client still in transport" window exact and deterministic.
- **AC3's oracle is the counterfactual, not a direct assertion.** The test can't assert "the daemon's `state` stayed `awaiting-rekey-init`" directly (no such accessor exists, by design). Instead it derives it: had the state been reset to `transport`, the client's real rekey `noise_init` would route to `handleReconnect`, whose `decodeEnvelope` over the rekey's empty early-data throws — so the resume frame's arrival is proof the state held.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- A test harness that is lax in the same direction as the code under test hides its own infidelity — worth checking, whenever a routing decision moves from A to B, whether the harness was ever exercising B honestly.
- `settle()` being first-wins makes a "harmless" baseline round-trip destroy observability: `handleTransport` settles `{ ok: true }` on its first reply, so every later reason is swallowed.
- Withholding an inbound frame from the initiator is cheaper than driving both sides of a race: the client stays in `transport` while the daemon has already synchronously assigned `awaiting-rekey-init`. No timers, no second Noise initiator.
