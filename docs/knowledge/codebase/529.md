# #529 — a clear path on `activeConversationStore` and `sessionIdStore`

Split from #508, sibling of [#528](528.md) (the timeline's `reset` arm — a reducer conversion, not
applicable here). Spec `81175e3`, shipped `37a3cd9`, zero deviation from
`docs/specs/architecture/529-store-clear-paths.md`. Size XS: three production files touched (two with
code, one comment-only), two test files, zero fan-out. Code review PASS, 1 NIT, PR#537.

## Summary

Both stores are app-lifetime singletons holding per-context state — one conversation, one pairing —
behind a single non-nullable setter with no way back except a process restart. Each already modeled
"nothing seen yet" as `null` and already exported the matching `initial*State` constant, so only the
road back was missing. This ticket adds that road, and nothing else:

- `activeConversationStore` gains `clearActiveConversation: () => void`
  (`src/renderer/src/store/activeConversationStore.ts`).
- `sessionIdStore` gains `clearSessionId: () => void` (`src/renderer/src/store/sessionIdStore.ts`).

Each is a single unconditional `set(initial<X>State)` in the factory — sourced from the exported
constant, not a fresh literal, so a future second field on either state stays covered for free. The new
member lands on the `*Store` type (state & mutations), never on the state-only `*State` interface, so
`selectActiveConversation`/`selectSessionId` can't see it and both `initial*State` constants stay
assignable — this is what makes "existing read surface untouched" structural rather than a promise.
Unconditional, so clearing an already-clear store is a no-op by construction, not by an early-return
guard.

**No production caller ships in this ticket (AC5).** `PairedShell.tsx:88` already holds
`setActiveConversation` and is the obvious-looking place to wire a clear from — it belongs to #530
(navigation), not this one; #531 (unpair / pair-another-server) is the other native blocker on #529.
Verified by `grep -rn "clearActiveConversation\|clearSessionId" src/ e2e/`: every hit is confined to the
two stores and their two `.test.ts` files.

### The design decisions (see the architecture doc for the full rationale)

- **Named second setter, not a widened setter, not a reducer.** A nullable `setSessionId(id: string |
  null)` was rejected: it would hand the *data path* (`sessionIdBridge.ts`) an un-set authority it must
  not have, and collide with the store's `''`-vs-`null` sentinel discipline. A `{ type: 'reset' }`
  reducer arm (the `threadTimeline`/`sessionStore`/`newFolderStore` precedent) was rejected too — every
  one of those precedents already *had* a reducer; converting a two-mutation store to host one nullary
  arm inverts the stores' own "single setter, not a reducer" reasoning instead of amending it.
- **Seven stale comment sites, all updated in the same commit** — both stores' header + selector
  docstrings, both test-file headers, and one cross-file site: `runSettingsWriteStore.ts:11`, which
  justified its reducer as "rather than `sessionIdStore`'s single setter... not one 'record the latest
  value' mutation." The architect's call (flagged as open in the ticket) was to fix it here rather than
  leave it stale — the replacement contrast is **coupling, not count**: `runSettingsWriteStore`'s three
  transitions are correlated and each reads prior state (a confirm/reject is a no-op without a matching
  pending record); `sessionIdStore`'s set and clear are independent whole-value writes that read
  nothing. The reducer's own justification survives, stronger, on the corrected premise.

## Patterns established

- **A second named setter beats a reducer conversion when the two mutations are independent
  whole-value writes.** The decisive test, reusable for any future single-setter-store clear-path
  ticket: do the mutations read prior state or constrain each other's ordering? If no (as here), a
  named setter is simplest and the store's existing "single setter, not a reducer" framing just needs
  its premise corrected from "exactly one mutation" to "independent whole-value writes." If yes (as in
  `runSettingsWriteStore`), a reducer is the honest shape — don't collapse a real state machine into
  named setters either.
- **A stale comment's cross-file blast radius is real and worth a grep, not just a skim of the two
  files being changed.** `runSettingsWriteStore.ts:11` was falsified by this ticket despite never being
  touched by the diff otherwise — the architecture doc's file-list caught it because it named the exact
  clause and the exact grep (`sessionIdStore` across `store/`) to distinguish it from eleven other,
  unrelated citations of `sessionIdStore` in the same directory.
- **Shipping a capability with a deliberately absent caller needs the absent caller stated as an AC**,
  not left to prose — same lesson [#528](528.md) drew, now confirmed twice: `PairedShell.tsx:88` is
  exactly the kind of open, in-file, plausible-looking site a developer agent will "helpfully" wire up
  unless the spec says not to and gives the grep to prove it didn't happen.
