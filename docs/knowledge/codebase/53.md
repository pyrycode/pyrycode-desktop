# #53 — Show the server-key fingerprint and require confirm before persisting the pairing

**Shipped:** 2026-07-04 · **Size:** S · **Scope:** background process only (`src/main/`) · greenfield, **zero consumer cascade** (nothing imports the new surface yet; composition-root wiring lands with #54) · **no new dependency** (`node:crypto` builtin) · one effectful edge, injected (the [paired-server store](../features/paired-server-store.md)) — **no keychain, filesystem, socket, IPC, or renderer** touched directly.
**Spec:** `docs/specs/architecture/53-server-key-fingerprint-confirm-gate.md` · **PR:** [#57](https://github.com/pyrycode/pyrycode-desktop/pull/57) · review: **PASS** (architect security-review pass in-spec, verdict PASS; code-review adversarial + security-goggles pass over the diff, **no findings**). Split from #9; folds in the fingerprint-confirm gate from #32 (mobile #501 parity, closed as superseded by the #9 split).

Adds the **fingerprint-confirm gate** — the pure `src/main/` service that turns a [validated pairing record](../features/pairing-payload-gate.md) into a short, human-comparable **fingerprint** of its `server_static_pubkey` and persists the record **only** through an explicit confirm step. It is the human-verify step mobile's paste path skipped (mobile #501): before the client trusts a pasted server key, the operator eyeballs its fingerprint against what `pyry pair` printed on pyrybox (and what the phone shows), and only then confirms. See the [pairing-confirmation feature doc](../features/pairing-confirmation.md) for the full contract, derivation, and security properties.

Scope lock held: **fingerprint derivation + one confirm-gated persist site only.** It consumes the `{ ok: true }` `QrPayload` from #52, derives the fingerprint, and returns (a) the fingerprint string and (b) a `confirm` handle over the injected store. It does **not** touch IPC / `safeStorage` / the filesystem / a socket / the renderer (all #54), does **not** re-parse or re-validate the payload (#52 owns that), and does **not** wire itself into app startup.

## Patterns established

- **A confirm gate makes "persist only after confirm" *structural*, not conventional.** `prepare` derives the fingerprint (sync, pure) and hands back the **only** persist handle, bound to the exact record it fingerprinted; deriving persists nothing. There is exactly **one** `store.save(` call site in the module — inside the `confirm` closure `prepare` builds (`grep` returns one hit) — reachable only through `prepare`, and **structurally absent on a rejected key** (a malformed key returns an `ok:false` arm with no `confirm` field). The security property is a shape of the code, not a rule someone must remember. This is the same "model the invariant into the type/shape so it can't be violated" discipline as [#52](52.md)'s discriminated-result gate and [#44](44.md)'s fail-loud `load`.
- **The reject arm carries no persist handle, so the type system enforces the gate.** `PreparedPairing` is a discriminated union on `ok`; reading `.confirm`/`.fingerprint` without narrowing on `ok === true` is a **compile error**. "No confirm on a malformed key" is partly type-enforced under `npm run typecheck`, not only tested.
- **A frozen snapshot at derive-time closes the derive→confirm TOCTOU.** `confirm` closes over a fresh `Object.freeze`d copy of the four fields captured at `prepare` time, **not** the caller's live reference. A caller (or a compromised #54 IPC round-trip) mutating its own record between derive and confirm cannot change the persisted bytes — the operator confirms exactly what they fingerprinted. Cheap belt (the store re-picks the four fields at encode time regardless), but it makes the confused-deputy gap unrepresentable.
- **Cross-implementation parity is pinned by a fixed vector, not recomputed in-test.** The fingerprint must be byte-identical to the daemon's `internal/pair.Fingerprint` and mobile's, so the operator's visual compare works across three implementations. The test **pins the literal** `32:0b:5e:a9:9e:65:3b:c2` for 32 zero bytes rather than recomputing it from `createHash` (which would be tautological — it would only prove the code equals itself). Code review recomputed the vector independently. This is the right shape for any value that must match another codebase byte-for-byte.
- **A load-bearing width is a named constant with its rationale in-code.** `FINGERPRINT_BYTES = 8` (64-bit truncation) carries a comment that narrowing is brute-forceable and widening defeats the operator's visual compare — so a future edit that "rounds it to 16 for safety" has to first delete the reason it can't.
- **Delegate the fail-closed contract; catch nothing.** Persistence goes through the injected [`PairedServerStore.save`](../features/paired-server-store.md); this service **catches nothing** from it, so the store's fail-closed `EncryptionUnavailableError` propagates uncaught. Wrapping `save` here would only risk swallowing the fail-closed guarantee — the store owns its error contract. The only errors this service *produces* are the two value-free `FingerprintReject` arms, and those are data (`ok:false`), never thrown — the same "rejection is routine data, not an exception" choice as [#52](52.md).
- **Log-free by construction, re-used verbatim.** No `console.*` anywhere; the record/key are opaque locals, never a reason field and never a returned field (the ok-object's own keys are exactly `ok`/`fingerprint`/`confirm`). The six-method console-spy test is copied from [#44](44.md)'s pattern. Same main-process-only, injected-seam, pure-core discipline as `secureStore`/`deviceKeypair`/`pairedServerStore`.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **Node's `Buffer.from(s, 'base64')` is lenient — and a re-encode-and-compare is the cheapest canonical-standard-base64 guard, which doubles as the malformed-key gate.** Node's base64 decode silently drops out-of-alphabet chars and tolerates missing padding, so a non-canonical string would decode to *some* bytes and produce a plausible-looking fingerprint. Guarding it with `keyBytes.toString('base64') !== pubkey` — re-encode the decoded bytes with the canonical (padded) standard alphabet and require it equals the input — rejects URL-safe alphabet, missing padding, dropped chars, and non-zero trailing bits in one check, and yields a **bijection** between accepted strings and 32-byte key sequences, which is exactly what the operator's visual fingerprint compare needs. This is the **third** appearance of the lenient-`Buffer.from`-base64 gotcha in this codebase ([#5 wire codec](5.md), [#52 payload gate](52.md), and here); each slice restores strictness the JS runtime discards. Encoding fidelity across the Go/JS boundary is a per-primitive audit, never automatic. (Note the two encodings in play: the **outer** envelope is `RawURLEncoding` — URL-safe, no padding, guarded in #52 — while the **inner** `server_static_pubkey` is standard padded `StdEncoding`, guarded here.)

No React re-render / effect-cleanup / dependency-version surprises to record — a pure main-process service with no React, no timers, no listeners, no new dependency; `prepare` is synchronous and total, `confirm` is a single `await store.save`.

## Deferred (open questions carried forward)

- **Composition-root wiring + IPC surface is #54's job, not this ticket.** Nothing constructs a live `PairingConfirmation`; the real `PairedServerStore` (over the real `createSecureStore`) is built at the composition root by the pairing IPC slice (#54). Wiring it in with no caller would be premature (the #21/#22/#42/#43/#44/#52 defer-wiring precedent), so no existing file was touched.
- **Hand-off requirements carried to #54** (from the spec's security review + #52's hand-off): the renderer must send a **bare "confirm" signal** (no payload, never a record) — the record stays in main keyed by the held `PreparedPairing`; only `fingerprint` (a hash) may flow to the renderer; #54 must hold **at most one** live `PreparedPairing` and **discard it on a new paste**, so `confirm` cannot persist a superseded record; and #54 must **validate the pasted-string IPC arg is a `string`** before calling `parsePairingPayload` (the renderer→main arg is untrusted; the deterministic type-guard belongs at the IPC boundary #54 introduces).
- **Fingerprint display styling is #54's renderer concern.** The colon-separated lowercase-hex form is fixed by parity (no desktop latitude); any spacing/label decoration wraps this exact 23-char string in #54, which carries its own Figma anchor.
- **Un-pair / re-pair after confirm** is out of scope (the store already overwrites last-writer-wins); confirm-then-reconnect is the transport's concern (#7/#30). A UI-level double-confirm button debounce is #54's concern — there is no observed double-confirm failure to defend at this layer (confirm is idempotent regardless).
