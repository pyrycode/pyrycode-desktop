# #530 — clear per-conversation context on a conversation switch

Split from #508, security-sensitive, native blocker on [#528](528.md) (timeline `reset` arm) and
[#529](529.md) (`clearActiveConversation`/`clearSessionId`), both landed. Spec `a02162b`, shipped
`d73d457`, zero deviation from `docs/specs/architecture/530-clear-per-conversation-context-on-switch.md`.
Size S: one new production file + its test, one file edited (`PairedShell.tsx`). Code review PASS,
0 blocking, 2 NITs, PR#540.

## Summary

Opening conversation B while A's rows sat in `timelineStore` rendered A's full history with B's stream
appended underneath — and if A was still streaming, its deltas kept landing in the thread the user was
reading as B. `sessionIdStore` had the same lifetime and a worse consequence: its single production
consumer, `RunConfigSections.tsx`, feeds the held id into an outbound `set_session_settings` write, so a
Run configuration change made while looking at B — including the YOLO / auto-approval toggle — was
addressed to A's still-running session.

`src/renderer/src/activateConversation.ts` (new) is the fix: a React-free helper, on the
`unpairAction.ts` / `composerSend.ts` Deps-bag precedent, that reads the previous active conversation
through an **injected getter**, and — only when `previous?.id !== conversation.id` — dispatches #528's
timeline `{ type: 'reset' }` and #529's `clearSessionId()` before unconditionally calling
`setActiveConversation(conversation)`. `PairedShell.tsx`'s two carrying nav sites (the `onOpen` row
click and the `conversationCreated` callback) now route through it; the notification-activated `open`
(#393, `PairedShell.tsx:99`) carries no conversation and so never reaches the helper at all — AC5 is
structural, not a runtime guard.

### The design decision (see the architecture doc for the full rationale)

- **Gate on the id, not the nav event.** Three sites dispatch `{ type: 'open' }`; only two carry a
  conversation. `onOpen` fires on every row click, including a re-click of the already-active row —
  clearing unconditionally there would destroy rows with no way to recover them (the timeline has no
  history backfill; its only production writers are `timelineBridge.ts:206` and `composerSend.ts:67`).
  The notification path (#393) dispatches the same `open` action with no conversation, deliberately —
  wiring a reset to `open` itself would wipe the thread on every notification click for the conversation
  already open.
- **A getter, not a value.** `useConversationCreatedNav` holds its callback in a ref refreshed by a
  *bare* effect (`conversationCreatedBridge.ts:84-87`) — i.e. after commit. A callback closing over a
  render-time "previous conversation" would let two `conversationCreated` events landing before that
  effect runs both compare against the same stale previous, and the second would skip a clear it owed.
  `getActiveConversation()` is invoked at call time, closing that gap by construction, and as a side
  effect keeps `PairedShell` from subscribing to `activeConversationStore` at all — it now holds **zero**
  store subscriptions (it had one) and re-renders only on its own `useReducer` nav dispatch.
- **`previous === null` takes the clear branch, no special case.** `previous?.id` is `undefined` on
  first activation and never equals a real id; clearing is free (`reset` returns `initialTimelineState`
  by reference, `clearSessionId` returns `initialSessionIdState`).
- **`setActiveConversation` stays unconditional on both branches** — #448's most-recent-wins contract is
  untouched, since a same-id re-open still refreshes the stored payload with a fresher
  `ConversationSummary` (a row click carries newer `last_message_ts`/`is_archived` than the held
  `ConversationCreatedPayload`).
- **`clearActiveConversation` (#529) is deliberately not called here** — it belongs to #531 (unpair /
  pair-another-server); calling it on this path would wipe the value the path is in the middle of
  setting.

## Files touched

- `src/renderer/src/activateConversation.ts` (new) — `ActivateConversationDeps` + `activateConversation`,
  fully documented inline (the ordering invariant, the getter-not-value rationale, the inert-controls
  consequence).
- `src/renderer/src/activateConversation.test.ts` (new) — plain-spy unit cases (AC1/AC2/AC3 branch
  behavior) plus integration cases against the real isolated stores, including the call-order assertion
  that pins clear-then-set (`['reset', 'clearSessionId', 'set']`) — the test that fails if the getter is
  ever "simplified" into a re-read after the write.
- `src/renderer/src/PairedShell.tsx` — drops the `useActiveConversationStore` hook read, adds a
  module-scope `activateDeps: ActivateConversationDeps` object wiring the three store singletons through
  `getState()` inside arrow bodies (the `timelineBridge.ts:206`/`sessionIdBridge.ts:68` idiom), and
  routes both carrying nav sites (`onOpen`, the `conversationCreated` callback) through
  `activateConversation(activateDeps, …)`. The notification nav site (`:99`) is untouched.

`PairedShell.test.tsx` gained **no new tests**, deliberately — the file has no jsdom harness (SSR
markup + `nextPairedRoute` reducer assertions only), so it cannot drive either callback; the behavior
lives in the pure helper where it is directly testable.

## Patterns established

- **A check-then-act decision fed by store state, sitting behind a bare-effect ref refresh, must take a
  getter, not a value.** `useConversationCreatedNav`'s ref-refresh-after-commit shape recurs anywhere a
  callback is threaded through a ref-holding hook; this ticket is the second one to hit it explicitly
  (see [#529](529.md)'s "Related" note on the same hook) and the first to need a getter to close it.
- **Mutually-protective positive/negative AC pairs are the cheap alternative to a mutation-testing run.**
  The code review verified this without running vitest (the review worktree has no `node_modules`):
  deleting the id guard fails AC3, inverting it fails AC1, dropping `clearSessionId()` fails AC1,
  reordering the set ahead of the clears fails the dedicated order test — every mutation to the branch
  is caught by some existing assertion, so the positive and negative cases stand as evidence without a
  live mutation run.
- **A capability shipped as call-site-free (#528, #529) with a same-named plausible call site nearby is
  exactly the shape a developer agent will "helpfully" wire up unless told not to** — third confirmation
  of the lesson [#528](528.md) and [#529](529.md) both drew: `clearActiveConversation` stayed uncalled
  here on purpose, reserved for #531.

## Lessons learned

- A callback held in a ref that is refreshed by a *bare* effect (`useConversationCreatedNav`,
  `conversationCreatedBridge.ts:84-87`) only refreshes after commit. Any per-render value such a
  callback closes over is stale for every event that lands before that effect runs — so a check-then-act
  decision fed by store state must take a getter, not a value. Both `PairedShell` nav callbacks are in
  this shape.
- Reading a zustand singleton through `getState()` inside a module-scope deps object (rather than a
  hook) removed the component's last subscription without breaking server-renderability, because the
  deref happens only when a callback fires, never during render.
