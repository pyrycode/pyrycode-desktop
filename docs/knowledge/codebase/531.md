# #531 — clear the ended pairing's thread, conversation id and session id

Split from #508, security-sensitive, last child; native blockers [#528](528.md) (timeline `reset` arm),
[#529](529.md) (`clearActiveConversation`/`clearSessionId`) and [#530](530.md) (the `activateConversation`
shape) all landed. Spec `0b89327`, shipped `65084a3`, PR#542. Code review PASS, 0 blocking, 3 NITs.
Size S: one new production file + its test, three files edited (`PairedShell.tsx`, `unpairAction.ts`,
`sessionStore.ts` comment-only) — 4 production files under the ≥5-file split gate.

## Summary

Unpair, then pair daemon B: the first thread opened still showed A's rows, and A's conversation id and
daemon session id survived to address outbound wire actions composed on B. Neither path that ends a
pairing cleared the state scoped to it — `runUnpair`'s ok branch reset only `sessionStore`, and
`onPairServerPaired` (pair-another-server, from inside the app) reset nothing at all.

`src/renderer/src/clearPairingScopedState.ts` (new) is the fix: a React-free, store-free helper — the
`activateConversation` / `unpairAction` / `composerSend` deps-bag idiom — that unconditionally and
synchronously runs all four clears already sitting capability-only: [#528](528.md)'s timeline `reset`,
[#529](529.md)'s `clearActiveConversation` and `clearSessionId`, and `sessionStore`'s own `reset`
(#166). Unlike [#530](530.md)'s `activateConversation`, there is no id gate — the pairing itself is
ending, so no state in which any of the four legitimately survives.

Both call sites live in `PairedShell.tsx`, wrapping the `onUnpaired` and `onPairServerPaired` props
where the shell hands them to `PairedShellView` — two adjacent lines over one module-scope deps bag —
rather than threading a new dep through `UnpairDeps` and `runUnpair`'s two `ConversationScreen.tsx` call
sites, as the ticket's own Technical Notes proposed. The spec's stated reason: it's the narrower shared
point (two lines apart, one file) and it makes AC3 (a failed unpair clears nothing) free — `runUnpair`
calls `onUnpaired` only on `result: 'ok'`, so wrapping that prop inherits the existing fail-safe posture
verbatim, no new branch. `runUnpair`'s own ok-branch `dispatch({ type: 'reset' })` is removed in the same
change: the helper is now the session store's single owner, so a later reader can't delete it from one
place believing the other still covers it.

## Design

The four clears, one seam:

| Store | Clear | Why it used to latch |
|---|---|---|
| `timelineStore` | `dispatch({ type: 'reset' })` (#528) | no history backfill |
| `activeConversationStore` | `clearActiveConversation()` (#529) | written only by a nav action |
| `sessionIdStore` | `clearSessionId()` (#529) | written only by a `sessionTransition` marker |
| `sessionStore` | `dispatch({ type: 'reset' })` (#166) | previously cleared on the unpair path only |

`sessionStore` is *in* the set, not beside it — folding it out to "the thing `runUnpair` already does"
would have left the pair-another path perpetually missing it, which is exactly the bug.

Both stores' idempotence-by-reference (`reset`/`clear*` return their shared `initial*State` constants)
is why the helper needs no guard: calling it on an already-clear store churns no `selectItems`/selector
subscriber. All four writes are synchronous with no `await` between them, so React's auto-batching lands
them in the same commit as the subsequent route change — no observer sees a half-cleared set.

- `src/renderer/src/store/sessionStore.ts` — comment-only. The `reset` arm's doc comment no longer claims
  the session reset alone "clears BOTH facets so a later re-pair never shows the previous pairing's

reducer assertions only), the same gap [#530](530.md) accepted for `activateConversation`.

## Patterns established

- **Wrap the gated callback prop at the shared parent rather than inject a dependency at every leaf call
  site.** `runUnpair` has two call sites 300 lines apart in a 1850-line file; the `onUnpaired` prop they
  both funnel through sits two lines from `onPairServerPaired` in `PairedShell.tsx`. When two divergent
  paths need one shared effect, look for the narrowest point they already share (a prop, a callback) before
  widening an interface to carry a new dependency through every call site.
- **A duplicate reset that's idempotent at runtime is still a divergence trap.** Leaving `sessionStore`'s
  reset in both `runUnpair` and the new helper would have been harmless today (idempotent by reference) but
  is the shape that lets a later reader delete the "redundant" one from the helper, silently breaking the
  path that had no other owner — with every existing test still green. The guard against this is a negative
  test pinning single ownership (`ok → dispatch never called`), not a comment.
- **Self-heal vs. latch is the mechanical scope test for "clear the stale state on X" tickets.** A store is
  in scope iff nothing on the new context re-asserts it — `conversationListStore`/`recentWorkspacesStore`/
  `serverInfoStore`/`queueStore`/`modalStore`/`runConfigStore` all self-heal (mount request, remount
  re-fetch, one-shot invoke, or the `connected` edge) and were correctly left out; `timelineStore`/
  `activeConversationStore`/`sessionIdStore`/`sessionStore` have no such path. Put the self-heal
  enumeration in the spec body — it forecloses spec-time scope creep and pre-answers the code review's
  "did you check the siblings" question.

## Lessons learned

- A duplicate, idempotent reset is a divergence trap, not a harmless redundancy — see Patterns
  established above. The regression guard is the negative assertion that pins single ownership.
- The design source (Figma node 16-8) anchored the *absence* of a visual change as usefully as a presence
  would have: the node is the populated thread, and the ticket's contract is that content belongs to the
  pairing that produced it, so a freshly paired server renders the already-shipped empty state with an
  inert run-config strip. Zero rendering code in the diff — worth confirming against the design doc
  anyway, since "no visual change" is a claim, not an default assumption.
- The code review's one open item worth carrying forward: the ordering invariant ("clear runs before the
  route flips") lost its only executable assertion when the pre-#531 `unpairAction.test.ts` ordering case
  was deleted, because `PairedShell.test.tsx` has no jsdom harness to drive the wrapper callback that now
  owns that ordering. Low-stakes today (all four writes are synchronous, batched into one commit with the
  route change), but the next time a jsdom harness lands in this repo, this is the assertion that should
  come back.
