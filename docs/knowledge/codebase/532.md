# #532 — route inbound frames in the rekey window by inner frame type

**Spec:** `docs/specs/architecture/532-route-inbound-frames-rekey-window-inner-frame-type.md` (`e0b793c`) · **Dev:** `3110fc2` · **PR:** [#534](https://github.com/pyrycode/pyrycode-desktop/pull/534). Split from [#507](https://github.com/pyrycode/pyrycode-desktop/issues/507); predecessors [#524](524.md) (daemon-side routing by inner type) and [#525](525.md) (fake tags handshake replies `noise_resp`) — both of which named this ticket as the reason they shipped first.

## What it does

Fixed a permanent-desync bug: while the client's `noiseSession` sat parked in `awaiting-rekey-reply`, it fed **whatever frame arrived next** into `hs.ReadMessage` as the daemon's rekey reply. The daemon does not stop the world for a rekey — per pyrycode spec #450, it keeps fanning out ordinary transport frames under the OLD ciphers for the whole awaiting-reply window, and any such frame that lands ahead of the genuine reply (TCP-ordered, since the daemon emits it before processing the client's `noise_init`) got consumed as the reply instead. `ReadMessage` MAC-failed, the fresh handshake was freed, and the client fell back to `transport` on the OLD ciphers and surfaced `error{handshake-read-failed}` — while the daemon had already completed its swap to the NEW ciphers. The client's next send, sealed under the now-dead old key, failed the daemon's new `s.recv` and hit its tampered-frame branch: `closeWith(4421)` and session removal. Not a dropped frame — the session was gone.

## What shipped

**`NoiseSession.onFrame` gains an optional inner-type label: `onFrame(frame: Uint8Array, innerType?: string): void`.** Optional, not required — the sizing constraint: 35 existing test call sites across `noiseSession.test.ts`/`noiseSession.interop.test.ts`/`fakeDaemon.test.ts` feed `onFrame` with no label, and a required parameter would have turned an S ticket into a fixture cascade. A module-private `NOISE_RESP_TYPE = 'noise_resp'` constant is added, sibling to the existing `REKEY_REQUEST_TYPE`.

**The label is consulted in exactly one state, `awaiting-rekey-reply`.** Every other state (`idle`, `awaiting-handshake-reply`, `transport`, `closed`) ignores it outright — the Noise state machine plus AEAD remain the sole authority everywhere else. Inside `awaiting-rekey-reply`:

```
isReply  ⇔  innerType === undefined  ||  innerType === NOISE_RESP_TYPE
```

- **`isReply` → the existing reply path, byte-for-byte unchanged** (`hs.ReadMessage` → `Split` → atomic swap, or on throw: `hs = null`, `state = 'transport'`, `failWithFrame('handshake-read-failed', frame)`).
- **Otherwise → a new old-cipher transport path**: `recvCipher.DecryptWithAd(EMPTY_AD, frame)`. On success, `config.onEvent({type:'message', plaintext})` — the same event, same consumer, as outside the window (AC1). On throw, `failWithFrame('transport-decrypt-failed', frame)` and **return without touching `hs` or `state`** — the session stays parked, the one-shot reply slot survives, so a genuine reply arriving afterward still completes the swap (AC5).

The rule is **positive on `noise_resp`, not negative on `noise_msg`** — an unknown or hostile label takes the gentler non-terminal branch rather than burning the one-shot handshake read. `innerType === undefined` routes to the reply path (the honest pre-#532 assumption, now written down); in production this arm is unreachable, since `decodeInnerFrame` rejects a non-string `type` before the session is ever called — it exists solely so the 35 legacy call sites keep behaving exactly as before.

**Deliberate asymmetry: the window path does not re-run `isRekeyRequest`.** A `rekey_request` interleaved into an already-open window can't be represented (`beginRekey`'s `state !== 'transport'` guard would no-op it), but emitting `rekey-requested` would still arm the driver's `rekeyInitPending` latch and mis-tag the *next* outbound app frame as `noise_init` after the swap — routing it into the daemon's reconnect handler and failing closed. So the window path only decrypts and emits `message`, nothing else.

**`noiseRelayDriver` threads the label through both delivery paths, taking no routing decision itself.** `onMessage` keeps the decoded `type` alongside `.data` and passes both to `session.onFrame(raw, type)` — pass-through only. The `pending` async-create-gap buffer changed shape from `Uint8Array[]` to `Array<{raw: Uint8Array; type: string}>`, so a buffered frame replays with its real tag rather than defaulting to `undefined` on reconnect. `MAX_PENDING_FRAMES` and the count-based bound are unchanged; the added string is itself bounded by the codec's frame-size cap. The stale threat-model comment at the old `onMessage` site ("The inner `type` label is NOT branched on") was rewritten to state the successor model: the label is forwarded verbatim, consulted by the session in exactly one state for routing only, and interpretation still belongs to the Noise state machine + AEAD — a hostile type can only pick which of two pre-existing rejections an already-doomed frame takes, never a downgrade or a transport bypass. Reused the mirror-image argument already written on the daemon side (`fakeDaemon.ts`).

**Two harness gates relaxed, both a precondition for reproducing AC1 at all — a test daemon that can't emit an app frame during its own rekey window can't exercise this fix:**

1. `fakeDaemon.pushFrame` no-op'd outside `state === 'transport'`. Now also serves in `awaiting-rekey-init`, since the fake's cipher swap happens only inside `handleRekeyInit` — the old send cipher is still live throughout that window, matching the real daemon per spec #450. The outbound tag is unchanged (`sendNoise`'s `noise_msg` default).
2. `createNoiseResponder` (the in-file double in `noiseSession.test.ts`, distinct from `fakeDaemon`) had the same shape: `sendMessage`'s `state !== 'transport'` gate now also admits `awaiting-rekey-init`, on the identical rationale. The double's `sendFrame` callback was also widened to `(frame, type) => void` so it tags its own outbound frames (`noise_resp` on both handshake replies, `noise_msg` on `sendMessage`/`initiateRekey`) — matching the real daemon and `fakeDaemon` exactly, and forcing no edits to existing one-parameter fixture lambdas (a narrower-arity function stays assignable).

## Testing

- `noiseSession.test.ts`: new scenarios covering AC1+AC2+AC3 (an interleaved app frame decrypts and surfaces as `message` with zero errors, then the genuine reply still completes the swap and K1 round-trips both ways), AC5 (an undecryptable non-reply frame in the window surfaces exactly one `transport-decrypt-failed` and no `handshake-read-failed`, and a subsequent genuine reply still swaps), and the routing mutation control (garbage labelled `noise_resp` still produces `handshake-read-failed` — the label, not the bytes, chooses the path). The pre-existing clean-rekey test (`:494-519`, nothing interleaved) and the AC4 unlabelled-garbage regression guard (`:584-636`) stayed green untouched, proving the defaulted parameter preserves every legacy caller.
- `noiseRelayDriver.test.ts`: new assertions that the driver forwards the inner type verbatim on live delivery, and that a buffered frame's label survives the async-create-gap replay intact rather than arriving as `undefined`.
- `fakeDaemon.test.ts`: `driveClient`'s `deliverFrame` now threads the decoded inner type into `initiator.onFrame` (previously discarded it entirely — a pre-#532 fidelity gap that would have left this whole suite blind to the client's new routing). A new end-to-end scenario drives the real `createNoiseSession` over the real codec and socket through the full interleave sequence — hold both daemon frames at the relay boundary, release and deliver in one synchronous turn, assert exactly one `message` for the interleaved frame, then the swap completing, then a K1 round-trip in both directions, zero errors, and the full ordered `inboundTypes` tag sequence via `toEqual` (the #525 oracle, which catches a handshake site regressing to `noise_msg` and a transport site wrongly becoming `noise_resp` in one assertion).
- Non-vacuity run before the PR: positive control (interleave scenario red with zero messages against unmodified code — that failure *is* the bug), an inverted routing predicate killing 4 tests including the pre-existing clean-rekey baseline, and independent mutation checks on the driver's live-delivery and replay label plumbing.

## Patterns established

- **A defaulted/optional parameter is the right shape when the ticket's constraint is "don't force N existing call sites to change."** The same call as [#525](525.md)'s `sendNoise` tag parameter, on the client-reading side this time: `onFrame`'s `innerType?: string` keeps all 35 legacy callers compiling and behaving identically, at the cost of an unreachable-in-production default arm that has to be documented as such so a future reader doesn't "tighten" it into a required parameter and cascade the fixtures.
- **An inverted-predicate mutation is only a convincing control if it kills a test that predates the change**, not just the new ones — otherwise a "positive on X" rule could just as easily have been "negative on Y" and nothing would have caught the difference. Here the inversion took down the pre-existing #111 clean-rekey baseline alongside the three new scenarios.
- **Widening a test double's callback signature (`sendFrame: (f) => void` → `(f, t) => void`) forces no call-site edits** — a narrower-arity lambda stays assignable in TypeScript, so only the fixture that needed labels opted in, and the untouched regression tests kept exercising the unlabelled path for free. Same idiom as [#525](525.md)'s `sendNoise`.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- A defaulted parameter's default arm can be production-unreachable and still be load-bearing: `codec.ts` rejects a non-string inner `type`, so production always supplies a label, and the `undefined` arm exists solely so the 35 pre-existing unlabelled call sites keep their old behaviour. Naming that in the code stops a future reader from "tightening" it into a required parameter and cascading the fixtures.
- Widening a test double's callback type forces no call-site edits — changing `createNoiseResponder`'s `sendFrame` to `(frame, type) => void` left every existing one-parameter lambda assignable, so only the one fixture that needed labels opted in, which is also why the two untouched regression tests kept exercising the unlabelled path for free.
- An inverted-predicate mutation is only convincing if it kills a test that predates the change — here it took down the #111 clean-rekey baseline alongside the three new scenarios; had it killed only the new tests, the "positive on `noise_resp`" rule would have been pinned by nothing but its own assertions.

## Deferred / carried forward

- **The fake-daemon interleave scenario doesn't pin the production driver's label plumbing.** It drives the real `createNoiseSession` over the real codec and socket, but through `driveClient`'s own delivery rather than `createNoiseRelayDriver` — so the driver's live-delivery and replay-buffer label forwarding are pinned by the `noiseRelayDriver.test.ts` scenarios instead, not by this end-to-end test. Named in the PR body as a boundary, not grown into a bigger harness (per spec open question 2).
- **A client-side timeout on `awaiting-rekey-reply` remains unbuilt**, named explicitly by the architect's security review as out of scope but worth flagging forward: nothing on the desktop side ever gives up on a stalled rekey today, and after this change a relabelled `noise_msg` frame no longer closes the window the way any frame used to. The exposure is bounded — the daemon's own 30s reply timer still closes at WS 4426 on expiry — but a genuine client-side deadline is real hardening and was recorded as a PO follow-up, not this S bug fix's job.
- **`fakeDaemon`'s pre-existing inbound `noise_resp` laxity** (the real daemon rejects an inbound `noise_resp` from a client; the fake still accepts one as an ordinary transport frame) is untouched — this ticket only reads the tag on the client side. Already tracked as a PO follow-up from [#525](525.md).
