## What it does

Fixed a silent-drop bug: `noiseSession.sendMessage` no-op'd in every state but `transport`, so a send issued while the session was parked in `awaiting-rekey-reply` — the ~one-relay-round-trip window during an in-session rekey — was discarded with no queue, no retry, and no error. Nothing upstream compensated: the driver delegated straight through, and all 22 of `daemonConnection`'s outbound commands `catch`-dropped. The loss was invisible to the user in the worst way — `composerSend` posts its optimistic `userText` echo into the timeline regardless of send outcome, so a message could be shown as sent while the daemon never received it; a modal answer lost this way left the daemon blocked on a prompt the user had already answered.

## What shipped

**The session now holds outbound plaintext during the window and flushes it after the atomic cipher swap, sealed under the *new* send cipher.** Mirroring [#532](532.md) — sealing under the still-live *old* send cipher — was considered and rejected as fatal, not merely lossy: the client enters `awaiting-rekey-reply` only *after* handing its own `noise_init` to `sendFrame`, so every windowed send is TCP-ordered **behind** that frame. The daemon swaps **both** ciphers the moment it processes `noise_init`, so an old-cipher frame arriving afterwards fails the daemon's new `recv` and hits its tampered-frame branch — `closeWith(4421)` and session removal, the same consequence [#532](532.md)'s doc records for the pre-fix desync. Buffer-and-flush-after-swap is the only shape that keeps the session alive.

**`sendMessage` gains one new branch, first in order:**

1. `state === 'awaiting-rekey-reply'` → buffer a **copy** of the plaintext (`plaintext.slice()`) if under `MAX_BUFFERED_SENDS`; otherwise drop the incoming send (never evict the oldest) and `fail('rekey-send-buffer-full')`. Return either way.
2. The pre-existing `state !== 'transport' || sendCipher === null` guard — byte-for-byte unchanged. `idle`, `awaiting-handshake-reply`, and `closed` stay inert; pre-handshake buffering is deliberately **not** added (no session exists yet — `sendCipher` is null until `Split` — and the composer's `canSend` gate is genuinely closed in that window, unlike the rekey window which presents as connected throughout).
3. `transport` → seal and send, unchanged.

**`MAX_BUFFERED_SENDS = 8`**, an exported const with its rationale written at the declaration (same shape as `noiseRelayDriver.ts`'s `MAX_PENDING_FRAMES`, deliberately diverging on one point: that buffer drops silently because a pre-session frame from a hostile relay is already anomalous garbage, while this buffer's dropped item is the user's own message, so the drop must be observable). The byte dimension needed no second cap: `encodeEnvelope` already rejects an over-cap envelope against `MAX_PLAINTEXT_BYTES = 65519` upstream in `daemonConnection`, so the worst case is a deterministic `MAX_BUFFERED_SENDS × 65519` ≈ 512 KiB.

**Flush (`flushBufferedSends`) runs at the very end of the atomic swap** — after both cipher assignments and after `state = 'transport'` — and drains the buffer **through `sendMessage` itself**, not a private seal loop:

- **Take, then drain** (`bufferedSends.splice(0)` before iterating): `config.sendFrame` is a synchronous sink that can re-enter `onFrame` (the same hazard `beginRekey`'s set-state-before-send ordering already documents), so iterating the live array while a re-entrant call mutates it would be a bug. `splice(0)` also makes a double-drain unrepresentable.
- **Re-entering `sendMessage` re-reads the live `sendCipher` on every iteration** — the security-load-bearing reason it isn't a private loop. A loop that captured a cipher reference before or during the swap could seal an item under `prevSend`, which the swap `free()`s — a use-after-free on a wasm object, and a frame the daemon can only reject. And if a re-entrant frame opens a *second* rekey mid-flush, going back through the entry point re-buffers the remaining items and flushes them after the second swap, still in issue order; a captured-cipher loop would seal them under a cipher no longer current.
- Ordering (AC1) then falls out for free: the flush completes synchronously inside the `onFrame` turn that performed the swap, so any send issued after the swap is necessarily issued after `onFrame` returns and lands last.
- **Frame tagging was verified, not assumed:** the driver's `firstFrame`/`rekeyInitPending` latches are both one-shot and already consumed by the rekey msg1 itself, so a flushed frame goes out as `noise_msg` — keeping this a session-only change with zero driver edit.

**Discard, at the reply-path failure `catch`.** If the rekey fails (garbage/malformed reply), the buffer is cleared *before* either error is emitted — `fail()`/`failWithFrame()` invoke a synchronous consumer that can re-enter `sendMessage` while `state` is already back to `transport`, so a stale item left behind could otherwise be picked up by a later window's flush. Then `failWithFrame('handshake-read-failed', frame)` (root cause, unchanged), then `fail('rekey-send-abandoned')` once — only if the buffer was non-empty, and never carrying a count (a count would correlate with user activity, which the module's content-free discipline forbids). Re-sending under the surviving old ciphers was rejected: the client cannot distinguish "our `noise_init` never reached the daemon" (old ciphers still valid there) from "the daemon swapped and the reply was corrupted in transit" (an old-cipher send is the fatal 4421 case) — both present identically as a failed `ReadMessage`, so the only safe branch assumes the worst and discards.

**Discard, at `close()`.** The buffer is released and nothing is emitted — an error during ordinary teardown would be noise on every window close and on the daemon's own 30s/WS-4426 path, which is the buffer's own worst-case terminator.

**Two new `NoiseSessionErrorReason` members**, both raised only in the rekey window: `rekey-send-buffer-full` (a send arrived at the bound; that one send was dropped) and `rekey-send-abandoned` (the rekey failed; every buffered plaintext was discarded unsent). **Zero fan-out**: `RelaySessionErrorReason` in `noiseRelayDriver.ts` is *defined as* `NoiseSessionErrorReason | <three adapter reasons>`, so the driver needs no edit; `daemonConnection`'s `messageFor` has a `default` arm and its `case 'error'` forwards `event.reason` generically — so both reasons reach `emitFailed` → `{type:'failed', retryable:false}` automatically. **This was a deliberate choice, not a discovery**: both reasons produce a terminal, non-retryable UI failure, including the overflow case, on the same precedent as the pre-existing `transport-decrypt-failed` (a recoverable session-level anomaly that already reads as a hard UI failure) — a softer mapping was explicitly rejected as an architecture change beyond an S bug fix, and because nine sends inside one relay round-trip already means the window is heading for the daemon's own 4426 teardown regardless.

## Testing

Five new scenarios in the `#111` rekey describe block, one per AC, built on the `pair()` helper's existing `holdInitiatorFrames`/`releaseInitiatorFrames` gate unmodified (no timers): AC1 delivery-and-ordering (three windowed sends plus a post-swap send arrive at the responder in issue order, zero errors — asserted against the **responder's** collector, since "never sealed" is only observable as "`sendFrame` never called with it"); AC2 the bound (`MAX_BUFFERED_SENDS + 1` sends → exactly one `rekey-send-buffer-full`, the incoming send dropped not the oldest, driven off the exported const); AC3 rekey failure (clones the `dropInitiatorFrames` shape, captures rather than discards the withheld frames, asserts both errors in order, zero buffered plaintext ever reached `sendFrame`, and the session still round-trips on the old keys afterward); AC4 close-releases (no error emitted, no frame ever escapes after a subsequent release); AC5 inertness elsewhere (`idle`/`awaiting-handshake-reply`/`closed` still emit nothing **and buffer nothing**, asserted by driving the session to `transport` afterward and showing no deferred frame appears).

**Non-vacuity controls, run and recorded in the PR body:** a positive control (the AC1 scenario against unmodified `sendMessage` is red, responder receives zero window messages); a mutation inverting the new state predicate (buffer in `transport` instead of `awaiting-rekey-reply`) kills 10 tests, **7 of which predate this change** (the mode-2 round-trip, all three #111 tests, all three #532 window tests) — proof the rule's direction is pinned by more than its own assertions, and specifically relevant because AC4/AC5 are negative-space ACs ("must not") that pass vacuously against code that doesn't implement the feature at all; their only evidence is this mutation.

## Patterns established

- **A negative-space AC ("must not X") needs a companion mutation, not just a green test** — it passes vacuously against unimplemented code. Here AC4 and AC5 are regression guards on the new code, not positive controls; the inverted-predicate mutation is what actually pins them.
- **Draining a buffer back through the same public entry point (rather than a private seal loop) can be the *safer* shape, not just the simpler one**, when the entry point re-reads live mutable state (here, the current cipher) on each call — it closes both a use-after-free window and a re-entrant-second-rekey window for free, at the cost of one extra state-predicate branch inside that entry point.
- **"The buffer is bounded" can already be true in bytes before a count bound is added** — check where an upstream size cap runs (here, `encodeEnvelope`'s `MAX_PLAINTEXT_BYTES` in `daemonConnection`, upstream of the driver) before adding a second one.
- **Copy-on-buffer (`plaintext.slice()`) turns a narrowing of an implicit contract into a no-op** — `sendMessage` used to consume its argument synchronously, so a caller could legally hand over a scratch buffer it intended to reuse; holding a reference across a round-trip would have made that legal caller a silent corruption bug.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- A negative-space AC needs a companion mutation, not just a green test. AC4 (`close()` releases the buffer) and AC5 (inertness elsewhere) both assert that nothing happens, so they pass against code that doesn't implement the feature at all. Their evidential value comes entirely from the inverted-predicate mutation; without it, two of the five AC tests would have been decorative. Worth checking on any ticket whose ACs are phrased as "must not".
- "The buffer is bounded" was already true in bytes before the count bound was added. `encodeEnvelope` enforces `MAX_PLAINTEXT_BYTES` in `daemonConnection`, upstream of `driver.sendMessage`, so every plaintext that can reach a main-process send buffer is already ≤ 65519 bytes — the count cap turns that into a deterministic ~512 KiB worst case, and a second byte cap here would have been redundant. Checking where the upstream cap actually runs is worth one grep before adding a bound.
- Draining through the public entry point bought two correctness properties for free. Re-entering `sendMessage` per item re-reads the live `sendCipher` (so no item can be sealed under the `prevSend` the swap just `free()`d — a use-after-free on a wasm object), and if a re-entrant frame opened a second rekey mid-flush the remaining items re-buffer and flush after that swap, still in issue order. A private seal loop would have had to re-implement both, and would look simpler while being wrong.
- Ordering of two emits at one failure exit is a real decision. The rekey-failure path emits `handshake-read-failed` then `rekey-send-abandoned` (root cause first), but the buffer is cleared *before* either — `fail()` invokes a synchronous consumer, and by then `state` is back to `transport`, so a stale item left behind could be picked up by a later window's flush.

## Deferred / carried forward

- **A client-side deadline on `awaiting-rekey-reply` is still unbuilt and still unfiled.** #532 named it as carried-forward; this ticket's security review named it again explicitly and asked the PO to file it — it has not been, as of this writing. Nothing on the desktop side ever gives up on a stalled rekey; the only backstop remains the daemon's own 30s reply timer closing at WS 4426. This ticket's bound is what makes that absence survivable *for the buffer specifically* (a deterministic ~512 KiB residency ceiling), but the residency *window* itself stays relay-controlled.
- **A discarded send leaves `daemonConnection`'s reply-correlation state orphaned** (`nextEnvelopeId` consumed, an `outstandingAnswers`/`pendingCreateFolders` entry never resolves). Pre-existing behaviour for *any* dropped send (the 22 `catch`-drop sites), not introduced here, and both new reasons already reach `emitFailed`'s connection-teardown net. Named as a boundary, not a requirement.
- **#510** (a modal answer clicked while *disconnected* is swallowed) is the same class of harm through a different door — a no-session state the UI already knows about, rather than a window invisible above the transport — and is not fixed by this ticket.
