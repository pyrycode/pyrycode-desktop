# #539 — a `reconnected` arm: clear stranded pending settings changes on reconnect

PR #543 (`b9ad858`, spec `1a5f42a`). Split from [#509](https://github.com/pyrycode/pyrycode-desktop/issues/509)
(sibling: [#538](538.md), thread-timeline reconcile). Size XS, as estimated: 2 production files, zero
forced call sites (`RunSettingsWriteEvent` is switched over in exactly one production place,
`reduceRunSettingsWrite`, under `assertNever`). `security-sensitive` (architect self-review PASS, no
findings). Code review: **PASS**, 0 blocking, 2 NITs (neither changed the implementation).

## Summary

A `changeDispatched` entry left `pending` only via a correlated confirm or reject. Main abandons its
envelope-id → `changeId` correlation on every re-dial (`daemonConnection.ts` `dial()`,
`pendingSettings.clear()`) and emits nothing in its place, so the reply for a change in flight during a
drop could never arrive — the entry strands. That was worse than a stuck banner:
`selectEffectiveSettings` gives `pending` precedence over `confirmed`, and a later same-field change
deletes only its **own** entry on confirm, so the stranded entry became the surviving overlay — the sheet
reverted to the never-applied value permanently, while the daemon ran the confirmed one. On the YOLO
toggle that meant the sheet could show auto-approval off while the daemon ran with it on, which is why
this XS slice carried `security-sensitive`.

`modalStore` (#415), `queueStore` (#197) and the thread timeline ([#538](538.md)) already reconcile on
the daemon's `connected` edge; this was the last of the four still missing its half.

Two production edits, both additive, in `src/renderer/src/store/`:

- **`runSettingsWriteStore.ts`** — a new nullary `{ type: 'reconnected' }` arm on
  `RunSettingsWriteEvent` (the first arm without a `changeId`, since its whole job is to abandon
  correlations rather than resolve one) and a `case 'reconnected'` after `case 'settingsRejected'`.
  Clears `pending` to a fresh `new Map()` — not the shared `initialRunSettingsWriteState.pending`
  reference, a latent footgun for zero gain — while **preserving** `confirmed` and `error` via
  `{ ...state, pending: new Map() }`. Early-outs to the same `state` reference when `pending.size === 0`
  already (AC4): load-bearing, not cosmetic, because `RunConfigSections.tsx:327` selects the **whole raw
  write state** as its zustand selector, so this `Object.is` short-circuit is what keeps a reconnect with
  nothing in flight from re-rendering the whole sheet.
- **`runSettingsWriteBridge.ts`** — `translateWriteEvent` gains `case 'connected': return { type:
  'reconnected' }` immediately above the existing `default: null`, ignoring `event.ack`
  (`HelloAckPayload`) entirely (placement mirrors `modalBridge.ts:61`). Unlike #538's timeline bridge,
  this one never had an exhaustive null-cluster listing `connected` to prune, so there was no
  stranded-fixture risk to guard against on removal — this is a pure addition.

**Spread vs. literal inverts vs. #538, same reasoning, opposite conclusion.** #538 argued *against*
`{ ...initialTimelineState, items: state.items }` for its arm — a future sixth `TimelineState` field
would be silently wiped. This arm spreads **`state`**, not the initial constant, so the same mechanism
runs the other way: an unknown future field is **preserved** by default, the conservative direction and
the one that matches AC3's posture ("clear the one thing that strands, leave everything else alone"). It
is also this file's existing idiom — all three prior arms already return `{ ...state, … }`. The residual
is the mirror image of #538's: a future field that is itself *pending-scoped* would need adding to this
arm by hand, and TypeScript will not force it — stated in an inline comment rather than engineered around.

**Accepted residuals, not engineered around (both named in the spec and the PR body):**

1. The outage window itself — the sheet still shows the optimistic never-applied value for the duration
   of a drop, because the clear fires on reconnect, not on the drop. Unavoidable: `{ type: 'disconnected'
   }` is emitted nowhere in `src/main` (every `emitDaemonEvent` call site was enumerated — only
   `connecting`, `connected`, `failed`).
2. A single-IPC-hop window — a change dispatched between main emitting `connected` and the renderer
   receiving it is genuinely sent and correlated, and gets cleared anyway; its later confirm lands as a
   no-match no-op via the existing fail-closed guards, so it never commits. Closing it would need
   per-change generation correlation across the IPC boundary, out of proportion to the defect.

9 new vitest cases across the two touched test files (7 reducer, 2 bridge) — clears N outstanding entries
regardless of count (AC1, with a `pending.size === 3` precondition assert so the test can't pass on a
store that recorded nothing); rolls back to the last confirmed value, or to the snapshot base absent one
(AC3, two cases); `confirmed` and `error` both survive (AC3); same-reference no-op from a
**dirty-but-not-pending** state — not the pristine initial state, which would let an implementation
predicate on the whole state being empty instead of on `pending.size` (AC4); idempotent on a second
`reconnected`; a change dispatched after the clear still confirms normally (not a dead-mode latch); and
the central regression (AC2) — dispatch `c1: model=opus`, `reconnected`, dispatch `c2: model=sonnet`,
confirm `c2`, assert `sonnet` — **then** fire a late confirm for `c1` and assert the effective model is
still `sonnet` and `confirmed.model` is still `sonnet`, which is what actually pins "cannot resurface"
rather than merely "is currently absent." `npm test` on the two touched files (42 tests, RED 10 → GREEN);
whole `src/renderer/src/store` directory green as a neighborhood check (34 files, 547 tests); `npm run
build` clean.

## Patterns established

- **A sibling's rule doesn't transfer — its reasoning does.** #538's "don't spread the initial constant"
  guidance and this arm's "spread `state`, not the initial constant" both follow from the same mechanism
  (an unspread field is silently dropped/kept by whichever thing you *didn't* spread) but land opposite
  conclusions once you ask what's actually being spread. Re-derive from the mechanism each time; don't
  copy the prior ticket's verdict.
- **A same-reference early-out is load-bearing exactly when its consumer selects the whole raw state.**
  `RunConfigSections.tsx:327`'s `(s) => s` selector is what turns the `pending.size === 0` early-out from
  a nice-to-have into the only thing standing between every reconnect and a full sheet re-render — grep
  the consumer's selector before calling an early-out "just" a churn optimization.
- **This is the fourth `connected`-edge reconcile arm of the same shape** (`modalPrompts.ts` #415,
  `queueStore` #197, `threadTimeline.ts` [#538](538.md), now `runSettingsWriteStore.ts`) — bare event in,
  one slice cleared, everything else preserved by reference, same-reference early-out. #509's split is
  now fully closed: no renderer store with reconnect-sensitive state lacks this reconcile.

## Lessons learned

*(from the PR body)*

- The spread-vs-literal choice in a "clear one slice" reducer arm inverts depending on *what* you spread,
  so a sibling's rule doesn't transfer as-is — see § Patterns established above. Worth copying a
  sibling's *reasoning* and re-deriving the conclusion, not copying the rule itself.
- A same-reference early-out can be load-bearing rather than cosmetic, and the consumer is what tells you
  which — `RunConfigSections.tsx:327` deliberately selects the whole raw write state, so `Object.is` is
  the only thing keeping every reconnect from re-rendering the entire sheet. The test that pins it has to
  use a *dirty-but-not-pending* state, or it passes on an implementation that predicates on the whole
  state being empty instead of on `pending.size`.

*(from code review, cosmetic — not applied, left as-is)* Two non-blocking NITs, neither changing the
shipped implementation (details not reproduced here; see PR #543 review thread if needed).
