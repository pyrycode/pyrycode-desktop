# #54 — Typed pairing IPC channel and main-process handler

**Shipped:** 2026-07-04 · **Size:** S · **Scope:** shared + background + preload + composition root (`src/shared/ipc/`, `src/main/`, `src/preload/`) · additive to the #17/#18 IPC module, **zero consumer cascade** (`PyryApi` auto-flows the two preload methods; `index.d.ts` untouched) · **no new dependency**.
**Spec:** `docs/specs/architecture/54-typed-pairing-ipc-channel.md` · **PR:** [#59](https://github.com/pyrycode/pyrycode-desktop/pull/59) · review: **PASS** (architect security-review pass in-spec, verdict PASS; code-review adversarial + security-goggles pass over the diff — **no MUST/SHOULD FIX, one non-blocking NIT**). Split from #9; `security-sensitive`.

The **request/response twin** of the [command channel](../features/command-channel.md) (#17): the seam the pairing screen (#55) drives to submit a pasted payload → receive a **display fingerprint** to confirm → send a bare confirm → receive success/failure, without ever handling the token or server key. It composes the two upstream slices — [#52 `parsePairingPayload`](../features/pairing-payload-gate.md) and [#53 `createPairingConfirmation`](../features/pairing-confirmation.md) — behind a single `ipcMain.handle` handler, and owns the composition-root wiring that first constructs the real secure-store chain in `src/main/index.ts`. See the [pairing IPC channel feature doc](../features/pairing-ipc-channel.md) for the full contract, layers, held-state model, and data flow.

## Patterns established

- **The request/response twin of a fire-and-forget channel keeps the same three-layer shape but inverts one invariant's weight.** #17 chose `send`/`on` precisely so there is **no reply channel** to leak data back through; #54 needs a reply (`ipcMain.handle`/`ipcRenderer.invoke`), so the "only the fingerprint or a value-free reason crosses back" invariant becomes **load-bearing at exactly this seam**. It is enforced **by construction**: no response arm *has* a field that could hold the `token` or `server_static_pubkey`, so a developer cannot serialize one back. When adding any main→renderer reply channel, model the response union so no arm can carry a secret — the type is the enforcement, not a convention. Same "model the invariant into the shape" discipline as [#53](53.md)'s confirm gate and [#52](52.md)'s discriminated-result gate.
- **`handle` must resolve; `on` may drop.** Unlike the command channel's silent `console.warn`-and-drop on a malformed command, a malformed invoke must **return** a typed error (`{ ok: false, reason: 'malformed-request' }`) — so the guard-reject path is a resolved value, not a dropped message. The one fixed value-free log (`'pyry:pairing — rejected malformed request'`) mirrors `receiveCommand`'s drop log; a well-behaved renderer never triggers it.
- **Two structural invariants replace disciplinary ones for the held state.** The handler holds at most one `pendingConfirm` closure between the submit and confirm round-trips. **Supersede-on-submit** (set `pendingConfirm = null` up-front on *every* submit, valid or not, before parsing) makes "a superseded/failed record is unpersistable" structural. **Consume-before-await** (`read → null → await confirm()`) makes "persists exactly once" structural — a second/concurrent confirm reads `null` → `no-pending-pairing`, so there is no double-save race across the single interleaving point (the `await`). Neither is a rule someone must remember; both are shapes of the code.
- **The boundary guard bounds *length*, not just type + shape.** `isPairingRequest` rejects a non-string paste **and** a paste over `MAX_PASTE_LENGTH` (8 KiB) — at the IPC trust boundary, before `parsePairingPayload` runs regex / base64-decode / `JSON.parse`. The length bound is the architect security-review's one SHOULD-FIX, addressed inline: a compromised/buggy renderer cannot force main to chew a multi-MB string (resource exhaustion). Validate size at the seam, not downstream.
- **Structural injected target over an imported `ipcMain`, again.** `PairingHandleTarget` (`{ handle, removeHandler }`) is the invoke/handle twin of `receiveCommand`'s `CommandSource` (`{ on, removeListener }`) — Electron's `ipcMain` is structurally assignable, so the handler unit-tests with a `vi.fn()` fake and imports no `electron`. Reuse for any main-side helper that touches an Electron object but shouldn't require an Electron harness.
- **The composition root maps error reasons coarsely to respect layering.** The handler collapses #52's eight parse reasons and #53's two key reasons into `invalid-paste` / `invalid-key`, because `shared` cannot import those main-only unions and the operator's recovery is per-category. Finer messaging (if #55 wants it) threads a *value-free* detail string alongside the category later — additive, no reshape.
- **The deferred-wiring precedent finally cashes out.** #21/#22/#42/#43/#44/#52/#53 each shipped with no live caller ("wiring is #54's job"). #54 is that composition root: it constructs `createSecureStore` (over the real `electronSecretEncryption` + `fileSecretPersistence(join(app.getPath('userData'), 'secrets'))`) → `createPairedServerStore` → `createPairingConfirmation` and registers the handler once. Single registration for the app lifetime (`ipcMain.handle` throws on a second registration on the same channel), inside `whenReady` (not `activate`), torn down on `will-quit`.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section, plus the code-review notes.*

- **Electron's `ipcMain` satisfies a minimal injected `{ handle, removeHandler }` interface structurally** — the same trick `receiveCommand` used with `CommandSource` over `ipcMain.on`. So the handler unit-tests with a `vi.fn()` fake and needs no Electron harness, confirmed by a clean typecheck of the composition root passing `ipcMain` directly. The structural-interface-over-`electron`-import pattern is now proven for both `on`/`removeListener` and `handle`/`removeHandler`.
- **`ipcRenderer.invoke` returns `Promise<any>`, so a preload wrapper can declare a narrower return type (`Promise<PairingSubmitResponse>`) with no `as` cast** — `any` is assignable to the narrower type, so the declared return is an honest typed wrapper, not an unchecked assertion. The narrower per-operation response types (`PairingSubmitResponse` vs `PairingConfirmResponse`) let #55 narrow cleanly.

No React re-render / effect-cleanup / dependency-version surprises to record — a main-process handler + shared contract + preload bridge with no React, no timers, no listeners beyond the single `will-quit` handler, no new dependency. `submit`/`parse`/`prepare` are synchronous; `confirm` is a single `await store.save`.

## Deferred (open questions carried forward)

- **Exhaustive `switch` over `if` on request dispatch (code-review NIT, non-blocking).** `pairingHandler.ts` dispatches with `if (request.type === 'submit') { … }` and falls through to the `confirm` path. Safe today (`isPairingRequest` rejects any unknown `type` before the listener runs), but if a *third* `PairingRequest` member is later added to the union **and** the guard's switch but **not** here, the fall-through would silently treat it as `confirm`. A `switch (request.type)` with a `never` default would surface that at compile time — matches the project's "exhaustive switch for closed unions" idiom (#19's `assertNever`, #17's flagged tripwire). Adopt when the request union grows.
- **Finer error granularity for #55's UX.** The coarse `invalid-paste` / `invalid-key` categories can later carry a *value-free* detail string if the pairing screen wants more specific operator messaging — additive, no reshape of the response union.
- **The renderer screen (#55).** The consumer that drives this channel — paste input, fingerprint display (decorating #53's fixed 23-char form), confirm button, and error-banner surfacing of the value-free `reason` — is the next slice. `will-quit` teardown is hygiene (single registration for the app lifetime), not a functional requirement.
