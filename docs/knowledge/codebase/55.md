# #55 — Pairing input screen

**Shipped:** 2026-07-04 · **Size:** S · **Scope:** renderer-only (`src/renderer/`) · consumes the existing #54 preload methods, no transport / preload / dependency changes · adds 3 M3 tokens to `tokens.css`.
**Spec:** `docs/specs/architecture/55-pairing-input-screen.md` · **PR:** [#60](https://github.com/pyrycode/pyrycode-desktop/pull/60) · review: **PASS** (architect security-review in-spec, verdict PASS; code-review over the diff — no MUST/SHOULD FIX). Split from #9.

The desktop's paste-only pairing screen: paste the payload printed by `pyry pair --print`, review the server-key **fingerprint** the background process derives, and explicitly **confirm** — or **cancel**, discarding the paste. It is the renderer consumer of the [pairing IPC channel](../features/pairing-ipc-channel.md) (#54), styled from the mobile "Paste pairing code" dialog (Figma node `19-54`) stretched to the window, plus the desktop-specific fingerprint-verify step ([#53](53.md)) mobile's paste path skipped. See the [pairing input screen feature doc](../features/pairing-input-screen.md) for the phase machine, view contract, and data flow, and [ADR 0006](../decisions/0006-ephemeral-screen-state-usereducer-not-store.md) for the `useReducer`-not-a-store decision.

**Out of scope (explicit):** where the screen mounts. App-level navigation/gating (show this when unpaired, the conversation screen when paired) is a separate slice — the screen exposes optional `onPaired` / `onCancel` seams that future slice will wire.

## Patterns established

- **A screen decomposes into pure layers + thin glue — three tested seams, one untested container.** The interaction is split into a React-free `pairingState.ts` (reducer + effect-runners + formatter, all unit-tested in the `node` env) and a thin `PairingScreen.tsx` container (`useReducer` + handlers, untested). This is the same "pure choke point is tested, thin React wiring is not" split as [session store](../features/session-store.md) (pure `reduceSession`) vs [daemon-event bridge](../features/daemon-event-bridge.md) (untested `useDaemonEventBridge`). AC5's "component tests" are satisfied **without a DOM harness** by testing the pure layers directly — no jsdom, no new dependency, matching `ConversationScreen.test.tsx`'s `renderToStaticMarkup` idiom.
- **Ephemeral screen-local state uses `useReducer`, not a module-singleton Zustand store.** The paste/phase/fingerprint/error belong to one in-progress attempt and must reset on remount; a module-singleton store (the [session store](../features/session-store.md) shape from [ADR 0004](../decisions/0004-renderer-session-store-reducer-wire-types.md)) would leak a stale fingerprint/error into a re-opened screen. `useReducer` over the pure `pairingReducer` keeps state at the lowest scope that resets correctly while preserving the unidirectional, dispatch-only, sealed-event discipline. Codified as [ADR 0006](../decisions/0006-ephemeral-screen-state-usereducer-not-store.md).
- **Async is handler-driven, so there is no `useEffect` — and no StrictMode double-invoke concern.** The two one-shot IPC calls fire from user-interaction handlers (`onSubmit`/`onConfirm`), React's idiomatic home for interaction side effects. This is the deliberate divergence from `daemonEventBridge`, which *legitimately* uses an effect because it subscribes for the component's display lifetime. No effect ⇒ no dev-mode double-fire to guard.
- **In-flight re-entrancy is blocked at the view, not with a ref/flag.** Pair/Confirm are `disabled` while `submitting`/`confirming` (and Pair is also disabled on an empty/whitespace paste). The disabled button *is* the guard — no in-flight `useRef`, no `AbortController`. `onSubmit` captures `state.paste` into a local before its `await` (no check-then-act race), and a `dispatch` after unmount is a harmless React-18 no-op, so no cleanup flag is needed.
- **`confirm-failed` routes to `editing`, never back to `reviewing`.** The main handler consumes its pending record *before* awaiting the persist (#54, consume-before-await), so after any confirm failure the pending record is already gone and a retry must be a **fresh submit**. Returning to `editing` with the paste preserved makes that a single Pair click; routing to `reviewing` would offer a Confirm button structurally guaranteed to fail with `no-pending-pairing`. The reducer's shape encodes the upstream held-state contract.
- **Fingerprint decoration is spatial only.** `groupFingerprint` returns the 8 verbatim colon-separated byte-pairs (`groups.join(':')` must equal the input); the view renders them as spaced monospace `<span>`s. The characters, case, and order are never altered — the operator compares this string byte-for-byte against what `pyry pair` printed and what the phone shows, so it is the trust anchor and must stay byte-faithful.
- **The paste is treated as sensitive even though no secret flows back.** It embeds the token, so it lives only in transient reducer state and the single `submitPairingPaste(paste)` call — never logged, never persisted, never sent on another channel, cleared on `cancel` and on reaching `paired`. The inline error renders only the value-free `reason` (a fixed `Record` lookup, no interpolation). Nothing inbound could carry a secret: the #54 response arms have no `token`/`server_static_pubkey` field, so AC4 ("no secret reaches the renderer") holds by construction upstream.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **No error-color token exists in `tokens.css`.** The inline validation message reuses `--color-tertiary` (`#ffb59f`) — the M3 dark error-adjacent warm color and the palette's only attention color. The Figma node draws no error state, so there is no visual reference to diverge from; reusing the existing token rather than adding one the spec didn't call for (evidence-based: no observed need for a dedicated `--color-error`). If a true error color is later required, add the token then.
- **Fidelity was validated against `get_design_context` values, not a running app.** Because mounting is out of scope, the screen is not yet in the render tree, so it can't be screenshotted in situ. Fidelity was checked by mapping each Figma value 1:1 to a theme token; the live visual comparison follows when the mounting slice lands.

No React re-render / effect-cleanup / dependency-version surprises to record: no `useEffect`, no timers, no subscriptions, no new dependency. The only React state is one `useReducer`; the two IPC calls are one-shot awaited promises off click handlers.

## Deferred (carried forward)

- **Mounting / navigation gating.** Showing this screen when unpaired vs. the conversation screen when paired is the next slice; it wires the `onPaired` / `onCancel` seams and decides whether the `paired` state lingers or the screen unmounts. The `paired` phase is a placeholder success marker until then.
- **Off-scale paste-field radius.** The design's 4px maps to `--radius-xs` (6px) — a 2px, imperceptible cost that keeps the value tokenized. Add a `--radius-2xs: 4px` token only if exact fidelity is later required (not worth a single-use token now).
- **Finer inline error copy.** The `PairingErrorReason` → message map is a starting point; the five keys are fixed but the wording can be tuned (and #54 can thread a *value-free* detail string alongside the category if more specific messaging is wanted — additive, no reshape).
