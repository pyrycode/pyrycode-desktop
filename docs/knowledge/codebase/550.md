# #550 — fakeDaemon.test.ts frame-decode-failed leg boundary: bound every await, re-dial the stalled one

**Shipped:** 2026-08-02 · **Size:** XS · **Labels:** `bug`, `security-sensitive` (the test under
repair *is* the fail-closed assertion for a non-trusted inbound frame at the relay leg boundary, plus
the module's log-freeness contract — both re-audited, not just the flake).
**Scope:** one file, `src/main/transport/fakeDaemon.test.ts`. No production change —
`fakeDaemon.ts`, `fakeRelayForwarder.ts`, `fakeRoutingRelay.test.ts`, `fakeRelayForwarder.test.ts` and
`relayConnection*` all absent from the diff.
**Spec:** `docs/specs/architecture/550-fakedaemon-framedecode-bounded-awaits.md` · **PR:**
[#551](https://github.com/pyrycode/pyrycode-desktop/pull/551).

Fixes a flaky test in [Fake daemon](../features/fake-daemon.md) (#91):
`fail-closes a non-InnerFrameV2 frame at the leg boundary to frame-decode-failed (security)`
intermittently hit `Error: Test timed out in 5000ms.` — only under full-suite (`npm test`)
contention, never in 6/6 isolated single-file runs across the PR and baseline branches. Unmasked
while QA-ing PR #549 (#513), a renderer-only diff with zero overlap with the transport layer. Fifth
member of this repo's flaky-transport-fake family
([#303](303.md)/[#311](311.md)/[#336](336.md)/[#342](342.md)) and the **second of hang shape**
(a hung `await`) rather than rejection shape (an emitted, classified dial error).

## What shipped

`connect()`'s test-file-local dial helper (`:60-78` pre-fix) was the **exact pre-#342 shape**: it
re-dials only on an emitted `'error'` matched by `isTransientDialError`, with no per-attempt timer,
so a silently-stalled dial (TCP connect lands, HTTP upgrade never processed by a CPU-starved
worker) hangs forever. Two additions, one file:

- **A `bounded(step, work, deadline)` helper** — a strict pass-through race: `work`'s own settle
  (value or error) always wins over a generic `#550 bound: <step> did not settle within the
  ${AWAIT_BUDGET_MS}ms test budget` rejection, `clearTimeout`s on both arms, emits no `console.*`.
  Wraps the test's three other reachable awaits (`startFakeRelayForwarder()`, `startFakeDaemon()`,
  `daemon.whenSettled()`) against **one shared wall-clock deadline**
  (`const deadline = Date.now() + AWAIT_BUDGET_MS`, `AWAIT_BUDGET_MS = 4000`) armed once at the top
  of the test — not per-step budgets, which would need summing to prove no combination of steps can
  exceed vitest's 5000ms.
- **`connect(url, deadline, attemptsLeft = 5)`** gained a per-attempt `dialTimer`
  (`DIAL_STALL_MS = 1500`, capped by the remaining deadline) that fires only while the socket is
  still `CONNECTING` (both the `'open'` and `onDialError` paths `clearTimeout` it first). On fire it
  detaches `onDialError`, `terminate()`s the half-open socket, and re-dials with the same `deadline`
  if attempts and budget remain — otherwise rejects naming the url and the exhausted limit. The
  existing emitted-`'error'` retry path is unchanged except it now also deadline-checks before its
  20ms backoff re-dial.
- **Teardown reshaping**: `cleanups.push(...)` for the forwarder and daemon now registers against the
  **start promise**, not the resolved value (`const forwarderStart = startFakeRelayForwarder(); …
  await bounded(...)`) — a non-blocking (`void`), rejection-handled disposer
  (`.then((f) => f.close(), () => {})`). If a `bounded()` timeout fires while the real start is still
  pending, the disposer still fires once the start eventually resolves, so a late-resolving
  forwarder/daemon can't leak a listening `WebSocketServer` into the rest of the run.

## Root-cause confirmation

The flake never reproduces in isolation, so the mechanism was established by elimination over the
test's four awaits, keyed on the one hard fact the symptom hands you: a 5000ms vitest timeout is
*definitionally* a hung `await`, categorically distinct from a rejection
([#342](342.md)'s established fork). `forwarder.whenReady()` was ruled out doubly: it is bounded at
1000ms and **rejects** with a distinct message, and — stronger — by the time it's reached both legs
are already registered, so `settleReady()` has already fired server-side
(`fakeRelayForwarder.ts:185`, *before* the dialling client even sees `'open'`) and the call never
arms its timer at all. `daemon.whenSettled()` was ruled unlikely but not impossible (kept in scope
for AC1, not remedied).

`connect()` was confirmed the site by a **call-site count**, not just the elimination table: it has
exactly one non-recursive call site in the whole file, and it's inside the flaking test. The other 11
tests dial through `driveClient` → `createRelayConnection`, whose subsequent waits all go through
`makeWaiter().wait()` — bounded and **resolving** (never rejecting) at 2000ms — so a stall there
degrades into a failed `expect`, never a vitest hang. Only this one test can produce the observed
symptom at all. Reinforcing evidence: this exact dial site was already a proven racer — [#336](336.md)
fixed a `404`-upgrade race here ("Site A"); this ticket's stall is the same site's *silent* failure
mode (no `'open'`, no `'error'` at all) rather than an emitted one.

## Rework — the remedy path itself was broken (MUST FIX)

Code review caught, by reading rather than running, that the shipped stall path detached
`onDialError` *before* `ws.terminate()`. The stall timer can only fire while the socket is still
`CONNECTING`; `terminate()` on a `CONNECTING` socket in the pinned `ws@8.21.0` takes the
`abortHandshake` branch, which ends in `process.nextTick(emitErrorAndClose) → emit('error')`. With
zero listeners at that instant, Node throws `Unhandled 'error' event` — out of band, deterministic on
*every* stall-path fire, converting the fix's own 5000ms nil-diagnosis timeout into an uncaught
exception with an even worse diagnosis. Fixed in `2a04568` by **swapping** the listener rather than
dropping it (`ws.off('error', onDialError); ws.on('error', () => {})`, mirroring the `'open'` path's
existing swallow), verified against a `net.createServer(() => {})` repro (accepts the TCP connection,
never answers the HTTP upgrade): pre-fix throws on the first stall; fixed, the ladder walks 3
attempts and rejects cleanly.

## Patterns established

- **A spec's "this can't be tested" rationale can be falsified by the fix's own rework commit.** The
  spec declined a stall-path regression test on the grounds that synthesising event-loop starvation
  "cannot be injected reliably." The rework commit that fixed the MUST FIX built exactly that
  injection (`net.createServer(() => {})`) to verify its own fix. Check a rework commit's message
  before accepting an "untestable" claim made earlier in the same ticket.
- **One shared wall-clock deadline, not per-step budgets, is what makes the AC1 proof a single line.**
  Per-step budgets would each need to be near the vitest limit individually and could still sum past
  it in combination; one deadline threaded through every bound and through both of `connect()`'s
  retry gates means no bounded await in the test can reject later than `start + AWAIT_BUDGET_MS`,
  full stop.
- **#342's dial timer had an un-closed hole — don't clone it verbatim into a new file.**
  `5 × DIAL_STALL_MS = 1500 = 7500ms` could in principle out-run the very 5000ms timeout it exists to
  prevent. This ticket's shared-deadline design closes that hole (worst case
  `1500 + 1500 + remainder ≈ 4000ms`) rather than propagating the unbounded-attempt-count arithmetic.
  `fakeRoutingRelay.test.ts` itself is untouched (scope guard) and still carries the un-closed
  version.
- **Wrapping a `start` promise in a bound moves `cleanups.push()` past a rejection point — register
  the disposer against the start promise, not the resolved value.** The pre-existing pattern
  (`cleanups.push(() => forwarder.close())` *after* `await`) silently assumed the await always
  resolves. Once an await can now reject (the new `bounded()` wrapper), a disposer registered after it
  never runs if a slow-but-eventually-successful start resolves *after* the bound already rejected —
  leaking a listening `WebSocketServer` into the rest of the run and turning a clean diagnostic
  rejection into a worker-level hang. The disposer must be `void`-chained (non-blocking, so a
  never-settling start can't stall `afterEach`) and rejection-handled (so a late-rejecting start can't
  surface as an `unhandledRejection`).
- **Declining to touch a shared, evidence-free site is itself a documented design decision, not an
  omission.** `fakeDaemon.ts:480-495` (the production-adjacent server-leg dial) is the fourth
  candidate in the elimination table and *could* have absorbed a timeout too — but it's shared by all
  12 tests and only one ever flaked, so the spec explicitly declined it (AC4 permits it; this ticket
  doesn't take the offer) and bought the same diagnosis at zero blast radius with a call-site
  `bounded()` wrap instead. If a future run ever rejects naming `startFakeDaemon /v1/server dial`,
  that rejection *is* the evidence that would earn a change there.

## Testing

- `npm test` full suite, 10/10 back-to-back clean: 133/133 files, 2209 passed, 0 failures, zero
  `Test timed out in 5000ms` attributed to `fakeDaemon.test.ts` (recorded by QA on the re-review after
  rework — the first review round's run count was never recorded in the PR body, called out as a
  SHOULD FIX and closed on the second pass).
- `npm run build` (typecheck + electron-vite): clean.
- Teeth check: `:966`'s `toEqual({ ok: false, reason: 'frame-decode-failed' })` and the six-spy
  `not.toHaveBeenCalled()` loop are byte-identical; every other `it` block's `expect(...)` is
  untouched, guaranteed structurally by `connect()`'s single call site and `bounded()`'s three call
  sites all being inside the one test under repair.
- Security re-review (architect self-review + code review, both PASS): no trust boundary, secret, or
  logging change; the retried resource is a raw pre-handshake `ws`, never a Noise initiator, so no
  `(key, nonce)`-reuse hazard; the retry is bounded twice over (`attemptsLeft` *and* the wall-clock
  deadline); no `console.*` added on any path.

## Open item (SHOULD FIX, not blocking)

Code review's second pass flagged that the remedy branch itself — the stall re-dial ladder that is
the entire point of this ticket — still has no regression test, and that this is exactly how the
MUST FIX above got through developer + QA and had to be caught by reading. The `net.createServer(()
=> {})` repro the rework commit used to verify its own fix is a legitimate, fast (~200ms) injection
for a ~15-line pinning test; left as a follow-up rather than expanding this ticket's XS envelope.
Also flagged for triage, not this ticket: `fakeRoutingRelay.test.ts:68-69` carries the identical
drop-the-listener shape from #342 and therefore the same latent `Unhandled 'error' event` on its
stall path — now confirmed by reproduction rather than suspected by analogy, and per this ticket's
scope guard it stays untouched here.
