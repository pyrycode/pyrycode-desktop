# #558 — Run config: show an in-flight settings change as pending, not as settled

Split from #556. Spec `7f2bf52` (size S held, security review PASS, self-review). Shipped `627ae4a`,
PR#562, code-review **PASS** (0 MUST/SHOULD, 3 NIT, zero deviations). Not a new production consumer
count of zero — this ticket is `selectPendingFields`'s **first** production consumer since it was
exported and unit-tested by [#256](256.md). Figma `20-100` subtree; the design draws no pending variant
for any of the three controls, so the treatment is an annotation layer over the drawn M3 states, not a
redraw.

## Summary

`runSettingsWriteStore`'s optimistic overlay ([#256](256.md), wired to the sheet by [#257](257.md))
rendered a value the daemon had not yet confirmed identically to a settled one — the radio filled, the
segment lit, the switch flipped, with nothing distinguishing an in-flight change from one already
accepted. The gap is a relay round trip during which the change can still be refused
(`sessionSettingsRejected`, [#269](269.md)) or abandoned by a reconnect
([#539](539.md)/`reconnected`). This mattered most on the YOLO switch: a settled-looking switch during
that window is a wrong belief about the permissions posture, held while claude may be running commands.

One production file changed — `src/renderer/src/screens/conversation/RunConfigSections.tsx`:

- `RunConfigView` gained one optional prop, `pending?: ReturnType<typeof selectPendingFields>` — typed
  as the selector's own return type rather than a restated literal, so a parallel pending shape is a
  compile error, not a review catch. Each of `ModelSection`/`EffortSection`/`YoloSection` gained a
  matching optional `busy?: boolean`.
- Each section renders `aria-busy={busy ? 'true' : undefined}` — omitted, never `"false"` — on **the
  element that owns that field's controls**: `.run-config__model-list` and `.run-config__effort` (the
  group, since each field has multiple controls) and `.run-config__switch` itself (the field has exactly
  one control, and it *is* the switch; `.run-config__yolo` also wraps the title/caption text and is not
  used). This is the file's existing `aria-current` idiom — one attribute as both the a11y marker and
  the CSS hook.
- The container derives `pending = selectPendingFields(writeState)` beside the pre-existing
  `effective = selectEffectiveSettings(snapshot, writeState)`, from the **same `writeState` reference in
  the same render pass** — no second `useRunSettingsWriteStore` subscription. That single-reference
  derivation is what makes the displayed value and its marker structurally incapable of disagreeing.

`conversation.css` gained two rules, both gated entirely on `[aria-busy='true']` so nothing-in-flight is
byte-identical to today: a dashed `--color-warning` `outline` on the two group wrappers, and a
`border-color`/`border-style: dashed` recolour on the switch (using `border`, not `outline`, because the
existing `:focus-visible` ring owns the switch's outline). `--color-warning` is the project's existing
in-progress amber ([#330](330.md)); no new theme token.

## Testing

`npm test`, `npm run typecheck` — no DOM harness, `RunConfigView` stays `renderToStaticMarkup`-able with
no bridge mock (the whole test file's founding property, unchanged). New
`describe('RunConfigView — pending marker (#558)')` in `RunConfigSections.test.tsx`:

- One field marked (model / effort / yolo, one `it` each) — exactly one `aria-busy="true"` in the
  markup, on the owning wrapper and not on a child (e.g. not on an individual effort segment).
- Two fields at once (`{model: true, effort: false, yolo: true}`) — exactly two occurrences, the
  untouched field has none. This is AC3's simultaneous case, and the reason `pending` could not be
  `errorField`-shaped (`field | null` can't express two outstanding changes).
- Nothing in flight, prop given as all-`false` vs. omitted entirely — both produce markup with no
  `aria-busy` at all, and the two strings are asserted **identical** to each other (AC5).
- Stays operable while marked — with `onChange` present and all three pending, `role="button"` and
  `tabindex="0"` still render and the markup contains neither `disabled` nor `aria-disabled` — the
  negative test against cloning `LogDataSection`'s `aria-busy` + `disabled` pairing.
- Existing markers untouched (AC2) — `aria-label="Current model"`, `aria-label="Auto-accept tool
  calls"`, `aria-current="true"`, `aria-checked` all still assert their pre-existing values with
  everything pending.
- Rejection alert not suppressed — with `pending` and `errorField` set for the same field, a
  `closedBefore()` helper (balances `<div>`/`</div>` between the wrapper's open tag and `role="alert"`)
  proves the alert falls **outside** the marked wrapper, i.e. is a sibling and not a descendant. Guarded
  by a non-vacuity assertion (the wrapper string itself contains `aria-busy="true"`) before measuring.
- Read-only path still marks (AC5) — `pending` set with `onChange` absent still renders
  `aria-readonly="true"` and no `role="button"`; the marker is independent of operability.
- Clears through the existing deletion (AC4) — composed against the real store
  (`createRunSettingsWriteStore` + `selectPendingFields`), one `it` loops `settingsConfirmed` /
  `settingsRejected` / `reconnected` (same `changeId`): each dispatch clears the marker, proving there is
  no second representation of pending state to keep in sync.

The pre-existing container SSR test gained one line: `expect(markup).not.toContain('aria-busy')` on the
opening frame.

**No e2e changes.** `aria-busy` contributes to no accessible name and alters no attribute the e2e specs
assert on; both `run-config-settings.spec.ts` and `real-daemon-session-settings.spec.ts` passed
unmodified.

## Patterns established

- **A selector's return type as a prop type, not a restated literal**, specifically to make "don't
  introduce a parallel representation" a compiler-enforced constraint rather than a review-time
  judgment call. Worth reaching for again anywhere a component prop mirrors a store selector's shape
  one-for-one.
- **Same-reference-same-render-pass as the anti-tear invariant.** Two derived views of one store's state
  (here: the effective value and its pending marker) must read the identical subscribed reference in the
  same render, not two independent selector subscriptions — the latter can interleave and show one
  without the other. This is now the second time this file relies on that (the container's raw
  `useRunSettingsWriteStore((s) => s)` selection was already load-bearing for `selectEffectiveSettings`
  in [#257](257.md); this ticket adds a second consumer of the same raw reference).
- **Take half a precedent, name which half.** `LogDataSection.tsx` pairs `aria-busy` with `disabled`;
  this ticket takes only `aria-busy` because disabling would contradict the store's deliberate
  last-write-wins for rapid same-field changes ([#256](256.md)). The negative test (marked-but-not-disabled)
  is what keeps a future clone from silently re-adding the paired half.

## Lessons learned

- **`aria-busy` on a container suppresses `role="alert"` inside it.** This is the one real trap in an
  otherwise mechanical change: placing the attribute on an element that *encloses* the rejection line
  would have told assistive technology to withhold the alert precisely on the field the operator was
  told was in flight — inverting the ticket's purpose. It survives here only because
  `RunConfigError`'s `<p>` is emitted as a **sibling** of each wrapper (`RunConfigSections.tsx:165/203/242`),
  never a descendant — nothing in the type system or lint config guards that placement; only the
  dedicated negative test does.
- **A `Map`-keyed store field and a single-value store field need different prop shapes**, even when an
  existing prop (`errorField: field | null`) looks like a ready-made template. `pending` is keyed by
  `changeId` "so two outstanding changes are told apart"; cloning `errorField`'s shape would have
  silently collapsed AC3's simultaneous-fields case into an either/or.
- Grepping for a docstring's own claim (`selectPendingFields`'s "so #257 can show a pending state") is
  what surfaced this slice in the first place: the selector had been exported and tested since
  [#256](256.md) with zero production reads, a bigger gap than the ticket text alone implied.
