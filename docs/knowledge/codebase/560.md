# #560 — Renderer: show the running model, resolved by exact match or rendered verbatim

Closes the transport → store → surface vertical opened by [#587](587.md) (wire decode) and
[#588](588.md) (`announcedModelStore`), both of which shipped dormant. Shipped on branch
`feature/560` (`2cc8a3f`, spec `d7f7d5b`), PR #594. Size S, security-sensitive (architect
self-review PASS), code review **PASS, three NITs, no MUST FIX / SHOULD FIX**.

## Summary

The run-configuration sheet gains a **read-only** sixth section, `RunningModelSection`, rendered
immediately **before** `ModelSection` — reading order is "what is running, then what you can
switch to." It answers a question the existing Model rows cannot: those rows mark the daemon's
*persisted override*, which reads `''`/unmarked on a daemon where nothing was ever overridden —
honest, but indistinguishable from broken. `RunningModelSection` instead renders what claude
actually announced for the running turn (`announcedModelStore`, #588).

- **`runningCatalogEntry(model)`** (`RunConfigSections.tsx`) — `MODEL_CATALOG.find((e) => e.family
  === model)`, `===` only. Deliberately **not** `matchedFamily`, the pre-existing case-insensitive
  *substring* matcher the Model rows use for the override: reusing it here would let `opus`
  inference-match `claude-opus-4-7`, which is exactly the guess this ticket exists to forbid. The
  lookup is dormant by design — the catalog holds family words, claude announces full identifiers
  — and a long code comment says so explicitly, so a later reader doesn't "repair" it into
  `matchedFamily`.
- **Render contract**, three states: `announced` absent/`null` → `.run-config__running-unknown`
  ("Running model not yet known"); hit → `.run-config__running-value` holding the catalog's
  `entry.name`; miss → the same element holding `announced.model` **verbatim**, character for
  character, including a reachable `{ model: '' }` (present-but-empty, never collapsed into the
  unknown state — that would erase the store's deliberate `null`-vs-`''` distinction one layer
  above). A cut marker, `.run-config__running-cut` ("Truncated by the daemon"), renders as an
  **independent sibling element** whenever `announced.truncated` is true — branching on the flag
  alone, never on which path the value took, so a daemon cannot suppress its own cut report by
  sending a value that happens to equal a catalog token.
- **Forgery resistance (AC3).** The cut marker is a client-owned module constant in a sibling
  element, never text concatenated into the value node — the third instance of the
  `BackgroundTaskPanel.tsx:236-255` / `ConversationScreen.tsx:487-500` idiom in this codebase.
  Concatenation would let an identifier ending in the marker's own words impersonate the sheet's
  claim (or vice versa).
- **Placement is a test-harness-informed decision**, not just a design choice: `segmentFor`
  (the test file's chunk-extraction helper) delimits a chunk by the *next* occurrence of a class
  token, so the last model row's chunk runs to end-of-document. A surface placed *after* the rows
  would land inside that open-ended chunk and corrupt existing negative assertions over it. Before
  the rows, the new surface sits in `segmentFor`'s chunk 0, which nothing existing targets.
- **The prop is optional** (`announced?: AnnouncedModel | null` on `RunConfigView`), and absence ≡
  `null` ≡ not-yet-known. That is what keeps all ~51 pre-existing `RunConfigView` render sites in
  `RunConfigSections.test.tsx` compiling and passing unmodified, and it is why the not-yet-known
  copy renders in every one of them — the new copy was checked against every counted/negated
  assertion in the file (six `Current model`-count sites, `aria-current`, `role="button"`,
  `aria-busy`, `role="alert"`, `% used`/`NaN`/`undefined`/`Infinity`) and collides with none.
- **Container** (`RunConfigSections`) adds a fourth narrow-slice store read,
  `useAnnouncedModelStore(selectAnnouncedModel)`, passed straight through with no derivation and no
  setter — the same unidirectional shape as the three sibling reads it sits beside.

13 new test cases in one `describe` block (RED first — both suites failed on the missing
prop/section before implementation); `npm test -- RunConfigSections.test.tsx` 54/54;
`ConversationScreen` + `announcedModelStore` + `runSettingsWriteStore` + `runSettingsControls`
195/195 unmodified; `npm run build` clean. 3 files touched (1 production `.tsx`, 1 `.css`, 1 test),
334 insertions — no new files, no new exported types (the section component and both copy
constants are module-local).

## Patterns established

- **A third instance of the sibling-element cut/forgery marker is still not worth extracting into
  a shared component.** Three independent call sites (`BackgroundTaskPanel`, `ConversationScreen`,
  now `RunConfigSections`) each hold their own client-owned copy constant and their own conditional
  sibling `<p>`, rather than a shared `<CutMarker copy={...} />`. The shape is two lines of JSX; a
  shared component would trade that for an import and a prop, without removing the one thing that
  actually needs care at each site (keeping the marker structurally outside the daemon-text node).
- **Placement relative to a test harness's chunk-extraction helper is a first-class design
  input, not an afterthought.** `segmentFor`'s "runs to end-of-document for the last match" behavior
  made "before the rows" the only placement that doesn't require touching six existing negative
  assertions. When a new section can go either side of an existing render, check what the test
  harness's extraction helpers do at the boundary before picking.
- **An optional prop defaulting to the "unknown" render state is what keeps a large existing call-site
  fleet (51 sites here) at zero fan-out.** The alternative — a required prop — would have forced
  either a mechanical edit of every test site or a wrapper indirection; optionality with a
  well-chosen default absorbs the whole fleet for free. Reusable whenever a new read-only surface is
  added to a component with a large pre-existing test-call-site count.

## Lessons learned

(Lifted from the PR body's own "Lessons learned" section.)

- **A backslash-u escape sequence for a control character (e.g. the four-character spelling of
  ESC) written through a tool call's JSON input arrives as a raw byte, not the escape sequence.**
  Tool input is JSON, so the escape is decoded before it reaches disk and a real
  ESC byte lands in the `.ts` source — invisible in a diff, the test still passes green, but the
  line becomes un-`Edit`-able afterward (the tool can no longer match it) and the same byte blocks
  `gh pr create` if it reaches a PR body. Check with `LC_ALL=C grep -c '[[:cntrl:]]' <file>`; repair
  with `perl -i -pe 's/\x1b/\\u001b/g'`. This is the same failure mode #588 hit from *typing* a
  control character directly — this ticket's version is typing the escape-sequence spelling through
  a tool call instead, and getting decoded a second time.
- **`closedBefore` (the test file's existing sibling-vs-descendant helper) cannot prove sibling-vs-
  descendant between two adjacent `<p>` elements.** It counts `<div>` balance, which is vacuously
  true when neither element is a `div` — so it would pass whether the marker were a true sibling or
  accidentally nested. The actual proof used instead: assert the two serialized elements as **one
  concatenated string run** (`<p class="...-value">x</p><p class="...-cut">...</p>`), relying on the
  fact that `renderToStaticMarkup` emits no separator between adjacent element children. This is the
  test technique that actually pins AC3's forgery-resistance property; `closedBefore` alone would
  not have caught a regression that nested the marker inside the value element.

## Code review

PASS, three NITs, no MUST FIX / SHOULD FIX. All three NITs are comment-accuracy only:
`RunConfigView`'s JSDoc still says "renders all four sections" (now five); `ModelCatalogEntry
.family`'s docstring describes only the substring-match consumer (`matchedFamily`) and doesn't yet
name the equality-match consumer (`runningCatalogEntry`) added by this ticket; and `App.tsx`'s
"Ships dormant" comment for `AnnouncedModelData` is now stale (left untouched per the don't-touch-
adjacent-code rule). The reviewer independently re-verified the wire contract against the daemon
Go source (`ModelAnnounced`, one per turn, `maxModelField` 256 at construction, no
normalisation, empty suppressed), confirmed the vertical is live end-to-end (`announcedModelBridge
.ts:86` writes the store, `<AnnouncedModelData />` is mounted at `App.tsx:135`), and confirmed the
attribute-shaped anti-XSS test guards (`href="`, `src="`, `/\son[a-z]+="/`) were used instead of the
vacuous `not.toContain('onerror=')`-style substring guards the architect's security review had
flagged as a SHOULD FIX risk.
