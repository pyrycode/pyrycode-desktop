# #565 — Decode the daemon `background_task_updated` frame into a typed `backgroundTaskUpdated` event

Transport slice of the background-task-panel vertical, split from #554. Second of three sibling frame
slices (#564 `background_task_started` → #565 `background_task_updated` → #566
`background_task_roster`); the store that joins all three by `task_id` is #567, the panel that renders
it is #568. Shipped on branch `feature/565` (`28204e7`), a strict subset clone of #564 (`dbb163e`).
Security-sensitive (security review PASS, self-reviewed by the architect per
`architect/security-review.md`); size S, at the ~600-LOC guideline rather than clear of it (see the
spec's § Scope note — the `DaemonEvent`-arm / bridges-atomic shape is structurally unsplittable). **No
render** — the event ships dormant, consumed by none of the three exhaustive renderer bridges.

## Summary

`background_task_started` (#564) opens a background task; `background_task_updated` reports what
happened to it afterwards. The two join on `task_id` — together they are what lets a client separate a
turn that ended with work still running from a genuine finish (pyrycode#1240). Before this ticket the
frame was unmodeled and fell through `parseInboundMessage`'s `default → inbound-unmodeled → null`.

**Four wire fields, not six.** `BackgroundTaskUpdatedPayload { conversation_id, task_id, patch,
truncated_fields: string[] | null }` — the sibling's `tool_call_id` / `description` / `task_type` are
absent, and this frame gains `patch`: claude's patch object, carried whole and unparsed as an opaque
string (one key observed so far, `is_backgrounded`). Seven touch-points, mirroring #564 exactly:

- **Wire type** (`src/shared/wire/types.ts`) — `'background_task_updated'` joins `EnvelopeType`, directly
  after `'background_task_started'` (the slot #564 had already forward-commented for this ticket).
  `BackgroundTaskUpdatedPayload` field order mirrors `interactive.go:215`.
- **Inbound decode** (`inboundMessage.ts`) — `parseBackgroundTaskUpdatedPayload` scales
  `parseBackgroundTaskStartedPayload` down to three `requireString` calls plus one
  `requireStringArrayOrNull` call. **No new field narrower** — #564's `requireStringArrayOrNull` already
  encodes this frame's exact `truncated_fields` contract, and its docstring names this ticket verbatim.
  `case 'background_task_updated'` narrows before logging (a malformed frame leaves no diagnostic
  record), then emits the existing content-free `inbound-decoded` shape — no decoded field added, least
  of all `patch`.
- **Consumer emit** (`daemonConnection.ts`) — one `case 'background-task-updated'`, a fresh named-field
  literal copied by name, never a spread of `inbound.backgroundTaskUpdated`. **`conversation_id` is KEPT
  as `conversationId`**, the same in-family precedent #564 established (daemon state keyed by id, the
  `queue_state` #720 rule) — settled, not re-argued. Deliberately performs **no join** against
  `background_task_started`: ordering is claude's, not the daemon's, so an `updated` for a task this
  client never saw opened is a legal frame that emits rather than buffers. Not compile-forced (no
  `assertNever` default on this inner switch) — the round-trip test is the guard.
- **`DaemonEvent` arm** (`src/shared/ipc/events.ts`) — `{ type: 'backgroundTaskUpdated'; conversationId;
  taskId; patch; truncatedFields: readonly string[] | null }`, placed after `backgroundTaskStarted`. The
  doc-comment carries the render-as-plain-text-never-HTML constraint for `patch` forward to #568/#567,
  since this slice has no DOM sink of its own, plus the "opaque, may not parse, never enumerate keys"
  rule and the "`truncatedFields` reports the cap cut only, may diverge from `patch`'s bytes" rule.
- **Three exhaustive bridge no-ops** — `daemonEventBridge.ts`, `modalBridge.ts`, `timelineBridge.ts` each
  add `case 'backgroundTaskUpdated': return null`, directly beside the `backgroundTaskStarted` arm in
  each file. In `timelineBridge.ts` the arm joins the no-op fall-through cluster (**not** the owned
  `apiRetry`/`compacting` arms) — daemon state, not a turn-stream item, and here the wire says so
  outright: no `turn_id`, opens and closes no turn.

`npm test` green across the touched test files (RED first, test-first per CLAUDE.md). 13 files touched
(7 production, 6 test), 0 new files — the same commit-time ≥5-production-file self-check #564 already
established as structurally unsatisfiable: a new `DaemonEvent` arm compile-forces a case in all three
exhaustive bridges, and the transport decode exists only to feed that arm.

## Patterns established

- **A subset clone deletes fields, it doesn't just add them — and the type system is the pin, not
  review.** The single most likely defect this ticket named up front (spec § Three traps) was a leftover
  `description` / `taskType` copied from `dbb163e`, since four of the seven touch-points would still
  compile fine with an extra field. `types.test.ts` pins the negative shape directly
  (`expect(payload).not.toHaveProperty('tool_call_id' | 'description' | 'task_type')`), and
  `daemonConnection.test.ts`'s whole-object `toEqual` assertion (not a field-reaching cast — see #564's
  own NIT about that pattern) fails on any extra emitted property. Worth reaching for whenever a "peer"
  or "subset twin" frame is cloned from a richer sibling.
- **An opaque, possibly-invalid-JSON string field needs no new decode helper — `requireString`'s bare
  `typeof` check already carries it.** `patch` is validated identically to any other required string;
  the daemon's own canonical fixture (`patch` cut mid-token) is the free proof that no parse is ever
  attempted on this path. The "do not type this as structured JSON" constraint lives entirely in
  doc-comments (three independent reasons, repeated at both `BackgroundTaskUpdatedPayload` and the
  `DaemonEvent` arm) rather than in code, because there is no code shape that would express it — the
  temptation is at the *next* consumer (#567/#568), not here.
- **A required field's valid-empty-string case and its fail-closed-on-omission case are two separate
  tests, because both are invisible in the code.** `patch: ''` passes free (type-not-truthiness, the
  `requireBoolean`/`false` precedent) and an omitted `patch` key throws — same helper, same one-line
  check, opposite outcomes depending on whether the key exists at all. Neither behavior has a dedicated
  branch to point a reviewer at, so both need their own pinned test rather than relying on code review
  to notice the omission.

## Lessons learned

- Cloning a one-commit-old sibling end to end (read `git show <sibling-commit>` first, then write the
  subset twin) kept the touch-point count, the doc-comment shape, and the fail-closed posture identical
  with no new decisions to make beyond "which three fields don't exist here" and "what does the new
  field need." The spec's own measured-LOC accounting (~620 lines, marginally over the ~600 guideline)
  held at face value rather than triggering a re-split, because the compile-atomicity argument (`events.ts`
  arm → three `assertNever`-guarded bridges) had already been proven unsplittable by the identical, larger
  #564 shape shipping clean at 684 lines.
- The `truncated_fields` element vocabulary is **per-frame**, not a stable global set: this frame's pair
  (`task_id`, `patch`) differs completely from the sibling's four (`task_id`, `tool_call_id`,
  `description`, `task_type`). That's not incidental — it's the concrete evidence for why the codebase
  never narrows `truncated_fields`'s elements into a closed union at the type level: a real second data
  point already contradicts a hypothetical allowlist built from the first.

## Open questions carried forward

- **`patch` is an opaque display blob that is not guaranteed to parse.** Any future key-reading must sit
  behind an error branch falling back to inert text, and must never enumerate a closed key set — the
  daemon deliberately enumerates none of `patch`'s keys, because a mapping that listed the keys it knew
  would silently discard every key claude ships next.
- **`patch` is untrusted, model-influenced text whose keys may carry command text** — inert plain-text
  rendering only when #568 builds the panel: never an HTML/attribute/URL sink, never executed or
  re-shelled.
- **`truncatedFields` reports the cap cut only.** The daemon also scrubs invalid UTF-8 out of `patch` by
  deletion, so `patch` can differ from claude's bytes without appearing in `truncatedFields` — a stated
  upstream limitation, not a defect for #567/#568 to reconcile.
- **The `task_id` join to `background_task_started` belongs to #567, not this slice**, and must tolerate
  an `updated` for a task it never saw opened, since ordering is claude's, not the daemon's.
- **No terminal event exists in this family by design** (inherited from #564) — "finished" stays a
  client conclusion drawn from a task's absence in a later roster (#566), never something the wire
  reports directly.
- **Inner-switch exhaustiveness** (`daemonConnection.ts`'s `switch (inbound.kind)` has no
  `default: assertNever`) is now seven tickets deferred (#180, #199, #214, #315, #492, #564, #565). The
  round-trip test remains the deterministic safety net for this arm too.
