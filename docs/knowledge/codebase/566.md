# #566 — Decode the daemon `background_task_roster` frame into a typed `backgroundTaskRoster` event

Transport slice of the background-task-panel vertical, split from #554. Third and last of three sibling
frame slices (#564 `background_task_started` → #565 `background_task_updated` → #566
`background_task_roster`); the store that joins all three by `task_id` is #567, the panel that renders it
is #568. Shipped on branch `feature/566` (`ffe9fbc`), the aggregate-peer clone of both shipped siblings
(#564 `dbb163e`, #565 `28204e7`) plus `queue_state` / `QueuedItem` / `parseQueuedItem` for the nested-row
half. Security-sensitive (security review PASS, self-reviewed by the architect per
`architect/security-review.md`); size S, held over the ~600-LOC guideline on a compile-atomicity proof (the
spec's § Scope note — deleting any one bridge arm fails `npm run build`, so no seam exists to split on).
**No render** — the event ships dormant, consumed by none of the three exhaustive renderer bridges.

## Summary

`background_task_started` (#564) opens a task; `background_task_updated` (#565) reports what changed about
one. This frame is their **aggregate peer**: it reports **what is alive**, all at once, as a snapshot —
not a delta. An empty roster is the *positive* statement that nothing is running, which is the payoff
signal pyrycode#1240's symptom needs: a `turn_end` carrying `end_turn` while a command claude started is
provably still alive is otherwise indistinguishable from a genuine finish. Before this ticket the frame
was unmodeled and fell through `parseInboundMessage`'s `default → inbound-unmodeled → null`.

**Three frame fields, a nested row array of four.** `BackgroundTaskRosterPayload { conversation_id, tasks:
BackgroundTask[], dropped_tasks }` — `tasks` is a **plain, non-optional array**, never `BackgroundTask[] |
null`, because the daemon's payload carries `interactive.go`'s only custom `MarshalJSON`, whose entire job
is normalising a nil `Tasks` to `[]` so an empty roster never serialises as `null`. Each row,
`BackgroundTask { task_id, task_type, description, truncated_fields: string[] | null }`, is **four fields
and not the scalar siblings' four** — no `tool_call_id`, no `patch`, since those ride the scalar frames'
*lines* and this row carries only what claude's roster line does. Seven touch-points, mirroring #564/#565
end to end:

- **Wire types** (`src/shared/wire/types.ts`) — `'background_task_roster'` joins `EnvelopeType`, directly
  after `'background_task_updated'` (the slot #565 had already forward-commented for this ticket). Two new
  exported interfaces: `BackgroundTask` (the row, mirroring `QueuedItem`'s posture — snake_case, not
  `readonly`) and `BackgroundTaskRosterPayload` (the frame).
- **Inbound decode** (`inboundMessage.ts`) — **the trap, and the whole reason this ticket exists as its own
  slice rather than a mechanical third clone.** `tasks` is decoded via `parseQueueStatePayload`'s inline
  shape (`Array.isArray` check, then `raw.map(parseBackgroundTask)`) — **not** `requireStringArrayOrNull`,
  which is what a developer arriving fresh off shipping that helper twice for this family would reflexively
  reach for. `Array.isArray(null)` is `false`, which is what makes `tasks: null` fail closed, while the
  *row's* `truncated_fields` still goes through the existing `requireStringArrayOrNull` per row, where
  `null` is a valid value. A new row narrower, `parseBackgroundTask`, clones `parseQueuedItem`'s **posture**
  (one bad row fails the whole frame, an empty array is valid, a fresh four-field literal out) rather than
  `parseBackgroundTaskStartedPayload`'s **shape** — a row narrower cloned from that one would wrongly
  require `tool_call_id` and fail-close every valid roster. `dropped_tasks` decodes through plain
  `requireNumber` — the frame's **only** truncation report, correct precisely because the Go field has no
  `omitempty`, so `0` is a genuine wire value carried as `0`. `case 'background_task_roster'` narrows before
  logging (a malformed frame leaves no diagnostic record), then emits the existing content-free
  `inbound-decoded` shape — deliberately **no `count`** either, even though `DiagnosticEvent` already has
  one: the roster size is itself a fact about the user's session, the `queue_state` posture.
- **Consumer emit** (`daemonConnection.ts`) — one `case 'background-task-roster'`, a fresh named-field
  literal copied by name, never a spread of `inbound.backgroundTaskRoster`. **`conversation_id` is KEPT as
  `conversationId`**, the siblings' precedent. `tasks` passes the already-narrowed row array **by
  reference**, snake_case — no snake→camel, no per-row re-literal, the `queueState` nested-array precedent.
  Deliberately stateless, and the temptation here is a *different* one from #565's join temptation: this
  frame is a snapshot in a family with no terminal event, so holding the previous roster to compute what
  disappeared looks like the obvious next step. The spec forbids it — it would be the only mutable state in
  the leg, keyed by an attacker-influenceable `task_id`, fed by a hostile daemon's frame stream, with each
  frame carrying an attacker-chosen *number* of rows. Not compile-forced (no `assertNever` default on this
  inner switch) — the round-trip test is the guard.
- **`DaemonEvent` arm** (`src/shared/ipc/events.ts`) — `{ type: 'backgroundTaskRoster'; conversationId;
  tasks: readonly BackgroundTask[]; droppedTasks }`, placed after `backgroundTaskUpdated`. The doc-comment
  carries: the snapshot-not-delta contract (#567 must replace its held set, not merge); `tasks: []` as the
  positive "nothing is alive" signal that must never be filtered as "no news"; `droppedTasks` as the frame's
  only truncation report (`tasks.length + droppedTasks` is the true size); and the SECURITY constraint that
  a **list** of command lines is a more tempting shape to feed somewhere structured than a single one — the
  daemon states the render-as-plain-text-never-HTML rule per row rather than delegating it to the scalar
  frames' sections, for exactly that reason.
- **Three exhaustive bridge no-ops** — `daemonEventBridge.ts`, `modalBridge.ts`, `timelineBridge.ts` each
  add `case 'backgroundTaskRoster': return null`, directly beside the `backgroundTaskUpdated` arm in each
  file. In `timelineBridge.ts` the arm joins the no-op fall-through cluster (**not** the owned
  `apiRetry`/`compacting`/`stallDetected` arms) — daemon state, not a turn-stream item, and here the wire
  says so outright: no `turn_id`, opens and closes no turn.

`npm test` green across the touched test files (RED first, test-first per CLAUDE.md). 13 files touched
(7 production, 6 test), 0 new files — the same commit-time ≥5-production-file self-check #564/#565 already
established as structurally unsatisfiable: a new `DaemonEvent` arm compile-forces a case in all three
exhaustive bridges, and the transport decode exists only to feed that arm.

## Patterns established

- **Two contracts that look like the same shape, in the same frame, can be opposite.** `tasks: null` fails
  closed while a row's `truncated_fields: null` is a valid value — the daemon's own `MarshalJSON` comment
  is the tell: it normalises the first, deliberately not the second, because nil and `[]` say the identical
  thing for a per-row cut-field list while `tasks` is the frame's *subject* and its empty value is the
  signal. The concrete guard against getting this backwards is `Array.isArray`, not a shared "nullable
  array" helper — reaching for the family's existing `requireStringArrayOrNull` at the frame level would
  have been the wrong reflex, primed by having just shipped it twice for the row-adjacent field.
- **A nested-row wire type clones `queue_state` / `QueuedItem` / `parseQueuedItem` for its posture (one bad
  element fails the whole payload, an empty array is valid, unknown keys tolerated but not copied through),
  never a flat sibling's field list for its shape.** The two templates answer different questions —
  "how does an array of records decode" vs. "what fields does this particular record have" — and conflating
  them (cloning `parseBackgroundTaskStartedPayload`'s six fields onto a four-field row) is the concrete
  failure mode the spec named up front and code review would need `types.test.ts`'s negative-shape pin
  (`not.toHaveProperty('tool_call_id' | 'patch')`) to catch.
- **A truncation report can be a count instead of a name, and the two aren't interchangeable.** The two
  scalar siblings each report a per-frame `truncated_fields` naming which of *their own* fields got cut;
  this frame has no top-level equivalent — `dropped_tasks` is a *count* of entries the daemon didn't send at
  all, because there's no field to name for a row that was never included. Grepping for `truncated_fields`
  at the frame level finds nothing, which is itself the trap: the roster's true size is
  `tasks.length + dropped_tasks`, not `tasks.length`.

## Lessons learned

- Reading `git show <sibling-commit>` for **both** shipped siblings before writing (not just the
  immediately-preceding one) paid off specifically because this frame's nested shape has no counterpart in
  either individual sibling — #564/#565 supplied the seven-file seam and the `conversation_id`-KEPT /
  not-compile-forced-emit precedents, while `queue_state` (a third, unrelated ticket) supplied the entire
  nested-array decode shape. A single "read the immediately-preceding sibling" habit would have missed the
  second template entirely.
- The spec's own measured-LOC accounting (~800 lines, clearly over the ~600 guideline and the family's
  largest instance) held at face value rather than triggering a re-split, on the same compile-atomicity
  argument #564/#565 already proved unsplittable — a `DaemonEvent` arm forces a case in three
  `assertNever`-guarded bridges, so any split yields either a dead-code leaf or an arm-bearing child still
  at the full file count. The overage was documentation prose (the four-trap docstrings this frame's
  asymmetric contract demands), not new structural surface.

## Open questions carried forward

- **The roster is a snapshot, not a delta** — #567 must replace its held set per frame, never merge.
- **An empty roster is the payoff signal** (`tasks: []` positively says nothing is alive) and must never be
  filtered out as "no news" anywhere downstream.
- **There is no terminal event in this family by design.** "Finished" is a client conclusion #567 draws from
  a task's absence in a *later* roster — legitimate for #567 to draw on its own terms, but it must own that
  state and its own bounding, and must not present the inference as something the daemon reported.
- **`droppedTasks` must survive into #567's held set unabridged** — a panel that shows only the carried rows
  silently presents a capped roster as the whole one.
- **Each row's `truncatedFields` is per row** — must not be hoisted or flattened, and `null` must not be
  collapsed into `[]`.
- **The `task_id` join across all three frames is #567's**, and it must tolerate a roster arriving *before*
  the `background_task_started` for a task it lists, since ordering is claude's, not the daemon's.
- **SECURITY:** every row's `description` is untrusted, model-influenced text and, for `task_type:
  local_bash`, is the literal command line claude ran — inert text rendering only when #568 builds the
  panel, never an HTML/attribute/URL sink, never executed or re-shelled, and the *list* shape is not an
  invitation to feed it somewhere structured.
- **Inner-switch exhaustiveness** (`daemonConnection.ts`'s `switch (inbound.kind)` has no
  `default: assertNever`) is now eight tickets deferred (#180, #199, #214, #315, #492, #564, #565, #566).
  The round-trip test remains the deterministic safety net for this arm too.
