# #573 — Hold the background-task roster the daemon reports, per conversation

Store slice of the background-task-panel vertical, split from #567 (itself split from #554) into this
ticket (the roster store) and #574 (the two scalar arms, still open). #567's own children were: #564
`background_task_started` → #565 `background_task_updated` → #566 `background_task_roster` (transport,
all shipped, dormant) → this ticket (store, first consumer of the roster arm only) → #568 (panel, still
open) → #569 (reconnect repopulation, still open, blocked on a daemon change). Shipped on branch
`feature/573` (`ca86ce2`), PR #575. Security-sensitive (security review PASS, self-reviewed by the
architect); size S; code review PASS, zero findings. **No render** — the store ships populated and unread,
the same dormant-on-arrival posture #564/#565/#566 already shipped for the underlying wire arms.

## Summary

Two new files in `src/renderer/src/store/` (`backgroundTaskRosterStore.ts`, `backgroundTaskRosterBridge.ts`)
plus a two-line mount in `App.tsx`. Structure is the `queueStore.ts` + `queueBridge.ts` pair — the
in-family precedent for "daemon-state snapshot, keyed by conversation, store + bridge, render deferred".

- **`backgroundTaskRosterStore.ts`** — `ReadonlyMap<conversationId, { tasks, droppedTasks }>`, two named
  setters (`setRoster`, `resetRosters`), DI-factory → singleton → hook → selector structure. `setRoster` is
  copy-on-write and unconditional: an empty `tasks: []` still writes an entry (the daemon's positive
  "nothing is alive" statement), it never deletes the key. `resetRosters` clears the whole map on the
  `connected` edge and returns the same state reference when already empty.
- **`backgroundTaskRosterBridge.ts`** — `translateBackgroundTaskRoster` maps the one owned
  `backgroundTaskRoster` arm to a fresh `{ conversationId, tasks, droppedTasks }` literal (never a spread —
  #574 will widen the entry, and a spread would silently start carrying fields this slice never agreed to
  hold), `default: null` for everything else. `subscribeBackgroundTaskRoster` branches on `connected`
  *before* the translator (`resetRosters()`, return) — the `queueBridge` posture, not `modalBridge`'s
  `reconnected`-as-translator-action posture, because this translator returns a value, not an action-union
  member. `BackgroundTaskRosterData` is the headless leaf, mounted as `App.tsx`'s **seventh** sibling.

The one deliberate divergence from the `queueStore` template: `selectRosterFor` returns `s.rosters.get(id)
?? null`, not the precedent's `?? EMPTY_BACKLOG`. Cloning the precedent's collapsing selector would have
made "no roster has ever arrived" and "observed, nothing alive" both read as a bare empty list — silently,
with no type error and no failing test unless one was written for it (AC4). `null` is a stable reference
for free, so this store needed no hoisted `EMPTY_*` constant at all, and the nullable return type forces
the eventual reader (#568) to branch on the distinction rather than being able to ignore it.

`npm test` (35 new tests) and `npm run build` green. 5 production files (2 new, `App.tsx` +2 lines, 2 new
test files), 0 consumer fan-out (ships unread), 5 ACs.

## Patterns established

- **A selector's `?? EMPTY_DEFAULT` collapse is a decision about the read surface, not a mechanical part
  of the DI-factory/copy-on-write template — check what distinction the new ticket's ACs need before
  cloning it.** The `queueStore` precedent hoists `EMPTY_BACKLOG` specifically so "no snapshot yet" reads
  as an empty list; that is correct for `queue_state` and wrong here, and the fix is one token (`?? null`)
  once spotted. The failure mode if missed has no compiler signal and no default test coverage — only a
  test written specifically for the distinction (a seam test driving one conversation to `tasks: []` and
  another to never-observed, then asserting they read differently) would catch a regression.
- **A translator that returns a value (not an action-union member) keeps the `connected`-edge reset as a
  leading listener branch, not a translator arm.** `modalBridge` folds `connected` into its translator
  because it already returns members of a `ModalEvent` union, where a payload-free `reconnected` member is
  natural. A translator returning a plain snapshot type would have to widen its return type to
  `Snapshot | 'reset' | null` to do the same, which destroys the "translator is a pure arm→snapshot filter"
  property. The right posture is decided by what the translator's return type already is, not by which
  shipped precedent is more recent.

## Lessons learned

*(from the PR body's own "Lessons learned" section)*

- The precedent's collapsing selector is the kind of thing that survives a faithful clone *and* a green
  test run: `?? EMPTY_BACKLOG` type-checks identically to `?? null` at every call site in this slice, so
  nothing but a test written specifically for the distinction catches it. The bridge seam test that drives
  one conversation to `tasks: []` and leaves another never-observed is the only assertion in either file
  that would fail under the collapse — worth naming as such in the test body so it is not later pruned as
  redundant with the store's own null test.
- `App.tsx`'s inline leaf comments stop numbering at "fifth" because `RelayLinkData` landed without one, so
  the JSX and the prose disagree by one. Counting the JSX is the only reliable read; the new comment says
  so rather than backfilling the existing ones.

## Open questions carried forward

- **#574 (open)** owns the two scalar arms, `backgroundTaskStarted`/`backgroundTaskUpdated`, and is
  expected to widen `BackgroundTaskRosterEntry` with their `toolCallId`/`patch` as optional fields, carried
  over for surviving rows across a roster replacement. Nothing in this store was built to accommodate that
  ahead of time — the fresh named-field literal in the translator is the seam that makes the widening safe
  rather than silent.
- **#568 (open)** is the first reader. It inherits the `description`-as-inert-text obligation this store
  only carries in prose (`backgroundTaskRosterStore.ts:25-29`, `backgroundTaskRosterBridge.ts:11-14`) —
  this slice ships no DOM sink and nothing iterates `tasks`.
- **#569 (open, blocked on a daemon change)** owns repopulating the roster after a reconnect. This store
  deliberately does not retain state across a reconnect — the roster is not in the daemon's
  reconcile-on-connect set and this app sends no `last_event_id`, so a conversation reads `null` after a
  reconnect until claude next emits a roster. Retaining the pre-disconnect set would present a stale list
  as live, which the wire cannot support.
