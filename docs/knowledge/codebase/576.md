# #576 — Join the background-task started frame onto the held roster set

Store slice 2 of the background-task-panel vertical (split from #567 alongside #573, #568, #569).
#573 (`ca86ce2`) shipped the roster store and bridge, keyed by `conversationId`, holding wire
`BackgroundTask` rows verbatim. This ticket reshapes both so a `backgroundTaskStarted` event (#564,
still dormant everywhere else) is *joined* onto that set — held per task, keyed by `conversationId` +
`taskId`, carrying the `toolCallId` and fuller label only that frame reports. Shipped on branch
`feature/576` (`7790a76`), PR #578. Not itself security-sensitive as new surface, but the architect
self-reviewed per the security-review checklist (PASS) since the slice touches the same untrusted
`description` text #573 did. Size S; code review PASS, one SHOULD FIX (below the merge-blocking gate).

## Summary

Two production files touched, zero new files: `backgroundTaskRosterStore.ts` and
`backgroundTaskRosterBridge.ts`.

- **New per-task type, `HeldBackgroundTask`** — `{ taskId, toolCallId: string | null, taskType,
  description, truncatedFields: readonly string[] | null }`, renderer-side camelCase, replacing the
  wire-row-by-reference posture #573 shipped. `BackgroundTaskRosterEntry.tasks` changed from
  `readonly BackgroundTask[]` to `ReadonlyMap<string, HeldBackgroundTask>`, built at **write** time so
  `selectRosterFor` still hands back the held entry itself (no fresh object/array per selector call).
- **Provenance is derived, not stored:** a held task is started-sourced exactly when
  `toolCallId !== null` — never truthiness, since `requireString` (main-side decode) admits `''` as a
  valid `tool_call_id`. A truthiness check would silently demote such a task back to roster-sourced.
- **`setRoster`** now rebuilds the conversation's task map from the snapshot's rows in row order: a row
  whose `task_id` is already held **and is started-sourced** keeps the held record unchanged (the
  started frame's label is authoritative — it never repeats, so refreshing from the row would throw it
  away permanently); every other row is rebuilt fresh with `toolCallId: null`. `droppedTasks` is taken
  from the snapshot unconditionally. Membership stays replacement truth regardless of provenance — a
  held task absent from a new roster is simply not carried over.
- **New setter, `setStartedTask`** — copy-on-write upsert into the conversation's entry (creating it if
  none exists yet, since a started frame can precede any roster for its conversation). `Map.set` keeps
  an existing key's position, so upgrading a roster-held task in place preserves roster order.
  `droppedTasks` is **preserved** from the existing entry (or `0` on create) — a started frame reports
  nothing about roster truncation and must not reset the count.
- **Bridge gains a sibling translator**, `translateBackgroundTaskStarted`, same posture as its
  neighbour (fresh named-field literal, `default: null`, single owned arm, React-free).
  `translateBackgroundTaskRoster` is behaviourally unchanged — the row → `HeldBackgroundTask` mapping
  happens inside `setRoster`, not the translator, because that is where the prior state the join needs
  lives. `subscribeBackgroundTaskRoster` gains a fourth parameter, `setStartedTask`; the `connected`
  reset stays the leading branch.
- **Four stale in-file claims corrected in place** (all predicted "widen `BackgroundTaskRosterEntry`
  with optional `toolCallId`/`patch`", the shape this slice closes): the store header's "holds BY
  CONSTRUCTION" null-preservation claim (now names the straight assignment + tests as the defence, since
  the per-row mapping this ticket introduces is exactly what could make a collapse possible), and three
  `#574`-forecasting docstrings in the bridge/tests (`#574` closed and split; `backgroundTaskUpdated` is
  `#577`'s).

`npm test` — 49/49 pass (33 failing before implementation, migrated rather than appended per file).
`npm run build` clean. 4 files changed (2 production, 2 test), 786 insertions / 205 deletions,
5 ACs, 0 fan-out (same zero-consumer surface #573 shipped — `App.tsx` untouched, same headless leaf).

## Patterns established

- **A "holds by construction" docstring is a liability the moment a mapping is introduced.** #573's
  null-preservation guarantee (`truncated_fields: null` never collapsing to `[]`) was genuinely free
  while rows were held verbatim by reference — no per-row mapping existed for a collapse to happen in.
  This ticket introduces exactly that mapping (rows → `HeldBackgroundTask`), and a `?? []` there would
  have been neither a type error nor a failure of any other test. The fix isn't different code, it's
  naming the *tests* as the defence in the docstring rather than leaving a "can't happen" claim standing
  once the thing that made it true stops being true.
- **`new Map<K, V>(existing?.tasks)` accepts `undefined` directly** — `new Map(undefined)` is an empty
  map, and a `ReadonlyMap` satisfies the constructor's iterable-of-entries overload. This is why
  `setStartedTask`'s create-a-new-entry path needs no explicit branch: `existing?.tasks` flows straight
  into `new Map(...)` whether or not the conversation has been observed before.
- **A required-and-nullable field beats an optional one when every construction site must state a
  value.** `toolCallId: string | null` (not `toolCallId?: string`) makes an omitted `toolCallId` a
  compile error at every place a `HeldBackgroundTask` is built. An optional property would let a
  construction site silently skip it and still compile — exactly the fabricated-identifier hazard AC4
  is written around (`''` collides with a real `toolUse`/`toolResult` id; `null` cannot).
- **Provenance derived from an existing field beats a new boolean flag** when the field's presence is
  already exact by the wire's construction (only the started frame ever reports `toolCallId`). Adding a
  separate `isStartedSourced: boolean` would be a second source of truth that could drift from the field
  it's meant to describe.

## Lessons learned

*(from the PR body's own "Lessons learned" section)*

- A "holds by construction" docstring is a liability the moment a mapping is introduced — #573's
  null-preservation guarantee was genuinely free and said so in the file header; this slice added the
  per-row mapping that falsifies it, and a `?? []` collapse there is neither a type error nor a failure
  of any other test. The header now names the tests as the defence rather than the shape.
- `new Map<K, V>(existing?.tasks)` accepts `undefined` directly, so the create-entry-if-absent path
  needs no branch — `new Map(undefined)` is an empty map, and `ReadonlyMap` satisfies the
  iterable-of-entries overload.
- A required-and-nullable field beats an optional one when every construction site must state a value —
  `toolCallId: string | null` makes an omitted `toolCallId` a compile error, where `toolCallId?: string`
  would let a construction site silently skip it, which is exactly the fabricated-identifier hazard AC4
  names.

## Open mutation-control gap (from code review)

Code review PASS with one **SHOULD FIX**, not merge-blocking, left as shipped:

`setRoster`'s keep-vs-rebuild condition is `held !== undefined && held.toolCallId !== null`
(`backgroundTaskRosterStore.ts:227`). No shipped test discriminates that from
`held !== undefined ? held : …` — deleting `&& held.toolCallId !== null` still passes the whole suite.
The missing case: a *second* roster reporting **changed** fields for an already-held **roster-sourced**
`task_id` (no prior started frame). Every existing test either has no prior held record, exercises the
started-sourced half, or re-reports byte-identical fields, so "roster-sourced records are rebuilt from
each new row" (stated as fact in the store docstring) is asserted in prose but not pinned by a mutant-
killing test. Not a live bug — the daemon does rebuild each row from claude's roster line per frame, and
the shipped code already handles a changed roster-sourced row correctly — but it is exactly the
silent-collapse class this ticket was written around. Worth a follow-up test if this store gets touched
again; not urgent enough to have blocked the merge.
