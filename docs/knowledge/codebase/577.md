## The trap — and why the ticket names it that

`HeldBackgroundTask`'s shipped-by-#576 docstring said "any field added here that a roster row cannot
report must join that predicate" (the `toolCallId !== null` keep-whole condition). `latestUpdate` is
exactly such a field, so the instruction reads as authoritative — and following it literally is wrong.
The predicate gates whether the whole record is kept unchanged; widening it to also gate on
`latestUpdate !== null` would make a *patched roster-sourced* task stop refreshing from later roster rows,
freezing its `description`/`taskType`/own `truncatedFields` forever. Leaving the rebuild branch as #576
shipped it (no `latestUpdate` field on the fresh literal) drops the patch at the very next roster instead.
**Both mistakes compile clean and break no pre-existing test** — the spec's own words, confirmed by code
review, which called out `backgroundTaskRosterStore.test.ts:396-420` (a second roster with a *changed* row
for an already-patched roster-sourced task) as the single test that kills all three mutants: the unfixed
branch, the widened predicate, and outright deletion of the `toolCallId !== null` check. That last one
also closes the SHOULD FIX #576's code review left open (no mutation coverage existed for a re-rostered
roster-sourced task with changed fields). The docstring itself was rewritten in place
(`:115-125`) into the correct two-kinds rule — a field either gates keeping the record whole
(`toolCallId`, because the started frame's copy of everything else is authoritative) or rides across the
rebuild individually (`latestUpdate`, because no roster row can report it *and* the row's other fields
must still refresh) — so the fix, not the trap, is what the next slice inherits.

## Patterns established

- **A field that "no source X can report" is not one kind of field — it's two, and the docstring that
  only names the first kind reads as a rule when it's actually one instance.** `toolCallId` and
  `latestUpdate` are both true of "no roster row reports this", yet they need opposite treatment in the
  rebuild branch. The generalizable move: when extending a shape a prior ticket built a rule around, check
  whether the new field is actually the same *kind* of exception the rule was written for, not just
  whether the rule's literal precondition matches.
- **`??` is not always the collapse a null-preservation rule forbids — check what it's normalising.**
  `held?.latestUpdate ?? null` passes no wire value through it; it collapses two spellings of "no update
  yet" (`undefined` from no prior record, `null` from a held-but-never-updated one) into the one reading
  they share. The file's no-`??`-near-`truncatedFields` rule is about not letting `??` silently turn a
  wire `null` into `[]` — a different operation wearing the same operator. Cargo-culting "no `??` in this
  file" would have deleted a correct expression.
- **Nesting two fields that only make sense together is cheaper than testing their independence apart.**
  `latestUpdate: { patch, truncatedFields } | null` costs zero tests to forbid "a patch cut report without
  a patch" — the shape itself can't represent it. Two sibling optional/nullable fields on the same record
  would have needed a test asserting that specific combination never arises, and would still have let a
  future construction site produce it by omission.

## Lessons learned

*(from the PR body's own "Lessons learned" section)*

- A field a rebuild cannot re-derive splits into two kinds, and the wrong choice is silent: `toolCallId`
  gates keeping a held record whole, `latestUpdate` must ride across the rebuild individually. The shipped
  docstring said any such field must join the predicate — literal compliance freezes a patched task's
  label forever; ignoring the field drops the patch. Both compile clean and break no pre-existing test.
- `??` is not always the collapse the null-preservation rule forbids: `held?.latestUpdate ?? null`
  normalises two spellings of "no update yet" and touches no wire value, unlike `truncatedFields ?? []`,
  which would destroy the null/`[]` distinction. A blanket "no `??` in this file" reading would have
  deleted a correct expression.
- Nesting made a two-field disagreement unrepresentable instead of merely untested — `latestUpdate:
  { patch, truncatedFields } | null` costs no test to forbid a patch cut report without a patch, where two
  sibling fields would have needed one.
