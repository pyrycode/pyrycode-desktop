# #581 — Background-task panel: an openable surface listing the tasks held for the conversation

First slice of #568's panel (split three ways: this ticket → #582 → #583), and the first reader of
[`backgroundTaskRosterStore`](../features/background-task-roster-store.md) since it shipped dormant at
#573 and gained its full three-arm join across #576/#577. Shipped on branch `feature/581` (`4d1d973`),
PR #584. Size S, security-sensitive (architect self-review PASS), code review PASS with zero findings.

## Summary

Two new files, two production files touched, one CSS file extended — 490 lines total, matching the
spec's ~500 projection:

- **`BackgroundTaskPanel.tsx` (new, 173 lines)** — `BackgroundTaskPanelView`, the exported pure
  props-in/markup-out view every AC binds to, plus the in-file `BackgroundTaskPanel` container, exported
  at the foot (the `WorkspacePickerSheet.tsx` three-part shape). `entry` is typed as exactly
  `BackgroundTaskRosterEntry | null` — `selectRosterFor`'s return type — so the three-way branch lives at
  the view, where the tests can reach it:
  1. `entry === null` → `.background-task-panel__unobserved`, "No background-task report yet"
  2. `entry.tasks.size === 0` → `.background-task-panel__empty`, "No background tasks"
  3. otherwise → `.background-task-panel__list` of `.background-task-panel__row` (`description` +
     `taskType`, `key={task.taskId}`, iteration order = roster order)

  Each reading is its own element with its own class and copy, not a shared "empty" node and not `null`
  — a deliberate divergence from `WorkspacePickerSheetView`'s not-loaded branch (`null`), because here
  the branch *is* the whole panel body.
- **The container** clones `QueuedBacklogControl`'s conversation-id idiom: a `useMemo`-stable
  `selectRosterFor(conversationId ?? '')` selector plus `useBackgroundTaskRosterStore(selectRoster)`. The
  `''` sentinel matches no store key, so no active conversation reads as `null` ("never observed") for
  free, with no extra branch. An Escape `keydown` effect (attach on mount, detach on cleanup — the panel
  only mounts while open) closes it, the `WorkspacePickerSheet` effect verbatim.
- **`ConversationScreen.tsx` (+51 lines)** — a fourth screen-local `useState(false)` (`panelOpen`, the
  `pickerOpen`/`channelInfoOpen`/`sheetOpen` twin, [ADR
  0006](../decisions/0006-ephemeral-screen-state-usereducer-not-store.md)); an in-file
  `BackgroundTaskTrigger({ onOpen })` — an icon-only `.background-task-trigger` button
  (`aria-label="Background tasks"`, `aria-haspopup="dialog"`) mounted **unconditionally** as a
  `StatusRow` sibling, not gated on tasks existing (gating would make both non-populated readings
  unreachable through the UI); and the `{panelOpen && <BackgroundTaskPanel .../>}` mount, before
  `<PermissionModal />`.
- **`conversation.css` (+84 lines)** — `.background-task-trigger`/`.background-task-panel__*`, token-only
  (no new token), the `.status-row`/`.workspace-picker__*` chrome vocabulary. No `.status-sheet …`
  descendant selector or positional CSS on the rows — only the outermost wrapper is chrome, per the
  spec's #580-forward-compat constraint.
- **No bridge mount.** `<BackgroundTaskRosterData />` is already the seventh headless leaf in `App.tsx`;
  this panel is a pure reader, the one structural divergence from the `WorkspacePickerSheet` precedent
  (which does mount `RecentWorkspacesData` inside itself).

`npm test -- BackgroundTaskPanel.test.tsx ConversationScreen.test.tsx` green (152 tests, RED-first per
AC) plus the six pre-existing `ConversationScreen` consumer suites; `npm run build` (typecheck +
electron-vite) clean.

## Patterns established

- **A nullable prop typed as exactly the selector's return type forces the hard branch to the pure
  view.** `BackgroundTaskPanelView`'s `entry: BackgroundTaskRosterEntry | null` is not a convenience
  narrowing — it is `selectRosterFor`'s signature verbatim, so the container cannot pre-collapse the
  reading before the view sees it, and the three-way branch becomes assertable under
  `renderToStaticMarkup` without a DOM harness. #582 and #583 extend this same prop (`droppedTasks`,
  `truncatedFields`, `latestUpdate`) rather than widening or narrowing it.
- **Two orthogonal collapse points, and only one AC to catch both.** The spec named the "reach for
  `.tasks` before checking `entry === null`" failure explicitly; three superficially reasonable
  one-liners (`[...(entry?.tasks.values() ?? [])].length === 0`, `(entry?.tasks.size ?? 0) === 0`,
  `entry?.tasks ?? new Map()`) all compile clean and break no pre-existing test. This is a display-layer
  restatement of the same collapse `selectRosterFor`'s `?? null` refuses to make at the store — the
  obligation crosses the store/view boundary rather than staying store-side.
- **A non-interactive row list is itself a security control, not just a UX choice.** No `<button>`, no
  `onClick`, no `data-*` task attribute — closing off the natural place a "run this again" affordance
  would grow from later, named explicitly in both the spec and the security review as the failure mode a
  rendered *list* of shell commands invites that a single one doesn't.

## Lessons learned

(Lifted from the PR body's own "Lessons learned" section.)

- **The `javascript:` assertion trap generalises past URLs.** The spec warned off
  `not.toContain('javascript:')`, but the same failure mode also hit `not.toContain('onerror=')` and
  `not.toContain('src=')`: React escapes markup metacharacters, not arbitrary text, so a *correct* render
  of `<img src=x onerror="alert(1)">` still contains both substrings inertly. The RED-first run caught it
  before it shipped. The guard that actually distinguishes a real sink is **attribute-shaped**:
  `renderToStaticMarkup` always quotes attribute values and escapes `"` → `&quot;`, so `href="`, `src="`,
  and `/\son[a-z]+="/` are unforgeable from escaped text — and asserting their absence across the *whole*
  markup still fails on any future attribute placement anywhere in the component, not just the field
  under test. Rule of thumb, now standing: a no-XSS string assertion is only meaningful if the substring
  it checks for contains a character React actually escapes.
- **A worktree can arrive without `node_modules`.** `npm test` failed with `vitest: command not found`;
  `npm install` in the worktree fixed it — not a code issue, just a reminder to check before assuming a
  test-runner failure is real.
