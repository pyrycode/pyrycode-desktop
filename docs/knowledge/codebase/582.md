# #582 — Background-task panel: show when the roster was capped or a task's text was cut

Second slice of #568's panel split (#581 → this ticket → #583). Extends
[`BackgroundTaskPanelView`](../features/conversation-shell.md#background-task-panel-581-cap-and-cut-display-since-582)
(#581, shipped `4d1d973`) with the two bounds the daemon reports on background tasks and the shell
showed neither of. Shipped on branch `feature/582` (`0f410a8`), PR #585. Size S, security-sensitive
(architect self-review PASS), code review PASS with zero findings.

## Summary

One production file touched (`BackgroundTaskPanel.tsx`, +109/-9), its test file (+204/-… ), and a CSS
extension — 334 changed lines total, close to the spec's ~230–250 projection once the diff-stat
overhead (context lines) is discounted. No prop, type, store, bridge, or wire change — the shell (#581)
pre-built both seams on the `entry` prop.

- **The partial-list notice** — `entry !== null && entry.droppedTasks > 0` gates a
  `.background-task-panel__partial` paragraph reading `partialListCopy(entry.droppedTasks)` →
  `` `Partial list (${n} not shown)` ``. It is a **sibling of the shipped three-way branch**, the first
  child of `.status-sheet__body`, not nested in any of its arms — so it shows whichever branch the task
  list itself takes, including the (daemon-unreachable but view-constructible) case of dropped tasks
  with zero carried rows. Boolean comparison, not `{entry.droppedTasks && …}` — the truthiness form
  would print a bare `0` text node on every non-truncated roster.
- **The per-field cut marker** — `wasCut(task.truncatedFields, wireFieldName)` (`truncatedFields !==
  null && truncatedFields.includes(wireFieldName)`), matched against two module-private constants,
  `CUT_FIELD_DESCRIPTION = 'description'` and `CUT_FIELD_TASK_TYPE = 'task_type'`. The second is the
  trap the ticket exists to defuse: the held property is `taskType` (camelCased at the IPC boundary),
  but the wire array's *contents* cross unconverted, so the match string must stay `'task_type'`. Each
  marker (`.background-task-panel__cut-description` / `-cut-type`) is a sibling `<span>` immediately
  after the field it describes, holding the one client-owned constant `BACKGROUND_TASK_PANEL_CUT_COPY`
  (`'Truncated by the daemon'`) — never concatenated into the field's own text node, never built from
  the field text itself.
- **`wasCut` is module-private and deliberately untested in isolation** — a predicate-level test passes
  whatever name it's handed and would stay green even if the call site matched on the held `'taskType'`
  name instead of the wire `'task_type'` name. The trap only shows up at the call site, so the test
  suite exercises it there (`BackgroundTaskPanel.test.tsx`, the wire-name scenario, `truncatedFields:
  ['taskType']` → asserts no marker renders).
- **One shipped #581 test was revised, not worked around**: `BackgroundTaskPanel.test.tsx:75-99` (the
  "renders no task field beyond description and taskType" test) had asserted
  `not.toContain('987654')` against a fixture using `droppedTasks: 987654`. That assertion became false
  under this ticket's own AC1. Fixed by changing the fixture to `droppedTasks: 0` and deleting the count
  assertion, leaving the test about task fields only, which is what its name claims.
- **CSS**: `.background-task-panel__partial` and the shared `.background-task-panel__cut-description,
  .background-task-panel__cut-type` rule, appended to the existing block, reusing the
  `.unrecognized-row__truncated` muted body-small declaration set. Neither is styled as an error — a
  bounded report is the daemon working as designed, reported honestly.

`npm test -- BackgroundTaskPanel.test.tsx ConversationScreen.test.tsx` → 160 passed; `npm run build`
(typecheck + electron-vite) clean.

## Patterns established

- **Match wire names, not held (camelCased) property names, when a wire array's *contents* are strings
  drawn from the same vocabulary as a field name.** Only the field key crosses the IPC boundary
  camelCased (`truncatedFields: row.truncated_fields` in the store); the strings inside the array are
  copied by reference and stay exactly as the daemon wrote them. This is a distinct trap from ordinary
  key camelCasing and doesn't show up in a type-checker or a naive test — `'taskType'` compiles,
  type-checks, and silently never matches.
- **A predicate meant to catch a naming trap must not be unit-tested in isolation** — isolate it as an
  unexported function and put its only test at the call site, so the test can't be satisfied by passing
  the predicate the wrong string.
- **A shell's sentinel test that pins a successor's field as absent (`not.toContain('987654')` for a
  not-yet-rendered `droppedTasks`) becomes a live test the successor must revise, not just satisfy.**
  Worth grepping a predecessor ticket's test file for this shape before estimating a follow-up slice.
- **A notice or marker keyed to a count reads on the count field alone, positioned as a sibling of an
  existing branch rather than folded into one arm of it** — otherwise the notice becomes invisible in
  whichever arm it wasn't added to, even for combinations the daemon can't currently produce, because
  the view is a pure function of its prop and a test can construct the untaken combination directly.

## Lessons learned

(Lifted from the PR body's own "Lessons learned" section.)

- **A wire payload carrying field NAMES as data is not camelCased at the IPC boundary — only the field
  itself is.** `truncatedFields: row.truncated_fields` hands the array over by reference, so the panel
  holds `task.taskType` but the list says `task_type`. Matching on `'taskType'` compiles, type-checks,
  never matches, and fails no pre-existing test. Two mutation controls were run to prove the new tests
  are not vacuous: flipping the constant to `'taskType'` kills 2 tests, and flipping the notice guard to
  the `{entry.droppedTasks && …}` truthiness form kills the bare-zero test (which renders `<div
  class="status-sheet__body">0<ul …`, caught by anchoring on the body's opening tag — `not.toContain('0')`
  is impossible when the close icon carries `viewBox="0 0 24 24"`).
- **The predicate is deliberately module-private and untested directly.** A unit test of `wasCut` passes
  whatever name it is handed and would stay green while the call site passed the held name. The trap
  lives at the call site, so the test does too.
- **A shell that pins its successors' fields as absent hands each successor a test it must flip.**
  #581's `expect(markup).not.toContain('987654')` became false under AC1 by construction; it was revised
  (fixture to `droppedTasks: 0`, count assertion deleted) rather than worked around. Worth grepping a
  predecessor's test file for such sentinels before estimating.
