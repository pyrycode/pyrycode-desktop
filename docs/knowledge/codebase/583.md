# #583 — Background-task panel: show the latest change claude reported about a task

Third and last slice of #568's panel split (#581 → #582 → this ticket). Extends
[`BackgroundTaskPanelView`](../features/conversation-shell.md#background-task-panel-581-cap-and-cut-display-since-582-latest-patch-since-583)
(#581, shipped `4d1d973`; #582, shipped `0f410a8`) with the last field the shell's header comment
named as deliberately unread: the held `latestUpdate` pair. Shipped on branch `feature/583` (`f7cb048`),
PR #586. Size S, security-sensitive (architect self-review PASS), code review **PASS with two
non-blocking SHOULD FIX + one NIT** (under the three-finding gate) — see *Code review findings* below.

## Summary

One production file touched (`BackgroundTaskPanel.tsx`, +86/-9), its test file (+197/-11), and a CSS
extension — 586 changed lines total (incl. the architecture spec). No prop, type, store, bridge, or
wire change — `latestUpdate` was already reachable on the `entry` prop, the same standing start #582
had.

- **Three readings of `task.latestUpdate`**, each rendering distinctly:
  - `null` (no update has ever matched this task) → **no element at all** — a deliberate divergence
    from the #581 three-way branch, where every reading gets its own element because that branch *is*
    the whole panel body. A row has other content (description, task type), so absence reads as
    legible rather than broken.
  - `{ patch: '', … }` (claude reported no change — the field always arrives on the wire, so `''` is a
    value, not an absence) → `.background-task-panel__no-change`, the client-owned sentence
    `BACKGROUND_TASK_PANEL_NO_CHANGE_COPY` = `'No change reported'`.
  - `{ patch: <non-empty>, … }` → `.background-task-panel__patch`, holding the patch as **inert,
    auto-escaped React children** — never parsed. The daemon truncates the patch at construction (its
    own golden fixture is cut mid-token), so a cut patch may no longer be valid JSON; a future parse
    would also need to fall back to this inert text on error and enumerate no closed key set, since a
    mapping of known keys would silently discard every key claude ships next. Rendering plain text
    answers the ticket in full and sidesteps the hazard.
  - The branch is on `task.latestUpdate !== null` then `patch === ''` beneath it — never a truthiness
    test on the patch. `{latestUpdate?.patch && …}` would render a recorded empty patch byte-identically
    to the never-updated reading: compiles, type-checks, breaks no pre-existing test. This is #582's
    `{entry.droppedTasks && …}` trap one field over, and quieter — `droppedTasks` at least printed a
    visible bare `0`; an empty string renders as nothing at all, leaving the collapse no trace for a
    test to catch by accident.
- **The patch's own cut marker** — a third module-private constant, `CUT_FIELD_PATCH = 'patch'`, beside
  the existing `CUT_FIELD_DESCRIPTION` / `CUT_FIELD_TASK_TYPE` pair, matched via the shipped `wasCut`
  predicate unchanged. `.background-task-panel__cut-patch` is a **sibling of the two-arm ternary**,
  inside the `latestUpdate !== null` guard rather than nested in the non-empty arm — the same placement
  rule #582's partial-list notice carries, and for the same reason: the cut report is a property of the
  update *record*, not of the patch's emptiness. A recorded `{ patch: '', truncatedFields: ['patch'] }`
  is unreachable daemon-side today (the 4 KiB cap never cuts to zero length) but is directly
  constructible against a pure view; a marker written only inside the non-empty arm would be invisible
  in exactly that state, leaving the panel claiming "no change reported" while the daemon reported a cut.
  Reads `task.latestUpdate.truncatedFields` **only** — no casing trap on this list (wire name equals
  held name, the same coincidence `description` enjoys), but the crossover trap is real: matching
  `task.truncatedFields` against `CUT_FIELD_PATCH`, or `task.latestUpdate.truncatedFields` against
  `CUT_FIELD_DESCRIPTION`/`CUT_FIELD_TASK_TYPE`, all compile and type-check (every list is `readonly
  string[] | null`) and never match, since neither vocabulary names the other's fields.
- **Row markup**: appended last, after the existing description/task-type fields and their markers, so
  identity fields stay at the top and each marker keeps sitting immediately after the field it
  describes. A `<>` fragment holds the two-arm ternary plus the marker under one `latestUpdate !== null`
  guard.
- **CSS**: `.background-task-panel__patch` (muted body-small mono, `min-width: 0` +
  `overflow-wrap: anywhere` so an unbroken 4 KiB token wraps instead of overflowing — no height clamp,
  `.status-sheet__body` already scrolls), `.background-task-panel__no-change` (the muted body-small set
  `.background-task-panel__type` wears), and `.background-task-panel__cut-patch` added to the existing
  shared marker selector list. None takes an error color; a bounded or empty report is the daemon
  working as designed, reported honestly.

`npm test -- src/renderer/src/screens/conversation/BackgroundTaskPanel.test.tsx` 17/17 (4 new, RED
before implementation); `ConversationScreen.test.tsx` 147/147; `npm run build` clean.

## One shipped test revised

`BackgroundTaskPanel.test.tsx:75-104` — *"renders no task field beyond description and taskType"* —
carried a fixture with `latestUpdate: { patch: 'SENTINELPATCH', truncatedFields: ['SENTINELPATCHCUT'] }`
and asserted both `not.toContain('SENTINELPATCH')` (true of #581's shell, false the moment this ticket's
AC1 renders the patch) and `not.toContain('SENTINELPATCHCUT')` (stays — becomes a live guard that an
unrecognised patch-cut name marks and displays nothing). Resolved exactly as #582 resolved the identical
shape against #581's `droppedTasks: 987654` sentinel: delete the one stale line, keep the neighbouring
guard, update the test's title and its now-false "unread" comment. Not flipped into a positive
`toContain('SENTINELPATCH')` — `SENTINELPATCH` is a prefix substring of `SENTINELPATCHCUT`, so that
"proof" would also pass on a render displaying only the forbidden cut-field name. New fixtures use
non-overlapping values (`PATCHTEXT`, `SENTINELFUTURENAME`) for the same reason.

## Code review findings

The implementation itself was found correct — both findings are about test coverage, not production
behavior, and neither was fixed in a follow-up commit as of this writing (the PR's head commit, `f7cb048`,
is the one the review was submitted against):

- **SHOULD FIX — the cut-marker placement decision has no test pinning it.** `BackgroundTaskPanel.tsx`
  places `wasCut(task.latestUpdate.truncatedFields, CUT_FIELD_PATCH)` as a **sibling** of the
  empty/non-empty ternary, inside the `latestUpdate !== null` guard — deliberately, so a
  daemon-unreachable-but-view-constructible state (`{ patch: '', truncatedFields: ['patch'] }`) still
  shows the marker rather than going invisible inside a non-empty-only arm. No shipped fixture
  constructs that exact state (the empty-patch fixtures all pair with `truncatedFields: null`), so
  moving the marker inside the non-empty arm would currently pass every test. #582 pinned the
  structurally identical decision (`emptyButCapped`, `BackgroundTaskPanel.test.tsx:207-214`) — one
  more render, following that precedent, closes the gap.
- **SHOULD FIX — a test comment overclaims what the whole-markup escaping net proves.** The comment at
  `BackgroundTaskPanel.test.tsx:388-393` says the three attribute-shaped guards (`href="`, `src="`,
  `/\son[a-z]+="/`) would catch the patch placed in a `title=` attribute. They would not: React quotes
  and escapes a `title` attribute in a way that happens to dodge all three patterns for the specific
  `<img src=x onerror="alert(1)">` fixture. Production code is unaffected (the patch is auto-escaped
  children, never an attribute); the comment's claim is broader than the assertions support.
- **NIT** — the file-header comment ("#583 added the last unread field") reads as though the panel
  now renders every `HeldBackgroundTask` field; `toolCallId` remains unread by design.

Both SHOULD FIX findings are candidates to fold into #580 (visual design) or a small follow-up, per the
review's own closing note.

## Patterns established

- **A branch that renders nothing for an absent reading is legitimate when the branch is a row field,
  not the whole surface** — #581's rule (every reading gets its own element) applies specifically
  because that branch *is* the panel body; a row with other content can let "never observed" render
  nothing, provided the next-more-populated reading (a recorded empty value) still renders something
  distinct, so no two readings collapse to the same markup.
- **An empty-string truthiness collapse is strictly quieter than an empty-number one.** `0` at least
  prints a visible bare digit if guarded with `&&`; `''` renders as nothing, so the same class of bug
  leaves no trace for an unrelated assertion to catch by accident — the collapse guard has to be written
  deliberately (`expect(emptyReading).not.toBe(neverReading)`), not discovered.
- **Two sibling lists of the same type over disjoint vocabularies are a standing crossover trap**, not a
  one-off: `task.truncatedFields` (`task_id`/`task_type`/`description`) and
  `task.latestUpdate.truncatedFields` (`task_id`/`patch`) are both `readonly string[] | null`, so any
  swap between them compiles, type-checks, and silently never matches. Every marker added against a
  second same-shaped list needs its own crossover test in both directions, not just a positive-match
  test.

## Lessons learned

(Lifted from the PR body's own "Lessons learned" section.)

- **A shell that pins a successor's field as absent hands the successor a test it must flip.**
  `not.toContain('SENTINELPATCH')` was true of #581's shell and false the moment the patch renders — the
  third run of this shape in the split (#581→#582 did it with `droppedTasks: 987654`). Resolved the same
  way: delete the one stale line, keep the neighbouring `SENTINELPATCHCUT` guard, now live rather than
  vacuous.
- **Two sentinels where one is a prefix substring of the other cannot both be asserted.**
  `SENTINELPATCH` ⊂ `SENTINELPATCHCUT`, so flipping the stale line into a positive `toContain` would
  have been satisfied by exactly the render the next line forbids. The new fixtures use non-overlapping
  values (`PATCHTEXT` / `SENTINELFUTURENAME`) for that reason — the same substring check #582 ran on
  class names, applied here to fixture strings.
- **An empty-string collapse leaves no trace in the markup, unlike an empty-number one.**
  `{latestUpdate?.patch && …}` renders a recorded `patch: ''` byte-identically to a never-updated task;
  #582's `{entry.droppedTasks && …}` at least printed a visible bare `0`. Nothing else fails, so the
  guard has to be a deliberate `expect(emptyPatch).not.toBe(noUpdate)` — no other assertion catches it
  by accident.
- **Two same-typed sibling lists (`readonly string[] | null`) over disjoint vocabularies swap
  silently.** Reading the task's list for the patch, or the update's list for the description, compiles,
  type-checks, and never matches — no error, no marker, no failing test. Both crossover directions need
  their own assertions; the sharper one is the update's list naming `description`/`task_type`, since
  both are live `CUT_FIELD_*` constants.
