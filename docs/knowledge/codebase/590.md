# #590 — Run config: offer the Fable model family

A fourth `MODEL_CATALOG` entry — `Fable 5` / `newest in the Fable family`, family token `fable` —
inserted between Sonnet and Haiku in the run-configuration sheet's Model section, reaching a
published model family the sheet previously made unselectable. Shipped on branch `feature/590`
(spec `37f4ebd`, implementation `ba20659`), PR [#592](https://github.com/pyrycode/pyrycode-desktop/pull/592).
Size XS, security-sensitive (architect self-review PASS, zero findings), code review **PASS, one
NIT** (see below). Split from #561.

## Summary

The sheet offered Opus, Sonnet and Haiku only. `fable` is a real published family the daemon
resolves like any other alias (measured live 2026-08-18: `/model fable` → `claude-fable-5`), so the
app had no way to reach it at all. The fix is one array entry — no JSX change, no CSS, no new
export, no store, no wire change:

```ts
// RunConfigSections.tsx:36-42
const MODEL_CATALOG: readonly ModelCatalogEntry[] = [
  { family: 'opus', name: 'Opus 4.7', descriptor: 'best for complex work' },
  { family: 'sonnet', name: 'Sonnet 4.6', descriptor: 'faster, cheaper' },
  { family: 'fable', name: 'Fable 5', descriptor: 'newest in the Fable family' },
  { family: 'haiku', name: 'Haiku 4.5', descriptor: 'fastest' }
]
```

The row is emitted by the existing `MODEL_CATALOG.map` in `ModelSection` with no per-family
branching, so a fourth entry needed no markup change. Also touched: the stale
`('opus'/'sonnet'/'haiku')` token comment at `:167` (now includes `'fable'`), and two stale
row-count comments in `e2e/run-config-settings.spec.ts` (`:87-88`, `:180`) — comments only, no
assertion changed.

`npm test` — `src/renderer/src/screens/conversation/` 354 passed (20 files), RED captured first (4
failures: the AC1 loop, AC2, AC3, AC5, before the catalog entry existed). `npm run build`
(typecheck + electron-vite) clean. 3 files touched, 69 insertions — the projected XS ceiling.

## Patterns established

- **A field with two uses removes the need for a test seam.** `entry.family` is both the value
  handed to `onSelect` (`:177`, what the row submits) and the token `matchedFamily`
  substring-matches the daemon's `model` string against (`:52-55`, what marks a row current).
  Rendering with the bare alias and observing the row marked *is* the round-trip proof, without
  firing a click the `node`-env server-render tests cannot fire. No `MODEL_CATALOG` export and no
  accessor were added — that would be new public surface an XS ticket does not need, and would leave
  the new row proved differently from its three siblings (which have no such seam either).
- **`segmentFor`'s negative assertions are only as tight as the row's position.** The helper's chunk
  runs from a row's own class token to the *next* occurrence of that token — except the last row's,
  which runs to end-of-document and swallows whatever follows (here, the effort segments and the
  YOLO switch, each carrying its own `role="button"`/`tabindex`). Fable was placed third of four
  specifically so its chunk is bounded by the Haiku row, keeping AC5's inert-case negative assertions
  meaningful rather than accidentally vacuous. Check a row's position before trusting any
  `segmentFor … not.toContain` on it.
- **Insertion position in a first-match-wins catalog is a display concern only when no real vector
  collides two tokens.** `matchedFamily` is `lower.includes(entry.family)` over the catalog in
  order; Fable at index 2 changes which row renders third and nothing about which row matches,
  because no AC4 vector (or real model id) contains two family tokens.
- **A green-on-RED regression-guard AC is not automatically vacuous.** AC4 ("the added row steals no
  existing match") passed even before the Fable entry existed, because `segmentFor(..., 'Fable 5')`
  returned `''` and every negative held trivially on an absent row. It is still worth keeping: its
  positive half (each sibling vector marks its own row, global count 1) is real in both states and
  is what would fail if the entry were mis-positioned or mis-tokenised later.

## Code review

PASS, one NIT: the widened token comment at `:167` is now the file's longest production line (113
chars) — this repo runs no Prettier/ESLint, so nothing enforces a wrap; non-blocking. No MUST FIX,
no SHOULD FIX. Reviewer independently swept the tree for `MODEL_CATALOG`/`run-config__model-row`/the
display names and confirmed the full consumer set (the test file, the two e2e comments, one
already-closed-sheet e2e assertion, one already-closed-sheet `ConversationScreen.test.tsx`
assertion) — nothing missed. Confirmed the security posture by reading the write path directly:
`entry.family` reaches `SetSessionSettingsPayload` as a structured field via `buildSettingsPayload`
(`runSettingsWriteBridge.ts:113-117`), never a shell/command-string interpolation, and the daemon's
`model` is matched with `String.prototype.includes` on a lowercased copy, not a constructed `RegExp`.
Named, not flagged, one pre-existing gap: the model rows are `role="button"` + `tabIndex={0}` with
no `onKeyDown` — #257's documented deliberate non-goal, unchanged by this row, out of scope here.
