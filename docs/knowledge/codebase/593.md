# #593 — Renderer: drop the announced running model when the pairing ends

Filed from #560's refinement, per the follow-up obligation recorded in `announcedModelStore.ts:24-32`
when [#588](588.md) shipped the store dormant. Spec `d718e07`, shipped `11d3a19`, zero deviation from
`docs/specs/architecture/593-announced-model-pairing-clear.md`. Size S, security-sensitive (architect
self-review PASS). Code review PASS.

## Summary

`announcedModelStore` ([#588](588.md)) holds claude's announced running model, rendered since
[#560](560.md) by `RunConfigSections`' `RunningModelSection`. Nothing on a fresh pairing re-asserts an
announcement — the next one arrives only with the new daemon's first turn — so after a pair-another-server
switch the sheet was attributing server A's identifier, and its `truncated` cut report, to server B under
a "Running model" header with no provenance marker. This ticket closes that: the store now clears on both
pairing-change paths.

- **`announcedModelStore.ts`** gains a second whole-value mutation, `clearAnnouncedModel: () => void`,
  mirroring `sessionIdStore`'s `clearSessionId` ([#529](529.md)) exactly: `set(initialAnnouncedModelState)`
  in the factory, sourced from the exported constant (not a fresh literal) and unconditional, so a
  redundant clear is a no-op by construction rather than by a guard. It lands on `AnnouncedModelStore`
  (the store type), never on `AnnouncedModelState`, so `selectAnnouncedModel` stays typed against the
  state-only interface. Restores the `null` "not yet announced" sentinel — never a
  `{ model: '', truncated: false }` record, the one case that distinguishes the store's two deliberately-
  separate sentinels.
- **`clearPairingScopedState.ts`** gains a fifth effect, `clearAnnouncedModel`, on
  `ClearPairingScopedStateDeps` and in the function body, placed after `clearSessionId` (no ordering
  constraint — all five are independent whole-value writes).
- **`PairedShell.tsx`**'s single `clearPairingDeps` object gains the one new field
  (`() => announcedModelStore.getState().clearAnnouncedModel()`), so both call sites (`onUnpaired`,
  `onPairServerPaired`) pick it up with no code change of their own.
- **`App.tsx`**'s mount comment for `AnnouncedModelData` is rewritten: it no longer states a deferral,
  it states *why* there is still no `connected` branch — a reconnect to the same daemon leaves the held
  announcement accurate, so the clear belongs to `clearPairingScopedState`, not the transport edge.

## Patterns established

- **The mechanism choice is a one-question discriminator, not a per-ticket judgement call: does a
  reconnect to the *same* daemon need to clear this store?** No ⇒ `clearPairingScopedState` (this store,
  `activeConversationStore`, `sessionIdStore`, the timeline, `sessionStore`). Yes ⇒ the transport's
  `connected` edge inside the store's own bridge (`backgroundTaskRosterStore`, whose branch is documented
  as "the sole enforcement of #573's AC5"). The two mechanisms are mutually exclusive by design —
  `clearPairingScopedState`'s docstring explicitly excludes stores the `connected` edge already clears —
  so a future pairing-scoped store's home is decided by that one question, not by which file looks more
  convenient to edit.
- **A store that ships a mutation dormant, with the clear deliberately deferred, needs the deferral
  written down at the exact place a future ticket will look** (`announcedModelStore.ts` header,
  `App.tsx`'s mount comment) — #588 did this, and it is what let this ticket start from "the code already
  settled the mechanism" instead of re-litigating it. When the deferral resolves, retire the note
  entirely rather than leaving it assert a now-false exclusion.
- **Idempotence on a nullable store is structural, not something to test with a raw `subscribe` spy.**
  Zustand's vanilla `set` notifies subscribers unconditionally, so `store.subscribe(spy)` +
  `expect(spy).not.toHaveBeenCalled()` fails on correct code. The real property lives one layer up, at
  the selector: `useStore`'s `Object.is` comparison on `null → null` short-circuits the re-render. For
  this store the by-reference claim is trivial (the cleared value *is* the sentinel `null`), unlike
  `timelineStore`'s `toBe(itemsBefore)` where a fresh `[]` would genuinely churn — don't manufacture a
  stronger-looking identity assertion than the type admits.

## Lessons learned

- **A PR editing a heavily-cited file drifts every `path:N-M` line-range pointer across the codebase that
  cites it — including the ranges the same commit itself just wrote.** `announcedModelStore.ts` gained 9
  lines in its header comment alone; every doc (this one included, on the first pass) that cited a
  specific line range into that file needed re-resolving against the new line count, not just the two or
  three ranges that moved the most.
- **`#560 has merged` was easy to miss as a load-bearing fact.** The ticket body was filed while #560 was
  still in flight and said so explicitly; by the time this ticket's spec was written, #560 had merged
  (`c3af075`), which changed the security posture from "store ships dormant, stale value is latent" to
  "stale value is observable today, in a shipped sheet, with no provenance marker distinguishing the two
  servers' models." The architecture doc's Context section states the correction explicitly rather than
  silently updating stale prose — worth doing any time a spec is written against a body that predates a
  relevant merge.
