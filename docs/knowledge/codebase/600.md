# #600 — A tolerant at-bottom test for the thread scroll region

Split from #599 (the follow-the-conversation feature) as its one genuinely unit-testable piece. Spec
`34a0997`, shipped `f3e7609`, PR #605, zero deviation. Size XS, not security-sensitive, code review PASS
(one NIT, documentary-only — see below). Ships **dormant**: #601 is the wiring ticket that gives it a
caller.

## Summary

The renderer has no scroll management at all — `.conversation__thread` scrolls because it is
`overflow-y: auto`, but nothing reads or writes its position. This ticket adds the pure arithmetic that
will decide "is the thread scrolled to the bottom?", isolated from the DOM/effect wiring that the
renderer's `node`-environment test layer cannot exercise: vitest runs with no jsdom and no layout engine
(`vitest.config.ts:27`), so renderer tests are `renderToStaticMarkup` string assertions — effects never
run and there is no `scrollTop` to read.

- **`src/renderer/src/screens/conversation/threadScrollPosition.ts`** — three exports:
  - `ThreadScrollMetrics { scrollOffset, viewportHeight, contentHeight }` — a named-field object, not
    three positional numbers. Positionals of the same type transpose silently (`clientHeight` ↔
    `scrollHeight`), and the call site (#601's scroll handler) is untested reviewed glue under this
    repo's renderer test posture, so the argument names have to make the glue correct by inspection.
  - `AT_BOTTOM_TOLERANCE_PX = 4` — a bare `CONST_CASE` number (the `MAX_FRAME_BYTES` /
    `MAX_PASTE_LENGTH` precedent, no `as const`, no wrapper object), and the renderer's first exported
    *numeric* constant (the existing renderer constants are all copy strings). Fenced on both sides:
    above the ~1–2px accumulated sub-pixel error across three metrics at high DPR/zoom, well below one
    line of message text (`--text-body-medium-line: 20px`).
  - `isAtBottom(metrics): boolean` — one comparison. `distanceFromBottom = contentHeight - (scrollOffset
    + viewportHeight)`, at-bottom iff `distanceFromBottom <= AT_BOTTOM_TOLERANCE_PX`. No clamp, no
    `Math.max`, no "can it scroll at all" guard — every one of the five ACs (boundary both sides, true
    bottom, elastic overshoot, content ≤ viewport) falls out of that single quantity's sign/magnitude
    rather than a branch of its own.
- **`threadScrollPosition.test.ts`** — 7 cases (8 assertions), all using fractional metrics; the two
  boundary cases use halves/quarters (`1000.5 - (270.5 + 726) === 4` exactly) so they test the `<=`
  boundary rather than floating-point rounding.

No existing file is edited. No ref, no scroll listener, no effect — #601 owns all of that. No consumer
in this ticket by design; the sibling test is what proves it, not a call site.

## Patterns established

- **`ThreadScrollMetrics`/`AT_BOTTOM_TOLERANCE_PX`/`isAtBottom` is the shape a future DOM-derived pure
  helper should clone**: an object-argument interface (never positional same-typed numbers) whenever a
  transposition between two fields would produce a wrong answer with no type error, paired with a
  docstring that states which two fields are the transposition risk and why the call site can't be
  trusted to catch it.
- **A tolerance/threshold constant's docstring must fence the value on both sides with the concrete
  numbers that bound it** (not just assert "this is a reasonable default") — `AT_BOTTOM_TOLERANCE_PX`'s
  comment cites both the accumulated sub-pixel error estimate and the exact CSS token (`20px`) it must
  stay under, which is what stops a future edit from "tidying" `4` into an arbitrary value.
- **A single-quantity comparison beats per-case branches when every ticket AC is provably a sign/range
  of one expression** — confirmed here by code review's mutation-control check (stubbing `true`/`false`,
  flipping `<=` to `<`, or sign-flipping the distance each fails a specific, different test). Reach for
  this shape before adding a guard clause "for safety": an unexercisable branch is itself a defect this
  team routes back on rather than keeping.

## Lessons learned

(From the PR body's own "Lessons learned" section.)

- **This repo has no ESLint/Prettier config and no lint/format script.** `npx prettier --check` runs
  against Prettier's own defaults (double quotes, semicolons) rather than the repo's actual convention
  (single quotes, no semicolons, 2-space) — it flags every existing file, including untouched siblings
  like `dropQueuedMessage.ts`. Read `--check` output as noise; never run `--write`, which would reformat
  the whole repo against the wrong style.
- **Boundary assertions on fractional scroll metrics need binary-exact fractions, not arbitrary
  decimals.** Halves and quarters (`.5`, `.25`) are exact in IEEE-754 binary floating point, so
  `1000.5 - (270.5 + 726)` is exactly `4` — the "equal to the tolerance" case genuinely tests the `<=`
  boundary. A decimal like `1000.3` would have turned the same assertion into an unintended rounding
  test.

## Code review

PASS, one NIT: `threadScrollPosition.test.ts:22` uses `toBeLessThan(20)` for the tolerance's upper
bound, which is weaker than the spec's "well below 20" and would admit `19.99`. Purely documentary —
`toBe(4)` on the preceding line already pins the exact value, so this doesn't change runtime behavior.
Not worth a rework cycle. Reviewer independently recomputed all seven `isAtBottom` cases by hand,
confirmed mutation control (stub/flip/sign-flip each fail a distinct case), confirmed zero blast radius
(`isAtBottom|AT_BOTTOM|scrollTop|scrollHeight|clientHeight|TOLERANCE` greps clean outside the two new
files), and flagged one **forward-looking, non-blocking note for #601**: a `viewportHeight` of `0`
(measured before layout) reads as scrolled-away rather than at-bottom, so an initial pin taken from an
unlaid-out ref would silently no-op — belongs in #601's ref/effect wiring, not a guard added here.
