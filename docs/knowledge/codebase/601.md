# #601 — Keep the thread pinned to the bottom when it is already at the bottom

PR [#611](https://github.com/pyrycode/pyrycode-desktop/pull/611), commit `7bfef98`. Code review PASS, no changes requested. Second half of the #599 split — rides the `isAtBottom` helper merged by [[600]].

## What shipped

`ConversationScreen.tsx` gained a `useThreadScrollPin()` hook and one optional `scrollPin` prop on `Timeline`. No new file, no store change, no stylesheet edit — the entire feature is ~85 lines in one file plus a new e2e spec (`e2e/thread-scroll-pin.spec.ts`).

The mechanism, in order:

1. **A `useRef(true)` flag** ("following the bottom"), screen-local, never rendered. Written only by `.conversation__thread`'s own `onScroll` handler, which maps `scrollTop`/`clientHeight`/`scrollHeight` to `isAtBottom({ scrollOffset, viewportHeight, contentHeight })` (the merged #600 helper's only call site).
2. **A dependency-free `useLayoutEffect`** that runs after *every* render of `ConversationScreen` and sets `el.scrollTop = el.scrollHeight` iff the flag is still `true`. No dependency array is deliberate, not an oversight: the seven chrome elements (thinking/stall/api-retry/compacting/queued/interrupt/status-row) mount and unmount off four different store slices, and enumerating them would be exactly the fragile coupling to avoid.
3. **`Timeline` stays pure props-in/markup-out.** It gained one optional `scrollPin?: ThreadScrollPin` prop (bundling `ref` + `onScroll` into one value, applied on `.conversation__thread`) so the 30 pre-existing `<Timeline` render sites needed zero edits — the same optional-prop precedent as `now`.

## Why chrome can't un-pin the thread (AC4)

A chrome mount shrinks `clientHeight` while leaving `scrollTop`/`scrollHeight` untouched. Shrinking the viewport *raises* the maximum scroll offset, so the browser never clamps `scrollTop` and **no scroll `event` fires** — the `onScroll` handler simply never runs, so the flag can't be touched by a chrome mount. This is a structural guarantee, not a test-covered behavior, and it's the reason the dep-free layout effect is safe: it's idempotent (writing a `scrollTop` that's already correct fires no further scroll event, so there's no feedback loop) and StrictMode's double-invoke is a no-op for the same reason.

## The isomorphic-effect alias

```ts
const useThreadLayoutEffect = typeof document === 'undefined' ? useEffect : useLayoutEffect
```

`vitest.config.ts:27` runs the `node` environment (see [[renderer-tests-are-server-render-only]]) — React 18 logs `useLayoutEffect does nothing on the server` for every component reached via `renderToStaticMarkup`, and there are 33 `<ConversationScreen` render sites in the renderer test suite. This alias was reproduced as an actual observed warning (not a speculative guard) before being added.

## Testing — no unit test for the glue, by design

The hook and the re-assert are untested reviewed glue in the same sense as `ChannelInfoSheet`/`WorkspacePickerSheet` — the node-env renderer suite can't run effects or measure layout. All proof is the new `e2e/thread-scroll-pin.spec.ts`:

- **Test 1** (at-bottom stays at bottom): sends a message, then walks through `tool_use`, `session_transition`, `turn_state{thinking}`, and a second user echo, asserting the pin holds across every thread-item kind and across a chrome mount.
- **Test 2** (scrolled-up stays put): sets `scrollTop = 0` via `evaluate`, yields a `requestAnimationFrame` pair (see Lessons learned below), pushes a frame, asserts `scrollTop` is still exactly `0`.
- Both tests gate on `scrollHeight > clientHeight` (inside the shared `primeOverflowingThread` helper) before any pin assertion — without it, a thread shorter than its viewport would pass both assertions with no feature present at all.
- The e2e imports `AT_BOTTOM_TOLERANCE_PX` from the production module and asserts the **raw** pixel distance, not `isAtBottom` itself — so a spec that transposed its own metrics couldn't agree its way past production code that transposed identically.

## Patterns established

- **Bundle DOM handles that must be wired together into one optional prop**, not two. `ThreadScrollPin { ref, onScroll }` makes "wired the ref, forgot the handler" unrepresentable — stronger than the `now`-style single optional value precedent it otherwise copies.
- **A dependency-free layout effect is the correct tool when the trigger set is open-ended** (arbitrary sibling chrome mounting/unmounting) and the effect body is idempotent. Enumerating triggers in a dep array would silently rot the moment an eighth affordance lands.
- Screen-local `useRef` (not `useState`) is correct whenever a value is read only by an effect/handler and never drives markup — avoids a full re-render on a frame-rate event stream.

## Lessons learned (from PR body)

- **A programmatic `scrollTop = 0` assignment does not settle before the next round trip.** The DOM `scroll` event it queues only dispatches at the next "update the rendering" step, which an in-process Noise round trip can outrace. The e2e test yields one `requestAnimationFrame` pair (`settleScrollEvent`) before pushing the next frame — otherwise it asserts against a flag the operator's scroll hadn't moved yet. Flagged by code review as a real, currently-unobserved property of *every* scroll-event-based chat pin (not just the test): a delta committing inside that sub-frame window during a real wheel-scroll-away could yank the view once, self-correcting on the next scroll event. Recorded because [[602]] and [[603]] scroll programmatically and inherit the same ordering — their `settleScrollEvent`-equivalent rAF pair is not optional.
- **`--screenshot` is a Playwright *config* option, not a CLI flag.** `playwright test --screenshot=on` exits `unknown option`; because `npm run e2e` chains after `npm run build`, the build succeeds first and the failure reads at a glance like a passing run with a trailing error. Capture from inside the spec instead.
- **`codegraph_callers` does not resolve JSX render sites as callers** — returned zero results for both `Timeline` (31 actual render sites) and `isAtBottom` (1 actual call site). Component/function fan-out for a prop or call-site change has to be counted by grep, not codegraph, in this repo. Corroborates the same gap noted in [[thread-scroll-pinning-599-family]].

## Closed, not deferred

- `overflow-anchor` stays unset — closed as indifferent on an **observed run** (no jump appeared that the re-assert failed to correct), not just on reasoning as the architecture doc proposed. If a mystery jump is ever observed, `overflow-anchor: none` on `.conversation__thread` is the documented remedy, filed as its own ticket with a reproduction.
- `flex-direction: column-reverse` was not reconsidered — still off the table per the #599 split rationale.
