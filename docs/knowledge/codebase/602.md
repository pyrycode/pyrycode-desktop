# #602 — Scroll the thread to the bottom when the operator sends a message

PR [#615](https://github.com/pyrycode/pyrycode-desktop/pull/615), commit `ab321ff`, spec commit `ce784a5`. Code review PASS, one non-blocking NIT (see below). Not security-sensitive — no wire/store/stylesheet change. Third child of the [[599]] split: [[600]] (helper) → [[601]] (conditional pin) → **#602 (this)** → #603 (open at bottom, pending).

## What shipped

One production file, one assignment, and the wire that carries it:

- `useThreadScrollPin()` widens its return from the bare `ThreadScrollPin` DOM bundle to `{ scrollPin, followBottom }` (a new file-local `ThreadPin` interface). `followBottom` is a single statement — `following.current = true` — no measurement, no `scrollTop` write of its own.
- `Composer` gains a **required** `onMessageSent: () => void` prop (the opposite call from `Timeline`'s optional `scrollPin?` — `<Composer />` has exactly one render site in the repo and is not exported, so requiring it costs no edit cascade and makes "forgot to wire it" a compile error).
- `ConversationScreen` wires `<Composer onMessageSent={followBottom} />` and calls `onMessageSent()` from inside `handleSubmit`'s existing `if (sent) { setText(''); onMessageSent() }` branch — not at the top of the function, not just past the `!canSend` gate.

`Timeline` is untouched; its 30 other render sites and the `ThreadScrollPin` type stay exactly as [[601]] shipped them.

## Why placement inside `if (sent)` is the whole mechanism

`sent === true` already means "a message entered the timeline" — both of `submitMessage`'s `false` returns (`composerSend.ts:47-48`, whitespace-only input and null conversation id) sit above its echo dispatch, and the bridge `catch` (`:60-63`) falls through to the dispatch and still returns `true`. So:

- A submit that sends nothing (not connected, whitespace-only, no active conversation) never reaches `onMessageSent()` — it leaves the scroll position exactly as the operator's own scrolling set it, and critically leaves **no armed pin behind** for the next unrelated arriving item to yank.
- A send whose bridge call throws still posts the optimistic echo and still jumps — correctly, since the timeline did move.

No new predicate was written to distinguish these cases; the existing `sent` boolean already carries the fact.

## Why one assignment is enough for both "jump now" and "stay pinned"

[[601]]'s re-assert layout effect has no dependency array, so it runs after *every* render. `submitMessage` dispatches the echo into the store before `followBottom()` runs, and the app mounts through `ReactDOM.createRoot` (`main.tsx:6`), so React 18 automatic batching means the store update flushes only once `handleSubmit` returns — there is no re-render point inside the synchronous handler body. So the sequence is: echo dispatched → flag armed → handler returns → React renders the new item → the layout effect reads `following.current === true` and scrolls before paint. That single fact, read at two different times, is the jump (first post-echo render) and the pin (every subsequent render while the reply streams) — no second mechanism, no sticky/turn-scoped lock. If the operator scrolls up mid-stream, `onScroll` still writes `false` exactly as before ([[601]] unchanged).

An immediate `scrollTop` write inside `followBottom` itself was considered and rejected — it would defend an ordering (the echo's render landing before the assignment) that cannot occur under `createRoot`'s batching, and would be a redundant write to a container whose content hasn't grown yet.

## Testing

No unit test, no renderer test edit — the renderer suite is `renderToStaticMarkup` in vitest's `node` environment (see [[renderer-tests-are-server-render-only]]); effects never run. `composerSend.test.ts` needed no change (`submitMessage`'s contract is unchanged).

A third `test(...)` appended to the existing `e2e/thread-scroll-pin.spec.ts` (no new spec file — every helper already existed): prime an overflowing thread, scroll to the top, `settleScrollEvent`, assert `scrollTop === 0` as a precondition, send a third message, assert pinned-to-bottom after the echo (2 user bubbles), then stream a reply the operator didn't ask for across two arrivals (delta + `turn_end`) and assert pinned-to-bottom after each. Test 2 (`:281-307`, the "arriving item leaves scroll unchanged" regression target) was **not edited**, confirmed both by design (nothing in this change reacts to an item arriving, only to a submit) and by code review re-reading the diff.

RED-first: the new test failed at the post-send pin assertion against the whole overflow (775px vs the 4px tolerance) before the fix, with the `scrollTop === 0` precondition passing — a real non-vacuity signal, not a guess.

## Lessons learned (from PR body)

- **The rAF-settle hazard inverts between the two scrolled-up tests.** [[601]]'s test 2 needs `settleScrollEvent` or a *correct* app fails; this ticket's new test needs it or a *broken* app passes — skip it and the flag is still `true` when the send lands, so the view reaches the bottom with no feature present at all. Same helper (`settleScrollEvent`), opposite failure direction — a reviewer can't carry the first test's reasoning across to the second without checking which way it points.
- **`sent === true` already means "a message entered the timeline"**, so no new predicate was needed to separate a real send from a no-op one. Arming anywhere earlier (e.g. right after the `!canSend` gate) would have required re-deriving `submitMessage`'s whitespace/null-conversation gate a second time, and getting that copy wrong leaves an armed-but-unspent flag whose failure surfaces one beat late — on the *next* unrelated arriving item, not on the send itself.
- **Required vs. optional prop is a fan-out question, not a style one.** `Composer` has exactly one render site and is not exported, so requiring `onMessageSent` makes "forgot to wire it" a compile error at zero cost. `Timeline`'s `scrollPin?` stays optional for the opposite reason: 30 existing render sites made optional the only non-cascading choice there.

## Code review note (non-blocking)

The fourth criterion (a no-op submit leaves no armed pin behind) has no live test — it's structurally guaranteed by the `if (sent)` placement rather than test-covered, and code review confirmed the guarantee by reading rather than gating on it. Flagged as a NIT, not a SHOULD FIX: an explicit fourth test (fill whitespace at the top, click Send, push a `tool_use` frame, assert `scrollTop` still `0`) would cost ~10 lines reusing existing helpers, but the spec's Testing strategy considered and deliberately stopped short of it — an architect-scope call, not developer rework.
