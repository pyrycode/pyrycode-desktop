# #603 — Prove re-opening a discussion lands at the most recent messages

PR (branch `feature/603`), commit `68dcb28`. Spec commit `e53c3a0`. Not security-sensitive. Last child of
the [[599]] thread-scroll-pinning family: [[600]] (helper) → [[601]] (conditional pin) → [[602]]
(send-forces-pin) → **#603 (this, closes the family)**.

## What shipped

**Zero production code.** One test, 71 lines, appended to `e2e/thread-scroll-pin.spec.ts`. The PR body
states this explicitly per AC5.

The ticket's original premise — "opening a conversation shows the top of the history, scroll to find the
live end" — did not survive PO refinement: this app has no history backfill (`buildClientHello` never
sends `last_seen_ts`; the timeline's only writers are the live stream and the composer's echo), so opening
a *different* discussion always starts from an empty `.conversation__empty`, no scroll node at all. The
only reachable form of the user story is **re-entry**: open a discussion, let it overflow, scroll away,
leave via Back, come back to the *same* discussion.

That guarantee already held on `main`, but as an emergent side effect of three independent facts, none of
them added for this case:

1. `activateConversation` resets the timeline only when the active conversation **id** changes
   (`activateConversation.ts:74-77`) — re-opening the same seeded row keeps every row.
2. `PairedShellView` returns a *different component type* at the same tree position when Back flips the
   route to `list` (`PairedShell.tsx:88-97`), so React destroys the `ConversationScreen` subtree —
   `following`'s ref is discarded, `.conversation__thread` is rebuilt with `scrollTop = 0`.
3. `following` starts `true` and the dep-free layout effect (ADR [[0006]]'s screen-local `useReducer`/`useRef`
   discipline) pins before paint on the very first render, because the rows are already in the store when
   the fresh screen mounts.

The new test drives the full round trip against the built app and asserts all three survive together:
prime an overflowing thread, scroll to the top, `settleScrollEvent`, assert the precondition
(`scrollTop === 0`), click `.conversation__back`, await the channel list, re-click
`.channel-list__row-open`, then assert — in order — the row count and last-bubble text are unchanged (same
conversation, no reset), the re-entered thread still overflows its viewport (non-vacuity, read fresh on
the *re-entered* node, not the primer's), `expectPinnedToBottom`, and finally that one further pushed
`tool_use` frame leaves it pinned with no manual scroll (AC3 — pinned, not merely positioned).

## Mutation control (AC4)

Required control, `ConversationScreen.tsx:347` `useRef(true)` → `useRef(false)`: fails at the
non-vacuity/pin assertion as expected, recorded in the PR. Confirmed collateral against the file's other
tests, as anticipated by the spec.

## Patterns established

- **A ticket whose premise doesn't hold gets its scope rewritten around the one reachable case, not
  force-fit onto the original wording.** The PO's rewrite here ("re-entry" replacing "open at bottom") is
  the reusable move; verify a body's load-bearing claims against the current code before designing against
  them.
- **An emergent guarantee (three independent choices happening to compose correctly) is worth converting
  into a locked test even when no production line changes.** The three facts above could each be edited in
  isolation by an unrelated future ticket without anyone noticing this broke; the test is what makes that
  regression visible.

## Lessons learned (from PR body)

- No production lessons — the spec's own reasoning (documented inline in the test's comments) is the
  deliverable. The `settleScrollEvent` hazard direction it relies on is the same one [[601]] and [[602]]
  already recorded: skipping it before the top-park would leave a broken app (flag surviving the remount)
  passing vacuously, because the queued scroll event hadn't yet cleared `following`.
