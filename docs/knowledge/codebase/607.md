# #607 — Preserve newlines and paragraph breaks in assistant messages

PR [#614](https://github.com/pyrycode/pyrycode-desktop/pull/614), commit `4538228`. Code review PASS, one non-blocking NIT (assertion ordering in the e2e spec, not a production defect). Not `security-sensitive` — a stylesheet declaration only, no parsing, no HTML sink. The whitespace half of #598, split alongside #608/#609/#610 (markdown rendering).

## What shipped

Two production edits:

1. `conversation.css` — a new `.bubble--assistant-text { white-space: pre-wrap; }` rule, placed immediately after `.bubble--daemon`.
2. `ConversationScreen.tsx:457` — `bubble--assistant-text` appended to the assistant-text bubble's className, so the string stays `"bubble bubble--daemon bubble--assistant-text"` (append-only, keeps the pre-existing `toContain('bubble bubble--daemon')` unit assertion matching).

No component structure change, no wrapper around `{item.text}`, no store/wire change — daemon text already carried its newlines intact through the codec and `threadTimeline.appendDelta`; only rendering discarded them.

## Why a new modifier, not `.bubble` or `.bubble--daemon`

`.bubble` reaches `.bubble--user` too and would collapse the last AC (user bubble must stay unchanged). `.bubble--daemon` reaches the four chrome affordances (thinking/stall/api-retry/compacting) — visually inert there today since all four are single-line client-owned constants with no newline or space run, but "inert because we read four string literals" needs re-verifying every time a fifth affordance is added. A dedicated `.bubble--assistant-text` modifier makes that AC true by construction instead: the rule provably cannot reach an element that doesn't carry the class. A `data-thread-role='assistant'` attribute selector was also considered and rejected — every existing attribute selector in this stylesheet is `aria-*`; styling off a role/test marker would be a new precedent, not a fit for the `.bubble--<variant>` idiom already used by `--thinking`/`--stall`/`--api-retry`/`--compacting`.

## Why `pre-wrap`, uniquely

The three positive ACs form a decision table that leaves exactly one CSS value:

| AC | eliminates |
|---|---|
| blank line renders as a visible break | `normal` |
| space runs and indentation survive | `pre-line` |
| long unbroken token still wraps, no h-scroll | `pre` |

`break-spaces` was considered and rejected too: unlike `pre-wrap`, it pushes preserved spaces onto the next line instead of hanging them, which would let a run of daemon-supplied spaces contribute to the bubble's intrinsic width. `word-break: break-word` (`conversation.css:298`) was already on `.bubble` and carries the long-token AC; it was confirmed, not restated.

## Testing — two tiers, deliberately different fabric

Renderer unit tests run `renderToStaticMarkup` in vitest's `node` environment (see [[renderer-tests-are-server-render-only]]) — no DOM, no stylesheet, so a whitespace-*rendering* assertion isn't expressible there. The unit tier (`ConversationScreen.test.tsx`) pins only the markup fact: the class is appended in the right order, a settled item's text sits flush between the opening tag and the cursor/closing tag (any stray JSX whitespace would become visible under `pre-wrap`), the text survives byte-for-byte into markup, and five `not.toContain('bubble--assistant-text')` guards prove the four chrome affordances and the user bubble are structurally unreached.

The e2e tier (new `e2e/assistant-whitespace.spec.ts`, cloning `thread-scroll-pin.spec.ts`'s `locator.evaluate()` idiom) pins the layout fact, streaming four distinct turns (control / blank-line paragraph / 24-space run / ~200-char unbroken token) and asserting computed `white-space` plus geometry (height delta, width, `scrollWidth` vs `clientWidth`) — never `toHaveText`, which hardcodes `normalizeWhiteSpace: true` on both its string and regex branches and would pass identically before and after the fix. See [[playwright-tohavetext-normalizes-whitespace]] (recorded from #607's spec work).

## Patterns established

- **A CSS rule scoped to a decision-table-derived value gets its own modifier class**, not reuse of the nearest existing one, whenever "the shared class is currently inert for the other elements it reaches" is the only thing keeping a broader AC true — reuse makes that AC an argument that has to be re-checked on every future addition; a dedicated class makes it structural.
- **A geometric/computed-style e2e assertion is the only valid detector for a whitespace-rendering AC** in this repo — `toHaveText` (and `useInnerText` generally) normalizes whitespace on both matcher branches, so any text-content assertion is vacuous for this class of change.

## Lessons learned (from PR body)

- Placing a computed-style assertion first in a multi-assertion e2e test short-circuits the geometric assertions behind it — a mutation run under a wrong CSS value (e.g. `normal`) fails on `whiteSpace` alone and never exercises the height/width assertions, so a single mutation pass proves less than it looks like. Verifying the geometric assertions were non-tautological needed a second mutation pass with the computed-style check disabled — which is what surfaced `pre-line`'s exact signature (newlines kept, space runs still collapsed). Code review flagged the same ordering as a NIT (not blocking): `expect.soft` or reordering the behavioral assertions ahead of the computed-style one would make a future regression report all three facts at once instead of stopping at the first.
- The design (Figma `16:43`) separates blocks inside one reply with an 8px gap; this plain-text rule gives a preserved blank line a full 20px line box instead. Reaching the 8px treatment needs block-level parsing — that's #609's markdown work, flagged in the architecture spec's open questions rather than treated as a fidelity miss here.

## Trap this ticket fixed in a sibling file

`e2e/thread-scroll-pin.spec.ts:57-62`'s comment justified streaming separate turns (rather than newlines inside one turn) partly on "`.bubble` sets no `white-space: pre-wrap`, so a newline buys no height at all" — that clause is now false. Amended in the same commit to lead with the reason that still holds (same-turn deltas coalesce into one bubble via `threadTimeline.appendDelta`, so newlines would grow one bubble instead of the row count that spec varies) and to note in-line that #607 changed the other premise. The spec's own streamed turns were not changed.
