## Verified construct coverage

Confirmed via the 13 test cases against `react-markdown@10.1.0` on the repo's actual `react@18.3.1`, not recalled from docs: `#`/`##` and setext headings → `<h1>`/`<h2>`; `**bold**` → `<strong>`; `*ital*` → `<em>`; `` `code` `` → `<code>`; fenced blocks → `<pre><code>`; ordered/unordered lists → `<ol>`/`<ul>`; `>` → `<blockquote>`; paragraphs → `<p>`; both hard-break forms (trailing two spaces, trailing backslash) → `<br/>`. Reference-style links (`[label][ref]`) and autolinks (`<https://example.com>`) get the same no-anchor treatment as inline links — each its own test case, not assumed to inherit from the inline-link override.

## Patterns established

- **A markdown/HTML rendering boundary earns a single-file, comment-as-contract treatment**: the production file is almost entirely a header comment stating that its configuration *is* the security boundary and any change to it is a security change — not incidental documentation, load-bearing for future editors. Precedent for any future untrusted-content rendering path in this repo.
- **Element-level suppression over policy-level suppression, when both are available.** Both AC3 (no anchor) and AC4 (no `<img>`) could theoretically lean on the CSP (no `img-src`) or `urlTransform` (blanks `javascript:`), but the design does neither — no anchor or image element is *constructed* at all. The CSP remains as an independent second layer, deliberately "different fabric" (deterministic policy vs. this module's stochastic-adjacent parsing), not a substitute.
- **Capability-absent beats capability-disabled** as the standing tie-breaker when choosing a dependency for a security-relevant path, even against a materially smaller alternative — see [ADR 0010](../decisions/0010-markdown-renderer-capability-absent-html.md).

## Lessons learned (from code review)

- **The architecture spec's "85 packages added" is not the number to cite.** Code review re-measured with an honest `comm -23` set difference between the pre/post lockfile package lists and got **79 net-new**. Two other numbers looked plausible and were both wrong: `npm install`'s own summary line ("added 256") was junk because the review's worktree had an *empty* `node_modules` directory that `ls`+`&& echo` reported as "present"; and a naive `grep -c '^+.*node_modules/'` over the lockfile diff gave an inflated 89, because npm re-sorts lockfile entries on install, so roughly 10 packages appear as both a removed and an added line for what is really the same version. When a PR's dependency-count claim matters (as it does here, since it's the entire justification a human reviewer reads), recompute it with a set difference rather than trusting any single tool's summary line.
- **Lockfile review must check version-drift, not just line-count.** The review confirmed the 79 net-new packages had zero changed versions among the four pre-existing runtime deps (added/removed/changed = 79/0/0) — a lockfile diff that *also* silently bumped an unrelated existing dependency would have been a separate finding, distinct from "how many new packages arrived."
- **A "capability-absent" claim must be checked against the locked tree, not the configuration.** The review grepped the actual installed lockfile for `rehype-raw`/`hast-util-raw`/`parse5`/`remark-gfm` and confirmed none were present — config (`rehypePlugins` absent) only proves the capability is *disabled*, which is exactly the weaker property this design was chosen to avoid relying on.
- **Run the mutation table on every negative-only AC.** Every acceptance criterion in this ticket is phrased as a negative ("no anchor," "no `<img>`," "HTML not interpreted"), each individually satisfiable by rendering nothing at all. The review mutated the implementation four ways and confirmed each broke exactly the tests it should: spreading `{...props}` on `a` → 4 failures, on `img` → 2 failures, setting `skipHtml: true` → 2 failures (correctly *not* the ampersand-escaping case, which is unaffected by that flag), stripping the `language-*` class → 1 failure. A positive assertion can also pass without discriminating anything: the reference-link fixture `[label][ref]` with no matching `[ref]:` definition would render as the literal text `[label][ref]`, and all three of that case's assertions (contains "label", no anchor, no URL) would still pass with the reference-resolution path entirely dead — the review confirmed the fixture does include the definition and that a real anchor-suppression, not a parse failure, is what's under test.
- **The `<img onerror>` fixture must never assert `not.toContain('onerror=')`.** The tag survives as escaped *text*, so `onerror=` is legitimately present in the output as characters — asserting its absence would be asserting something false about a passing, correct implementation. The fixture instead pins the exact escaped string `&lt;img src=q onerror=alert(1)&gt;`.
