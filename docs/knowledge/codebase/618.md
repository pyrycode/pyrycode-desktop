**Comment re-anchoring** was the one piece of real design work. Four live comments cited the removed
view, container or classes as their design precedent — the ticket body named three, and the spec
found the fourth by grepping the removed names rather than working the body's list:

1. `ConnectionStatusIndicatorControl` ("the `ScreenSnapshotControl` two-store precedent") →
   `QueuedBacklogControl`, the surviving container reading two stores through narrow selectors.
2. `.bubble__markdown pre` (#609, citing `.screen-snapshot__screen` as the *anti*-precedent) →
   `.unrecognized-row__raw`, which carries the identical bounded-scroll treatment.
3. `.unrecognized-row__raw` itself (previously "`.screen-snapshot__screen`'s treatment") — the ticket
   body's claim that this had a live sibling to point at was wrong; after the removal it's the only
   bounded-scroll `<pre>` left in the file (the other `max-height` rules are `90%` dialog/sheet
   bodies, a different pattern), so it now states its treatment directly instead of citing one — and
   becomes the anchor re-anchor 2 points at. That ordering is what leaves no dangling name.
4. `.background-task-trigger` ("the `.screen-snapshot__request` treatment") → `.conversation__back`,
   *not* `.conversation__unpair` — the tempting move, since `.screen-snapshot__request`'s own comment
   credited `.conversation__unpair`, but that selector carries no `align-self` at all and was only
   ever the precedent for the de-emphasized text-button look, not the self-align.

## Patterns established

- **A removal's stale-comment sweep must be scoped by grepping the deleted names, not by working the
  ticket body's enumerated list.** The body named three re-anchor sites; the fourth (`conversation.css:365`,
  written by the immediately preceding ticket #609) wasn't in it. A list in a ticket body is a
  starting point, not the boundary of the search.
- **"Each pattern has a live sibling to point at" needs verifying against the cited property, not just
  the cited relationship.** Two ways this failed here: `.unrecognized-row__raw` turned out to have no
  sibling at all (it had to become the origin instead), and the tempting `.conversation__unpair`
  target for re-anchor 4 doesn't actually carry the `align-self` the comment needs — it's precedent
  for a different property entirely. Check the property is really there before pointing a comment at it.
- **A re-anchored comment's direction word (`above`/`below`) needs checking independently of the name
  swap.** #609's comment said the anti-precedent was "below" it; the new target happened to still be
  below, but that was proven, not assumed.

## Lessons learned (from the PR body and code review)

- **Checking a re-anchor target must verify the property actually cited, not just the relationship a
  neighboring comment implies.** `.screen-snapshot__request`'s own comment credited
  `.conversation__unpair` for the self-align idiom, which made it the tempting swap for
  `.background-task-trigger`'s re-anchor — but `.conversation__unpair` carries no `align-self` at
  all, only the de-emphasized-button look. Verifying the target holds the cited CSS property (not
  just following the citation chain) is what caught it.
- **`e2e/` sits outside both tsconfigs, so `npm run typecheck` cannot see a Playwright spec.** Every
  stranded import, fixture and helper in `stall-bundle.spec.ts` had to be found by reading and
  confirmed by actually running the spec — a green unit suite and a green build prove nothing about
  that file. (Independent re-confirmation of a gap [#609](609.md) also hit.)
- **Control characters typed into a comment fix land as raw bytes, not escapes** — not hit on this
  ticket, but the direction-word check above is the same class of "verify the literal text, don't
  assume the swap preserved meaning" discipline the repo's memory already flags for other contexts.
