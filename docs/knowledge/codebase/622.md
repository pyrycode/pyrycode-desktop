## Design in one paragraph

`Envelope.type` is `EnvelopeType | string` — an open union — so deleting `screen_snapshot` from the
modeled set does not make an inbound frame of that type unrepresentable or fatal; it falls through to
the tolerant `default` arm, which logs it content-free (`inbound-unmodeled`) and returns `null`. The
removal is therefore **behaviourally inert** except for one diagnostic-log detail, and the ticket's
actual deliverable is the **test that pins that tolerance** rather than assuming it — a client that
crashed on an unexpected wire type would be a worse failure than the one being removed.

## Patterns established

- **A modeled-arm removal on an open union is a routing change, not a representability change — pin the
  fallback, don't assume it.** `default` already existed and already tolerated unknown types; the new
  coverage proves *this specific* type lands there without throwing, both well-formed and malformed.
  Generalizes to any future `EnvelopeType` member removal on this decoder.
- **Deleting a fail-closed parser can invert an existing "does NOT log on the throw path" test rather
  than obsolete it.** The malformed `screen_snapshot` `it` at `inboundMessage.test.ts:3246` (old)
  asserted zero log lines on the throw path; post-removal there is no throw, so the frame *does* log.
  The new pin asserts the **resulting indistinguishability** as a property — capturing both the
  well-formed and malformed records and comparing them to each other (equal on `event`/`code`/key set,
  differing only in `bytes`/`hash`) — rather than asserting either record in isolation. That framing
  states the diagnostic cost of the removal directly, and is the more honest assertion whenever a
  removal moves a frame from a fail-closed path onto a tolerant one.
- **When retitling/repurposing a retained test after a removal, name what it now *uniquely* proves, not
  what it used to test.** The oversize `it` at `inboundMessage.test.ts:680` used a `screen_snapshot`
  envelope only as its vehicle — it was always proving `MAX_PLAINTEXT_BYTES` runs frame-level, before
  the type switch. After this removal it became the **only** oversize test in the file using an
  unmodeled envelope type (all ~12 siblings use modeled types), so it's now the sole proof that an
  oversized frame of an *unrecognised* type still fails closed. Retitled to state that ordering claim.
  A removal sweep that deletes a whole describe block wholesale can silently drop a test that was never
  really about the thing being removed.
- **An anti-leak log assertion tied to a specific arm must be carried forward when that arm's traffic
  moves to a different logging path, not deleted with the arm.** `inboundMessage.test.ts:3227`
  (`SECRET_TEXT` never appears in the log) was the file's only log pin whose frame carried sensitive
  content — every sibling `default`-arm pin uses `type: 'ack'` with an empty payload and has nothing to
  leak. Rewritten onto the unmodeled path rather than deleted.
- **Comment triage on a removal: "describes-the-removed-thing" dies with it; "cites-it-as-precedent-for-
  surviving-code" is left dangling for a dedicated sweep ticket.** `inboundMessage.ts:1305`'s "Mirrors
  the screen_snapshot arm above" (on the immediately-following `session_settings` arm) is the highest-
  collision-risk example — it sits directly under the diff and looks like this ticket's mess, but
  belongs to [#635](https://github.com/pyrycode/pyrycode-desktop/issues/635)'s single-pass tail sweep.
  Re-anchoring it here would reopen the file twice.
- **Prove a claimed "deletions only" diff, don't just assert it.** The spec required the production diff
  add zero statement lines outside a doc rewrap; PR#641 reports the final shape as exactly that (two
  added lines, both comment). Confirms code-review's routed finding from #621 continues to hold here.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **Deleting a modeled arm can silently delete an anti-leak assertion along with it.** Worth asking on
  any arm removal: does a test attached to this arm prove something about the *class* of frame (e.g.
  "sensitive content never leaks") rather than the arm's specific mechanism? If so it needs a new home,
  not a deletion.
- **Removing a fail-closed parser inverts its "does NOT log on the throw path" pin rather than obsoleting
  it.** Asserting the resulting two records against each other is stronger than asserting each alone.
- **The base-commit control paid off a second time** ([#621](621.md) established this same lesson): the
  real-daemon gate's one failure looked like a regression until stash → rebuild → rerun reproduced it
  byte-for-byte on the base tree, unrelated to this diff.

Two further dangling citations were found and left standing (not in the spec's enumerated list, but
matching its own cites-it-stays rule, since both name the removed **kind/wire verb** rather than an
export): `inboundMessage.ts:97` ("Unlike `snapshot`, the assistant delta `text` IS the render payload")
and `types.ts:249` ("unlike `screen_snapshot.text` it is NOT dropped downstream"). Flagged for #635's
handoff list alongside the three sites #621 already flagged.
