# #628 — Size an assistant reply's markdown headings from the type scale

Commit `c96da16` on `main`. Not `security-sensitive` (CSS-only; never touches `AssistantMarkdown.tsx`,
#608's markdown security boundary). Split from #624 (heading/list/blockquote/inline-code type scale)
alongside #629 (nested-content margin reset) and #630, following [#623](623.md) (fenced code block chrome).

## What shipped

One production file, `conversation.css`, +71 lines, no markup change:

- Four descendant-selector rules under `.bubble__markdown`, giving `h1`–`h6` an explicit type quartet
  (`font-size` / `line-height` / `letter-spacing` / `font-weight`), each level taking all four from a single
  type-scale token step rather than falling through to the UA stylesheet's `2em..0.67em` at `bold`:
  - `h1` → `headline-small` (24/32/0/400)
  - `h2` → `title-large` (22/28/0/400)
  - `h3`, `h4` → `title-medium` (16/24/0.15/500)
  - `h5`, `h6` → `label-large` (14/20/0.1/500)
- Placed immediately after `.bubble__markdown pre` (the descendant-selector precedent it follows) and
  before `.code-block`, keeping the container's own rules contiguous.
- Descendant selectors, not `>`, so a heading nested in a blockquote or list item is sized too — but such a
  nested heading is not a direct child of `.bubble__markdown` and so still keeps its UA `margin-block`; that
  leftover reset is explicitly left for #629, shared with nested paragraphs/lists.
- No `margin`, `color`, `font-family`, `word-break` or `display` declared — each omission is documented
  inline as load-bearing (margin: `.bubble__markdown > *` already zeroes it for direct children and #629
  owns the nested case; color: inherits `--color-on-surface` from `.bubble--daemon`; font-family: inherits
  `--font-sans` from `.conversation`; word-break: inherited from `.bubble`, #607's precedent; display: block
  by tag, blockified/stretched as a flex item regardless).

One e2e test added to `e2e/assistant-whitespace.spec.ts` (+73 lines), no new fixture, no new turn in the
reply stream. A `readHeadingTypeMetrics` helper resolves `.bubble__markdown h2` inside the existing `RHYTHM`
bubble and reads, in one `locator.evaluate()`, both the element's computed type quartet and the four
`--text-title-large-*` custom properties off that same element at runtime — then asserts they're equal.
Reading the expected values from the live custom properties (rather than writing `22px`) keeps the spec
literal-free, mirroring how `readRhythmMetrics` reads `--space-2` instead of a bare `8`. A small
`normal` ↔ `0px` letter-spacing normalizer handles Blink serializing zero tracking as the keyword on one
side and `0px` (the token's literal value) on the other. One level of six (`h2`) is exercised — sufficient
to prove the class of failure that matters (a heading typed by the browser, not the theme); adding another
level would require a new turn, which the stream's positional indexing (`CONTROL / SPACE_RUN / CODE / RHYTHM
/ TAIL`) forbids without shifting every existing index.

`AssistantMarkdown.test.tsx` and `ConversationScreen.test.tsx` were left untouched — server-render tests
can't see computed size, and their attribute-free `'<h1>Heading one</h1>'` / `'<h2>Heading two</h2>'`
assertions already guard the CSS-only constraint this ticket depends on.

## Patterns established

- **Which four scale steps to use, and how to group six levels onto them, was settled by a census of the
  renderer's own existing usage of each step — not by picking the "nearest" size.** `headline-small` /
  `title-large` / `title-medium` / `label-large` are exactly the renderer's pre-existing title vocabulary
  (five dialog/screen titles, two screen titles, the two `title-medium` consumers, and
  `.settings__section-header`); `body-large`, though it also sits above body-medium, was excluded because
  all fourteen of its consumers are row-body text, none a heading — including one deceptively named
  `.run-config__yolo-title`, which is a `<p>` label, not a title. The generalizable move: when a type-scale
  choice is ambiguous by size alone, resolve it against how the codebase already uses each step for the
  *role* in question, and treat a name like `*-title` in a class as a false precedent until you've read what
  element it's actually on.
- **A heading's step follows its semantic role, not its tag** — precedent already existed in this app
  (`<h2>` is `headline-small` in four dialogs, `label-large` in settings), which is what licenses collapsing
  `h3`+`h4` and `h5`+`h6` onto shared steps rather than inventing two more.
- **A computed-style e2e assertion can be made literal-free by reading both sides off the same live
  element** — comparing `getComputedStyle(el)` against `getComputedStyle(el).getPropertyValue('--token-*')`
  read on that same node, rather than against a hand-typed expected value. This both proves the rule reached
  the element and proves its values trace to the scale rather than to a duplicated literal, and it's the
  same idiom `readRhythmMetrics` already used for spacing.

## Lessons learned

- Two of the ticket's five ACs (AC3 no-horizontal-scroll, AC4 the 8px rhythm) needed zero new test work,
  established in the architecture spec before implementation started: `assistant-whitespace.spec.ts` already
  measures both against the `RHYTHM` turn's `<h2>`/`<ul>` blocks, and a larger `font-size`/`line-height`
  cannot move `readRhythmMetrics`' gap measurement (`rect.top - previous.bottom` on border boxes) — only an
  added margin could, and this ticket adds none. Worth re-checking on any future ticket that only changes
  type size/weight inside an already-instrumented container: the existing box-geometry tests may already
  cover it for free.
- `conversation.css` keeps compounding as a single append-only file across #607/#609/#623/#628 — each
  ticket's own comment block documents its own reasoning inline (why a step, why an omission), which has so
  far kept the file legible despite the size, but any future ticket relying on a line-number anchor into it
  should expect the anchor to be stale before the work starts (true again this ticket: `.bubble--thinking`
  moved to `:486` per #623's note, and this ticket's own insertion shifts everything below it again).
