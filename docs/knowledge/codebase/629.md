# #629 — Indent an assistant reply's lists and blockquotes within the bubble measure

Commit `52d1017` on `main` (spec `2ea4024`, PR #632, code review PASS with two non-blocking NITs). Not
`security-sensitive` (CSS-only; never touches `AssistantMarkdown.tsx`, #608's markdown security boundary —

type scale) alongside [#628](628.md) (heading type scale, merged first) and #630 (inline code, not yet

## What shipped

Two files, no markup change — `AssistantMarkdown.tsx` is untouched.

**`conversation.css`, +95 lines.** Four rules under `.bubble__markdown`, replacing the last two markdown
constructs the UA stylesheet still laid out:

- `.bubble__markdown ul, .bubble__markdown ol { padding-inline-start: var(--space-4) }` — trades the UA's
  40px for 16px, a **descendant** selector (not `>`) so a list nested inside a blockquote or list item is
  reached at every depth.
- `.bubble__markdown blockquote { margin-inline: 0; padding-inline-start: var(--space-3); border-left: 4px
  solid var(--color-outline) }` — trades the UA's 40px-each-side margin for a 16px-equivalent indent (the
  4px bar plus `--space-3`) plus a leading accent bar, the idiom this file already carries four times
  (`.conversation__banner`, `.bubble--stall`, `.bubble--compacting`, `.modal-rejection`), in the neutral
  `--color-outline` role rather than the `--color-error`/`--color-primary` status vocabulary those four own.
- `.bubble__markdown li > *, .bubble__markdown blockquote > * { margin-block: 0 }` plus
  `.bubble__markdown li > * + *, .bubble__markdown blockquote > * + *, .bubble__markdown li + li {
  margin-block-start: var(--space-2) }` — a reset/owl pair, both `>` (own children only, so the step applies
  once per level rather than compounding down the tree), that **establishes** the container's 8px rhythm one
  level down rather than merely uncovering it. `.bubble__markdown > *` (#609) is direct-child only and never
  reached a `<p>` in a blockquote, a `<p>` in a loose `<li>`, a list in a blockquote or a blockquote in a
  blockquote — all four still carried a 14px UA margin before this ticket. Flex `gap` never applies inside
  either container (a blockquote and an `<li>` are block boxes, not flex items), which is why zeroing alone
  would have shipped 0px gaps rather than the 8px rhythm.
- `li + li` is a deliberate, named side effect: it takes a **tight** list's items from 0px to 8px, restoring
  the same step a **loose** list's items lost when the `<p>`-inside-`<li>` margin that was silently holding
  them apart got zeroed by the reset above.

One rule block, one long inline comment (nine intra-file line-anchor references, flagged as a NIT in

- **Nested rhythm (AC4).** Every gap inside the blockquote, inside each loose `<li>`, and between loose

## Patterns established

- **A container that needs a rhythm one level below itself must *establish* it, not merely clear the UA's
  leftover margin — flex `gap` does not reach through a block-box child.** `.bubble__markdown`'s own `gap`
  applies strictly between its flex *items*; a `<li>` or `<blockquote>` one level down is a block box whose
  children stack in normal flow with no gap at all. The generalizable move for any future nested-rhythm
  ticket in this file: zero the leftover margin, then re-add the step as an adjacent-sibling margin scoped
  to that container's own children (`>`, not a descendant selector) — reviewed and confirmed correct here
  down to specificity ordering (reset and owl both (0,1,1), owl second so it wins by source order) and
  margin-collapse behavior (every adjacent pair's only live margin is the later sibling's top).
- **`display: flex` cannot be cloned onto a list item to get its rhythm — `list-item` only combines with
  `flow`/`flow-root` in the CSS `display` property, so `display: flex` computes the marker away.** This is
  why the fix here is a margin pair rather than the same flex-column mechanism `.bubble__markdown` itself
  uses; worth checking before reaching for the container's own layout mechanism on any future `<li>`- or
  `<blockquote>`-shaped nested-rhythm problem in this file.
- **Zeroing a UA margin can silently remove separation the layout was depending on — check what the margin
  was buying before deleting it.** The `<p>` margin inside a loose `<li>` was the *only* thing separating
  that list's items; zeroing it for the nested-rhythm reset (above) would have taken item-to-item spacing to
  0px while restoring 8px between an item's own paragraphs — narrower between items than within one, which
  reads as broken. `li + li` exists specifically to close that gap the ACs didn't name.
- **Chromium's UA stylesheet already zeroes a list nested inside a list**
  (`:is(ul, ol, menu, dir) :is(ul, ol, menu, dir)`, no `div` ancestor permitted) — a fixture or AC built on a
  bare nested list proves nothing in `.bubble__markdown`, since it passes before any fix. The leftover-margin
  cases in this container all have a non-list block ancestor (a blockquote or a loose list item); this is
  worth re-checking on any future "reset a UA margin one level down" ticket in this file before writing the
  test fixture.
- **A "no marker is clipped" criterion with no screenshot tooling and no `::marker` geometry API has to be
  expressed as box arithmetic over an indent and the paddings it can overhang into, using conservative
  literals from a one-off pixel scan** — not skipped, not asserted by inspection. The three marker constants
  here are a documented **bound**, not a regression detector (they hold at the UA's 40px too); the honesty
  about that scope is in the test's own comment, and it's the right shape to reuse the next time a metric
  needed for an AC has no browser API to read it from directly.

## Lessons learned

- `display: flex` on an `<li>` destroys the marker (`list-item` combines only with `flow`/`flow-root`) —
  confirms the pattern above; recorded here because it's the kind of thing that looks like it should work
  and silently doesn't.
- Zeroing a UA margin one level down gives 0px, not the container's rhythm, because flex `gap` only applies
  between flex items and a blockquote/`<li>` child stacks in normal flow — "reset the leftover" and "the
  rhythm holds inside" are different outcomes, and a test written for the first passes on a visibly broken
  render.
- Probe what a UA margin was silently buying before removing it — the loose-`<li>` case above was the
  concrete instance; the general habit is worth carrying into any future ticket that resets a UA default in
  this stylesheet.
- Chromium's UA already zeroes a list nested inside a list, so a fixture built on a bare nested list proves
  nothing here — the live nested cases all need a non-list ancestor.
- `e2e/` is outside both tsconfigs, so `npm run typecheck` never sees a spec's helper types; a type error in
  a new `locator.evaluate()` helper surfaces only when Playwright actually runs it, not at the build gate.
  ([Prior instance of this same fact, #628.](628.md))
- Code review independently re-derived the contrast ratio for the blockquote's bar (`--color-outline`
  #8c9199 against the daemon bubble's `--color-surface-container-high` #272a2f) and got 4.5:1 against the
  spec's 4.6:1 — both comfortably clear the 3:1 floor for a meaningful non-text graphic, and the small
  discrepancy is rounding, not a defect; noted here in case a future ticket needs the same pair's ratio and
  wants a checked figure rather than a re-derivation.
