# #630 — Distinguish inline code in an assistant reply without touching the fenced block

Commit `1c5db00` (spec `30a136f`, PR #633, code review PASS with two non-blocking NITs). Not
`security-sensitive` (CSS-only; never touches `AssistantMarkdown.tsx`, #608's markdown security boundary —
mechanically enforced by the attribute-free `<code>` assertions in `AssistantMarkdown.test.tsx` and
`ConversationScreen.test.tsx`, not just argued). Split from #624 (heading/list/blockquote/inline-code type
scale), the last of the four, following [#628](628.md) (heading type scale) and [#629](629.md)
(list/blockquote indent + nested rhythm), which it was blocked on.

## What shipped

One production file, `conversation.css`, +64 lines, no markup change:

```css
.bubble__markdown code:not(.code-block__body code) {
  padding-inline: var(--space-1);
  border-radius: var(--radius-xs);
  background: var(--color-surface);
  font-family: var(--font-mono);
}
```

- **The exclusion is by ancestry, not by class.** react-markdown routes a fence's contents through `<code>`
  too, and a fence with no info string leaves its `<code>` carrying no class at all — attribute-identical to
  an inline one. The rule uses the complex-`:not()` form (`code:not(.code-block__body code)`) over the
  child-combinator alternative (`:not(.code-block__body) > code`) because it fails safe: it excludes at any
  depth inside a fenced body, so a future syntax highlighter wrapping fence content in spans stays excluded,
  where the child-combinator form tests only the immediate parent and would start painting inline chrome
  inside the fence the day that ships. `:not()` takes its argument's specificity, so the rule computes to
  `(0,2,2)` against `.code-block__body code`'s `(0,1,1)` — the two selectors match disjoint element sets by
  construction, so they never compete.
- **No `font-size` declared, and none of the rest of the quartet.** Inline code takes its nearest block
  ancestor's own step — body-medium from `.bubble` in prose, #628's headline-small/title-large/title-medium/
  label-large in `h1`–`h6` — which is what lets one rule cover a paragraph, a heading, a list item, a
  blockquote and `<em>`/`<strong>` with no per-context override. A `.code-block__body`-style body-small
  absolute step was rejected: it doesn't transfer from a block (which owns its line box) to an inline run,
  it makes an `<h1>`'s block 4px taller at a *smaller* font (33px → 37px), and the "mono looks bigger, step
  it down" optical premise measured wrong-signed in the app's own Electron 33 runtime (see Lessons learned).
- **The fill is `--color-surface`**, the same fill `.code-block` already uses, so inline and fenced code
  read as one code surface; ink stays inherited `--color-on-surface`. `--radius-xs` and `--space-1` are the
  scale's smallest radius and step.
- **Seven declared omissions**, each load-bearing rather than forgotten: no `padding-block` (would grow the
  16px inline box to 24px inside a 20px line box, overlapping the next line), no `margin` (#629 owns the
  nested rhythm), no `white-space`/`overflow-wrap`/`word-break` (inherited `break-word` from `.bubble` is
  what AC4's wrap rides on — restating any of them here is the concrete way to break it), no
  `box-decoration-break` (default `slice` keeps a wrapped chip's padding on its first/last fragment only;
  `clone` would add width inside the measure), no `color`, no `display`/`vertical-align`.

**`e2e/assistant-whitespace.spec.ts`, +271 lines.** `RHYTHM_TEXT` (shared with #628/#629) extended in
place — inline code threaded through the *existing* five blocks rather than a sixth reply turn, since the
stream is indexed positionally and inline content adds no block or child count. Seven code spans cover the
paragraph, the `<h2>`, a tight list item, a blockquote (landing in the `<p>` CommonMark wraps quote content
in), and nested inside `<em>` and `<strong>`; one is the existing `LONG_TOKEN_TEXT` reused for the wrap
assertion. A new vacuity-guard constant, `RHYTHM_INLINE_CODE_COUNT` = 7, in the same shape as #629's block/
child-count constants. Two new tests:

- **Inline code reads as code, at its container's own step.** One reader (`readInlineCodeMetrics`, the
  `readHeadingTypeMetrics` idiom) returns every span's measured `fontFamily`/`backgroundColor`/
  `borderTopLeftRadius`/`paddingLeft`/`paddingRight`/`fontSize` beside the token or live element (the
  fence's own fill) it's expected to equal, plus each span's ancestor-tag chain and its nearest
  non-inline-display ancestor. The per-entry loop runs over *all seven* spans, which is what actually
  discharges "one rule, no per-context override," then two extra checks name the `<p>`/`<h2>` cases against
  `--text-body-medium-size`/`--text-title-large-size` specifically — the size claim proved in two different
  scale steps, not just "everything sits at one size." The long token's `clientRectCount > 1` (it wrapped)
  plus `readThreadWidths` staying equal covers AC4 geometrically.
- **Nothing reaches a fenced block's contents (AC3).** Reads the `<code>` inside the `CODE` bubble's
  `.code-block__body` — the languageless fence, the strictly harder case since its `<code>` carries no
  attribute at all. `backgroundColor`/`borderTopLeftRadius`/`paddingLeft`/`paddingRight` all still read the
  pre-#630 absence values (`rgba(0, 0, 0, 0)` / `0px`), while `fontSize`/`fontFamily` still read #623's own
  body-small/mono values. The PR body records the required manual vacuity check: deleting
  `:not(.code-block__body code)` from the selector turned this test red (fence background became
  `rgb(16, 20, 24)`, the chip fill) before being restored.

`AssistantMarkdown.test.tsx`/`ConversationScreen.test.tsx` were left untouched — their attribute-free
`<code>` assertions already mechanically enforce CSS-only (a `className` on inline code would fail all
three), same reasoning as #628/#629.

## Patterns established

- **When a UA-typed inline construct also appears inside another construct this file already chipped
  (a fence's `<code>`), the only sound discriminator is ancestry, and the `:not()` form should say "not
  *inside*" (a descendant-combinator argument) rather than "whose *parent* is not" (a child-combinator
  argument).** The descendant form keeps excluding if a later ticket wraps the excluded region's contents
  one level deeper (here: syntax highlighting spans inside `.code-block__body`); the parent-only form
  silently stops excluding the moment that happens. Worth the specificity increase — the two selectors
  matching disjoint sets by construction means source order between them is never a live concern.
- **An inline run inside a container that already carries the type scale on every context should declare no
  `font-size` of its own** — reusing the container's absolute step (rather than the token a sibling *block*
  construct uses) is what lets one rule satisfy "distinguishable, no per-context override" simultaneously;
  a block's own full quartet doesn't transfer to an inline element because the other three quartet members
  belong to the line box, which the inline run doesn't own.
- **A perceptual/optical justification for a design decision ("X looks bigger than Y") should be measured in
  the runtime that actually ships (here, the app's own Electron/Chromium build), not only in whatever
  browser build the e2e suite happens to drive** — see Lessons learned; the two disagreed and the
  disagreement inverted the argument's sign, not just its magnitude.

## Lessons learned

*(lifted from the PR body)*

- **A probe's numbers do not transfer between Chromium builds, and one of the spec's did not.** The
  architecture spec's font evidence came from `chromium_headless_shell-1208` (the Playwright browser
  download), but this suite's app under test is Electron 33 / Chromium 130. Re-measured there, `--font-mono`
  falls through to Menlo at an x-height of 7.66px against `--font-sans`'s 7.37px — mono is the *larger* of
  the two, inverting the spec's figure (6.32px / 86%) rather than merely shifting it. The conclusion
  (declare no `font-size`) survived unchanged and now rests on a stronger version of its own reasoning.
  Worth re-probing any inherited CSS measurement in the renderer that actually ships, not just the one the
  test tooling happens to drive.
- **Two specificity/inventory facts in the spec were off and were corrected in the shipped rule's comment:**
  `.code-block__body code` is `(0,1,1)`, not `(0,2,0)`; and the file's pre-existing `:not()` uses are eight
  — six `:not(:disabled)` and two `:not([aria-readonly])` — not "nine, all `:not(:disabled)`." The
  load-bearing point survived both corrections: every pre-existing use is a *simple* selector, so a complex
  `:not()` argument is genuinely new here. `padding-block: var(--space-1)` also measured to a 24px inline
  box, not 22px as the spec estimated.
- **`e2e/` sits outside both tsconfigs**, so `npm run typecheck` never sees a Playwright spec and Playwright's
  own transpile strips types without checking them — the new spec's types were verified out-of-band. Same
  fact recorded by [#628](628.md) and [#629](629.md); now confirmed a third time on a third ticket in this
  file.
- **A fresh worktree has no `out/`, and `npx playwright test` does not build it.** Running the spec directly
  against a stale/absent bundle times out all nine tests and reads exactly like a broken app — `npm run
  build` first, or the `e2e` script.
- **Code review independently re-verified both spec corrections above** and additionally confirmed the two
  `:not()` selectors match disjoint element sets (so their relative source order in the file is inert) and
  that no other stylesheet under `src/` carries a `code` selector. Flagged two non-blocking NITs, neither
  gating: the rule comment's "no new colour, so no contrast question" understates that the chip fill against
  the *bubble's* fill measures ~1.29:1 (not a criterion this ticket carries, and the chip isn't the sole
  signal — mono family and the inset also carry it); and an `expect(x?.y).toBeGreaterThan(1)` optional-chain
  read in the new long-token assertion, which is non-vacuous but inconsistent with the file's usual
  guard-presence-first idiom.
