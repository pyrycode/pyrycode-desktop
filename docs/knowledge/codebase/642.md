# #642 — Decode the tool input map off `tool_use`

Transport slice threading pyrycode#1678's sixth `tool_use` field, `input`, down the existing
wire type → narrower → IPC event type → emit chain — the same shape as [#217](217.md) (the original
`tool_use` decode) and [#229](229.md) (`tool_result`). Split from #606. Shipped as PR
[#695](https://github.com/pyrycode/pyrycode-desktop/pull/695), code-review **PASS** (one SHOULD FIX,
three NIT, none blocking), security review **PASS** (architect self-review, mandatory —
`security-sensitive` label). Size S; four production files, 0 forced call-site changes. **Ships
dormant** — nothing in this slice reads the new field. [#643](https://github.com/pyrycode/pyrycode-desktop/issues/643)
carries it into the timeline bridge and store; [#645](https://github.com/pyrycode/pyrycode-desktop/issues/645)
draws it.

## Summary

Before this ticket `ToolUsePayload` carried five always-present strings. pyrycode#1678 (merged as
pyrycode PR #1682, live on `pyrycode` `main` since 2026-08-21) added a sixth field, `input` — the
tool's own input fields as a `map[string]string`, so a client can eventually list what a tool is
acting on instead of showing only the daemon's `input_summary` précis. This slice decodes it and
carries it to the renderer; nothing consumes it yet.

The wire fact that shapes the whole design: the Go field carries **no `omitempty`**, and a custom
`MarshalJSON` normalises a nil map to `{}`. So from a post-#1678 daemon `input` is **always present
and never `null`** — an absent, empty, or non-object input all arrive identically as `"input":{}`. The
absent-key case is exclusively a **pre-#1678 daemon**, which is the case the design must survive
(daemon and client are built days apart). This makes `input` optional *to the client*, not optional
*on the wire* — the same shape as the `conversation_updated.is_archived` scar
([memory](../../../CLAUDE.md), pyrycode#881): requiring the field would fail-close every frame from an
older daemon.

Four production touch-points:

- **Wire type** (`src/shared/wire/types.ts`) — `input?: Record<string, string>` added to
  `ToolUsePayload`, mutable (not `Readonly`) to match the file's convention for wire payload types
  (`QueueStatePayload.queued: QueuedItem[]`). The doc comment is the deliverable that carries the
  contract forward to #643/#645: display strings not capabilities, daemon-chosen field names, optional
  client-side vs. always-present wire-side, alphabetical-and-meaningless key order, the map may be
  incomplete (daemon's 8500-rune total bound drops fields, names none, `input_summary` stays the
  fallback), the `…` shortened-value marker, and the three reserved keys never appearing.
- **Narrower** (`src/main/transport/inboundMessage.ts`) — a new module-private helper,
  `optionalStringMap(payload, field)`, placed directly after `requireStringArrayOrNull` (#564), whose
  posture it rotates from a list to a map:

  | `payload[field]` | Result |
  |---|---|
  | `undefined` (key absent) | `undefined` — a pre-#1678 daemon |
  | `null`, an array, a string, a number, a boolean | **throws** |
  | `{}` | a fresh `{}` — an empty map, distinct from `undefined` |
  | an object, every own value a string | a fresh object, reserved keys removed |
  | an object with any non-string own value | **throws** the **whole frame** — never a partial map |

  `parseToolUsePayload` gets one added line and returns `input` unconditionally (`undefined` when
  absent — `toEqual` treats that as equal to a missing property, so the existing "drops unknown server
  keys" test at `:2577` passes unchanged). The failure message is a **new category**,
  `malformed optional field: ${field}` — deliberately not `missing required field:`, which would be
  actively misleading here since an absent key is the one case that does *not* throw.
- **Consumer emit** (`src/main/daemonConnection.ts:825-831`) — `input: inbound.toolUse.input` added to
  the existing fresh literal, unconditional, by reference (the narrower already stripped it to string
  values with reserved keys removed, so nothing is left to drop and no second copy is warranted).
- **IPC arm** (`src/shared/ipc/events.ts:369-`) — `input?: Readonly<Record<string, string>>` added to
  the `toolUse` `DaemonEvent` arm, with the doc comment carrying the absent/empty distinction and the
  plain-text-never-HTML constraint forward.

### The reserved-key decision: drop, don't carry, don't throw

This is the first narrower in `inboundMessage.ts` where the **daemon chooses the object keys** — every
other one copies a fixed set of known field names. `RESERVED_MAP_KEYS = new Set(['__proto__',
'constructor', 'prototype'])` is dropped from the fresh container rather than carried or thrown on:

- **Throwing would be an evasion vector.** Failing the whole frame on a reserved key would let a model
  suppress its own tool row from the timeline by naming a tool parameter `__proto__` — the daemon
  copies model-authored key names verbatim.
- **Carrying would buy inconsistency, not fidelity.** A future downstream `Object.assign(target, map)`
  or `target[k] = map[k]` invokes `Object.prototype`'s `__proto__` setter; with string values that's a
  silent no-op, so the entry would survive in `main` and silently vanish downstream.
- **The value-type check runs for every key, reserved ones included, before the skip.**
  `{"__proto__": {"a": 1}}` throws (non-string value); `{"__proto__": "x"}` decodes with that one entry
  dropped. Both are pinned by tests, including a fixture built via `JSON.parse` rather than an object
  literal — a `{ __proto__: 'x' }` object literal sets the prototype instead of creating an own
  property, so it never reaches the decoder as a key at all.

No client-side re-policing of the daemon's own bounds (16 fields / 4000 runes per value / 8500 runes
total) — `MAX_PLAINTEXT_BYTES` in `parseInboundMessage` remains the only client-side size bound, gating
the whole frame upstream of this narrower (ADR 0002's no-cross-validate posture).

## Patterns established

- **`requireStringArrayOrNull`'s posture (one bad entry throws the whole payload closed; an empty
  container is valid and distinguishable from absent; the result is a fresh container) generalises
  cleanly from an array of scalars to a daemon-keyed map** — `optionalStringMap` needed no new
  fail-closed idiom, only the reserved-key strip. A future daemon-keyed-map field should reach for this
  helper's shape rather than reinventing it.
- **A field narrower's name must say "optional" when it deviates from the `require*` family's
  fail-on-absence contract.** `requireStringArrayOrNull`'s own doc comment already draws this line
  ("an OMITTED key is `undefined` … and therefore fails closed, which is what separates this from an
  optional-field parse") — `optionalStringMap` is deliberately not named `requireOptionalStringMap` or
  similar, so the call site reads its contract without opening the helper.
- **The correct response to "daemon picks the keys" is drop-the-three-reserved-names, not
  `Object.create(null)`.** A null-prototype container would not survive structured clone across IPC (the
  renderer receives a plain object regardless), so it buys a false sense of protection at the boundary
  that actually matters. With the three reserved keys removed at decode, an ordinary-prototype container
  is safe for a consumer that iterates (`Object.entries`) rather than probes by key.
- **A new failure-message category beats reusing an existing one when the existing one's semantics don't
  fit.** `malformed optional field:` was coined rather than reusing `missing required field:`, because for
  an optional field an absent key is precisely the non-throwing case — reusing the required-field message
  would have been actively misleading to whoever reads a caught error.

## Lessons learned

*(from the PR #695 body)*

- **A wire fixture carrying `__proto__` must be built with `JSON.parse`, not an object literal.**
  `{ __proto__: 'x' }` sets the prototype instead of creating the own property the wire actually
  delivers, so a literal-built fixture tests nothing — it never reaches the decoder as a key at all.
  `JSON.parse` (and `JSON.stringify` on the way out) both treat it as an ordinary own enumerable
  property, matching what the daemon's frame produces.
- **`expect(probe.constructor).toBeUndefined()` is the wrong prototype-invariant assertion** and fails
  on a clean object — `({}).constructor` is `Object`. Assert on the *values* a hostile frame carried
  (`probe.polluted` undefined, `Object.values(probe)` empty, prototype identity unchanged), never on the
  reserved key names themselves.
- **`JSON.stringify(events)` is a deterministic way to assert an IPC field is "absent"** when the emit
  assigns it unconditionally: the property exists holding `undefined`, `toEqual` can't distinguish that
  from missing, and `JSON.stringify` drops it. Watch for substring collision when sweeping —
  `"input"` does not match inside `"inputSummary"`, but only because of the closing quote in the
  serialized form.
- **`missing required field:` is actively misleading for an optional field**, since an absent key is
  the one case that does *not* throw. A dedicated `malformed optional field:` category keeps the
  message honest while still naming only the client-owned constant.

**Code review SHOULD FIX, not yet applied as of this doc pass.** The doc comments at
`daemonConnection.ts:829` and `inboundMessage.ts:965` both claim the `undefined`-valued `input`
property is dropped by "structured clone" on its way to the renderer. That mechanism claim is wrong:
`emitDaemonEvent` (`src/main/emitDaemonEvent.ts:45`) sends over `webContents.send`, i.e. the Structured
Clone Algorithm, which **preserves** an `undefined`-valued own property rather than dropping it —
`JSON.stringify` never runs at that IPC boundary at all; it is only what the *test* uses to assert
absence. The behavioural contract the comments state — test `event.input === undefined`, never
`'input' in event` — is correct and unaffected; only the stated mechanism is wrong. `events.ts:378-379`
states the same contract correctly, with no wrong mechanism claim, and needs no fix. A future edit to
either flagged comment should read: the property crosses as a **present-but-`undefined`** own property
(structured clone preserves it), which is precisely why the `=== undefined` test is the mandated one
rather than a stylistic preference.

## Open questions carried forward

- **`timelineBridge.ts:48`'s comment is now stale, flagged but not fixed here** (out of scope — "don't
  refactor adjacent code"): it claims the `DaemonEvent` and `ThreadEvent` `toolUse` shapes are
  field-for-field identical, which stopped being true the moment the `DaemonEvent` arm gained a sixth
  field. The code itself is unaffected (`timelineBridge.ts` builds a fresh five-field literal, so
  `input` correctly stops there and the slice stays dormant) — #643 lands on exactly this arm and will
  rewrite the comment.
- **Dropping `constructor`/`prototype` alongside `__proto__` is broader than strictly necessary** — only
  `__proto__` is dangerous via `[[Set]]`; the "a downstream `Object.assign` would lose it anyway"
  argument holds only for that one key. The consequence: an MCP tool with a field literally named
  `constructor` or `prototype` has it vanish silently from the expanded row. Ratified by AC3, justified
  in the architecture spec § 2.3, and lands inside a contract #645 must already handle (the daemon's own
  bound drops fields and names none) — correct as shipped, worth remembering when the row is drawn.
- **The `…` shortened-value marker is carried verbatim, never detected or stripped.** #645 owns the
  decision of whether to signal shortening in the UI; a value that legitimately ends in `…` is
  indistinguishable from one the daemon cut, an accepted cost inherited from the daemon.
- **Naming: `optionalStringMap` vs `optionalStringRecord`** was left open by the architecture spec
  (`Map` meaning the wire concept, not the JS `Map` type — the return is deliberately a plain object,
  since a `Map` would not survive structured clone as a plain record and would imply an ordering
  guarantee the wire does not have). Shipped as `optionalStringMap`; an acceptable rename if a future
  reader finds `Map` ambiguous, contract unchanged either way.
