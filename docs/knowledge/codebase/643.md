# #643 — Carry the tool input fields onto the timeline tool-call item

Store slice widening the two renderer-local hops between the `toolUse` `DaemonEvent` (#642, carried
to the IPC boundary) and the `toolCall` `ThreadItem` so the tool's input map reaches the item —
unchanged, by reference, absence kept distinct from emptiness at both hops. Interprets the map in
neither hop; the headline pick, the shortening, and the fallback are all
[#645](https://github.com/pyrycode/pyrycode-desktop/issues/645)'s decisions. Split from #606. Shipped
as PR [#698](https://github.com/pyrycode/pyrycode-desktop/pull/698), code-review **PASS** (0 MUST FIX,
0 SHOULD FIX, 3 NIT). Size XS; two production files, four production lines. **Ships dormant** —
`ConversationScreen.tsx:550`/`:1053` are untouched, so nothing renders the field yet.

## Summary

[#642](642.md) decoded pyrycode#1678's `tool_use.input` map (name → value) down to the IPC boundary
but stopped there — the field crossed to the renderer with no consumer. This slice moves it the last
two hops:

- **`ThreadEvent`'s `toolUse` arm** (`src/renderer/src/store/threadTimeline.ts:94`) — gained
  `input?: Readonly<Record<string, string>>`, matching `events.ts:390` character-for-character so
  the bridge assigns with no cast. The arm expanded from a single-line union member to the
  multi-line form with a doc comment carrying the absence/emptiness contract forward — there was
  nowhere else in the file to put it.
- **`ThreadItem`'s `toolCall` member** (`threadTimeline.ts:42-51`) — the same field, the same shape,
  beside `inputSummary`. Optional, so no existing construction site was forced to change.
- **The bridge's fresh literal** (`src/renderer/src/store/timelineBridge.ts:51-58`) — `input:
  event.input`, unconditional, by reference.
- **The reducer's appended literal** (`threadTimeline.ts:281-286`) — the same assignment, same
  discipline.

`fillResult` (`threadTimeline.ts:232`, the `toolResult` correlate-and-fill) needed **no production
change** — its `{ ...item, result }` already preserves any field the item carries, including this
one. The new test pins that against a future edit rather than doing work.

### The one hard fact, again

The Go field carries no `omitempty` and normalises a nil map to `{}`, so from a post-#1678 daemon
`input` is *always present*: absent, empty, and non-object inputs all arrive as `{}`. An **absent**
map means exactly one thing — a pre-#1678 daemon — and the operator runs client and daemon builds
days apart, so collapsing absence into emptiness would break his older-daemon days. Both hops
therefore assign `event.input` verbatim, never `{ ...event.input }` (which turns an absent map into
`{}` on the way through) and never a conditional spread (which reshapes the literal and breaks the
"stays a rename" contract).

### Why the unconditional assignment type-checks

Neither `tsconfig.node.json` nor `tsconfig.web.json` sets `exactOptionalPropertyTypes`, and
`strict: true` does not imply it. So `input: event.input` — a possibly-`undefined` value assigned to
an optional property — compiles at both hops with no cast and no guard. This is the fact that makes
a conditional spread merely wrong rather than necessary.

## Patterns established

- **A field narrower's absence/emptiness contract, once decoded upstream (#642), rides forward as a
  doc comment at every hop rather than being re-validated.** Neither hop here re-checks the map's
  shape — the narrower already fail-closed on a malformed one — so widening an optional field is
  purely mechanical once the type is declared correctly.
- **A sibling fixture builder beats widening an existing one when a test file builds events
  exclusively through builders.** `threadTimeline.test.ts` never builds a `ThreadEvent` inline;
  adding `toolUseWithInput(...)` beside `toolUse(...)` kept all 20+ existing callers byte-identical
  and let `toolUse(...)` itself keep serving as the absent-map (pre-#1678 daemon) builder two of the
  new cases use directly. `timelineBridge.test.ts` has the opposite idiom (inline `DaemonEvent`
  literals) and the new bridge cases follow that file's own convention instead.
- **A present-but-`undefined` optional field is invisible to every existing `toEqual` assertion in
  this codebase.** Both store test files use `toEqual` throughout (0 `toStrictEqual`), so widening
  `toolUse`/`toolCall` with an optional field left every pre-existing literal passing unchanged —
  the correct diagnostic reading if one goes red is a conditional spread or a defensive re-copy, not
  a stale fixture.
- **Widening a `ThreadItem` acquires no log or persistence sink to defend.** Code review confirmed
  by grep: `timelineStore.ts:10` declines the #134 diagnostics observer by design, no store persists
  `items` to `localStorage` (the two stores that do are both unrelated prefs), and `React.memo`
  appears nowhere in `src/`. So carrying untrusted daemon text onto an item needs only the doc
  comment, not runtime enforcement — re-grep this before assuming a sink exists on a future ticket
  touching the same item (#645, #696, #697).
- **A contract restated at multiple sites drifts on its first outing.** The spec asked for the
  absence/emptiness comment to appear at three renderer sites beside the canonical one
  (`events.ts:374-383`); the very first copy (`threadTimeline.ts:94`/`:281-286`) dropped
  "alphabetical" from "key order is meaningless (**alphabetical**, a Go map artefact)" — the
  load-bearing half for #645, which needs to know a sorted-first key carries no salience. A shared
  contract is safer pointed-to than repeated.

## Lessons learned

*(from the PR #698 body)*

- **`toEqual` passing on an unchanged fixture is the signal the carry is right, not that it is
  stale.** Every existing `toEqual` on a `toolUse` event / `toolCall` item passed unchanged after the
  widening, because `toEqual` treats a present-but-`undefined` property as equal to a missing one. A
  red one here would have meant a conditional spread or a defensive re-copy had crept in — the
  failure mode the slice guards against — rather than a fixture needing an update.
- **A key-order assertion needs deliberately non-alphabetical, non-numeric keys.** Integer-like
  string keys are reordered ahead of the rest by the JS engine regardless of insertion order, and
  alphabetical keys would pass even if something sorted the map, so `{ pattern, path, output_mode }`
  is what gives the assertion teeth.
- **A sibling fixture builder beats widening the existing one.** `threadTimeline.test.ts` builds
  events only through its builders; adding `toolUseWithInput(...)` beside `toolUse(...)` left all
  20+ existing callers byte-identical and kept `toolUse(...)` itself as the absent-map builder, which
  two of the new cases use directly.

## Open questions carried forward

- **Which of `input === undefined` (pre-#1678 daemon) vs. `input` present-but-empty (this daemon
  sent no fields) should read differently in the row, if at all, is #645's call.** This slice's job
  was only to make sure the distinction survives long enough for #645 to have that choice — both
  facts are pinned by tests at both hops.
- **The contract-comment drift noted above (missing "alphabetical") is unfixed here** — it does not
  change behavior, only the comment's completeness, and #645 is the next ticket to read it closely.
