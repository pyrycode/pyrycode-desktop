# #644 — a display shortener for tool subject paths

Split from #606 (the tool kind/subject render split). Spec `75304d0`, shipped `79d492d`, PR #647, zero
deviation. Size XS (dropped from the ticket's own `S` estimate — the spec invited the override), not
security-sensitive, code review PASS (one NIT, forward-looking only — see below). Ships **dormant**: #645
is the wiring ticket that gives it a caller.

## Summary

The tool row today draws `inputSummary` — the daemon's whole tool input squeezed onto one line and cut
at 200 characters. #642 and #643 carry the daemon's new `kind`/`subject` onto the timeline item; #645
will draw it. This ticket is the one piece of that work with no daemon dependency and no UI: the pure
display rule #645 will call for the file-acting `kind`s.

- **`src/renderer/src/screens/conversation/shortenPath.ts`** — two exports, zero imports (notably no
  `node:path`, which would split on a backslash under Windows and make the result vary with the host):
  - `KEPT_SEGMENTS = 4` — trailing segments kept when a path is shortened: three folders plus the file
    name.
  - `shortenPath(path: string): string` — split on `/`, drop the empty entries (the whole of the
    leading/trailing/repeated-separator handling, no case of its own), return the input **unchanged**
    when `KEPT_SEGMENTS` or fewer segments remain, otherwise `.../` followed by the last `KEPT_SEGMENTS`
    rejoined with a single `/`. Total over `string` — no guard, no `try`/`catch`, no length cap; the
    signature is the contract.
- **`shortenPath.test.ts`** — 16 cases (17 assertions) as plain string-literal-in/string-literal-out
  table rows; the node-environment renderer test tier covers this completely since nothing renders.

No existing file is touched. No caller is wired — the sibling test is what proves the function works,
not a call site (mirrors #600's posture exactly).

### The resolved ambiguity

#606 stated the rule as "the last three folders plus the file name" (four trailing segments) but
illustrated it with a two-folder example (`.../screens/conversation/ConversationScreen.tsx`) — the
example was written with no source path beside it, so the two never had to agree. Neither
[pyrycode#1678](https://github.com/pyrycode/pyrycode/issues/1678) ("shortening for display is the
client's job and must not be done here") nor mobile (no counterpart helper) settles it. The spec took the
rule as written and corrected the example; `KEPT_SEGMENTS` is exported specifically so this resolution is
a named, testable fact rather than implicit in a dozen expected strings — reverting to "three segments in
total" is a one-number change plus one test assertion, nothing else in either file moves.

### Two deliberate asymmetries (from the doc comment, worth knowing before touching this file)

- **The passthrough is verbatim; the shortened form is not.** A path that fits is returned as the exact
  same string — `a//b/c.txt` and `a/b/c/` keep their doubled/trailing separator. A path that is shortened
  is rebuilt from its kept segments, so a doubled separator inside the kept window collapses and a
  trailing one is dropped (`a/b/c/d/e/` → `.../b/c/d/e`, not `.../b/c/d/e/`).
- **The shortened output is display text, not a path.** `.../b/c/d/e.txt` resolves to nothing and must
  never be fed back into a path operation. No normalisation of any kind: `.` and `..` are ordinary
  segments and count toward the budget (`../a/b/c.txt` is four segments, returns verbatim).

## Patterns established

- **Dormant pure-helper-before-consumer, second instance of the #600→#601 shape.** Isolate the total
  function with a tested core before any component exists to call it, specifically so the piece with no
  daemon dependency can dispatch while its siblings (#642/#643, blocked on the daemon) wait. Same
  reasoning, same file layout (`.ts` + `.test.ts` beside the screen, no consumer, no INDEX.md entry until
  the consumer lands and cites it retrospectively — see `600.md` for the precedent this is now confirmed
  against twice).
- **An exported constant as the sole location of a resolved spec ambiguity.** `KEPT_SEGMENTS` is not
  inlined precisely so a future disagreement about the rule is a one-line diff with a test assertion
  sitting next to it, rather than a search-and-replace across a dozen literal strings — the
  `AT_BOTTOM_TOLERANCE_PX` precedent from #600.
- **Bundle-hash dormancy proof, reused from #608.** Building once with the module present and once moved
  aside and comparing Vite's content-addressed output filename (`index-CyKIfOks.js`, hash `6bfab893…`,
  identical both times) proves the helper is provably absent from the shipped renderer bundle — stronger
  than a grep for the export name, which only proves no import *statement*. See
  `dormant-renderer-module-proved-by-bundle-hash` in project memory for the general technique; both
  builds must exit 0 or a stale `out/` reads as a false "dormant".

## Lessons learned

(From the PR body's own "Lessons learned" section.)

- **Vite's content-addressed asset names make "ships dormant" provable as data**, not argued from the
  absence of an import statement: build twice, once with the module moved aside, compare the hash. Only
  sound if both builds exit 0.
- **`npm run typecheck` is `tsc -p tsconfig.node.json && tsc -p tsconfig.web.json`** — the `&&`
  short-circuits, so a node-side failure hides the entire renderer half. Worth running the web project
  alone when the change is renderer-only.
- **A new-module TDD step goes RED as a module-resolution failure, not an assertion failure**, so it
  proves less than the usual RED — the module doesn't exist yet, so of course the import fails. A
  separate mutation run (degenerate always-passthrough, `KEPT_SEGMENTS = 3`, rejoin-instead-of-return)
  is what actually establishes the suite's assertions discriminate; each mutation was caught by a
  different, specific subset of tests.

## Code review

PASS, one NIT, forward-looking rather than a change request: `shortenPath.test.ts:99` covers `..` only in
its verbatim (four-segment) form. A five-segment relative path drops the `..` like any other lost
segment — `../a/b/c/d.txt` → `.../a/b/c/d.txt` — which is the correct consequence of "no normalisation,
`..` is an ordinary segment," but differs from its input by a single period and could read as though
nothing happened. Worth knowing in **#645**; the reviewer explicitly did not ask for a branch here, since
the spec is explicit that a fifth step would mean the criteria are wrong. Reviewer also hand-checked all
14 worked-table rows, confirmed `AC4`'s "no Node `path` import" via `grep -c '^import '` = 0, and
confirmed dormancy by repo-wide grep (the bundle-hash evidence was the author's own run, not reproduced —
the review worktree has no `node_modules`, see `code-review-worktree-has-no-node-modules` in project
memory).
