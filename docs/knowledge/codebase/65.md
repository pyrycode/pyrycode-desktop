# #65 — Outbound send path: encrypt a send-message command onto the relay

**Shipped:** 2026-07-04 · **Size:** S · **Labels:** `security-sensitive` · **Scope:** one new transport-layer builder (`src/main/transport/sendMessageEnvelope.ts`) + two edits (`daemonConnection.ts`, `index.ts`) · additive, zero consumer cascade · **no new dependency**.
**Spec:** `docs/specs/architecture/65-outbound-send-encrypt-command.md` · **PR:** [#67](https://github.com/pyrycode/pyrycode-desktop/pull/67) (review: PASS, one NIT — the already-agreed exhaustiveness-tripwire deferral).

Wires the **last missing seam of the outbound send flow**: a validated `sendMessage` command that reaches `onCommand` in the background process becomes an encrypted `send_message` envelope on the live Noise relay session. The **main / transport half**; the renderer half (composer submit + optimistic echo) is [#66](https://github.com/pyrycode/pyrycode-desktop/issues/66), which drives this seam from the other end. The three pieces were all present but wired by no one — the [command channel](../features/command-channel.md)'s `onCommand` seam ([#17](17.md)), the [daemon connection](../features/daemon-connection.md)'s live transport ([#62](62.md)), and the [Noise relay driver](../features/noise-relay-driver.md)'s `sendMessage` ([#50](50.md)). Closes #17's deferred "single registration + teardown ownership" item. Entirely `src/main/`; no renderer touched. See the [outbound-send-path feature doc](../features/outbound-send-path.md) for the full contract, data flow, and security properties.

## Patterns established

- **A post-handshake app-envelope builder is a new sibling to `helloExchange.ts`, not an addition.** `helloExchange.ts` is scoped to the handshake exchange (`hello` / `hello_ack`); `send_message` is post-handshake application traffic. Same one-concern-per-file split the `transport/` module already follows. The builder is pure (caller supplies `id` + `ts`, exactly like `buildClientHello`) — no clock, no counter, no side effects — and **thinner** than the hello builder because a `SendMessagePayload` has no defaulted fields (no `make…Payload` constructor to route through; contrast `makeHelloClientPayload` / `codec.ts:157`).
- **The single `driver === null` guard suffices — no `connected` flag.** The load-bearing correctness argument: the driver's own `sendMessage` is already inert pre-handshake / post-terminal (`noiseRelayDriver.ts:229`, rooted in `NoiseSession`'s `if (state !== 'transport') return`), so the connection layer does **not** track handshake state itself. The one `driver === null` guard plus that documented inertness covers every "not connected" state (before start, mid-bootstrap, bootstrap-failed, pre-handshake, post-terminal, post-stop). A flag would add state for no functional gain — the message is dropped either way; the only difference is whether an id is consumed, which is harmless.
- **Full-body `try/catch` is the deterministic no-throw guarantee (parity #490).** Wrapping the *whole* body (not just the build) is what makes "never throws out of the module" true — it covers both the over-cap `WireEncodeError` from `buildSendMessage` and any driver/wasm throw from `sendMessage`. This is the belt-and-suspenders deterministic net the mobile-#490 parity note demands (a stochastic "be careful" rule would not do).
- **The envelope-id counter advances only on a successful build.** A module-local, single-writer counter; `send` has **no `await`**, so it runs to completion with no check-then-act race. Advancing only after a successful build means a dropped over-cap send does not consume an id. Gaps are harmless — the daemon uses envelope `id` for `in_reply_to` correlation, not sequencing. (It is a wire correlation id, **not** a Noise nonce; the session owns its own per-direction nonce counter, so no randomness is needed.)
- **`onCommand` registered once, at composition time, not gated on `did-finish-load`.** The handler is inert until a driver exists (`send` no-ops with no driver), so an early command is a safe no-op — no need to defer registration to first load. `onCommand` uses `ipcMain.on` (additive), so the **single-call discipline at the sole registration site** is what makes "registering twice does not double-dispatch" true; the `will-quit` unsubscribe is symmetric with `unregisterPairing`. This is the reusable shape for wiring any future `RendererCommand` member.
- **Classify-don't-forward, inherited unbroken (#62).** The `catch` **drops** the caught object and emits nothing — a codec error message could echo the message plaintext (`SendMessagePayload.text`). Log-free, pinned by the six-method `console`-spy + a no-plaintext-in-events assertion. Inherited [#5](5.md)/[#7](7.md)/[#22](22.md)/[#50](50.md)/[#62](62.md).
- **Do not re-test the driver's inertness at the connection layer.** The connection relies on the driver's post-terminal/pre-handshake inertness, but that contract is already proven by `noiseRelayDriver.test.ts:304-358`. The `daemonConnection.test.ts` send suite tests only what *this* layer does (what it hands the driver, id monotonicity, no-throw), with a one-line comment pointing at the driver's tests. Don't duplicate a downstream contract's coverage at the consumer.

## Lessons learned

*Lifted from PR #67's "Lessons learned" section.*

- **The single `driver === null` guard plus the driver's documented inertness cover every not-connected state**, so the connection layer needs no `connected` flag to gate `send` — the only difference a flag would make is whether an envelope id is consumed, which is harmless (the daemon uses `id` for `in_reply_to` correlation, not sequencing).
- **The envelope-id counter advances only on a successful build**, so a dropped over-cap send does not consume an id; verified by the "next successful send still uses id 2" test.

## Deferred / carried forward

- **Send-failure UX → [#34](https://github.com/pyrycode/pyrycode-desktop/issues/34)/[#35](https://github.com/pyrycode/pyrycode-desktop/issues/35).** Surfacing "message not delivered" (retry indicator, dropped-send toast) to the renderer. No `DaemonEvent` models it today (`failed` = the *connection* failed, not one message); a dropped send surfaces nothing, matching the AC (drop, don't crash). **Do not invent an event for it** — it likely lands with the reconnect/status choreography.
- **Exhaustiveness tripwire (`Record<RendererCommand['type'], true>`) → deferred per [#17](17.md).** The `switch (command.type)` in `index.ts` has no `default`/`never` guard, so a future union member added without a case would be silently dropped. Correct to defer while `sendMessage` is the only member; add the tripwire (+ the matching `isRendererCommand` case) when connect/disconnect land. The code-review NIT flagged this as the already-agreed deferral.
- **The renderer half → [#66](https://github.com/pyrycode/pyrycode-desktop/issues/66).** Composer submit + optimistic echo drive this seam from the other end. `message_id` generation lives with that producer (`crypto.randomUUID()`), not in this pure path (see [#17](17.md) § Patterns).
- **The broader no-throw sweep across all relay commands → [#31](https://github.com/pyrycode/pyrycode-desktop/issues/31).** #65 landed the mobile-#490 parity guard for the one send path; #31 is the wider audit.
