# #652 — deleting the open discussion returns to the Channel List

Split from #596 (found by hand-driving the app against a real daemon). Spec (architect), shipped
`a726873`, PR [#656](https://github.com/pyrycode/pyrycode-desktop/pull/656). Size S (as estimated).
Code review: **PASS**, one SHOULD FIX (missing regression pin, not a defect) and one NIT (documented,
not fixed). Not filed as `security-sensitive` — renderer-only, no `src/main/` or wire change, the same
posture as the sibling renderer state-clear tickets #530/#531/#593.

## Summary

Deleting the discussion currently open in the thread used to fire `delete_conversation`, close the
Channel Info sheet, and stop there: the thread kept rendering the deleted discussion's rows, kept
accepting input, and stayed recorded as the active conversation — so the composer send and the
queued-message drop kept addressing a conversation id the daemon no longer held, silently, since the
app has no send-failure surface.

Three production files close the wiring gap, all renderer-only:

- **`src/renderer/src/exitActiveConversation.ts`** (new) — the pure decision. Gates on
  `getActiveConversation()?.id !== conversationId`; on a match, `dispatchTimeline({ type: 'reset' })`
  → `clearActiveConversation()` → `clearSessionId()` → `navigateToList()`, in that order (clear before
  nav, so no observer sees the Channel List rendered against the deleted discussion's thread state).
  A mismatch — including no active conversation at all — is a total no-op. Every effect is injected, so
  the function is React-free, store-free, and tested with plain spies.
- **`src/renderer/src/store/conversationDeletedBridge.ts`** (new) — the event seam, the
  `conversationCreatedBridge` twin: `translateConversationDeleted` maps the `conversationDeleted`
  `DaemonEvent` to its bare `id` (`default: null` for everything else, not `assertNever` — this path
  intentionally consumes only one arm), `subscribeConversationDeleted` wires that through an injected
  `onDaemonEvent`, and `useConversationDeletedExit` is the thin React binding (ref-held latest callback,
  empty-dep effect, off-handle cleanup — one live listener under StrictMode double-mount).
- **`src/renderer/src/PairedShell.tsx`** (modified) — wires the two above beside the existing
  `useConversationCreatedNav`: `useConversationDeletedExit((conversationId) =>
  exitActiveConversation({ ...exitConversationDeps, navigateToList: () => dispatch({ type: 'back' }) },
  conversationId))`. `exitConversationDeps` sits at module scope (the `activateDeps`/`clearPairingDeps`
  idiom — `getState()` inside each arrow, nothing read at module load or during render); `navigateToList`
  is the one effect that can't live there, since it needs the container's `dispatch`, hence the
  `Omit<ExitActiveConversationDeps, 'navigateToList'>` typing that makes the missing field explicit.

`ConversationScreen.tsx` is unchanged — `requestDeleteConversation` keeps firing the command and
closing the sheet exactly as before; the sheet unmounts with the thread when the route flips.

**Navigate on the daemon's confirmation, not on the click.** This is the delete-side mirror of
`useConversationCreatedNav`'s existing rule (a create the daemon never confirms doesn't navigate) — a
delete the daemon never confirms leaves the operator in the thread (AC5), rather than stranding them on
a list that still shows the row.

**The clear set is three stores, not `clearPairingScopedState`'s five.** The pairing has not ended —
the daemon connection is alive and the operator lands on a *working* Channel List — so resetting
`sessionStore` would blank a live connection status into a false disconnected state, and clearing
`announcedModelStore` would drop daemon-scoped (not conversation-scoped) state. The set here is
`activateConversation`'s clear branch (timeline `reset` + `clearSessionId`) plus
`clearActiveConversation`, which `activateConversation` deliberately excludes only because it
immediately re-sets the value — here there is no successor conversation, so the clear is the point.
`queueStore` is left out too: the queued backlog is selected by matching the active conversation id, and
a `null` active id yields the stable empty backlog via the existing `''` sentinel, so no stale queued
row can render.

**The security payload**, the same one `activateConversation` and `clearPairingScopedState` already
document: clearing the session id makes `RunConfigSections`' `onChange` `undefined`, so the Run
configuration controls render **inert** instead of addressing a YOLO / auto-approval write to a session
that belonged to a conversation the daemon has just destroyed.

## e2e — a required edit, not incidental

Both `e2e/conversation-archive-lifecycle.spec.ts` and `e2e/real-daemon-conversation-lifecycle.spec.ts`
used to click `.conversation__back` immediately after the confirming Delete click to reach the list
before asserting the row was gone. Once the app returns on its own, that control unmounts before the
click runs and Playwright's auto-wait times out — so removing the line was a required edit, not a
cleanup. Each spec now asserts `.conversation` at `toHaveCount(1)` immediately before the confirming
click (the non-vacuity anchor) and at `toHaveCount(0)` immediately after (the navigation proof, auto-
waiting the delete → `conversationDeleted` → exit round trip). The pre-existing row-count assertion
alone does **not** prove the navigation — it's driven by the delete re-list, which already worked
before this ticket — so both specs' comments now say so explicitly.

## Patterns established

- **Reuse `activateConversation`'s clear branch by naming its three-of-five subset explicitly, rather
  than calling `clearPairingScopedState` and documenting which two clears to ignore.** The doc comment
  on `exitActiveConversation` records *why* each of the five candidate stores is in or out — the next
  ticket (#653) can read the reasoning without re-deriving it.
- **A getter, not a threaded value, for the gate's left-hand side** — `activateConversation.ts`'s
  established reason applies verbatim: the bridge callback is held in a ref refreshed by a bare
  (post-commit) effect, so a callback closing over a render-time value could compare against a stale
  previous. `exitActiveConversation` reads `getActiveConversation()` at invocation time instead.
- **`navigateToList` is an injected effect, not a returned boolean**, because AC4 and AC5 are both
  statements about navigation *not* happening — putting the nav inside the gated body makes both directly
  assertable on a spy, where a boolean would push "did it navigate?" into the container glue, which is
  reviewed rather than tested (`PairedShell.test.tsx:7-11`).
- **A second subscription on an already-consumed daemon event is correct, not a duplicate**, the same
  arrangement `conversationListBridge.ts` already documents for `conversationCreated`:
  `conversationListBridge` re-requests the list off `conversationDeleted`; this ticket's bridge only
  navigates and clears. The two touch disjoint state, so delivery order between them is irrelevant.
- **The gate means "this id names the conversation on screen," not "this reply answers a delete I
  issued."** `daemonConnection.ts` emits `conversationDeleted` unconditionally on decode with no
  `in_reply_to` correlation state threaded (#375's deliberate decision — the bare `id` is
  self-sufficient for the list-reflect path). The helper's doc comment states this explicitly so a future
  reader doesn't assume a correlation check exists that isn't there. The fail-direction is safe: every
  move the gate triggers is a clear.

## Lessons learned

(From the PR body's own "Lessons learned" section.)

- **The e2e non-vacuity check was worth running, not just reasoning about.** The author rebuilt with the
  gate's id deliberately mismatched and watched the `toHaveCount(0)` assertion time out against
  `locator resolved to 1 element` — falsifying, rather than assuming, that the `.conversation` 1→0 delta
  is actually caused by this fix and not by some other pre-existing transition.
- **On a primitive return value, `!== null` vs. truthiness is not cosmetic.** The `conversationDeleted`
  arm carries a bare `string` id, and a degenerate `''` is a real value the daemon could emit — falsy,
  so a truthiness check (`if (deletedId)`) would silently drop the exit for that one id. Sibling bridges
  that return objects or arrays don't have this trap; a primitive does. (Code review's SHOULD FIX below
  is exactly this claim, stated in prose in two places but unpinned by a test.)
- **A `real-*.spec.ts` edit needs its own explicit playwright invocation to prove it runs at all.**
  `playwright.config.ts` structurally ignores `real-*.spec.ts`, so a bare `npx playwright test` reports
  nothing about `e2e/real-daemon-conversation-lifecycle.spec.ts` either way — worth invoking
  `--config playwright.real-claude.config.ts` explicitly whenever a change touches a `real-` spec, since
  the default run's silence looks identical to "not affected."

## Code review

**PASS.** Two findings, neither blocking:

- **[SHOULD FIX]** `conversationDeletedBridge.test.ts` doesn't pin the `!== null` guard's load-bearing
  claim above — `subscribeConversationDeleted` is never exercised with a `{ type: 'conversationDeleted',
  id: '' }` event, so a later simplification to `if (deletedId)` would pass the whole suite green while
  silently dropping the exit for a degenerate empty id. Stakes are low (the downstream gate no-ops for
  any real conversation id, since a real active id is never `''`), but the claim is stated twice in prose
  and pinned nowhere. Left as a cheap follow-up, not required for merge.
- **[NIT]** `PairedShell.tsx`'s `{ type: 'back' }` is absolute, so the exit navigates to the list from
  wherever the operator happens to be — not just from the thread. AC4 covers "opened a different
  discussion" but not "left the thread without opening one": confirm Delete → Back → Settings (or
  Archive, or Pair-another-server) → a delayed confirmation still fires `dispatch({ type: 'back' })` and
  yanks the operator to the Channel List from settings/archive/pairServer. Needs a delayed reply to reach
  by hand; the fail direction is benign (the three clears are correct and wanted in that window, and
  `list` is a valid destination). Flagged for #653's seam discussion, not fixed here — the underlying fix
  would be route-aware navigation, not a wider gate.

Also verified: `requestDeleteConversation` has exactly one production call site
(`ConversationScreen.tsx:1699`), so no Archive- or list-side delete path exists to surprise the new
gate; the architect's security-review PASS held (no logging in either new file, session id cleared and
never read/logged/transmitted, no new `contextBridge`/`ipcMain` surface); and the by-hand precedent
citations (`activateConversation.test.ts`'s shared recording array, `pairedRoute.ts`'s absolute
`back → list` arm) both checked out against the actual source.
