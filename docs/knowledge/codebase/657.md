## Patterns established

- **A screen with its own desktop Figma frame (not the mobile frame stretched to the window) is still
  the same container/pure-view split as every prior screen** — `WelcomeScreen`/`WelcomeView` mirror
  `PairingScreen`/`PairingView` exactly, down to the optional dormant-navigation prop
  (`onPair?`/`onPaired?`). The frame being desktop-native changed layout and CSS, not the component
  shape.
- **A dormant screen with zero I/O is the cheapest possible AC7 ("no throw with no Electron bridge")**:
  the container must not acquire even a `bridge ?? window.pyry` line, unlike `PairingScreen`'s — keeping
  it bridge-free makes the no-bridge render trivially safe instead of stub-dependent, and the test can
  skip the `globalThis.window` stub idiom (`App.test.tsx:26-44`) entirely, with a comment saying the
  absent stub *is* the assertion.
- **Visual-fidelity verification without a DOM harness**: `vite-node` renders a screen to static markup
  outside the test run, and the Playwright browsers already installed for e2e screenshot that output —
  enough to numerically diff a dormant screen against its Figma frame (colour, bounding-box, and glow
  comparisons) with no running app and no jsdom. Useful specifically for screens nothing mounts yet.
- **A `scaleY(-1)`-style CSS transform, not edited path data, is the right way to reproduce a Figma
  transform on a ported vector asset** — keeps the `d` and `viewBox` sourced from one file (the mobile
  drawable) rather than hand-adjusting coordinates, and the revert is one CSS line if the flip reading
  is ever contested.

## Lessons learned

(Lifted from the PR body's "Lessons learned" section.)

- **Both Figma frames draw the pyrycode mark vertically flipped relative to what mobile's drawable
  actually renders.** Node `103:749` (this ticket's desktop frame) and `80:2` (mobile's own welcome
  frame) both carry a `-rotate-180 -scale-x-100` transform on `pyrycode-mark 1`; `ic_pyry_logo.xml` is
  rendered unflipped in the mobile app itself. Measured on rendered silhouettes rather than eyeballed:
  unflipped mismatches the Figma asset by 11.3% IoU-gap, flipped by 4.0% (antialiasing noise), and the
  two Figma frames agree with each other to 2.6% — so this is design intent on both frames, not a
  placement artifact unique to the newly-created desktop one, and it is the mobile **app** that diverges
  from its own design. Shipped as one `transform: scaleY(-1)` in `welcome.css`
  (`.welcome__mark`) so the path data and viewBox stay single-sourced from the mobile drawable; reverting
  is that one line. Worth a mobile-side ticket. General lesson: "port the drawable verbatim" is not
  automatically "match the Figma frame" — check the frame's own transform on the node, not just its path.
- **The Figma dev-mode literal trap (light-scheme fallbacks) did not reproduce on this frame.** Node
  `103-744` resolves against the *dark* mode, so every literal it emits (`#e0e2e8`, `#c2c7cf`, `#9dcbfc`,
  `#101418`, `#134a74`, `#003355`) already matched `tokens.css` — contrary to the spec's warning that
  on-primary would come out as `white`. The rule that survives regardless: map by M3 **role name**, never
  by literal, because which mode a given fetch resolves against isn't the caller's to control — it held
  here, but won't always.
- **`vite-node` + the already-installed Playwright browsers can validate visual fidelity for a screen
  nothing mounts.** No running app is needed to numerically diff a screen against its Figma frame —
  render to static markup outside the test run, screenshot it, compare. Precisely the tool for a dormant
  screen, which by definition no running app can show.

## Code review disposition

PASS with one SHOULD FIX and two NITs, none blocking, none applied post-review (all left as documented,
intentional trade-offs — see the [feature doc](../features/welcome-screen.md#edge-cases-and-limitations)
for the footer-contrast one):

- **SHOULD FIX** (not applied) — `.welcome__footer`'s `opacity: 0.55` composites to 4.07:1 against
  `--color-surface`, short of WCAG AA's 4.5:1. `opacity: 0.6` would clear it at 4.61:1 with no visible
  difference at 11px, but AC5 only required "reduced opacity" without pinning .55, and fidelity to the
  frame (and to mobile's own `alpha = 0.55f`) was kept instead. One-line fix available if a later pass
  wants AA compliance on this line.
- **NIT** (not applied, tracked as follow-up) — `settings.css:421` and `conversation.css:1784-1786` now
  contain a stale comment claiming `--color-on-primary` doesn't exist; this ticket added it. Retro-
  fitting those two switch-knob substitutions to the new token is out of scope here per
  "don't refactor adjacent code while you are there."
- **NIT** (verified, not a defect) — the `scaleY(-1)` mark flip was independently re-verified by the
  reviewer (rasterized-silhouette IoU comparison) rather than taken on the PR's claim; confirmed genuine
  frame intent, called out as a decision worth a human's eyes rather than a hidden diff.
