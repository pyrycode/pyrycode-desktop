# #66 — Composer send: submit a message with an optimistic local echo

**Shipped:** 2026-07-07 · **Size:** S · **Scope:** renderer-only (`src/renderer/`) · one new pure module + two modified files · no transport / preload / IPC / dependency change.
**Spec:** `docs/specs/architecture/66-composer-send-optimistic-echo.md` · **PR:** [#74](https://github.com/pyrycode/pyrycode-desktop/pull/74). Split from [#11](https://github.com/pyrycode/pyrycode-desktop/issues/11); was blocked by [#69](69.md) (the store→thread binding, now merged).

The **renderer half of the send flow** — the counterpart to [#65](65.md)'s main/transport half. Wires the previously-inert conversation composer: typing drives controlled input state; submit (send button or Enter) mints a `message_id`, emits a `sendMessage` command over the existing bridge (`window.pyry.sendCommand`, main receiver landed in [#65](65.md)), and appends the just-sent message to the [session store](../features/session-store.md) optimistically. Because the store dedupes by `message_id` (`appendUnique`, added in #27), the daemon's later echo of the same id drops instead of double-posting — so the sent bubble appears instantly and never doubles. The optimistic echo only becomes *visible* because [#69](69.md) bound the thread to the store; the two tickets share the store as their seam (#66 appends a wire `MessagePayload { role: 'user' }`; #69 renders `role: 'user'` → a `user` bubble).

See the [Composer send feature doc](../features/composer-send.md) for the full behaviour spec and data flow.

## Patterns established

- **The pure-logic / thin-container split, third instance.** `submitMessage` is a framework-free function whose effects are injected, tested directly with spies; the React `Composer` is thin glue. Same shape as [`pairingState.ts`](../features/pairing-input-screen.md) (`runSubmit`) and [`messageViewModel.ts`](../features/conversation-shell.md) (`toMessageViewModel`) — the pure choke point is tested, the thin React wiring is not. Co-located with the screen, no React/store/Electron import.
- **One minted id, reused for both sides — the dedupe seam (AC3).** `message_id` is minted **once** in `submitMessage` (via injected `newMessageId`, `crypto.randomUUID()` in the container) and carried by both the wire `SendMessagePayload` and the optimistic `messageSent` echo. That shared id is what lets the store's existing `appendUnique` drop the daemon's later echo of the same message instead of double-posting. The store owns dedupe (ADR 0004); the composer's only obligation is to keep the two ids equal.
- **Guarded send, unconditional echo (AC4).** The `sendCommand` call is wrapped in `try/catch` (`console.error`, swallow) so a bridge failure never crashes the window. The optimistic echo is dispatched and the input cleared **regardless** of the send outcome — "optimistic" means show-immediately, and this milestone has no send-failure UI surface.
- **`window.pyry` dereferenced only at interaction time.** `handleSubmit` builds its `deps` (including `window.pyry.sendCommand`) **inside the handler body**, never during render — so the server-rendered `ConversationScreen` smoke test never touches the bridge and stays green. Same reason the pairing container defers its `window.pyry` reference to handlers.
- **Additive union arm, zero edit fan-out.** `messageSent` extends the sealed `SessionAction` union cleanly; the `assertNever` exhaustiveness guard is the only forced edit. `translateDaemonEvent` (the [daemon-event bridge](../features/daemon-event-bridge.md)) returns a *subset* of `SessionAction` and produces no `messageSent`, so it needed no change — `messageSent` is dispatched only by the composer.
- **Milestone conversation id as a single-change-point constant.** There is no conversation-selection surface and no pre-existing conversation id in the renderer (`HelloAckPayload` carries `server_id`/`conn_id`, not a conversation; the message list is empty until the first message). `MILESTONE_CONVERSATION_ID = 'default'` is the correct source per the ticket, and the daemon treats `conversation_id` as opaque (echoes back whatever it is sent).

## Lessons learned

*Lifted from PR #74's "Lessons learned" section.*

- **The optimistic echo carries the wire `MessagePayload { role: 'user' }` shape — not the placeholder `Message` view-model shape — and the wire command uses `SendMessagePayload` (no `role`).** Keeping the store append on the wire contract (`role`, `message_id`, `conversation_id`, `text`) is precisely what lets the daemon's later same-`message_id` echo dedupe against it: the store holds wire types verbatim (ADR 0004), the daemon echoes a wire `MessagePayload`, so both the optimistic copy and the echo hit `appendUnique` in the same shape and the id match fires. Had the composer appended the presentation `Message` (`type`, `id`) shape instead, the store would hold a foreign shape and the dedupe key would never line up. The `role: 'user'` is also load-bearing for render: [#69](69.md)'s `toMessageViewModel` maps `role: 'user' → type: 'user'`, so the echo renders as a right-aligned user bubble.

No React re-render / effect-cleanup / dependency-version surprises: `Composer` has no `useEffect`, no timers, no subscriptions. Submit is synchronous and handler-driven — nothing outlives the click, nothing to tear down. `useState('')` re-renders only `Composer` on keystroke; selecting the stable `dispatch` adds no churn; the thread re-renders separately off `selectMessages` when the echo lands.

## Deferred / carried forward

- **DOM interaction is not tested yet.** Only the pure `submitMessage` is unit-tested. The container wiring — `onChange` updating `value`, Enter-to-send vs Shift+Enter-newline, clear-on-success — has no test, because the render harness is `renderToStaticMarkup` (node env, no DOM events), not jsdom. The existing server-rendered smoke tests only assert the `<textarea>` and `aria-label="Send"` still render. Closing this needs the same jsdom/Testing-Library harness [#69](69.md) deferred — carried forward together.
- **No send-failure UI / echo rollback.** The echo posts even when `sendCommand` throws; there is no per-message delivery state, banner, retry, or rollback. A future ticket that adds per-message delivery status may want to mark or roll back an echo whose send failed. Out of scope here (flagged in the spec's Open Questions so it isn't mistaken for an oversight). The main-side twin [#65](65.md) similarly drops a failed send silently; delivery UX likely lands with the reconnect/status choreography ([#34](https://github.com/pyrycode/pyrycode-desktop/issues/34)/[#35](https://github.com/pyrycode/pyrycode-desktop/issues/35)).
- **Milestone conversation id value.** `'default'` is arbitrary-but-stable; if the daemon or #65's main-side path ever expects a specific id for the single milestone conversation, `MILESTONE_CONVERSATION_ID` is the one change point. No such expectation is visible in the wire contract.
- **Auto-grow textarea.** The `rows={1}` textarea does not grow with multi-line input; auto-grow was named as in-scope for the composer slice in earlier notes but is cosmetic and unbuilt. Not required by any AC.
