# #662 — Make the welcome screen the unpaired app root

Split from #658 (scaffolding half; #661 built the shared e2e arrival step this ticket relies on).
Spec (architect, self-reviewed security-sensitive), shipped `1d95531`, PR
[#666](https://github.com/pyrycode/pyrycode-desktop/pull/666). Size S (as estimated, compile-atomic —
no split). Code review: **PASS**, one SHOULD FIX (unresolved — see below) and one NIT (this doc).

## Summary

`routeForStatus` (`appRoute.ts`) and the rejected-launch-query catch arm (`App.tsx`) — the two
launch-time non-paired fallbacks — now both land on the new `welcome` route instead of `pairing`.
`AppRoute` gains `'welcome'`, and `routeForStatus`'s return type narrows from
`Exclude<AppRoute, 'pending'>` to `Exclude<AppRoute, 'pending' | 'pairing'>`: pairing is no longer a
*launch* destination at all after this ticket, only a place reached by user action.

`WelcomeScreen`, which shipped dormant in #657 (nothing mounted it), is now that launch destination.
Its `onPair` prop is wired to a new `AppView` prop, `onPairRequested`, which flips the route to
`pairing`. `PairingScreen`'s existing-but-unwired `onCancel` seam is wired for the first time, via a
new `onPairingCancelled` prop, back to `welcome` — the two seams both shipped in earlier tickets purely
as future navigation posture (`PairingScreen.tsx:163`), and this is the ticket that finally calls them.

The fail-safe ternary (ADR [0005](../decisions/0005-secret-at-rest-safestorage-fail-closed.md)) keeps
its exact shape — `status.status === 'paired' ? 'conversation' : 'welcome'` — and picks up a
type-level strengthening: because the return type no longer includes `'pairing'`, a future
launch→pairing mapping would be a compile error, not a silent behaviour change.

The mid-session `onUnpaired` flip (`App.tsx:133`, from #166) is **unchanged** — it still routes to
`pairing`, deliberately: an operator who just unpaired is re-pairing, not landing cold, so the pairing
screen stays the right destination for that flip specifically. `e2e/unpair-repair.spec.ts`, which
exercises that flip, is byte-unchanged (`git diff --stat` empty), serving as the negative control that
this ticket did not over-reach into the session-exit path.

On the e2e side, #661's shared step `pairFromUnpairedLaunch` (`e2e/fixtures/pairingArrival.ts`) needed
exactly the one-line edit it was built for: a click on the welcome screen's `I already have pyrycode`
CTA prepended ahead of the existing six lines, with the `pasteBox` visibility wait kept — its meaning
shifted from "settle pending→pairing" to "the CTA hop actually landed on pairing", the only executable
proof of the welcome→pairing hop across all ten call sites. `smoke.spec.ts`'s unpaired-boot assertion
flipped from `.pairing` to `.welcome`, and gained a second test round-tripping welcome → CTA → pairing
→ Cancel → welcome (an addition beyond the ticket's literal wording, flagged and accepted in the PR
body, since AC4 — cancel returns to welcome — otherwise shipped with zero executable coverage: the
renderer test tier is server-render only and cannot fire a callback).

## Patterns established

- **A type-level exclusion is a stronger fail-safe than a matching return value.** Narrowing
  `routeForStatus`'s return type to exclude `'pairing'` (not just reproducing the pre-ticket output)
  means a future regression — someone routing a launch outcome back to `pairing` — fails to compile
  instead of silently reintroducing the pre-#657 UX. Worth reaching for whenever a function's output
  set legitimately shrinks: encode the shrink in the type, not just the body.
- **Required props over optional ones when a switch is `assertNever`-guarded.** `onPairRequested` and
  `onPairingCancelled` were added as required, not optional, specifically so that forgetting to wire
  either at the single call site (`App.tsx`) fails the build rather than shipping a silently dead-end
  CTA. The `assertNever` guard on `AppView`'s switch is only as strong as the props feeding into it.
- **A shared e2e step's payoff shows up in the comment budget, not just the code budget.** #661
  collapsed ten pairing drives into `pairingArrival.ts` specifically so this ticket's e2e half would be
  a one-line edit — and the code was exactly that. What took longer was updating four prose references
  across two files that had been written in the future tense, anticipating this exact ticket. A seam
  built ahead of its consumer accrues comment debt that doesn't shrink the way the code diff does.

## Lessons learned

(From the PR body's own "Lessons learned" section.)

- **A shared-step module pays off in the comment budget, not just the code budget.** See "Patterns
  established" above — the module's *prose* had accumulated four forward-references to this ticket,
  and updating those was the larger part of the e2e diff.
- **"Keep the redundant-looking wait" was load-bearing.** After the new CTA click settles
  `pending → welcome`, `await expect(pasteBox).toBeVisible()` looks like a leftover — it isn't. Its
  meaning changed from "settle the route" to "the CTA hop actually landed on pairing," the only
  executable proof of the welcome→pairing navigation across all ten drives. Deleting a wait that a
  preceding action now seems to subsume can silently delete an assertion.
- **A `real-*` failure's line number is the fastest provenance check.** The one `real-claude` failure
  (`real-daemon-session-settings.spec.ts:72`, `selectedRadioIn('Sonnet')` timeout) sits ~60 lines past
  the segment this ticket touches, on a locator unrelated to routing — which classified it as
  pre-existing before consulting [#661's codebase notes](661.md), which had already verified it
  reproduces identically on `main`.

## Code review

**PASS.** One finding left unresolved at merge, one NIT (addressed by this doc):

- **[SHOULD FIX, unresolved]** `e2e/smoke.spec.ts`'s round-trip test asserts
  `await expect(page.locator('.conversation')).toHaveCount(0)` as its Cancel-doesn't-leak-to-conversation
  proof. This is **vacuous**: `.conversation` is `ConversationScreen`'s own root class
  (`ConversationScreen.tsx:167`), but the `conversation` *route* mounts `PairedShell`, which enters at
  `'list'` (`PairedShell.tsx:148`) and renders `.channel-list`, not `.conversation` — so the assertion
  reads count 0 whether or not Cancel wrongly routed to `conversation`. It also can't fail for the
  regression it claims to guard: `expect(welcome).toBeVisible()` earlier in the same test already
  proves the route is `welcome`, and the app's routes are mutually exclusive arms of one `switch`. The
  reviewer's suggested fix — assert `.channel-list` instead, or drop the line and trim the claim in the
  adjacent comment — was not applied before merge; still open as of this writing.
- **[NIT]** `docs/knowledge/features/app-shell.md` (plus `welcome-screen.md` and
  `pairing-input-screen.md`, found in the course of applying this fix) were stale in multiple places —
  the pairing-as-root framing, the two-screen route diagram, the "onCancel deliberately unwired"
  section. Addressed in this documentation pass.
