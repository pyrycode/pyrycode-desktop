# #664 — Identify the pairing field by its aria-label alone, not by element type or card heading

Split from #613 (blocks #665). Spec (architect, self-reviewed `security-sensitive`), shipped
`3ac5958`, PR [#667](https://github.com/pyrycode/pyrycode-desktop/pull/667). Size S (as estimated).
Code review: **PASS**, two NITs (both non-blocking wording nits, not reworked). Zero production
code — the entire diff is test-side selectors, markers, and comments.

## Summary

Every site outside `src/renderer/src/screens/pairing/` now locates the pairing field by
`aria-label="Pairing code"` alone — never by the `<textarea>` element type, never by the
`Paste pairing code` card heading — so #665's restyle (an M3 filled `<input>`, hero holding only the
field, heading dropped) can swap the markup without a silent-green cascade. `e2e/` sits outside both
tsconfigs and the two unit markers are plain string matches against `renderToStaticMarkup` output, so
none of the six original breakages were compile-enforced; a bare `playwright test` additionally skips
every `real-*` spec.

Eleven sites across five files (the spec doc found five comment sites the ticket's own six-site table
missed — AC1 covers prose, and the ticket's selector-grep can't see a comment that names the element
without the full selector string):

- `e2e/fixtures/pairingArrival.ts` — the `pasteBox` locator (`:54`) plus three header comments
  (`:5`, `:23`, `:31` INVARIANT 4).
- `e2e/unpair-repair.spec.ts` — two `pairingBox` locators (`:42`, `:73`) plus two header comments
  (`:13`, `:15`).
- `e2e/paired-shell-navigation.spec.ts` — the renamed `pairingEntry` → `pairingField` locator (`:47`),
  now `page.locator('[aria-label="Pairing code"]')`.
- `src/renderer/src/App.test.tsx` — `PAIRING_MARKER` (`:22`) now `'aria-label="Pairing code"'`.
- `src/renderer/src/PairedShell.test.tsx` — `PAIRING_MARKER` (`:32`) plus its comment, same rewrite.

`getByLabel` was deliberately **not** introduced (it resolves by accessible name, so once #665 wraps
the filled field in a `<label>` it would match twice and reintroduce the count ambiguity this ticket
removes) — the suite's existing attribute-selector idiom (`[aria-label="…"]`, already used for
`section[aria-label="Conversations"]` and `[aria-label="Server key fingerprint"]`) is used everywhere
instead.

`pairingArrival.ts`'s INVARIANT 4 previously told the reader *not* to finish this sweep — it named
`unpair-repair.spec.ts` staying byte-unchanged as #662's negative control and said its two locators
"stay correct exactly as written." That control had already served its purpose (per #664's own ticket
body), so the directive was retired while the still-true half survived: `unpair-repair.spec.ts` is not
a `pairFromUnpairedLaunch` caller and converting it into one remains out of scope — its locators sit
after a mid-session unpair flip, not an unpaired launch.

## Patterns established

- **A single shared binding per marker is what makes a negative assertion non-vacuous, not the
  inversion check alone.** Inverting `unpair-repair.spec.ts`'s `toHaveCount(0)` to `(1)` fails
  identically whether the locator is live or stale — both read count 0 on a live thread. What actually
  discriminates the two: `pairingBox` (and `PAIRING_MARKER` in `App.test.tsx`) is asserted **both**
  negatively and positively from the *same* const. A stale locator fails loudly at the positive site
  (`:65` `toBeVisible()`, `App.test.tsx:87` `toContain`). The rule this ticket leaves behind: never
  inline the selector at the positive site, never split it into a second const — two independently
  typed strings that agree today can silently diverge later, and the moment they do the negative half
  goes vacuous again.
- **A prose mention of the very string a sweep is retiring breaks the sweep's own completeness grep.**
  First pass explained the change in comments that quoted `Paste pairing code` and `getByLabel`
  verbatim, pushing those greps to 5 and 1 against targets of 4 and 0 (recorded in the PR's own
  "Lessons learned"). When `grep → N` *is* the acceptance test, the abandoned vocabulary is off-limits
  in new prose too — describe it obliquely ("the screen's card heading", "the accessible-name query
  helper") instead of quoting it.
- **An in-repo comment that instructs the reader not to do the current ticket must be retired precisely
  along its claim boundary, not wholesale.** `pairingArrival.ts` INVARIANT 4 carried two claims: a
  still-true one (`unpair-repair.spec.ts` isn't a caller) and an expired one (the "do not finish the
  sweep" directive whose control had already served its purpose). Only the expired half was removed.

## Lessons learned

(From the PR body's own "Lessons learned" section.)

- **A prose mention of a forbidden token breaks a bare-word acceptance grep.** Quoting `Paste pairing
  code` and `getByLabel` verbatim inside explanatory comments — even while removing them as *locators*
  — inflated the completeness greps that check for their absence. Worth remembering for any future
  ticket whose deliverable is "this string no longer appears": the ticket's own vocabulary is unsafe to
  quote in the replacement prose.
- **Inverting a count-0 assertion is weaker evidence of non-vacuity than it looks.** It fails the same
  way under a stale selector as a live one. The check that actually discriminates is typo-ing the
  shared binding and confirming the count-0 half passes *silently* while a positive assertion sharing
  that binding fails loudly — the structural (one-binding, both-directions) guarantee, not the one-off
  inversion.

## Code review

**PASS.** Two non-blocking NITs, neither reworked:

- **[NIT]** `paired-shell-navigation.spec.ts:44`'s comment ("the accessible-name query helper is
  deliberately absent from this whole suite") is opaque unless the reader already knows it means
  `getByLabel` — a deliberate omission per the lesson above (naming it would push the AC2 grep to 1),
  flagged only so a future reader doesn't read the vagueness as sloppiness.
- **[NIT]** `unpair-repair.spec.ts:24`'s "do not split it into a second const" reads as slightly
  contradicted by `:73`'s second `pairingBox` declaration — it's a different `test()` block whose only
  usage is positive, so there's no vacuity risk, but the sentence doesn't scope itself to "the first
  test" explicitly.

All four completeness greps were re-derived independently by the reviewer rather than taken on the PR
body's word, and landed exactly on target: 0 occurrences of `textarea[aria-label="Pairing code"]`, 4
occurrences of bare `textarea` (all `ConversationScreen.*`, the composer's own field, unrelated), 4
occurrences of `Paste pairing code` (all inside `src/renderer/src/screens/pairing/`, untouched), 0
occurrences of `getByLabel`. Marker uniqueness (`aria-label="Pairing code"` has exactly one production
occurrence, `PairingScreen.tsx:96`) and the `pairingEntry` → `pairingField` rename's completeness were
also independently re-verified. The `real-daemon-session-settings.spec.ts:72` `real-*` failure was
confirmed pre-existing by reverting `pairingArrival.ts` to `main` and re-running that spec alone.
