# #665 — Pairing screen: restyle the paste phase to the desktop Pair Screen frame (103-2901)

Split from #613 (after [#661](661.md), [#662](662.md) and [#664](664.md)). Spec:
`docs/specs/architecture/665-pairing-paste-phase-desktop-frame.md`, architect self-review
`security-sensitive` PASS. Shipped `159dd9c` + rework `c2e4381`, PR
[#668](https://github.com/pyrycode/pyrycode-desktop/pull/668). Size S (as estimated). Code review:

NITs (comment-wording only) left open.

## Summary

The pairing screen's paste phase becomes a full-window page drawn from desktop's own Figma frame
`103-2901` (1280×1024), replacing the 420px dialog card it had inherited from mobile's `19-54`: the
radial glow over `--color-surface`, `--space-7`/`--space-8` frame padding, an M3 filled `Pairing code`
field inset 64px inside the content column, a supporting line carrying the instruction or the mapped
error, and a bottom-pinned CTA stack (`Pair` pill, bare `Cancel` row, the open-source footer). Behaviour
is unchanged apart from one new control — a clear button in the field's trailing slot, present only on a
non-empty paste, that writes a constant `''` through the existing `onPasteChange` seam. The fingerprint
confirm and paired phases keep the card treatment untouched; they have no frame yet.

Four files, no new files: `PairingScreen.tsx` (`EntryCard` → `EntryPage`, phase-derived root class),
`pairing.css` (`.pairing` split into a shared base + `.pairing-card` / `.pairing-page` siblings, plus a
new `.pairing-field*` block), `PairingScreen.test.tsx`, and one line of `scripts/live-drive.mjs`.

## Class taxonomy

`.pairing` is reduced to what the card and page treatments share (`box-sizing`, `flex` column, colour,
font) and **stays on the root in every phase** — it is an e2e contract, not a style choice:
`e2e/smoke.spec.ts:81` binds `.pairing` once and asserts it visible after the welcome CTA and count-0
after Cancel. `.pairing-card` and `.pairing-page` are siblings, not overrides — neither undoes a property
the other sets, which is what keeps the two treatments separable for the eventual confirm-phase lift
(described in the spec as "a class swap on the root, not a rewrite"). Root class is derived from the
phase the view already branches on:

```ts
const isPaste = state.phase === 'editing' || state.phase === 'submitting'
// className={`pairing ${isPaste ? 'pairing-page' : 'pairing-card'}`}
```

## The field

An M3 filled field (`.pairing-field`) with no wrapping `<label>` — deliberately. HTML forbids interactive
content inside a `<label>`, so the clear `<button>` couldn't share the field's row under that idiom; and
a wrapping label would put a *second* element under the accessible name "Pairing code", reintroducing the
count ambiguity [#664](664.md) had just removed. The visible label is an `aria-hidden` `<span>`; the
`<input>` carries the literal `aria-label="Pairing code"` attribute that six outside consumers (four e2e
attribute selectors, two test markup-substring markers) match as a raw string. `PairingScreen.test.tsx`
now asserts that exact-count-1 as a deterministic tripwire under the stochastic contract.

Hygiene attributes: `type="text"` (not `password` — the operator may need to eyeball the value; not
`url` — the payload is base64url, not a URL), `autoComplete="off"`, `spellCheck={false}`, no `name`, no
`id`, no `<form>` ancestor. The placeholder is dropped rather than restyled: the frame draws none, and
the old string (`pyry://home.lan:7117?token=…`) misdescribed the payload shape
(`pairingPayload.ts:89,108` requires strict base64url).

The container's 72% fill lands on a `::before` pseudo at `opacity`, per the house rule against bare
`rgba()`/`color-mix()` literals. `.pairing-field__row` needs `position: relative` — the absolutely
positioned fill has `z-index: auto` and paints *above* non-positioned in-flow siblings, so without it the
label/input/glyph would be hidden behind the fill.

## The clear control

Rendered only when `paste !== ''` (literal-empty, not `.trim()`), never rendered `disabled` — it needs no
`busy` guard because `pairingReducer`'s `paste-changed` arm is already a no-op outside `editing`
(`pairingState.ts:64-68`). Its accessible name, `Clear pairing code`, is distinct from both `Pairing code`
and `Pair` (the latter is C3: ten `pairingArrival` drives plus `live-drive.mjs` match `Pair` with
`exact: true` while the clear control is on screen). `onClick` writes a constant `''` — the handler never
reads the paste it discards.

## Error handling: the reconciliation bug (MUST FIX, resolved)

Code review's blocking finding: the supporting slot's two `<p>` branches (instruction vs. error) read as
two elements in JSX but reconcile as **one DOM node**. Both are a `<p>` at the same array position with
`key === null`, so React's `updateSlot` matches the slot and `updateElement` sees
`current.elementType === elementType` (`'p' === 'p'`) and reuses the existing fiber — no `Placement`
effect, no insertion. A failed submit was mutating a *live* node's `role` to `alert` in the same commit
that rewrote its text — exactly the "flipping role on a live element is unreliable across screen readers"
failure mode the architecture spec had explicitly ruled out, reached by a route the spec hadn't
anticipated (mutually-exclusive sibling JSX, not a single element's flipped prop). It was also a
regression against `main`, where the error slot held nothing until an error arrived, so a failed submit
genuinely inserted a fresh live region.

Fix: distinct `key="instruction"` / `key="error"` on the two `<p>`s, forcing the reconciler down the
delete-then-place path instead of the reuse path. **Caveat for future readers, recorded in-file:** keys
only force a re-place if the slot *alternates* between renders — this ticket is safe only because the
reducer forces `error` to `null` on every path through `submitting` (`PairingScreen.tsx:86`), so the slot
provably cycles error → instruction → error and two consecutive errors without an intervening insertion
are structurally impossible. A supporting slot that could show error A then error B directly, with the
same key surviving both, would still mutate a live node.

Verified in a real DOM (server-render tests can't see this): drove the built app with Playwright,
confirmed the error `<p>` is a *new* node (`dataset.probe` goes from `"original-instruction-node"` to
`null` with `role: "alert"`) while the **sibling** field div survives re-render unrebuilt (input node
identity + focus/caret intact) — the reconciler's fast path resolves the field div at index 0 before the
key mismatch at index 1 breaks it.

## Two SHOULD FIX, also resolved in the rework

- **Focus indicator was a 1.00:1 hue-only flip.** `--color-on-surface-variant` (`#c2c7cf`, L=0.5684) and
  `--color-primary` (`#9dcbfc`, L=0.5691) are indistinguishable in greyscale or under a blue-yellow
  deficiency, and with `outline: none` on the input that flip was the *entire* keyboard-focus affordance
  — below WCAG 1.4.11's 3:1 floor, and worse than what it replaced (`--color-outline` was 1.87:1). Fixed
  with an **outset** `box-shadow: 0 1px 0 var(--color-primary)` on `:focus-within`, doubling the
  indicator's thickness (a non-colour cue) instead of relying on hue. Outset, not inset: an inset shadow
  would paint under the `::before` fill and wash out at 72% opacity.
- **Clearing the field dropped focus to `<body>`.** The clear control unmounts itself the instant
  `paste === ''`, and a self-removing focused element falls back to `document.body` — ejecting a keyboard
  or screen-reader user to the top of the tab order on a screen with no heading and only three named
  controls. Fixed by returning focus to the input (`inputRef.current?.focus()`, the
  `ConversationScreen.tsx:2099-2107` focus-return idiom) in the same click handler, before the unmount
  commits.

## Patterns established

- **Mutually exclusive sibling JSX with the same tag and no key is ONE DOM node to React, not two.**
  `{cond ? <p>A</p> : <p>B</p>}` at the same array position reconciles via `updateSlot` → `updateElement`,
  which reuses the fiber whenever `elementType` matches — regardless of how different the two branches'
  props or children are. A `role="alert"` (or any prop meant to fire on *insertion*, not on *mutation*)
  needs a `key` that changes between the branches, or an entirely different element type. This is a
  general React trap, not specific to accessibility — anything relying on mount/unmount semantics
  (animation triggers, `IntersectionObserver` re-attach, `key`-driven remount-to-reset) hits the same
  wall on a same-tag ternary.
- **Keys only re-place if the slot alternates between renders.** The fix here is only complete because
  the reducer's `error` value is forced to `null` between any two errors (routes through `submitting`).
  A supporting slot that could show two different error variants back-to-back with the same discriminant
  would still need per-content keys, not just per-branch keys.
- **Verify DOM-identity claims by probing the node that's supposed to survive, not just the one that's
  supposed to change.** The `inputSurvivedRerender` probe (checking the *sibling* field div's node
  identity, not just the error `<p>`'s) was the check that would have caught a broader breakage — if the
  keyed fix had accidentally also remounted the field div, the caret/focus would have been lost even
  though the error announcement worked.
- **`fill()` in a Playwright/DOM probe focuses the element it fills** — measuring a "resting" computed
  style immediately after `fill()` actually measures the *focused* style. Blur before reading a resting
  value. (First focus-indicator measurement in this PR's rework read as a no-op for exactly this reason.)
- **An absolutely-positioned `::before` with `z-index: auto` paints above non-positioned in-flow
  siblings.** The translucent field fill needed the sibling row to be `position: relative`, not a
  negative `z-index` on the pseudo (which would drop it behind the parent's own background too).
- **`inset: 0` on a fill pseudo resolves against the padding box, not the border box** — so it never
  covers a `border-bottom`, which is what lets the field's 1px active indicator be a plain border rather
  than a separate always-on-top element.
- **The canonical Material `highlight_off` glyph path already carries the frame's 8.33% inset** — its
  ring spans 2..22 in a 24-box, exactly the 20×20 art Figma exports inside a 24×24 box. A `viewBox` "fix"
  for that would double-inset the glyph.
- **A wrapping `<label>` can be structurally impossible, not merely undesirable, once an interactive
  sibling needs to live in the same row.** Worth checking before reaching for `RenameConversationDialog`'s
  field as a template — its wrapping-`<label>` accessible-name mechanism is exactly the piece that doesn't
  transfer here.
- **Aliased discriminant narrowing covers a multi-arm union at the alias site.**
  `const isPaste = state.phase === 'editing' || state.phase === 'submitting'` still narrows
  `state.paste` correctly downstream — deriving the root class from the phase cost no repeated comparison
  and no cast.

## Lessons learned

(From the PR body's own "Lessons learned" section — see § Patterns established above for the ones that
overlap; these are additional or restate with different framing.)

- A prose "fix" that reads as more robust (an inset shadow, a negative z-index, a `useEffect`-deferred
  focus call) is sometimes the *wrong* direction — each of those was the tempting alternative to the fix
  actually shipped, and each would have been strictly worse (washed-out shadow, pseudo behind the wrong
  layer, a focus call racing the button's unmount).

## Code review

**FAIL → PASS**, two rounds. First round: 1 MUST FIX (the reconciliation bug above) + 2 SHOULD FIX (focus
indicator contrast, focus drop on clear) + 4 NIT. Rework (`c2e4381`) resolved the MUST FIX and both
SHOULD FIX, took one of the four NITs (`.pairing-field__input:disabled { opacity: 0.38 }`, restoring the
in-flight dimming the `<textarea>` had), and added the `submitting`-phase test a second NIT asked for.
Second round: **PASS**, two NITs left open (both comment-wording only, neither gating) — one on a
misleading "the button's mount state" phrasing in the focus-return comment (the *input's* mount state is
what actually matters), one on a citation that names the opposite CSS idiom (`inset`) from the one the
surrounding sentence argues against (`outset`).

Reviewer independently re-walked React's `reconcileChildrenArray` against the actual two-child array
(`[div.pairing-field, <p>]`) rather than taking the key fix on faith, and re-verified C1/C2/C3, the AC9
grep, and the security posture (no logger/diagnostic-channel call added; `inputRef` holds a DOM node,
never the paste value) in both rounds.

**Not addressed in this PR, deferred to documentation** (per the reviewer's "Handoff to documentation"
note): `docs/knowledge/features/pairing-input-screen.md` and `docs/knowledge/codebase/55.md` both still
described the pre-#665 `EntryCard`/`<textarea>` shape. The feature doc is updated as part of this
documentation pass; `codebase/55.md` is a sibling ticket's frozen per-ticket record and is left as an
accurate account of what #55 shipped at the time — current behaviour lives in the feature doc and here.
