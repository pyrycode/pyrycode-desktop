# #69 — Render streamed daemon replies in the conversation thread

**Shipped:** 2026-07-07 · **Size:** XS · **Scope:** renderer-only (`src/renderer/`) · one 1-line binding swap + one new ~36-LOC adapter, two files deleted · no transport / preload / IPC / dependency change.
**Spec:** `docs/specs/architecture/69-render-streamed-daemon-replies.md` · **PR:** [#73](https://github.com/pyrycode/pyrycode-desktop/pull/73). Split from [#12](https://github.com/pyrycode/pyrycode-desktop/issues/12).

The **renderer half** of showing a daemon reply: bind the [conversation shell](../features/conversation-shell.md)'s message thread to the live [session store](../features/session-store.md) so streamed replies render in the window. The background decode that fills the store already landed ([#68](68.md)); this ticket swaps `MessageThread`'s data source from the static `placeholderMessages` array to `useSessionStore(selectMessages)`, adapting each wire `MessagePayload` to the shell's `Message` view model at the component boundary. This is the seam [ADR 0004](../decisions/0004-renderer-session-store-reducer-wire-types.md) deliberately deferred (store holds wire types verbatim; the `role`/`message_id` presentation transform is the component's job) and the [conversation-shell feature doc](../features/conversation-shell.md) named ("keep the array the sole data source so the swap stays one line"). With this, the end-to-end path is closed: daemon frame → [#68](68.md) decode → [daemon-event channel](../features/daemon-event-channel.md) ([#18](18.md)) → [bridge](../features/daemon-event-bridge.md) ([#19](19.md)) → [session store](../features/session-store.md) ([#2](2.md)) → thread render.

## Patterns established

- **The wire→view-model transform lives at the store-read boundary, in its own framework-free module.** `messageViewModel.ts` sits beside the component but imports no React and no store, so the adapter unit-tests as a pure function — the same "pure choke point is tested directly, thin React wiring is not" split the renderer already uses ([session store](../features/session-store.md)'s pure `reduceSession`, [daemon-event bridge](../features/daemon-event-bridge.md)'s translate). Adapting in `ConversationScreen` (not inside `MessageThread`) keeps `MessageThread`'s `Message[]` prop and `MessageBubble` untouched, honouring the feature doc's seam contract.
- **Container/view split, mirroring `PairingScreen`/`PairingView` ([#55](55.md)).** `ConversationScreen` is the store-bound container; the now-**exported** `MessageThread` is the pure view. Tests server-render the pure view with hand-built `Message[]` to prove ordering + role→type rendering, and smoke-test the container for "reads the store, not the old array." This split is what makes the render testable without a DOM harness — see Lessons.
- **`assertNever` on `WireRole` makes a future third role a compile error, not a silent `'user'`.** The adapter's exhaustive `switch (m.role)` mirrors the sealed-union idiom in `reduceSession` / `translateDaemonEvent`. `WireRole` is a sealed two-member union over already-validated wire payloads (decoded upstream in [#68](68.md)), so the switch is total and needs no runtime guard for malformed input.
- **No `useMemo`, no re-sort, no coalesce — the render is a straight `.map` over the slice in store order.** The store already dedupes by `message_id` and preserves arrival order (`appendUnique`, ADR 0004); `message_chunk` batches carry complete messages, so there is no streaming-token assembly. The per-render `.map` is O(n) over a small thread and only runs when `selectMessages` changes reference (a new message landed) — no observed perf issue, so no pre-optimization (evidence-based-fix rule).
- **Narrow-slice selection is the re-render guard, and it is proven at the store level, not re-proven here.** `useSessionStore(selectMessages)` subscribes to the `messages` slice only; `reduceSession` returns the same `messages` reference on every status action, so Zustand's `Object.is` skips the thread re-render on a connection-status change. `sessionStore.test.ts:135-144` already pins this; the component just consumes it.
- **Empty store → empty thread, no new guard code.** `selectMessages` returns `[]` on `initialSessionState`; `[].map(...)` is `[]`; the existing `messages.map` in `MessageThread` renders an empty scroll region. No placeholder fallback, no crash.

## Lessons learned

*Lifted from PR #73's "Lessons learned" section.*

- **zustand v5's `useStore` uses `getInitialState()` — not `getState()` — as the `useSyncExternalStore` server snapshot.** So `renderToStaticMarkup` (a *server* render) always reflects the store's **initial** state; a dispatch-then-server-render never shows the dispatch. The spec's Open Question assumed `getState`. This is the trap for any future test that server-renders a store-bound container expecting to see dispatched data — it will silently see the empty initial state. Resolved by leaning on the repo's existing container/view split: the pure `MessageThread` is server-rendered with arbitrary `Message[]` (proving order + role→type end-to-end), while the store-bound `ConversationScreen` gets only a "renders without throwing / empty store → empty thread" smoke test. The reactive store→UI path stays proven at the store level (`sessionStore.test.ts`) and the adapter in its own unit test — no DOM harness, no new dependency. A client-render (jsdom) harness would be the only way to *server-observe* a populated container render; that remains deferred (per [#1](1.md)).

No React re-render / effect-cleanup / dependency-version surprises beyond the snapshot gotcha above: this component has no `useEffect`, no timers, no subscriptions (the daemon-event subscription lives in `useDaemonEventBridge`, already wired in `App.tsx`); it is a pure reader with nothing to tear down.

## Deferred / carried forward

- **Composer send + optimistic echo → [#66](https://github.com/pyrycode/pyrycode-desktop/issues/66).** The composer stays inert this ticket (uncontrolled `<textarea>`, no `onClick`). Controlled input, auto-grow, and the send dispatch are the composer's own slice; this ticket changed only the thread's data source.
- **Populated-container render assertion → a future jsdom/Testing-Library harness.** Because of the server-snapshot behavior above, no test yet observes a *populated* `ConversationScreen` render through the store. The store-level reactivity test + the pure-view render test + the adapter test cover the seam without one; a client-render harness is the only way to close that last gap and stays deferred (the deferral note from [#1](1.md) still holds).
- **Richer message kinds (tool-call chips, code blocks, session delimiters) → later.** The `Message` view model is still the two-arm `user`/`daemon` union. The Figma node shows tool-call chips, a session delimiter, and a code block; those remain out of scope per the conversation-shell feature doc. The adapter and union extend cleanly when they land.
- **Multi-conversation scoping.** `conversation_id` is dropped at the adapter (the shell renders one active conversation, all messages appended). Multi-conversation routing stays an ADR 0004 open question.
