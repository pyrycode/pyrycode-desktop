# #697 — Toggle a resolved tool row open and closed

Split from #669 (sibling of #696, the shell #696 built the expanded body into). Consumed #696's
`ToolRow`/expanded body; feeds #645 (the per-input-field list inside the same body). Shipped as PR #701
(`4b8199e`), code-review **PASS** (0 MUST FIX, 2 NIT). Size S; one production `.tsx`, one production
`.css`, the test file, plus one new e2e spec — `+316/-15` lines total.

## Summary

#696 forked `ToolRow`'s render on an `expanded` flag and drew a result body, but shipped no way to reach
it — the production call site passed no flag, so every row in the app rendered collapsed. This ticket
supplies the missing control:

- **The chip on a resolved row becomes the disclosure control itself.** `result ? <button …> : <div …>`
  forks the chip element on `result`, not on `expanded` — the same condition `rowClass` already reads.
  A pending row (`result === null`) keeps the original `<div className="tool-row__chip"
  data-thread-role="tool">` byte-for-byte and renders no button, no `aria-expanded`, no affordance at
  all, so "activated while pending" is unreachable rather than guarded. Both branches share one
  `chipRuns` JSX fragment (the two `<span>`s) declared once, so the children provably cannot fork
  alongside the element.
- **State is one `useState<boolean>` local to `ToolRow`**, mirroring `UnrecognizedRow`'s own shape
  exactly — the design this ticket's own comment cites as the ADR 0006 precedent, not the container's
  four screen-level booleans (`sheetOpen`/`channelInfoOpen`/`pickerOpen`/`panelOpen`). Toggled with the
  functional updater (`setExpanded((open) => !open)`), never a captured-value form, matching
  `UnrecognizedRow`'s own race-avoidance. No `useEffect`, because nothing needs resetting: `Timeline`'s
  array-index key strategy plus `fillResult`'s in-place `items.map` replacement (never insert, never
  reorder) mean a row's component instance is stable across its whole pending → resolved life, and a
  thread `reset` empties `items` to `[]`, unmounting every row and taking its boolean with it — including
  the in-thread `conversation_created` reset path that leaves the screen mounted
  (`activateConversation.ts:75`).
- **`expanded` → `defaultExpanded`.** The prop was a controlled value under #696; here it becomes the
  mount-time initial value only, and the rename says so honestly rather than leaving a prop named
  `expanded` that a re-render cannot actually change. Seven `<ToolRow …>` test call sites renamed
  mechanically; the one production call site (`:556`, passes no flag) is untouched, and so are
  `Timeline`/`TimelineRow`'s signatures — no edit cascade past this component.
- **One additive CSS rule**, `.tool-row__chip--toggle`, appended after `.tool-row__chip` (which is not
  edited, keeping the pending markup and the collapsed geometry byte-identical to #696). It supplies
  only what a UA `<button>` would otherwise inject or override: `font-family: var(--font-sans)`
  (load-bearing — `.tool-row__summary` inherits it from `.conversation`, and a bare `<button>` would
  silently re-parent that inheritance to the UA font), `color`, `text-align: left`, `box-sizing:
  content-box` (a UA button defaults to border-box; holding it at content-box keeps `max-width: 100%`
  bounding both chip branches identically so a resolving row doesn't shift width), `cursor: pointer` and
  a `:hover` background tint lifted verbatim from `.unrecognized-row__summary`. Deliberately absent:
  `border` in any form — `.tool-row--error .tool-row__chip` retints the border at specificity (0,2,0)
  against this rule's (0,1,0) and keeps winning only as long as this rule stays silent about it.

`npm test` 469/469 green (4 new `ToolRow` cases + 7 mechanical renames), `npm run build` clean, `npm run
e2e` 40/40 including the new spec.

## Patterns established

- **A control-vs-content element fork gates on the same predicate its sibling markup decision already
  reads (`result`), not on the state the fork exists to toggle (`expanded`).** Keeps "non-activatable
  while pending" structural rather than a second condition that could drift from `body`'s own gate.
- **Forking the element rather than always rendering one disabled control** is the right call whenever
  the disabled state would itself change markup or accessibility-tree shape that an AC says must stay
  unchanged — a `<button disabled>` is still a control screen readers see; a `<div>` isn't there at all.
- **A CSS rule meant to be additive on top of a UA element should be audited for what it *doesn't* say,
  not just what it does** — the omissions (no `border`, no `font-size`/`line-height`/`letter-spacing`/
  `font-weight`, no `outline`) are exactly what keeps existing higher-specificity rules and inherited
  chrome (focus ring, error accent) working unchanged. Write the reasoning for each omission into the
  comment; a reviewer (or a future editor) has no way to rediscover "why isn't `border` here" from the
  rule alone.
- **`box-sizing` is not implied by "make a `<div>` into a `<button>`."** A UA `<button>` is `border-box`
  by default; a bare `<div>` in a stylesheet with no global `box-sizing` reset is `content-box`. Any
  future div→button conversion in this codebase should check `box-sizing` alongside `font-family` and
  UA `align-items`/`text-align`/`cursor` — see the checklist in the security-fixed-in-review memory below.

## Lessons learned

*(from the PR #701 body)*

- **A `*/` inside a CSS block comment closes the comment early, and the parser's error recovery then
  swallows the entire next rule.** The draft comment above `.tool-row__chip--toggle` read `every
  --space-*/--radius-* token is px`; the `*/` in that glob closed the comment there, and
  `.tool-row__chip--toggle`'s declaration block vanished from the built stylesheet while the following
  `:hover` rule (a separate rule, unaffected) survived — so the feature half-worked with the chip
  rendering in the UA's Arial at `border-box`. **No test tier in this repo catches this class of bug**:
  vitest is `renderToStaticMarkup` string assertions (blind to computed style), and the e2e spec asserts
  classes/counts/`aria-expanded` (all present regardless of which CSS rule won). The full 40-test e2e
  suite passed green with the rule silently dropped. What found it was a throwaway `getComputedStyle`
  probe comparing the resolved and pending chip's font stack, box-sizing and rendered width pixel-for-
  pixel; the cheap repeatable version is `grep`ping the built `out/renderer/assets/*.css` for the rule
  name after any CSS-comment edit that contains a `*` immediately before a `/`.
- **`npx playwright test` does not rebuild the app; only `npm run e2e` does.** A renderer fix verified
  with a bare `playwright test` invocation is being verified against the *previous* build — this is how
  the swallowed-rule bug above stayed invisible through one verification pass.
- **Comment line references drift on every insertion in a hand-edited stylesheet.** #696's citations of
  `.unrecognized-row__raw`'s line numbers were already ~60 lines stale by this ticket's start
  (`f77ba3c`), before this ticket added anything. Cite the rule name plus a short excerpt for a
  cross-reference likely to outlive a nearby edit, not just a line number, or expect to re-verify every
  citation in a security-sensitive file at review time (code review here re-verified all six new-comment
  line references against HEAD and found them accurate — not free, given the file had just shifted 39
  lines).

## Code review — two NITs, both left open

- `ConversationScreen.tsx:551-555` — #696's `toolCall` arm comment still forward-references "#697's
  'which rows are expanded' state shape." #697 landed and explicitly declined that hoisted shape; the
  boolean is row-local, not container-level. The sentence is still literally true (the flag isn't
  threaded through the arm, and the arm still passes no `defaultExpanded`) but now points at a design
  that never shipped, in a file where every other #696/#697 comment was updated with care. One clause,
  non-blocking.
- AC3 (no row inherits another's expansion, none survive a reset) is established by argument in the code
  comment and independently re-verified by the reviewer against all 17 `items:` sites in
  `threadTimeline.ts`, not pinned by a test. Correct today, but nothing fails if a future reducer change
  breaks the index-key invariant, and #645 lands inside this same body next. Flagged for the `tabIndex`
  follow-up ticket (below) to pick up alongside its own scope.

## Out of scope — declined deliberately, and where each went

- **Extracting a shared collapsible component.** `UnrecognizedRow`'s own comment ties that extraction to
  a *second* expand/collapse arriving — this ticket is that second one, and the answer stayed no: a
  shared component with exactly one migrated caller (`UnrecognizedRow` itself) is the speculative work
  the comment warns against. Not filed as a follow-up; would need `UnrecognizedRow`'s own migration to
  become worth doing.
- **`tabIndex={0}` on the two `overflow: auto` scroll regions** (`.tool-row__result` and
  `.unrecognized-row__raw`) — both keyboard-unscrollable in Blink, a pre-existing gap in both components
  that predates this ticket. Not fixed here (fixing only one would leave the pair inconsistent); needs a
  follow-up ticket covering both.
- **Collapsing consecutive uses of the same tool into one entry** — deferred on #645, 2026-08-20.
- **Any DOM test environment** (jsdom/happy-dom/@testing-library) — the click is proven in Playwright
  instead; `vitest.config.ts`'s `environment: 'node'` is untouched.
- **`aria-controls`/`id` pairing, `aria-label`, `title` on the toggle, and a toggle log line** — each
  would put daemon-supplied text (`toolUseId`, `name`, `inputSummary`) into an attribute or a log,
  forbidden by CLAUDE.md's 2026-08-20 ruling and ADR 0007. Declined by design, not merely unimplemented;
  see the SAFETY block in `ConversationScreen.tsx` and the architect's security review for the full
  five-sink walk.
