# #703 — Group each sidebar tree's rows by workspace under the host row

Split from #671, sibling of #702/#704 (both not yet shipped as of this writing). Shipped as PR #717
(`3d51d44` spec commit + `473be9a` feature commit), code review **PASS** (0 MUST FIX, 0 SHOULD
FIX, 3 NIT). Size S; 5 files touched, ~330 LOC (~77 view-model incl. comments, ~65 TSX, ~43 CSS,
~205 test).

## Summary

Each sidebar tree now groups its rows by workspace between the [host row](710.md) and the
conversation rows: one group per distinct `cwd`, each headed by a 28px `WorkspaceRow` one indent
deeper than the host row above it (Figma `106:3098`). `ConversationSummary.cwd` already carries
the workspace — the daemon has no separate workspace-id concept, a workspace *is* a conversation's
cwd (pyrycode#823) — so this needed no new data and no wire change. Both trees group
independently, on purpose (operator, 2026-08-21): a workspace with rows in both Channels and Chats
appears in both.

Two new pure exports in `channelListViewModel.ts` carry the whole derivation:

- **`workspaceLabelFor(cwd: string): string | null`** — the last usable path segment, or `null`
  when there is none. Split `cwd` on `/` and walk the segments from the end, returning the first
  that is non-blank after trimming; the trim is only the usability predicate, the returned segment
  itself is not trimmed. One walk covers a trailing separator, repeated trailing separators, and a
  whitespace-only tail without a special case for each. `\` is deliberately **not** treated as a
  separator — that would assume the daemon's host OS, an interpretation this client never makes —
  so a backslash-separated value survives whole as its own single segment. Total over `string`:
  never throws, no `path`/`fs`/`node:*`/`URL`.
- **`groupByWorkspace(rows): readonly WorkspaceGroup[]`** — accumulates into a `Map<string, {label,
  rows}>`, never a plain object: object keys that look like integers enumerate first in numeric
  order regardless of insertion order, and `cwd` is arbitrary untrusted text, so a relative `cwd`
  of `'2'` would jump ahead of every earlier group with an object accumulator. `Map` preserves
  insertion order for every key, which is what makes "group order follows first appearance, row
  order is array order, no sort anywhere" (AC4) hold. A row whose `cwd` yields no usable label
  keys into the module-local sentinel `UNKNOWN_WORKSPACE_KEY = ''` instead of `row.cwd`, and
  labels as `UNKNOWN_WORKSPACE_LABEL = 'Unknown workspace'`.

`ChannelList.tsx`'s `renderBody` wraps each existing `.map` one level, inside a keyed `Fragment`
(the shorthand `<>` cannot carry a key — the file's first `Fragment` import):

```tsx
{groupByWorkspace(channels).map((group) => (
  <Fragment key={group.key}>
    <WorkspaceRow label={group.label} />
    {group.rows.map((c) => <Row key={c.id} row={c} ... />)}
  </Fragment>
))}
```

`Fragment` emits no DOM, so the rendered list stays a flat sibling sequence — header, host,
workspace, rows, workspace, rows — and `.channel-list__row` keeps the exact ancestry it had before
this ticket. The wrap sits *inside* the pre-existing `length > 0` gate that already decides the
host row and section header, so "a zero-row tree renders nothing at that level" holds by
construction, with no new condition added.

## The fallback-key trap this ticket exists to avoid

**A fallback grouping key is collision-proof by construction when it's a sentinel the classifier
already routes to that bucket — not by comparing the derived label against the fallback
constant.** The sentinel here is `''`: a `cwd` of `''` has no usable segment (`workspaceLabelFor`
returns `null` for it), so any row that could theoretically collide with the sentinel key is
*already* in the fallback bucket by the same logic that assigned it. No prefix hack, no `Symbol`,
no guessing an improbable string.

The trap the sentinel avoids: deriving the grouping key by checking whether the *label* equals
`UNKNOWN_WORKSPACE_LABEL` would silently fold a real directory literally named `Unknown workspace`
into the fallback group — the exact merge AC3 forbids in both directions. This is also why
`workspaceLabelFor` returns `string | null` rather than following `titleFor`'s fold-the-fallback-in
shape (`channelListViewModel.ts:16`): the caller is a *grouper* that must tell "no usable label"
from "a label that happens to read like the fallback," and that distinction has to survive the
return value. `channelListViewModel.test.ts` pins both directions: several different unusable
`cwd`s collapse into one fallback group, and a row whose `cwd` is literally `'Unknown workspace'`
gets its own separate group in the same input.

## The two selector/text hazards (the #710 pattern, re-verified)

Same failure mode as [#710](710.md), both closed by construction:

- **Class-token guard.** `channel-list__workspace`/`__workspace-icon`/`__workspace-label` share no
  class token — and no substring — with `channel-list__row`, `__row-open`, `__section-header`, or
  `__host`. Zero `[class*=]`/`[class^=]`/`[class$=]` selectors exist anywhere in `e2e/` or
  `src/renderer`, so no substring selector could reach it regardless.
- **Text guard — the new half, since this label is daemon-derived rather than a constant.** Every
  fake fixture seeds `cwd: '/fake/workspace'` (`conversationStateFake.ts`, `launchPairedApp.ts`,
  each spec's own seed), so the default e2e tier renders the literal `workspace` twice per launch.
  That string equals none of the suite's `exact: true` locator strings and carries none of the
  classes its `hasText` locators are scoped to. Unlike #710's compile-time constant, this check has
  to be run against what the fixtures actually seed, not against the source.

**Zero files under `e2e/` were edited.** `npm run e2e` stayed 40/40, which is the real proof; the
new `ChannelList.test.tsx` cases that pin the exact pre-existing counts of `__row`/`__row-open`/
`__section-header`/`__host` are the unit-level mirror, not a substitute.

**What the default e2e tier does not, and must not be asked to, prove.** One seeded `cwd` per
launch means exactly one group per tree — multiple groups, first-appearance ordering, and the
fallback group have zero e2e coverage and are unit-tested only (`channelListViewModel.test.ts`),
including the integer-like-key ordering case that fails against a plain-object accumulator and
passes against the `Map`.

## Patterns established

- **A fallback grouping key should be a sentinel the classifier already routes to that bucket, not
  a value compared against the fallback label.** Generalizes past this ticket: any "derive a key,
  fall back on failure" shape has the same trap if the fallback check compares against the
  *display* value instead of re-deriving membership the same way the primary path did.
- **A daemon-derived label collapses the class-token/text hazard check from "read the source" to
  "read the fixtures."** #710's constant-label host row could be checked by grep; this workspace
  label can only be checked against what `conversationStateFake.ts`/`launchPairedApp.ts` actually
  seed for `cwd`.
- **`Map`, never a plain object, for any accumulator keyed by untrusted or arbitrary string
  content that must preserve insertion order.** Integer-like string keys on a plain object jump to
  the front in numeric order regardless of insertion order — the same trap `threadTimeline.ts` hit
  with `Object.entries` (#706).

## Lessons learned

*(from the PR #717 body)*

- The Figma's 10px gap has no slot on the 4px spacing scale, so the label lands at x=48 rather than
  the design's x=46. The +2px is the `--space-3` tie-break the spec chose deliberately so the
  glyph→label rhythm matches the host row directly above (the same treatment #710 shipped) —
  flagged so it reads as a decision, not drift.
- A fallback grouping key can be collision-proof by construction rather than by picking an
  improbable string (see § above) — this is also why `workspaceLabelFor` returns `string | null`
  instead of following `titleFor`'s fold-the-fallback-in shape.
- `e2e/`'s text guard is fixture-decided here, not constant-decided: #710's host label was a
  compile-time constant checkable by reading the source; this label is daemon-derived, so the check
  has to be against what the fakes actually seed (`cwd: '/fake/workspace'` → the literal
  `workspace`), not against the code.
