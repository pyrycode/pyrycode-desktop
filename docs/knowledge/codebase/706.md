# #706 — List the tool input fields in the expanded tool row

Split from #645 (sibling of #705, the collapsed headline pick). Consumed #642 (wire `input` map decode),
#643 (item carry) and #696/#697 (the expanded body + toggle this ticket fills). Shipped as PR #708
(`702c7bf` spec commit + `1ea0db4` feature commit), code review **PASS** (0 MUST FIX, 2 NIT). Size S;
three files, `+277/-6` total.

## Summary

`ToolRow`'s expanded body held only the tool's result. This ticket lists every entry of the `toolCall`
item's `input` map — name above value, in arrival order — as the first children of that body, above the
unchanged result block. It is deliberately literal where #705's headline is selective: no path
shortening, no salience pick, no re-ordering, and no skipping the field the headline already promoted.

- **The insertion is a bare `Object.entries(...).map(...)`, inline inside `{body && (…)}`**, never hoisted
  to a `const` — consumed once, so inlining keeps "a collapsed or pending row never computes the list"
  structural rather than guarded. `Object.entries`, never `for...in` or `input[key]`: own enumerable keys
  only, in insertion order, per `threadTimeline.ts`'s "the map is an ordinary-prototype object" rule
  carried forward from #642.
- **`item.input ?? NO_INPUT_FIELDS`, a named module-level constant, not a bare `{}` literal.** `item.input
  ?? {}` widens to `Readonly<Record<string, string>> | {}`, and TypeScript resolves `Object.entries` on
  that union to the `entries(o: {}): [string, any][]` overload — silently typing every **value** as `any`
  on a render path handling untrusted daemon text. With both branches carrying the same named type, `T`
  infers as `string`. Neither `noUncheckedIndexedAccess` nor `exactOptionalPropertyTypes` is on in this
  repo's tsconfigs, so nothing else would have caught it.
- **No list-wrapper element and no `.length > 0` guard.** The per-field `<div className="tool-row__input">`
  is a direct child of the body; zero entries renders literally nothing. This is what makes "an absent or
  empty `input` draws no field list *and* no empty container" structural — there is no separate element
  that could be left behind by a wrong guard, and absent/`{}` collapse into the same `Object.entries([])`
  regardless of which one it was (the distinction between the two stays alive only at the item, per #643).
- **The value is a `<pre className="tool-row__input-value">`, not a styled `<div>`** — a `<div>` inherits
  `white-space: normal` and would collapse the daemon's newlines onto one line, the defect #607 fixed for
  assistant text and #696 fixed for the result block.
- **`key={name}` is a React reconciliation identity, not a new exposure.** Object keys are unique by
  construction, a key is never serialised to the DOM, and the same string is rendered as a text child two
  lines below anyway. Commented explicitly so a future review doesn't reopen it.
- **CSS: `.tool-row__input-value` joins the existing `.tool-row__result` rule as a second selector**,
  rather than copying its ten declarations into a rule of its own — makes "the field list takes the result
  block's visual language" a fact by construction (identical `white-space: pre`, `overflow: auto`,
  `max-height: 240px`, mono type, surface fill) instead of two declaration sets that could drift apart.
  Purely additive: the failed-tool accent (`.tool-row__body--error .tool-row__result`, a **descendant**
  selector naming `.tool-row__result` alone) gains nothing from the join, which is the mechanism behind
  the ticket's decision to decline the error treatment for input — costs nothing to enforce, nothing to
  extend.
- **New rules `.tool-row__input` (column flex, `gap: --space-1` — tighter than the body's own
  `--space-2`, so a name reads as belonging to its value) and `.tool-row__input-name`** (mono, but
  `--color-on-surface-variant` — the muted *label* colour, never `--color-tertiary`, which is reserved for
  the tool's own identity). `word-break: break-word` on the name is load-bearing, not cosmetic: a field
  name has no spaces, so an absurd multi-thousand-character one would not wrap and would widen the row —
  the repo's house value for an unbounded string (`.bubble:298`), stated explicitly because `.tool-row` is
  not a `.bubble` descendant and inherits nothing from it.
- **Corrected three stale `#645` comments** in the two files this ticket opens (`ConversationScreen.tsx`,
  `conversation.css`) — two were "this ticket lands the field list here" promises kept in the past tense;
  the third, at `conversation.css:1081-1083` (pre-change line numbers), was **false**: it claimed the
  error-accent selector reached `.tool-row__empty` and a future field list, when the selector beneath it
  is a descendant rule naming `.tool-row__result` alone. Fixed the comment, not the selector — five other
  `#645` references outside these two files (`threadTimeline.ts`, `timelineBridge.ts`, `wire/types.ts`,
  `ipc/events.ts`, `inboundMessage.ts`) are stale attribution, left untouched per CLAUDE.md's "don't
  refactor adjacent code while you are there."

Nine new server-render (`renderToStaticMarkup`, no DOM) test cases in `ConversationScreen.test.tsx`, one
per AC plus the arrival-order and absent-vs-`{}`-equality cases. `npm test` (515 pass) and `npm run build`
both green. **The free regression baseline held exactly as the spec predicted**: no existing unit test and
no existing e2e spec needed editing — the invariant is a disjointness, {carries `input`} ∩ {renders
`defaultExpanded`} = ∅, which #705's six new `input`-carrying fixtures (all collapsed/pending) and every
pre-existing `defaultExpanded` fixture (all `input`-less) both independently satisfy.

## Patterns established

- **A container built to hold a future addition earns its shape back exactly once** — `.tool-row__body`'s
  column-flex-with-gap layout, built by #696 for "a result block, plus whatever #645/#706 add later," took
  the field list as siblings with zero layout changes. Building a container "as a container" ahead of its
  second child is worth doing when the doc comment says so up front, as #696's did.
- **Joining a new selector to an existing rule (rather than copying its declarations) is how a design
  intent ("reuse this visual language") becomes a fact the diff proves rather than a claim a reviewer has
  to trust.** `.tool-row__result, .tool-row__input-value { ... }` cannot drift the two apart; a second,
  hand-copied rule could, silently, on the next edit to either.
- **A named constant beats a bare `{}` / `[]` literal at a nullish-coalescing call site whenever the
  literal's inferred type is a union that changes how a downstream generic resolves.** `Object.entries`
  is the concrete trap here, but the shape generalizes to any call whose return type depends on the shape
  of its argument's type, not just its runtime value.
- **An arrival-order assertion must key off the rendered field *name*, never a value, whenever a sibling
  component might draw the same value elsewhere in the row.** #705's headline draws the first entry's
  *value* in the same chip; a value-keyed `indexOf` order check would have passed under a `.sort()` that
  the name-keyed check correctly fails. See Lessons learned.

## Lessons learned

*(from the PR #708 body, lightly edited)*

- `item.input ?? {}` types as `Readonly<Record<string, string>> | {}`, and TypeScript resolves
  `Object.entries` on that union to the `entries(o: {}): [string, any][]` overload — silently typing every
  **value** as `any` on a render path handling untrusted daemon text. A named
  `const NO_INPUT_FIELDS: Readonly<Record<string, string>> = {}` as the `??` right-hand side keeps both
  branches one type and `T` infers as `string`. `strict` alone does not catch this — neither
  `noUncheckedIndexedAccess` nor `exactOptionalPropertyTypes` is set in this repo's tsconfigs.
- Pinning "the client never re-sorts" has to key on the rendered field **names**, not their values.
  #705's headline picker also draws the first entry's value in the collapsed chip beside this body, so a
  value-keyed `indexOf` ordering assertion would still pass under a sorted body — a false green. Names
  appear only in the expanded body, so they are the half that actually pins the order.
- A "free regression baseline" claim inherited from a ticket body can go stale between sizing and
  implementation. The ticket body said this test file sets `input:` on zero fixtures; #705 (blocking this
  ticket, landed first) then added six. The invariant that actually held was a *disjointness* —
  {carries `input`} ∩ {renders `defaultExpanded`} = ∅ — not the raw fixture count. Re-derive a baseline
  claim from the current file rather than trusting a ticket body's count when a blocking sibling landed in
  between.

## Code review — PR #708, PASS (0 MUST FIX, 2 NIT)

- **NIT** — `conversation.css`, the `min-width: 0` on `.tool-row__input`'s justification ("holding a
  potentially very wide `<pre>`") is mechanically off: `min-width` on a container doesn't constrain its
  children, and `.tool-row__input` is a flex *item* of a **column** container (`.tool-row__body`), where
  automatic minimum size applies on the main (vertical) axis only — so `min-width: auto` already resolves
  to `0` and the declaration is inert. Harmless, mirrors an identically-inert declaration #696 already
  shipped on `.tool-row__body` itself — left as-is, not touched.
- **NIT** — the doc comment's "`Object.entries` … in insertion order" is true for every field name the
  daemon realistically sends but not universally: integer-like string keys (`'0'`, `'1'`) enumerate first,
  in ascending numeric order, ahead of the insertion-ordered rest (`OrdinaryOwnPropertyKeys`). That
  reordering happens at object construction, not in this render, so AC1's "never re-sorts" still holds
  exactly as written. Noted for the record; no code change.
