# #719 — A distinct not-yet-known state for the relay dot

Split from #672 (sibling: [#718](718.md), the sidebar dot pair itself, shipped first). Shipped as
PR #726 (`4681f05` spec commit + `420052a` feature commit), code review **PASS** (0 MUST FIX, 1
SHOULD FIX, 0 NIT). Size S; 6 files, 92 insertions / 40 deletions.

## Summary

`relayLinkStore` holds `RelayLinkStatus | null`, where `null` is the initial "no status has arrived
yet" sentinel — none of the three categories the wire delivers. The renderer used to collapse that
sentinel into the same `down`/`Relay Offline` state as a genuinely dropped socket
(`relayLeg(null)`), a deliberate choice #330 made while the indicator lived only in the
conversation status row. Since [#718](718.md) put the dots on the sidebar host row — on screen from
the first frame of every launch — that collapse meant every cold start opened by claiming an
outage before anyone had asked. This ticket reverses that one mapping decision and nothing else.

`LegCategory` (`ConversationScreen.tsx`) widens from three members to four:

```ts
export type LegCategory = 'up' | 'in-progress' | 'down' | 'unknown'
```

`relayLeg`'s pre-switch `null` guard now returns `{ category: 'unknown', label: 'Relay Unknown' }`
instead of `{ category: 'down', label: 'Relay Offline' }`. The guard stays a plain `if` ahead of
the `switch` rather than folding into a `case null:` arm — that is what keeps the `switch`
operating on a bare three-member `RelayLinkStatus` with an explicit return type and no `default`,
so a future `RelayLinkStatus` member still trips TS2366 (AC4, proved in the PR by a temporary
fourth-member probe, then reverted). `daemonLeg` is untouched byte-for-byte apart from one added
comment clause: `ConnectionStatus` has no null, so the host leg never produces `unknown` — the
widened member is the relay leg's alone (AC3).

The colour binding is one new rule, `.conn-dot--unknown { background: var(--color-outline); }`,
declared flat in `conversation.css` as a fourth sibling immediately after `.conn-dot--down` — not
nested under `.conn-dot`. That placement is the entire risk in this ticket: the sidebar's 6px dot
wears the modifier *without* the `.conn-dot` base (which bakes the status row's 8px box), so a
binding declared anywhere else — nested under `.conn-dot`, or re-declared in `channels.css` — would
leave the sidebar dot with no background at all, invisibly, since the unit tier renders markup in a
node environment and never asserts computed colour. Declared flat, one rule reaches both dot sizes
(AC2). `--color-outline` is reused, not new — it already fills the `.run-config__switch-knob` /
`.settings__switch-knob` off-state chips with the same "not on, not wrong" semantic, is the only
achromatic option among the four categories (separating by chroma as well as hue at 6px), and
carries no M3 success/failure valence.

## Patterns established

- **A CSS class assembled by template string has no exhaustiveness guard, ever — TS2366 covers only
  the mapping.** Adding a `LegCategory` member compiles, renders, and ships even with zero matching
  colour rule; the class → paint binding and the type-level exhaustive switch are two entirely
  different mechanisms, and only one of them is automatic. Widening an enum-like union that also
  drives a runtime string template needs its own explicit check — code review or a manual visual
  pass — not just a green `npm run build`.
- **`getComputedStyle` against a headless render of the real stylesheets closes a CSS-cascade risk
  a `environment: 'node'` unit suite structurally cannot reach**, without adding a new test tier.
  The PR proved AC2 this way: rendering both dot sizes and asserting both computed to
  `rgb(140, 145, 153)` (`--color-outline`) is a stronger check than reading the CSS source, because
  it proves the cascade actually resolves the intended rule rather than merely that a matching rule
  exists somewhere in a file.
- **A `null`/sentinel guard placed *ahead of* a switch, rather than folded into a `case null:` arm,
  is what keeps an exhaustiveness guard scoped to the real wire union.** Rewriting the guard into
  the switch would still type-check today, but it would be a needless rewrite of a working line
  (§ Don't) for zero behavioural gain, and it's the kind of change that makes a future diff harder
  to review because the switch's "operates only on `RelayLinkStatus`" invariant becomes implicit
  again instead of visible in the function's shape.
- **A one-value semantic (not-yet-known ≠ down) can ship as a pure reversal of a prior ticket's
  documented, tested decision**, when the trigger is a change in that state's screen real estate
  (#330's status row was behind a navigation; #718 put the same dots on screen at launch) rather
  than a new requirement. The whole diff is one guard's return value, one union member, one CSS
  rule, and the stale prose naming the old mapping — no new component, prop, store field, or wire
  change.

## Lessons learned

*(from the PR #726 body, verbatim)*

- A CSS class applied by template string has no exhaustiveness guard anywhere: adding a
  `LegCategory` member compiles, renders and ships even with no matching colour rule. TS2366
  covers the mapping, not the class → paint binding — the two are guarded by completely different
  mechanisms, and only the first is automatic.
- Reading `getComputedStyle` out of a headless render against the real stylesheets is a cheap way
  to close a CSS-cascade risk that a `environment: 'node'` unit suite cannot reach — it proves the
  *cascade*, not just the emitted markup, without adding a test tier.

One more, from the code review finding below rather than the PR body:

- **A "reword these stale-prose sites" spec's own site list is not exhaustive by construction.**
  The architecture spec named ten sites whose prose asserted the old three-category mapping and
  needed updating; an eleventh — `ConversationScreen.tsx:2203`'s doc comment on
  `ConnectionStatusIndicatorControl`, "initial state → two \"Offline\" dots" — was missed, even
  though its own mirror comment in the other consumer (`ChannelList.tsx:362`) *was* correctly
  updated in the same diff. Grepping the falsified claim's own vocabulary (`"Offline" dots`, `two
  "Offline"`) across the changed files would have caught it; grepping only the spec's named line
  numbers would not. As of this writing the stale comment is still unfixed in `src/` — the review
  decision was PASS because it is prose-only with no behavioural or gate consequence, so it shipped
  as a SHOULD FIX left open rather than blocking the merge.
