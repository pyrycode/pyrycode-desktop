# #72 — Log data Download button in the Run configuration modal

The client debug-bundle download's **sole user-facing entry point**, closing the [#71](https://github.com/pyrycode/pyrycode-desktop/issues/71) family end to end. Shipped as PR [#186](https://github.com/pyrycode/pyrycode-desktop/pull/186), landed to spec (`docs/specs/architecture/72-log-data-download-button.md`). Renderer-only, **not security-sensitive** (labels confirmed; the three consumed events carry only a count, a local path, and a closed enum).

**Shipped:** 2026-07-09 · **Size:** S · **Scope:** 2 new files (`logDataDownload.ts`, `LogDataSection.tsx`) + 2 new test files + `ConversationScreen.tsx` (+`children` seam) + `conversation.css` (+section/button/status styles) + `tokens.css` (+2 tokens). 7 files, 505 insertions. `npm test` 643 pass / 3 pre-existing skips (+16 new), `npm run typecheck` and `npm run build` both clean.

## What it does

Adds the "Log data" section — a header plus a full-width filled-tonal **Download** button — as the last (bottom) section of the [Run configuration sheet](../features/conversation-shell.md#run-configuration-sheet-177) shipped by [#177](177.md), beneath where [#181](181.md)/[#182](182.md) mount Model/Effort/YOLO/Context-window. Pressing it fires the already-wired `requestDebugBundle` command and drives a local state machine off the three already-typed `debugBundle*` daemon events ([#168](168.md)) through to the [#169](169.md) orchestrator, which was otherwise unconsumed until now.

## Patterns established

- **The `StatusSheet` per-section `children` contract, confirmed working on its first real consumer.** A childless `<StatusSheet/>` still renders no sections, so #177's existing `renders an empty scrollable body` test stayed green **untouched** — no test file edit needed to add the first section. Confirms the extension point #181/#182 will use next; each section owns both its header and its content, and mounts as an additional child in document order ("beneath Context-window" = last child).
- **The `composerSend.ts`/`pairingState.ts` pure-logic-file idiom, now with a fourth instance.** `logDataDownload.ts` is a total reducer (`reduceDownload`) + an event filter (`toDownloadAction`, the `translateDaemonEvent` analogue — `default: null`, not `assertNever`, because ignoring unrelated events is *permanent* intended behavior for a section that owns only 3 of the `DaemonEvent` union) + a view-model deriver (`downloadView`, the `composerAvailability` analogue). All three are plain, React-free, Electron-free functions — the entire state machine is unit-tested with zero DOM harness.
- **The reducer is deliberately phase-agnostic, not a state-transition graph.** Each `DownloadAction` fully determines the next `DownloadState` with no branching on the prior phase (`progress → downloading{chunks}` regardless of whether the prior phase was `idle` or `downloading`). This is what lets a bare `progress` event re-hydrate the view cleanly after a mid-download sheet close/reopen unmounts and remounts the section (accepted ephemerality, ADR 0006) — the reducer doesn't need to know it "missed" the `requested` action.
- **Single-in-flight is belt-and-suspenders across two different fabrics, not duplicated in the same one.** The button is `disabled` while `busy` (UI) + `onDownload` re-checks `state.phase` before sending (React state) — both client-side and both advisory; the deterministic backstop is the **already-shipped** [#169](169.md) orchestrator's `active` flag on the main-process side, which silently drops a stray duplicate command. No second React-side state machine was built to enforce this authoritatively — one deterministic guard is enough, per the [pipeline's belt-and-suspenders-means-different-fabric principle](../../../CLAUDE.md).
- **The optimistic `requested` transition is load-bearing, not cosmetic.** `onDownload` dispatches `{type:'requested'}` synchronously after sending the command, *before* any daemon event arrives — because the `unavailable` failure path emits **no** `debugBundleProgress` at all. A busy state gated on the first progress event would never appear on that path; entering `downloading` on the press is the only way AC3's "busy state while a download is in progress" holds across all three failure/success shapes.
- **`window.pyry` dereferenced only inside effects/handlers, never during render** — the same discipline as `Composer.handleSubmit` — so `renderToStaticMarkup(<LogDataSection/>)` renders the idle view with no bridge mock required.

## Deviation from spec

- **Copy only.** The spec's proposed `unavailable` sentence was `"Debug data isn't available right now..."`; the shipped copy is `"Debug data isn't ready right now..."` — this dodges an AC5 substring trap (`available` would otherwise partially echo language close to a raw-code style message). The spec explicitly flagged the proposed sentences as refinable, constraining only the *shape* (a plain sentence, never a raw code/errno/stack) — this is copy refinement within that latitude, not a deviation from the contract.
- No other deviation: file count, module structure, token additions, and the `children` seam all landed exactly as specced.

## Testing

- **`logDataDownload.test.ts`** — `reduceDownload` totality from representative prior states; `toDownloadAction` maps the 3 events correctly and returns `null` for non-bundle events (`connected`, `messageReceived`, `snapshotReceived`); `downloadView` per-phase, including a negative assertion that none of the three failure captions contains its raw reason token, `"errno"`, or a stack marker (AC5).
- **`LogDataSection.test.tsx`** — server-renders the pure `LogDataView` per phase (idle/downloading/saved/failed) via `renderToStaticMarkup`, plus a smoke test that `<LogDataSection/>` itself renders without touching `window.pyry`.
- No DOM/jsdom harness — consistent with the rest of this screen's test suite (server-render only).
