# #724 — Carry the conversation id on the `turnState` IPC arm

Split from #712 (sibling: #725, the cross-reference comment sweep, not yet run). Shipped as PR #727
(`57d1378` spec commit + `346d272` feature commit), code review **PASS** (0 MUST FIX, 0 SHOULD FIX,
0 NIT). Size S; 12 files, 49 insertions / 27 deletions.

## Summary

The wire's `turn_state` frame has always carried `conversation_id`, and the decoder
(`parseTurnStatePayload`, `inboundMessage.ts`) has always required it as a string — but the
transport's `turn-state` emit (`daemonConnection.ts:609`) discarded it, on a documented assumption
that exactly one conversation is ever active. That assumption is what the desktop's new sidebar
layout breaks: the operator ruled on 2026-08-21 that a chat must keep working while he looks at a
different one, and the sidebar list must show each chat's own state. This ticket moves the id one
layer — decoded payload → IPC event — and stops there. No daemon change, no wire-type change, no
behaviour change anywhere a user can see; the per-conversation consumers are #674.

`DaemonEvent`'s `turnState` arm (`src/shared/ipc/events.ts`) gains `conversationId: string`,
required, not optional:

```ts
| { type: 'turnState'; state: WireTurnState; conversationId: string }
```

The emit (`src/main/daemonConnection.ts`, `turn-state` case) copies it **by name** off the
already-decoded payload, never a spread — the house idiom at every emit in the file, and the reason
a decoder that later grows a field can't smuggle it across IPC:

```ts
emitDaemonEvent(sink, {
  type: 'turnState',
  state: inbound.turnState.state,
  conversationId: inbound.turnState.conversation_id
})
```

The id **stops at the renderer timeline bridge**. `translateTimelineEvent`
(`src/renderer/src/store/timelineBridge.ts:43-46`) still rebuilds a fresh `ThreadEvent` naming only
`state`; `ThreadEvent.turnState` (`threadTimeline.ts:123`) and the reducer are byte-unchanged. That
seam was already covered by an existing assertion — `timelineBridge.test.ts:55`'s
`expect(translated).toEqual({ type: 'turnState', state })` — which needed no edit and no new test:
`toEqual` fails on an extra own enumerable property, so it now doubles as a deterministic guard that
a future bridge change can't leak the id into the reducer by accident.

## Patterns established

- **A 16-site fixture cascade stayed a single S ticket instead of forcing a Strangler-Fig split**,
  because every site was reachable by the type system: all 16 `DaemonEvent` `turnState` literals
  live inside `tsconfig.node.json` / `tsconfig.web.json`'s included paths, so `npm run typecheck`
  enumerates every one a table could miss. The spec's own framing: the compiler is the checklist, the
  site table is a convenience, not a thing to be trusted. Contrast pyrycode#75 (26 call sites
  characterised but not *located* — 61 turns burned on discovery); here discovery was already paid
  for by the type system, which is what the count-based split gate is meant to route around when it
  doesn't apply.
- **Optional-first staging was rejected on design grounds, not effort grounds, for a routing key.**
  A required field on a union arm has no compiling intermediate — type edit, emit edit, and every
  construction site land in one commit or the build is red. The one staging that *would* compile,
  `conversationId?: string` flipped to required later, was refused because an optional routing key
  invites `?? activeConversation` fallbacks in the eventual per-conversation consumer (#674) — exactly
  the misattribution ambiguity this work exists to remove. Worth remembering for any future ticket
  that carries a daemon-asserted id across a new boundary: optional-first is a staging tool, not a
  free move, when the field is a routing key rather than a display value.
- **An existing `toEqual` on the far side of a boundary becomes a free leak guard once the near side
  gains a field it must not carry across** — no new test needed. This only works because the
  assertion targets the *translated* type (`ThreadEvent`), not the *source* type (`DaemonEvent`); a
  test written against the source object wouldn't have this property.
- **`assertNever` + `JSON.stringify` sinks are a compile-time impossibility for any explicitly
  handled arm**, closing a log-sink question deterministically rather than by inspection: `turnState`
  is a named `case` in every bridge that has one (`timelineBridge.ts`, `modalBridge.ts`,
  `daemonEventBridge.ts`), so the `JSON.stringify(event)` inside each bridge's exhaustiveness-check
  `assertNever` throw can never serialise this arm. Reviewers reached for this instead of grepping
  for `console.*`.

## Lessons learned

*(from the PR #727 body, verbatim)*

- vitest's `toEqual` fails on an *extra* own enumerable property, which turns the pre-existing bridge
  assertion at `timelineBridge.test.ts:55` into a free deterministic guard that the id stopped at the
  seam — leaving that line alone *is* the test for "the id does not reach `ThreadEvent`". No new test
  was needed. The corollary is the hazard: a `replace_all` over the shorthand
  `{ type: 'turnState', state }` (3 occurrences in that file, one of them `:55` on the far side of the
  boundary) would have corrupted the guard *and stayed green*, because the assertion would have grown
  the same stray key it was meant to catch.
- Because all 16 construction sites were `DaemonEvent`-typed and both tsconfigs include the test
  directories, `npm run typecheck` enumerated the cascade rather than the developer having to.
  Running it before `npm test` made the spec's site table a convenience rather than something to be
  trusted.
