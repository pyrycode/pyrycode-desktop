## Summary

#732 widened the `DaemonEvent` `stallDetected` IPC arm to carry `conversationId` and rebuilt every
claim about that arm's own behaviour where it is made (`events.ts`, `daemonConnection.ts`, and its
decode paragraph in `inboundMessage.ts:104-110`). The retired "nullary by construction" property had
been load-bearing enough that other arms borrowed it as an exemplar — those citations lived in files
#732 never opened, phrased "nullary" / "no payload" / "decodes it nullary" rather than "drops
`conversation_id`", so the grep that found #732's own sites found none of them. This ticket rewrites
those eight borrowed citations, comment-only, across `inboundMessage.ts`, `timelineBridge.ts`,
`threadTimeline.ts` and `e2e/stall-bundle.spec.ts`.

The word `stallDetected` names two different things after #732: the `DaemonEvent` (IPC) arm, which
now carries a payload, and the `ThreadEvent` arm, which is still genuinely nullary. The ticket's whole
difficulty was that split — three true ThreadEvent-side nullary claims sit inside the same paragraphs
as the falsified IPC-side ones, and a pass that chased the AC gate to zero would have deleted them.
Each of the eight repairs keeps the surviving claim and swaps only the reason clause that had gone
false, following the same "conclusion stays true, reason moved" shape throughout:

- `inboundMessage.ts:147-149` (`background-task-started`) — the `so` connecting "not a claude

- `timelineBridge.ts:97-100` — "Both the DaemonEvent and the ThreadEvent are `{ type: 'stallDetected'

## Patterns established

- **A grep-based AC gate over prose is a floor, not a census, for two independent reasons — and a
  ticket's own verification command can fall into the second one without anyone noticing.** The gate
  here (`grep nullary|no-payload | grep -i stall`) only counts a line where both vocabularies land on
  one physical line; a true claim on a wrapped comment can vanish from the count without being wrong,
  and a re-wrap of a counted survivor can silently drop the count without deleting anything. The
  spec's own step-4 verification (`grep "claude sub-state" inboundMessage.ts`) predicted 3 hits and
  measured 2, for the same reason: the phrase itself wraps across `:147`/`:148` in one of the three
  paragraphs. The fix in both cases is the same — verify by content (an expected file:line list), or
  measure a wrapped-tolerant command before trusting its predicted count, never assume a phrase grep's
  arithmetic transfers from a spec's mental model to the actual file.
- **Line-count-neutral edits make a stale-reference retirement provably not create new stale
  references.** Every one of the eight sites was held to its original physical line count. That
  discharged, mechanically, both the risk this ticket exists to police (a ticket about retiring stale
  `file.ts:NNN` citations that creates six new ones by shifting line numbers under them — the literal
  #725 → #734 failure mode) and the shared-sentence contract with #729 at `inboundMessage.ts:115`,
  without either ticket needing to coordinate: #729 finds its clause exactly where it left it.
- **"Leave a claim standing" governs the claim, not its supporting reason.** Site S5
  (`threadTimeline.ts:133`) was the one AC-adjacent judgment call: the AC said leave the line standing,
  but leaving it unedited would have shipped a paragraph contradicting itself within four lines (`:132`
  now says the daemon event carries `conversationId`; `:133` unedited would still say the wire frame
  carries no field the renderer keeps). The repair kept the claim ("A NULLARY arm", "no payload")
  verbatim in substance and replaced only the reason — the same shape used at every other site, applied
  under real AC-wording pressure rather than a clean slate. Code review agreed this was the correct
  reading, not a violation.
- **A repair that states the rule rather than the neighbour survives its own future.** #729/#730/#714
  (all open at ship time) will each widen another arm in this family in turn; a rewrite that said
  "unlike `api-retry`, which drops it" would go false again in a few tickets, reproducing the defect
  being retired here. Every new reason clause cites either #732's already-merged wording or a named
  rule (#720's queue-state rule, #493's render slice) instead of a sibling arm's current behaviour.

## Lessons learned

*(from the PR #736 body, verbatim)*

- **A grep-based AC gate can be a floor for two independent reasons, and only one of them was
  anticipated here.** The spec correctly flagged that the AC1 gate is a line-scoped conjunction (it
  counts only when both vocabularies land on one physical line). The same wrap effect silently broke
  its *own* step-4 verification command, which greps a single two-word phrase that happens to straddle
  a line break in one of the three paragraphs it is meant to check. A verification command written
  against wrapped prose needs its expected count measured, not derived — or it needs to be a content
  check.
- **Line-count-neutrality is cheap to hold and worth stating as a contract.** Holding it made the six
  live cross-file `file.ts:NNN` back-references pointing below the edit sites structurally impossible
  to invalidate, and it discharged the shared-sentence contract with #729 at `inboundMessage.ts:115`
  without coordination. The cost was re-wrapping inside each block to a fixed line budget; the
  alternative is this ticket's own failure mode (retiring stale references by creating six new ones).
