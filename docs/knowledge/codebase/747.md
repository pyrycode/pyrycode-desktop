# #747 — Hold the four activity facts per conversation, keyed by conversation id

Split from #674 (sibling: #748, the writer; #749, the clears — this ticket's own body defers both).
Shipped as PR #750 (`ab70dae` spec commit + `840bfc7` feature commit), code review **PASS**, zero MUST,
zero SHOULD, two NIT. Size S, `security-sensitive`, architect self-security-review PASS; 2 new files,
489 insertions, no existing file touched.

## Summary

The renderer previously held turn-running, stalled, api-retrying and compacting as single scalars
belonging to whichever conversation is open (`threadTimeline.ts:189-224`, the "chrome scalars"). A
future sidebar needs the same four facts for every conversation at once, to draw a status dot on a row
the user has never opened. This ticket ships the holder for that — `conversationActivityStore.ts` — and
nothing else: no writer, no reader, and the existing chrome scalars are completely untouched.

Built to the `backgroundTaskRosterStore.ts` shape rather than re-derived: a `zustand/vanilla`
`createStore` DI factory, an app-wide singleton, a `useStore`-backed hook, and a `selectActivityFor(id)`
selector factory. State is `{ entries: ReadonlyMap<string, ConversationActivityEntry> }`. Four named
setters (`setTurnRunning`, `setStalled`, `setApiRetrying`, `setCompacting`), each a same-value guard
composed onto one private `writeEntry` copy-on-write helper — never a reducer, never a shared
multi-field equality check.

The store's single security surface, per the ticket body, is the daemon-supplied `conversationId` used
as a `Map` lookup key: `ReadonlyMap` is mandated and `Record<string, …>` forbidden, so `'__proto__'`,
`'constructor'` and `''` are ordinary keys by construction (`Map.prototype.get`/`.set` never touch the
prototype chain) rather than by validation. See
[conversation activity store](../features/conversation-activity-store.md) for the full feature writeup.

## Patterns established

- **A same-value guard must compare its own named field, not `undefined`-coalesced identity, for "first
  write creates the entry" to survive a first write of `false`.** `s.entries.get(id)?.field === value`
  yields `undefined` on an absent key, and `undefined` is never `===` a boolean, so the create branch
  always runs on a first write — including a first write of `false`, which is a real scenario here since
  `apiRetry`/`compacting` both carry explicit falling edges as their first-ever frame for a
  conversation. A guard shaped as a truthiness check or a shared four-field `entriesEqual` would
  conflate "never observed" with "observed idle" silently — no type error, no other failing test.
- **Guard per-setter on its own field, never a shared exhaustive comparison inside the write helper.** A
  shared `entriesEqual(a, b)` would silently stop writing the moment a fifth fact is added to the entry
  shape without a matching addition to the comparison. Four independent per-setter guards mean a fifth
  fact needs only a fifth setter with its own guard — no shared surface to forget to update.
- **Don't export the seed/default-entry constant.** The module-private `idleActivity` (all four fields
  `false`) is never exported. An exported seed invites `selectActivityFor(id) ?? idleActivity` at a read
  site, which collapses the absent-vs-observed-idle distinction with no type error and no failing test —
  the same collapse `queueStore`'s `?? EMPTY_BACKLOG` makes. This is the second time this exact trap has
  been named in this repo (see [background-task roster store](../features/background-task-roster-store.md)'s
  own warning against it) and is now avoided from spec time rather than found in review.
- **A store whose only job is holding a fact for a screen module's predicate should not import that
  predicate.** `isTurnRunning` already exists, tested, at `ConversationScreen.tsx:1343` — but it's
  exported from a React screen module. Importing it into this store would drag React, JSX and the
  screen's import graph into a store whose tests need no React and no DOM. The spec pushed the
  derivation to #748 instead and pinned a hard, grep-checkable constraint in the store's header: its
  only imports are `zustand/vanilla` and `zustand`. That constraint doubles as the AC3 (no
  misattribution) defense — with no reference to `activeConversationStore` in scope, a
  `?? activeConversation` fallback isn't something a developer must remember to avoid; it's unavailable.
- **Ship a store "populated and unread" ahead of its writer and reader, when the precedent already
  validates the posture.** `backgroundTaskRosterStore` shipped the same way across #573/#576/#577 before
  #568 became its first reader. This ticket, #748 and #749 repeat that staging deliberately, keeping
  each slice at one production file.

## Code review — PR #750, PASS, 0 MUST / 0 SHOULD / 2 NIT

- AC1 (writes create, including a first write of `false`), AC2 (cross-conversation reference stability,
  proven via a real `store.subscribe` counter plus a negative control so "the guard works" can't pass
  for a store that never writes), AC3 (the three-way read, plus the no-misattribution test that reads
  `null` for an unwritten id *while other conversations hold live facts*), and AC4 (hostile keys read
  before any write, write-side pollution checks, and non-aliasing between `''` and `'__proto__'`) were
  all independently re-verified against the diff, not just the spec's claims.
- Grepped the production file for the security invariants the spec asked to keep checkable: no `Record<`,
  no `Object.fromEntries`, no `JSON.stringify`, no computed object key (`{ [x]: v }`) anywhere.
- **NIT 1** — `conversationActivityStore.test.ts:92,101`: templated test titles render as
  `setturnRunning:` / `setapiRetrying:` (lowercase `set` + camelCase field name), not matching the
  actual setter names — cosmetic, but what a future reader greps for.
- **NIT 2** — `conversationActivityStore.test.ts:149-182`: the same-value-guard churn test and its
  negative control run against `setCompacting` only, not fanned across all four setters via the `facts`
  table already in the file. By hand-mutation, a guard cross-wired to the wrong field is caught for
  `setStalled`, `setApiRetrying` and `setCompacting` (via the independence test and the churn test), but
  **`setTurnRunning`'s guard field is pinned by no test** — it is only ever called first on a fresh
  store in this suite, so its short-circuit branch is unreachable. Not blocking: the shipped guards are
  all correct as written; the gap is in test coverage, not in the four setters themselves.

## Lessons learned

*(from the PR #750 body, verbatim)*

- A same-value guard written as `s.entries.get(id)?.field === value` is what makes "a first write of
  `false` still creates the entry" true, and it is true only because `undefined` is never `===` a
  boolean. Any guard shaped differently (a shared multi-field comparison, a truthiness check) silently
  conflates *never observed* with *observed idle* — no type error, no other failing assertion. Each
  setter therefore guards on its own named field rather than sharing one comparison, so a fifth fact
  added later cannot quietly stop a write.
- The `ReadonlyMap`-not-`Record` rule is invisible to `tsc`: swapping one for the other compiles clean.
  The assertion that actually bites is the **read before any write** — on a `Record`,
  `entries['__proto__']` yields `Object.prototype` and `entries['constructor']` yields the `Object`
  function, neither nullish, so `?? null` never fires and the selector hands back a non-entry. The
  write-side pollution checks alone would not catch the swap.
- Deliberately *not* exporting the module-private idle-entry seed is load-bearing rather than tidiness:
  an exported one invites `selectActivityFor(id) ?? idleActivity` at the read site, which is the same
  absent-vs-observed-empty collapse `queueStore`'s `?? EMPTY_BACKLOG` makes — again with no type error
  and no failing test.
