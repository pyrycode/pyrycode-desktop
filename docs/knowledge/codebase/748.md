# #748 — Feed the per-conversation activity store from the four daemon arms

Split from #674 (sibling: #747, the holder, shipped; #749, the clears, still open). Shipped as PR #759
(`a140232` spec commit + `a609f0d` feature commit), code review **PASS**, zero MUST, one SHOULD (both
non-blocking), two NIT. Size S, `security-sensitive`, architect self-security-review PASS; 2 new files
(`conversationActivityBridge.ts` + its test), 600 insertions, plus a one-line `App.tsx` mount and the
`pairing.css:59` citation repair that mount displaced.

## Summary

`conversationActivityStore` (#747) shipped as a holder with no writer. This ticket is the writer: a
second, independent subscriber on the daemon-event channel — in the `queueBridge` /
`backgroundTaskRosterBridge` reactive-only posture, no command sent, no connected-edge fetch — that
lands `turnState`, `stallDetected`, `apiRetry` and `compacting` into the store under **each event's
own** `conversationId`, never the open conversation's. `timelineBridge.ts` keeps feeding the open
conversation's existing chrome scalars exactly as before; the two paths don't overlap and neither was
touched by the other.

New file `src/renderer/src/store/conversationActivityBridge.ts` (231 lines): a `ConversationActivityWrite`
tagged union (`{fact,conversationId,<factName>:boolean}`, four members), a pure
`translateConversationActivity(event)` returning `readonly ConversationActivityWrite[]` (`default: []`
for every unowned arm — not an `assertNever`, since falling through is this path's permanent intended
behaviour), an injected `subscribeConversationActivity(onDaemonEvent, setTurnRunning, setStalled,
setApiRetrying, setCompacting)`, and the headless mount `ConversationActivityData(): null`. Mounted as
the eighth App-level leaf in `App.tsx`, after `AnnouncedModelData`, unconditional and route-independent
— which is what makes AC4 true: an arm for a conversation never opened, or one arriving before any
reader exists, still lands.

`turnState` is the one arm that isn't a straight copy: it fans out to **two** writes — `turnRunning`,
derived by reusing `isTurnRunning` (imported from `ConversationScreen.tsx:1343`, not re-derived — the
#648 defect is exactly what re-deriving would repeat) so a conversation counts as running in both
`thinking` and `responding`, and an unconditional `stalled: false` clear on any phase including `idle`,
reused verbatim from `threadTimeline.ts:356-359`. That two-facts-from-one-arm coupling is why the
translator returns a write union rather than the precedent's four sibling single-arm filters — the
ticket's one departure from `backgroundTaskRosterBridge`, whose own test header records it rejected a
tagged union for the opposite reason (its arm→setter mapping is one-to-one).

`apiRetrying` and `compacting` are deliberately **not** cleared by turn activity — mirroring
`threadTimeline.ts:196-205`, both have an explicit wire falling edge (`active: false`) and only that
clears them. This is the one place the four facts' clear semantics genuinely differ, and the module
header states the choice per fact rather than applying one rule to all four.

## Patterns established

- **A store/ → screens/ import is a legitimate, load-bearing exception to the store-must-not-import-React
  rule, when the constraint that forbids it is scoped to a different module.** #747's hard import
  constraint ("only `zustand/vanilla` and `zustand`") is pinned to `conversationActivityStore.ts` itself
  — a module whose tests run with no React and no DOM — and in the same breath names this ticket as the
  owner of the `isTurnRunning` derivation. A bridge is not that module; the precedent
  (`backgroundTaskRosterBridge.ts:18`) already imports `react`. The import costs nothing measurable
  because `App.tsx:2 → PairedShell.tsx:4 → ConversationScreen` is already in the boot graph on every
  route, and `vitest.config.ts:27`'s global `environment: 'node'` means `ConversationScreen.test.tsx`
  already pays that graph's test cost. One consumer is an import; a second store-side consumer of the
  same predicate would be the signal to relocate it instead.
- **When one wire arm fans out to more than one store fact, return a tagged-union write list from a pure
  translator rather than reusing sibling single-arm filters.** The precedent's per-arm filter shape is
  correct only when the arm→setter mapping is one-to-one; forcing `turnState`'s two writes through that
  shape either hides the coupling in a second filter switching on the same arm, or moves the clear into
  the subscriber — exactly where the precedent deliberately keeps only its `connected` reset. The union
  keeps the whole derivation, clear coupling included, inside one function a test can call directly, and
  is the smaller surface (one exported type, one switch) besides.
- **Name a write union's payload field after the fact, never a shared `value`.** With a shared `value`,
  `{ fact: 'stalled', value: false }` cross-wired to the wrong setter is a tag swap that type-checks.
  With `{ fact: 'stalled', stalled: false }`, `{ fact: 'stalled', turnRunning: false }` is a compile
  error. This is the same cross-wire class #747's review found at the store's setter tests (a
  cross-wired setter that passed all 22 of its tests) — made unrepresentable here rather than caught by
  a test.
- **A discriminant-only `assertNever` cannot be fully cast-free when the union carries untrusted payload
  data.** Property access on a `never` is `TS2339`, so reaching `write.fact` inside the throw needs
  `(write as { fact: string }).fact` (tightened in review to `(write as ConversationActivityWrite).fact`
  to keep the literal type). The repo's usual `JSON.stringify(event)` idiom needs no cast — an argument
  position accepts `never` — but would embed the untrusted `conversationId` in a thrown message here, on
  a path that's otherwise log-free by construction. Stringify the discriminant alone; diverging from the
  house idiom is deliberate, not an oversight, and the module header says so.
- **Four setters that all share the signature `(conversationId: string, value: boolean) => void` make
  positional wiring at the call site the one cross-wire the write union doesn't close.** Flagged in
  review as a SHOULD FIX, not blocking: swapping two setters in `ConversationActivityData`'s call to
  `subscribeConversationActivity` compiles clean, and no test in this repo can catch it, because
  `vitest.config.ts:27`'s global `environment: 'node'` means the mount's `useEffect` — the only place
  the positional call happens — never runs under any test tier. The precedent's own four-arg call is
  safe by accident of distinct payload types per argument (`backgroundTaskRosterBridge.ts:146-149`); here
  all four collapse to the same arity and the same primitive, so that accident doesn't transfer. Shipped
  order was verified field-by-field correct against the spec. Cheapest close, not applied here: pass the
  four setters as one named object so the call site states each name beside its call — left as an easy
  pickup for #749, which touches this same subscriber next.

## Lessons learned

*(from the PR #759 body, verbatim)*

- A leaf added to `App.tsx` falsifies file:line citations pointing past the insertion. The one-line
  import shifted `pairing.css:59`'s `App.tsx:51` pointer to `:52`; repaired in this diff.
  `announcedModelStore.ts:118`'s `App.tsx:126-142` was already stale before this branch (an earlier leaf
  addition moved it) and was left alone as someone else's drift — worth knowing for #749/#676, which
  mount nothing but sit in the same file.
- The repo has no wired `lint`/`format` script and no prettier/eslint config — `npx prettier --check`
  flags shipped files including `backgroundTaskRosterBridge.ts` and `App.tsx` at HEAD, so prettier's
  defaults are not this repo's style. Match the existing ~100-column/2-space/single-quote/no-semicolon
  convention by hand instead, and measure line length in characters, not `awk length` bytes — em-dashes
  and `→` count double there, and every comment line in this repo has them.

## Known divergence, named not fixed

In the open conversation, `stalled` also clears on `assistantDelta`, `toolUse`, `toolResult` and
`userText` (`threadTimeline.ts:284`). This path can't do that: those four arms carry no `conversationId`
at all (`events.ts:109-110`, `:459-466`, `:467-472` — dropped at the emit), so there's no id to key a
write on, and redirecting them onto the open conversation is the exact `?? activeConversation` fallback
`events.ts:116-117` bans. Consequence: a stall in a conversation the operator isn't looking at persists
from onset until that conversation's next `turnState` — bounded (every turn ends with one), not latched,
but coarser than the open conversation's chrome. #676 inherits this knowingly. Closing the gap is #675's
transport work, not this ticket's.
