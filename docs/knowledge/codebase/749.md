# #749 — Activity-store eviction: drop on delete, clear all on the handshake edge

Split from #674 (sibling: #747, the holder; #748, the feed — both shipped first). Shipped as PR #760
(`55ed027` spec commit + `0bfee97` feature commit), code review **PASS**, zero MUST, one SHOULD
(non-blocking), one NIT. Size S, security-sensitive, architect self-security-review PASS. 4 files
changed (2 production, 2 test), 401 insertions / 62 deletions, no new files.

## Summary

`conversationActivityStore` (#747) shipped as a holder with no eviction, and #748's feed left it
unbounded. This ticket adds the two removal paths and wires each at its own seam:

- **`dropConversation(conversationId)`** (`conversationActivityStore.ts`) — removes exactly one key.
  Guards on `s.entries.has(conversationId)`; an absent key returns `s` itself so zustand's
  `Object.is` short-circuit wakes no subscriber. Otherwise clones the outer map (`new Map(s.entries)`),
  `delete`s on the clone, and returns `{ entries: next }` — never `s.entries.delete(...)` in place, the
  same clone-on-write discipline `writeEntry` already documents, so every surviving entry stays
  `Object.is`-identical to the one held before the drop.
- **`clearAllActivity()`** (`conversationActivityStore.ts`) — drops every key. Shaped verbatim after
  `backgroundTaskRosterStore.ts`'s `resetRosters`: guard on `s.entries.size === 0`, else return a fresh
  empty `Map`. Deliberately does not hand back `initialConversationActivityState` — that exported
  constant holds a module-shared *mutable* `Map`, so returning it as live state would make every
  cleared store instance share one object.
- **Wiring** (`conversationActivityBridge.ts`) — two early-return branches in
  `subscribeConversationActivity`, ahead of the unchanged `translateConversationActivity` switch:
  `conversationDeleted` → `deps.dropConversation(event.id)` (no truthiness guard — `''` is a real id
  the daemon can emit), `connected` → `deps.clearAllActivity()`. Neither becomes a member of the
  `ConversationActivityWrite` union; the translator stays a pure arm→fact filter.
- **The `connected` edge, not `clearPairingScopedState`.** On that file's own discriminator ("does a
  reconnect to the SAME daemon need to clear it?") the answer here is yes: all four facts are
  liveness, so a turn that finished while the socket was down must not leave a stale working dot after
  reconnect. `clearPairingScopedState.ts` and its five-key pin are untouched by design. Because the
  `connected` edge fires on every completed handshake (`daemonConnection.ts:466-481`, the sole emit
  site) and both pairing-change paths (unpair, and pair-another-server) re-handshake, and the
  subscriber is mounted App-level rather than inside `PairedShell`, one live listener spans both
  transitions without a keyed branch for either.
- **Delete seam deliberately not `PairedShell.tsx:230-235`.** That existing `useConversationDeletedExit`
  callback runs `exitActiveConversation`, gated on the id matching the *open* conversation. Eviction
  must be ungated — a background conversation losing its dot is the entire point — so this ticket adds
  a third, independent listener on the same `conversationDeleted` arm rather than folding into the
  gated one.

## Patterns established

- **A positional list of same-shaped effects gets *less* safe as a ticket adds to it, not more, and the
  hazard can be structurally uncoverable.** The four setters already collapsed to
  `(string, boolean) => void`. Because a function of fewer parameters is assignable to one of more, this
  ticket's two new members — `(string) => void` and `() => void` — are *also* assignable into any of
  those four slots. `vitest.config.ts:26-27`'s global `environment: 'node'` means no test in this repo
  ever runs the effect (`ConversationActivityData`'s mount) that does the positional wiring, so a
  cross-wire would compile and pass the whole suite. The fix is a named `ConversationActivityDeps`
  object — closes the SHOULD FIX #748's review assigned forward to this ticket in as many words.
  Deliberately **not** given an `Object.keys(deps).sort()` pin like `clearPairingScopedState.test.ts`'s:
  that pin guards divergence between two independent call sites, and this seam has one.
- **An `Object.is`-survivor assertion alone does not catch an in-place `delete`.** With a single map,
  survivors are trivially identical whether the removal cloned or mutated in place, so that assertion
  passes against the mutation it looks like it guards. The test that actually catches it captures the
  previous `entries` map before the drop and asserts it *still* `has` the dropped id afterward.
- **A same-value guard on an absent key needs a negative control, not just the zero-notification
  assertion.** A `store.subscribe` counter staying at 0 after a no-op drop also passes for a drop path
  that never writes at all. Pin it with a paired test proving a held-id drop *does* notify.
- **Map-store clear = the size guard, never the exported `initial*State` constant.** The module-shared
  `Map` inside `initialConversationActivityState` is mutable; handing it back as live state on every
  clear would alias every cleared store instance to one object. `backgroundTaskRosterStore.ts`'s
  `resetRosters` is the copyable shape.
- **Editing a heavily-cited file's header shifts every inbound `file:line` citation below it.** The
  store's header and type docstring grew by 6 lines here, falsifying four `conversationActivityStore.ts:<line>`
  refs inside the bridge plus one self-citation. All five were re-derived and repaired in this diff
  (`:26-27`→`:28-29`, `:47-49`→`:49-51`, `:15-18`→`:17-20` ×2, `:140-151`→`:146-157`).

## Code review — PR #760, PASS, 0 MUST / 1 SHOULD / 1 NIT

- All three ACs independently re-verified against the diff: AC1 (drop is `Object.is`-survivor-safe,
  proven by the previous-map-still-has-the-id test, not just the identity assertion), AC2 (absent-key
  drop notifies nobody, proven with a paired negative control showing a held-id drop *does* notify), AC3
  (the `connected`-edge seam covers both pairing-change paths, is re-armable rather than one-shot, and
  `disconnected` does **not** clear — a socket flap must not empty the store before it reconnects; that
  last pin wasn't asked for and was called out as a good addition).
- **SHOULD FIX** (non-blocking) — bare `(ACn)` test tags collide once an A→B→C split lands in one test
  file: `(AC1)`/`(AC2)`/`(AC3)` in both `conversationActivityStore.test.ts` and
  `conversationActivityBridge.test.ts` each now name **two different tickets'** ACs (#747's vs #749's),
  with no qualifier to disambiguate — e.g. the store's own production comment at one line calls a
  property "AC2" while the test for that same property is tagged `(AC1)`. Not a behaviour defect; the
  fix is a per-ticket qualifier (`(#749 AC1)`) on new tags, leaving sibling tags alone. **This is a
  cross-ticket test-tag convention gap, not specific to this ticket's code** — future tickets extending
  a test file another ticket already tagged should qualify their own tags from the start.
- **NIT** — the store header's new quotation of the seam discriminator cites `announcedModelStore.ts:29-45`,
  which is itself quoting `clearPairingScopedState.ts:30-33` (where the rule actually lives, and what the
  bridge cites for the identical argument). Two files, two citations, one rule.
- Blast radius verified by grep (codegraph still holds no index for this repo —
  `.codegraph/` is config-only). `subscribeConversationActivity`'s signature change has exactly three
  call sites (the mount plus two tests), all converted.
- Security walk: no `console.*`, no `localStorage`, no `ipcRenderer`, no computed object keys on the
  removal paths (`event.id` reaches `Map.prototype.delete` as a value, never a key/path/URL/render), the
  spec's explicit instruction not to log a "dropped N" or "cleared N entries" count was honoured, and the
  hostile-key test at the drop path keeps the read-before-write ordering that is the only assertion that
  would survive a future `Map`→`Record` swap.

## Lessons learned

*(from the PR #760 body, verbatim)*

- A positional list of same-shaped effects gets *less* safe as a ticket adds to it, and the hazard here
  is structurally uncoverable. The four setters already collapse to `(string, boolean) => void`; the two
  members this ticket adds — `(string) => void` and `() => void` — are also assignable into any of those
  four slots, because a function of fewer parameters is assignable to one of more. So a cross-wire
  compiles and passes the whole suite, and no test can catch it: `vitest.config.ts:26-27` is
  `environment: 'node'` globally, so nothing in this repo ever runs the effect in
  `ConversationActivityData` that does the wiring. A named deps object is the only mechanism available.
- An `Object.is`-survivor assertion does not catch an in-place `delete`. With one map the survivors are
  trivially identical, so the identity check passes against the mutation it looks like it guards. What
  catches it is capturing the previous `entries` map and asserting it *still* holds the dropped id
  afterwards — verified by mutation, not assumed.
- Editing a heavily-cited file's header shifts every `file:line` citation below it. The store's header
  and type docstring grew by 6 lines, falsifying four `conversationActivityStore.ts:<line>` refs inside
  the bridge and one self-citation. Repaired by re-locating each anchor and rewriting only what this
  diff moved.
