# #752 — Carry the conversation id on the `turnEnd` IPC arm

Split from #675 (child B of an 8-way split: #751-754 transport arms / #755 store / #756 bridge /
#757 clears / #758 screen). Shipped as PR #762 (`06de251` spec commit + `335e5ab` feature commit),
code review **PASS** (0 MUST FIX, 1 SHOULD FIX, 2 NIT — non-blocking). Size S, `security-sensitive`,
architect self-security-review PASS. 8 files, 78 insertions / 13 deletions, no new files.

## Summary

`TurnEndPayload` has always carried `conversation_id` on the wire, and `parseTurnEndPayload`
(`inboundMessage.ts:566`) has always `requireString`d it — but the transport's `turnEnd` emit
discarded it, the same single-active-conversation assumption #724/#732/#737/#742/#751 already
retired for `turnState`/`stallDetected`/`apiRetry`/`compacting`/`assistantDelta`. This is the sixth
instance of that widening and the second on a turn-stream item, landing directly on top of #751:
that ticket rewrote the shared `events.ts` comment block the two v2 interactive-stream arms used to
share, so the seam this ticket edits did not exist on `main` until #751 merged — this ticket built
and cited against #751's merged result, not `main`.

**Production change — two files, matching #751's shape:**

- `src/shared/ipc/events.ts` — the `turnEnd` arm gains `conversationId: string`, required, last:
  `{ type: 'turnEnd'; turnId: string; stopReason: string; conversationId: string }`.
- `src/main/daemonConnection.ts` — the `turn-end` case's literal gains one line, reading the id
  **bare** from the already-decoded payload: `conversationId: inbound.turnEnd.conversation_id`.
  Copied **by name**, never a spread, so a decoder that later grows a field cannot smuggle it
  across IPC.

**No decode change.** `parseTurnEndPayload` already required `conversation_id` before this ticket
existed, so AC2 ("the id is a required, never-optional, fail-closed routing key") was already true
by construction; the new test at `daemonConnection.test.ts` is a **guard** pinning the bare read at
the emit, not a fix for present behaviour — the live risk was always `?? ''` turning a fail-closed
drop into a silent misattribution.

The id **stops at the renderer timeline bridge** exactly as it did for #751: `translateTimelineEvent`
(`timelineBridge.ts:41-42`) rebuilds a fresh three-field `ThreadEvent.turnEnd` by name and is
untouched by this diff — `ThreadEvent` carries no conversation id. Routing lands in #756. The four
other consumers (`daemonEventBridge.ts`, `pushNotifyBridge.ts`, `modalBridge.ts`,
`conversationActivityBridge.ts`) access no field on this arm and needed no change.

## Patterns established

- **A shared comment block that "defers" to a sibling arm's paragraph must actually defer — restating
  the terms it points at is a duplicate, not a reference.** SHOULD FIX-adjacent NIT from code review:
  the `events.ts:131-140` rewrite opened with *"it crosses for the reason the delta arm above carries
  it, on the same terms"* and then restated all four terms anyway (required-never-optional, routing
  key not rendered text, fail-closed decode, stops-at-the-bridge), landing at 10 lines against the
  spec's ~6-9 target, three lines under #751's already-stated 21-line paragraph. Two near-identical
  blocks that close together read worse than one deferring sentence, not better — worth settling the
  shorter shape before #753/#754 repeat it a third and fourth time.
- **A guard test's comment must claim only what the specific inputs it feeds can prove.** The SHOULD
  FIX: the new no-emit guard's comment says a future `?? ''` regression *"would turn this fail-closed
  drop into a silent misattribution, and nothing else in the suite would notice"* — but both fixtures
  the test feeds (`conversation_id: undefined`, `conversation_id: 42`) make `parseTurnEndPayload`
  throw before the `turn-end` case ever runs, so a `??` fallback at the emit is unreachable dead code
  for *this* test and it would stay green either way. The test is still valuable — it pins the true
  end-to-end invariant (no bad-id frame ever reaches IPC, whichever layer enforces it today) — but the
  comment should say that composite claim, not claim detection power the test's own inputs don't
  exercise. #751's twin comment phrased the equivalent claim as a statement about the *code*
  ("the emit reads it bare so it cannot paper over the absence"), which stayed accurate; this one
  phrased it as a claim about the *test's* detection power, which didn't. Template risk for #753/#754.
- **An AC4 census inherited from a precedent ticket still needs an independent re-sweep — the count is
  never the same shape twice.** The architecture spec found five census sites where the ticket body
  named two: a test *name* enumerating fields (`daemonConnection.test.ts:1381`), an executable leak
  guard that must **invert** (`:1390`, `not.toContain` → `toContain`), and a second field-counting
  comment (`pushNotifyBridge.test.ts:110`) the body missed entirely. Code review then re-ran the
  census independently rather than inheriting the spec's list (145 `turnEnd`/`turn_end` hits across 32
  files) and found nothing further — but confirming that took a fresh sweep, not trust.
- **The `toEqual`-before-guard ordering trap recurs per arm, and getting caught by it twice in the same
  family is expected, not a regression.** `daemonConnection.test.ts:1389`'s `toEqual` throws before
  `:1390`'s `not.toContain('conv-1')` guard ever executes — identical in shape to #751's `:1359-1361`
  trap one arm over. Both had to be edited in the same pass; the PR body confirms the guard was
  verified to have genuinely executed after GREEN, not merely skipped by the ordering.
- **A `-XYZ` leak-guard fixture value is load-bearing per field it's meant to cover, not per test.**
  `pushNotifyBridge.test.ts`'s `not.toContain('XYZ')` assertion only proves no daemon field leaks if
  every new fixture value also contains `XYZ` — `conversationId: 'conv-1'` would have compiled,
  passed, and left the shipped guard silently vacuous for the new field. `'conv-XYZ'` was used instead,
  and code review swept every other touched test file for `not.toContain('conv-1')` guards the new
  fixture value could have quietly interacted with, finding none.
- **Debt flagged as out-of-scope by one ticket in a chain must be re-flagged, not silently absorbed,
  by the next.** The nine already-stale absolute `events.ts:<line>` citations #751 left unrepaired
  (repairing them would have pulled 4 more production files into a 2-file ticket) got further out of
  date when this ticket grew the same comment block again. Correctly left alone a second time — fixing
  them now would still cross the split threshold — but code review flagged it again rather than
  treating #751's deferral as having already covered it. Sweep still pending until #753/#754 land.

## Lessons learned

*(from the PR #762 body, verbatim)*

- The compiler finds five of the six "gains" sites; vitest finds the sixth. `tsc -p
  tsconfig.node.json` reports **zero** errors for this change — the one node-side fixture
  (`daemonConnection.test.ts:1388`) sits inside a `toEqual`, invisible to the compiler. A clean
  `npm run typecheck` looks done while a test fixture is still stale; the test run is a separate gate,
  not a formality.
- The `toEqual`-before-guard ordering trap is real and self-concealing. In the same test, the
  `toEqual` throws *before* the following `not.toContain('conv-1')` line ever runs. Fixing only the
  `toEqual` and re-running surfaces the leak guard as a fresh, surprising failure on the *next* run.
  Both must be edited together — and confirmed genuinely executed after GREEN, not merely skipped.
- `-XYZ` fixture values are load-bearing, not decorative. `pushNotifyBridge.test.ts` asserts
  `not.toContain('XYZ')` to prove no daemon field reaches the notification payload; a `'conv-1'`
  fixture would have compiled, passed, and silently left that shipped guard vacuous for the new field.
- Nine `events.ts:<line>` citations across five files are already stale on `main` (#751 grew this same
  comment block without repairing them), and this block grew again here. Deliberately out of scope —
  repairing them would pull four more production files in — so no absolute `events.ts:<line>`
  reference was written into any new comment; arms are referred to by name. Worth one sweep ticket
  once #753/#754 stop moving the block.
- `src/main/transport/fakeRelayForwarder.test.ts` flakes on a full-suite run independently of this
  change; the spec documents it and it passes 8/8 in isolation.
