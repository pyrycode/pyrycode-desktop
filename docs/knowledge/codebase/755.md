# #755 — Hold a timeline per conversation, bounded and least-recently-viewed evicted

Split from #675 (sibling: #756, the writer; #757, the clears; #758, the reader cutover — this ticket's
own body defers all three). Shipped as PR #770 (`5768777` spec commit + `afe2cc3` feature commit), code
review **PASS**, zero MUST, zero SHOULD, two NIT. Size S, `security-sensitive`, architect self-security-
review PASS; 2 new files, 817 insertions, no existing file touched.

## Summary

The renderer holds exactly one timeline — `timelineStore.ts` types and singletons a single flat
`TimelineState` belonging to whichever conversation is open, and `activateConversation.ts` resets it on
every switch to a different id. Leaving a chat and coming back threw the thread away. This ticket ships
the keyed holder for that — `conversationTimelineStore.ts` — and nothing else: no writer, no reader, the
existing flat store untouched.

Built directly to the twin's shape rather than re-derived: [conversation activity
store](../features/conversation-activity-store.md) (#747) is the same slice of the same problem one
family over, keying four booleans instead of a whole thread. Same `zustand/vanilla` DI-factory →
singleton → `useStore` hook → selector-factory shape, same `ReadonlyMap<string, …>` state, same
copy-on-write, same `?? null` three-way read. The payload here is `TimelineState` itself (no wrapper
entry type — the whole flat timeline's `items`/`phase`/four chrome scalars is what a key holds), and
`reduceTimeline` is reused unchanged for the fold, so this store is smaller than its twin despite having
one more write path.

The one deliberate divergence from **both** keyed precedents (`backgroundTaskRosterStore` and
`conversationActivityStore`, which each refuse a cap on purpose) is `MAX_RETAINED_TIMELINES = 10` with
least-recently-**viewed** eviction — because a timeline slice is a whole thread of assistant text with
no wire-side ceiling, and because a timeline must survive a reconnect (unlike its two siblings, which
both empty wholesale on the `connected` edge) so there is no periodic floor to bound growth for free. The
bound needs a second write path beyond the fold — `markViewed(conversationId)` — since "least recently
viewed" requires a "this conversation was made active" signal distinct from being written to. See
[conversation timeline holder](../features/conversation-timeline-holder.md) for the full write-up of the
eviction invariant.

## Patterns established

- **Head-insert / tail-promote is the shape for a bounded, keyed LRU-viewed cache: new/daemon-driven
  writes enter at the head, only the deliberate "viewed" signal promotes to the tail, and eviction always
  takes the head.** The map's own iteration order *is* the eviction order — no separate ordering
  structure. This is a reusable shape, not a one-off: any future keyed store that needs "evict what
  nobody's looking at" over "evict what's oldest" should copy this rather than re-derive it.
- **When new keys must not enter at the position eviction targets, prove the threat scenario, not just
  the happy path.** Entering new (never-viewed) slices at the tail would let a burst of unknown
  conversation ids evict the operator's actually-open threads — the bound becoming the attack's mechanism
  rather than its defense. Entering at the head instead means an unbounded burst of unknown ids displaces
  **at most one** viewed slice and thereafter only evicts its own never-viewed predecessors. Reinforced
  structurally, not just by policy: `dispatchFor` (daemon-driven) can only ever insert at the head, and
  only `markViewed` (renderer-local, reachable only from the operator's own activation) can promote to
  the tail — the protected region of the map is populated by operator action alone.
- **`Map` has no insert-at-head primitive**, so a head-insert-with-eviction is a full `Map` → entries →
  `Map` rebuild (`withNewSliceAtHead`), not a `.set` on the existing map. This reads like the map-spread
  the twin's header forbids but is not it: the prohibition is about materializing the map into an
  **object** (`Object.fromEntries`, a spread into `{}`, `JSON.stringify`), and `new Map(iterable)` uses
  `Map.prototype.set` semantics throughout, so a hostile key like `'__proto__'` stays an ordinary own
  entry across the rebuild. Worth stating explicitly in the header before code review has to re-derive it.
- **A same-value guard on the *tail* position, not on `size`, is what makes "already-viewed re-click"
  free of churn.** `markViewed` first checks whether the target is already the tail key; only a genuine
  move or a genuine create touches the map. This matters because `activateConversation`'s `onOpen` fires
  for every row click including a re-click of the already-active row — the common case, not an edge one.
- **`markViewed` must create an entry on an absent key, not no-op.** This is underivable from the
  method's own signature or from AC text alone — it falls out of the future #758 call order: the operator
  opens a conversation *before* any daemon event for it has arrived, so if `markViewed` no-opped on
  absence, a later fold would create the slice **at the head**, making the conversation currently on
  screen the next eviction victim. The word "viewed" exists specifically to prevent that.
- **Avoiding `Map.keys().next().value`'s `string | undefined` without a non-null assertion**: a `let
  evicting` boolean that starts `true` when the map is already at the bound, and falls to `false` on the
  first loop iteration either way, both skips the head entry and copies every survivor in one pass with
  no key ever extracted or asserted non-null.
- **A twin's structural defense can be unavailable, and needs a substitute named explicitly rather than
  silently dropped.** The twin's rule ("don't export the seed/empty-entry constant, or a read site can
  collapse absent-vs-empty via `?? seed`") can't transfer here — `initialTimelineState` is already
  exported from `threadTimeline.ts` for the flat store's own use, and un-exporting it would be an
  adjacent refactor. The substitute is three compensating controls: a module-header ban on
  `selectTimelineFor(id) ?? initialTimelineState` at any read site, not re-exporting the constant from
  this module (so a collapse needs a deliberate import from `threadTimeline` instead of an easy local
  reference), and the AC4 tests asserting the distinction through the read surface alone.

## Code review — PR #770, PASS, 0 MUST / 0 SHOULD / 2 NIT

- Re-traced the eviction invariant independently of the suite (a throwaway one-turn script, not the test
  file's own scenarios): a 15-id hostile burst against a map holding one viewed thread left that thread
  present **and still at the tail**; all-viewed-at-bound evicted the LRV; a move of a present key at the
  bound evicted nothing and preserved size.
- Verified two claims the store leans on that live outside the file: `TimelineState` is exactly the six
  fields the payload copies unchanged, and `reduceTimeline` has no in-place mutation anywhere (`push`/
  `splice`/`sort`/`reverse`/indexed assign all absent from `threadTimeline.ts`), which is what makes
  seeding a new slice with the shared `initialTimelineState` reference safe.
- Grepped the file for every security invariant the spec asked to keep checkable: no `Record<`, no
  `Object.fromEntries`, no `JSON.stringify`, no computed object key, and the hard import constraint
  (`zustand/vanilla`, `zustand`, `./threadTimeline` only — no `activeConversationStore`, no
  `./timelineStore`, no `screens/`).
- **NIT 1** — `conversationTimelineStore.test.ts:162`: the one-over-bound id is a bare `'c11'` rather than
  `` `c${MAX_RETAINED_TIMELINES + 1}` ``. Raising the exported constant — which the module's own docstring
  advertises as "a one-literal edit" — turns `'c11'` into an already-present key, degrading this one test
  to a vacuous pass instead of a failure, even though four sibling tests in the same file still fail
  loudly on the same edit.
- **NIT 2** — `conversationTimelineStore.ts:183-199`: `withNewSliceAtHead` is partial (no guard against
  being called with an already-held key) where its neighbour `withSliceAtTail` is total (guards with
  `if (id !== conversationId)`). The single call site is correctly gated (`held === undefined`) and the
  docstring says "a NEWLY CREATED slice," so nothing is wrong today, but the asymmetry between two
  adjacent helpers is worth an explicit precondition line for whoever adds a second call site.

## Lessons learned

*(from the PR #770 body, verbatim)*

- `Map` has no insert-at-head operator, so rule 2 (a newly created slice enters at the head) needs a full
  `Map` → entries → `Map` rebuild. That rebuild reads like the map-spread the twin's header forbids but
  is not it: the prohibition is about materialising the map into an **object**, and `new Map(iterable)`
  uses `Map.prototype.set` semantics, so `'__proto__'` stays an ordinary own entry. A
  hostile-key-survives-eviction test pins it.
- `markViewed` must **create** on an absent key. That is underivable from its signature and falls out of
  the #758 call order: the operator opens a conversation before any event for it arrives, so a no-op
  would let a later fold create the slice at the head — making the conversation on screen the next
  eviction victim.
