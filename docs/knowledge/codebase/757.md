# #757 — clear per-conversation timelines on the exit and pairing-end edges

Child G of #675 (siblings: #751-#754 the transport arms, shipped; #755 the holder, shipped; #756 the
writer, shipped; #758 the reader cutover, open). Shipped as PR #781 (`452d86d` spec commit + `8df0546`
feature commit), code review **PASS**, zero MUST, two SHOULD (both comment-cite drift, folded into the
citation-sweep ticket rather than gating), one NIT. Size S, architect self-security-review PASS. Seven
files touched (four production, three test), 404 insertions / 54 deletions, 16 RED → 52 green.

## Summary

The keyed holder ([conversation timeline holder](../features/conversation-timeline-holder.md)) shipped
in #755 with two write paths — `dispatchFor` and `markViewed` — and no clear at all. #756 gave it its
first writer, which meant an unpair or a pair-another-server left every conversation's thread from the
previous pairing sitting in renderer memory, keyed by ids the *next* server could reuse. This ticket adds
the two clears the store was always going to need and wires them at the two edges that already reset the
flat `timelineStore`:

- `clearAllTimelines()` — nullary, drops the whole map. Wired into `clearPairingScopedState` (the shared
  pairing-end helper: unpair or pair-another-server), immediately after the flat store's `reset`. AC3's
  "takes no conversation id at all" is a property of the signature, so `tsc` enforces it rather than a
  test.
- `clearTimelineFor(conversationId)` — drops exactly one key. Wired into `exitActiveConversation` (fired
  when the conversation on screen was deleted or archived out from under the operator), also immediately
  after the flat store's `reset`, keyed by the helper's own `conversationId` argument rather than a
  second `getActiveConversation()` call.

Both methods **delete**, never overwrite with an empty slice — `set(id, initialTimelineState)`
type-checks identically but would collapse "nothing is held" into "observed; nothing in the thread",
exactly the distinction `selectTimelineFor`'s `?? null` exists to preserve. Both guard the no-op case
(already-empty map; already-absent key) by returning the state object unchanged, which is what keeps
`clearPairingScopedState.ts`'s idempotence claim — asserted by a shipped test — true rather than merely
convenient. `Map.prototype.delete` preserves the iteration order of every surviving entry, so the
eviction invariant from #755 (head-insert on create, tail-move on view) needs no new rule: a removal
re-orders nothing.

The store gained no new import and no new file; `ConversationTimelineStore` grew from two write paths to
four. The two dep interfaces (`ClearPairingScopedStateDeps`, `ExitActiveConversationDeps`) each gained one
*required* field, so every construction site — `PairedShell.tsx`'s two module-scope dep objects, both
`spyDeps()`/`realDeps()` factories, and one inline literal in `exitActiveConversation.test.ts` — was a
compile error until updated, which is what made "wire it or fail the build" the enforcement mechanism
rather than a review checklist.

## Patterns established

- **A whole-map clear's "already empty → return the same object" branch is a consumer's docstring
  contract, not an allocation micro-optimisation.** `clearPairingScopedState.ts` claims all of its clears
  are idempotent by construction and a shipped test asserts it; dropping the guard on `clearAllTimelines`
  would fail that test two files away with nothing pointing back at the cause. When a sibling helper
  documents idempotence as a property of *your* store, the short-circuit that makes it true is load-bearing
  even where it reads like a nicety.
- **A per-key clear takes the deleting helper's own already-validated id argument, not a second read of
  the source it was compared against.** `exitActiveConversation`'s gate
  (`getActiveConversation()?.id !== conversationId`) already proves the two are equal past that line;
  `clearTimelineFor(conversationId)` uses the parameter, so there is no second `getActiveConversation()`
  call and no non-null assertion to ban.
- **The dual-write idiom generalises to dual-clear at the same call-site position.** #756 established
  "flat store first, keyed store second" for the two writers (`composerSend.ts`, `timelineBridge.ts`);
  this ticket places both new clears immediately after the pre-existing flat `dispatchTimeline({ type:
  'reset' })` call in each helper, for the same reason — one fact expressed against two stores, and
  retiring the flat store later becomes a deletion at that position rather than a search for where the
  keyed clear belongs.
- **A cite's staleness and its correct target are separate questions, and the target depends on the claim
  being cited, not just the file.** `clearPairingScopedState.ts:53` and `PairedShell.tsx:38` both cited
  the same stale `timelineBridge.ts:206`, for different claims ("the timeline's production writers" vs.
  the `getState()`-inside-the-arrow idiom). Both happen to re-pin to `:347` — a coincidence of that one
  line being both, not a rule that would generalize to a different pair of stale cites.
- **A "post-edit anchors" table built by grepping cites *pointing into* the diff will still miss cites
  authored, and immediately stale, *inside* the diff.** Code review found two: a spec-authored `:218`
  cite in a freshly-written comment landed on an unrelated `if (evicting)` brace after the docblock above
  it grew, and a `:65-70` cite to the idempotence paragraph drifted to `:69-76` when this same PR edited
  that paragraph. Both are zero-cost fixes since the target file is already in the diff, but neither was
  caught by measuring drift only in files the diff doesn't touch — a self-authored cite needs the same
  measurement pass as an inherited one.

## Lessons learned

*(from the PR #781 body, verbatim)*

- **A cite's staleness and its correct target are separate questions, and the target depends on the
  claim.** `clearPairingScopedState.ts:53` and `PairedShell.tsx:38` both cite the same stale
  `timelineBridge.ts:206`, but for different claims — "the timeline's production writers" vs. the
  `getState()`-inside-the-arrow idiom. They happen to re-pin to the same line (`:347`), which is a
  coincidence of that line being both; grading one by the other would not generalise.
- **`Map.prototype.delete` preserving iteration order is what lets a removal sit under an eviction-ordered
  map with no invariant edit.** Worth asserting on `[...timelines.keys()]` directly rather than only
  behaviourally: the behavioural form needs two follow-up writes to force an eviction, and the
  never-viewed-first policy means the newly created victim dies first and masks whether the survivors
  kept their order.
- **The `size === 0` short-circuit in a whole-map clear reads like an allocation micro-optimisation and is
  actually a consumer's docstring contract.** `clearPairingScopedState.ts:65-70` claims every one of its
  clears is idempotent by construction and a shipped test asserts it, so dropping the guard fails a test
  two files away with no mention of allocation.
