## Summary

#763 (`52dc0cc`) widened the `toolUse` IPC arm with `conversationId`, sweeping its own two files and
their test twins in the same commit. Three comments outside those files still described the
pre-widening contract, each encoding the drop **indirectly** — a grep on `conversation_id` reached
none of them:

- `src/main/transport/inboundMessage.ts:218-219` — the `tool-use` kind's decode-layer contract
  paragraph, which named the drop directly ("the consumer carries the four render fields onward,
  dropping `conversation_id`") and had the count wrong twice over: "four" was already off by one
  before #763 (#642's `input` made it five), and the drop clause went false the moment #763 shipped.
- `src/renderer/src/store/threadTimeline.ts:103-104` and `src/renderer/src/store/timelineBridge.ts:48-50`
  — the load-bearing pair. Both asserted the `DaemonEvent` and `ThreadEvent` `toolUse` shapes are
  **field-for-field identical**, using that equivalence to justify why `translateTimelineEvent`'s arm
  is "a filter + fresh copy, not a remap." A comment asserting equivalence with a type that must *not*
  gain the field encodes the drop as firmly as one naming it — and `translateTimelineEvent` is exactly
  the seam where the id must stop, the seam the per-conversation routing slice (#756) builds on.

The repair rewrites all three to say what the arm now does: the decode-layer paragraph states the
consumer carries **five render fields plus `conversation_id`**; the two renderer comments state the
`DaemonEvent` carries `conversationId` beside the render fields while the `ThreadEvent` this bridge
returns does not, so **the id stops here** — matching the shipped idiom `stallDetected`/`apiRetry`/
`compacting` already carry in both files, per #738/#743's precedent. Zero executable lines change,
zero tests touched — #763 had already swept its own test twins.

## Patterns established

- **Two adjacent "five"s in one sentence can both be true, and the fix is to split the sentence
  rather than reconcile the numbers.** `inboundMessage.ts:218`'s repaired paragraph names "the five
  render fields" (`turn_id`/`tool_use_id`/`name`/`input_summary`/`input` — excludes the id) and "(five
  strings, no enum)" (the fail-closed decode's required strings — includes the id, excludes `input`,
  which isn't a string). The developer split the clause at the semicolon rather than "harmonising" the
  counts, which is what the spec's § D1 flagged as the failure mode to avoid.
- **A `replace_all` on the obvious grep phrase inverts when a sibling ticket's still-true claim uses
  near-identical wording.** `inboundMessage.ts:224` (#767's `tool-result` claim, true until #766 lands)
  is the only single-line match for the phrase this ticket's Site 1 paraphrases; Site 1's own copy
  wraps across two lines and never matches on one. The review confirmed this inversion did not occur —
  the developer edited both blocks individually rather than reaching for a repo-wide replace.
- **Drop a stale absolute line citation rather than re-pinning it, when the sentence is being rewritten
  anyway.** `threadTimeline.ts:103`'s `(events.ts:384-391)` no longer pointed at the `toolUse` arm even
  before this ticket (it had moved to `:498-506`) and moves again with #755. The repair names `#763`
  instead of a line number — an absolute citation would re-enter the same deferred stale-citation
  backlog on the very next arm. Same posture #738/#743/#763 already took.
- **A ticket's own spec can correctly predict a review's two sharpest hazards, and the review's job is
  then to confirm neither one was triggered, not to discover new ones.** Both traps flagged in the
  architecture spec (the `replace_all` inversion, the two-fives collision) were the two things code
  review explicitly checked and reported clean — the spec's hazard analysis and the review's
  verification matched line for line.

## Lessons learned

*(from the PR #768 body, verbatim)*

- A `replace_all` on the obvious grep phrase inverts here. `carries the four render fields onward
  (dropping \`conversation_id\`)` matches exactly one line in `inboundMessage.ts` — `:224`, which is
  #767's `tool-result` claim and still *true* until #766 lands. This ticket's own copy wraps across
  `:218-219` and never matches on one line. The natural single-command edit would have written a
  falsehood into another ticket's deliverable, missed the target entirely, and passed `tsc` and the
  whole suite on one plausible-looking match.
- The repaired sentence contains the word "five" twice, counting two different sets, and both are
  true. "Five render fields" is `turn_id`/`tool_use_id`/`name`/`input_summary`/`input` — excluding the
  id; "(five strings, no enum)" is the fail-closed decode's required strings — including the id,
  excluding the non-string `input`. Verified against `parseToolUsePayload:974-985`. Splitting the
  semicolon into two sentences keeps the coincidence from reading as a copy-paste error; neither number
  changed.
- The renderer store files spell it capital-`F` `Field-for-field`. A case-sensitive sweep of the two
  files returns hits only in `timelineBridge.ts` and reads as if `threadTimeline.ts` were uninvolved —
  silently losing a whole file of the census.
