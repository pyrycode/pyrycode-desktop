# #766 — Carry the conversation id on the `toolResult` IPC arm

Code child of the #754 split (arm, `size:s`; sibling #767 owns the comment-only citation sweep in the
three files this ticket deliberately does not open). Shipped as PR #769 (`56dd1c9` spec commit +
`4ce4bf3` feature commit), code review **FAIL** (1 MUST FIX, 2 NIT) → rework `9842087` → re-review
**PASS** (0 MUST FIX, 0 SHOULD FIX, 1 NIT). Size S, `security-sensitive`, architect self-security-review
PASS. 8 files touched across both commits, no new files.

## Summary

`ToolResultPayload` has always carried `conversation_id` on the wire, and `parseToolResultPayload`
(`inboundMessage.ts:996-1006`) has always `requireString`d it at `:1000` — but the `tool-result` emit
discarded it, the same single-active-conversation assumption #675's other seven arms already retired.
This is the eighth and **last** arm in that family: `toolResult` was the fourth and final turn-stream
arm (`assistantDelta` #751, `turnEnd` #752, `toolUse` #763 preceded it; the four sub-state arms
`turnState`/`stallDetected`/`apiRetry`/`compacting` went through it earlier still).

**Production change — two files, matching #751/#752/#763's shape:**

- `src/shared/ipc/events.ts:512` — the `toolResult` arm gains `conversationId: string`, required,
  expanding from a single-line union member to a braced one matching `toolUse`'s shape
  (`events.ts:521-528`).
- `src/main/daemonConnection.ts:925` — the `case 'tool-result':` emit's fresh literal gains one line,
  reading the id **bare** from the already-decoded payload: `conversationId:
  inbound.toolResult.conversation_id`. Copied **by name**, never a spread, so a decoder that later grows
  a field cannot smuggle it across IPC.

**No decode change.** `parseToolResultPayload` already required `conversation_id` before this ticket
existed. AC2 was already green, pinned by two shipped tests that needed no edit
(`inboundMessage.test.ts:2796-2801` missing-field loop, `:2803-2813` non-string case). An emit-site
`?? ''` would be unreachable for any input a test can supply, since `parseToolResultPayload:1000` throws
first — the `?? ''` ban is an **inspection** criterion for code review, not a test obligation, per
#752/#763's precedent finding. **Zero new tests** — the developer widened fixtures, retired stale names
and comments, and inverted one guard.

The id **stops at the renderer timeline bridge** exactly as it did for #751/#752/#763:
`translateTimelineEvent`'s `case 'toolResult':` (`timelineBridge.ts:69-80`) rebuilds a fresh
`ThreadEvent.toolResult` by name and is untouched by this diff — `ThreadEvent` carries no conversation
id, and the consumers that route by it are #756. Proved executably: all 38 `timelineBridge.test.ts`
tests pass with the widened fixture, because the exact `toEqual` at `:173-179` (unwidened) would fail if
the id ever leaked across.

**AC4 census — sixteen sites, ten invisible to the compiler, nine of those invisible to the suite too**
(one guard — `daemonConnection.test.ts:3022` — is caught by vitest on a second run, once the fixture
above it stops masking it with an earlier `toEqual` failure). Three neighbouring-arm contrast comments
(`events.ts:292`, `events.ts:515`, `daemonConnection.ts:927` — all "unlike toolResult, which still drops
it"), two field-count claims (`events.ts:507`, `daemonConnection.ts:912-914`), two test names
(`daemonConnection.test.ts:2996`, `timelineBridge.test.ts:164`), one test comment
(`daemonConnection.test.ts:3021`), and one guard that had to **invert**
(`daemonConnection.test.ts:3022`, `not.toContain('conv-1')` → `toContain`).

## Code review — first pass FAIL, one MUST FIX

The first-pass commit (`4ce4bf3`) retired the three "unlike toolResult, which still drops it" contrast
comments with a single universal replacement — "every arm whose frame supplies it now does" — which
`unrecognizedMessage` falsifies: its frame supplies `conversation_id`
(`parseUnrecognizedPayload` requires it) and its arm still drops it, and both of that arm's drop-claims
(`events.ts:422`, `daemonConnection.ts:832`) are correctly on the must-NOT-sweep list, still true. The
over-broad universal would have pointed a future sweeper straight at them, and at `events.ts:292` it also
directly contradicted the very next sentence, which rejects "does the frame have the field" as the
correct test.

Rework (`9842087`) narrowed the replacement to the scope the spec actually supplied: `toolResult` was the
last still-dropping **turn-stream** arm specifically, not the last arm with any drop-claim at all. Both
sites now read "as every turn-stream arm now does". Two NITs were folded into the same commit: the
`tool_result` test name's field count was dropped to match #763's shipped sibling wording (132 → 107
chars, keeping every line under the file's 125-column ceiling), and the `queue-state` comment blocks in
both `events.ts` and `daemonConnection.ts` were re-filled to their original reflow rather than left short
— an under-filled line had split "REPLACEMENT-truth" awkwardly across the wrap.

Re-review: **PASS**, 0 MUST FIX / 0 SHOULD FIX / 1 NIT (non-blocking, unrelated cosmetic).

## Patterns established

- **A retired one-line contrast comment must be narrowed to the scope the spec measured, not
  generalized to the broadest true-sounding replacement.** "Unlike toolResult, which still drops it"
  becoming "every arm whose frame supplies it now does" reads plausible and is false — the correct
  discriminator was always "turn-stream arm", stated two sentences earlier in the same comment block.
  Read the surrounding paragraph's own stated test before writing a replacement clause, not just the one
  line being retired.
- **A code-review MUST FIX on a retired comment is exactly the kind of finding that ships silently
  without an adversarial re-derivation of the claim** — `unrecognizedMessage` was already correctly
  parked on this ticket's own must-NOT-sweep list, but the first-pass developer wrote a universal replacement
  without re-checking it against that same list. The list existed; it just wasn't re-consulted at the
  moment of writing the new sentence.
- **This closes the #675 family.** All eight arms `assistantDelta`/`turnEnd`/`turnState`/`toolUse`/
  `toolResult`/`stallDetected`/`apiRetry`/`compacting` now carry `conversationId`. `rg -i "unlike
  toolResult" src/` returns 0. The only remaining `conversation_id`-drop claims in `src/` belong to
  `unrecognizedMessage`, which genuinely still drops it and is not part of this family.

## Lessons learned

- A universal restatement of a narrowing fact ("as every X now does") is a stronger claim than the
  specific fact it replaces ("unlike Y") and needs its own falsification check against every sibling arm
  that could contradict it — not just against the one arm the sentence used to name.
- Re-filling a retired clause to its pre-change line width is not cosmetic busywork: an under-filled wrap
  can split a load-bearing multi-word term (here, "REPLACEMENT-truth") across a line break in a way that
  degrades readability even though nothing is functionally wrong.
