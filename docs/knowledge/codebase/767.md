## Summary

#766 (`4ce4bf3` + `9842087`) widened the `toolResult` IPC arm with `conversationId`, sweeping its own two
files and their test twins in the same PR — but not these two, which it deliberately left open for this
ticket so its own production diff stayed at two files. Both comments encoded the drop **indirectly**:

- `src/main/transport/inboundMessage.ts:224` — the `tool-result` kind's decode-layer contract paragraph,
  naming the drop directly ("the consumer carries the four render fields onward, dropping
  `conversation_id`"). **Only the parenthetical was false.** The "four render fields" count was and stays
  true — `toolResult`'s render fields (`turn_id`/`tool_use_id`/`is_error`/`result_summary`) never gained a
  fifth the way `toolUse` gained `input` (#642), so unlike #764's twin edit this one does **not** bump the
  count.
- `src/renderer/src/store/timelineBridge.ts:70-71` — the load-bearing one. Asserted the `DaemonEvent` and
  `ThreadEvent` `toolResult` shapes are **field-for-field identical**, using that equivalence to justify
  why `translateTimelineEvent`'s arm is "a filter + fresh copy, not a field remap." A comment asserting
  equivalence with a type that must *not* gain the field encodes the drop as firmly as one naming it, and
  this is exactly the seam where the id must stop — the seam the per-conversation routing slice (#756)
  builds on.

The repair rewrites both to say what the arm now does: Site 1 states the consumer carries the four render
fields **plus `conversation_id`** onward (`#766`), matching #764's word order four lines above it. Site 2
states the `DaemonEvent` carries `conversationId` beside the four render fields, the `ThreadEvent` this
bridge returns does not, so **the id stops here** — the filter-plus-fresh-copy conclusion survives with a
new stated reason, including the *"never a pass-through of the DaemonEvent object"* clause that forecloses
the exact "simplify to a pass-through" edit the comment exists to prevent. Zero executable lines change.

## Patterns established

- **A twin's count fix can be pre-existing repair, not the widening itself, and inheriting it blind ships
  a fresh falsehood.** #764 bumped `toolUse`'s render-field count four→five, but that repaired #642's
  `input` staleness — `toolResult` never had an equivalent field added, so its "four" stays true. The
  vocabulary is pinned at the emit site (`daemonConnection.ts:912-914`: "the five named fields carrying
  the render fields and `conversationId`"), not by counting `DaemonEvent` union members (which gives five
  and invites a false "correction").
- **One sentence can carry two different counts of the same number, and a range quoted for one AC clause
  can bleed into another that must survive untouched.** `inboundMessage.ts:224-225` names "four render
  fields" (the emit, now-false-parenthetical) and "four required strings" (`parseToolResultPayload`'s
  decode, `:996-1006`, wholly true, repeated at `:988-989`). A `replace_all` on "four" — or a mechanical
  count-bump borrowed from the twin's diff — corrupts one or both silently, since neither `tsc` nor the
  suite reads a comment.
- **`replace_all` inverts in both files on the obvious grep phrase, confirmed rather than assumed.**
  `` dropping `conversation_id` `` also matches `inboundMessage.ts:192` (`unrecognized-message`, still
  true — its id drops upstream at `events.ts:422`). The `timelineBridge.ts` phrase fragments reach `:85`
  (`sessionTransition`) and `:123` (`unrecognizedMessage`, near-verbatim the target 53 lines below it, and
  true for the same reason) plus `:50` (#764's just-repaired `toolUse` prose). Each edit used a unique
  anchor instead.
- **A capitalized grep phrase hides from a lowercase sweep.** The renderer store files spell it
  capital-`F` `Field-for-field`; the post-edit verification sweep had to be `-i` or it would silently miss
  the very line just edited — the same invisibility mechanism (§ next bullet) that let a different
  citation go unnoticed for a year.
- **A retired one-line contrast/equivalence comment's replacement must foreclose the specific dangerous
  edit it exists to guard against, not just state a neutral fact.** Deleting Site 2 entirely would have
  scored a clean sweep on every mechanical check; the spec required the replacement to positively assert
  "the id STOPS here" and preserve "never a pass-through of the DaemonEvent object" — the clause that
  blocks a future "simplify this to a pass-through" edit from carrying the id into the reducer silently
  while the (deleted) comment no longer warned against it.

## Lessons learned

*(from the PR #771 body, verbatim)*

- A twin's count fix can be pre-existing repair, not the widening. #764 bumped the `toolUse` count
  four→five, but that repaired #642's `input` staleness — `toolResult` never had it. Inheriting that half
  of the twin's diff would have replaced a retired falsehood with a fresh one, silently: `tsc` and the
  suite have nothing to say about a comment. The count at `:224` is TRUE and survives byte-identical.
- Render field ≠ emitted field, and the vocabulary is pinned at the emit site. Counting the `DaemonEvent`
  `toolResult` union members gives five and invites "correcting" a true four. `daemonConnection.ts:912-914`
  ("the five named fields carrying the render fields and `conversationId`") and `events.ts:507` are what
  settle it.
- `replace_all` inverts in both files, and the case-sensitive sweep loses the target. `` dropping
  `conversation_id` `` also matches `inboundMessage.ts:192` (`unrecognized-message`, TRUE); the
  `timelineBridge.ts` phrase fragments reach `:85`/`:123`, the latter near-verbatim the target 53 lines
  below it and TRUE for the same reason (`events.ts:422`). Separately, the target's capital `F` in
  "Field-for-field" means a lowercase grep misses it — the post-edit sweep must be `-i`.
- The second "four" sits inside the quoted AC range and is wholly true. `:224-225` is one sentence
  carrying two different counts; `:225` is about `parseToolResultPayload`'s decode (4 `requireString` + 1
  `requireBoolean`), not the emit.
