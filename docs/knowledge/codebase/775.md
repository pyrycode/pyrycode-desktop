# #775 — Hold a last-read mark per conversation, keyed by conversation id

Split from #677 (child A; siblings: #776 persist, #777 stamp-on-open, #778 derive, #779 clear-on-unpair).
Shipped as PR #783 (`f7ad516` spec commit + `e9167f4` feature commit), code review **PASS**, zero MUST, one
SHOULD, two NIT. Size S, architect self-security-review PASS; 2 new files, 491 insertions, no existing file
touched.

## Summary

Nothing in the app tracked read state: `ConversationSummary` carries `last_message_ts`/`last_used_at` but
no read cursor, and the daemon has none to give. This ticket ships the in-memory holder for a client-side
last-read mark — `conversationLastReadStore.ts` — and nothing else: no writer, no reader, no clear. See
[conversation last-read store](../features/conversation-last-read-store.md) for the full write-up.

Built to the same shape as its two keyed precedents, [conversation activity
store](../features/conversation-activity-store.md) (#747) and [conversation timeline
holder](../features/conversation-timeline-holder.md) (#755): `zustand/vanilla` DI-factory → singleton →
`useStore` hook → selector-factory, `ReadonlyMap<string, …>` state, copy-on-write, `?? null` two-way read.

The one substantive decision this ticket made that neither precedent had to: **the recorded value's
shape.** The ticket body offered two timestamp-shaped options; the architect ruled both out during spec
writing because no timestamp exists anywhere the renderer can reach (a grep across the whole IPC event
union for a time field returns zero), and a client clock reading can't answer #778's question about a
conversation that isn't open. The mark is instead a **count of timeline items seen** —
`conversationTimelineStore`'s per-conversation `items.length`, append-only per keyed slice since #756.

## Patterns established

- **A numeric-valued keyed store has two traps its object-holding siblings structurally cannot have, and
  both compile clean.** `s.marks.get(id) || null` in the selector collapses a real mark of `0` into the
  same reading a never-read conversation produces — the `??`-vs-`||` trap. A falsy-shaped write guard
  (`!s.marks.get(id)`) drops a legitimate first record of `0` — the numeric analogue of
  `conversationActivityStore.ts:148-152`'s first-write-of-`false` property, sharper here because `0` is not
  an edge case but what opening an empty conversation stamps. Both got a dedicated, mutation-checked test.
- **The copy-on-write identity proof the object-holding precedents use is degenerate for a primitive.**
  `backgroundTaskRosterStore.ts:415-417`'s "an untouched entry is `Object.is`-identical" passes however the
  map was built, because `Object.is(5, 5)` holds regardless. The assertion that actually catches an
  in-place `Map.set` is that the *previously held map*, captured before the write, still reads as it did —
  worth reusing for any future keyed store holding a primitive rather than an object.
- **A monotonic guard is not replacement, and replacement is the correct contract here.** `Math.max(held,
  incoming)` was considered and rejected: a conversation whose timeline slice gets evicted and later
  recreated restarts its `items.length` near zero, and a legitimate lower mark must stay recordable for
  that case, or #778 loses the ability to recover.
- **A keyed store can decline the bound its nearer precedent set, when the per-entry cost argument doesn't
  transfer.** `conversationTimelineStore` (#755) caps at ten slices because an entry there is a whole
  thread of assistant text. An entry here is one number plus one bounded id string — cheaper than
  `conversationActivityStore`'s four booleans, which already declines a cap — so this store copies only the
  *other* half of #755's two-part justification (no periodic floor exists to bound growth for free) and
  ships genuinely unbounded, deferring a ceiling to #776 once persistence makes growth survive a restart.

## Code review — PR #783, PASS, 0 MUST / 1 SHOULD / 2 NIT

- Independently drove all four documented traps by execution rather than trusting the header: on a
  `Record`, `'__proto__'`/`'constructor'` read back non-nullish prototype values (so `?? null` never fires)
  and `rec['__proto__'] = 42` is silently dropped, confirming the `Map`-vs-`Record` claim; confirmed `''` is
  genuinely not diagnostic in the hostile-key set (reads `undefined` either way).
- Independently confirmed the append-only claim the value shape rests on: `type: 'reset'` has three
  production dispatch sites (`activateConversation.ts:75`, `exitActiveConversation.ts:102`,
  `clearPairingScopedState.ts:98`), all wired to the **flat** `timelineStore`, none reaching `dispatchFor`
  (the keyed store's one production call site).
- Cite-audited 25+ line-number anchors in the module header against their targets — a documented history
  of drift in this family (#757) made a skim insufficient. All correct.
- **[SHOULD FIX]** The header's second falsy-guard example, `(s.marks.get(id) ?? -1) === itemsSeen`, does
  not actually reproduce the failure it is named for: on an absent key this evaluates `-1 === 0` (false),
  so the create path runs and the record is written. Verified by execution. The shape that actually drops a
  first `0` is `(s.marks.get(id) ?? 0) === itemsSeen`, where `0 === 0` short-circuits the create. The
  shipped `===`-against-raw-`get` guard is correct; only the illustrative wrong-example text is wrong.
  Flagged as worth fixing before #776 branches off these notes, but under the failure threshold — merged
  unfixed. **Carry this correction into #776/#777/#778's specs rather than re-copying the `-1` form.**
- **[NIT]** The append-only header cite (`:41-42`) names only one of the three `reset` dispatch sites
  (`activateConversation.ts:75`), reading as a complete census in a header that is exhaustive everywhere
  else.
- **[NIT]** Ragged comment wrap at `:20-22`.
- Naming settled: `recordLastRead` over `markLastRead`, closing the spec's one open question — confirmed
  against `conversationTimelineStore.ts:153`'s existing, differently-shaped `markViewed`.

## Lessons learned

*(from the PR #783 body, condensed; see the code review section above for the one correction it needed)*

- A numeric entry adds two traps the object-holding keyed precedents structurally cannot have: the
  `??`-vs-`||` selector collapse and a falsy-shaped write guard, both invisible to `tsc` and both live
  defects here (`0` is producible — an empty conversation's first read stamps it).
- The identity assertion the object-holding precedents use to prove copy-on-write (`Object.is` on an
  untouched entry) is degenerate for a primitive; assert on the captured pre-write map instead.
- This repo has no `.prettierrc` and no lint/format script — `npx prettier --check` warns even on the
  shipped precedent files, so `--write` would reformat away from the prevailing hand-matched style
  (single quotes, no semicolons, ~110 columns), not toward it.
- `''` is not a diagnostic hostile key on a `Record` (`rec['']` reads `undefined` either way, same as on a
  `Map`) — it stays in the AC4 set because it's still a legal `Map` key and an illegal conversation id, just
  not the assertion that catches a `Record` swap.
