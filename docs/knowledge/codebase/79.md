# #79 — Launch-time signal: does a stored pairing exist?

**Shipped:** 2026-07-07 · **Size:** S · **Scope:** shared + background + preload + composition root (`src/shared/ipc/`, `src/main/`, `src/preload/`) · additive to the #54 pairing IPC family, **zero consumer cascade** (`PyryApi` auto-flows the new preload method; `index.d.ts` untouched) · **no new dependency**.
**Spec:** `docs/specs/architecture/79-launch-time-pairing-status-signal.md` · **PR:** [#81](https://github.com/pyrycode/pyrycode-desktop/pull/81) · review: **PASS** (architect security-review pass in-spec, verdict PASS; code-review adversarial + security-goggles pass over the diff — **no MUST/SHOULD/NIT**). Split from #78; the data-path half of the app-shell composition — the renderer routing that consumes it is **#80** (blocked on this slice).

Exposes the paired-server store's existence fact to the renderer as a clean, **connect-independent, value-free** answer over a new request/response IPC channel (`pyry:pairing-status`, invoke/handle), so the app shell can choose a screen before first paint (#80) **without inferring pairing state from a late, error-shaped connection event** (`daemonConnection`'s `failed{ code: 'not-paired' }`). The main-side handler is a stateless sibling of [#54's `pairingHandler`](54.md) over the already-constructed `pairedServerStore`; the response is the three-outcome `PairingStatus` enum. See the [pairing-status signal feature doc](../features/pairing-status-signal.md) for the full contract, layers, determinism model, and data flow.

## Patterns established

- **The stateless, body-free counterpart to the #54 request/response channel.** #54 established the invoke/handle three-layer shape for a pairing round-trip that *holds state* (`pendingConfirm`) and *carries an untrusted body* (the paste, guarded by `isPairingRequest`). #79 is the same shape with **both** of those stripped: the query carries **no request body**, so there is no `isXxxRequest` guard and no untrusted-input surface at the boundary; and the handler holds **no state**, so each invoke is an independent `store.load()`. When a renderer→main query is a pure read with no argument, this is the template — a constant + a value-free response union in `src/shared/ipc/` (the `events.ts` "no runtime logic, no companion runtime test" precedent), a stateless injected-target handler, and a zero-argument preload wrapper.
- **Value-free-by-construction, reused verbatim.** As in [#54](54.md), the reply invariant is enforced by the *type*: no `PairingStatus` member declares a field beyond the `status` discriminant, so the handler cannot serialize the token / `server_static_pubkey` / relay / record back — a developer *can't* leak one. The runtime backstop test (secret-shaped record → `JSON.stringify(paired-response)` contains none of the secrets) locks it in. Model the response union so no arm can carry a secret; the type is the enforcement.
- **Classify-don't-forward, and log-free by construction.** The single type-blind `catch` maps every throw to `{ status: 'error' }` and **drops** the caught object (its message could echo a filesystem path from a decrypt failure or record bytes from a malformed blob). No `console.*` anywhere in the module — matching the `secureStore` / `pairedServerStore` / `daemonConnection` posture. Unlike `pairingHandler` (one fixed value-free log on a malformed request), a body-free read has no untrusted-request path and thus no reason to log at all. Code-review rejects any `console.*` here.
- **`invoke` (pulled), not a daemon event (pushed), when the answer must beat a race.** A startup event would (a) grow the `DaemonEvent` union — forbidden by the additive-only constraint — and (b) *race* `connecting` / `failed`, which is the exact late-signal anti-pattern this slice removes. A pulled `invoke` resolves from a single cache-free `store.load()` independent of the connect sequence. When a signal must be **deterministically available before** the renderer acts, pull it; don't push it.
- **A new channel per concern, not a new member on an existing channel.** The status query became `pyry:pairing-status`, not a third `PairingRequest` member, because the pairing channel holds submit→confirm state and this is a stateless read. Keeping them separate leaves `PairingRequest` / `isPairingRequest` / `pairingHandler` untouched — same "separate channels per concern" split as `pyry:command` vs. `pyry:daemon-event`.
- **Reuse the composition-root store, register once, tear down on `will-quit`.** The handler is wired with the *already-constructed* `pairedServerStore` (no second store), synchronously in `whenReady` before `createWindow()` so it is present for the renderer's first invoke, with `will-quit` teardown symmetric to `unregisterPairing`. The `ipcMain`-satisfies-the-structural-target trick (`{ handle, removeHandler }`) carries over from #54 unchanged.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section, plus the code-review notes.*

- **The three-outcome distinction turns on one invariant that is easy to get subtly wrong: `null` from `load()` is the *only* not-paired path; *every* throw is `error`.** Both mandated error sub-cases — `MalformedPairedServerRecordError` (a decoded-but-malformed blob) and a **propagated decrypt failure** (tamper / keychain rotation, which is *not* a `MalformedPairedServerRecordError` — it propagates straight out of `secureStore.get`) — surface as a throw out of `load()`, so a single **type-blind** `catch` covers both. The handler must **not** branch on the error type. [ADR 0005](../decisions/0005-secret-at-rest-safestorage-fail-closed.md)'s "never mask an unreadable record as never-paired" is the reason the `error` arm exists and must stay distinct from `not-paired`.
- **The propagated-decrypt test asserts a *plain* `Error` on purpose.** Throwing a generic `Error` (not a `MalformedPairedServerRecordError`) from the fake `load()` and still expecting `{ status: 'error' }` is what *proves* the handler doesn't branch on the error type — a test that used the domain error for both cases would pass even if someone wrongly added `if (err instanceof MalformedPairedServerRecordError)`. The two error tests also assert `.resolves` (never `.rejects`): `handle` must produce a value, never propagate.

No React re-render / effect-cleanup / dependency-version surprises to record — a main-process handler + shared contract + preload bridge with no React, no timers, no listeners beyond the single `will-quit` handler, no new dependency. The listener awaits exactly once (`load()`) and returns; no read-then-mutate across the await.

## Deferred (carried forward)

- **Renderer consumption / screen routing — #80.** The consumer that calls `window.pyry.pairingStatus()` and routes on the answer (pairing screen vs. conversation shell, and what to show on `error`) is the next slice, blocked on this one.
- **`error`-outcome recovery policy — #43/#44.** ADR 0005 defers "re-pair prompt vs. hard error" to the recovery slices. This slice only guarantees `error` is *distinguishable* from `not-paired`; if those slices ever need to distinguish the two error sub-cases (malformed vs. undecryptable), the `PairingStatus` union extends additively — no reshape.
- **`will-quit` teardown is hygiene, not functional.** Single registration for the app lifetime (`ipcMain.handle` allows one handler per channel); process exit reclaims everything. Kept for symmetry with #54's teardown note.
