# #80 — App shell: pairing screen until paired, then conversation

**Shipped:** 2026-07-07 · **Size:** S · **Scope:** renderer only (`src/renderer/src/`) · **additive** — `App`'s default-export signature `(): JSX.Element` is unchanged (so `main.tsx` still mounts it untouched) and the new exports (`AppView`, `routeForStatus`, `AppRoute`) are purely additive · **no main-process code**, **no new dependency**.
**Spec:** `docs/specs/architecture/80-app-shell-pairing-then-conversation.md` · **PR:** [#84](https://github.com/pyrycode/pyrycode-desktop/pull/84) · review: **PASS** (QA gates green — `npm test` 357 pass / 2 pre-existing skips, `npm run build` clean; code-review **PASS — no blocking findings**, "clean, well-scoped, spec-faithful slice"). Split from #78; **blocked on [#79](79.md)** (the launch signal it consumes).

The **routing half** of the app-shell composition #79 set up the data-path for. Turns `App` from a hard `<ConversationScreen />` render into a **router container**: it consumes #79's launch-time `window.pyry.pairingStatus()` signal to pick the initial screen, and the [pairing screen](../features/pairing-input-screen.md)'s existing `onPaired` seam ([#55](55.md)) to advance to the conversation screen in-session — with no restart. This is the app-shell assembly the end-to-end milestone (#13) waits on: the send / render / pair slices were all green, but nothing assembled the built screens into a runnable whole. See the [app-shell feature doc](../features/app-shell.md) for the full router model, the pending-phase / fail-safe design, and the data flow.

Three parts, mirroring the codebase's established split — pure logic in a tiny testable module (`composerSend.ts`), a pure props-in/markup-out view (`PairingView`, `MessageThread`), a thin untested async container (`PairingScreen`, `useDaemonEventBridge`):

1. **`routeForStatus`** (pure module) — the fail-safe status→screen decision.
2. **`AppView`** (pure exported view) — a hookless `switch (route)` over the three members: `pending`→`null`, `pairing`→`<PairingScreen onPaired={…} />`, `conversation`→`<ConversationScreen />`, `default`→`assertNever`.
3. **`App`** (container) — owns `useState<AppRoute>('pending')`, a one-shot `[]`-deps launch effect that calls `pairingStatus()` and sets the route (`.then(routeForStatus)` / `.catch(() => 'pairing')`, guarded by an `active` cancellation flag), and returns `<AppView route onPaired={() => setRoute('conversation')} />`. `useDaemonEventBridge()` stays the unconditional first line — unchanged.

## Patterns established

- **Fail-safe-by-construction routing as a total function (AC2 / [ADR 0005](../decisions/0005-secret-at-rest-safestorage-fail-closed.md)).** The security-load-bearing invariant — *the conversation screen is reachable **only** on a genuine `paired`* — is enforced as the shape of `routeForStatus`, not as a runtime check. The **ternary is deliberate over a per-arm `switch`**: `paired ? conversation : pairing` structurally guarantees that anything not exactly `paired` — `not-paired`, `error`, **or any future `PairingStatus` member** — fails safe to the pairing screen. `error` is never collapsed into `not-paired`; here they simply share the only re-pair surface. This is the routing analog of #79's "value-free by construction" — the safe outcome is the default the type forces, not a branch a developer must remember.
- **Two exhaustiveness strategies, chosen by intent.** `routeForStatus` uses the fail-safe *ternary* (open to future `PairingStatus` members, all routed safe). `AppView` uses a `switch` + **`assertNever` default** (closed over the 3-member `AppRoute` we own — a new route without a case is a *compile error*, the same guard as `reduceSession` / `toMessageViewModel`). The distinction: fail-safe-default for an *external, possibly-growing* union where safety must not depend on updating a map; compile-error-default for an *internal, fully-owned* union where a missing case is a bug to catch at build time.
- **Route state is `useState`, not the store ([ADR 0006](../decisions/0006-ephemeral-screen-state-usereducer-not-store.md)).** Screen selection is ephemeral, shell-local UI state — the same category as the composer's `text`. No store slice; the [session store](../features/session-store.md) stays the single source of *conversation* state, untouched. `pending` → `pairing`/`conversation` is a single `useState<AppRoute>`.
- **App-lifetime subscription stays app-level, above the route branch.** `useDaemonEventBridge()` is called unconditionally on every render, **not** moved inside the conversation branch. One stable listener for the whole session with no subscribe/unsubscribe churn as the route flips pairing→conversation — and, crucially, already mounted before `onPaired` fires, so when connect-on-pair ([#82](https://github.com/pyrycode/pyrycode-desktop/issues/82)) later starts the connection at pair time, no early daemon event can be missed in the gap between the pair completing and the conversation screen mounting.
- **Correct wiring can be the *absence* of a handler (AC5).** `onCancel` is deliberately **not** passed to `PairingScreen`. When unpaired the pairing screen is the app root — there is no screen to cancel *back* to. Cancel's correct app-shell behavior is "stay on the pairing screen," which is exactly what happens when `App` does not navigate on cancel (`PairingScreen`'s internal reducer resets itself to `editing`; the route stays `pairing`). Wiring an `onCancel` that navigated anywhere would risk exposing the conversation screen before pairing. Documented in the code, not accidental.
- **The pending phase renders `null` for a neutral first paint (AC3).** No splash component, no loading token — while `pairingStatus()` is unresolved the route is `pending` and `AppView` returns `null`. `:root { color-scheme: dark }` (`tokens.css:13`) with no `body`/`#root` background paints the UA's dark canvas until a screen mounts, so first paint is dark → the correct screen, never the eventually-wrong screen even briefly. The single local `store.load()` over IPC makes `pending` a sub-frame sliver in practice.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section, plus the code-review notes.*

- **The async launch effect and `onPaired`→`setRoute` are untested React glue by design.** `renderToStaticMarkup` (node vitest, no DOM harness) never runs effects, so this harness *cannot* drive the effect resolving or a click firing `onPaired` — an integration assertion is not possible here. The coverage is carried by the pure seams the container is composed from: `routeForStatus` (tested for all three outcomes incl. `error`→pairing) and `AppView` (tested per-route). AC1/AC4 are then guaranteed by the trivial composition `AppView(route, onPaired=…setRoute('conversation'))` over the tested mapping; AC5 by the deliberate absence of a navigating `onCancel`. This is the same precedented gap as `useDaemonEventBridge` / `PairingScreen`'s IPC wiring — leave the thin async glue to a smoke test, put the assertions on the pure choke points.
- **No ordering hazard between the two `setRoute`s, so no functional-update guard is needed.** `onPaired` can only fire *after* the pairing screen is mounted, which only happens *after* the launch query has already resolved to a non-paired route. So the launch effect's `setRoute` has always run to completion before `onPaired`'s `setRoute('conversation')` is reachable. The `active` cancellation flag exists **solely** for StrictMode double-mount hygiene (dev mounts→unmounts→remounts; the first run's promise is cancelled so only the second resolution applies) — *not* to defend this ordering. Each `pairingStatus()` call is an idempotent local read, so a duplicate in-flight call is benign regardless.
- **Testing a store-bound container server-side needs a store reset, but no window stub; testing the pairing view needs a window stub, but no store.** `AppView`'s `conversation` case renders the store-bound `ConversationScreen`, which server-renders fine but shows the store's state — reset it in `beforeEach` (`sessionStore.setState({ status: { type: 'disconnected' }, messages: [] })`). The `pairing` case renders `PairingScreen`, which dereferences `window.pyry` **at render** (`target = bridge ?? window.pyry`); the node env has no `window`, so stub a minimal `globalThis.window = { pyry: {} }` in `beforeEach` and delete it in `afterEach` (an empty `pyry` suffices — no method is called until interaction, and the render never drives interaction). The `App` container smoke needs *neither*: under server rendering effects never run, so the route stays `pending` → `AppView` renders `null` and `useDaemonEventBridge`'s effect never touches `window`.

## Deferred (carried forward)

- **Error-recovery UI for the `error` outcome — [#43](43.md)/[#44](44.md).** This slice makes `error` and `not-paired` visually identical (both land on the re-pair surface, per ADR 0005); a richer "your pairing is unreadable" recovery prompt is out of scope and may extend this **additively** (a third `AppView`-level state or a prop on the pairing screen) without reshaping the router.
- **Connect-after-pair choreography — #34/[#82](https://github.com/pyrycode/pyrycode-desktop/issues/82).** Navigation on `onPaired` is independent of the main-process connect sequence: landing on the conversation screen does not require the socket to be up, because the [composer is already gated on connection status](../features/composer-send.md) ([#31](31.md)). When #82 starts the connection at pair time, the app-level daemon bridge is already mounted to catch its events.
- **A perceptible-flash fallback for the pending phase.** Spec's open question: if in-app testing ever reveals a flash, a `<div className="app-pending" />` with a surface background is an acceptable additive follow-up. Not needed for AC3; default stays `null`.
