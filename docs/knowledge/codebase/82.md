# #82 — Connect immediately after a fresh pairing (connect-on-pair)

**Shipped:** 2026-07-07 · **Size:** S · **Labels:** `enhancement`, `security-sensitive` · **Scope:** background-process lifecycle wiring only — `src/main/daemonConnection.ts` (re-arm), `src/main/pairingHandler.ts` (trigger), `src/main/index.ts` (rewire); **no renderer change**, **no new dependency**, **no wire-type drift**.
**Spec:** `docs/specs/architecture/82-connect-on-pair.md` · **PR:** [#85](https://github.com/pyrycode/pyrycode-desktop/pull/85). Split from [#34](https://github.com/pyrycode/pyrycode-desktop/issues/34); sibling [#83](https://github.com/pyrycode/pyrycode-desktop/issues/83) (reload-per-dial for *automatic* supervisor reconnects) is **blocked-by** this and out of scope here.

Wires the pairing-confirm success signal to the [daemon connection](../features/daemon-connection.md) so a pairing made **during a running session** dials the daemon with no manual step. Before this, `start()` was once-only (`if (started || stopped) return`) and fired only on `did-finish-load` ([#62](62.md)): a client that *launched* already-paired connected, but a client that *paired mid-session* persisted the record yet never connected until the next launch — the operator had to restart. Mirrors mobile #489. **Not UI-visible** — the renderer already renders the resulting `connecting`→`connected`/`failed` daemon events ([#19](19.md)); this is main-process wiring only (AC2).

## Design in one paragraph

Two seams, one composition-root rewire. **(1) Re-arm** — `reconnect()` re-arms the once-only lifecycle by copying the driver's own [`generation`-counter idiom](../features/noise-relay-driver.md) (`noiseRelayDriver.ts:100-118`) **one layer up**: a single monotonic counter, bumped in `dial()` before the old driver is stopped, plus a per-dial `onEvent` wrapper that early-returns when `gen !== generation`. **(2) Trigger** — `pairingHandler` fires `onPaired?.()` only on the confirm-success path. **(3) Rewire** — the composition root wires `onPaired: () => connection.reconnect()`, which required moving the pairing handler registration below the daemon-connection construction. `bootstrap` already sources the record fresh at dial time (`await pairedServer.load()` runs when the connect *begins*), so the re-arm alone makes the triggered dial pick up the just-persisted record (AC3) — **no record-reload plumbing here** (that's [#83](https://github.com/pyrycode/pyrycode-desktop/issues/83)).

## Patterns established

- **Mirror the driver's `generation` fence one layer up.** The transport [driver](../features/noise-relay-driver.md) already uses a monotonic `generation` counter + a `teardownConnection` to fence its async `createSession` against superseded events; `daemonConnection` now copies that exact idiom to fence a superseded **driver** — including the `terminal{1000,'stopped'}` a driver emits synchronously when `dial()` stops it. The reusable shape: bump the counter **before** the tear-down, capture `gen` in a per-dial closure, and drop any event/continuation whose `gen !== generation`. The same fence resolves all three reconnect races (superseded-driver terminal, a reconnect superseding an in-flight `bootstrap` mid-`await`, rapid double-reconnect) with one counter.
- **`stopped` and `generation` are two orthogonal fences that coexist.** `stopped` fences **permanent** teardown (app quit — the terminal-suppression [#62](62.md) added); `generation` fences **reconnect supersession**. `stop()` deliberately does **not** bump `generation`, so the pre-`createDriver` guard must check **both** (`if (stopped || gen !== generation) return`) and the `catch` gates on `gen === generation` while `onDriverEvent` still gates the app-quit terminal on `stopped`. One flag would not have sufficed: a stopped connection must stay stopped even as generations advance.
- **Extract the shared fresh-connect path (`dial()`), keep the public wrappers thin.** `start()` (once-only guard) and `reconnect()` (no-op-after-stop guard) both funnel through one private `dial()`. The `connecting` emit and `void bootstrap()` moved *into* `dial()` with zero behaviour change on first start — the classic "make the second caller by extracting the first caller's body" refactor, done without touching the first caller's observable behaviour.
- **A must-not-throw in-process callback as the lifecycle trigger.** `onPaired` mirrors the `onEvent`/sink discipline already in `main`: a trusted, argument-free, must-not-throw callback. `reconnect()` satisfies it structurally — it bumps a counter, calls the guarded `driver?.stop()`, and emits into a sink that itself must not throw — so it cannot corrupt the confirm response. AC4 (no dial on a failed persist) and AC5 (no secret crosses) are **structural**: the callback fires only after `await confirm()` resolves, and it carries no arguments, so the dial re-sources the record from the trusted secure store, never from anything the renderer supplied.
- **Fire-and-forget composition-root reorder is safe within one `whenReady` tick.** Moving `registerPairingHandler` below `createDaemonConnection` is safe because the whole `whenReady` callback runs to completion in one synchronous tick while `createWindow()` merely *starts* the async document load; an operator-driven pairing invoke (paste + click) arrives many ticks later, after first paint — well after the handler is registered.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **The old driver's synchronous `terminal{1000,'stopped'}` on a reconnect must be fenced by a generation counter bumped *before* `driver?.stop()`, or it surfaces a spurious `failed` between the new `connecting` and `connected`.** This is the single most important thing the fence buys: `dial()` does `++generation` first, so when it then calls the old `driver.stop()` (which synchronously emits its terminal), that terminal carries the *old* gen and the per-dial `onEvent` wrapper drops it. Without the pre-stop bump, the terminal would reach `onDriverEvent` and emit `failed('connection-closed')` mid-reconnect. This mirrors the driver's own generation idiom (`noiseRelayDriver.ts`) one layer up — `stopped` and `generation` coexist precisely because `stop()` does not bump `generation`.
- **Moving `registerPairingHandler` below `createDaemonConnection` (to pass `onPaired`) is safe.** The whole `whenReady` callback runs to completion in one synchronous tick, while an operator-driven pairing invoke arrives many ticks later, after first paint — so the handler is up before any pairing invoke can land. The registration reorder introduces no window where a pairing invoke could hit an unregistered channel.

## Deferred / carried forward

- **Reload-per-dial for *automatic* supervisor reconnects → [#83](https://github.com/pyrycode/pyrycode-desktop/issues/83)** (blocked-by this). This ticket's `reconnect()` re-sources the record on an **explicit** re-arm; the supervisor's in-session transient auto-reconnect still reuses the config snapshotted at construction (the record is snapshotted at 3 layers — `daemonConnection`/driver/supervisor — so #83 is a real refactor). Distinct concerns: `reconnect()` **replaces the driver entirely**; the supervisor auto-reconnect re-dials the *same* driver.
- **Reconnect rate-limiting / relay-side abuse handling → [#83](https://github.com/pyrycode/pyrycode-desktop/issues/83) + the relay.** A compromised renderer looping `submit`→`confirm` churns one dial per real persist (a local socket teardown/redial, no secret leak, no privilege escalation — process isolation per [ADR 0002](../decisions/0002-remote-head-over-relay-shared-wire.md) still contains it). Human-paced dial-per-pairing needs no backoff here; the automatic-reconnect discipline is #83's and the relay's.
- **Richer per-drop status choreography → [#34](https://github.com/pyrycode/pyrycode-desktop/issues/34)/[#35](https://github.com/pyrycode/pyrycode-desktop/issues/35).** #34 split into this (explicit re-arm) and #83 (auto-reconnect record-reload); the failed-vs-disconnected / status-sync-on-mount refinements remain with #34/#35.

## Testing

`daemonConnection.test.ts` reuses the fake-driver / spied-sink harness (`build`, `tick`, `reachConnected`, `emitted`) with **no** harness change — a multi-return `load` closure (a queue + counter) covers the fresh-record and not-paired→paired cases. Seven scenarios: `reconnect()` replaces the driver and emits a fresh `connecting`; fences the superseded driver's terminal (no spurious `failed`); sources the record fresh at dial time (RECORD_A→RECORD_B, asserting `drivers[1].config.connection.url`/`X-Pyrycode-Server`, AC3); connects after a not-paired boot (`load` → `null` then RECORD, the primary scenario); is a no-op after `stop()`; restarts envelope numbering at 2 on the fresh session; and never logs / carries no token/key across a reconnect (the [#62](62.md) secret-free sweep extended over a re-dial). `pairingHandler.test.ts` adds the three `onPaired` cases beside the existing confirm tests. `index.ts` has no unit test (composition root) — the `onPaired` wiring and `reconnect()` call are covered by `npm run build` typecheck + the operator smoke test (pair during a running session → watch it connect with no restart).
