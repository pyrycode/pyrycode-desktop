# #83 — Reload the paired-server record on every automatic reconnect (reload-per-dial)

**Shipped:** 2026-07-07 · **Size:** S · **Labels:** `enhancement`, `security-sensitive` · **Scope:** background-process transport only — `src/main/daemonConnection.ts` (construct + inject the provider), `src/main/transport/noiseRelayDriver.ts` (session-material reload), `src/main/transport/relaySupervisor.ts` (connection reload). **No renderer change**, **no new dependency**, **no wire-type drift**.
**Spec:** `docs/specs/architecture/83-reload-paired-record-per-dial.md` · **PR:** [#87](https://github.com/pyrycode/pyrycode-desktop/pull/87). Split from [#34](https://github.com/pyrycode/pyrycode-desktop/issues/34); **blocked-by** and layers onto sibling [#82](82.md) (connect-on-pair, PR #85), which re-sourced the record on the *explicit* dial but deliberately left the *automatic* supervisor reconnect untouched.

Closes the gap #82 left open: the [relay supervisor](../features/relay-supervisor.md)'s **automatic** transient-drop reconnect now re-sources the paired-server record from storage on every re-dial — for **both** the connection headers (relay url + `token`/server) **and** the Noise session material (`server_static_pubkey` + `hello`) — instead of reusing the two construction-time snapshots. So a re-pair mid-session takes effect on the next reconnect, with no stale pre-pairing view surviving in memory. Mirrors mobile #489 (reload-per-dial) and the daemon's reload-at-handshake + fail-closed discipline ([pyrycode #782](https://github.com/pyrycode/pyrycode/issues/782)). **Not UI-visible** — the renderer only observes the resulting typed daemon events ([#19](19.md)).

## The two residual snapshots this closes

#82's `reconnect()` **replaces the whole driver** and re-reads the record at dial time, but the supervisor's *own* automatic re-dial re-uses the **same** driver + supervisor, which each captured their inputs **once, at construction**:

1. **The supervisor** captured `config.connection` (relay url + `X-Pyrycode-Server` / `X-Pyrycode-Token` headers); its transient-drop re-dial rebuilt the connection from that snapshot.
2. **The driver** captured `config.session` (`staticPrivateKey`, `remoteStaticPublicKey`, `hello`); its `onConnected` rebuilt a fresh Noise session from that snapshot on every `connected`.

Neither path returned through `daemonConnection.dial()`, so neither re-read the record. This ticket threads a **per-dial config provider** through both layers so each is re-sourced from storage on every automatic reconnect.

## Design in one paragraph

One idea: replace the two construction-time **snapshots** with an injected **provider function** `loadDialConfig` that loads the record and derives both halves fresh. It is constructed in `daemonConnection` (which owns the `pairedServer` store) and threaded down; the transport layers stay **store-agnostic and IPC-free** — they receive a plain async function, never the store. The provider is used **only for automatic re-dials**; the *first* dial keeps the config `bootstrap` already loaded (no reason to reload microseconds after loading it, and #82's first-dial not-paired/connect-failed messaging stays put). This makes every change additive. The load-bearing subtlety: **one `load()` per re-dial feeds both halves** — the driver's `resolveConnection` gives the supervisor the `connection` and stashes the same record's `session` as `pendingSession` for the next `onConnected` — so a re-pair mid-dial can never split the headers from the key.

## Patterns established

- **A provider function, not the store, crosses the transport boundary.** The paired-server store lives *above* transport (in `daemonConnection`, the connection consumer). Threading a plain `() => Promise<DialConfig | null>` down keeps the driver and supervisor exactly as store-agnostic and IPC-free as before — they never learn there is a store, a keychain, or a record. This is the reusable shape for "re-source X per operation" without leaking X's owner into the layer that consumes it.
- **One `load()` feeds both halves of a dial.** The naïve version would have the supervisor reload its connection and the driver *separately* reload its session — two `load()`s that could straddle a mid-dial re-pair and dial relay-A's URL with server-B's key. Instead the driver's `resolveConnection` is the **single** load site: it returns the connection to the supervisor and stashes the session for the next `onConnected` from the *same* record snapshot. Whenever two derived values must come from one source-of-truth read, resolve them at one site and hand each consumer its half.
- **Fail-closed is the whole risk surface of making `dial()` async.** Once the re-dial `await`s a keychain read, a malformed/undecryptable record or keychain failure makes `loadDialConfig` **throw**. If uncaught it escapes as an *unhandled rejection at the supervisor's `await`* — a crash out of the transport (AC3 violation) that could echo a key/token in the reject. The mandatory `resolveConnection` catch (drop the caught object, return `null`, null `pendingSession`) makes a bad record on an automatic reconnect fail closed **identically** to the no-record case. This is the client analog of the daemon's reload-at-handshake + fail-closed ([pyrycode #782](https://github.com/pyrycode/pyrycode/issues/782)).
- **A synthetic, never-on-the-wire close code carries a client-side terminal reason.** `NO_PAIRED_RECORD_CLOSE_CODE = 4000` (WebSocket private-use range) is minted client-side so a reconnect-finds-no-record fail-closed rides the *existing* `terminal{code,reason}` event → driver `onTerminal` → `daemonConnection` `failed('connection-closed')`, with **no new `DaemonEvent` code**. Reuse the existing terminal channel with a named, documented sentinel instead of adding a state-machine branch.
- **`firstDial` / `firstConnect` are single-writer "skip the reload on the first pass" gates.** Both are module-locals flipped once, never reset, with no cross-`await` check-then-act. They encode "the consumer already loaded the record for the first dial; only *subsequent* automatic dials need the provider" — the same shape in both the supervisor (connection) and the driver (session).
- **The async re-dial is fenced by a single post-`await` `stopped` re-check.** During a backoff gap there is no live connection, so `stop()` is the *only* event that can race the reload; its `emitTerminal` sets `stopped` and clears timers, and the one post-`await` check aborts the dial. No new timers, listeners, sockets, or `AbortController`s — the reload reuses the existing backoff-timer callback and session lifecycle. The driver's [`generation` counter](../features/noise-relay-driver.md) continues to fence a late/stale session install (unchanged from #50/#82).

## Lessons learned

*Lifted from the PR body's "Lessons learned" section.*

- **One `load()` per automatic re-dial must feed both halves** (supervisor connection + driver session): the driver's `resolveConnection` stashes the reloaded session for the next `onConnected` from the same record snapshot, so a re-pair can't split the headers from the key.
- **Making `dial()` async is the whole risk surface.** The fail-closed discipline (mirroring daemon [pyrycode #782](https://github.com/pyrycode/pyrycode/issues/782)) rests on `resolveConnection` catching a thrown `loadDialConfig` and returning `null`; otherwise the throw escapes as an unhandled rejection at the supervisor's `await`. The async re-dial is fenced by a single post-`await` `stopped` re-check (during a backoff gap `stop()` is the only event that can race it).
- **Collapsing #82's two gen-checks into one is correctness-equivalent.** #82's `bootstrap` checked `gen` after `load()` *and* after building `hello`; folding the load+derive into `loadDialConfig` leaves one post-`loadDialConfig` gen check. A superseded bootstrap does a little extra cheap, side-effect-free derivation, then bails at the same fence before `createDriver` — no event and no driver for a superseded gen. The **not-paired-before-gen-check order is preserved** (gen check first, then `dc === null`) so a superseded bootstrap never emits a spurious `not-paired`.

## Deferred / carried forward

- **A dedicated not-paired message on the reconnect path.** A reconnect that finds no record currently surfaces as `failed('connection-closed', '…(code 4000)')` — a non-connected event (AC3 satisfied) whose message says "closed", not "not paired". The common never-paired-at-launch case still gets the correct "No paired pyrybox" message via `bootstrap`. Routing the synthetic code to a `not-paired` classification in the driver's `onTerminal` is a possible refinement — **deferred as evidence-based**: this path requires clearing the record mid-session *without* a clean `stop()`, which is rare.
- **Supervisor race hardening → [#35](https://github.com/pyrycode/pyrycode-desktop/issues/35).** This ticket fences only the one named race (in-flight reload vs `stop()`/supersede); broader supervisor race hardening stays with #35.
- **Reconnect rate-limiting / relay-side abuse → the relay** (per #82's carry-forward). Cadence, capped jittered backoff, and fatal-close handling are explicitly **unchanged**, so the added per-dial keychain read is bounded by backoff (≤ one per capped interval) — no tight loop, no DoS amplifier.

## Testing

Every change is additive (optional provider fields), so the **entire pre-existing suite across all three files passes unchanged** — asserted explicitly with a no-provider case in each. New scenarios reuse each file's existing harness (no harness change):

- **`relaySupervisor.test.ts`** (+5): the immediate first dial uses `config.connection` (not the provider, built synchronously before any timer/await); an automatic re-dial re-sources the connection via `resolveConnection` (asserts `connections[1]` carries B's url/headers); a `null` reload fails closed with exactly one `terminal{NO_PAIRED_RECORD_CLOSE_CODE,'no-paired-record'}`, no phantom re-dial, no dangling timers; a `stop()` racing an in-flight (deferred) reload does **not** dial and yields only `terminal{1000,'stopped'}`; and the no-provider synchronous re-dial path is pinned. A `tick()` (macrotask flush) drains the async re-dial's `await` deterministically.
- **`noiseRelayDriver.test.ts`** (+5): reloads the session material on reconnect when `loadDialConfig` is set (`SESSION_MATERIAL` on the first connect, `SESSION_B`'s key/`hello` after driving the captured `resolveConnection()` then a second `connected`); first connect uses `config.session` even with a provider present (the `firstConnect` gate); a thrown `loadDialConfig` **resolves `null`, never rejects**, and leaves `pendingSession` null (the mandatory catch); a `connected` with `pendingSession` null emits `error{'session-load-failed'}` (defensive, structurally unreachable); and with no provider every connect uses `config.session` and the supervisor gets no `resolveConnection`.
- **`daemonConnection.test.ts`** (+4): `loadDialConfig` is threaded into the driver as a function; the threaded provider re-sources the record (multi-return `load` RECORD_A→RECORD_B → asserts `DialConfig.connection.url`/`X-Pyrycode-Server`/`X-Pyrycode-Token` are B's and `session.remoteStaticPublicKey` decodes B's key via the **real** codec); the provider resolves `null` when a later load is unpaired; and the secret-free/log-free sweep ([#62](62.md)/[#82](82.md)) extended across a `loadDialConfig()` reload — no `console.*`, and no emitted `DaemonEvent` serialization contains the token, `server_static_pubkey`, or private key (AC4/AC5).

## Security

Ticket carries `security-sensitive`; the architect's security-review verdict is **PASS**. Key points:

- **Same boundary, re-crossed per dial.** The only trust boundary is the existing disk→memory read `pairedServer.load()` (safeStorage-decrypted → `decodeRecord`-validated → `decodeServerKey`'s 32-byte check). This ticket re-crosses that *same* boundary once per automatic reconnect and **re-runs the validators each dial** — a strengthening (the client analog of the daemon's reload-at-handshake). No new boundary; no renderer boundary crossed — `loadDialConfig` is a main→main in-process function; the record never reaches IPC/preload/renderer (**AC5**).
- **The mandatory catch is the load-bearing SHOULD-FIX** the security review flagged and the spec resolved in-line: without it a malformed-record/keychain throw on reconnect escapes as an unhandled rejection echoing a key/token. `pendingSession` is a main-process-only local, never logged or crossed.
- **No `(key, nonce)` reuse.** Every reconnect already drives a **fresh** Noise_IK handshake (v2 has no session resume); the reload only changes *which* static key / `hello` feed that fresh session, and each `onConnected` builds a new session with new ephemerals and reset nonces.
- **Log-free, secret-free.** No new logging; caught errors dropped (classify-don't-forward); the AC4 secret-free test is extended to exercise a reload. The reconnect fail-closed surfaces a static `failed('connection-closed', '…(code 4000)')` — no token/key/transcript in any message.
