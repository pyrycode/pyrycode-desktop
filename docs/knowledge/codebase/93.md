# #93 — E2E: pair through the window against the fake relay + fake daemon, reach the conversation screen

**Shipped:** 2026-07-07 · **Size:** S · **Labels:** `security-sensitive` (it drives a **real** `Noise_IK_25519_ChaChaPoly_BLAKE2s` handshake through the built app's pairing UI and enables two `isPackaged`-gated dev affordances for the run — so the test-only quarantine boundary and token discipline are under review) · **Scope:** one new test-only file `e2e/pair-to-conversation.spec.ts` (~151 LOC). **Zero production-source edits**, no config/package/`playwright.config` change, no new dependency, no wire-type drift. The first UI-level e2e scenario; the terminal consumer of the round-trip harness through the renderer.
**Spec:** `docs/specs/architecture/93-e2e-pair-through-window-to-conversation.md` · **PR:** [#102](https://github.com/pyrycode/pyrycode-desktop/pull/102). Split from [#41](https://github.com/pyrycode/pyrycode-desktop/issues/41) (the full UI round-trip); blocked-by [#97](97.md) (loopback `ws://` relay affordance) + [#99](99.md) (keychain-free secret backend), both merged. The send-and-see-reply half is [#94](https://github.com/pyrycode/pyrycode-desktop/issues/94), which builds on the `connected` state this scenario reaches.

Adds the first e2e scenario that drives the **built** app's main-process transport at a controllable target instead of the live relay + real `pyry` daemon (that live round-trip is the manual runbook, [#13](13.md)). It launches the compiled app through the [#40 harness](../features/e2e-harness.md) shape pointed at the in-process [fake relay forwarder](../features/fake-relay-forwarder.md) ([#90](90.md)) + [fake Noise_IK responder daemon](../features/fake-daemon.md) ([#91](91.md)) — the same doubles the transport-level round-trip test ([#89](89.md)) drives — and enters through the **real pairing screen**: paste → fingerprint → confirm → the app dials and handshakes on its own. Where #89 constructs `createDaemonConnection` directly, this scenario is the UI-level entry point.

This is the automated counterpart of the [live e2e runbook](../features/live-e2e-runbook.md)'s pair→connect half, with the live infra swapped for the in-process fake target: repeatable, no network, run by `npm run e2e`.

## Design in one paragraph

Consume two already-merged, `app.isPackaged`-gated dev affordances (relaxing **no** validation itself) and set only their two env flags for the run: `PYRY_ALLOW_LOOPBACK_RELAY=1` ([#97](97.md)) so `parsePairingPayload` accepts the fake `ws://127.0.0.1:<port>` relay, and `PYRY_TEST_SECRET_BACKEND=1` ([#99](99.md)) so `secureStore.set` does not fail closed in the keychain-less runner. A launched-from-`.` build is `!isPackaged`, so the flags take effect exactly here; a packaged build never reads them. The fake target's coordinates flow into the app through the **pasted payload** (typed into the real textarea), not through env — that is the whole point of driving the pairing UI. The `page` fixture launches with a per-run `mkdtemp` `--user-data-dir` so the launch-time pairing-status query resolves `not-paired` and the router shows the pairing screen (a genuinely unpaired start — **not** the shared, stale-pairing userData `smoke.spec.ts` leans on). It mirrors `electronApp.ts`'s two hardening moves — `args: ['.']` (built entrypoint via `package.json` `main`) and stripping `ELECTRON_RENDERER_URL` (built renderer, not a dev server) — but cannot reuse the shared fixture, which is deliberately scenario-agnostic and can carry neither the extra env nor the isolated dir.

### Evidence model — three DOM observables, three distinct proofs

The single most load-bearing subtlety (spec §"Evidence model"): AC5's wording ("only after a successful handshake does the window route to `.conversation`") is **imprecise against the code** and the test does not rely on it. The route flip to `.conversation` fires from `App.onPaired` — wired to the pairing screen's `confirm-succeeded`, i.e. the confirm IPC **persisting the record**, not the handshake. The handshake is kicked off *separately* by the main-process `onPaired: () => connection.reconnect()` (`index.ts`) and completes a network round-trip later. So the test asserts **all three** observables, each standing in for a different proof:

| Observable | Proves |
|---|---|
| Fingerprint card `[aria-label="Server key fingerprint"]` after `Pair` | `parsePairingPayload` accepted the loopback `ws://` relay → **#97 active** |
| `.conversation` visible after `Confirm` | confirm IPC persisted the record (`secureStore.set` succeeded) → **#99 active** + pair-through-UI works |
| Send button `[aria-label="Send"]` becomes **enabled** | the `connected` daemon event reached the renderer store → **Noise_IK handshake completed** |

## Patterns established

- **Fork the shared e2e fixture *locally* when a scenario needs per-run env or isolation; keep the shared one scenario-agnostic.** The [#40 harness](../features/e2e-harness.md)'s `electronApp.ts` hardcodes `args`/`env`, so it cannot carry this scenario's two dev flags or an isolated `--user-data-dir`. Rather than grow the shared fixture with per-scenario knobs (which would couple every scenario to this one's needs), this spec declares its **own** `test.extend` in-file and re-implements only the two hardening moves it needs (`args: ['.']`, strip `ELECTRON_RENDERER_URL`). The shared primitive stays a scenario-agnostic launch/teardown; per-scenario setup lives in the scenario. This is the reusable shape for the follow-up UI scenarios ([#94](https://github.com/pyrycode/pyrycode-desktop/issues/94) onward).
- **Isolate persisted state with a per-run `mkdtemp` `--user-data-dir`; never share userData between e2e runs.** The Electron `--user-data-dir` switch (passed in `args`, `.` staying the first non-switch arg) overrides `app.getPath('userData')`, so every persisted secret lands in a throwaway dir removed at teardown. This both guarantees a genuinely **unpaired** start (the router shows the pairing screen, the transition-under-test is real) and keeps the developer's real userData — and the shared stale pairing — from contaminating the run. `smoke.spec.ts`'s reliance on the shared userData is precisely the non-hermetic trap this avoids (see [#105](https://github.com/pyrycode/pyrycode-desktop/issues/105)).
- **Drive the app at its real trust boundary — the pasted payload — through the genuine gate; carry the target's coordinates *in the paste*, not in env.** The fake relay + daemon are addressed by the `QrPayload` fields (`relay` = the forwarder's `/v1/client` leg, `server_static_pubkey` = the fake daemon's static), so the test exercises the **real** `parsePairingPayload` end to end (base64url → JSON → 4-field → relay scheme+host → embedded-credentials) and bypasses none of it. The env flags only *enable the affordances*; they never inject the connection. This keeps the gate the single enforcement site even under test.
- **Assert the *transition*, not a static end-state — and pin the handshake to its own DOM signal.** Pre-state asserts `.conversation` has count 0 before pasting, so the later `toBeVisible()` proves a real route flip. And because `.conversation` gates on *persist*, not the handshake, the **Send-enabled** assertion is required, not optional — it is the only DOM-observable handshake proof (`composerAvailability` yields `canSend` only on `status.type === 'connected'`). `.conversation` alone would pass even if the handshake later failed. #89 already proved the handshake is deterministic through this exact assembled stack + fake daemon, so Send-enabled is a reliable, non-flaky signal here.
- **Never ship the deliverable disabled — re-audit skip guards after a `main`-merge lands your blocker on-branch.** (The rework this ticket bounced on; see Lessons.) A `test.fixme` / `describe.skip` justified by an open blocker becomes stale the moment that blocker merges into your branch, and a skipped e2e delivers **zero** executable coverage — the QA gate (`build` + vitest) does not run `e2e/`, so nothing catches it. The fix is to treat "my blocker just merged via the main-merge" as a trigger to re-audit every skip guard the branch carries.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section, plus the rework loop.*

- **e2e is where main-process-runtime-only bugs first surface.** vitest exercises `src/main` under Node's full OpenSSL; only an Electron-launching e2e catches BoringSSL / `app.isPackaged` / native-module divergence. This scenario is what surfaced [#101](101.md) (the Electron/BoringSSL BLAKE2s fingerprint bug — `createHash('blake2s256')` throws "Digest method not supported" under BoringSSL) and [#105](https://github.com/pyrycode/pyrycode-desktop/issues/105) (the stale `smoke.spec.ts` assertion). The corollary: a feature that passes every unit test can still be wedged in the built app, and only an e2e run proves the assembled path.
- **`noise-c.wasm` loads under Playwright's Node via the ArrayBuffer fallback.** The run logs `wasm streaming compile failed … falling back to ArrayBuffer instantiation` — benign: the fake daemon's wasm still loads and the real handshake completes (Send enables). This closes the spec's open question about whether Playwright's TS loader could resolve and run the `src/` wasm imports (`startFakeDaemon` → `noise-c.wasm`) in its Node context. It can.
- **Non-hermetic e2e stays invisible until a sibling scenario runs the whole `e2e/` dir.** `smoke.spec.ts`'s dependence on a pre-seeded shared userData was hidden while it was the only spec; adding a real scenario (and running `npm run e2e`, which runs all specs) exposed it. Filed as [#105](https://github.com/pyrycode/pyrycode-desktop/issues/105) — out of #93's one-file scope, and the #93 spec explicitly says not to reconcile against `smoke.spec.ts`.
- **The rework loop:** the first revision committed the scenario as `test.fixme`, blocked on #101 (the fingerprint step couldn't complete in the built app). Code-review FAILed it: the blocker had **already merged into `feature/93`** via the `main`-merge (`3bf58a8`), so the guard was stale and the deliverable shipped inert. The fix flipped `test.fixme` → `test`, stripped the stale "blocked on #101" title/comment, and verified green in real Electron (the first such run). `--user-data-dir` arg position (`['.', --user-data-dir]`) and the wasm-under-Playwright question — both spec Open Questions — were closed empirically on that run.

## Testing

The deliverable **is** the test — one e2e scenario, run by `npm run e2e` (builds, then `playwright test` over `e2e/`). No new unit tests (no new `src/` production code); layering is unchanged (`npm test` = vitest over `src/` only, `npm run typecheck` doesn't touch `e2e/`, Playwright transpiles the spec + its `src/` imports at run time). Acceptance = the single test passes: an isolated-userData built app, driven through the real pairing UI against the in-process fake target, reaches `.conversation` and enables Send. Every failure surfaces as a Playwright timeout with a locator diagnostic (no silent pass): #97 flag inert → fingerprint card never appears; #99 flag inert → route never flips; handshake fails → Send stays disabled. No failure diagnostic serializes the payload or any secret — the assertions read DOM visibility / enabled-state only (security-review hardening, so a future real-credential variant cannot inherit a leaky pattern).
