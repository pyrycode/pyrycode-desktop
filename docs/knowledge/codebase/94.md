## Design in one paragraph

The scenario is [#93](93.md)'s harness with a single substantive addition — a **reply-driving `buildReply`** — so the fake daemon returns an actual daemon message instead of the default verbatim echo. Everything else (fixtures, teardown ordering, the two dev affordances, the isolated userData, the pairing-through-UI precondition) is copied verbatim: duplication is the established pattern here because [#93](93.md)'s fixtures are deliberately file-local (the [#40](40.md) decision keeps the shared `electronApp.ts` scenario-agnostic), so a new file also means **zero merge overlap** with #93's landed file. Each Playwright spec launches its own app instance (`workers: 1`, serialized), so #94 re-runs the real pairing flow to reach `connected` rather than sharing #93's process — the reuse is the harness *pattern*, not a running app.

### The reply-driving `buildReply` — the load-bearing shape

The fake daemon's reply **must be a `message` envelope carrying `role: 'assistant'`** (mirroring [`daemonConnection.roundtrip.test.ts`](89.md) `:214–221`), **not** a `send_message`:

```ts
const REPLY_TEXT = 'streamed reply from the fake daemon'   // fixed literal, ≠ typed text
const buildReply = (): Uint8Array =>
  encodeEnvelope({
    id: 99, type: 'message', ts: FIXED_TS,
    payload: { conversation_id: 'default', message_id: 'reply-1', role: 'assistant', text: REPLY_TEXT }
  })
```

- **Why not the default echo (the trap the earlier ticket draft mis-stated).** [#91](91.md)'s `startFakeDaemon` default `buildReply` echoes the client's inbound frame verbatim — i.e. re-sends the client's own `send_message`. But `parseInboundMessage` ([`inboundMessage.ts`](../features/inbound-message-decode.md), [#68](68.md)) routes only `message`/`message_chunk` and **ignores `send_message`** (it's the *client→daemon* type). A default-echo reply would therefore render **no daemon bubble**, and AC4 would time out. The `message`/`assistant` envelope is the guard against that regression.
- **`buildReply` ignores its inbound-plaintext argument** — a fixed literal reply keeps the assertion deterministic (same rationale as [#89](89.md)).
- **`message_id: 'reply-1'` is a fixed literal** that cannot collide with the optimistic user echo's `crypto.randomUUID()`, so both survive the store's `appendUnique` as **two distinct bubbles**. `conversation_id` is not filtered by `selectMessages`; `'default'` matches `MILESTONE_CONVERSATION_ID` but any literal renders.
- **`REPLY_TEXT` must differ from the typed text** so the two role-selected assertions are unambiguous by both selector and text.

### Evidence model — two role-selected bubbles, asserted against real product markup

The assertions read the [conversation screen](../features/conversation-shell.md)'s real markup — `.bubble[data-message-role="user"|"daemon"]` — **no test-only hooks added under `src/`**. The `role → data-message-role` mapping is `messageViewModel.ts`'s adapter (`role:'user' → user`, `role:'assistant' → daemon`), which is why an `assistant`-role reply becomes `data-message-role="daemon"`:

| Assertion | Proves | Timing |
|---|---|---|
| `.bubble[data-message-role="user"]` carries the exact typed text (AC3) | the **optimistic echo** — `submitMessage` dispatches `messageSent` (role `user`) **synchronously**, regardless of send outcome | asserted *before* the reply, but with **no** racy "daemon-absent" pairing |
| `.bubble[data-message-role="daemon"]` carries `REPLY_TEXT` (AC4) | the full **send → Noise round-trip → decode → store → render** path | auto-waited (`MESSAGE_TIMEOUT_MS`) through the genuine handshake + round-trip |

## Patterns established

- **Extend a landed e2e scenario by copying its file-local harness into a new spec, not by editing the sibling.** [#93](93.md) established the local-`test.extend` fork (per the [#40](40.md) scenario-agnostic-`electronApp.ts` decision); #94 reuses that *pattern and fixtures* by duplicating the block into a **new** file with exactly one delta (the `daemon` fixture's `buildReply`). A new file means zero merge overlap with #93's landed spec and no widening of #93's surface — the deliberate trade against DRY when the shared primitive must stay scenario-agnostic. This is the reusable shape for further UI scenarios.
- **A reply-driving fake-daemon test must return a `message`/`assistant` envelope, never the default echo.** The [#91](91.md) fake daemon's default `buildReply` re-sends the client's `send_message`, which [`parseInboundMessage`](68.md) drops on the floor — so any scenario that needs a *rendered daemon reply* (not just a settled round-trip) has to pass a `buildReply` returning a `message`-typed envelope. This is the exact `buildReply` shape [#89](89.md) uses at the transport layer; #94 is its UI-level twin. Copy it; don't re-derive the envelope shape.
- **Honor "optimistic before reply" without a race: assert the user bubble as a distinct step, but never pair it with a daemon-absent check.** The reply is a real network round-trip that can land fast; a "user present AND daemon absent" assertion would be flaky. Two sequential role-selected `expect`s (user, then daemon) satisfy the AC's "asserted before the reply" intent unambiguously — the daemon reply is a *separate* role-selected bubble, so the user-bubble assertion holds regardless of reply timing.
- **Send is gated on the handshake, not the route — the wait-for-Send-enabled precondition is load-bearing.** Reaching `.conversation` only proves the pairing record persisted (`confirm-succeeded`); the `connected` daemon event that enables Send arrives a network round-trip later (`composerAvailability` → `canSend` on `status.type === 'connected'`, [composer send](../features/composer-send.md) [#31](31.md)). Typing + sending *before* Send enables hits the `canSend` guard, drops the send, and posts **no** optimistic echo — so the spec waits `toBeEnabled` (the same signal [#93](93.md) already asserts) before typing.

## Lessons learned

*Lifted from the PR body's "Lessons learned" section — both confirm/reinforce prior observations rather than being novel to #94.*

- **`e2e/` type errors surface at neither `npm run typecheck` nor `npm run build`.** The `e2e/` dir is not in either `tsconfig.*.json` `include`, and Playwright transpiles specs without type-checking. A standalone `tsc` pass over `e2e/ + src/main/ + src/shared/` is the only way to type-check specs; it flags a **pre-existing benign** `env = { ...process.env }` → `electron.launch` `string | undefined` mismatch shared by `pair-to-conversation.spec.ts` and `fixtures/electronApp.ts` (not introduced here). (Matches the standing project note on `e2e/` type-checking.)
- **The `noise-c.wasm` "wasm streaming compile failed … falling back to ArrayBuffer instantiation" line during e2e runs is benign** — a Node fallback, present in [#89](89.md)/[#93](93.md) runs too, not a test failure. The fake daemon's wasm still loads and the real handshake completes (Send enables, the round-trip lands).

## Testing

The deliverable **is** the test — one e2e scenario, run by `npm run e2e` (builds, then `playwright test` over `e2e/`). No new unit tests (no new `src/` production code); layering unchanged (`npm test` = vitest over `src/` only, `npm run typecheck` doesn't touch `e2e/`, Playwright transpiles the spec + its `src/` imports at run time). Acceptance = the single test passes end to end: an isolated-userData built app, driven through the real pairing UI against the in-process fake target to `connected`, sends a typed message and sees both the optimistic user bubble and the streamed daemon reply render. Every failure surfaces as a Playwright timeout with a locator diagnostic (no silent pass): handshake never completes → Send stays disabled → the precondition times out; `buildReply` regressed to a `send_message` → `parseInboundMessage` ignores it → the daemon-bubble assertion times out. No failure diagnostic serializes the payload, token, or plaintext — assertions read DOM text / visibility / enabled-state only; the typed + reply texts are non-secret literals. Code review PASS with zero findings.
