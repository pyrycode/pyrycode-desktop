# Question panel — Continue answers the batch (#922)

Split out of [Question panel](conversation-shell-question-panel.md) on 2026-09-02 to keep that document
under the size cap, the same move [Cancel refuses the batch](question-panel-cancel-refusal.md) made for
\#921. Part of the question vertical's render slice; see that document for inline placement and all-question
controls, and [Question-batch model](question-batch-model.md) for the model and bridge
underneath both.

Through #916 the Actions row's trailing button read Next on every question but the last, where it read
Continue and carried no handler at all — the row's last inert control. #919 landed the `question_answer`
wire type, #920 the command that mints its `answer_token` main-side, #921 the local optimistic clear this
slice reuses. This slice gives Continue its handler: it assembles what the operator picked into that
frame's `answers` array, sends it, and keeps itself unavailable until every question in the batch holds a
value and its owning host is connected. See [host availability and reconnect](conversation-shell-question-panel.md#continue-answers-the-batch-922).

**The gate is the operator-facing feature, not a nicety.** Upstream's `answerVerdict`
(`cmd/pyry/modal_resolve_v2.go`) rejects an answer whose entry count is not exactly the parked question
count, and the rejection is total and silent: `AnswerQuestion` returns false having assembled nothing, the
batch's one-shot is not consumed, no `question_dismissed` fires, and the relay handler's false branch is a
debug log with no reply and no error envelope. An under-filled Continue would therefore produce no
round-tripped rejection at all — the button would appear to do nothing until the approval window elapsed.
Gating client-side is what keeps that state unreachable, which is also why #853's rejection-banner
criterion never landed here: there is no daemon-originated rejection on this path to correlate a banner
against, and the reachable local failure (a throwing send bridge) is already #921's.

## `resolveQuestionAnswers` — one function, gate and payload together

**`questionResolution.ts`** (new export, beside `refuseQuestionBatch`):

```ts
export function resolveQuestionAnswers(
  questions: readonly Question[],
  selections: ReadonlyMap<number, QuestionSelection>
): QuestionAnswerEntry[] | null
```

Deciding whether the batch is complete and building what is sent are the same computation: a batch with a
gap has no entry to emit for that question, so the button's availability and the frame's contents cannot
disagree. The container uses this function for the render-time completeness gate and recomputes it
from current picks at response activation. Host availability and current batch ownership are checked
separately before that synchronous send.

Iterates the **questions**, never the selections — a picks map can hold an entry for a position a
shortened re-delivery removed, and one phantom entry would break the daemon's exact-count check on an
otherwise complete answer. Per question, in order: each ticked option's position resolves to
`question.options[position].label` (ascending display order, since `optionIndices` is held that way and
nothing here re-sorts); then, only if the Other row is ticked **and** its trimmed text is non-blank, that
trimmed string is appended last, carried as the value itself and never the word "Other". An empty
`values` for any question means the batch is incomplete: the function returns `null` immediately. `null`
is the only incomplete signal — there is no partial array and no per-question flag.

**A stale option position is skipped, and that path is reachable rather than defensive.**
`reduceQuestionBatches`'s `shown` arm replaces a held batch in place (latest wins), and neither store
clears picks on a re-delivery, so a same-nonce `question_shown` carrying fewer options than before leaves
a pick pointing past the end of the new `options` array. This function runs during render to compute the
gate, so `question.options[position].label` would otherwise throw `undefined.label` out of the render —
on traffic the daemon controls and the reducer explicitly supports. All questions now render together; there is no active-index clamp or stepping state. The out-of-range position contributes no value; if that empties the question, the batch
is incomplete and the operator re-picks against what is on screen. This is also the concurrency finding
the [picks store's own security review](question-batch-model.md) named and handed forward: it is
discharged here, not by a second guard elsewhere.

**Nothing here is validated against the offered labels**, deliberately — claude's contract permits free
text anywhere, so an unlisted value is legal traffic. `question_index` is not range-checked either; it is
generated by iterating the batch this client holds, the bound is the daemon resolver's own. The
single-select shape needs no extra rule: `optionPicked` replaces the pick and clears the tick, and
`otherPicked` clears the options, so a single-select question can never assemble more than one value.

### This is where claude-authored text first leaves the module boundary

`questionResolution.ts`'s module docblock previously claimed nothing claude-authored reached it, true
only because the refusal path took a batch id and nothing else. That claim is **corrected in the same
commit** rather than left standing: `option.label` is claude-authored, crossed the subprocess trust
boundary unsanitized, and this is the one place in the app it is read for a purpose other than rendering.
It goes into an entry's `values` array and nowhere else — entries are built from the fixed literal keys
`question_index` and `values`, never a computed key, so no label becomes an object key, a `Map` key, a
React key, an attribute, a URL, a filename, a cache key or a lookup path. Publishing it outbound does not
make it trusted, which is exactly why the frame names a question by index and never by its text — the
daemon rebuilds the text-keyed map claude receives from its own parked copy of the batch. Nothing on the
incomplete path is logged either: an incomplete batch is the gate working, not a fault, and the reflex
debug line a developer reaches for there would put the partial payload — labels plus the operator's own
typed text — into a sink.

## `answerQuestionBatch` — the send effect

```ts
export function answerQuestionBatch(
  questionBatchId: string,
  answers: QuestionAnswerEntry[] | null,
  deps: QuestionResolveDeps
): void
```

`answers === null` performs **no effect at all** — no send, no clear, no log. That is the gate's second
layer, deterministic code rather than a second stochastic rule: the same value that renders Continue
`disabled` also refuses the send, so a handler firing anyway (there is none, but the function does not
trust that) cannot post an under-filled answer the daemon rejects totally and silently.

Non-null takes `refuseQuestionBatch`'s shape verbatim: `sendCommand(answerQuestionsCommand({...}))` inside
a `try`, both local dispatches **outside** it, picks-first — the same optimistic-clear posture and the
same picks-before-batch ordering [Cancel](question-panel-cancel-refusal.md) established, restated there in
full. A swallowed send still clears the panel; the daemon keeps the batch parked and re-asserts it at the
next reconnect, so the operator sees the ask again rather than believing an answer landed that did not.
The catch logs a static, content-free string (`'question answer send failed'`) with the caught error
dropped — binding harder here than on the refusal, since the payload this send choked on now carries
claude-authored labels and the operator's own typed text beside the nonce, and an `Error` raised by a
failing structured clone can stringify the argument it choked on.

**`QuestionRefuseDeps` is renamed `QuestionResolveDeps` and now serves both exits** — the fields are
identical, and `modalResolution.ts`'s `ModalResolveDeps` is the precedent for one interface across an
answer and a cancel. Four line edits, no behaviour change to the refusal path.

**Two new client-owned constants**, `QUESTION_ANSWER_OUTCOME = 'answered'` and
`QUESTION_ANSWER_SOURCE = 'client'`, going through the same `dismissed` arm the refusal uses.
`'answered'` must not be the refusal's `'refused'` — a later reader merging the two families has only
this field to tell an operator who answered from one who declined. The source stays `'client'` rather than
`'local'` for the reason `QUESTION_REFUSAL_SOURCE` already records: `'local'` is a member of
`WireModalSource`'s closed `{remote, local, timeout}` set, where it means an *answered* outcome in the
modal vocabulary, so borrowing it here would make a client-side event indistinguishable from the daemon's
own. `reduceQuestionBatches` consults neither field; both are a forward carry.

## The picks store's new read shape

```ts
export const selectBatchSelections =
  (questionBatchId: string) => (s: QuestionPicksState): ReadonlyMap<number, QuestionSelection>
```

The whole batch's picks in one read, mirroring `selectQuestionSelection`'s factory shape and stability
contract: a held batch answers with the inner map **by reference** (`withSelection` clones on write, so
the reference is stable across a write to any other batch), and an untouched batch answers with a hoisted
shared empty `Map` rather than `undefined` — the `EMPTY_QUESTION_SELECTION` mechanism one nesting level
up, because `useStore` compares the selector's result under `Object.is` and a fresh `new Map()` per call
would spin the panel forever. Safe to call inline in a render with no `useMemo`, exactly as the existing
per-question selector is.

`QuestionPanelSlot` now reads only this whole-batch map and supplies it to all rendered cards.
There is no active-question subscription. The map can hold removed question positions after same-ID
redelivery; resolution filters them by iterating current questions, not by mutating the selector.

## The view's conjunction

The single inline Continue button uses `disabled={!canAnswer || !responseAvailable}` and `onClick={onAnswer}`.
Every card remains editable without stepping. `canAnswer` is computed by the container with
`resolveQuestionAnswers`; host availability comes from `usePromptResponseAvailability`.

At activation, `isCurrentQuestionBatch(batch)` checks the active conversation, captured object identity
against the current owning store entry, and absence of outstanding permission/trust. Checking only the
nonce would accept callbacks captured before a same-ID redelivery changed the available positions.
`canRespondToPromptNow` then rereads the owning host's availability. Only after both checks does the
handler resolve the current picks and enter `answerQuestionBatch`:

```ts
onAnswer={() => {
  if (!isCurrentQuestionBatch(batch) || !canRespondToPromptNow(batch.conversationId)) return
  const currentAnswers = resolveQuestionAnswers(batch.questions,
    selectBatchSelections(batch.questionBatchId)(questionPicksStore.getState()))
  answerQuestionBatch(batch.questionBatchId, currentAnswers, deps())
}}
```

A duplicate, replaced, redelivered, navigated-away, permission-covered or offline activation sends
nothing and clears no state. `window.pyry` is dereferenced only during an accepted interaction, never
in render. Optimistic removal still occurs on a throwing send; unresolved requests can reappear after
reconnect, with the old picks cleared and an explicit new answer required.

## CSS — unavailable response controls

Inline batch actions use body-large typography through `.question-batch` overrides. Its disabled
Continue retains the primary/on-primary token pair at opacity 0.38; Cancel retains its outline with
muted text/border tokens. The base disabled Continue rule uses neutral surface-container-high and
on-surface-variant for other shared consumers, including permissions. Scope the inline override so
changing the questionnaire does not redraw the permission panel.

## Testing strategy

`questionResolution.test.ts`: a complete multi-question batch yields entries in question order with
labels in ascending display order; Other text is trimmed, carried as its own value, placed after the
ticked labels; whitespace-only Other text does not satisfy the gate; a ticked Other with no options is a
complete question; an untouched question, an empty selection, and a ticked-but-blank Other each yield
`null`; an out-of-range position is skipped and can itself make the batch incomplete; a value matching no
offered label is carried unchanged. `answerQuestionBatch`: `null` performs no effect at all; a complete
answer sends exactly one `answerQuestions` command carrying the entries and no token; the two dispatches
land picks-first and outside the `try`; a throwing send still clears both stores.

`questionPicksStore.test.ts`: `selectBatchSelections` — an untouched batch returns the shared empty map
(same reference twice), a picked batch returns the held inner map by reference, a write to a sibling batch
leaves that reference intact, hostile keys (`__proto__`, `constructor`, `''`) answer empty before any
write.

`QuestionPanel.test.tsx` checks the inline Continue disabled matrix for completeness and host
availability, independent native group names and exactly one action row after all cards.
`QuestionPanelSlot.test.tsx` checks live-pick recomputation, duplicate and stale callback rejection,
replacement retirement, shorter same-ID delivery, reconnect, permission coverage and navigation.

`e2e/question-answer-continue.spec.ts` drives all three cards at once: single-select, multi-select and
Other. Partial answers and whitespace-only Other keep Continue disabled; completing every question
permits one ordered, trimmed `question_answer`. Footer model selection preserves the pending picks;
optimistic removal preserves the visible composer's draft. The frame capture keeps only
`{ type, question_batch_id, answers }`, excluding `answer_token` from stored test diagnostics.

This spec proves the click and the outbound frame against a scripted `daemon.pushFrame` — it cannot
show a real claude ever receiving or reading the answers. [#928](real-claude-liveness-e2e.md) closed
that gap: `e2e/real-claude-question-answer.spec.ts` drives the same panel against a real `pyry` +
real `claude`, with no outbound-frame capture available (the daemon is a separate process behind the
content-blind relay), so its proof is claude's own next reply naming the chosen label before any
unchosen one — see that doc's sibling entry for the non-vacuity argument.

## Security review: PASS

Builder self-review. The two SHOULD-FIX findings are both addressed in the design above rather than
deferred: the stale module docblock (corrected in the same commit) and the two logging reflexes (a static
content-free catch, and nothing logged on the incomplete path). The renderer→main crossing is #920's
`isAnswerQuestionsPayload`, which recurses into each entry and each `values` element and is unchanged by
this slice; `answerQuestions` deep-rebuilds the payload from fresh literals, so an extra key at either
depth is dropped rather than serialized. No new `contextBridge` API, no new `ipcMain` channel, no
filesystem or persistence surface — `questionPicksStore` still refuses to persist this family.

**Concurrency is guarded at activation since #1729.** The container rejects stale captured objects
and navigated-away owners, then recomputes answers from current picks. Same-ID redelivery no longer
leaves a valid callback holding the previous delivery's payload. Edits share the identity/permission
checks and validate positions, preventing cleared drafts from being recreated by retained handlers.

**Threat model.** The applicable desktop threat is a hostile or degraded relay dropping the answer; the
design fails open in the safe direction, the same posture as the refusal. A compromised renderer gains no
new capability class beyond what `sendMessage` already permits — the widest new capability is "answer a
batch whose nonce you already hold, with values you choose," strictly weaker than sending an arbitrary
chat message, and it approves nothing (a question batch is a clarifying ask, not a permission modal).
Out of scope: pyrycode#702's per-device remote-permission opt-in, which defaults to deny and makes a
correct answer from a non-opted-in device indistinguishable from a swallowed send at this layer — a
live-run concern owned by #923, wired blocked-by this ticket.
