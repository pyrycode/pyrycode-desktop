# Spec #342 — fakeRoutingRelay AC1 lifecycle-parity: absorb the silent dial-establishment stall

**Ticket:** #342 · **Size:** XS (test-only) · **Labels:** `bug`, `size:xs`, `security-sensitive`

One-line: the AC1 lifecycle-parity test flakes with a **5000ms vitest timeout** (a genuine *hang*,
not a rejection) because a raw `connect()` dial can **stall** under parallel-worker CPU
starvation — the socket emits neither `'open'` nor `'error'`, so the test's existing retry ladder
(which re-dials only on an emitted `'error'`) never fires and the `connect()` promise never settles.
The fix adds a **per-attempt dial timeout** to the test file's `connect()` helper, plus gives the AC1
test's own `whenReady()` call explicit headroom so the retry can converge at the client-leg dial
site. **Test-only, no production change, no touch to any behavioural assertion.**

## Context

`fakeRoutingRelay.test.ts` → `startFakeRoutingRelay — lifecycle parity (AC1)` →
`exposes an ephemeral loopback url and holds whenReady until BOTH server and a client leg are up`
fails intermittently with `Error: Test timed out in 5000ms.` It flakes **only** under full `npm test`
(parallel workers): 3/3 clean single-file in ~200–250ms; unmasked 2026-07-13 while QA-ing PR #341
(#339), which has **zero** code overlap with this file — established pre-existing, not caused by #341
(merge-base and PR branch both showed the same rate; the isolated single-file re-run passes).

This is a **new member of the `fakeRoutingRelay`/`fakeDaemon` dial-race flake family**
([#104](../../knowledge/codebase/104.md), [#311](../../knowledge/codebase/311.md),
[#336](../../knowledge/codebase/336.md)) but a **distinct failure shape**: #311 (`Parse Error`) and
#336 (`404`) are *rejections* — the upgrade response arrives but is malformed/wrong, an **emitted
`'error'`** the ladder re-dials past once classified. This is a **hang** — an `await` that never
settles — which the emitted-error ladder cannot see.

**Scope guard:** the sibling `fakeRelayForwarder.test.ts` carries a twin `connect()` helper with its
own still-live flake (desktop memory "Flaky fakeRelayForwarder socket-hang-up"). That is a **separate
ticket** — do **not** edit `fakeRelayForwarder.test.ts` (or `fakeDaemon.test.ts`) here. This ticket
hardens `fakeRoutingRelay.test.ts`'s copy only.

## Root-cause confirmation (why a dial timeout, and not a `whenReady` margin bump *as the fix*)

The flake is **not machine-reproducible in isolation** (single-file always passes; full-suite ~1/3 at
peak), so — exactly as #311 and #336 confirmed their mechanisms — the root cause is established by
**elimination over the test's awaits**, keyed on the one hard fact the symptom hands us: a
**5000ms vitest timeout is a hung `await`, definitionally distinct from a rejection**.

Enumerate every `await` in AC1 (lines 104–119) and ask which can hang for 5000ms:

| `await` | Can it hang 5000ms? | Why / why not |
|---|---|---|
| `standUpRelay()` (104) | No (not AC1-specific) | resolves on `wss` `'listening'`; a bind failure *emits `'error'` → reject*, not a hang, and would affect every test, not just AC1. |
| `serverLeg(relay)` → `connect(/v1/server)` (107) | **Yes** | hangs iff the dial emits neither `'open'` nor `'error'`. **Candidate.** |
| `new Promise(setTimeout(r,20))` (113) | No | a 20ms macrotask timer; timers are not starved to 5s under vitest. |
| `clientLeg(relay)` → `connect(/v1/client)` (116) | **Yes** | same as `serverLeg`. **Candidate.** |
| `relay.whenReady()` (117) | No | by line 117 it is already **settled** — resolved when both legs connected (`maybeSettleReady`), or rejected by its own 1000ms timer. If the timer had fired, the failure would be `both legs did not connect within 1000ms` **at ~1000ms**, not a 5000ms vitest timeout. |
| `Promise.resolve()` (118) | No | a microtask; always settles. |

**Conclusion — the only awaits that can produce a 5000ms hang are the two `connect()` dials.** Because
`connect()` re-dials only on an **emitted `'error'`** (line 47) and has **no per-attempt timeout**, a
dial that stalls with neither `'open'` nor `'error'` leaves its Promise permanently unsettled →
`await serverLeg`/`await clientLeg` hangs → the 5000ms vitest timeout. **This is the confirmed
mechanism: a silent dial-establishment stall.**

Why it can stall silently: `startFakeRoutingRelay` resolves on `'listening'`, so the server is
bound before any dial, but the server's per-connection **upgrade handler runs on the same event
loop** that six transport test files are starving under worker fan-out. If a client's TCP connect
lands but the server's event loop is stuck long enough that it never processes the HTTP upgrade to
send a `101` (or an error), the `ws` client — which sets **no `handshakeTimeout`** here — sits
waiting indefinitely. No `'open'`, no `'error'`. (Contrast #311/#336, where a *malformed* `101`/`404`
arrives and emits `'error'`.)

**Why AC1 specifically:** per [#104](../../knowledge/codebase/104.md), vitest starts every file's
first `it` at ~the same wall-clock instant across workers, concentrating peak loopback
accept-queue / ephemeral-port pressure on each file's **source-order-first** test. AC1 is
`fakeRoutingRelay.test.ts`'s first `it`, and its very first operation is a dial (`serverLeg`, line
107) — exactly where a stall is most likely. This matches "only AC1, only under full-suite load."

**The `whenReady` 1000ms margin (candidate seam B from the ticket) is *ruled out* as the mechanism.**
If that timer fired, `ready.promise` rejects and the test fails with `both legs did not connect within
1000ms` **at ~1000ms** — a fast, distinctively-messaged rejection, *not* a 5000ms hang. The observed
symptom is unambiguously the hang, so the margin is **not the root cause**. Per the family's
"retry vs. barrier vs. margin are different-layer remedies" discipline, the margin therefore does not
get a fix *as the remedy*. It does, however, sit in the way of the remedy at the client-leg dial site
(next section) — a different concern from being the cause.

## Design

Two test-file changes, no production change. The exact literals below are recommended values with the
budget arithmetic that constrains them; the developer may finalise within the stated bounds.

### 1. Per-attempt dial timeout in `connect()` (the mechanism-matching remedy)

Add a timer to each dial attempt in `connect()` (`fakeRoutingRelay.test.ts:32-54`). Contract (the
added block — the rest of `connect()` is unchanged):

```ts
const DIAL_STALL_MS = 1500 // > healthy contended dial (~250ms); leaves ≥2 attempts within the 5000ms test budget

// inside the Promise executor, alongside the existing once('error')/once('open'):
const dialTimer = setTimeout(() => {
  ws.off('error', onDialError)      // detach so terminate()'s events are inert
  ws.terminate()                    // drop the stalled half-open socket before re-dialling
  if (attemptsLeft > 1) {
    resolve(connect(url, { headers, attemptsLeft: attemptsLeft - 1 })) // stall is inherently transient
  } else {
    reject(new Error(`dial to ${url} stalled: no open/error within ${DIAL_STALL_MS}ms`))
  }
}, DIAL_STALL_MS)
```

- **Clear the timer on every settle path.** `onDialError` and the `'open'` handler must both
  `clearTimeout(dialTimer)` first, so the timer never fires after the dial has already resolved or
  entered the error/retry path (which would spawn a duplicate re-dial). This is the one structural
  invariant the developer must get right; assert nothing leaks by the teeth check + full-suite run.
- **The timeout path retries unconditionally (bounded by `attemptsLeft`), *not* gated by
  `isTransientDialError`.** A stall produces no error object to classify, and by construction the
  server is already `'listening'`, so a dial that yields neither event within a generous timeout is a
  contention artifact — the same recoverable class the three emitted-error siblings already re-dial
  past. On exhaustion it `reject`s with a descriptive stall message (so a *genuine* never-accept
  regression still surfaces — see teeth check).
- **Reuse the existing `attemptsLeft = 5` budget and `20`ms backoff.** Do not tune retry count or the
  emitted-error path — unrequested scope. Only the new timer and its clear-on-settle wiring are added.
- **Do NOT add an `isTransientDialError` clause.** Unlike #311/#336 there is no error string here; a
  new classifier clause would be dead code. This is the "remedy matches the *confirmed* mechanism"
  point from AC1 — the mechanism is a *stall*, whose remedy is a *timeout*, not a retry-list widening.

**Value rationale (`DIAL_STALL_MS`).** The failure mode is bimodal: healthy dials complete in
~250ms even contended; a stall is effectively "stuck until reset" (the 5000ms timeout proves it does
not self-complete within the budget). Any timeout in the wide gap between them cleanly separates the
two. `1500ms` is comfortably above healthy (no false-positive re-dials on merely-slow dials) and
leaves room for ≥2 attempts inside the 5000ms per-test budget
(`1500 + 20 + 1500 + 20 + ~250 ≈ 3290ms < 5000ms`). A single fresh re-dial is the realistic need — the
stalled socket sat behind a momentary event-loop starvation that clears; a fresh dial re-enters the
accept queue after it disperses.

### 2. Give AC1's own `whenReady()` call headroom (decouple, so the remedy can converge at the client leg)

Change the AC1 test's line-109 call from `relay.whenReady()` to an explicit generous margin, e.g.
`relay.whenReady(4000)`. **This is not a second remedy for a second cause** — it removes an obstacle:

- The **server-leg** dial (107) is dialled *before* `whenReady()` is armed (109), so a server-leg
  stall is a clean 5000ms hang the § 1 dial timeout fixes with no `whenReady` interaction.
- The **client-leg** dial (116) runs *concurrently* with the readiness timer armed at 109. At the
  default `1000ms`, that timer would fire and **reject** before a stalled client dial (detected at
  `DIAL_STALL_MS = 1500ms`) can time-out-and-re-dial — converting the 5000ms hang into a 1000ms
  rejection. Still a failure; the § 1 remedy would be **pre-empted at the client-leg site**.
- Widening *this test's* readiness gate to `4000ms` lets a stalled-then-retried client dial converge
  (`~20 + 1500 + 20 + 250 ≈ 1790ms`, and even a double-stall `~3290ms`, both `< 4000ms`) before the
  gate fires. It touches **no `expect`**, and **not** the production `DEFAULT_READY_TIMEOUT_MS`
  (still `1000`, unchanged for every real consumer).

This does not weaken AC1's coverage: the line-114 `expect(resolved).toBe(false)` is checked after a
fixed 20ms tick — a larger timeout cannot fire in 20ms, so "whenReady stays pending with only the
server leg" is asserted **identically** (if anything, more robustly). The line-119
`expect(resolved).toBe(true)` (resolution once both legs are up) is independent of the margin size.

### Why this is teeth-preserving (AC3 + AC4)

- **The dial timer is consulted strictly pre-`'open'`.** Like the existing `onDialError` (detached on
  `'open'`, line 49), the new timer is cleared the instant the dial resolves or errors. A genuine
  *behavioural* regression — wrong `close_code`, dropped frame, mis-routed conn-id — occurs
  **post-open** in `onServerMessage`/`onClientMessage` and is asserted by the AC2–AC5 tests; the dial
  timer never touches those. Their `expect(...)`s stay byte-identical.
- **A genuine never-accept regression still fails.** If the relay were truly broken so dials never
  open, the timer retries `attemptsLeft` times then `reject`s with the stall message → the test still
  turns red (and a persistent stall exhausts the ladder well within budget). The retry absorbs only
  the *transient* stall, never a real fault. Same boundary as #104/#311: "does an assertion re-run?" —
  no assertion re-runs; only dial *establishment* is retried.
- **AC4 by construction:** `fakeRoutingRelay.ts` is **not in the diff**. Content-blindness, log-free,
  and token-non-leak cannot drift when the production file is byte-identical.

## State + concurrency model

No new persistent state. `connect()`'s recursion already carries `attemptsLeft` and `terminate()`s the
half-open socket before each re-dial, so no socket leaks across retries — the new timeout path reuses
that exact discipline (`off` + `terminate` + fresh `connect`). The only new resource is the
per-attempt `dialTimer`, which **must be cleared on all three settle paths** (`'open'`, `'error'`,
timeout-fire) to guarantee at most one live dial per attempt and no post-settle re-dial. No stores, no
async iterables, no shared mutable state introduced. `whenReady`'s cached-single-promise semantics
(production) are untouched; the test merely passes a larger `timeoutMs` argument.

## Error handling

- **Silent stall (new)** → `off('error')`, `terminate()`, then re-dial a fresh socket
  (`attemptsLeft − 1`) if attempts remain, else `reject(new Error('dial to … stalled: …'))`.
- **Emitted transient (`ECONNRESET`/`ECONNREFUSED`/`socket hang up`/`Parse Error`)** → unchanged:
  `onDialError` → `terminate()` → 20ms backoff → re-dial / reject.
- **Non-transient emitted error, or attempts exhausted** → `reject(err)` unchanged.
- **Post-open errors** → swallowed by the `ws.on('error', () => {})` installed at `'open'` (line 50),
  never seen by the classifier or the timer. Unchanged.

## Testing strategy

- **No new unit test.** Consistent with #104/#311/#336: the flake never reproduces single-file, so a
  deterministic "a stalled dial is retried" unit test would require synthesising an event-loop stall,
  which cannot be injected reliably. The regression guard is empirical (below), and the existing five
  AC groups already assert the behaviour under test.
- **Verification (AC2):** run the **full** suite `npm test` **≥10× back-to-back** and confirm **zero**
  AC1 `Test timed out in 5000ms` failures. Anchor on the vitest `Test Files N passed (N)` summary line
  (a `wasm streaming compile failed` stderr line is benign noise-c.wasm fallback, per #336 — not a
  failure signal). Record the run count in the PR. Then `npm run build` (typecheck + electron-vite
  build) must pass (AC5-of-body).
- **Teeth check (AC3 + AC4):** `git diff` must touch **only** `connect()` in
  `fakeRoutingRelay.test.ts` (the new timer + its clear-on-settle wiring) and the line-109
  `whenReady()` argument. Confirm every `expect(...)` across all five AC groups (lifecycle, wrap+token,
  unwrap+close_code, conn-id multiplexing, content-blindness) is **byte-identical**, and that
  `fakeRoutingRelay.ts` and `fakeRelayForwarder.test.ts` are **absent** from the diff.

## Open questions

None blocking.

- If a future change gives the `ws` client an explicit `handshakeTimeout`, this dial timer becomes
  partly redundant (the client would emit its own timeout `'error'`, which the existing `onDialError`
  path would then need to classify). Not shipped now — evidence-based scope: no `handshakeTimeout` is
  set today, and adding one would be a behavioural change to every dial, broader than this flake.
- `DIAL_STALL_MS` and the `whenReady(4000)` headroom are tunable within the budget bounds stated in
  § Design; if a real machine shows healthy contended dials approaching `1500ms`, raise both
  proportionally (keeping `2 × DIAL_STALL_MS + overhead < whenReady margin < 5000ms`).

## Security review

**Verdict:** PASS

Adversarial re-read of the two test-file changes (a per-attempt dial timeout in `connect()`, and a
larger `whenReady()` argument in AC1). This module is `security-sensitive` because it *simulates* the
content-blind relay; the invariants it guards are **content-blindness**, **log-free**, and
**token-non-leak**. Both changes are in `fakeRoutingRelay.test.ts`; `fakeRoutingRelay.ts` (the actual
relay data path) is **not modified**.

**Findings:**

- **[Trust boundaries]** No findings — the new timer fires on the *absence* of any event; it reads no
  frame payload, no disk content, no renderer IPC. It crosses only into a `boolean`-equivalent
  retry-vs-reject decision. No trusted state is derived from relay-origin or attacker-controlled bytes.
  The `whenReady` argument is a compile-time integer literal.
- **[Tokens, secrets, credentials]** No findings — the client `x-pyrycode-token` flows through
  `onClientMessage`/`encodeRoutingEnvelope` in the untouched production file. Neither the timer nor the
  `whenReady` argument references, logs, or branches on the token.
- **[File / storage operations]** N/A — no filesystem path, no `fs` call, no path construction; the
  changes are an in-memory timer and an integer argument.
- **[Inter-process / Electron attack surface]** N/A — test-only harness under vitest/Node. No
  `BrowserWindow`, `webPreferences`, `contextBridge`, `ipcMain`, or custom-protocol surface touched.
- **[Cryptographic primitives]** N/A — no RNG, no Noise handshake, no key/nonce handling, no secret
  comparison. Unlike #336's Site-B re-dial, the retried resource here is a **raw `ws` test socket**,
  not a Noise session initiator — so there is no `(key, nonce)`-reuse hazard to gate. No
  `Math.random()`, no `===`-on-secret added.
- **[Network & I/O]** No findings — the retry the timer feeds stays **bounded** (reuses the existing
  `attemptsLeft = 5`) and leak-free (`ws.terminate()` drops the stalled half-open socket before each
  re-dial, and the timer is cleared on every settle path), so making a *stall* transient adds no
  unbounded-retry or socket-exhaustion vector. This is a `ws://127.0.0.1` loopback test dial, never
  the production `wss://` relay client; no `maxPayload`, TLS, or production timeout is touched.
- **[Error messages, logs, telemetry]** No findings — no `console.*` is added; the stall `reject`
  message contains only the loopback `url` and the timeout literal, never a token, key, or frame. The
  AC5 `is log-free … never logging the token` test remains the deterministic guard and stays
  byte-identical.
- **[Concurrency]** One structural obligation, not a vulnerability: the new `dialTimer` **must be
  cleared on `'open'`, `'error'`, and its own fire**, else a late fire could spawn a duplicate re-dial
  against an already-resolved attempt. This is a correctness/teeth requirement (called out in
  § Design and the teeth check), not a trust-boundary issue — a duplicate loopback test dial leaks no
  secret and crosses no boundary. Otherwise no new shared state, listener, or async task beyond the
  bounded retry the file already performs.
- **[Threat model alignment]** No findings — the change is test-only and never runs in production, so
  it does not touch the malicious-relay, token-theft, hostile-daemon, or renderer-compromise surfaces.
  The simulator's content-blind + log-free contract is preserved by construction: `fakeRoutingRelay.ts`
  is byte-identical and no logging is introduced.

No MUST FIX findings.
