## Context

`subscribePushNotify` sends a `notify` command for every `modalShown` it sees and holds no memory of
what it has already announced. The daemon re-sends every still-outstanding `modal_shown` after each
re-handshake (#415 reconcile), so a prompt left unanswered while the window is in the background earns
one fresh OS notification per network flap or sleep/wake cycle.

Two things that look like they could absorb the duplicate, and cannot:

1. **The modal store.** Since #510, `reduceModal`'s `reconnected` arm clears *both* `outstanding` and
   `resolved` (`modalPrompts.ts:178-196`), so immediately after a handshake it has no record that a
   prompt was ever seen. It also cannot be extended to hold one: #510 exists precisely because
   retaining `resolved` across the reset swallowed an Allow clicked while the link was down.
2. **The background process.** The command payload is `{ kind }` only, so `modalId` never crosses IPC,
   and `fireNotification` gates solely on window focus.

The ticket body carries a pre-discharged verification block. Its premise is confirmed and needs no
re-checking — **but the fix sketch it proposed is a no-op** and is explicitly not what this spec
builds. That sketch cleared the memory "on the same reconnect edge the store resets on"; on that edge
`connected` arrives *before* the re-sent frames (`modalBridge.ts:61-65` → `modalPrompts.ts:178-196` is
built on exactly that ordering), so memory cleared there is empty when the re-sends land and every
reconnect re-notifies as it does today. **The memory must survive the reconnect edge.**

## Design

One production change, inside `subscribePushNotify`: a closure-local set of already-announced
`modalId`s, created once per subscription and consulted only on the `modalShown` arm.

```ts
export function subscribePushNotify(/* signature UNCHANGED */): () => void {
  const announcedModalIds = new Set<string>()
  return onDaemonEvent((event) => {
    // filter → dedup → toggle → send → record
  })
}
```

The listener body, as a contract (the developer writes the code):

1. `const kind = notifyKindForEvent(event)`; `null` → return. Unchanged.
2. Bind the dedup key once by narrowing on the discriminant:
   `const modalId = event.type === 'modalShown' ? event.modalId : null`. This is the *only* new read of
   a daemon-supplied field, and it never leaves the listener.
3. If `modalId !== null && announcedModalIds.has(modalId)` → return. **Use `!== null`, not a truthiness
   check** — `requireString` (`inboundMessage.ts:236-242`) admits `''`, and `if (modalId)` would treat
   an empty id as "not a modal" and skip both the check and the record.
4. `if (!isPushEnabled()) return`. Unchanged, and still read per-event.
5. `sendCommand({ type: 'notify', payload: { kind } })`. **The literal is unchanged** — `modalId` is a
   local that is never spread, never interpolated, never referenced here (AC5).
6. `if (modalId !== null) announcedModalIds.add(modalId)`.

### Why the record happens *after* the send, not at step 3

If a `modalShown` is dropped by the toggle gate, it was never announced, so it must not be recorded. A
user who has push notifications off while a prompt arrives, then turns them on, must still be notified
when the daemon re-sends that prompt. Recording at the dedup check instead of after the send would
silently swallow it. This ordering is what makes "announced" mean *announced*, and it has a dedicated
test below.

### Why `turnEnd` is untouched

`turnEnd` carries a `turnId`, but turn-completes are not re-sent on reconnect and two turns completing
genuinely warrant two notifications. `modalId` is `null` for every non-`modalShown` event, so both the
check and the record are skipped for the whole rest of the union by construction, not by a second rule.

### Lifetime: the subscription, and nothing shorter

The set lives in the closure returned by `subscribePushNotify`, so it spans exactly one subscription:

- **Reconnect** — does not touch it. `PairedShell` mounts on App's `conversation` route
  (`App.tsx:181-186`), and that route flips only on the mount-time pairing-status read, `onPaired`, or
  `onUnpaired` — no daemon event moves it. `usePushNotify()` is called unconditionally in the shell
  body (`PairedShell.tsx:141`) with an empty-dep effect. A `connected` event therefore does not
  re-subscribe, and the memory survives. **This is the property the bug turns on.**
- **Unpair** — `onUnpaired` flips the route, unmounts the shell, runs the effect cleanup, and the set is
  garbage. A new pairing is a new daemon relationship and starts with no memory. Correct reset edge.
- **StrictMode double-mount** — subscribe → cleanup → subscribe nets one live listener with one fresh
  set, same as today.

Closure-local, not module-level: module state would leak across tests and across unpair/re-pair, and
would make the reset edge implicit rather than structural.

### Deliberate non-goal: never prune the set

There is no `modalDismissed`-driven eviction, and no size cap. Pruning on dismissal would reintroduce
#510's bug in notification form: an Allow clicked while the link is down is swallowed by the transport
(`answerModal` early-returns on a null driver), the renderer optimistically dispatches `dismissed`
anyway, and the daemon re-sends the still-outstanding prompt after the handshake. If a dismissal
evicted the id, that re-send would re-notify — the exact duplicate this ticket removes. The ticket
calls this out: same `modalId`, so no second notification, no special case.

Growth is one short string per distinct prompt per pairing session, which is not a failure mode anyone
has observed; a cap would trade a real correctness property for a hypothetical one. Do not add one.

### Boundary: a first delivery the focus gate drops still counts as announced

Dedup is per *command*, not per *raised OS notification*. If the window is focused when a prompt first
arrives, the bridge sends `notify`, `fireNotification` early-returns without showing anything
(`fireNotification.ts:62`), and the id is recorded — a later re-send while unfocused is suppressed.

This is accepted, and is the only behaviour available: `isWindowFocused()` lives in the main process,
the payload is `{ kind }`-only by AC5, and there is no reply channel. Widening either is out of scope
(the ticket is explicitly renderer-local: no wire type, no IPC contract, no main-process change). The
residual risk is small — a focused window means the prompt was rendered on screen in front of the
user, which is a stronger signal than a notification, and the prompt stays visible. Documented here so
code review reads it as a decision rather than an oversight.

## State + concurrency model

No store, no async, no new subscription. The set is renderer-local mutable state confined to one
listener closure; `onDaemonEvent` delivers synchronously on the main-world event loop, so there is no
interleaving between the `has` check and the `add`. Teardown is unchanged: the returned handle is still
`onDaemonEvent`'s own off handle, used as the effect cleanup, and the set becomes unreachable with it.
No timers, no `AbortController`, no listener added or removed beyond what ships today.

## Error handling

No new failure modes. `Set.has` / `Set.add` on a `string` cannot throw; nothing new is parsed, and the
listener still never throws into React. A daemon that sends a duplicate or empty `modal_id` collapses
prompts in `modalPrompts.ts` already (match-and-replace by `modalId`, shipped since #195) — this bridge
inherits that same uniqueness assumption and adds no new exposure to it.

## Testing strategy

`src/renderer/src/store/pushNotifyBridge.test.ts`, plain vitest with the existing `fakeBridge()` spies —
no React, no Electron, no store singleton. Every existing test stays as written and must still pass
(they pin AC1's toggle-on single-send, AC4's turnEnd behaviour, AC5's no-leak assertions, the
per-event toggle read, and the cleanup handle).

Add a second `modalShown` fixture with a different `modalId` (keep an `XYZ`-bearing value so the AC5
assertion stays meaningful), plus an `ack: HelloAckPayload` copied from `modalBridge.test.ts:8-13`.

New scenarios:

- **Same `modalId` twice → exactly one command.** Emit `modalShown`, emit the identical event again;
  `sendCommand` called once, with `{ kind: 'prompt' }`.
- **Same `modalId` across a reconnect → exactly one command (AC2, the ticket's shape).** Emit
  `modalShown`, then `{ type: 'connected', ack }`, then the same `modalShown`; `sendCommand` called
  once. This is the test that fails on the rejected clear-on-`connected` sketch.
- **A genuinely new `modalId` after a suppressed re-delivery still notifies (AC3).** Emit `modalShown`,
  the same one again, then one with a different `modalId`; two commands total, both `{ kind: 'prompt' }`.
- **Two `turnEnd`s with the toggle on still send two commands (AC4).** Distinct from the existing
  mid-session-flip test, which turns the toggle off between the two emits — this one leaves it on.
- **Toggle-off first delivery is not recorded.** Toggle off, emit `modalShown` (no command); toggle on,
  emit the same `modalShown`; exactly one command. Pins the record-after-send ordering — this test is
  the one that fails if the developer records at the dedup check.
- **Memory is per-subscription, not module-level.** Subscribe, emit `modalShown`, tear down; subscribe
  again on a fresh `fakeBridge` with a fresh `sendCommand`, emit the same `modalShown`; the second
  subscription sends its command. Guards the unpair reset edge and catches a module-level `Set`.
- **AC5 survives dedup.** In the same-`modalId`-twice test, assert
  `JSON.stringify(sendCommand.mock.calls[0][0])` does not contain `XYZ` — the dedup key is read but
  never sent.

Type-level coverage: `npm run typecheck`. The `event.type === 'modalShown'` narrowing is what makes
`event.modalId` legal; if the developer reaches for a cast to get the id, that is the wrong shape.

Gates: `npm test`, `npm run typecheck`, `npm run build`.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings. The one new read of untrusted data is `event.modalId`, taken from
  an already-decoded `DaemonEvent` that crossed the trust boundary in the main process
  (`inboundMessage.ts:846`, `requireString`). It is bound to a listener-local, used only as a `Set`
  key, and never re-crosses IPC. The renderer→main direction is untouched: the `notify` payload literal
  is unchanged, so AC5 ("no daemon-supplied field reaches `sendCommand`") is preserved structurally and
  asserted by the retained `not.toContain('XYZ')` tests.
- **[Over-suppression — the reason this ticket carries the label]** No MUST FIX. Suppressing a
  notification for a permission/trust prompt is the failure that matters here, so each path was walked:
  (a) *toggle off on first delivery* — handled by design; the record happens after the send, so an
  unannounced prompt is never marked announced, with a dedicated test. (b) *focus-gated first delivery*
  — accepted and documented above; the prompt was on screen in a focused window, and closing it needs
  an IPC-contract change the ticket excludes. (c) *`modalId` collision or an empty id from a hostile or
  buggy daemon* — a genuinely distinct prompt reusing an announced id goes unnotified, but the same
  input already collapses the two prompts in the render (`modalPrompts.ts` match-and-replace by
  `modalId`, shipped #195), so this introduces no new exposure and the render, not the notification, is
  the load-bearing surface. (d) *the render is never suppressed* — this ticket touches only the notify
  path; the prompt itself still displays on every re-delivery, so the worst case is a missing second
  buzz, never an invisible permission request. That is the categorical difference from #510, whose bug
  was suppressing the prompt itself.
- **[Resource exhaustion / DoS]** No findings. The set grows by one short string per distinct prompt
  per pairing session and is released on unpair. A daemon able to flood distinct `modal_shown` frames
  already floods OS notifications and the render queue — strictly louder failures than the memory. A
  cap was considered and rejected: no such failure has been observed, and eviction is unsafe (see the
  never-prune rationale — pruning on dismissal reintroduces #510 in notification form).
- **[Tokens, secrets, credentials]** Not applicable, and verified rather than assumed: this file
  touches no key, token, or credential, and the change adds no logging of any kind. `modalId` is a
  correlation nonce, not a secret, and is not written anywhere observable.
- **[File / storage]** Not applicable. No filesystem access, no path construction, no persistence. The
  memory is in-process only and deliberately does not reach `localStorage`, IndexedDB, or disk — it must
  not survive a process restart, since a restart re-handshakes and legitimately re-announces.
- **[Inter-process / Electron attack surface]** No findings. No new `contextBridge` API, no new
  `ipcMain` channel, no `webPreferences` change, no navigation or protocol handler. The existing
  `notify` command's main-side validator (`commands.ts:258`, closed-set membership on `kind`) is
  untouched and still rejects anything but the two literals.
- **[Cryptographic primitives]** Not applicable. No randomness, no comparison against a secret, no
  handshake surface. `Set` membership compares two daemon-supplied nonces to each other — neither side
  is a secret, so `timingSafeEqual` is not indicated.
- **[Network & I/O]** Not applicable. No socket, no URL, no frame handling; this is a pure consumer of
  the already-decoded event channel.
- **[Error messages, logs, telemetry]** No findings. The design adds no `console` call and no error
  path. A suppressed notification is silent by intent — logging `modalId` on suppression would put a
  daemon-supplied nonce in the renderer DevTools console for no diagnostic gain. **Do not add one.**
- **[Concurrency]** No findings. Synchronous listener, no `await` between the `has` check and the `add`,
  so no check-then-act gap. No timer, no `AbortController`, no listener added beyond today's; teardown
  is the unchanged off handle and the set dies with the closure.
- **[Threat model alignment]** Hostile relay: it is on-path and can force reconnects at will, which is
  exactly the flood this ticket closes — after this change a relay that flaps the link cannot generate
  more than one notification per distinct prompt. Hostile daemon: covered under over-suppression (c)
  above; defensive parsing stays in the main process where it already is. Renderer compromise: the
  blast radius is unchanged — the set holds nonces the renderer already had in hand.
