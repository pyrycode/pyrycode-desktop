## Context

Three fixtures register teardown only *after* `await use(...)`. Anything that throws between "resource created" and "`use` returned" makes the cleanup lines unreachable: the Electron process and its `mkdtemp --user-data-dir` both leak. With `workers: 1` in both configs the orphan then persists across every remaining spec in the run.

The dir is not incidental — it is credential storage. The `PYRY_TEST_SECRET_BACKEND` path persists the pairing record into it, and at site 1 that record pairs against a live spawned `pyry`. The fix narrows the window in which that artefact survives a failed run from "the rest of the developer's session" to "microseconds".

## Design

### Decision: nested `try`/`finally`, not a teardown stack

The ticket leaves the shape to the architect. Take **nested `try`/`finally` per resource** at sites 1 and 3:

- Each site owns exactly **two** resources (dir, app). A `teardown[]` array pays for itself at `launchPairedApp`'s four; at two it is pure ceremony.
- Nesting makes "no `await` between create and cleanup registration" a **structural** property — the `try` textually follows the `const x = await create()` — rather than a discipline a future edit can silently break by inserting a line.
- LIFO ordering is guaranteed by construction: the inner `finally` (`app.close`) completes before the outer `finally` (`rm`) begins. That is AC2's app-close-then-`rm` with no bookkeeping.

`launchPairedApp.ts` keeps its stack and is not touched.

### Site 1 — extract the `page` fixture body (`e2e/fixtures/realDaemon.ts`)

AC3 requires the regression test to drive the **real** converted setup path. That means the body must be reachable from a test, so it moves out of the fixture closure into an exported function in the same module:

```ts
export type IsolatedElectronApp = {
  page: Page
  app: ElectronApplication
  userDataDir: string
}

/** Launch the built app against a throwaway --user-data-dir, hand the handles to `run`, and reap
 *  both (app.close, then rm) on every raised exit path. Rethrows whatever `run` or setup threw. */
export function withIsolatedElectronApp(
  run: (handles: IsolatedElectronApp) => Promise<void>
): Promise<void>
```

Behaviour, in order: `mkdtemp(join(tmpdir(), 'pyry-e2e-realclaude-'))` → `try` → `electron.launch({ args: ['.', '--user-data-dir=' + dir], env })` → `try` → `firstWindow()` → `await run({ page, app, userDataDir })` → inner `finally` `app.close()` → outer `finally` `rm(userDataDir, { recursive: true, force: true })`.

The fixture collapses to a delegation; `daemon` is still depended on for teardown ordering only:

```ts
page: async ({ daemon }, use) => {
  void daemon
  await withIsolatedElectronApp(({ page }) => use(page))
}
```

This is a **pure move** of `:352-359`'s env and launch args. `ELECTRON_RENDERER_URL` stripped, `LOOPBACK_RELAY_ENV_FLAG` and `TEST_SECRET_BACKEND_ENV_FLAG` set, `args: ['.', ...]` — byte-identical. Changing any of them is out of scope, and widening them is a security regression (see § Security review, category 4).

**Hard constraint on the signature: `withIsolatedElectronApp` takes no path parameter.** The `rm` target is always the value `mkdtemp` just returned. A caller-supplied path would turn a test helper into an arbitrary recursive-delete primitive. If a future ticket wants `launchPairedApp`-style dir reuse, it registers no second `rm` (see `launchPairedApp.ts:154-158` for the correct handling); it does not add a path argument here.

The externally-visible fixture contract is unchanged — `page` still yields a `Page`. Fan-out is zero: `withIsolatedElectronApp` gets exactly one production caller (the fixture, same file) plus the new test. The nine `real-*` specs importing `./fixtures/realDaemon` consume `test`/`expect` and are untouched.

### Both teardown steps at site 1 are best-effort (swallow, do not rethrow)

Each `finally` wraps its call in `try { … } catch { /* best-effort */ }`, matching `launchPairedApp.ts:245-249`. Three reasons, and one accepted cost:

1. **A throwing `finally` replaces the in-flight exception.** Without swallowing, an `app.close()` failure would mask the causal error the developer needs to see — and would make the regression test's rejection assertion non-deterministic.
2. **AC1 says the dir is removed on *every* exit path.** If a failed `close` aborted the unwind, the credential-bearing dir would survive — reintroducing exactly this bug on a narrower path.
3. It is the established shape in this directory.

Accepted cost: if `close()` fails and the process is genuinely still alive, `rm` runs anyway and a live Electron briefly outlives its dir. AC2 fixes the *order* (close is always attempted first), not a conditional. Between "dir leaks" and "process may outlive a removed dir", the credential artefact wins. The swallowed error is **discarded without logging** — see § Security review, category 7.

### Site 2 — `relay` fixture (`e2e/fixtures/realDaemon.ts:139-143`)

Plain single-level `try`/`finally` around `use(relay)`, with `relay.close()` in the `finally`. **No swallow here**, deliberately: one resource means there is no drain to protect from an aborted unwind, and a fake-relay close failure is a genuine harness signal worth surfacing. Consistency conversion only — its resource is an in-process server that dies with the worker, so per the ticket it gets no test.

### Site 3 — `e2e/smoke.spec.ts:27-42`

Same nested `try`/`finally` shape as site 1, **transcribed independently**. Do not import `withIsolatedElectronApp` and do not extract a shared helper — de-duplicating the three launch recipes is explicitly out of scope. The three recipes stay three recipes; only their control flow converges.

AC5 — the comment at `:24-26` currently claims a property the code lacks. After the fix the guarantee is *stronger*, so the comment is rewritten to state exactly it: the nested `try`/`finally` reaps the app then the dir on pass, on test failure, **and on a failure raised after launch but before `use` returns**. It must also name the bound: an `await` that never settles (a hung `firstWindow()`) is not covered — Playwright kills the worker without unwinding the stack, so no `finally` runs.

## State + concurrency model

No store, no renderer state. The concurrency surface is fixture lifecycle only:

- **Async ownership.** `withIsolatedElectronApp` owns exactly one Electron process and one temp dir, and releases both before returning on every raised path. Nothing outlives the call.
- **Serialization.** `workers: 1` in both configs — no parallel launches contend, and equally, one orphan poisons the whole remaining run (the reason this ticket exists).
- **Bounded waits.** The regression test's process-death probe polls with a deadline; no unbounded wait is introduced anywhere.
- **Uncovered residual (named, not fixed).** A never-settling `await` inside the fixture body. `try`/`finally` cannot unwind a pending promise, and Playwright's fixture-timeout path kills the worker rather than injecting a rejection. AC1 scopes to a failure *raised*, so this is out of scope. A follow-up would race `firstWindow()` against a deadline; no ticket filed.

## Error handling

- Setup failure (`mkdtemp`, `launch`, `firstWindow`) and callback failure both propagate to the caller **after** teardown completes.
- Teardown failures at site 1 are swallowed (above). Teardown failure at site 2 propagates.
- Nothing is surfaced to a UI; every failure lands in the Playwright reporter.
- **Diagnostics inherit `realDaemon.ts`'s no-echo rule** (`:404-406`, `:449-453`: `pyry pair` stdout is never echoed because it carries the token). Teardown emits no message at all — no `console.*`, no re-thrown wrapper carrying a path.

## Testing strategy

One new Playwright spec: `e2e/fixture-teardown-leak.spec.ts`.

**Placement is forced.** `vitest.config.ts:32` scopes the unit run to `src/**`, and `playwright.config.ts` overrides no `testMatch`, so Playwright's default glob claims `e2e/**/*.test.ts` as well as `.spec.ts` — a vitest-style `*.test.ts` under `e2e/` would be run by Playwright and collected correctly by neither. `.spec.ts` under `e2e/`, and not named `real-*` (AC4: `testIgnore` in the default config, `testMatch` in the real config).

**Imports:** `test`/`expect` from `@playwright/test` directly — *not* the `test` exported by `realDaemon.ts`, which carries the `daemon` fixture. Only `withIsolatedElectronApp` comes from `./fixtures/realDaemon`. Importing that module runs `base.extend({...})` and nothing else; no daemon is spawned unless a test declares the fixture. AC4 holds on a machine with no `pyry` and no `claude`.

**Do not make the runner's own failure the test** (cross-project lesson, `pyrycode/docs/lessons.md:122`, #68): an inner test whose failure you want to observe ends the parent before the post-state assertions run. The extracted function sidesteps it — call it directly with a callback that throws, and assert post-state in the same test.

Scenario — *a setup failure after launch still reaps the app and its user-data dir*:

- Raise the per-test timeout to ~60s (one built-app launch plus a bounded death poll; the 30s default is tight on a cold runner — same rationale as `launchPairedApp.ts:52`).
- Call `withIsolatedElectronApp` with a callback that, in order:
  - reads `app.process().pid` and asserts it is a number;
  - asserts the liveness probe **succeeds** here — `process.kill(pid, 0)` does not throw. This is the mutation control; without it the later "process is gone" assertion could pass because the probe is broken or the app never launched.
  - asserts `existsSync(userDataDir)` is `true` — the same control for the dir assertion;
  - records `{ pid, userDataDir }` into an outer-scope variable;
  - throws a sentinel `Error` whose message is a **fixed literal** — no path, pid, or env interpolation.
- Assert the returned promise rejects with that sentinel message. This proves teardown neither swallowed nor replaced the causal error.
- **Assert the outer-scope record is non-null before reading it.** A capture-in-callback pattern makes every post-assertion vacuously pass if the callback never ran; this is the explicit non-vacuity guard.
- Assert the process is gone by polling a `pid → boolean` liveness helper (`process.kill(pid, 0)` in a `try`, `false` in the `catch`) until it reports `false`, with a bounded timeout. Poll rather than assert once: `app.close()` resolving does not guarantee the OS has reaped the pid in the same tick.
- Assert `existsSync(userDataDir)` is now `false`.
- Assert on **booleans only**. Do not interpolate `userDataDir` or the pid into any assertion message (§ Security review, category 7).

**Developer ordering — this is how AC3's "fails before, passes after" is demonstrated** (and it is the repo's test-first rule):

1. Extract the `page` fixture body into `withIsolatedElectronApp` **verbatim** — plain sequential, no `try`/`finally`. The fixture delegates. This extraction *is* `main`'s control flow, which is what makes the next step a real RED (on `main` the function does not exist, so the AC cannot be read literally).
2. Write the spec. Run `npm run e2e`. It must **fail on both post-assertions** — process alive, dir present. Record that output; it is the evidence for AC3.
3. Add the nested `try`/`finally` + swallow. Re-run — GREEN.
4. Convert site 2 and site 3; fix the `smoke.spec.ts:24-26` comment. Re-run the full `npm run e2e` — green with **no assertion changes in any existing spec** (AC5).

**Type-checking note:** `npm run typecheck` and `npm run build` do not cover `e2e/` (neither tsconfig includes it), and Playwright transpiles without type-checking. A type error in the new code surfaces only when the spec runs. Don't treat a green `npm run build` as coverage.

**Unit tests:** none. There is nothing under `src/` to test; `npm test` is unaffected.

## Accepted risks

- **pid reuse.** Between `app.close()` and the poll, the OS could theoretically hand the pid to another process. The window is seconds and the failure mode is a poll timeout (a flake toward *failure*), never a false pass. Not defended — the ticket's own precedent uses the same probe.

## Open questions

- None blocking. The hang case and pid reuse are named above as out-of-scope and accepted respectively.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings — no new boundary. The change is test-harness control flow; nothing untrusted is parsed, and no data crosses renderer↔main. The one new input is the `run` callback, supplied at two in-repo call sites.
- **[Tokens, secrets, credentials]** No findings; net-positive delta. The `--user-data-dir` **is** the credential store — `TEST_SECRET_BACKEND_ENV_FLAG` persists the pairing record into it, and at site 1 that record pairs against a live spawned `pyry`. This change creates, logs, and stores no new secret; it strictly narrows the window in which the existing artefact survives a failed run. The regression test's app never pairs, so its dir holds no pairing record — and is removed regardless.
- **[File / storage operations]** No MUST FIX, one hard constraint recorded in § Design: `withIsolatedElectronApp` takes **no path parameter**; the `rm` target is always the value `mkdtemp` just returned. No untrusted input reaches a filesystem path, so there is no traversal surface. No TOCTOU: the test's `existsSync` calls are post-hoc assertions, never a gate before an open. The dir keeps `mkdtemp`'s 0700 mode. The deliberate decision that `rm` runs even when `close()` failed is reasoned in § Design — prioritising removal of the credential-bearing dir over a possibly-live process, consistent with AC1's "every exit path".
- **[Inter-process / Electron attack surface]** No findings, one constraint. No `webPreferences`, IPC channel, custom protocol, or navigation guard is touched. The extraction is a **pure move** of the env and launch args at `realDaemon.ts:352-359` — the two `app.isPackaged`-gated dev flags (`PYRY_ALLOW_LOOPBACK_RELAY`, `PYRY_TEST_SECRET_BACKEND`) keep exactly today's scope. Widening `env` or `args` during the move is a regression and code-review's anchor is a byte-diff against `:352-359`.
- **[Cryptographic primitives]** Not applicable — no key, nonce, RNG, hash, or handshake is touched. The Noise session lives in `src/main/transport/` and is not reachable from this change.
- **[Network & I/O]** No findings — no socket, no relay URL, no TLS setting, no frame cap changes. Site 2's `relay` is an in-process fake (`startFakeRoutingRelay`); converting its teardown adds no network surface.
- **[Error messages, logs, telemetry]** One **SHOULD FIX**, plus two design decisions. (a) The swallowed `close`/`rm` errors are **discarded without logging** — an Electron close error can carry the launch argv, which embeds `--user-data-dir=<path>`; `realDaemon.ts`'s no-echo rule (`:404-406`, `:449-453`) extends to teardown diagnostics per the ticket's security note. (b) The sentinel error thrown by the regression test is a fixed literal with no interpolation. (c) **SHOULD FIX** — the test must assert on booleans and must not interpolate `userDataDir` or the pid into an assertion message. The tmp path is not itself a secret and is already deleted by then, so this is discipline rather than an exploit; it is cheap to keep and gives code-review a concrete check. Note also that `playwright.config.ts` enables no trace, screenshot, or video, so no artefact captures the dir's contents.
- **[Concurrency]** No findings, one named residual. `workers: 1` in both configs removes parallel-launch contention. The helper owns exactly two resources and releases both before returning on every raised path; the death probe is bounded. **OUT OF SCOPE:** a never-settling `await` inside the fixture body is not reapable by `try`/`finally` (Playwright kills the worker without unwinding). AC1 scopes to a failure *raised*. No follow-up ticket filed; a future one would race `firstWindow()` against a deadline.
- **[Threat model alignment]** The applicable desktop threat is **token theft from disk**. Today an orphaned `--user-data-dir` under `/var/folders` persists past the run holding a real pairing record for a live daemon; this change reduces that exposure window to the teardown path itself. Malicious relay, hostile daemon response, and renderer compromise are unaffected by this change and remain governed by the existing transport design.
