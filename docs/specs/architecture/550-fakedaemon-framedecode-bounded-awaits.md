# Spec #550 — fakeDaemon.test.ts frame-decode-failed leg boundary: bound every await, re-dial the stalled one

**Ticket:** #550 · **Size:** XS (test-only) · **Labels:** `bug`, `size:xs`, `security-sensitive`

One-line: the `fail-closes a non-InnerFrameV2 frame at the leg boundary to frame-decode-failed
(security)` test flakes with a **5000ms vitest timeout** — a genuine *hang*, not a rejection —
because its raw `connect()` dial is the **exact pre-#342 shape** (re-dials only on an emitted
`'error'`, no per-attempt timer), so a silently-stalled dial never settles. The fix propagates #342's
per-attempt dial timeout into this file's `connect()`, and — per AC1 — puts a **shared deadline
bound** on the test's three remaining unbounded awaits so any future stall *anywhere* in this test
rejects below 5000ms **naming the step**, instead of yielding another nil diagnosis. **Test-only. No
production change. No behavioural assertion touched.**

## Context

`src/main/transport/fakeDaemon.test.ts:864` intermittently fails with `Error: Test timed out in
5000ms.` (observed at 5006ms, in a file whose other 11 tests took ~391ms combined in the same run).
Unmasked while QA-ing PR #549 (#513), a renderer-only diff with **zero** overlap with the transport
layer. Evidence from the ticket: 1 failure across 3 full-suite PR-side runs, 0 across 3 full-suite
baseline runs, 0 across 6 isolated single-file runs (~740–760ms each). Pre-existing,
contention-only, not machine-reproducible on demand.

Fifth member of this repo's flaky-transport-fake family ([#303](../../knowledge/codebase/303.md),
[#311](../../knowledge/codebase/311.md), [#336](../../knowledge/codebase/336.md),
[#342](../../knowledge/codebase/342.md)) and the **second of hang shape** rather than rejection
shape.

## Root-cause confirmation

The flake never reproduces in isolation, so — exactly as #311/#336/#342 did — the mechanism is
established by **elimination over the test's awaits**, keyed on the one hard fact the symptom hands
us: **a 5000ms vitest timeout is definitionally a hung `await`, categorically distinct from a
rejection** (`docs/knowledge/codebase/342.md`).

| `await` in `:864-886` | Can it hang 5000ms? | Why / why not |
|---|---|---|
| `startFakeRelayForwarder()` `:867` | Possible, unlikely | `fakeRelayForwarder.ts:232-251` waits on `'listening'`/`'error'` with no timer. But it runs in **all 12** tests; the other 11 were green in the same contended run. |
| `startFakeDaemon({ url })` `:869` | Possible, unlikely | `fakeDaemon.ts:485-495`, a bare `open`/`error` promise, no timeout, no retry. Also runs in **all 12** tests. |
| `connect(.../v1/client)` `:876` | **Yes — confirmed** | See below. |
| `forwarder.whenReady()` `:878` | **No — ruled out** | Bounded at 1000ms and it **rejects** with a distinct message (`fakeRelayForwarder.ts:188-197`). A ~1000ms rejection cannot present as a 5006ms hang. Stronger still: by `:878` both legs are already registered, so `settleReady()` (`:185`) has fired and `whenReady()` returns an **already-resolved** promise without ever arming its timer. |
| `daemon.whenSettled()` `:881` | Possible, unlikely | Unbounded by construction (`fakeDaemon.ts:499`). But it is reached only *after* `whenReady()` resolved (both legs up) and the daemon's server leg is `OPEN`, so the `{not json` text frame is forwarded (`fakeRelayForwarder.ts:170`) and decoded synchronously into the `frame-decode-failed` settle (`fakeDaemon.ts:435-438`). Reaching a 5000ms hang requires a loopback frame on an OPEN socket to be *lost*, not merely delayed. |

**Confirmed mechanism — a silent dial-establishment stall at `connect()` (`:876`).** Three
independent lines converge:

1. **It is the only un-timed dial unique to this test.** `connect()` has exactly one non-recursive
   call site in the file (`:876`), and it is in the flaking test. The other 11 tests dial through
   `driveClient` → `createRelayConnection`, and every subsequent wait there goes through
   `makeWaiter().wait()`, which is bounded and **resolves** at 2000ms — so a stall in those tests
   degrades into a failed `expect`, never a 5000ms hang. Only this test can produce the observed
   symptom at all.
2. **The shape is the exact one #342 proved hangs.** `connect()` (`:60-78`) re-dials only on an
   emitted `'error'` and has no per-attempt timer. `grep -rn DIAL_STALL_MS src/` returns **only**
   `fakeRoutingRelay.test.ts` — #342 deliberately scoped its fix to that one file, leaving this
   file's copy pre-#342.
3. **This dial site is already a proven racer.** #336 fixed a `404`-upgrade race at this very dial
   ("Site A") in this very file. Same site, same contention; the only difference is whether the race
   *emits* (`404` → rejection, #336) or *stalls silently* (no `'open'`, no `'error'` → hang, here).
   `ws` sets no `handshakeTimeout`, so a dial whose TCP connect lands but whose HTTP upgrade a
   CPU-starved server never processes sits forever with no signal at all (#342 lesson).

The two "possible, unlikely" rows are **not** dismissed — they are the reason AC1 asks for bounds on
*every* reachable await, not just the fixed one. They get a **diagnostic bound**, not a remedy
(§ Design 2). That distinction matters: a remedy without confirmed evidence is the "defence for an
unobserved failure mode" this pipeline defers, whereas a bound that converts a nil diagnosis into a
named step is an *instrument*. It is also the durable win here — five tickets in this family have
each paid the cost of hand-walking an elimination table; after this ticket, the next stall in this
test names itself.

## Design

Two constants, one new file-local helper, changes to `connect()`, and four call-site edits inside the
`:864` test. **One file: `src/main/transport/fakeDaemon.test.ts`.** No production file is touched.

Recommended literals are given with the arithmetic that constrains them; the developer may finalise
within the stated bounds.

```ts
const AWAIT_BUDGET_MS = 4000 // every await in the :864 test settles by start+4000ms, < vitest's 5000ms
const DIAL_STALL_MS   = 1500 // per-attempt stall detection; > a healthy contended dial (~250ms)
```

### 1. A single shared deadline, not per-step budgets (the AC1 proof)

Arm **one** deadline at the top of the `:864` test — `const deadline = Date.now() + AWAIT_BUDGET_MS`
— and measure every bound against it. Per-step budgets would have to be summed to prove AC1 (three
near-limit-but-successful steps plus a dial ladder can exceed 5000ms in aggregate); one absolute
deadline makes the proof a single line: **no bounded await in this test can reject later than
`start + AWAIT_BUDGET_MS`, regardless of how the earlier steps behaved.** The 1000ms of headroom
under vitest's default absorbs the rejection's own unwinding and `afterEach` teardown, so the
*rejection* is what fails the test, never the vitest timeout.

New file-local helper — contract only:

```ts
/** Reject at `deadline` naming `step`, unless `work` settles first (its own settle passes through
 *  unchanged, so a more specific diagnosis always wins). Clears its timer on every settle path. */
function bounded<T>(step: string, work: Promise<T>, deadline: number): Promise<T>
```

- Arms `setTimeout(..., Math.max(0, deadline - Date.now()))`; rejects with a message naming `step`
  and the budget, e.g. `` `#550 bound: ${step} did not settle within the ${AWAIT_BUDGET_MS}ms test
  budget` ``. This is AC1's "names the step that stalled".
- **Must `clearTimeout` on both of `work`'s settle paths**, so no timer handle outlives the test and
  no rejection fires after the test body has moved on.
- Adds **no** `console.*` output on any path — load-bearing for AC2's six-spy assertion.
- Not exported; used **only** by the `:864` test. Adding it to the other 11 tests is out of scope
  (their waits are already bounded by `makeWaiter`), and doing so would touch their `expect`s' inputs,
  violating AC3.

### 2. Per-attempt dial timeout + deadline-capped ladder in `connect()` (the remedy)

Signature change (one call site, so no compatibility concern):

```ts
function connect(url: string, deadline: number, attemptsLeft = 5): Promise<WebSocket>
```

Behaviour added to the existing executor — the emitted-`'error'` path, the `'open'` swap, and
`isTransientDialError` are otherwise **unchanged**:

- **Arm a per-attempt stall timer** at `Math.min(DIAL_STALL_MS, Math.max(0, deadline - Date.now()))`.
  On fire: `ws.off('error', onDialError)` **first** (so `terminate()`'s teardown events cannot spawn a
  duplicate re-dial), then `ws.terminate()` to drop the half-open socket, then re-dial with
  `attemptsLeft - 1` **carrying the same `deadline`** if `attemptsLeft > 1 && Date.now() < deadline`,
  else `reject` with a descriptive stall message naming the url and the limit that was hit.
- **`clearTimeout(dialTimer)` at the top of both `onDialError` and the `'open'` handler.** This is
  the one structural invariant the developer must get exactly right — mirror
  `fakeRoutingRelay.test.ts:49` and `:59` verbatim.
- **The emitted-`'error'` retry path also checks the deadline** before its 20ms backoff re-dial, and
  threads `deadline` through. Without this, five slow-but-emitting attempts could still outrun the
  budget.
- **The stall path retries unconditionally** (bounded by `attemptsLeft` *and* the deadline), **not**
  gated by `isTransientDialError`: a stall produces no error object to classify, and the server is
  already `'listening'` by construction, so a dial yielding neither event within a generous margin is
  a contention artifact. **Do not add an `isTransientDialError` clause** — it would be dead code
  (#342's established rule).

**Value rationale.** The failure mode is bimodal: healthy dials complete in ~250ms even contended; a
stall is stuck until reset (the 5000ms timeout proves it does not self-complete). `DIAL_STALL_MS =
1500` sits in the wide gap — no false-positive re-dials on merely-slow dials — and the shared deadline
guarantees convergence: worst case `1500 + 1500 + min(1500, ~1000) ≈ 4000ms`, i.e. **two full
re-dials available** before the ladder rejects, still below 5000ms. (Note this closes a hole in
#342's shipped version, where `5 × DIAL_STALL_MS = 7500ms` could in principle have out-run the very
timeout it was added to prevent. Do **not** back-port that here — `fakeRoutingRelay.test.ts` is
untouched by this ticket; it gets its own ticket if it ever exhausts.)

**Why `fakeDaemon.ts:485-495` is deliberately NOT changed** (AC4 permits it; this spec declines):
the server-leg dial there is production-adjacent and shared by every consumer of `startFakeDaemon`,
so a timeout inside it would change behaviour for 11 other tests in this file plus other files —
unrequested blast radius for a site with **no** supporting evidence (it runs in all 12 tests; only
this one flaked). The call-site bound in § 3 gives it AC1-compliant diagnosis at zero blast radius.
If a future run rejects naming `startFakeDaemon`, *that* is the evidence which earns a change there.
Consequence: `fakeDaemon.ts` is **absent from the diff**, so AC4 holds vacuously.

### 3. Bound the three remaining awaits in the `:864` test (AC1's literal requirement)

| Line | Change |
|---|---|
| `:867` | `startFakeRelayForwarder()` wrapped in `bounded('startFakeRelayForwarder', …, deadline)` |
| `:869` | `startFakeDaemon({ url })` wrapped in `bounded('startFakeDaemon /v1/server dial', …, deadline)` |
| `:876` | `connect(url)` → `connect(url, deadline)` (self-bounding; **not** wrapped, or the wrapper would cut its retry ladder short) |
| `:878` | `forwarder.whenReady()` — **unchanged**; already bounded and already settled by this point |
| `:881` | `daemon.whenSettled()` wrapped in `bounded('daemon.whenSettled', …, deadline)`, **inside** the existing `expect(await …).toEqual(...)` so the assertion's expectation is byte-identical |

**Teardown obligation — register the two disposers against the START PROMISE, not the resolved
value.** Today `cleanups.push(() => forwarder.close())` runs *after* the await; if the new bound
rejects, the cleanup is never registered and a forwarder that resolves **late** leaks a listening
`WebSocketServer` into the rest of the run — turning a clean diagnostic rejection into a worker-level
hang, exactly what this ticket removes. Instead, capture the promise first and register a
**non-blocking** disposer against it:

```ts
const forwarderStart = startFakeRelayForwarder()
cleanups.push(() => void forwarderStart.then((f) => f.close(), () => {}))
const forwarder = await bounded('startFakeRelayForwarder', forwarderStart, deadline)
```

Same shape for `startFakeDaemon`. Two properties are load-bearing:

- **Non-blocking** (`void`, not `return`): `afterEach` awaits each cleanup, so a disposer chained to a
  promise that *never* settles would stall teardown — re-introducing a hang one layer up.
- **The rejection arm `() => {}` is required**, so a start that rejects after the bound already fired
  is a handled rejection, not an `unhandledRejection` (which vitest surfaces as a suite-level error).

Both `FakeRelayForwarder.close()` (`fakeRelayForwarder.ts:217-230`) and `FakeDaemon.close()`
(`fakeDaemon.ts:462-478`) cache a `closePromise`, so a disposer firing alongside a normal close is a
documented no-op. The only behavioural give-up is that `wss.close()`'s callback is no longer awaited
before the next test — benign here (ephemeral port, synchronous socket `terminate()`s, and the
following test stands up its own forwarder).

## State + concurrency model

No new persistent or shared state. Two new timers, both with a strict clear-on-settle obligation:

- `bounded()`'s deadline timer — cleared on `work`'s resolve **and** reject.
- `connect()`'s `dialTimer` — cleared on `'open'` and on `'error'`; on its own fire it detaches
  `onDialError` before `terminate()`, so at most one live dial exists per attempt and no settle path
  can double-fire.

`connect()`'s recursion already carries `attemptsLeft` and `terminate()`s the half-open socket before
each re-dial; the stall path reuses that exact discipline and additionally threads `deadline`, which
makes the whole ladder terminate by construction rather than by attempt-count arithmetic. No stores,
no async iterables, no listener accumulation. The `deadline` is a plain number captured once per test
run — no mutable module state, so parallel workers cannot interfere.

## Error handling

- **Silent dial stall (new)** → detach `onDialError`, `terminate()`, re-dial with the same deadline if
  attempts and budget remain; else `reject` naming the url and the exhausted limit.
- **Emitted transient dial error** → unchanged `isTransientDialError` path (`ECONNRESET` /
  `ECONNREFUSED` / `socket hang up` / `Parse Error` / `Unexpected server response: 404`), now
  additionally deadline-checked before the 20ms backoff re-dial.
- **Non-transient emitted error, or attempts exhausted** → `reject(err)` unchanged.
- **Any bounded step exceeding the deadline** → `reject` with `#550 bound: <step> …`, i.e. a named,
  sub-5000ms failure instead of a nil-diagnosis vitest timeout.
- **`work` rejecting on its own** → passes through `bounded()` untouched, so the specific error
  (e.g. `fake relay: both legs did not connect within 1000ms`) always beats the generic bound message.
- **Post-open socket errors** → still swallowed by the `ws.on('error', () => {})` installed at
  `'open'` (`:74`). Unchanged.

No path adds `console.*` output.

None blocking.

- If a future run rejects naming `startFakeRelayForwarder` or `startFakeDaemon /v1/server dial`, that

## Security review

**Verdict:** PASS

Adversarial re-read of the three changes (a `bounded()` deadline helper, a per-attempt dial timeout
plus deadline cap in `connect()`, and reshaped teardown registration in one test). This ticket is
`security-sensitive` because the test under repair **is** the fail-closed assertion for a non-trusted
inbound frame at the relay leg boundary, plus the module's six-method log-freeness contract. Every
change is in `src/main/transport/fakeDaemon.test.ts`; `fakeDaemon.ts` (the responder state machine and
the untrusted→trusted decode boundary at `:427-439`) is **not modified**.

**Findings:**

- **[Trust boundaries]** No findings — the fail-closed boundary is `fakeDaemon.ts:427-439`
  (`decodeInnerFrame` → `settle({ ok: false, reason: 'frame-decode-failed' })` → `close()`), and it is
  byte-identical. The new timers fire on the **absence** of an event; they read no frame payload, no
  disk content, no renderer IPC. `bounded()` is a pass-through — it cannot alter the settled value the
  assertion inspects, so "a malformed frame fails closed" remains asserted on the real path. The one
  behaviour the design deliberately does **not** relax is the settle-once caching: the spec forbids
  touching it, so a hostile frame arriving after settle still cannot rewrite the verdict.
- **[Tokens, secrets, credentials]** No findings — the test dials a raw `ws` with **no** headers and
  sends the literal `'{not json'`; no token is in scope at this dial site (the dummy
  `buildTestHello()` credential belongs to the `driveClient` tests, untouched). Neither the stall
  message nor the bound message interpolates anything but the loopback url, a step label, and an
  integer literal.
- **[File / storage operations]** N/A — no filesystem path, no `fs` call, no path construction
  anywhere in the diff; the changes are in-memory timers, an integer deadline, and two closure
  registrations.
- **[Inter-process / Electron attack surface]** N/A — test-only harness under vitest/Node. No
  `BrowserWindow`, `webPreferences`, `contextBridge`, `ipcMain`, or custom-protocol surface is touched,
  and nothing in the diff ships in the app bundle.
- **[Cryptographic primitives]** No findings — the retried resource is a **raw pre-handshake `ws`
  socket**, not a Noise session initiator: this test never constructs `createNoiseSession`, so unlike
  #336's Site B there is no `(key, nonce)`-reuse hazard for the re-dial to gate. `initiator.start()`
  is not reachable from any retry path added here. No RNG, no key material, no secret comparison; no
  `Math.random()` and no `===`-on-secret is introduced (`Date.now()` is used for deadline arithmetic
  only, never as entropy).
- **[Network & I/O]** No findings — the retry stays **bounded twice over** (the existing
  `attemptsLeft = 5` *and* the new wall-clock deadline), which is strictly tighter than today's
  unbounded-in-time ladder, so making a *stall* transient adds no unbounded-retry or
  socket-exhaustion vector. `ws.terminate()` drops each stalled half-open socket before re-dialling,
  and the timer is cleared on every settle path, so no socket or handle leaks across attempts. All
  dials are `ws://127.0.0.1` loopback test dials; no production `wss://` client, `maxPayload`, or TLS
  setting is touched (`fakeDaemon.ts:480`'s `MAX_FRAME_BYTES` cap is untouched).
- **[Error messages, logs, telemetry]** No findings — **no `console.*` is added on any path**, which
  the six-spy `not.toHaveBeenCalled()` assertion (`:882`) enforces deterministically and which the
  spec calls out as a hard constraint on `bounded()`. Both new rejection messages carry only a
  loopback url / step label and a timeout literal — never a token, key, frame, or Noise transcript.
  The pass-through design means a rejection from `work` is re-thrown as-is, so the helper cannot
  broaden an existing message either.
- **[Concurrency]** Two obligations, both structural rather than exploitable, and both called out in
  § Design so code-review can check them: (a) every new timer must be cleared on every settle path,
  else a late fire could spawn a duplicate re-dial or reject a test that has moved on; (b) the two
  teardown disposers must be **non-blocking and rejection-handled** — a disposer chained to a
  never-settling start would stall `afterEach`, re-introducing a hang one layer up, and an unhandled
  rejection would surface as a suite-level error. Neither crosses a trust boundary (a duplicate
  loopback test dial leaks no secret), but (b) is the one place where a careless implementation would
  *worsen* the very symptom being fixed. No new shared mutable state: `deadline` is a per-run local.
