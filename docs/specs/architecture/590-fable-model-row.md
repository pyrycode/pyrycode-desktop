## Context

The Model section offers Opus, Sonnet and Haiku. `fable` is a real published family, so the sheet
currently makes an existing family unreachable from the app. The daemon resolves each bare family
alias to the current model in that family (measured live 2026-08-18: `fable` → `claude-fable-5`),
which is precisely how the three existing rows already work — the row submits the family token and
the app never picks a version.

This is the one slice of #561 that needs no daemon change. #561's real fix — deriving the rows from a
daemon-published model list — is blocked on `pyrycode#1646`. When derivation lands, the hardcoded
catalog and this row are deleted together.

**Out of scope, deliberately:** refreshing the three existing row labels (`Opus 4.7`, `Sonnet 4.6`,
`Haiku 4.5`). They name a generation-old version, but the rows resolve to the newest in each family
regardless of the label. #560 answers that by showing the model actually running; #561 removes it
entirely. Touching them here would cascade through roughly nineteen assertions across five test files.

## Design

### The change

One entry appended to `MODEL_CATALOG` (`RunConfigSections.tsx:36-40`) **at index 2 — between
`sonnet` and `haiku`**:

```ts
{ family: 'fable', name: 'Fable 5', descriptor: 'newest in the Fable family' }
```

That is the entire production change, plus the stale comment below. No new type, no new export, no
JSX change, no CSS, no new prop.

### Copy — use these literals as written

No operator comment overrode them (the issue carries only PO's own refinement pass), so the defaults
in the ticket body stand:

- **Name `Fable 5`** — the siblings are `<Family> <version>` and the alias resolved to
  `claude-fable-5`. This makes it the only accurate label of the four, which is a consequence of the
  out-of-scope note above, not a defect to fix here.
- **Descriptor `newest in the Fable family`** — honest but not parallel with its siblings, which
  carry a when-to-pick-it line (`best for complex work`, `faster, cheaper`, `fastest`). A
  when-to-pick-it line would be better but means a capability claim unverifiable from this repo.

**Both literals are apostrophe-free.** `renderToStaticMarkup` escapes `'` to `&#x27;`, which breaks
string assertions — the standing renderer-test constraint. Do not introduce one.

### Why no seam is added for the submitted token

`entry.family` is **one field with two uses**: it is the value handed to `onSelect` (`:171`) and it is
the token `matchedFamily` substring-matches the daemon's model against (`:48`). So rendering with
`fable` and observing the Fable row marked *is* the round-trip proof — it exercises the same literal
the row submits, without firing a click the `node` test env cannot fire.

**Do not export `MODEL_CATALOG` and do not add an accessor.** That is new public surface an XS ticket
does not need, and it would leave the Fable row proved differently from its three siblings — which
have no such seam either (`runSettingsControls.test.ts` covers change-to-command *given* a value,
never row-to-token).

### Why the insertion point is display order only, and why it is still load-bearing for the tests

`matchedFamily` is first-match-wins over the catalog (`lower.includes(entry.family)`). Position would
only matter if some model string contained two family tokens; no vector in AC4 does, and no real model
id does. So placing Fable third changes which row renders third and nothing about which row matches.

It *does* matter for one test mechanic. `segmentFor` splits the markup on the class token and takes
the chunk containing the needle, so a chunk runs until the **next** row's class token. Because Fable
sits third of four, its chunk is bounded by the Haiku row — it contains Fable's row markup and
nothing else. A negative assertion on that chunk (AC5's inert case) is therefore tight, not
over-broad. Had Fable been last, its chunk would run to the end of the document and swallow the
effort segments and the YOLO switch, which carry their own `role="button"` / `tabindex`.

### Why zero CSS

Two independent reasons, both verified:

- `.run-config__model-list` (`conversation.css:1258`) is a `gap`-ed flex column with padding — no
  fixed height, no `:nth-child`, no positional rule anywhere in the model block. A fourth child lays
  out identically to the third.
- The section grows the sheet by one 62px pitch (182px → 244px in Figma terms). The sheet already
  absorbs that: `.status-sheet` is `max-height: 90%` (`:916-920`) and `.status-sheet__body` is
  `overflow-y: auto; min-height: 0` (`:993-997`) — written for exactly this ("tall future section
  content scrolling inside the body rather than overflowing the window").

### The stale comment

`RunConfigSections.tsx:161` documents the submitted token as `('opus'/'sonnet'/'haiku')`. Widen it to
include `'fable'`. It is one line and it goes stale with the array — fix it in the same edit.

## State and concurrency model

None added. No store slice, no async task, no subscription, no effect, no cancellation surface. The
row is drawn from a module-level frozen-by-convention constant inside an existing pure `map`.

The row participates in the existing `aria-busy` group marker without change: #558 marks
`.run-config__model-list` (the element owning the field's controls), never an individual row, so the
fourth row is covered by the marker that already exists.

## Error handling

No new failure mode. The only input is the `model: string` prop:

- **Empty or unrecognized** → `matchedFamily` returns `null`, no row is marked. Already the designed
  default; the fourth row inherits it.
- **A string containing a family token** → that row is marked. Display-only.

`RUN_CONFIG_ERROR_COPY` and the `role="alert"` rejection surface are untouched — this ticket adds no
field and no write path, so there is no new rejection to surface.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings. The daemon-supplied `model` string is the untrusted input, and
  this ticket enlarges the set it is matched against. Two properties make that safe and both are
  pre-existing, not introduced here: (a) the string is **never rendered** — only the static catalog
  `name` / `descriptor` literals reach the markup, so no daemon text can inject markup through this
  path; (b) matching is `String.prototype.includes` on a lowercased copy (`:47-48`), **not** a
  `RegExp` built from either operand, so a crafted `model` string is not a ReDoS or pattern-injection
  vector. Do not "improve" the matcher into a regex while adding the row.
- **[Trust boundaries — direction of flow]** No findings, and this is the load-bearing one.
  Daemon input never reaches the outbound value. The token submitted on select is `entry.family` from
  the module-level catalog (`:171`), never anything derived from the received `model`. So a hostile
  daemon can influence *which row is marked* but not *what the app sends back*.
- **[Network & I/O]** No findings. The added row can cause one outbound
  `set_session_settings` carrying `model: 'fable'` — a developer-authored static literal placed in a
  **structured payload field** (`SetSessionSettingsPayload`), not interpolated into a command string
  or a shell. No new command shape, no new verb, no new frame type.
- **[Inter-process / Electron attack surface]** No findings. No new IPC channel, no new
  `contextBridge` member, no `webPreferences` change. The change is confined to a renderer-side
  constant; nothing crosses `ipcMain`. Transport, keys and sockets are untouched and remain in the
  main process.
- **[Hostile daemon response — accepted, named rather than fixed]** Adding `fable` at index 2 changes
  the marked row for exactly one class of string: one containing **both** `fable` and `haiku` (e.g. a
  fabricated `fable-haiku`), which marks Haiku today and Fable after this change. No real model id has
  that shape, the effect is display-only, and the operator-facing consequence is bounded — a daemon
  already controls that display completely (it can report `opus` while running anything), so this adds
  no capability an attacker did not have. AC4 pins every realistic vector. Placing Fable last would
  remove even the fictional case, but AC1 fixes the display position between Sonnet and Haiku, and
  #560 (show the model actually running) is the ticket that answers "is the sheet telling me the
  truth" properly.
- **[Tokens, secrets, credentials]** Not applicable, by design decision rather than by omission: this
  ticket introduces no token, reads none, and logs none. `session_id` — the sheet's only identifier —
  is a non-secret routing id and is neither read nor written here.
- **[File / storage operations]** Not applicable. No filesystem path is constructed, read or written;
  the change is a compile-time constant in the renderer bundle.
- **[Cryptographic primitives]** Not applicable. No randomness, no comparison against a secret, no
  hashing, no handshake code path is reached.
- **[Error messages, logs, telemetry]** No findings. `RUN_CONFIG_ERROR_COPY` is untouched and no new
  log call is added. The field-scoped rejection copy remains client-derived from the field name, so no
  daemon text is surfaced through the new row.
- **[Concurrency]** No findings. No async task, timer, listener or `AbortController` is created, so
  there is nothing to cancel on teardown. The row is rendered synchronously inside an existing pure
  `map` and shares the existing `aria-busy` group marker on `.run-config__model-list` rather than
  introducing a per-row one.
- **[Threat model alignment — renderer compromise]** No findings, unchanged posture. A compromised
  renderer could already submit any model value through the existing rows; a fourth row widens the
  menu, not the capability. Process isolation still keeps keys, the token and the socket out of
  renderer reach.
