## Design source

## Context

The renderer has no scroll management at all — `.conversation__thread` scrolls because it is
`overflow-y: auto`, but nothing reads or writes its position. #599 split the missing
follow-the-conversation feature so that its one genuinely unit-testable piece — the arithmetic that
answers "am I at the bottom?" — lands first, isolated from the DOM wiring that the renderer's test layer
cannot execute (vitest runs in the `node` environment; renderer tests are `renderToStaticMarkup` string
assertions, so effects never run and there is no `scrollTop` to read).

The tolerance is the whole point. An exact `offset + viewport === content` test fails intermittently for
reasons unrelated to operator intent: fractional scroll metrics on non-integer device pixel ratios,
elastic/momentum overshoot that pushes `offset + viewport` past `content`, and zoom reintroducing
fractions at every level. A named band is the only form that survives real rendering.

**There is no mobile value to mirror.** `ThreadScreen.kt:249-256` uses a Compose `LazyColumn` in
`reverseLayout = true` mode with an exact discrete check
(`firstVisibleItemIndex == 0 && firstVisibleItemScrollOffset == 0`), so the parity source carries no
pixel tolerance anywhere. The tolerance below is a desktop invention forced by the DOM; its value is
derived here, not inherited.

## Design

### Exports

Three symbols, all from `threadScrollPosition.ts`:

```ts
export interface ThreadScrollMetrics {
  scrollOffset: number
  viewportHeight: number
  contentHeight: number
}

export const AT_BOTTOM_TOLERANCE_PX = 4

export function isAtBottom(metrics: ThreadScrollMetrics): boolean
```

**Body:** a single comparison — the distance from the bottom (`contentHeight` less the sum of
`scrollOffset` and `viewportHeight`) is at most `AT_BOTTOM_TOLERANCE_PX`. `<=`, not `<`: a distance
*equal* to the tolerance reads as at-bottom (AC3). That one expression discharges all five criteria; see
§ "Why one comparison" below.

**Why an object argument rather than three positional numbers.** The AC's "three plain numbers" is a
constraint on the *inputs' nature* — plain numbers, no DOM node, no React, no store — and an object of
three numbers satisfies it exactly. Positional would not: three same-typed parameters transpose
silently, and the transposition that matters (`clientHeight` ↔ `scrollHeight`) produces a wrong answer
with no type error. The call site is #601's scroll handler, which per the renderer's test posture is
untested reviewed glue — a mistake there ships silently, so the argument names have to make the glue
correct by inspection. Named-fields interfaces are already house style at this seam
(`ComposerSendDeps`, `DropQueuedMessageDeps`).

**Field naming.** `scrollOffset` (not `scrollTop`) keeps the helper free of DOM vocabulary while
carrying the DOM's own convention: the offset grows downward from zero. No scroll-direction convention
beyond that is prescribed or needed.

### The tolerance value: 4

`AT_BOTTOM_TOLERANCE_PX = 4`, bounded on both sides by behaviour:

- **Lower bound.** Sub-pixel error is under 1px per metric, but three metrics feed the comparison and
  the integer-vs-fractional split between them is engine-dependent (`scrollHeight`/`clientHeight` are
  rounded, `scrollTop` is fractional), so the accumulated error is realistically ~1–2px at high DPR or
  under zoom. 4 clears that with headroom.
- **Upper bound.** One line of message text is `--text-body-medium-line: 20px`. At 4px the band is a
  fifth of a line, so it can never swallow a deliberate one-line scroll-away.

Any value in roughly 2–8 would satisfy both bounds; 4 is the conventional small band and sits centrally.
The docstring on the constant must state *both* bounds — the next person to touch this needs to know the
value is fenced, not arbitrary. The test pins it (AC3).

This is the renderer's first exported *numeric* constant (the existing renderer constants are all copy
strings plus one boolean), so follow the `src/shared` precedent — `export const AT_BOTTOM_TOLERANCE_PX = 4`,
a bare number, not `as const`, not a config object.

### Why one comparison, and no second branch

All five criteria are consequences of the single distance quantity, not five code paths:

| AC | Distance | Result |
|----|----------|--------|
| Boundary (AC3, at tolerance) | `=== AT_BOTTOM_TOLERANCE_PX` | at-bottom (`<=`) |
| Boundary (AC3, just beyond) | `> AT_BOTTOM_TOLERANCE_PX` | not at-bottom |
| True bottom (AC4) | `0` | at-bottom |
| Elastic overshoot (AC4) | negative | at-bottom |
| Content ≤ viewport (AC5) | negative or `0` | at-bottom |

**No clamp, no `Math.max`, no "can it scroll at all" guard, no NaN/finite check.** Every such guard
would add a branch this ticket has no way to exercise, and each is already handled by the sign of the
distance. (For the record: a `NaN` input makes the comparison `false` — reads as scrolled-away, which is
the safe direction — but do not add a branch to make that explicit.)

If a case turns up during implementation that genuinely needs a second branch, that is a signal the
criteria are wrong: **route back (`needs-rework:po`) rather than guarding around them.**

### Explicitly out of scope

- **No ref, no scroll listener, no effect, no re-assert after the list changes.** #601 owns all of it.
- **No caller.** The helper ships unreferenced by design — that is what keeps the tested arithmetic
  separate from the untestable DOM wiring. Do not add a call site "to prove it works"; the test proves it.
- **No edit to any existing file.** Not `ConversationScreen.tsx`, not `conversation.css`, not
  `vitest.config.ts`, not `tokens.css`.
- **`flex-direction: column-reverse` is a rejected alternative, not an undiscovered one.** It is the
  browser analogue of mobile's `reverseLayout` and would let the browser pin natively with no arithmetic
  at all — which would leave this helper dead code forever and invalidate all five criteria. #599's
  split deliberately chose the measured-tolerance path and hung #601/#602/#603 on it. Adopting it is a
  route-back to PO, **never** a silent redesign inside the implementation.

## State + concurrency model

None. The helper holds no state, subscribes to nothing, touches no store, and performs no effects. It is
a total function of its argument.

## Error handling

None, deliberately. There are no failure modes to surface: the function is total over the numbers it is
given, and the "wrong" direction under degenerate input (`NaN`) is the conservative one. Nothing throws,
nothing logs, nothing returns a result type.

## Testing strategy

One sibling `threadScrollPosition.test.ts`, plain `vitest` in the existing `node` environment — no DOM,
no `@testing-library`, no config change. Open the file with a short comment (the `dropQueuedMessage.test.ts`
shape) noting that the arithmetic is isolated here precisely because the DOM half of the feature cannot
be tested in this environment.

Scenarios, as bullets — write them in the project's test idiom, naming the AC each discharges:

- **Pins the constant (AC3).** `AT_BOTTOM_TOLERANCE_PX` is exactly `4`. Assert the band too — greater
  than `1` (above sub-pixel error) and well below `20` (`--text-body-medium-line`) — so the two bounds
  from the design are executable, not just prose.
- **Distance exactly equal to the tolerance reads as at-bottom (AC3).** Fractional metrics.
- **Distance just beyond the tolerance reads as not at-bottom (AC3).** Fractional metrics, a fraction of
  a pixel past the band — not a whole pixel past, so the assertion is about the boundary and not about a
  comfortable margin.
- **Sitting exactly at the bottom reads as at-bottom (AC4).** Distance zero, fractional metrics.
- **Elastic overshoot reads as at-bottom (AC4).** `scrollOffset + viewportHeight` exceeds
  `contentHeight` — a negative distance — and is not mistaken for scrolled-away.
- **Content shorter than the viewport reads as at-bottom (AC5).** The un-scrollable short thread,
  `scrollOffset` zero. Include the equal case (`contentHeight === viewportHeight`) as well as the
  strictly-shorter one; both are the same expression, and the pair documents that no "can it scroll"
  branch is missing.
- **Scrolled well away reads as not at-bottom.** The sanity anchor: parked near the top of a long
  thread. Without it, a helper that returned `true` unconditionally would pass every other case above.

**Fractional inputs are the motivating case, so feed non-integer metrics rather than only round
numbers** — but choose fractions that are exact in binary floating point (halves and quarters) for the
two boundary cases, so the "exactly equal to the tolerance" assertion tests the boundary rather than
floating-point rounding. Values like `contentHeight: 1000.5`, `scrollOffset: 270.5`,
`viewportHeight: 726` give a distance of exactly `4`; the same offset and viewport with
`contentHeight: 1000.75` gives exactly `4.25`, just beyond. Elsewhere in the file, arbitrary fractions
are fine and preferable.

Type coverage comes from `npm run typecheck` (the renderer project already includes
`src/renderer/src/**`); no test-config or tsconfig change is needed for either new file.
