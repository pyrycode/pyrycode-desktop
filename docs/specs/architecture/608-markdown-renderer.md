## Context

Markdown syntax in assistant replies currently reaches the screen verbatim. This slice builds the
conversion — markdown source in, React elements out — and nothing else. Nothing on screen changes
because nothing imports it yet; #609 is the consumer, and the `blocked-by` edge is already in place.

The hard part of "render untrusted markup in Electron" is already closed at the process level
(sandbox, context isolation, the window-open allowlist, the navigation guard, and a CSP with no
`img-src`). What is *not* closed is the renderer-side question: what elements does markdown source
turn into? That is this slice.

## Design

### Library decision: `react-markdown`

Every claim below was verified empirically against `react-markdown@10.1.0` with `react@18.3.1` (the
repo's version) under `renderToStaticMarkup`, not recalled from documentation.

The string-emitting family (`marked`, `markdown-it`, `snarkdown`) is ruled out structurally: consuming
an HTML string requires `dangerouslySetInnerHTML`, which AC2 forbids. That leaves the
React-element-emitting candidates:

| Candidate | Packages added | Raw-HTML posture | Verdict |
|---|---|---|---|
| `react-markdown@10` | **85** | No HTML parser exists. Enabling HTML requires *adding* `rehype-raw` | **Chosen** |
| `markdown-to-jsx@9` | **1** (zero deps) | HTML parser present and **on by default**; suppressed by `disableParsingRawHTML: true` | Rejected |
| `marked-react@4` | 4 | `marked` lexer + a thin React bridge | Rejected |

`markdown-to-jsx` is by far the smaller supply-chain footprint and that is a real point in its favour,
especially given the repo has **no automated dependency gate** (`check:electron-digest` is #101's
BLAKE2s/BoringSSL parity check and vets nothing about dependencies). It is rejected on three
measured grounds:

1. **Capability-absent beats capability-disabled.** Its raw-HTML support is its headline feature,
   live by default. Verified: by default it turns `<b>bold</b>` into a real `<b>` element. A config
   regression that drops one boolean silently re-enables genuine HTML element construction. With
   `react-markdown`, the same regression is impossible without adding a new package to
   `package.json` — a visible, reviewable act.
2. **It puts untrusted text into an attribute.** It auto-slugs headings into `id` attributes
   (`# H1` → `<h1 id="h1">`). React escapes the value so it is inert, but it breaks this repo's
   stated invariant that daemon text lands in exactly one JSX *text* position and never an attribute.
3. **Its root element is unstable** — verified to emit bare text, `<span>`, or `<div>` depending on
   the source. #609 has to style a container; a root that changes shape with the message content is a
   downstream cost.

The 85 packages are the honest cost and the developer must state it in the PR. Mitigating context,
which also belongs in the PR: they are overwhelmingly the `micromark-*` / `mdast-util-*` /
`hast-util-*` micro-packages from one maintainer's (wooorm's) CommonMark toolchain, all MIT. The
*tarball* count is 85; the *distinct-maintainer* trust surface is roughly comparable to the
single-package alternative. That is the trade being made: a larger install surface bought in exchange
for the safety property being structural rather than configurational.

### Module shape

One new file — `src/renderer/src/screens/conversation/AssistantMarkdown.tsx`. It sits beside its
future consumer, matching `LogDataSection.tsx` / `RunConfigSections.tsx` / `BackgroundTaskPanel.tsx`.
No new directory.

```tsx
export function AssistantMarkdown({ text }: { text: string }): JSX.Element
```

A pure function of `text`: same input, same markup, no state, no effects, no store access. It renders
no wrapper element of its own — `react-markdown` v10 emits block elements directly (verified), so the
container and its class belong to #609.

This file is the **entire** security boundary for markdown rendering. The configuration below is not
incidental; it is the contract. Any future change to it is a security change.

### Configuration contract

| Setting | Value | Why |
|---|---|---|
| `rehypePlugins` | **absent** | `rehype-raw` is the only way to interpret HTML. Never add it. |
| `remarkPlugins` | **absent** | CommonMark covers all of AC1. `remark-gfm` would also manufacture anchors from bare URLs. |
| `skipHtml` | **not set** | See below — the trap. |
| `components.a` | render `children` only | AC3 |
| `components.img` | render `alt` only (`''` when absent) | AC4 |
| `components.code` | **not overridden** | See § Why `code` keeps its `language-*` class |

**The `skipHtml` trap.** It reads like the safety option and is the wrong choice here. Verified
behaviour on the fixture `Before <script>alert(1)</script> and <b>bold</b> after`:

- **Default (no `skipHtml`)** → `Before &lt;script&gt;alert(1)&lt;/script&gt; and &lt;b&gt;bold&lt;/b&gt; after` — escaped to visible characters.
- **`skipHtml: true`** → `Before alert(1) and bold after` — the tags are *deleted* and their text
  content silently promoted into the message.

Both satisfy AC2's "literal text or is dropped", but the default is correct on two counts: it matches
the existing bubble posture at `ConversationScreen.tsx:493` ("HTML inside a delta renders as visible
characters"), and it is the only one that preserves the `&lt;` / `&amp;` discriminator the tests need
to tell "escaped" from "absent". Leave it unset.

**The two overrides must render nothing but their one value.** No `{...props}` spread anywhere in
either component — a spread reintroduces `href` / `src` and silently defeats AC3 and AC4. This is the
single most likely way for this module to regress; call it out in a code comment.

Both overrides are load-bearing and neither falls out of "raw HTML disabled". Verified defaults
*without* them: `[click me](https://example.com)` → `<a href="https://example.com">click me</a>`, and
`![alt text](https://evil.example/pixel.png)` → `<img src="https://evil.example/pixel.png" alt="alt text"/>`.
With them: `<p>see click me and evil</p>` and `<p>alt text</p>`.

Note that `react-markdown`'s built-in `urlTransform` already blanks a `javascript:` href
(verified: `href=""`). The design does **not** rely on it — no anchor is produced at all, so no URL
reaches the DOM by any path. Stating this so #610, which opens the `http:`/`https:` allowlist, knows
`urlTransform` is the mechanism it will be re-enabling rather than inventing.

### Why `code` keeps its `language-*` class

The obvious hardening move is to override `code` and drop its `className`, since the fence info string
is untrusted daemon text landing in an attribute. **Do not do this.** Figma `16:47` specifies a
language label ("typescript") on the code-block header bar, and `react-markdown`'s
`class="language-typescript"` is the only carrier for that value — stripping it would delete the data
#609 needs and force #609 to re-parse the source.

Keeping it is safe on inspection: the value is React-escaped as an attribute (inert), and the
mandatory `language-` prefix makes collision with an app CSS class structurally impossible. Verified
with a hostile info string — ` ```<script>alert(1)</script> ` renders as `<pre><code>` with the class
omitted entirely by the parser, not injected.

### Verified construct coverage (AC1)

All confirmed rendering correctly: `#`/`##` and setext headings → `<h1>`/`<h2>`; `**bold**` →
`<strong>`; `*ital*` → `<em>`; `` `code` `` → `<code>`; fenced blocks → `<pre><code>`; `1.` → `<ol>`
(with `start="5"` when the list starts at 5 — a numeric attribute, harmless); `-` → `<ul>` with
correct nesting; `>` → `<blockquote>`; paragraphs → `<p>`; and **both** hard-break forms (trailing
two spaces, and a trailing backslash) → `<br/>`.

Out of scope by design, and correct: GFM tables render as literal text, and bare URLs are **not**
auto-linked (both require `remark-gfm`).

### Where the dependency goes

Put `react-markdown` in **`dependencies`**, matching `zustand` — the repo's own precedent for a
renderer-only runtime library, and consistent with the ticket's "four runtime dependencies" framing
that the PR justification is written against.

Noted for the PR reader so it is visible as a considered choice rather than an oversight: `react`
itself sits in `devDependencies` because Vite inlines the renderer bundle, so a renderer-only library
technically need not ship in a packaged app's `node_modules`. The repo has no packaging config today,
so this is inert either way; consistency with `zustand` wins.

No `tsconfig` change, no `vitest.config.ts` change, no `electron.vite.config.ts` change. Confirmed:
`moduleResolution: "Bundler"` resolves the ESM-only package and its types, and `react-markdown@10`
peers on `react >= 18` — verified working against the repo's exact `18.3.1`.

## State + concurrency model

None. The component holds no state, subscribes to nothing, launches no async work, and touches no
store. Parsing is synchronous and happens during render.

**Handoff to #609, not a change here:** because parsing runs on every render, wiring this into the
message list re-parses every settled message whenever the timeline re-renders — which during
streaming is many times per second. The component is a pure function of `text`, so `React.memo` at
the #609 seam is sufficient and requires no change to this module. Deliberately not added here: it
would be an untestable production change in a dormant module, and #609 owns the render site where the
cost is actually measurable.

## Error handling

No failure modes to surface. `react-markdown` has no invalid input — CommonMark is total, and any
byte sequence is a valid document. Empty string renders empty. There is no result type, no error
branch, and nothing for the UI to show; do not add a try/catch or an error boundary for a failure
that cannot occur.

## Testing strategy

One new file, `src/renderer/src/screens/conversation/AssistantMarkdown.test.tsx`, cloning
`ArchivedCountRow.test.tsx`'s idiom: a local `render(md: string): string` helper wrapping
`renderToStaticMarkup`, then substring assertions. Server rendering covers every criterion in this
slice.

**Every negative assertion in this file must be paired with a positive one in the same case.**
`not.toContain('<script')`, `not.toContain('<a ')` and `not.toContain('<img')` all pass against the
empty string. The expected markup for each case below is already known from the verification runs
above, so a case that renders nothing is a bug, not a pass.

Scenarios:

1. **Block constructs (AC1)** — one fixture covering h1, h2, bold, italic, inline code, fenced code,
   ordered list, unordered list, blockquote. Assert each expected tag is present.
2. **Hard line breaks (AC1)** — trailing-two-spaces and trailing-backslash fixtures both yield a
   `<br` , with both lines' text present.
3. **Raw HTML is escaped, not interpreted (AC2)** — fixture `x <img src=q onerror=alert(1)> y`.
   Positive: contains `&lt;img` **and** the surrounding `y`. Negative: no `<img`, no `onerror=` as
   markup.
4. **Script tags likewise (AC2)** — positive: contains `&lt;script&gt;`. Negative: no `<script`.
5. **Ampersand escaping (AC2)** — a fixture containing a bare `&` renders `&amp;`, proving the path
   escapes rather than deletes.
6. **Link renders as its text, no anchor (AC3)** — `[click me](https://example.com)`. Positive:
   contains `click me`. Negative: no `<a `, no `href`, no `example.com`.
7. **Dangerous scheme, same treatment (AC3)** — `[evil](javascript:alert(1))`. Positive: contains
   `evil`. Negative: no `<a`, no `javascript:`.
8. **Reference-style link (AC3)** — the indirect-href path, `[label][ref]` with a `[ref]:` definition.
   Positive: contains `label`. Negative: no `<a`, and the definition's URL does not appear.
9. **Autolink (AC3)** — `<https://example.com>`. Positive: the URL renders as visible text. Negative:
   no `<a`.
10. **Image renders as alt text (AC4)** — `![alt text](https://evil.example/pixel.png)`. Positive:
    contains `alt text`. Negative: no `<img`, no `evil.example`, no `src=`.
11. **Image with empty alt (AC4)** — `![](...)` beside a sibling sentence. Positive: the sibling
    sentence renders. Negative: no `<img`, no URL.
12. **Fenced code keeps its language class** — ```` ```typescript ```` yields
    `class="language-typescript"`. This is the #609 handoff guard; without it, a future
    "simplification" that strips the class breaks the Figma `16:47` label with no test failing.

**AC5 (ships dormant)** is not a unit test — it is a grep the developer runs and the reviewer
repeats:

```bash
grep -rn "AssistantMarkdown" src/ | grep -v "src/renderer/src/screens/conversation/AssistantMarkdown"
```

Expected: no output. Also confirm `git diff --stat` touches only the two new files plus
`package.json` / `package-lock.json` — in particular `src/renderer/index.html` must be unchanged
(AC4) and `conversation.css` must be unchanged (that is #609's).

Gates: `npm test`, `npm run typecheck`, `npm run build`.

## Traps

- **Do not set `skipHtml`.** It looks like the safe option, deletes content, and destroys the test
  discriminator. See § Configuration contract.
- **Do not spread props in the `a` / `img` overrides.** `{...props}` puts `href` / `src` straight
  back and both ACs regress silently — the visible text still renders, so a carelessly-written test
  keeps passing.
- **Do not strip the `language-*` class.** It looks like hardening; it deletes the data #609 needs
  for the Figma `16:47` label.
- **Do not add `remark-gfm`** "for completeness". It is not in AC1, and its bare-URL autolinking
  manufactures exactly the anchors AC3 forbids.
- **Do not edit `src/renderer/index.html`.** The CSP is correct as-is; AC4 asserts it is unchanged.
  Images fail via the `default-src 'self'` fallback, which is intended.
- **Do not edit `conversation.css` or `ConversationScreen.tsx`.** Both are #609's. This module has no
  importer when you are done — that is the point, not an oversight.
- The ticket body's claim that Figma specifies no markdown treatment is **wrong for fenced code**.
  See § Design source.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings. The boundary is explicit and singular: `AssistantMarkdown.tsx`
  is the one place daemon-supplied text becomes markup, and its whole surface is one `text: string`
  prop. Upstream, the string is already the untrusted daemon text rendered today at
  `ConversationScreen.tsx:499`; this slice does not widen what crosses. Downstream, callers receive
  React elements, never HTML strings — so no consumer can be tricked into a sink. The operator's
  2026-08-20 decision that daemon text may render as content is the documented "trusted" definition,
  and it is scoped to message content, not chrome.
- **[Electron attack surface]** No findings, and nothing is rebuilt or weakened. `sandbox: true` +
  `contextIsolation: true` (`src/main/index.ts:46-47`), the http/https-only
  `setWindowOpenHandler` → `shell.openExternal` (`:56-70`), and the same-document `will-navigate`
  guard (`:79-90`) are all untouched. This slice adds no IPC channel, no `contextBridge` surface, and
  no main-process code at all. Critically, it produces **no anchor element**, so no click target
  reaches those guards in the first place — the deny-first sequencing means the repo is never in a
  state where an unvetted href is in the DOM. A `javascript:` URL is the reason this ordering
  matters: it executes in the document rather than navigating it, so `will-navigate` would never see
  it. #610 opens the allowlist and must do its scheme check renderer-side, at render time.
- **[Content injection / XSS]** No findings — this is the category the slice exists to close. No
  `dangerouslySetInnerHTML` and no `innerHTML` is introduced; `src/` stays free of both (today all 9
  occurrences of the string are comments asserting its absence). Verified adversarially rather than
  assumed: `<script>`, `<img onerror=>`, and HTML comments all render as escaped text, and inline
  code containing `<script>` renders as `<code>&lt;script&gt;</code>`. The residual risk is
  configuration drift, addressed structurally — interpreting HTML requires adding `rehype-raw` to
  `package.json`, not flipping a boolean. That property is the stated reason `markdown-to-jsx` was
  rejected despite its far smaller dependency tree.
- **[Untrusted data in attributes]** One accepted residual, documented rather than silently taken.
  `<code class="language-*">` and `<ol start="N">` are the only attributes on this path carrying
  source-derived values. Both are React-escaped (inert); the `language-` prefix makes CSS-class
  collision structurally impossible, and `start` is numeric. The class is deliberately retained
  because Figma `16:47` needs it — see § Why `code` keeps its `language-*` class. Every genuinely
  dangerous attribute (`href`, `src`) is eliminated at the element level, not sanitised.
- **[Network & I/O]** No findings. The module makes no network request and produces no element that
  can make one — that is AC4, and it is enforced at the element level (no `<img>` is created), not
  merely at the policy level. The CSP's absent `img-src` falling back to `default-src 'self'` remains
  as the independent second layer, and it is deterministic policy rather than a second stochastic
  check — different fabric, correctly. No `img-src` is added and `default-src` is not widened.
- **[Supply chain]** SHOULD FIX, and it is the one real cost of this design. 85 packages enter the
  tree with **no automated gate** in the repo to vet them — `check:electron-digest` is #101's
  BLAKE2s/BoringSSL parity check and is not wired into CI. The justification is a human PR read or
  nothing, so the developer must state the choice, the package count, and the rejected alternative in
  the PR body. Not a MUST FIX: it is the ticket's explicitly-anticipated trade, the alternatives were
  measured rather than assumed, and the safety property bought is structural.
- **[Denial of service]** No findings that gate this slice. A pathological document (deeply nested
  lists, a multi-megabyte reply) costs parse time on the render thread, and re-parsing on every
  render makes that cost recurrent. Bounded in practice by the daemon's own message sizing, and
  `micromark` is a fuzz-tested CommonMark parser rather than a backtracking regex engine, so
  catastrophic blowup is not the expected failure shape. The mitigation seam (`React.memo`) is named
  in § State + concurrency model and belongs to #609, where the render site makes it measurable.
- **[Tokens / secrets]**, **[File & storage]**, **[Cryptography]**, **[Concurrency]** — not
  applicable, by design rather than by omission: this module is a pure synchronous function of one
  string. It opens no file, holds no credential, performs no comparison against a secret, and starts
  no async work, so there is no lifecycle to own or cancel and no shared state to race on.
- **[Threat model alignment]** The applicable threat is **hostile daemon response** — text
  impersonating markup. It is addressed head-on: the response is parsed by a CommonMark parser with
  no HTML capability, and the two element types that could reach out to the network or to a
  navigation handler are suppressed by explicit overrides. **Renderer compromise reaching the
  transport** is unaffected: no main-process code changes, and process isolation is untouched.
  Malicious relay and token theft are out of scope for a renderer-side pure function.
