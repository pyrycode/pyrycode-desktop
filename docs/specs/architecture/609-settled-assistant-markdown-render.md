## Context

`AssistantMarkdown` (#608) converts markdown source to React elements and ships dormant — grep confirms
it still has no importer outside its own test. This slice is its first and only consumer: it forks the
`assistantText` arm so a settled message renders through it, gives the output a container with the
mock's block rhythm, and makes fenced code wrap. Nothing else about the thread changes.

The settled signal already exists (`ConversationScreen.tsx:465`) and costs nothing to reuse. The daemon
emits one event per complete content block, and the store coalesces consecutive deltas per turn, so a
settled item's text is a whole document — the reason "render only when complete" is close to free rather
than a new state machine.

## Design

### The fork in the `assistantText` arm

The arm becomes two renderings of the same bubble element, selected on the `inProgress` prop that is
already there:

```tsx
// in-progress  → today's markup verbatim: {item.text} then the cursor span
// settled      → <div className="bubble__markdown"><AssistantMarkdown text={item.text} /></div>
```

The `<div className="message-row message-row--daemon">` wrapper, the bubble's `data-thread-role`, the
cursor markup and the `default`-free switch are all unchanged. Compute the bubble's class string above
the `return` in the `toolCall` arm's `rowClass` idiom (`:528-530`) rather than interpolating inside JSX,
so the two class strings are readable side by side.

`AssistantMarkdown` emits no wrapper of its own (its `:52-55` docstring), so without this container the
markdown blocks would be direct children of `.bubble` and there would be nothing to hang the gap on.

### `bubble--assistant-text` becomes conditional on `inProgress`

The settled bubble carries `bubble bubble--daemon`; the in-progress bubble carries
`bubble bubble--daemon bubble--assistant-text` exactly as today.

This is the design decision AC3 turns on, so it is worth stating why it is not the obvious alternative.
#608's handoff note anticipated a `white-space: normal` **neutralisation** on the container, leaving
`pre-wrap` declared on the bubble and then undone one level down. Both approaches satisfy AC3; the
conditional modifier is better on three counts:

1. It makes AC3 true **by construction** rather than by override — the same argument #607's own comment
   makes (`conversation.css:327-333`: a rule "provably cannot reach an element that does not carry the
   class"). A neutralisation has to be re-verified every time a new element type appears inside the
   container; an absent declaration does not.
2. It removes a latent hazard rather than adding one. `pre-wrap` left live on a bubble whose only child
   is a container means any stray text node — a JSX whitespace slip of exactly the kind
   `ConversationScreen.test.tsx:376` exists to catch — renders as a visible blank.
3. It costs one fewer CSS declaration and makes the modifier's name true again: it marks the plain-text
   streaming tail, which after this ticket is the only place #607's rule does any work.

**Do not rename the modifier.** "`--assistant-text` now means the in-progress tail" is a real naming
drift, but renaming touches four files for no behavioural gain. Record it in the CSS comment instead;
see § Open questions.

Update #607's rationale comment (`conversation.css:317-333`) in the same edit. It currently claims the
rule governs "the assistant reply's whitespace treatment", which this ticket makes false — the rule now
governs only the still-growing tail. A stale comment here is worse than usual because it is the exact
comment a future reader consults before touching whitespace.

### The block rhythm (AC4)

Container rule, all tokens, no literal:

```css
.bubble__markdown { display: flex; flex-direction: column; gap: var(--space-2); }
.bubble__markdown > * { margin-block: 0; }
```

**Correcting the ticket's Technical Notes:** the gap is *not* "one rule on the container rather than
per-element margins". It is one rule **plus** a margin reset, because `src/renderer/src/index.css` resets
only `body` — every UA block margin is live and adds to the gap, so `<p>` neighbours would sit ~24px
apart, not 8px. The gap approach is still clearly right (two rules, not one per element type, and flex
`gap` applies strictly *between* items so "no extra space at the first and last block" is free rather
than a `:first-child` / `:last-child` pair). But the reset is not optional and the e2e assertion in
§ Testing strategy is specifically shaped to catch its absence.

`margin-block`, not `margin` — zero only the axis that conflicts with the gap. `margin-inline` is
`<blockquote>`'s 40px indent and is the only thing making a blockquote visually distinct before #624
lands; a blanket `margin: 0` would flatten it to a paragraph. Direct children only: a `<p>` nested
inside a `<blockquote>` or a loose `<li>` keeps its UA margins, which is #624's to tune and not a
rhythm violation at the container level.

Do **not** set `align-items`. Figma's `items-start` + `w-full` children is precisely CSS flex's default
`stretch`, so the default already matches the mock.

### Code wrapping (AC3)

```css
.bubble__markdown pre { white-space: pre-wrap; }
```

`<pre>`'s UA `white-space: pre` is a declaration on the element, and a declaration always beats an
inherited value regardless of origin — so `pre` keeps `pre` unless overridden here, and a long line
would spill past the bubble's `max-width`. `word-break: break-word` is deliberately **not** restated:
it is inherited from `.bubble:298`, and #607 set the precedent of not restating it
(`conversation.css:324-325`).

No `max-height`, no `overflow`. The thread is its own scroll region (`.conversation__thread`,
`conversation.css:231-241`, `flex: 1 1 auto; min-height: 0; overflow-y: auto`) with `.composer` as a
**sibling**, so a tall bubble lengthens the thread and cannot push the composer anywhere. Bounding the
height here would defend a failure mode that cannot occur.

**Known remedy, do not pre-apply.** A flex item's default `min-width: auto` is computed from min-content
width, and the legacy `word-break: break-word` does not reduce min-content the way `overflow-wrap:
anywhere` does — so it is *possible* the code block refuses to shrink and overflows. Write the e2e
overflow assertion first (repo convention is test-first), observe, and add `min-width: 0` to the `pre`
rule **only if it actually fails**. Do not ship it speculatively.

### What this slice does not style

`<pre><code>` gets UA monospace, `<h1>` gets UA sizing, `<ul>` gets UA indentation — enough for AC1's
"appear as markup rather than as literal syntax" without this ticket making any type decision. The code
panel's fill / border / radius / header bar is #623; the heading, list, blockquote and inline-code type
scale is #624. Adding either here is scope creep into a ticket that already has a spec waiting.

### `React.memo`: declined, deliberately

#608 handed this decision here. **Do not add it.** Parsing does run on every render, and during
streaming the timeline re-renders per delta, so every settled message re-parses. Three reasons it still
does not ship in this slice:

1. **It would be untestable.** Renderer tests are `renderToStaticMarkup` in vitest's `node` environment —
   there is no tier in this repo that can observe a skipped re-render. It would ship unverified.
2. **No failure has been observed.** `micromark` parses a chat-sized document in microseconds; the cost
   is real but not measured to matter. Shipping a defence for an unobserved failure mode is exactly what
   this pipeline defers.
3. **It matches the house idiom.** `React.memo` appears nowhere in `src/`, and `ConversationScreen.tsx`
   twice *declines* memoization with a stated reason (`:374`, `:393`).

State the decision and the seam in a comment, in that same declining register: if it is ever needed, the
fix is a memoized wrapper component (not `useMemo` — hooks cannot be called from inside `TimelineRow`'s
switch), keyed on `text`, which is a pure function of its prop.

## State + concurrency model

None. No store slice, no new state, no effect, no async work, no subscription, no cancellation surface.
`inProgress` is derived at render from array position and item kind (`:465`) and is already computed.
Parsing is synchronous during render.

## Error handling

No failure modes. CommonMark is total — any byte sequence is a valid document, and an empty string
renders empty. There is no result type, no reject branch and nothing for the UI to surface. Do not add a
try/catch or an error boundary for a failure that cannot occur.

## Testing strategy

Gates: `npm test`, `npm run typecheck`, `npm run build`, plus the reworked Playwright spec.

### Unit — `ConversationScreen.test.tsx`

**Two existing cases assert the old settled rendering and will fail. Both must be re-pointed, and
neither is being weakened — #607's claim genuinely narrowed to the tail.**

- `:376-389` *"renders the assistant text flush against its bubble tag and its cursor"* — its settled
  half asserts `data-thread-role="assistant">settled reply</div>`. The settled bubble now opens with the
  container. Re-point that half at the container opening flush against the bubble tag; leave the
  in-progress half exactly as it is.
- `:391-400` *"carries newlines and space runs into the markup verbatim"* — its fixture is settled and
  contains a four-space-indented line, which CommonMark reads as an **indented code block**. Re-point the
  whole case at an **in-progress** item, where "React escapes markup characters, never whitespace" is
  still exactly true. The assertion shape changes from `>${text}</div>` to text-then-cursor, because the
  cursor now follows.

The other five assistant-bubble cases (`:109`, `:119`, `:125`, `:132`, `:138`, `:365`) hold unchanged —
each either uses a single item (which is therefore the in-progress tail) or asserts only ordering and
cursor placement. Verify rather than assume.

New scenarios, as bullet-pointed cases in the file's existing idiom:

- **AC1 — a settled bubble renders markdown markup.** One fixture covering a heading, bold, inline code,
  a fenced block, a list and a blockquote. Positive: each expected tag present. Negative: the literal
  syntax (`**`, `# `) absent. Pair every negative with a positive — `not.toContain` passes against the
  empty string.
- **AC2 — the in-progress tail is never markdown-rendered.** The same markdown source as the tail item:
  the literal syntax renders as visible characters, no `<strong>`, and the cursor is present.
- **AC2 — the container appears only on settled bubbles.** A settled item plus an in-progress tail:
  exactly one `bubble__markdown`, on the first; exactly one `bubble--assistant-text`, on the tail.
- **AC5 — the escaping posture survives the new path.** `<b>hi</b>` in a **settled** item still renders
  `&lt;b&gt;`, never a live `<b>`. `:119` covers the in-progress path today; this extends it to the
  markdown path and is the security regression guard at the consumer seam.
- **AC5 — nothing else gains the container.** A user bubble, a tool row, a session boundary and the four
  daemon-bubble affordances carry no `bubble__markdown`. Extend the existing `:402` case rather than
  writing a new one if that reads better.

**Fixture trap.** Build every multi-line markdown fixture with `[...].join('\n')`, never an indented
template literal. A template literal indented to match the surrounding code puts four or more leading
spaces on each line, which CommonMark reads as an indented code block — the test then passes or fails
for a reason unrelated to what it claims. (Same lesson as #608's hard-break fixtures.) Keep apostrophes
out of fixtures: `renderToStaticMarkup` escapes `'` → `&#x27;`.

### e2e — rework `e2e/assistant-whitespace.spec.ts` in place

**This file must change; it is not optional.** Its AC2 assertion (`spaceRun.width > control.width`,
`:203`) measures a settled bubble and is designed so that "equal widths IS the broken state" — after
this ticket, equal widths is the *correct* state. Its `expect(control.whiteSpace).toBe('pre-wrap')`
(`:194`) also reads a settled bubble.

Rework in place rather than adding a sibling spec: the file's subject ("assistant bubble whitespace") is
unchanged, a second spec would duplicate ~120 lines of frame-builder harness, and the invalidated
assertions cannot simply be left behind.

**Stream shape.** Keep the multi-turn `assistant_delta` + `turn_end` builders, but leave the **last**
turn open — a delta with no `turn_end` — so the tail bubble is the in-progress one and every earlier
bubble is settled. Adjust the settle gate: it currently waits on the last bubble's exact text, which now
includes the cursor glyph; wait on a settled bubble's text instead.

The thinking and stall affordances will appear while the tail turn is open. Confirmed non-perturbing:
`data-thread-role="assistant"` is carried **only** by the assistant bubble (`ConversationScreen.tsx:499`),
so the measured locator is unaffected by either.

Scenarios — every one a computed style or a geometric measure, never `toHaveText` (see the file's own
`:16-21` vacuity warning):

- **#607's rule still governs the tail.** Computed `white-space` is `pre-wrap` on the in-progress bubble
  and **not** `pre-wrap` inside a settled bubble's container. Plus one geometric half, so this is not
  purely a style assertion: a tail whose text contains a blank line stands more than one line box taller
  than a settled single-line bubble (both are `.bubble`, so padding cancels; the cursor is inline and
  adds no height).
- **AC3 — markdown owns whitespace inside the container.** Two settled bubbles whose sources differ
  *only* in collapsible whitespace — one with a long run of spaces or a soft-wrapping newline, one with
  the single-space equivalent — render at **equal** width and height within the existing
  `SUBPIXEL_TOLERANCE_PX`. Under the old rendering they differed; that is what makes this
  non-vacuous, and it is the deliberate inverse of the assertion it replaces.
- **AC3 — code wraps within the measure.** A settled bubble containing a fenced block with a ~200-char
  unbroken token: computed `white-space` on the `<pre>` is `pre-wrap`, the `pre`'s `scrollWidth` does not
  exceed its `clientWidth` beyond tolerance, and the thread grows no horizontal scrollbar. Keep the
  thread check — it is the over-correction guard the original spec carried.
- **AC4 — the 8px rhythm.** A settled bubble with three blocks. Assert **both**: the container's computed
  `row-gap` equals the computed value of `--space-2` (read the custom property rather than writing `8`),
  **and** the measured distance from each block's bottom to the next block's top equals that same value.
  The second assertion is the load-bearing one — `row-gap` alone reads correct even when UA margins add
  16px on top of it, so a `row-gap`-only test would pass with the margin reset missing entirely. Also
  assert the first block's top and the last block's bottom sit flush with the container's content box.

Before committing, run the mutation table against the new assertions — the discipline that caught a
vacuous positive in #608. For each of: delete the margin reset, delete the `pre` rule, drop the
conditional on the modifier, render the in-progress tail through markdown — name which assertion fails.
If any mutation fails nothing, that assertion is not pulling its weight.

## Traps

- **`e2e/assistant-whitespace.spec.ts` will fail if you do not touch it.** It is not collateral damage;
  its subject moved. Read it before you write any CSS.
- **Two unit cases at `:376` and `:391` will fail** for the same reason. Re-point them at the
  in-progress tail; do not delete them and do not weaken them into tautologies.
- **The gap does not remove the need for a margin reset.** There is no global element reset in this repo
  (`index.css` is 13 lines). Verify by reading it, not by assuming a reset exists.
- **`.screen-snapshot__screen` is the wrong precedent.** `white-space: pre` + `max-height` + `overflow`
  is right for a terminal grid that must not reflow, and wrong for source code in a chat bubble.
- **Do not bound the bubble's height "so it never pushes the composer off-screen."** Structurally
  impossible — the thread is its own scroll region and the composer is a sibling.
- **Do not restate `word-break: break-word`** on the code rule; it is inherited from `.bubble:298`.
- **Do not use `margin: 0`** on the container's children — it flattens `<blockquote>`'s indent, which is
  its only visual distinction until #624. `margin-block: 0`.
- **Do not add `min-width: 0`** to the `pre` rule pre-emptively. Add it only if the overflow assertion
  actually fails.
- **Do not edit `AssistantMarkdown.tsx`.** Its configuration is #608's security contract — no
  `rehypePlugins`, no `remarkPlugins`, no `skipHtml`, no `{...props}` in the `a` / `img` overrides, and
  the `language-*` class stays (it is #623's only carrier for the Figma `16:47` label).
- **Do not add `remark-gfm`, `rehype-raw`, or any dependency.** This ticket adds none.
- **Do not touch the CSP (`src/renderer/index.html:7`) or the main-process guards
  (`src/main/index.ts:56`, `:79`).** A remote image failing to load is the intended outcome.
- **Do not style the code panel or the type scale.** #623 and #624 respectively, both already scoped.
- **Do not add link handling.** Links stay deny-first exactly as #608 left them; the `http:` / `https:`
  allowlist and open-in-browser behaviour are #610, which is blocked on this ticket.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings; the boundary does not move. Daemon-supplied `item.text` is already
  rendered at `ConversationScreen.tsx:499` today and this ticket changes only *how* the same string is
  turned into elements, not what crosses or where. The boundary stays singular and explicit —
  `AssistantMarkdown.tsx` is the one place that string becomes markup, its whole surface is one
  `text: string` prop, and it returns React elements rather than an HTML string, so no consumer can be
  handed something it could feed to a sink. The operator's 2026-08-20 decision that daemon text may
  render as content is the documented definition of "trusted" here, and it is scoped to message content;
  this ticket does not extend it to chrome. The one genuinely new question — *can the in-progress path
  and the settled path disagree about escaping?* — is answered by a dedicated unit case (settled
  `<b>hi</b>` still renders `&lt;b&gt;`), because a fork is exactly where two paths drift apart.
- **[Content injection / XSS]** No findings, and this is the category the fork could plausibly have
  reopened. No `dangerouslySetInnerHTML` and no `innerHTML` is introduced; both remain absent from
  `src/` outside comments asserting their absence. The container is a plain `<div>` with a static
  `className` — no interpolation of daemon text into a class, an `id`, a `style` or any other attribute.
  The settled path inherits #608's verified posture unchanged (`<script>`, `<img onerror=>` and HTML
  comments all render as escaped text), and the in-progress path is byte-identical to today's. The
  residual risk is drift in `AssistantMarkdown.tsx`'s configuration, which this spec names as
  off-limits and which #608 made structural: interpreting HTML requires *adding* `rehype-raw` to
  `package.json`, a visible reviewable act, not flipping a boolean.
- **[Untrusted data in attributes]** No new findings; no new attribute carries source-derived data. The
  two pre-existing ones (`<code class="language-*">`, `<ol start="N">`) are unchanged and were accepted
  in #608 — React-escaped and therefore inert, the mandatory `language-` prefix making collision with an
  app class structurally impossible. Worth stating because this ticket is the first to *style* by
  descendant selector: `.bubble__markdown pre` matches on element type only, never on the untrusted
  class, so no daemon-supplied string participates in selector matching.
- **[Electron attack surface]** No findings; nothing is rebuilt, widened or weakened. `sandbox: true` +
  `contextIsolation: true` (`src/main/index.ts:43-47`), the http/https-only `setWindowOpenHandler` →
  `shell.openExternal` (`:56-70`), and the same-document `will-navigate` guard (`:79-90`) are untouched,
  as is the CSP (`src/renderer/index.html:7`). This ticket adds no IPC channel, no `contextBridge`
  surface and no main-process code. Critically the deny-first sequencing is preserved: the settled path
  still produces **no anchor and no `<img>`**, so no click target and no subresource URL reaches those
  guards in the first place. That ordering matters specifically because a `javascript:` URL executes in
  the document rather than navigating it and `will-navigate` would never see it — which is why #610 must
  do its scheme check renderer-side, at render time.
- **[Network & I/O]** No findings. The module fetches nothing and this ticket produces no element that
  can fetch — `img` is suppressed at the element level, so the absent `img-src` in the CSP remains an
  independent deterministic second layer rather than the only one. No `img-src` is added, `default-src`
  is not widened, and a remote image failing to load stays the intended tracking-pixel defence.
- **[Denial of service]** SHOULD FIX, and it is the one place this ticket's choices differ from #608's
  analysis. Wiring the parser into the message list makes parse cost recurrent: every settled message
  re-parses on every timeline re-render, and during streaming that is many times per second, scaling with
  thread length. The spec **declines** `React.memo` (§ `React.memo`: declined) on the grounds that no
  failure has been observed, that `micromark` is a fuzz-tested non-backtracking parser rather than a
  regex engine, that chat-sized documents parse in microseconds, and — decisively — that this repo has no
  test tier that could observe a skipped re-render, so it would ship unverified. Not a MUST FIX: the
  worst case is a laggy window on the operator's own machine, not a security boundary failure, and it is
  bounded by the daemon's own message sizing. The mitigation seam is named in the spec and in a code
  comment so the fix is one small component away if it is ever measured.
- **[Supply chain]** No findings and no change. This ticket adds zero dependencies; `package.json` and
  `package-lock.json` must be untouched in the diff, which is a reviewable one-line check. #608's 79 net
  new packages are already in the tree and are not re-litigated here.
- **[Error messages, logs, telemetry]** No findings. This ticket adds no log call, no error path and no
  diagnostic string. Nothing daemon-supplied is echoed into a message, and the e2e assertions read
  computed styles, geometry and counts rather than content — so a failure diagnostic cannot serialise
  reply text, a conversation id, a token or a key.
- **[Concurrency]** Not applicable by design rather than omission: the change is a synchronous render
  fork with no async task, no timer, no listener and no subscription, so there is no lifecycle to own or
  cancel and no shared state to race on. The one shared-state question a fork could raise — whether a
  message can be observed mid-transition between the two renderings — is answered structurally: both
  renderings are derived from the same `inProgress` boolean within a single render pass, so no
  intermediate state exists.
- **[Tokens / secrets]**, **[File & storage]**, **[Cryptography]** — not applicable. Renderer-only view
  code touching one string prop: it opens no file, holds no credential, compares nothing against a
  secret, and performs no cryptographic operation. Process placement is unchanged; nothing moves toward
  the renderer.
- **[Threat model alignment]** The applicable threat is **hostile daemon response** — reply text
  impersonating markup, or shaped to be pathological to parse. The first is addressed head-on and now
  tested on *both* branches of the fork; the second is the DoS finding above, accepted with reasons.
  **Renderer compromise reaching the transport** is unaffected — no main-process code changes and
  process isolation is untouched. **Malicious relay** and **token theft from disk** are out of scope for
  a renderer-side render fork and are unaffected by it. Link navigation is explicitly deferred to
  **#610**, which is blocked on this ticket and inherits a repo state in which no unvetted href has ever
  been in the DOM.
