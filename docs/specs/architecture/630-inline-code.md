## Context

`.bubble__markdown code` is the last construct in the settled reply still typed entirely by the UA
stylesheet. Measured in the shipping renderer today (probe A below): an inline `<code>` computes to
`font-family: monospace` — the bare generic, resolving to the platform's default fixed face — and takes no
fill, no radius and no padding. Its only signal is the family, which is exactly what AC1 calls
insufficient.

The trap is #623's: react-markdown routes a fence's contents through `<code>` too, and a **languageless**
fence's `<code>` carries no class at all, making it attribute-identical to inline code. Only ancestry
discriminates.

## Decision 1 — the exclusion selector

**Use the complex-`:not()` form.** Both forms were probed in the shipping renderer and both correctly
leave a languaged fence *and* a languageless fence untouched (probe C). The tiebreak is failure direction:

| form | says | if a future ticket nests the `<code>` deeper inside `.code-block__body` |
|---|---|---|
| `code:not(.code-block__body code)` | not **inside** a fenced body | still excluded — **fails safe** |
| `:not(.code-block__body) > code` | whose **parent** is not the fenced body | matches — **fails open**, paints inline chrome inside the fence |

Syntax highlighting is the concrete future that does this (a highlighter wraps fence content in spans).
AC3 is the trap this whole ticket exists around, so the form that cannot regress into it wins.

Note for the reviewer: `:not()` takes the specificity of its argument, so the rule computes to `(0,2,2)`
— higher than #623's `.code-block__body code` at `(0,2,0)`. That is a consequence, not a weapon: the two
selectors match **disjoint** element sets by construction, so they never compete and source order between
them is irrelevant. The file's nine existing `:not()` uses are all `:not(:disabled)`; a complex argument
is new here, verified working in probe C.

## Decision 2 — the size (the ticket's flagged decision)

**Declare no `font-size`.** Inline code takes its container's step, which in every container inside
`.bubble__markdown` is already a scale token: body-medium from `.bubble` in prose, and #628's
headline-small / title-large / title-medium / label-large in `h1`–`h6`. Measured: `14px` in a `<p>`,
`24px` in an `<h1>`, each equal to its container's token (probe D). AC1's "at a size taken from the type
scale" is therefore satisfied structurally *and asserted in two different containers* by the e2e test
below — this is a tested property, not a skipped criterion. #628's precedent: two of its five criteria
needed no new code.

Three findings killed the body-small alternative the ticket floats:

1. **The quartet discipline forbids it.** `conversation.css` has **67** rules declaring the full
   size/line-height/letter-spacing/weight quartet and **zero** declaring `font-size` alone (the one
   partial, `.unrecognized-row__raw`, still carries `line-height`). `.code-block__body` takes the whole
   body-small quartet because it is a *block* and owns its line box. An inline run can take only the size
   — the other three belong to the line it sits in — so "reuse `.code-block__body`'s step" does not
   transfer. A lone `font-size` is a size literal wearing a token's name.
2. **It breaks headings, and not only visually.** With `font-size: var(--text-body-small-size)`, a
   `<code>` in an `<h1>` renders at 12px inside 24px prose *and makes the heading's block 4px taller*
   (33px → 37px measured, probe B) — a smaller font producing a bigger box. AC2 forbids a per-context
   override, so this cannot be patched for headings only. At the container's own step, every block height
   in the reply is **identical to today** (probe B, `noSize` row).
3. **The optical premise is uncalibratable, and here it is wrong-signed.** "Mono looks bigger, step it
   down" assumes a known face. `--font-mono` is not bundled (`tokens.css:41-43` records this for
   `--font-sans`; the same self-only CSP applies) and resolves per platform. Measured at 14px on the e2e
   runner: sans x-height **7.37px**, the resolved mono **6.32px** — mono is already 86% of the prose, and
   body-small would take it to 73%. Yet `Menlo` on the same machine measures **7.66px**, *larger* than the
   sans. A 21% swing in x-height for the same declaration is not something a fixed step can correct.

`font-size: inherit` was considered and rejected: it computes identically (probe B) and would restate an
inherited value, which this file has now declined three times (#607's `word-break`, followed by #623 and
#628).

## Design

One rule, appended after #623's `.code-block__body, .code-block__body code` pair — the file's own
convention (each ticket appends where its argument reads, and this rule's whole substance is "everything
the rule above does not cover").

```css
.bubble__markdown code:not(.code-block__body code) {
  padding-inline: var(--space-1);
  border-radius: var(--radius-xs);
  background: var(--color-surface);
  font-family: var(--font-mono);
}
```

Four declarations, each load-bearing:

- `font-family` — the UA declares `code { font-family: monospace }`, and a *declaration* beats an
  inherited value whatever its origin. This is #623's exact argument for `.code-block__body code`, and
  measured: without this the computed family is the bare generic, not the token stack.
- `background` — AC1's "more than font family alone". `--color-surface` is the fill `.code-block` already
  uses, so inline and fenced code share one code surface; the ink stays inherited `--color-on-surface`,
  making the pair `.conversation`'s own base fill/ink combination. No new colour, no contrast question.
- `border-radius` / `padding-inline` — the chip. `--radius-xs` is the scale's smallest radius;
  `--space-1` its smallest step, and some horizontal padding is required or the fill clips the glyphs.

Seven omissions, each load-bearing rather than forgotten:

- **No `font-size`** and none of the rest of the quartet — Decision 2.
- **No `padding-block`.** Measured: `padding: var(--space-1)` grows the inline box to 22px inside a 20px
  line box, overlapping the neighbouring line (probe B, `sizeTokenPadBlock`). Vertical breathing room is
  the line-height's existing leading — a 16px content box in a 20px line box.
- **No `margin`.** #629 owns the nested rhythm; the ticket forbids one here.
- **No `white-space`, `overflow-wrap` or `word-break`.** AC4's risk is exactly a restatement here.
  `word-break: break-word` inherits from `.bubble` — #607's precedent, followed by #623, #628 and #629.
- **No `box-decoration-break`.** The default `slice` paints a wrapped run as one chip broken across lines:
  measured, the first fragment takes the 4px start padding and the last the 4px end, middles unpadded.
  `clone` would repeat both on every fragment, adding width inside the measure AC4 protects.
- **No `color`** — inherited; AC5 forbids a new colour.
- **No `display`/`vertical-align`** — the inline box is the construct; anything else changes what wraps.

Nothing reaches the user bubble or `.bubble--thinking` / `.bubble--stall` / `.bubble--api-retry` /
`.bubble--compacting`: `.bubble__markdown` has exactly one call site and it is the settled-assistant branch
only. This is the modifier discipline #607 established, and it is structural, not "inert because we read
the four literals".

No state, no async, no error path — this is a stylesheet rule. Failure modes are visual and are covered by
the tiers below.

## Testing strategy

**Unit (`npm test`) — no new tests.** AC3's markup half is already green in
`AssistantMarkdown.test.tsx:44-51, 151-167` (both fence shapes) and the attribute-free `<code>` assertions
there and in `ConversationScreen.test.tsx:466` mechanically enforce CSS-only: adding a `className` to
inline code fails 3 assertions across 2 specs. Renderer tests are server-render only, so nothing computed
can live here.

**e2e (`e2e/assistant-whitespace.spec.ts`) — extend the fixture in place, add two tests.**

Fixture: add inline code to *existing* `RHYTHM_TEXT` lines — no new turn (indices are positional), no new
block. Cover the paragraph, the `## Beta heading`, `- Gamma item`, the `> Delta` quote, and an `<em>`- and
a `<strong>`-nested case, plus one long unbroken token for AC4. Invariants that must not move:
`RHYTHM_BLOCK_COUNT` 5, `RHYTHM_QUOTE_CHILD_COUNT` 4, `RHYTHM_LOOSE_ITEM_CHILD_COUNTS` [2,2],
`RHYTHM_LIST_COUNT` 4, and exactly one `<h2>` (`readHeadingTypeMetrics` goes strict-mode ambiguous
otherwise). Inline content adds no block, so none of them move. Add a `RHYTHM_INLINE_CODE_COUNT` vacuity
guard in the `readNestedRhythmMetrics` child-count idiom, and extend the fixture's comment block with why
the counts hold.

Two mechanical traps, both turn-burners:
- The fixture's lines are **single-quoted** strings, so markdown backticks need no escaping. For the long
  token, concatenate (`'… with `' + LONG_TOKEN_TEXT + '` inline.'`) rather than switching the line to a
  template literal, where every backtick would need escaping.
- **Do not add a second fence to the `CODE` bubble.** `readCodeMetrics` resolves `.bubble__markdown pre`
  as a single locator and would throw a strict-mode violation.

*Test 1 — inline code is typed and filled as code, at its container's own step.* One reader over the
RHYTHM bubble returning, per inline `<code>`, its measured values **beside the tokens read off the same
element** (`readHeadingTypeMetrics` idiom):
- entry count equals `RHYTHM_INLINE_CODE_COUNT` (vacuity guard) and the ancestor tags cover `p`, `h2`,
  `li`, `blockquote`, `em`, `strong` — AC2's container set, one rule, no override.
- computed `fontFamily` equals the `--font-mono` token. **Spellings differ**: computed serialises with
  double quotes, the token source uses single quotes and a leading space. Normalise both (`.trim()` plus
  `"` → `'`) — the `normal`/`0px` normaliser #628 wrote for tracking, same reason.
- computed `backgroundColor` equals the `.code-block` element's — the same token resolved by the browser,
  so no hex/rgb conversion and the assertion states the intent (one code surface). Reach it from the same
  evaluate via the thread; throw if absent.
- `borderTopLeftRadius` equals `--radius-xs`, `paddingLeft` and `paddingRight` equal `--space-1` (these
  three compare as literal-identical strings; measured).
- computed `fontSize` equals the nearest **block** ancestor's (walk up while `display === 'inline'`) — the
  no-per-context-override property. Then specifically: the `<p>` case equals `--text-body-medium-size` and
  the `<h2>` case equals `--text-title-large-size`. This is AC1's "size taken from the type scale", proved
  in two different steps.
- computed `whiteSpace` is `normal` and `wordBreak` is `break-word` — AC4's non-regression guard, pinning
  that nothing here re-declared them.

*Test 2 — nothing reaches a fenced block's contents (AC3).* Read the `<code>` inside `.code-block__body`
in the `CODE` bubble: `backgroundColor` is `rgba(0, 0, 0, 0)`, `borderTopLeftRadius` and `paddingLeft` are
`0px`, `fontSize` equals `--text-body-small-size`, `fontFamily` equals the `--font-mono` token (still
#623's rule). The fixture's fence is the **languageless** one, which is the strictly harder case: the
selector names no attribute, so a `language-*` class cannot change whether it matches, and the languageless
`<code>` is the one attribute-identical to an inline one. A languaged fence is covered at the markup tier.

**Required manual check before opening the PR** — an exclusion test that passes vacuously is exactly this
ticket's failure mode. Temporarily delete `:not(.code-block__body code)` from the selector, run test 2,
confirm it goes **red**, restore. State the result in the PR body.

*AC4* also stays covered by the existing thread-width assertion; assert the long inline token produced more
than one client rect (it wrapped) alongside `readThreadWidths` staying equal. Measured with the rule
applied at 1200 / 640 / 420 / 320 px: `scrollWidth === clientWidth` at every width, the token wrapping to
3 / 5 / 7 / 9 fragments, every fragment inside the bubble's right edge.

## Probe evidence

Measured in `chromium_headless_shell-1208` — the cached build the e2e suite drives, so these are the
numbers the tests below will see. The app itself ships Electron 33 (Chromium 130), an *earlier* build:
worth naming rather than glossing, though nothing here sits near a feature boundary (complex-`:not()`
arguments have been supported since Chromium 88). Run against the real `index.css` + `conversation.css` at
`ac34e35` and the production DOM shape. Not committed — a one-off, in the scratchpad.

- **A. baseline** — inline `<code>`: `14px`, family `monospace` (bare generic), background
  `rgba(0,0,0,0)`, radius `0px`, padding `0px`. In an `<h1>`: `24px`. The Blink monospace-rescale quirk
  does **not** fire (an ancestor's absolute size suppresses it), so no size declaration is needed to
  defeat a quirk — the family declaration is the load-bearing one.
- **B. variants** — `noSize` and `font-size: inherit` compute identically and leave every block height and
  the bubble height byte-identical to baseline (`[20,33,20,20,20,20,80,75,42]`, 418px). `body-small`
  perturbs every block by 1px and the `<h1>` block by 4px (33 → 37). `padding: var(--space-1)` yields a
  22px inline box in a 20px line box. The container's `gap` stays 8px in every variant, so #629's rhythm
  assertions cannot fire.
- **C. exclusion** — both selector forms leave the languaged and the languageless fence at transparent /
  `0px` / `0px` / `12px` / Roboto Mono stack, i.e. exactly as #623 left them.
- **D. scaling** — inline `fontSize` equals its container's in both a `<p>` (`14px` =
  `--text-body-medium-size`) and an `<h1>` (`24px` = `--text-headline-small-size`).
- **E. fonts** — `document.fonts.check()` returns `true` for a nonsense family and is useless here.
  By advance/x-height, `--font-mono` resolves to the generic default (x-height 6.32px at 14px) and
  `--font-sans` to `system-ui` (7.37px); `Menlo` measures 7.66px on the same machine.

## Open questions

- **Wrapped-chip appearance.** `slice` is specified above on measured grounds (no added width). If the
  broken chip reads badly against a real reply once shipped, `-webkit-box-decoration-break: clone` is the
  one-line change — but it needs a visual judgement this repo has no tooling for (`e2e/` carries no
  screenshot or visual-regression tooling), so it is deliberately not pre-emptively added.
- **`--radius-xs` is 6px on a ~16px-tall chip**, which is the roundest the scale allows at this size. It
  is the smallest radius token, so there is no alternative that stays within AC5; flagging it as the one
  value derived from scale-floor rather than from a mock.
