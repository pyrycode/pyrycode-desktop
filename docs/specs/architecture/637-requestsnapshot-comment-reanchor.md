## Context

`requestSnapshot` was the desktop's outbound "photograph claude's terminal" verb. The terminal was
deleted upstream (pyrycode#1348), and #620 removed the client half: the command, guard, dispatch case,
connection method, `requestSnapshotEnvelope.ts`, and the `request_snapshot` wire type.

It was also the transport module's most-cited precedent. Twenty-three comments in files #620 never
opened introduce themselves by kinship or contrast with it. Those comments document **live** siblings
and carry real design rationale — deleting them wholesale strips that rationale off a dozen healthy
call sites; leaving them names a symbol that no longer exists. They carry no compile dependency on
the removal, which is why they are their own slice rather than riding #620's nine-file atomic deletion.

The work is prose, not code. **Zero production lines change**, and AC5 requires that be proved
mechanically rather than asserted.

### Why `buildSendMessage`, settled

Two independent constraints select it, and both were checked:

1. **Shape.** Decision A's sentence asserts an `(id, ts, payload)` signature.
   `buildSendMessage(input: SendMessageInput)` has exactly that (`sendMessageEnvelope.ts:19-26`).
   `buildClientHello` does **not** — it takes a `ClientHelloInput` and constructs its payload
   internally via `makeHelloClientPayload` (`helloExchange.ts:51-57`). Anchoring A on `buildClientHello`
   would make the shape claim false. The body left this open; it is now closed.
2. **No citation cycle.** `buildCreateConversation`, `buildDequeueMessage`, `buildModalResolution` and
   `buildSetSessionSettings` all live in citing files, so anchoring on them makes those files cite
   themselves — the cycle #620 hit. `sendMessageEnvelope.ts` has **zero** hits in the sweep.

`sendMessageEnvelope.ts:16-17` anchors its *own* purity sentence on `buildClientHello`. That is a
chain (`X → buildSendMessage → buildClientHello`), not a cycle, and it is the arrangement
`requestDebugBundleEnvelope.ts` already ships. Leave it as is.

### Decision E — the selector contrast

`requestSessionSettingsEnvelope.ts:6-8` currently reads "It is the BARE control frame, NOT the
payload-carrying `requestSnapshotEnvelope`: the daemon's reply is daemon-wide, so there is no
`conversation_id` or any other field a client could use to select another session's data."

The contrast turns on a **selector**, not on payload-carrying-ness in general. **Do not use
`createConversationEnvelope`** — `CreateConversationPayload` has no `conversation_id` (it *creates* the
conversation, so no id exists yet), which is why the body's earlier draft recommendation was withdrawn.

`sendMessageEnvelope` qualifies: `SendMessagePayload.conversation_id` at `types.ts:166`.
`requestDebugBundleEnvelope.ts:5-7` already makes this identical argument against `buildSendMessage`
("no payload struct, no conversation_id, no session-selecting field") — follow that phrasing.

The second sentence at `:8` ("That also means it cannot be rejected with `conversation.not_found`")
does **not** match the grep and is not a sweep site — but see decision H before deciding whether to
leave it. Leaving it untouched is acceptable and is the default.

### Decision H — the site with no valid re-anchor (MEASURED)

`requestSessionSettingsEnvelope.test.ts:27-28`: "…the request would also become rejectable with
`conversation.not_found` — which this verb, unlike `request_snapshot`, must never be."

**`conversation.not_found` is attested nowhere in this repository as a live rejection code.**
A tree-wide sweep (`grep -rniE 'conversation[._]not_found' src/ e2e/`) returns exactly four hits, all
of them comments: `requestSessionSettingsEnvelope.ts:8`, `requestSessionSettingsEnvelope.test.ts:27`,
`runConfigSnapshot.ts:49`, and `runConfigSnapshot.test.ts:101`. The only rejection code the desktop
actually knows as a literal is **`session.not_found`** (`daemonConnection.ts:300`, `:1476`,
`inboundMessage.test.ts:543`).

The fourth hit settles *why* no survivor qualifies. `runConfigSnapshot.test.ts:100-101` narrates the
**removed** route — "The old route asked for a screen snapshot, which the daemon validated against a
conversation and rejected as `conversation_not_found` for an unknown one." The
`conversation_not_found`-rejectable property belonged to `request_snapshot` itself. Deleting the verb
deleted the only thing the sentence could have pointed at, so there is nothing to re-anchor onto by
construction — not merely nothing convenient.

Worse: `daemonConnection.ts:1476` documents that `archiveConversation`'s empty/unknown
**`conversation_id`** is rejected with **`session.not_found`**. So even the most natural-looking
candidate contradicts the claim rather than supporting it.

**Therefore: no survivor is demonstrably rejectable with `conversation.not_found`, and swapping any
name into this sentence would assert a security property the codebase contradicts.** Take AC4's
explicit escape — **state the shape directly** and drop the comparative. The surviving claim is the
one the test actually asserts (`expect(Object.keys(envelope.payload)).toHaveLength(0)`): this verb
carries no selector, so there is no id for the daemon to fail to resolve. Preserve the "no
attacker-controlled field selects another session's data" argument intact; only the dangling
`unlike request_snapshot` clause goes.

This is the one site where a mechanical name swap silently injects a false security claim. It is why
the ticket is `security-sensitive`.

### Decision I — a comparative against a deleted route

`runConfigSnapshot.ts:48-50`: "Bare — no conversation id — because the reply is daemon-wide, so unlike
the old `requestSnapshot` route there is no id to validate and no `conversation_not_found` to fire into."

The contrast is with a route that no longer exists in any form, so there is nothing to re-anchor onto
— the ticket's "delete rather than re-anchor" ground (#618's precedent). Drop the `unlike the old
requestSnapshot route` clause and keep the positive claim, which stands on its own and still explains
why `requestRunConfigSnapshot` takes no argument. The `conversation_not_found` phrase in the same
sentence is not a grep hit; dropping it alongside the clause is natural but not required.

### Decision J — the actively false claim

`e2e/run-config-settings.spec.ts:192` says mounting `RunConfigData` sends `request_snapshot`. False
since #491/#500 — the sheet reads its own dedicated run-configuration reply, which the same spec
asserts 13 lines later (`:205`, "exactly one bare read request went out") and which
`runConfigSnapshot.ts:46` states outright ("Fire exactly one `requestSessionSettings` (#491)"). Read
literally it suggests the snapshot removal breaks the settings sheet — the bug #500 just fixed.
Replace with `request_session_settings`.

**Out of scope, do not touch:** `:193`'s loose "snapshot arrival" wording and `:199`'s "the app asked
for a screen snapshot". `:199` is accurate narration of the parent commit's bug and is worth keeping.
Neither matches the AC1 grep, so neither blocks it.

### Known friction: slash-list drops need re-wrapping

#620 measured this: a pure **drop** from a slash-list wrecks the line wrap (8 of 11 sites needed a
hand re-wrap — more edits than the deletion itself), whereas a name **swap** reflows free. Decision D's
three drops will each need the comment block re-wrapped to the file's ~100-col width. Budget for it;
it is the least mechanical part of an otherwise mechanical sweep. Re-wrapping is still comment-only
and does not endanger AC5.

## Verification

Four instruments, in order. The first three are cheap; run them before the e2e spec.

1. **AC1 — the boundary sweep.** Must return zero lines:
   ```
   grep -rniE 'requestsnapshot|request_snapshot' src/ e2e/ | grep -v '^src/shared/ipc/commands.test.ts:'
   ```
   Case-insensitivity is load-bearing: `buildRequestSnapshot` (capital R) is **13 of the 24 hits**, in
   four files the original ticket table never listed. A case-sensitive sweep goes green while leaving
   more dangling references than it removed. **Re-run this as the actual boundary — do not trust the
   table above**; #618 shipped a re-anchor site its own body had not listed.
2. **AC2 — the allowlisted file is untouched.** `git diff --stat main -- src/shared/ipc/commands.test.ts`
   must be empty.
3. **AC5 — the comment-stripped diff.** Strip `//` line comments, `/* */` blocks and leading ` * `
   lines from every changed file at both `main` and `HEAD`, then diff the residue. **An empty residue
   *is* the proof** that no executable line moved. This is the primary instrument of the whole ticket
   and it cannot be substituted:
   - `npm run typecheck` cannot see it — `noUnusedLocals` is off in this repo, so an edit that orphans
     an import still compiles clean.
   - `npm run build` cannot see it either — every guard in the touched files returns `boolean`, so a
     mangled guard body still typechecks. This check is what discharges the security review's "no
     guard body was edited" obligation.
4. **The e2e spec must actually be run.** `e2e/` sits outside **both** tsconfigs, so
   `npm run typecheck` never sees `run-config-settings.spec.ts`. A green unit suite and a green build
   prove nothing about decision J's file. Run `e2e/run-config-settings.spec.ts` directly.

**Testing strategy: no new tests.** This ticket adds no test cases and changes no assertion. The
existing unit suite plus `npm run build` prove nothing regressed; instruments 1–3 prove the change is
comment-only; instrument 4 proves the one e2e file still passes. Any urge to add a test here means
a code line is being changed — which belongs in a different ticket (see Constraints).

## Constraints

- **No behaviour changes.** If a fix looks like it needs a code line, it belongs in a different ticket.
- **Do not touch the daemon's `request_snapshot` verb.** It stays in the protocol; only the desktop
  client's use of it is gone. This sweep covers `src/` and `e2e/` only.
- **Prefer re-anchoring; delete only when there is genuinely nothing left to point at** (decisions H
  and I). Say which sites were deleted rather than re-anchored in the PR body.
- Direction words — `above` / `below` / `sibling` / `thinner` — are checked **independently of the
  name** (AC3). A swap that keeps a direction word true of the old target but false of the new one
  fails the AC even though the name is live.

## Scope note — the §4 five-production-file gate

This spec prescribes modified content in **7 production files**
(`dequeueMessageEnvelope.ts`, `listConversationsEnvelope.ts`, `requestSessionSettingsEnvelope.ts`,
`modalResolutionEnvelope.ts`, `setSessionSettingsEnvelope.ts`, `createConversationEnvelope.ts`,
`runConfigSnapshot.ts`), which trips the architect's ≥5-production-file gate. **Recorded as a
deliberate, measured false positive**, joining the irreducible-S precedents (#492 at 7 files, #381 at
~10):

- **The production-code delta is exactly zero lines, and AC5 proves it mechanically.** The gate is a
  proxy for production-code volume and cross-file coordination cost; here the comment-stripped diff
  is required to be empty, so the quantity the gate measures is provably nil. Nothing in the diff
  compiles against anything else in it.
- **The deliverable is not divisible.** It is defined as one tree-wide grep reaching zero. A child
  fixing 4 of 13 files cannot assert AC1, AC2 **or** AC5 — all three are tree-wide — so the second
  child would carry the entire verification burden while the first ships unverifiable.
- **Splitting is actively harmful.** Decision A spans 9 sites in 6 files; split across two children,
  each would choose an anchor independently and could land two different precedents in one module —
  the exact inconsistency this ticket exists to repair.
- **Turn budget is bounded.** 23 single-line comment edits with zero compile coupling, so a bad edit
  cannot cascade into a build-failure loop (the mechanism that burned #75's 26-call-site cascade).
  All 8 decisions are pre-made and verified above, so the developer applies rather than judges.

Flagging for code review rather than hiding it: if the reviewer disagrees, the correct remedy is a
split of the *follow-up*, not a mid-flight split of a tree-wide grep AC.

## Open questions

- **Decision D's three drops vs swaps.** The spec prescribes a plain drop where a live sibling
  remains, because that is the minimal edit. If a re-wrap turns out uglier than expected on a given
  line, swapping the dead name for another live sibling (e.g. `dequeueMessageEnvelope.ts`) instead of
  dropping it reflows free and is equally correct — developer's judgment, no AC turns on it.
- **The `conversation*not_found` vocabulary is out of AC scope.** None of the four mentions is a grep
  hit. `runConfigSnapshot.test.ts:100-101` is accurate historical narration of the removed route —
  the same class as `e2e/run-config-settings.spec.ts:199`, and worth keeping for the same reason.
  `requestSessionSettingsEnvelope.ts:8` states a live claim whose code the desktop never uses as a
  literal. A follow-up could reconcile the vocabulary against the daemon's actual codes, but that
  needs daemon-side source; this ticket is comment-only within the desktop tree. **Leave all four
  as-is except where decisions H and I already touch them.**
