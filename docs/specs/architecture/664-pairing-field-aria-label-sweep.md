## Context

Six sites identify the pairing screen by markup that #665 is about to change: three pin the field to a `<textarea>` (the desktop Pair frame `103-2901` draws an M3 *filled* field, i.e. an `<input>`), and three use the `Paste pairing code` card heading as the "we are on the pairing screen" marker (the new hero holds only the field; the heading goes away). The accessible name `aria-label="Pairing code"` survives both changes and already sits directly on the element (`PairingScreen.tsx:96`), so re-pointing at it is green on `main` *before* any visual work exists and green after.

None of these breakages are compile-enforced: `e2e/` sits outside both tsconfigs, so `npm run typecheck` never type-checks a spec, and the two unit markers are plain string matches against `renderToStaticMarkup` output. A bare `playwright test` additionally skips every `real-*` spec. Bundling this into #665 means a partly-updated cascade reports green while proving nothing.

## Design

### The selector contract

One string replaces all three shapes. Everything below is a consequence of it.

| Layer | Target |
|---|---|
| e2e locator | `page.locator('[aria-label="Pairing code"]')` |
| unit marker | `'aria-label="Pairing code"'` |

Two properties make this the right anchor, both verified against `main`:

1. **Unique in the entire renderer.** `grep -rn 'aria-label="Pairing code"' src/` returns exactly one hit — `PairingScreen.tsx:96`. No other screen, route, or component carries that label, so every `toContain` / `not.toContain` / `toHaveCount` assertion below stays honest without further disambiguation.
2. **Element-agnostic and heading-agnostic.** It survives `<textarea>` → `<input>` and survives the heading's removal, which is the whole point.

**`getByLabel` is prohibited** (AC2). It appears zero times in `e2e/` today — verified — and it resolves by *accessible name*, so once #665's filled field wraps the input in a `<label>`, it matches both the label and the control and reintroduces exactly the count ambiguity this ticket removes. The attribute-selector idiom is already established at `pairingArrival.ts:63` (`[aria-label="Server key fingerprint"]`) and `real-daemon-session-settings.spec.ts:85` (`[aria-label="Current model"]`). Use it.

### Non-vacuity is structural, not just a one-off check

AC4 asks for an inversion on `unpair-repair.spec.ts:52`. That check is worth running, but on its own it is **weak evidence**: inverting `toHaveCount(0)` to `toHaveCount(1)` fails under a *stale* locator exactly as it fails under a live one, since both yield count 0 on the thread. It proves the assertion executes and the selector parses; it does not by itself discriminate stale from live.

What actually makes the count-0 non-vacuous is that **the same binding is asserted positively later in the same test**:

- `unpair-repair.spec.ts`: `pairingBox` is asserted `toHaveCount(0)` at `:52` and `toBeVisible()` at `:59`. A stale locator fails at `:59`. One binding, both directions.
- `App.test.tsx`: `PAIRING_MARKER` is `not.toContain` at `:56` and `:110` but `toContain` at `:81`. Same property — the positive at `:81` is what keeps the two negatives honest. **This file carries the identical trap and the ticket does not mention it.**
- `PairedShell.test.tsx`: only a positive usage at `:106`. Self-proving; no trap.
- `pairingArrival.ts`: `toBeVisible()` only. Self-proving.

**Therefore, a hard constraint on the edit:** each file must keep **one** shared binding per marker — the `pairingBox` const, the `PAIRING_MARKER` const. Do not inline the selector at the positive site, and do not introduce a second const for the visible/`toContain` half. Two independently-typed strings that happen to agree today can silently diverge under #665, and the moment they do, the negative half goes vacuous again — the exact failure this ticket exists to eliminate.

Run AC4's inversion as specified and record it; the shared-binding property is what the PR should claim as the actual guarantee.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings — not applicable by construction. This ticket adds no data path. Every edit is a test-side *selector* or *marker* string; no value crosses `contextBridge`, no `ipcMain` channel is added or altered, and no production module is touched (AC5). The one boundary in view, `PairingScreen.tsx:96`, is read-only here.

- **[Tokens, secrets, credentials]** No findings, and this is the category that earned the label. `pairingArrival.ts` is the single chokepoint every pairing payload now flows through (#661), and its INVARIANT 2 (`:23`) is the contract: `payload` is filled into the field and referenced nowhere else — never asserted on (no `toHaveValue(payload)`, whose failure diff would print it), never interpolated into an assertion message or `test.step` title, never logged or attached to the report. **The edit at `:23` rewords that invariant's prose and must not weaken it.** The reviewable property, unchanged by this ticket: every assertion reads DOM visibility / enabled-state / count only, so Playwright's own timeout message names the selector and the timeout, never the filled value. The new selector `[aria-label="Pairing code"]` is a static attribute string containing no secret-derived data, so it is safe in a failure diagnostic — which is exactly what a locator string becomes on timeout.

- **[Error messages, logs, telemetry]** No findings — but this is where a regression would land, so it is the explicit review target. The sweep must add **no** new failure message, custom assertion message, `console` call, `test.step` title, or locator description. Re-pointing a locator inside `pairingArrival.ts` and `unpair-repair.spec.ts` is precisely the edit during which a developer might add "helpful" diagnostics that echo the bearer token. The shared-binding rule in § *Non-vacuity* reinforces this: it forbids introducing new inline selector strings, which is the most likely vector for an ad-hoc message. `unpair-repair.spec.ts:24-27` carries the suite's secret-hygiene contract verbatim ("no failure diagnostic serialises a token, key, pairing payload, or close reason") — that comment block is **not** in the edit surface and must survive byte-unchanged.

- **[File / storage operations]** Not applicable — no filesystem path is constructed, read, or written. No `fs` call is added.

- **[Inter-process / Electron attack surface]** Not applicable — no `webPreferences`, no IPC channel, no `contextBridge` surface, no protocol handler, and no navigation guard is added or modified. `AppView` and `PairedShellView` are rendered through `renderToStaticMarkup` in the unit tests, which mounts no window.

- **[Cryptographic primitives]** Not applicable — no RNG, no key material, no Noise handshake code is in the edit surface. The fake stack's synthetic token and fake static key live inside `launchPairedApp`, which this ticket does not touch.

- **[Network & I/O]** Not applicable — no socket, no relay URL parsing, no timeout or frame-size policy is in scope. `pairingArrival.ts`'s INVARIANT 3 (the step ends at Confirm; it introduces no wait and no timeout override) is unchanged by a locator swap and must stay that way.

- **[Concurrency]** No findings. One thing to preserve deliberately: `pairingArrival.ts:54-57`'s comment explains that the `pasteBox` visibility wait is *load-bearing* after #662 — it is the only executable proof that the welcome CTA landed on the pairing screen, across all ten drives. Re-pointing the locator keeps that wait; **deleting it as "redundant" would remove #662's sole liveness proof.** Keep the `toBeVisible()` at `:57`.

- **[Threat model alignment]** Out of scope by design, correctly. Malicious relay, token theft from disk, hostile daemon response, and renderer compromise are all unaffected — this ticket changes no production code and no runtime behaviour. The single security-relevant property in play is test-diagnostic secret hygiene, covered above.
