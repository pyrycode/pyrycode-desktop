## Context

The wire's `turn_state` frame carries `conversation_id` on every occurrence, the decoder already requires it, and the transport then deliberately discards it on the stated assumption that exactly one conversation is active. The desktop sidebar retires that assumption: a chat must keep working while the operator looks at another one, and the list must show each chat's state (operator ruling, 2026-08-21). Phase is the first of those facts.

This slice moves the id one layer — from the decoded payload onto the IPC event — and stops. No behaviour changes anywhere a user can see. The consumers that will key off it are #674.

## Design

Two production edits. Nothing else in `src/` changes.

### 1. The IPC arm — `src/shared/ipc/events.ts:114`

The arm gains one required field:

```ts
| { type: 'turnState'; state: WireTurnState; conversationId: string }
```

Required, not optional. Field order follows `backgroundTaskStarted`'s precedent (payload fields first, id last is not a convention here — match what reads well beside `state`).

### 2. The emit — `src/main/daemonConnection.ts:609`

The fresh literal gains one named copy from the already-decoded payload:

```ts
emitDaemonEvent(sink, {
  type: 'turnState',
  state: inbound.turnState.state,
  conversationId: inbound.turnState.conversation_id
})
```

**By name, never `...inbound.turnState`.** This is the house idiom at every emit in the file (`assistant-delta` `:591-596`, `api-retry` `:628-632`) and is what stops a decoder that later grows a field from smuggling it across IPC. snake→camel at the boundary, as everywhere else.

The emit may stay one line or become a multi-line literal — the file has both shapes; pick whichever fits the line budget.

### 3. Where the id stops

`translateTimelineEvent` (`timelineBridge.ts:43-46`) keeps rebuilding a fresh `ThreadEvent` with named fields and keeps omitting the id. `ThreadEvent.turnState` (`threadTimeline.ts:123`) is untouched. The reducer is untouched.

This is not incidental — it is the seam the ticket exists to hold. Widening `ThreadEvent` would push a daemon-supplied routing key into a reducer with no consumer for it, and would drag in that reducer's 19-literal fixture set for no gain.

**The seam gets a free deterministic guard.** Once `timelineBridge.test.ts:53` gains the field, the existing assertion at `:55` (`expect(translated).toEqual({ type: 'turnState', state })`) proves the id stopped: vitest's `toEqual` fails on an extra own enumerable property, so a bridge that ever spread the event would turn that line red. No new test is needed for AC4's "the id stops at the bridge" — leaving `:55` alone *is* the test.

### ⚠️ The one hazard: `replace_all` inside `timelineBridge.test.ts`

The exact substring `{ type: 'turnState', state }` (shorthand) occurs **three** times in that file:

- `:53` — the `DaemonEvent` literal. **In scope.**
- `:55` — `expect(translated).toEqual(...)`, asserting the translated **`ThreadEvent`**. **Must not change.**
- `:484` — `bridge.emit(...)`. **In scope.**

A `replace_all` on that substring corrupts `:55` and silently destroys the exact separation this ticket exists to hold — and it would still be green, because a `ThreadEvent` with a stray extra key would then match a `toEqual` that also carries it. The *other* substring, `bridge.emit({ type: 'turnState', state: 'thinking' })`, occurs exactly twice in that file (`:494`, `:499`) and both are in scope, so `replace_all` is safe there. Same string appears in five other files at one site each.

What the rewritten prose must establish (write it in each file's own voice; these are the claims, not the wording):

Keep the security framing that currently rests on the drop: it must now rest on the field's *nature* (a routing key that reaches no sink) rather than on its absence.

## State + concurrency model

Unchanged. No new async work, no new subscription, no teardown surface. The field rides the existing `emitDaemonEvent` → `DAEMON_EVENT_CHANNEL` → preload pass-through → bridge path, which is synchronous per frame and already owned.

Adding a required field to an existing arm does not break exhaustive `switch` statements — they discriminate on `type`. No consumer code changes; only construction sites do.

## Error handling

No new failure mode. The decode is the only place that can fail and it is unchanged: `parseTurnStatePayload` (`inboundMessage.ts:575-585`) `requireString`s `conversation_id` today, so a missing or non-string value already throws `WireDecodeError` and drops the whole line without emitting. The reject test at `daemonConnection.test.ts:1442-1453` passes unchanged and is the proof.

The emit cannot fail on the new field: it reads an already-validated `string` off an already-narrowed payload.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings. The untrusted→trusted boundary is `parseTurnStatePayload` (`inboundMessage.ts:575-585`), a single named function that `requireString`s `conversation_id` and returns only the two known fields — unknown server keys are tolerated but not copied through. This ticket moves an *already-validated* value across the second boundary (main→renderer) and adds no new parse site. The copy is by name from a narrowed payload, never a spread, so a decoder that later grows a field cannot smuggle it across IPC. The renderer remains untrusted relative to main; nothing here flows renderer→main.
- **[Error messages, logs, telemetry]** No findings — and this is the category the retired doc comment's safety claim actually rested on, so it got the closest walk. Three sinks could in principle serialise the new field, and all three are closed: (a) `emitDaemonEvent` (`emitDaemonEvent.ts:25-46`) is log-free *by construction*, documented in its own header as a deliberate choice ("a console.log of the event would leak MessagePayload.text"); (b) `preload/index.ts:99-103` is a bare pass-through with no logging; (c) `timelineBridge.ts:18`, `daemonEventBridge.ts:13` and `modalBridge.ts:18` each `JSON.stringify(event)` into an `assertNever` Error message — but `turnState` is an explicitly handled case in all three (proved by `daemonEventBridge.test.ts:116` asserting `null`, not a throw), so that sink is a compile-time impossibility for this arm. The decoder's own no-echo discipline is unchanged: `parseTurnStatePayload`'s error names the failure category only and never interpolates `conversation_id`.
- **[Inter-process / Electron attack surface]** No findings. No new IPC channel, no new `contextBridge` API, no new `ipcMain` handler — the field rides the existing `DAEMON_EVENT_CHANNEL`, whose payload type is pinned to `DaemonEvent` at `emitDaemonEvent.ts:22`, so no non-event payload can reach it. Process placement is unchanged: keys, socket and Noise handshake stay in main. What crosses is one additional daemon-supplied string on an arm that already crosses.
- **[Threat model alignment — hostile daemon response]** No findings, and this is the one that matters most for a routing key. A hostile or impersonating daemon controls the value of `conversation_id` entirely. Within this ticket that buys nothing: no consumer reads the field. `translateTimelineEvent` (`timelineBridge.ts:43-46`) rebuilds a fresh `ThreadEvent` without it, and the existing `toEqual` at `timelineBridge.test.ts:55` becomes a deterministic guard that it stopped there. The value is never rendered as markup, never used as a filename, cache key, lookup path, or attribute/URL — it reaches no sink at all. **The real exposure is #674's**, where the id first becomes a lookup key into per-conversation state; a hostile or unknown id must be handled there as an explicit no-match, never as a fallback onto the active conversation. Named here as **OUT OF SCOPE, owned by #674** — and it is the reason this ticket refuses an optional field, since `?? activeConversation` is exactly the misattribution primitive a hostile id would want.
- **[Cryptographic primitives]** Not applicable — no randomness, no key material, no comparison against a secret, no change to the Noise session. The field is decoded from an already-authenticated, already-decrypted frame.
- **[Tokens, secrets, credentials]** Not applicable — `conversationId` is a daemon-asserted routing identifier, not a credential. It grants nothing, is not compared against anything, and is not persisted. No storage, rotation, or revocation surface is introduced.
- **[File / storage operations]** Not applicable — nothing here touches the filesystem. Notably, the field is never used as a path component or cache key anywhere in this slice, which is what keeps the path-traversal surface closed by construction rather than by check.
- **[Network & I/O]** Not applicable — no socket, URL, timeout, or frame-size decision changes. The frame already carried this field on every occurrence and was already size-capped upstream.
- **[Concurrency]** Not applicable — no async task, timer, listener, or cancellation surface is added. The emit is synchronous within the existing per-frame handler, and adding a field to a literal introduces no shared state and no check-then-act gap.
